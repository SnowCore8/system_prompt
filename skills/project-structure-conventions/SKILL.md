# 项目结构与模块化

项目结构是依赖关系的物理形态。目录放错，模块边界会消失；包边界不清，循环依赖会穿过工作区；公开面不受控，任何内部改动都会变成跨团队变更。本 skill 规定项目级目录、包与工作区、模块依赖图、公开面与结构门禁；逻辑边界与依赖方向由 `architecture-and-design-conventions` 裁定，文件与模块内部风格由 `code-style-conventions` 裁定。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。
   包管理器、构建工具、语言模块系统与托管平台的限制，均不可选。
2. 本 skill 的规则。
   目录、包与工作区、依赖图、公开面、生成与第三方目录以及结构门禁，以本文件为准。
3. 既有项目约定与事实。
   代理应当先阅读目录树、manifest、工作区配置、构建图、导入规则、CODEOWNERS 与 ADR；这些是事实输入，按本 skill 的规则处理。项目约定只在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

分工边界如下：

- 逻辑模块与组件边界、分层、依赖方向、循环与模块公开接口，由 `architecture-and-design-conventions` 裁定；本 skill 把已裁定的边界落到目录、包、工作区、导入/构建图与包导出/入口，并配置物理门禁。未裁定的，先回该 skill；与 architecture 的裁定冲突时，以该 skill 为准，物理落点按本 skill。
- 目录类别与默认形态由本 skill 定义；具体目录名依 `naming-conventions` 与项目事实，本 skill 不重命名现有目录。
- 文件与资源在模块内部的布局、格式化、依赖版本与锁文件、配置、错误与日志，由 `code-style-conventions` 管辖；本 skill 不决定 formatter、依赖版本或文件命名。
- 命名由 `naming-conventions` 管辖；API 契约与数据由 `api-and-data-conventions` 管辖；测试策略与门禁阈值由 `testing-and-quality-conventions` 管辖；
  必需文件、打包与发布由 `repository-governance-conventions` 与 `release-operations-conventions` 管辖。
- 强制规则冲突的，代理应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与所选约定，并记录于结构决策或 ADR。

## 流程

1. 读取项目事实。
   代理应当列出目录树、manifest、工作区配置、构建图、导入规则、CODEOWNERS、生成命令与 ADR；记录哪些目录是模块、包、应用、工具、生成物或第三方。
2. 选择项目形态。
   代理应当按“项目形态与目录决策表”选择单包、库、多包工作区或 monorepo；不得把不同形态的目录约定混用。
3. 把目录映射到模块与所有者。
   每个代码顶层目录应当对应一个模块或包，具有单一职责、明确所有者与公开面；`docs`、`tools`、`generated`、`vendor` 等非模块目录按用途单列，指定所有者与只读/生成规则；不得保留 `utils`、`common`、`misc` 等无边界目录。
4. 画依赖图。
   代理应当以模块与包为节点描绘物理导入与构建依赖；标记循环、反向依赖、跨层边、深层导入与未声明的包依赖。循环、反向与跨层的架构判定由 `architecture-and-design-conventions` 负责；本 skill 只阻断该 skill 判定为违规的物理边。
5. 定义公开面与内部可见性。
   每个包应当声明入口与导出；内部子路径应当不可被外部导入；共享代码应当有稳定契约与所有者，不得成为业务编排的垃圾桶。
6. 放置测试、文档、生成物与第三方代码。
   测试应当靠近模块或按模块镜像；跨模块测试只应经由公开面；生成物与第三方引入目录应当只读、可重生成，并排除于手工编辑与格式化之外。
7. 设置结构门禁。
   代理应当以导入检查、构建图、包导出、CI 与 CODEOWNERS 强制边界；例外应当有具名所有者、范围与到期条件。
8. 记录决策。
   结构决策应当写入 README、包说明或 ADR；改变边界时同步更新导入、测试、文档与所有者。

## 核心规则

- **目录必须表达模块边界。** 每个代码顶层目录对应一个模块或包；同一层不得同时按“功能”和“技术层”两套轴组织，共享层、基础设施层与入口层可按 `architecture-and-design-conventions` 的裁定单列。无边界目录会把不相关变更绑在一起。
- **物理依赖图必须符合 architecture 的裁定。** 依赖方向、循环、反向与跨层判定由 `architecture-and-design-conventions` 负责；本 skill 负责让目录、包、导入与构建图在物理上可检查，并阻断该 skill 已判定为违规的边。
  本规则指运行与构建依赖图；dev/test 依赖图按项目工具语义与 architecture 的裁定记录，不与运行图混同。先修边界，再继续功能。
- **包与工作区边界必须显式。** 有包/工作区概念时，每个包应当有 manifest、所有者、公开入口、测试与版本策略或私有标记；工作区根只做编排与共享配置，不得承载业务实现。
- **入口文件只做装配。** 入口解析参数、加载配置、构建依赖并调用应用；业务规则、查询与格式化逻辑不得放入入口。
- **公开面应当最小化。** 包通过导出或入口文件暴露稳定 API；内部子路径、内部类型与实现细节不得被外部深层导入；不得用全量 barrel 文件把内部结构重新导出。
- **共享代码必须有归属与稳定契约。** `shared`、`common` 或 kernel 仅承载稳定契约与通用机制；被两个模块使用的代码应当按 architecture 的裁定明确依赖方向，而不是把两边逻辑堆进共享目录。
- **生成与第三方引入目录只读。** 生成代码应当有生成命令、来源与所有者；第三方引入代码应当保留上游来源与补丁记录；两者都不得手工编辑，并应当排除于格式化与 lint 之外。
- **测试与文档位置固定。** 测试应当靠近模块或镜像模块目录；跨模块测试只应使用公开面；文档应当位于包或仓库的既定位置；构建产物与缓存不得进入源码树。
- **边界必须可执行。** 仅有目录约定而无导入检查、构建图或审查门禁的，边界会在一季度内失效；门禁失败信息应当指出违反的边与修复方式。
- **结构调整与行为变更分开。** 一次变更只应移动或重划一类边界；移动文件时同步更新导入、测试与文档，保持构建通过；大规模结构调整应当使用 `refactoring-conventions` 的安全手法。
- **结构决策必须可追溯。** 新增包、调整依赖边、引入共享层或放宽门禁，均应当记录理由、所有者与后续审查时点。

## 项目形态与目录决策表

表中目录名是默认形态；具体名称依 `naming-conventions` 与项目事实调整。

| 形态 | 目录约定 | 依赖与公开面 | 禁止 |
|---|---|---|---|
| 单包应用 | `src/<功能>` 或 `src/<层>`，只选一套轴 | 单一入口；内部目录不导出 | 功能与层混用；`utils` 垃圾桶 |
| 可复用库 | `src/`、`tests/`、`docs/`、`examples/` | 包入口导出公共 API；内部子路径不对外 | 依赖示例应用；把内部类型放入入口 |
| 多包工作区 | `apps/`、`packages/`、`tools/`；每包独立 manifest | 应用依赖包公开入口；根只编排 | 跨包相对路径；根承载业务代码 |
| Monorepo | `apps/`、`packages/`、`tools/`、`docs/` | 构建图与所有者矩阵；包入口导出 | 应用间互相导入；未声明的包依赖 |
| 生成与第三方 | `generated/`、`vendor/` | 生成命令与上游来源；只读 | 手工编辑；混入业务模块 |

## 依赖与模块边界

| 来源 | 允许 | 禁止 |
|---|---|---|
| 应用 | 依赖包的公开入口、共享契约 | 导入另一应用的内部；跨包相对路径 |
| 包 | 依赖更稳定的包或公开契约 | 反向依赖应用；循环依赖；深层导入 |
| 功能模块 | 依赖共享契约或公开 API | 导入另一功能的内部目录；共享可变状态 |
| 共享层 | 依赖稳定契约与通用机制 | 承载某一业务的编排；依赖应用或功能 |
| 测试 | 本模块内部与公开 API | 跨模块导入其他模块内部；复制实现 |

- 包导出应当使用 manifest 的 exports 或等价入口；内部子路径应当以命名或构建规则阻断。
- 构建图应当包含源码导入、路径别名、包导出与生成物；仅靠目录命名判断边界会漏掉别名与生成代码。
- 依赖声明应当与导入一致：应用和包只依赖 manifest 声明的包；开发依赖、peer 与可选依赖按用途声明，不得出现幽灵依赖。
- 跨模块的共享状态应当通过显式契约传递；不得以全局变量、隐式单例或共享可变文件绕过边界。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| `utils/`、`common/` 持续膨胀 | 无所有者、无公开面，任何模块都依赖它 | 按领域拆分，明确所有者与稳定契约 |
| 功能模块互相导入内部 | 形成环，任一改动牵动两侧 | 提取公开契约或反转依赖，禁止深层导入 |
| 上帝模块覆盖多个变更理由 | 审查与测试无法隔离 | 按变更理由拆分模块与包 |
| 全量 barrel 重导出内部 | 内部实现变成事实公开面 | 只导出稳定 API；内部路径阻断 |
| 根包承载业务实现 | 工作区边界失效，发布与测试无法独立 | 根只做编排与共享配置 |
| 生成代码被手工修改 | 下次生成覆盖改动，来源与差异不可追 | 修改生成源并重新生成 |
| 测试导入其他模块内部 | 边界被测试绕过，重构受限 | 跨模块测试改用公开 API |
| 路径别名隐藏深层导入 | 静态检查与构建图看不到真实依赖 | 别名与导入规则纳入同一门禁 |
| CODEOWNERS 与目录脱节 | 变更无人审查，边界漂移 | 目录调整时同步所有者映射 |

## 审查清单

- [ ] 已读取目录树、manifest、工作区配置、构建图与 CODEOWNERS。
- [ ] 每个顶层目录对应一个模块或包，具有单一职责与所有者。
- [ ] 依赖图无环、无反向边、无未声明的包依赖。
- [ ] 包有 manifest、公开入口、测试与版本策略；根只做编排。
- [ ] 公开面最小化；内部子路径不可被外部深层导入。
- [ ] 共享代码有稳定契约与所有者，未承载业务编排。
- [ ] 生成与第三方目录只读，具备生成命令与上游来源。
- [ ] 测试与文档位置符合约定；构建产物未进入源码树。
- [ ] 导入检查、构建图、CI 或 CODEOWNERS 已强制边界；例外有所有者与到期条件。
- [ ] 结构决策已记录，导入、测试、文档与所有者已同步。

## 示例

<example>
场景：新工作区包含 `apps/web`、`packages/ui` 与 `packages/core`。
问题：所有代码都从根目录相对导入，包边界不存在。
修复：`apps/web` 只依赖 `packages/ui` 与 `packages/core` 的公开入口；`packages/ui` 只依赖 `packages/core`；`packages/core` 不依赖应用。每个包有 manifest、导出与测试；CI 用导入检查阻断跨包相对路径。
</example>

<example>
场景：`features/orders` 与 `features/billing` 互相导入内部实现，形成循环依赖。
问题：两个功能无法独立测试，改动一侧会牵动另一侧。
修复：把共享的稳定契约提取到独立包或共享层，两个功能都依赖该公开契约；禁止导入对方内部目录；以导入检查阻断环，补充跨功能契约测试。
</example>

<example>
场景：`src/utils` 容纳格式化、鉴权、日期与数据库助手，所有模块都依赖它。
问题：目录无所有者，任何工具变更都可能影响全部模块。
修复：按领域拆分助手，归入对应模块的公开面；真正通用的稳定函数进入有所有者的共享包；删除 `utils`，更新导入并由 CODEOWNERS 指定各目录所有者。
</example>
