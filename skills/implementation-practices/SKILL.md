# 实现实践

构建阶段的失效很少因为“代码不会写”，而在于纪律：提交混杂无法回滚、增量不可运行无从评审、在制品无上限互相阻塞、修复与重构夹带、
调试靠猜、完成靠感觉。
本 skill 管辖 S3 构建的执行纪律：怎么把工作切成小步提交、怎么保证每一步可构建可测试、怎么控制并行数量、
怎么把修复与重构分开提交、缺陷怎么处理，以及怎么用 DoD 判定一个增量真的完成。
它把 G2 的计划变成可验证的增量，把 G4 需要的证据在构建中攒齐。
与相邻 skill 的分工：在制品上限与阻塞流程见 `project-lifecycle`，修复与重构的判定见 `refactoring`，
缺陷诊断流程见 `debugging`；本 skill 只写衔接要求并引用其规则。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制约束。诚实（HON）、变更（CHG）与不可逆（IRR）条款优先：未完成不得报完成，不得夹带无关改动，调试残留与生成产物不得进入提交（IRR-9）。
2. 本 skill 的规则。提交拆分、增量可运行与 DoD 检查的规则以本文件与 `references/` 为准；
   在制品上限、修复与重构判定、缺陷诊断的完整规则归上述三个 skill，本 skill 不复制，只引用。
3. 项目约定与事实。既有提交规范、构建命令与审查流程是事实输入，先阅读再实施；项目约定仅在本 skill 未规定时补充。

本 skill 管辖：小步提交与提交拆分、增量可运行，以及修复与重构分离提交、缺陷处理与 DoD 检查的构建纪律。
本 skill 不管辖：需求与验收标准（`requirements-engineering`）、模块边界与分层（`architecture-design`）、任务拆分与估算（`planning-estimation`），
以及测试策略（`testing-quality`）、代码风格（`code-style`）与提交协作流程（`vcs-collaboration`）。

## 生命周期定位

上游：G2 的任务清单、验收标准与设计。下游：G4 的验证证据与审查对象。
停止条件：增量不可运行、DoD 未完成、缺陷无法复现或出现未授权改动时停止申报完成，报告受阻项。

| 阶段 | 职责 | 产出与证据 |
|---|---|---|
| S2 设计 | 核对条目满足 DoR，明确增量目标与提交边界 | DoR 结论、增量切分 |
| S3 构建 | 以小步提交交付可运行增量，控制在制品，缺陷按 `debugging` 处理，执行 DoD 检查 | 提交记录、可运行增量、评审记录、DoD 结论、G3 证据 |
| S4 验证 | 提供提交与增量证据配合审查，修复失败项并回归 | 修复提交、回归证据、G4 证据 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 设计 | DoR 结论与增量切分：条目可判定、依赖就绪、提交边界明确 | Hold：条目未满足 DoR 不得进入 S3 |
| G3 构建 | 可运行增量、拆分提交记录、DoD 逐项结论、评审结论、无调试残留 | Recycle 到 S3：增量不可运行或 DoD 未完成 |
| G4 验证 | 修复提交与回归证据、失败项的修复结论 | Hold：证据缺失；Recycle 到 S3：验证未通过 |

## 核心规则

- 每次提交只承载一个逻辑单元。修复、重构与无关改动分开提交，审查者应能从小步 diff 理解行为变化。
- 每步可构建可测试。任一步完成时主干处于可运行状态；大变更拆成可独立验证与回滚的步骤。
- 在制品上限与阻塞项规则由 `project-lifecycle` 裁定，构建期间不得绕行上限。
- 修复与重构的判定由 `refactoring` 裁定。判定为重构的不得夹带行为变更，判定为修复的必须以测试证明该变化属于有意，两者分开提交。
- 缺陷处理依 `debugging`：先复现、再定位、后修复、必验证的顺序不可跳过，无法复现时不得提交猜测性改动。
- DoD 逐项核对。完成申报必须附逐项结论与证据，不得整表打勾，也不得把“代码写完”当作完成；DoD 条目清单由 `project-lifecycle` 裁定。
