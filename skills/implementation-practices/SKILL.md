# 实现实践

构建阶段的失效很少因为“代码不会写”，而在于纪律：提交混杂无法回滚、增量不可运行无从评审、在制品无上限互相阻塞、修复与重构夹带、调试靠猜、完成靠感觉。
本 skill 管辖 S3 构建的执行纪律：怎么把工作切成小步提交、怎么保证每一步可构建可测试、怎么控制并行数量、怎么区分修复与重构、怎么按“先复现、再定位、后修复、必验证”调试，以及怎么用 DoD 判定一个增量真的完成。
它把 G2 的计划变成可验证的增量，把 G4 需要的证据在构建中攒齐。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制约束。诚实（HON）与变更（CHG）条款优先：未完成不得报完成，不得夹带无关改动；调试残留不得进入提交。
2. 本 skill 的规则。提交拆分、增量可运行、在制品、修复与重构、调试与 DoD 的规则，以本文件与 `references/` 为准。
3. 项目约定与事实。既有提交规范、构建命令与审查流程是事实输入，先阅读再实施；项目约定仅在本 skill 未规定时补充。

本 skill 管辖：小步提交与拆分、增量可运行、在制品控制、修复与重构的区分、调试纪律、Definition of Done。
本 skill 不管辖：需求与验收标准（`requirements-engineering`）、模块边界与分层（`architecture-design`）、任务拆分与估算（`planning-estimation`），以及测试策略、代码风格与提交协作流程（对应专业 skill）。

## 生命周期定位

上游：G2 的任务清单、验收标准与设计。下游：G4 的验证证据与审查对象。停止条件：增量不可运行、DoD 未完成、调试无法复现或出现未授权改动时停止申报完成，报告受阻项。

| 阶段 | 职责 | 产出与证据 |
|---|---|---|
| S2 设计 | 核对条目满足 DoR，明确增量目标与提交边界 | DoR 结论、增量切分 |
| S3 构建 | 以小步提交交付可运行增量，控制在制品，执行调试纪律与 DoD 检查 | 提交记录、可运行增量、评审记录、DoD 结论、G3 证据 |
| S4 验证 | 提供提交与增量证据配合审查，修复失败项并回归 | 修复提交、回归证据、G4 证据 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 设计 | DoR 结论与增量切分：条目可判定、依赖就绪、提交边界明确 | Hold：条目未满足 DoR 不得进入 S3 |
| G3 构建 | 可运行增量、拆分提交记录、DoD 逐项结论、评审结论、无调试残留 | Recycle 到 S3：增量不可运行或 DoD 未完成 |
| G4 验证 | 修复提交与回归证据、失败项的修复结论 | Hold：证据缺失；Recycle 到 S3：验证未通过 |

## 核心规则

- 每次提交只承载一个逻辑单元。修复、重构与无关改动分开提交，审查者应能从小步 diff 理解行为变化。
- 每步可构建可测试。任一步完成时主干处于可运行状态；大变更拆成可独立验证与回滚的步骤。
- 在制品设上限。到达上限先完成、评审或清理，不启动新条目；排队不是进度。
- 修复与重构按外部行为区分。重构不改变行为，修复改变行为且必须用测试证明该变化属于有意。
- 调试四步不可跳过。先复现、再定位、后修复、必验证；无法复现时报“无法复现”，不得提交猜测性改动。
- DoD 逐项核对。完成申报必须附逐项结论与证据，不得整表打勾，也不得把“代码写完”当作完成。
