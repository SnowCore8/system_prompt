# 修复与重构的区分

## 1. 修复与重构的区分

修复与重构的判定标准（外部行为是否变更）与判定流程由 `refactoring` 管辖；修复的回归证明（修复前失败、修复后通过）由 `debugging` 要求；
本维度只规定两者在构建中的分离纪律。

- 判定先行。动手前按 `refactoring` 的判定流程确定这次改动是修复还是重构，再选提交类型。
- 修复必须可证明。修复提交附“修复前失败、修复后通过”的测试或可复现步骤（见 `debugging`）；证明不了的不得称修复。
- 分开提交。修复与重构分别提交，先修后重构或先重构后修由依赖决定，不得混在同一提交。
- 不夹带。重构不改变外部行为且既有测试保持通过；既有测试因重构而改动方可通过的，按 `refactoring` 的判定处理。

| 正例 | 反例 | 原因 |
|---|---|---|
| “重命名变量”单独一个 refactor 提交 | 修复缺陷时顺带重命名与格式化 | 后者无法分辨哪项改动修复了缺陷。 |
| 修复附失败转通过的测试 | 修复只改代码不加测试 | 后者无法证明缺陷曾经存在。 |
