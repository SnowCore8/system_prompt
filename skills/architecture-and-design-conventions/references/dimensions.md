# 架构与设计维度

本文件与 `SKILL.md` 配合使用。每一节规定一个架构维度的规则、边界情况与失败模式。项目已有架构、分层约定或 ADR
的，代理应当先阅读，并将其作为事实输入；本 skill 的规则优先，项目约定仅在本 skill 未规定时补充。本文件提供
默认值与理由。章节编号与 `SKILL.md` 中的维度索引对应。

## 1. 模块与组件边界

模块是系统中可独立理解与替换的单位，其边界决定一次改动所牵动的范围。边界划定正确的，改动限于一个模块之内；
划定错误的，任何改动均需跨模块协调。

- **一个模块一个变更理由。** 变更理由（change reason），指“这个模块会因为什么而变”，例如“支付方式变了”或
  “计费规则变了”。一个模块仅应有一个理由；判定标准：同一模块总是因两个不同理由而变化，即视为边界划定错
  误，应当将其拆分。反例：将用户资料、订单与计费塞入一个 `Account`
  模块，变更用户字段与变更计费规则均将牵动该模块。
- **高内聚：模块内的一切服务于同一理由。** 内聚衡量模块内部元素是否一起变化。功能内聚（一起完成同一事务）
  优于偶然内聚（凑于一个文件）。判据：模块内任意两个元素是否因同一理由而变；并非如此的，视为内聚不足。
- **低耦合：模块之间仅通过最小公共接口交互。** 耦合衡量一个模块的变化对另一模块的波及程度。应当优先采用数
  据耦合（仅传值）与接口耦合（仅依赖抽象），避免内容耦合（直接读取对方内部结构）与控制耦合（以参数指挥对方
  分支）。判据：变更一个模块的内部实现时，另一模块是否需要改动；需要改动的，视为耦合越界。
- **公共接口应当最小化。** 模块仅应暴露调用方实际需要的入口；内部类型、实体、存储细节与辅助函数不得越过边
  界。暴露愈少，可变面愈小，后续改动愈不易破坏调用方。
- **组件属于模块的一种，边界依职责而非文件规模划定。** 组件可以为包、服务或进程内子模块；划分标准为职责与
  依赖方向，而非行数。一个组件承载多个职责的，拆分较合并更接近正确。

| 正例 | 反例 | 原因 |
|---|---|---|
| `Billing` 模块仅含计价与开票 | `Account` 模块同时含资料、订单与计费 | 前者仅有一个理由，后者三个理由相互牵动。 |
| 模块间仅传 DTO 与抽象接口 | 模块间直接传 ORM 实体并读写对方表 | 后者属于内容耦合，迁移将波及两个模块。 |
| 仅暴露 `place_order` 一个入口 | 暴露全部内部函数供上层直接调用 | 暴露愈多，可变面愈大，改动愈易破坏调用方。 |

## 2. 分层与依赖方向

分层将变化的速率与稳定性分开：内层稳定、变化较慢，外层易变、变化较快。依赖方向决定变更约束的归属。

- **依赖不得由内层指向外层；同层允许但不得成环。** 分层（例如接口、领域、基础设施与表现）中，外层可以依
  赖内层，内层禁止依赖外层；同层依赖允许，但依赖图必须为有向无环图（DAG）。出现环或反向依赖的，应当于同一
  次变更中重构，不得以 ADR 豁免。代理应当以构建或静态分析工具校验（层依赖校验、循环依赖检测），使违反在
  合并前被捕获。
- **抽象属于内层，实现属于外层。** 依赖倒置：内层定义抽象（接口、协议），外层提供实现并依赖该抽象。内层因
  此不依赖任何易变的具体实现，可以独立演进与测试。落点为“内层依赖抽象，外层实现抽象”，而非“内层依赖外
  层”。
- **接口隔离。** 调用方不得依赖其不使用的方法。宽泛的上帝接口将使所有调用方受接口内任何变化的牵连；应当按
  调用方拆分为小而聚焦的接口，每个接口仅承载一组真实使用的方法。判据：去掉接口内任意一个方法，是否有调用
  方因此破坏；无调用方使用该方法的，视为接口过宽。
- **新代码遵守边界；存量越界以接缝逐步收紧。** 新模块应当自始置于正确的层；对已有越界依赖，代理应当先增设
  接缝（见第 5 节），矫正依赖方向，不得一次性重写整层。依赖方向的修复属于重构，手法由
  `refactoring-conventions` 管辖，目标结构由本文件裁定。
- **分层属于变化速率的排序，而非教条。** 仅当内层较外层稳定、变化更慢时，分层方有价值；对仅有一层且永
  不变化的系统强加四层的，属于过度设计（见第 6 节）。

| 正例 | 反例 | 原因 |
|---|---|---|
| 领域层定义 `PaymentGateway` 抽象，基础设施层实现该抽象 | 领域层直接 `import` 具体支付 SDK | 前者内层独立演进，后者内层受外层约束。 |
| 依赖图经校验器判定为 DAG | 模块 A 依赖 B，B 依赖 A | 环将使编译、测试与发布相互阻塞。 |
| 按调用方拆分为 `Reader` 与 `Writer` 两个接口 | 一个 `Repository` 接口含全部 20 个方法 | 调用方被迫依赖不使用的方法。 |

| 依赖方向 | 允许 | 说明 |
|---|---|---|
| 外层 → 内层 | 是 | 默认方向，外层消费内层抽象。 |
| 同层 → 同层 | 是 | 同层依赖允许，但不得成环。 |
| 内层 → 外层 | 否 | 违反依赖倒置，应当通过接缝反转。 |
| 环（A → B → A） | 否 | 必须拆分模块或抽取接口以打破。 |

## 3. 数据流与控制流

数据流回答“数据从何而来、由谁处理、流向何处”，控制流回答“谁调用谁、谁编排谁”。两者混合，将滋生副作用与
隐式状态。

- **数据流应当显式。** 数据应当通过参数与返回值在模块间传递，来源与去向应当可在签名中读出；不得依靠模块级
  或全局可变状态隐式传递。判据：仅阅读一个函数的签名，是否能够说出其接收与返回的内容；须翻遍全局变量方能补全
  的，视为数据流隐式。
- **控制流应当显式。** 编排关系（谁触发谁、谁依赖谁的结果）应当通过调用、回调或明确的事件在代码中可见；
  不得依靠隐式注册、反射或全局总线的隐式触发。事件与消息的投递契约由 `api-and-data-conventions` 管辖，本文件
  的职责为使编排关系可读。
- **数据流与控制流应当分开。** 一个模块可以仅处理数据（纯转换），或仅实施编排（调用其他模块），但职责应当
  分清；既转换数据又编排下游的模块，属于内聚不足的信号。
- **跨模块的数据传递应当通过契约，不得通过内部结构。** 模块间传递的应当为契约定义的值对象（契约内容由
  `api-and-data-conventions` 管辖），而非对方的内部实体或存储行。数据流穿越边界时，存储形状因此不会泄漏至
  另一侧。
- **副作用应当有明确归属。** 写操作、IO 与状态变更应当集中、可见、可定位；“某函数顺带变更他处状态”属于隐
  式数据流，属于缺陷，而非捷径。

| 正例 | 反例 | 原因 |
|---|---|---|
| `parse(raw) -> Order` 仅做转换 | `parse(raw)` 中顺带写缓存并发送通知 | 后者既转换又编排，且隐藏副作用。 |
| 数据经参数与返回值传递 | 数据存入模块级可变状态再被读取 | 后者数据流隐式，来源与去向难以追踪。 |
| 编排关系通过显式调用表达 | 依靠全局事件总线隐式触发 | 后者控制流不可读，难以静态校验。 |

## 4. 设计决策记录

ADR 将架构决策由“某人记忆中的默认”转为“仓库中的权威来源”，使下一次变更遵循该决定，而非重新争论。

- **ADR 的编写时机。** 新建或推翻架构决策时应当编写：采用或替换核心技术、划分或合并模块边界、变更分层或依
  赖方向、引入或移除抽象、确定数据流或控制流的主路径，以及任何影响后续变更走向的决定。修改已应用代码的行
  为、日常功能或纯风格选择的，不编写 ADR。
- **ADR 的内容。** 每篇 ADR 至少应当包含：背景（须解决的问题与约束）、决定（所选择的内容，以可判定的语言表
  述）、后果（带来的收益与代价，以及因此变贵的路径）、替代方案（被否定的选项及否定理由）。状态仅应书写当
  前为真的一项，不得追加历史。
- **一条决策一篇，按序号命名，已接受的 ADR 永不修改。** 决策变更的，应当编写新 ADR，并标注其取代的 ADR；修
  改旧 ADR 将使历史与现状分叉。文档归属与发布节奏由 `documentation-conventions` 裁定，本文件裁定内容口径与
  触发时机。
- **新决策或推翻决策必须有 ADR。** 未编写 ADR 的新决策或推翻决策不构成决策，将在下一次变更时被重新争论；
  模块文档可以记录由 ADR 派生的局部决定，但不得替代 ADR。

| 正例 | 反例 | 原因 |
|---|---|---|
| “支付网关用接口隔离，依赖倒置”写成 ADR | 该决定仅存在于某个 PR 的讨论中 | 讨论会过期，ADR 是可引用的权威来源。 |
| 新决策编写新 ADR，标注取代旧篇 | 直接改写旧 ADR 的“决定” | 改写将使历史与现状分叉。 |
| ADR 仅写当前为真的决定 | ADR 追加“某日改成了 X”的变更记录 | 变更记录将腐化；仅应陈述当前行为。 |

## 5. 可测试性设计

可测试性并非测试完成后补充的事项，而是由依赖方向与接缝设计出的属性。设计可测的模块，即设计可被替换与隔离
的模块。

- **接缝是依赖的可替换点。** 接缝指代码中可以不变更生产行为即替换某处依赖的位置（接口、函数参数、注入点）。
  显式接缝使测试能够隔离缓慢、不稳定或外部的依赖；无接缝的模块仅能够依靠全局状态或真实外部系统测试，测试脆
  弱且缓慢。
- **接口的抽取应当在测试之后。** 需要替换某依赖以便测试的，代理应当先编写暴露该需求的测试，再抽取满足该需
  求的最小接口；不得为假设的“以后可能替换”抽取接口（见第 6 节）。接口的形状因此由真实使用驱动，而非由想
  象驱动。
- **依赖注入属于接缝的一种，而非唯一形式。** 构造器注入、方法参数注入、工厂与配置点均属于接缝；应当选择最
  贴合语言与现有风格的接缝（风格由 `code-style-conventions` 管辖），本维度决定接缝的位置与可替换性。注入点
  应当少而清晰，不得在各处散落可选参数。
- **外部依赖始终置于接缝之后。** 网络、时钟、文件系统、随机源与第三方 SDK 属于测试中最需替换的依赖，均应当
  置于接缝之后；测试策略与门禁由 `testing-and-quality-conventions` 管辖，本文件负责将上述依赖设计为可替换。
- **可测试性与良好架构同向。** 依赖不由内层指向外层、接缝显式的模块，天然可测；需要大量 mock 方能测试的模块，通常
  属于边界划定错误或耦合过紧的信号。

| 正例 | 反例 | 原因 |
|---|---|---|
| 时钟通过参数或接口注入，测试可传固定时间 | 代码中直接 `new Date()`，测试依靠睡眠对齐 | 后者不可替换，测试脆弱且缓慢。 |
| 先写“替换日志实现”的测试，再抽接口 | 先抽 10 个方法的日志接口，无人使用 | 前者由真实使用驱动，后者是过度设计。 |
| 网络调用集中于接缝后，测试以桩替换 | 测试连接真实外部服务，依靠开关切换 | 后者没有接缝，测试依赖外部且不稳定。 |

## 6. 演进与简化

架构的演进方向为由具体至通用、由简单至必要，而非相反。为尚未出现的需求付出通用性成本的，属于过度设计。

- **实现应当先具体，后通用。** 默认应当编写具体实现，直接满足当前需求；仅在出现第二个真实使用场景时，方可
  引入抽象、参数化或泛型。抽象的形状应当由第二个场景“回填”，而非由第一个场景“预演”。
- **YAGNI：不得为尚无使用者的能力付出成本。** 不得实现“以后可能使用”的开关、插件点、泛型或配置项；上述
  内容无使用者，无法证明其效用，且增加维护面。判据：该能力当前是否存在真实调用方；不存在的，不得编写。
- **不得过度设计。** 分层、抽象与接缝的数量应当与系统的真实变化速率成正比。变化较多之处应当多留接缝，恒定
  之处应当直接写定；对永不变化的部分强加多层抽象，成本高且无回报。
- **先跑通，再演进。** 新模块应当先以最简单可用的形态落地并运行，以真实使用确认边界，再于出现第二个场景时
  演进；不得在编写第一行代码前设计全部未来形态。
- **移除未使用的抽象。** 抽象失去全部使用者（接口仅剩一个实现且无替换需求、开关永远关闭）的，应当删除，
  不得保留；未使用的抽象属于负担，而非资产。删除属于重构，手法由 `refactoring-conventions` 管辖。

| 正例 | 反例 | 原因 |
|---|---|---|
| 第二家支付方式接入时才抽 `PaymentGateway` 接口 | 初始即为“可能多家”抽全套抽象 | 前者由真实需求驱动，后者为想象付成本。 |
| 恒定不变的配置直接写定 | 为一个永不变化的开关增设插件点 | 没有变化的接缝属于纯负担。 |
| 抽象失去使用者后删除 | 仅实现过一次的接口永久保留 | 未使用的抽象增加维护面。 |
