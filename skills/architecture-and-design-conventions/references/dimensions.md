# 架构与设计维度

把本文件与 `SKILL.md` 一起使用。每个章节给出一个维度的规则、边界情况与失败模式。当项目已有架构、分层约定或 ADR
时，先阅读并应用更高优先级的规则；本文件提供默认值与理由。章节编号与 `SKILL.md` 中的维度索引对应。

## 1. 模块与组件边界

模块是系统里可独立理解与替换的单位，它的边界决定一次改动会牵动多大的区域。边界画对时，改动局限在一个模块内；
画错时，任何改动都要跨模块协调。

- **一个模块一个变更理由。** 变更理由（change reason）是「这个模块会因为什么而变」，例如「支付方式变了」或「计费规则
  变了」。一个模块只该有一个理由；当两个不同的理由总是迫使同一个模块同时变化，就把它们拆开。可判定：说出模块名，
  能补全「它因为……而变」且只有一个理由。反例：把用户资料、订单和计费塞进一个 `Account` 模块，改用户字段和改计费
  规则都会牵动它。
- **高内聚：一个模块里的一切服务于同一个理由。** 内聚衡量模块内部元素是否一起变化。功能内聚（一起完成同一件事）好
  于偶然内聚（凑在一个文件里）。判据：模块里的任意两个元素，是否因为同一个理由而变；不是，就说明内聚不足。
- **低耦合：模块之间只通过最小公共接口交互。** 耦合衡量一个模块的变化会多大程度波及另一个。优先数据耦合（只传值）
  与接口耦合（只依赖抽象），避免内容耦合（直接读对方内部结构）与控制耦合（用参数指挥对方分支）。判据：改一个模块
  的内部实现，另一个模块是否需要改动；需要，就说明耦合越界。
- **公共接口最小化。** 模块只暴露调用方真正需要的入口；内部类型、实体、存储细节与辅助函数不越过边界。暴露越少，可
  变面越小，后续改动越不会破坏调用方。
- **组件是模块的一种，边界按职责而非文件大小划分。** 组件可以是一个包、一个服务或一个进程内的子模块；划分标准是职责
  与依赖方向，而不是行数。一个组件承载多个职责时，拆开比合并更接近正确。

| 正例 | 反例 | 原因 |
|---|---|---|
| `Billing` 模块只含计价与开票 | `Account` 模块同时含资料、订单、计费 | 前者一个理由，后者三个理由互相牵动。 |
| 模块间只传 DTO 与抽象接口 | 模块间直接传 ORM 实体并读写对方表 | 后者是内容耦合，迁移会波及两个模块。 |
| 只暴露 `place_order` 一个入口 | 暴露全部内部函数供上层直接调用 | 暴露越多，可变面越大，改动越易破坏调用方。 |

## 2. 分层与依赖方向

分层把变化的速率与稳定性分开：内层稳定、变化慢，外层易变、变化快。依赖方向决定谁被谁绑架。

- **依赖只能从外层指向内层。** 分层（如接口/领域/基础设施/表现）里，外层可以依赖内层，内层禁止依赖外层。依赖图必须
  是有向无环图（DAG）；出现环或反向依赖时，在同一次变更中重构，而不是把它记录为例外。用构建或静态分析工具校验
  （层依赖校验、循环依赖检测），让违反在合并前被捕获。
- **抽象属于内层，实现属于外层。** 依赖倒置：内层定义抽象（接口、协议），外层提供实现并依赖这个抽象。这样内层不依赖
  任何易变的具体实现，可以独立演进与测试。落点是「内层依赖抽象，外层实现抽象」，而不是「内层依赖外层」。
- **接口隔离。** 调用方不依赖它用不到的方法。一个宽泛的上帝接口会让所有调用方被接口里任何一处变化牵连；按调用方拆
  成小而聚焦的接口，每个接口只承载一组真实使用的方法。判据：去掉接口里任意一个方法，是否有一个调用方会破坏；没有
  调用方使用它，就说明接口过宽。
- **新代码遵守边界，存量越界用接缝逐步收紧。** 新模块一开始就放对层；对已有越界依赖，先加接缝（见第 5 节）把依赖方向
  掰正，而不是一次性重写整层。依赖方向的修复是重构，手法归 `refactoring-conventions`，目标结构在这里裁定。
- **分层不是教条，是变化速率的排序。** 只有当内层确实比外层稳定、变化更慢时，分层才有价值；为一个只有一层、永不
  变化的系统强加四层，是过度设计（见第 6 节）。

| 正例 | 反例 | 原因 |
|---|---|---|
| 领域层定义 `PaymentGateway` 抽象，基础设施层实现它 | 领域层直接 `import` 具体支付 SDK | 前者内层独立演进，后者内层被外层绑架。 |
| 依赖图经校验器判定为 DAG | 模块 A 依赖 B，B 依赖 A | 环会让编译、测试与发布互相卡死。 |
| 按调用方拆成 `Reader` 与 `Writer` 两个接口 | 一个 `Repository` 接口含全部 20 个方法 | 调用方被迫依赖用不到的方法。 |

| 依赖方向 | 允许 | 说明 |
|---|---|---|
| 外层 → 内层 | 是 | 默认方向，外层消费内层抽象。 |
| 内层 → 内层 | 是 | 同为稳定层，但仍要保持无环。 |
| 内层 → 外层 | 否 | 违反依赖倒置，需通过接缝反转。 |
| 环（A → B → A） | 否 | 必须拆模块或抽接口打破。 |

## 3. 数据流与控制流

数据流回答「数据从哪来、被谁处理、到哪去」，控制流回答「谁调用谁、谁编排谁」。两者混在一起，是副作用与隐式状态
的温床。

- **数据流显式。** 数据通过参数与返回值在模块间传递，来源与去向在签名里可读；不靠模块级或全局可变状态隐式传递。判据：
  只看一个函数的签名，能否说出它接收什么、返回什么；要翻遍全局变量才能补全时，数据流就是隐式的。
- **控制流显式。** 编排关系（谁触发谁、谁依赖谁的结果）通过调用、回调或明确的事件在代码里可见；不靠隐式注册、反射
  或全局总线的魔法触发。事件与消息的投递契约归 `api-and-data-conventions`，这里的责任是让编排关系可读。
- **数据流与控制流分开。** 一个模块可以只处理数据（纯转换），或只编排（调用别的模块），但职责要分清；既转换数据又
  编排下游的模块，是内聚不足的信号。
- **跨模块的数据传递通过契约，不通过内部结构。** 模块间传的是契约定义的值对象（契约内容归 `api-and-data-conventions`），
  而不是对方的内部实体或存储行。这样数据流穿过边界时，不会把存储形状泄漏到另一侧。
- **副作用有明确归属。** 写操作、IO 与状态变更集中、可见、可定位；「某函数顺带改了别处的状态」是隐式数据流，是缺陷而
  不是捷径。

| 正例 | 反例 | 原因 |
|---|---|---|
| `parse(raw) -> Order` 只做转换 | `parse(raw)` 里顺带写缓存和发通知 | 后者既转换又编排，还藏副作用。 |
| 数据经参数与返回值传递 | 数据存进模块级可变状态再被读取 | 后者数据流隐式，来源去向难追踪。 |
| 编排关系通过显式调用表达 | 靠全局事件总线魔法触发 | 后者控制流不可读，难以静态校验。 |

## 4. 设计决策记录

ADR 把架构决策从「某人脑子里的默认」变成「仓库里的权威来源」，让下一次变更遵循它而不是重炒它。

- **何时写 ADR。** 新建或推翻一个架构决策时写：采用或替换一项核心技术、划分或合并模块边界、改变分层或依赖方向、引入
  或移除一个抽象、确定数据流或控制流的主路径，以及任何会影响后续变更走向的决定。修改已应用代码的行为、日常功能
  或纯风格选择不写 ADR。
- **写什么。** 每篇 ADR 至少含：背景（要解决什么问题、有哪些约束）、决定（选择了什么，用可判定的话说清）、后果（带来
  的收益与代价，以及哪些路径因此变贵）、替代方案（被否掉的选项及否掉理由）。状态只写当前为真的一条，不追加历史。
- **一条决策一篇，按序号命名，永不修改已接受的 ADR。** 决策变了就写一篇新 ADR，标注它取代哪一篇；修改旧 ADR 会让历史
  与现状分叉。文档归属与发布节奏由 `documentation-conventions` 裁定，这里裁定的是内容口径与触发时机。
- **不写 ADR 的决策不算决策。** 没有记录的架构决策会在下一次变更时被重新争论；只有 ADR 或模块文档里有裁决的决策，才是
  后续变更可以引用的权威来源。

| 正例 | 反例 | 原因 |
|---|---|---|
| 「支付网关用接口隔离，依赖倒置」写成 ADR | 该决定只存在于某个 PR 的讨论里 | 讨论会过期，ADR 是可引用的权威来源。 |
| 新决策写新 ADR，标注取代旧篇 | 直接改写旧 ADR 的「决定」 | 改写会让历史与现状分叉。 |
| ADR 只写当前为真的决定 | ADR 追加「某日改成了 X」的变更记录 | 变更记录会腐烂；只陈述当前行为。 |

## 5. 可测试性设计

可测试性不是测试之后补的东西，而是依赖方向与接缝设计出来的属性。设计可测的模块，就是设计能被替换、被隔离的模块。

- **接缝是依赖的可替换点。** 接缝是代码里可以不改生产行为就替换某处依赖的位置（接口、函数参数、注入点）。显式接缝让
  测试能隔离慢的、不稳定的或外部的依赖；没有接缝的模块只能靠全局状态或真实外部系统来测，测试脆弱且慢。
- **先测后抽接口。** 需要替换某依赖以便测试时，先写一个暴露这个需求的测试，再抽取最小接口满足它；不为假设的「以后可
  能替换」抽接口（见第 6 节）。这样接口的形状由真实使用驱动，而不是由想象驱动。
- **依赖注入是接缝的一种，不是唯一。** 构造器注入、方法参数注入、工厂与配置点都是接缝；选最贴合语言与现有风格的接缝
  （风格归 `code-style-conventions`），本维度决定接缝的位置与可替换性。注入点要少而清晰，不在各处散落可选参数。
- **外部依赖总在接缝后面。** 网络、时钟、文件系统、随机源与第三方 SDK 是测试里最需要替换的依赖，都放在接缝后面；测
  试策略与门禁归 `testing-and-quality-conventions`，这里负责把这些依赖设计成可替换。
- **可测性与好架构同向。** 一个依赖方向向内、接缝显式的模块，天然可测；一个需要大量 mock 才能测的模块，往往是边界画
  错或耦合过紧的信号。

| 正例 | 反例 | 原因 |
|---|---|---|
| 时钟通过参数或接口注入，测试可传固定时间 | 代码里直接 `new Date()`，测试靠睡眠对齐 | 后者不可替换，测试脆弱且慢。 |
| 先写「替换日志实现」的测试，再抽接口 | 先抽 10 个方法的日志接口，无人使用 | 前者由真实使用驱动，后者是过度设计。 |
| 网络调用集中在接缝后，测试用桩替换 | 测试连真实外部服务，靠开关切换 | 后者没有接缝，测试依赖外部且不稳定。 |

## 6. 演进与简化

架构的演进方向是从具体到通用、从简单到必要，而不是反过来。为尚未出现的需求付通用性成本，是过度设计。

- **先简单后通用。** 默认写具体实现，直接满足当前需求；只有出现第二个真实使用场景，才引入抽象、参数化或泛型。抽象
  的形状由第二个场景「回填」，而不是由第一个场景「预演」。
- **YAGNI：不为尚无使用者的能力付成本。** 不实现「以后可能要用」的开关、插件点、泛型或配置项；它们没有使用者，无法
  证明有用，还增加维护面。判据：这个能力现在有没有一个真实调用方；没有，就不写。
- **不过度设计。** 分层、抽象与接缝的数量与系统的真实变化速率成正比。变化多的地方多留接缝，恒定的地方直接写死；为
  一个永不变化的部分强加多层抽象，成本高且无回报。
- **先跑通，再演进。** 新的模块先以最简单可用的形态落地并运行，用真实使用确认边界，再在出现第二个场景时演进；不要
  在写第一行代码前就设计好全部未来形态。
- **移除未使用的抽象。** 一个抽象失去了所有使用者（接口只剩一个实现且无替换需求、开关永远关闭）时，删掉它而不是留
  着；未使用的抽象是负担，不是资产。删除是重构，手法归 `refactoring-conventions`。

| 正例 | 反例 | 原因 |
|---|---|---|
| 第二家支付方式接入时才抽 `PaymentGateway` 接口 | 一开始就为「可能多家」抽全套抽象 | 前者由真实需求驱动，后者为想象付成本。 |
| 恒定不变的配置直接写死 | 为一个永不变的开关加插件点 | 没有变化的接缝是纯负担。 |
| 抽象失去使用者后删除 | 只实现过一次的接口永久保留 | 未使用的抽象增加维护面。 |
