# 架构与设计规范

架构是系统里最难改的部分：模块边界一旦画错，每次改动都要牵动一整片区域；依赖方向一旦倒转或成环，编译、测试与
发布都会互相卡死；接口一旦暴露在错误的位置，所有调用方都被它绑架。本 skill 定义如何划分模块与组件、如何让依赖只从
外层指向内层、如何设计可测试的接缝，以及如何用 ADR 把决策固定下来，避免每次变更重炒同一个问题。它服务于新增模块
的作者、划分边界的架构师，以及审查依赖图、循环依赖与过度设计的审查者。

## 适用范围与优先级

采用第一条适用的规则，同一范围内不要混用标准：

1. 强制的运行时、框架、语言与平台约束。宿主框架的模块系统、编译单元边界、包管理器的依赖解析与构建图的拓扑约
   束都不是可选项。
2. 既有架构与已记录的决策。发明规则之前，先读模块清单、依赖图、分层约定与 ADR，以及当前代码里已经成形的边界。
3. 本 skill 的默认值，在前两层未作规定时适用。
4. 个人偏好，永远不能覆盖上述三层。

分工边界：

- **API 契约内容属于 `api-and-data-conventions`。** 它拥有资源、错误、分页、幂等、版本化与 schema 演进；本 skill 拥有
  接口在架构中的位置：谁依赖谁、通过哪个接缝隔离、依赖方向是否向内。接口的形状在那里定义，接口的位置在这里定义。
- **代码风格属于 `code-style-conventions`。** 它拥有目录布局、命名、格式化、依赖管理与错误/日志风格；本 skill 拥有这
  些元素如何组成模块与分层，而不拥有单个文件的写法。
- **重构手法属于 `refactoring-conventions`。** 它拥有安全地改变代码结构的手法与步骤；本 skill 拥有重构要达成的目标结
  构（依赖方向、边界、接缝）。需要动手改结构时，把手法交给它，只在这里定目标。
- **测试策略与门禁属于 `testing-and-quality-conventions`。** 本 skill 拥有可测试性设计：依赖注入点、接缝与可替换的
  依赖；它拥有运行测试与把测试作为门禁的机制。
- **当两条规则冲突时，说明冲突与所选规则。** 把决定记录在 ADR 或模块文档中，让下一次变更遵循它，而不是重炒同一个
  问题。

## 流程

1. 定位变更所在的分层与边界：确定要新增或修改的代码属于哪个模块、哪一层，以及它当前的依赖方向。画出或找到依赖
   图，列出它会依赖谁、谁又依赖它；图上出现环或指向内层的依赖时，先修依赖，再写功能。
2. 检查既有架构与决策：读模块清单、分层约定与 ADR，确认当前边界是否已有裁决；没有裁决时，判断这次变更是否需要
   新建 ADR（判断标准见 `references/dimensions.md` 第 4 节）。
3. 定义模块与组件边界：为每个新模块写清它的单一职责与变更理由；高内聚、低耦合，公共接口最小化。无法用一句话说
   出模块的变更理由时，说明边界还没画对。
4. 确定依赖方向与接缝：依赖从外层指向内层，稳定的抽象在内层，易变的实现在外层。为需要替换或测试的依赖设计接缝
   （接口、注入点），先测后抽接口。
5. 设计数据流与控制流：明确数据从哪进入、被谁处理、流向哪里，以及谁编排谁；两者分开表达，跨模块的数据传递通过
   契约（归 `api-and-data-conventions`），而不是内部结构。
6. 记录决策：新建或推翻架构决策时写 ADR，写明背景、决定、后果与替代方案；不写的决策会在下一次变更时被重新争论。
7. 审查：运行 `references/checklists.md` 中的清单，确认无循环依赖、依赖方向向内、每个模块一个变更理由、接缝可测。

## 核心规则

- **依赖只能从外层指向内层，出现环就重构。** 依赖图必须是有向无环图（DAG）；用构建或静态分析工具校验（层依赖校验、
  循环依赖检测），出现环或反向依赖时在同一次变更中重构，而不是记录为例外。
- **每个模块一个变更理由。** 一个模块因一个明确的原因而变化；当同一改动总是同时触碰多个模块的多个理由，边界就画
  错了。可判定：说出模块名，能补全「它因为……而变」且只有一个理由。
- **公共接口最小化，内层不依赖外层的实现细节。** 模块只暴露调用方真正需要的接口；内部类型、实体与存储细节不越过
  边界。接口隔离：调用方不依赖它用不到的方法。
- **先测后抽接口。** 需要替换某依赖以便测试时，先写测试暴露这个接缝，再抽取接口；不为假设的「以后可能替换」抽接口。
- **先简单后通用。** 默认写具体实现；只有出现第二个真实使用场景，才引入抽象。YAGNI：不为尚无使用者的通用性付出
  成本。可判定：没有第二个调用方时，禁止引入参数化、泛型或多态。
- **抽象属于内层，实现属于外层。** 稳定、低变的抽象放内层；易变的具体实现放外层依赖抽象。这是依赖倒置的落点。
- **数据流显式，控制流显式。** 数据从哪进、被谁处理、流向哪，以及谁编排谁，都能在代码里读出来；不靠隐式全局状态
  或跨模块副作用传递数据。
- **接口的位置与形状分开。** 接口「在哪里、谁依赖谁」由本 skill 裁定；接口「长什么样」（资源、错误、分页）由
  `api-and-data-conventions` 裁定。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 循环依赖 | 编译、测试与发布互相卡死，无法单独变更任一模块。 | 依赖图 DAG 化，抽接口或拆模块。 |
| 上帝模块 | 一个模块承载多个变更理由，每次改动都牵动整片。 | 按单一职责拆，每个模块一个理由。 |
| 内层依赖外层实现 | 稳定的内层被易变的外层绑架，无法独立演进。 | 依赖倒置，抽象在内层。 |
| 把存储模型直接暴露给上层 | 上层耦合到表结构，迁移变成架构级破坏。 | 边界处映射为契约。 |
| 为假设的通用性提前抽象 | 抽象没有第二个使用者，成本白付且更难改。 | YAGNI，出现第二个场景再抽象。 |
| 上帝接口 | 调用方被迫依赖用不到的方法，改动互相牵连。 | 接口隔离，按调用方拆小。 |
| 决策只活在脑子里 | 下一次变更重炒同一个问题，边界反复横跳。 | 写 ADR 固定决策。 |
| 靠隐式全局状态传递数据 | 数据流不可读，副作用跨模块难排查。 | 显式数据流，用参数或返回值传递。 |

## 审查清单

- [ ] 依赖图是有向无环图，依赖只从外层指向内层。
- [ ] 每个模块能用一个变更理由描述。
- [ ] 公共接口最小化，内部类型与存储细节不越过边界。
- [ ] 接口按调用方隔离，没有上帝接口。
- [ ] 接缝与注入点显式，可替换依赖可测试。
- [ ] 新接口的契约内容已交由 `api-and-data-conventions` 审查。
- [ ] 抽象在内层，实现在外层，无反向依赖。
- [ ] 数据流与控制流显式，不靠隐式全局状态。
- [ ] 新建或推翻的架构决策有 ADR。
- [ ] 没有为假设的通用性引入抽象（YAGNI）。
- [ ] 与相邻 skill 的边界清楚：契约、风格、重构手法各有归属。

## 示例

<example>
场景：在订单模块里新增「支付」逻辑，发现支付要依赖订单，订单也要依赖支付。
问题：出现循环依赖，两个模块无法单独编译与测试。
修复：抽取一个内层抽象（如 `payment-gateway` 接口），订单依赖它，具体支付实现在外层依赖同一接口。依赖图回到 DAG。
</example>

<example>
场景：想为日志库写一个可替换的抽象，但目前只有一个日志实现。
问题：为一个假设的「以后可能换」引入接口，是过度设计。
修复：先直接用具体实现；等出现第二个真实实现（如测试桩或另一后端）时，先写测试暴露接缝，再抽接口。
</example>

<example>
场景：数据层把 ORM 实体直接返回给上层界面。
问题：上层耦合到表结构，每次迁移都变成架构级破坏。
修复：在边界处把实体映射为契约（契约内容归 `api-and-data-conventions`），上层只依赖契约，不依赖存储形状。
</example>
