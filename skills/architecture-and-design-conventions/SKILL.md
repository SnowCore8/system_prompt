# 架构与设计规范

架构是系统中最难的变更区域。
模块边界划错，每次改动都会牵动整个区域；依赖方向倒置或成环，编译、测试与发布互相阻塞；接口放在错误位置，所有调用方都被它约束。
本 skill 规定模块与组件怎么划分、如何保证依赖不得由内层指向外层、可测试接缝如何设计，以及如何用 ADR 固定决策，使后续变更无需重复争论同一问题。
读者是新增模块的作者、划分边界的架构师，以及审查依赖图、循环依赖与过度设计的审查者。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与用户全局约束。
   宿主框架的模块系统、编译单元边界、包管理器的依赖解析与构建图的拓扑约束，都不是可选项。
2. 本 skill 的规则。
   模块边界、分层与依赖方向、数据流、接缝与 ADR 的规则，以本文件与 `references/` 为准。
3. 既有项目约定与事实。
   代理应当先阅读模块清单、依赖图、分层约定、ADR 与代码中已经成形的边界；这些是事实输入，按本 skill 的规则处理。
   项目约定只在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

分工边界如下：

- **API 契约内容由 `api-and-data-conventions` 管辖。** 该 skill 管辖资源、错误、分页、幂等、版本化与 schema 演进；本 skill 管辖接口在架构中的位置：谁依赖谁、经哪个接缝隔离、依赖方向是否向内。接口的形状由该 skill 定义，接口的位置由本 skill 定义。
- **代码风格由 `code-style-conventions` 管辖。** 该 skill 管辖目录布局、格式化、依赖管理与错误及日志风格；命名由 `naming-conventions` 管辖。本 skill 管辖上述元素如何组成模块与分层，不管辖单个文件的写法。
- **重构手法由 `refactoring-conventions` 管辖。** 该 skill 管辖安全变更代码结构的手法与步骤；本 skill 管辖重构应当达成的目标结构，即依赖方向、边界与接缝。需要变更结构时，代理应当把手法交给该 skill，本 skill 只确定目标。
- **测试策略与门禁由 `testing-and-quality-conventions` 管辖。** 本 skill 管辖可测试性设计，包括依赖注入点、接缝与可替换的依赖；测试的运行与门禁机制由该 skill 管辖。
- **ADR 的内容与触发时机由本 skill 裁定。** 目录与模板由 `documentation-conventions` 裁定；文件名与编号由 `naming-conventions` 裁定；发布节奏由 `release-operations-conventions` 管辖。
- **强制规则冲突的，代理应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与所选约定。** 所选约定应当记录于 ADR；模块文档可记录派生决定，不得替代 ADR，使下一次变更遵循该决定，避免重复争论同一问题。

## 流程

1. 定位变更所在的分层与边界。
   代理应当确定待新增或修改的代码所属的模块与层次，以及其当前的依赖方向。
   代理应当绘制或查找依赖图，列出该代码依赖的对象与被依赖的对象；依赖图出现环，或依赖由内层指向外层的，应当先修复依赖，再编写功能。
2. 检查既有架构与决策。
   代理应当阅读模块清单、分层约定与 ADR，确认当前边界是否已有裁决；无裁决的，应当判断本次变更是否应当新建 ADR，判断标准见 `references/dimensions.md` 第 4 节。
3. 定义模块与组件边界。
   代理应当为每个新模块写明单一职责与变更理由；模块应当高内聚、低耦合，公共接口应当最小化。
   无法说明模块变更理由，或同一模块总是因两个不同理由而变化的，视为边界尚未划定正确。
4. 确定依赖方向与接缝。
   依赖默认由外层指向内层，同层允许但不得成环；稳定的抽象置于内层，易变的实现置于外层。
   代理应当为需要替换或测试的依赖设计接缝，即接口与注入点；接口的抽取应当在测试之后。
5. 设计数据流与控制流。
   代理应当明确数据的入口、处理者与流向，以及编排关系；两者应当分别表达，跨模块的数据传递应当通过接口或契约，不得通过内部结构。
   内部模块接口与值对象形状由本 skill 裁定；跨服务 API 契约由 `api-and-data-conventions` 管辖。
6. 记录决策。
   新建或推翻架构决策的，代理应当编写 ADR，写明背景、决定、后果与替代方案；未记录的决策会在下一次变更时被重新争论。
7. 审查。
   代理应当运行正文“审查清单”，并按 `references/checklists.md` 中的工作表执行；确认无循环依赖、依赖不由内层指向外层、每个模块仅有一个变更理由、接缝可测试。

## 核心规则

- **依赖不得由内层指向外层；同层允许但不得成环。** 依赖图必须为有向无环图（DAG）；代理应当以构建或静态分析工具校验，包括层依赖校验与循环依赖检测。
  本次新增或修改的依赖出现环或反向依赖的，应当于同一次变更中重构，不得以 ADR 豁免；存量越界按记录的迁移步骤以接缝逐步收紧，不得一次性重写整层。
- **每个模块仅有一个变更理由。** 模块仅应因一个明确原因而变化；判定标准：同一模块总是因两个不同理由而变化，即视为边界划定错误，应当拆分。
- **公共接口应当最小化；内层不得依赖外层的实现细节。** 模块仅应暴露调用方实际需要的接口；内部类型、实体与存储细节不得越过边界。接口应当隔离：调用方不得依赖其不使用的方法。
- **接口的抽取应当在测试之后。** 需要替换某依赖以便测试的，代理应当先编写暴露该接缝的测试，再抽取接口；不得为假设的“以后可能替换”抽取接口。
- **实现应当先具体，后通用。** 默认应当编写具体实现；仅在出现第二个真实使用场景，或存在明确的测试、替换需求时，方可引入抽象。YAGNI：不得为尚无使用者的通用性付出成本。测试接缝与外部依赖注入不受 YAGNI 限制。
- **抽象属于内层，实现属于外层。** 稳定、低变的抽象应当置于内层；易变的具体实现应当置于外层并依赖抽象。此为依赖倒置的落点。
- **数据流与控制流应当显式。** 数据的入口、处理者与流向，以及编排关系，均应当能够在代码中读出；不得依靠隐式全局状态或跨模块副作用传递数据。
- **接口的位置与形状应当分别裁定。** 接口的位置，即位于何处、谁依赖谁，由本 skill 裁定；接口的形状，即资源、错误与分页，由 `api-and-data-conventions` 裁定。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 循环依赖 | 编译、测试与发布相互阻塞，任一模块均无法单独变更。 | 将依赖图改为 DAG，抽取接口或拆分模块。 |
| 上帝模块 | 一个模块承载多个变更理由，每次改动均牵动整个区域。 | 按单一职责拆分，使每个模块仅有一个变更理由。 |
| 内层依赖外层实现 | 稳定的内层受易变的外层约束，无法独立演进。 | 实施依赖倒置，将抽象置于内层。 |
| 把存储模型直接暴露给上层 | 上层耦合于表结构，迁移即构成架构级破坏。 | 在边界处映射为契约。 |
| 为假设的通用性提前抽象 | 抽象无第二个使用者，成本无回报，变更亦更困难。 | 依 YAGNI 处理，出现第二个场景后再抽象。 |
| 上帝接口 | 调用方被迫依赖其不使用的方法，改动相互牵连。 | 实施接口隔离，按调用方拆分。 |
| 决策仅存于记忆 | 下一次变更重复争论同一问题，边界反复变动。 | 编写 ADR 固定决策。 |
| 依靠隐式全局状态传递数据 | 数据流不可读，副作用跨模块，难以排查。 | 采用显式数据流，以参数或返回值传递。 |

## 审查清单

- [ ] 依赖图为有向无环图；依赖不得由内层指向外层，同层允许但不得成环。
- [ ] 每个模块能够以一个变更理由描述。
- [ ] 公共接口已经最小化，内部类型与存储细节未越过边界。
- [ ] 接口按调用方隔离，不存在上帝接口。
- [ ] 接缝与注入点显式，可替换的依赖可测试。
- [ ] 新接口的契约内容已交由 `api-and-data-conventions` 审查。
- [ ] 抽象置于内层，实现置于外层，不存在反向依赖。
- [ ] 数据流与控制流显式，未依靠隐式全局状态。
- [ ] 新建或推翻的架构决策均有 ADR；模块文档仅记录派生决定，不替代 ADR。
- [ ] 未为假设的通用性引入抽象（YAGNI）。
- [ ] 与相邻 skill 的边界清晰：契约、风格、重构手法、测试策略与文档各有管辖者。

## 示例

<example>
场景：在订单模块中新增“支付”逻辑，发现支付依赖订单，订单亦依赖支付。
问题：出现循环依赖，两个模块均无法单独编译与测试。
修复：抽取内层抽象（例如 `payment-gateway` 接口），订单依赖该接口，具体支付实现于外层依赖同一接口。依赖图恢复为 DAG。
</example>

<example>
场景：拟为日志库编写可替换的抽象，但目前仅有一个日志实现。
问题：为假设的“以后可能更换”引入接口，属于过度设计。
修复：先直接使用具体实现；出现第二个真实实现（例如测试桩或另一后端）时，先编写测试暴露接缝，再抽取接口。
</example>

<example>
场景：数据层将 ORM 实体直接返回给上层界面。
问题：上层耦合于表结构，每次迁移均构成架构级破坏。
修复：在边界处将实体映射为契约（契约内容由 `api-and-data-conventions` 管辖），上层仅依赖契约，不依赖存储形状。
</example>
