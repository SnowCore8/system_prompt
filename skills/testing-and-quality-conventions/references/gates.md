# 质量门禁

本文件是 `SKILL.md` 的操作配套：按技术栈的命令、默认阈值，以及团队定义门禁集合时会改造的模板。配置流水线
时读技术栈一节，设定阈值时读覆盖率工作表，套件变得不可靠时读不稳定测试流程，必须规避门禁时读豁免模板。每条
命令均为默认值；应当采用项目的实际工具、固定其版本，并使流水线与本地目标共用一份定义。阻塞意味着必需状态校
验使合并失败；提示性意味着结果会被报告和审查，但从不阻塞。某个技术栈需要运行器无法提供的服务的，应当记录其
实际运行的替代方案。

正文“审查清单”为设计阶段的权威依据；本文件仅放置配置门禁与套用豁免时点的工作表，以及正文未展开的条件。

## 按技术栈的门禁矩阵

每行给出一个必需校验、一条默认命令，以及使其失败的阈值。除行中另有说明外，均在 PR 上运行；某技术栈没有付费
服务即无法运行某行的，应当记录其改为运行的等价方案。

有两个必需门禁没有通用命令，各技术栈需调用自己的项目工具：

| 跨栈门禁 | 默认命令 | 默认阈值 |
|---|---|---|
| 契约验证 | 变更方的契约目标，例如 `contract` 测试标记 | 任何失败的交互都算失败；部署前双方都必须通过 |
| 静态应用安全测试 | 安全策略指定的扫描器，例如 `semgrep ci` | 按策略严重级别阻塞；PR 上扫描变更代码，main 上完整扫描 |

上述两项应当与各技术栈的行并列，作为必需状态校验。

### Python

| 门禁 | 默认命令 | 默认阈值 |
|---|---|---|
| 格式 | `black --check .` 或 `ruff format --check .` | 任何 diff 都失败 |
| lint | `ruff check .` | 新错误失败；新警告零新增并审查，按严重级别表升级为阻塞；基线只缩不增 |
| 类型校验 | 新模块用 `mypy --strict`，已建基线的模块用 `mypy` | 任何错误失败；新模块必须保持严格 |
| 单元测试 | `pytest -m "not integration" --cov --cov-branch` | 套件 2 分钟；变更覆盖率 80% |
| 集成测试 | `pytest -m integration` | 套件 15 分钟 |
| 依赖审查 | 针对 lockfile 运行 `pip-audit` | 有修复方案的高危或严重漏洞失败 |
| 机密扫描 | `gitleaks detect --no-banner` | 任何发现失败 |

禁；会运行但非必需的行仅具参考性质，下一个截止日期即会将其删除。

## 覆盖率策略工作表

每个仓库根据实测值填写一次本工作表，每季度以及每次事故后复查，并提交于覆盖率配置旁。仅存在于看板上的策略将
在每次审查中被重新议定。

| 项目 | 默认策略 | 如何设定 |
|---|---|---|
| 项目行覆盖下限 | 实测 main 分支覆盖率，向下取整到最近的 5 | 读取最近一次绿色的 main 构建报告 |
| 变更下限 | 新增与修改的可执行行的 80% | 在与测试结果同一次运行中按 diff 计算 |
| 分支下限 | 处理资金、权限或数据丢失的模块 70% | 在策略文件中列出模块路径 |
| 变异目标 | 关键模块 60-70% | 在计划作业中对这些模块运行变异工具 |
| 上调步长 | 下限提高 5 个百分点 | 实测覆盖率连续一个发布周期高出下限 5 时上调 |
| 排除清单 | 生成、第三方引入、迁移与入口粘合代码 | 每项记录路径、原因、负责人与到期时间 |
| 豁免时限 | 每条豁免 90 天 | 到期时复查，然后移除或用证据续期 |
| 复查节奏 | 每季度及每次事故后 | 用固定工具版本重新测量并记录命令 |

- 变更覆盖率按“已覆盖的变更可执行行 ÷ 全部变更可执行行”计算，并在产生测试结果的同一次运行中测量；单独
  的覆盖率运行可能与其所描述的套件不一致。
- 设定下限时应当使用提交在仓库中的工具与配置，因为用不同覆盖率工具的本地运行与 CI 运行会产生不可比的分
  字。
- 应当为策略文件指定负责人与复查触发条件，使这些数字在人事变动后仍能够存续，也不会被无关 PR 在未察觉时重新议
  定。
- 覆盖率工具升级后应当重新运行工作表，因为新工具可能以不同方式统计生成行或部分分支，将稳定的下限变为意
  外失败。

## 不稳定测试流程

同一提交在同一环境中一次运行失败、另一次通过，该测试即属不稳定；仅在修复前失败的测试不算不稳定。不稳定测试
应当经历下列阶段，并在根因修复前将其留在阻塞性套件之外。

| 阶段 | 触发条件 | 必须动作 | 负责人 | 期限 |
|---|---|---|---|---|
| 检测 | 观察到间歇性失败，或重复运行结果不一 | 记录提交、种子或输入，以及失败率 | CI 负责人 | 1 天内 |
| 确认 | 未变更的提交上或重复运行下出现混合结果 | 创建工单，附日志与复现命令 | 测试作者 | 2 天 |
| 隔离 | 阻塞性套件中确认的不稳定测试 | 取得项目豁免具名批准后，将其移出阻塞集合，连同工单加入计划隔离作业 | 测试作者 | 当天 |
| 指派 | 隔离之后 | 指定一名修复负责人与修复截止日期 | 团队负责人 | 1 天 |
| 修复或移除 | 到达修复截止日期 | 修复根因，或删除该测试并在工单中记录覆盖缺口 | 修复负责人 | 14 天 |
| 重新启用 | 修复已合并 | 在 CI 中连续 20 次绿色运行，然后放回阻塞性套件 | 修复负责人 | 2 天 |

- 隔离测试数量上限为五个或套件的 1%，取较小者；超过上限的套件在降回之前不得新增测试。
- 隔离标记、工单与负责人应当放在项目的测试配置中，使下一位读者看到该测试为何不在阻塞集合中。
- 生产代码竞态导致的不稳定应当视为事故级的生产缺陷，不得视为测试噪声。
- 不得以自动重试替代隔离；重试会使失败从本应捕获它的指标中消失。
- 隔离清单应当导出到构建状态旁，使团队无需逐个打开工单即可看到隔离清单所代表的负担，超期未解除的隔离在审查中也可见。

## 静态分析严重级别与基线

在工具配置中一次性将每个工具的输出映射到下列桶，并使该映射随质量策略其余部分一起受审。

| 校验 | 默认严重级别 | 门禁效果 | 基线策略 |
|---|---|---|---|
| 类型校验 | 错误 | 阻塞合并 | 按模块允许，需迁移工单；新模块保持严格 |
| lint 错误 | 错误 | 阻塞合并 | 按文件允许；计数不得增长 |
| lint 警告 | 警告 | 使零新增警告校验失败 | 现有警告入基线；计数不得增长 |
| 复杂度与重复度 | 变更代码上为警告 | 审查意见；采用后转为阻塞 | 仅变更级别；不做全仓基线 |
| 机密扫描 | 错误 | 立即阻塞 | 无基线；排查误报；真实发现先停止、保留证据并报告，取得明确同意后 24 小时内轮换，再审计，调查结束后清理历史 |
| 依赖审查 | 策略严重级别上的错误 | 按漏洞策略阻塞 | 无基线；策略负责人接受例外；严于漏洞策略的阈值需安全负责人批准并记录例外 |
| 静态应用安全测试 | 策略严重级别上的错误 | 安全策略要求时阻塞 | 逐项接受，带负责人与到期时间 |
| 格式化工具 | 错误 | 工作区有差异时阻塞 | 无基线；提交前格式化 |

- 用仓库中固定的工具版本生成基线，审查计数，并将文件提交于工具配置旁，使基线与产生它的规则一起变动。
- 像审查代码一样审查每次基线变化：缩小应当受到鼓励，增长则需要关联理由、负责人与到期时间，不得以重新生成的文件
  替代。
- 抑制应当保持局部，限定在行或函数范围，并附理由与到期时间；文件级抑制需要具名负责人与清理工单。
- 工具升级后应当重新测量，并在重新生成前审查差异，因为新规则会发现值得单独决策的新违规。
- 应当记录每个已接受的发现，包括负责人、产生它的规则与审查日期，使安全审查与质量审查读取同一份清单，
  不得各自从工具输出重建。

## 本地环境清单

改动 bootstrap 或流水线前，应当对全新克隆运行本清单：

- [ ] 一条命令从全新克隆到达可运行环境，并打印解析后的版本。
- [ ] bootstrap 幂等，失败时指出缺失的前置条件。
- [ ] 运行时、包管理器与服务版本来自固定文件。
- [ ] 容器镜像按 digest 或次版本标签固定；任何地方都没有 `latest`。
- [ ] devcontainer 或等价方案能够复现 CI 工具链。
- [ ] `.env.example` 列出每个必需键并提供假默认值；`.env` 被忽略。
- [ ] 配置校验在启动时快速失败，并指出违规键。
- [ ] 测试服务暴露健康检查，测试带有超时上限地等待就绪。
- [ ] 测试数据库或 schema 每次运行创建，结束后删除。
- [ ] 种子数据是确定性的、幂等的，且为合成数据。
- [ ] 测试命令与 CI 运行的是同一个目标。
- [ ] `make doctor` 校验工具、端口与服务健康。
- [ ] `make clean` 删除容器、卷、缓存与构建制品。
- [ ] bootstrap 与 CI 配置读取相同的固定配置文件。
- [ ] 服务启动失败会留下清晰错误，恢复步骤有文档记录。
- [ ] 完整的 PR 门禁集合能够在全新克隆上运行，且无需未记录的步骤。
- [ ] 提交的本地配置中不出现机密、令牌或个人数据。

## 豁免模板

将本模板复制到仓库的质量策略或 PR 中，填写每个字段，并在修复落地或到期后删除该记录。

```markdown
## Waiver: <gate> on <scope>

- Approver: <code owner, not the change author; single-person repo: maintainer, named>
- Reason: <the failure and why it cannot be fixed in this change>
- Scope: <paths, jobs, or branch the waiver covers>
- Expiry: <YYYY-MM-DD, no more than 90 days out>
- Tracking: <issue key>
- Remediation: <change that removes the waiver>
```

- 没有到期时间或没有具名批准人的豁免无效，将在审查中被拒绝。单人维护的，批准人由维护者具名自批，并在治理文件记录该自批与补偿控制；代理不得自行批准。
- 一条豁免仅覆盖一个门禁与一个范围；两个门禁需要两条记录。
- 禁止豁免机密扫描发现；依赖漏洞的豁免按 `security-compliance-conventions` 的到期记录与批准流程执行，本
  skill 仅要求每条豁免有具名批准人与到期日。
- 到期时应当移除豁免，或以新证据续期；没有证据即续期的豁免属于排除项。
- 应当将豁免记录在仓库或 PR 中，不得记录在聊天中，使下一位审查者能够找到并评判该记录。
- 豁免记录应当与任何门禁配置变更放在同一次受审变更中落地，使规避操作与使其必要的规则同时可见。
