# 测试与质量维度

本文件与 `SKILL.md` 配合使用。每一节规定一个质量维度的决策、示例与边界情况。项目已有策略与配置的，应当先阅
读上述内容并将其作为输入，按 `SKILL.md` 的规则审查与处理；项目约定仅在本 skill 未规定时补充，不得覆盖本
skill。本文件提供默认值与理由。代理应当仅阅读与待修改测试或待调整门禁相匹配的一节。

## 1. 测试策略与分层

分层决定每种风险在何处得到证明。形状不当的测试套件，或者花费一小时回答单元测试一毫秒即可回答的问题，或者
在其从未跨越的集成已经损坏时仍报告绿色。

- 代理应当按项目类型与失败代价选择形状。领域服务采用金字塔：大量单元测试、较少的集成测试，以及一层薄薄
  的、针对关键流程的端到端测试。客户端逻辑很重的 UI 产品采用奖杯形：扎实的单元与组件层，加上更少但更宽
  的集成测试。数据管道或 CLI 主要采用集成测试，并在输入与输出处实施契约校验。避免冰淇淋锥形：端到端测
  试占主导，每个失败均须通过浏览器调试。选定的形状应当记录于仓库的测试说明中，并在主要风险变化时重新审
  视；仅选一次、从不复查的形状将沦为无依据的惯例。
- 按“什么是真实的”划分层级边界，不按目录名划分。单元测试替换所有 I/O；组件测试保留进程内协作者为真
  实；集成测试恰好跨越一个真实边界；端到端测试从入口跨越到持久化；契约测试在不部署双方的情况下检查接口
  约定。应当通过“该测试会注意到哪种依赖故障”检查分类：停掉数据库亦无法使其失败的，无论置于哪个目录，
  均属单元或组件测试。
- 每一对共享请求与响应形状的可部署单元均使用契约测试。消费方记录期望，提供方在自己的流水线中验证，形状
  变更时任意一方均会失败。不得以共享预发环境替代契约测试：预发属于共享、缓慢的环境，并会因与契约无关的
  原因漂移。契约制品应当与消费方放在一起，并有意识地升级其版本，使提供方的变更产生迁移窗口，而非意外故
  障。
- 禁止 mock 被测单元、值对象、项目自身的序列化、数据库约束与迁移、授权决策，或测试声称要证明的行为。持
  久化不属于被测行为的，单元测试可以使用 fake 替换项目的 repository；集成测试必须使用真实引擎，因为该处
  的 mock 仅能够证明 mock 被调用过。以 fake 替换数据库的，应当对其运行真实的迁移路径并验证生产方言，否则
  测试将批准生产环境拒绝的 SQL。
- 在测试中永远不得真实执行：支付扣款、邮件或短信发送、带配额或成本的外部 API、生产数据，以及任何需要人
  参与的事项。应当以沙箱、边界处的 fake 适配器或录制的契约制品替换上述内容，并将每个替换物与其他测试替
  身放在一起，避免 fake 扩散进生产代码。应当使每个 fake 在遇到意外交互时失败，使新增的生产调用不会因无
  人想到断言而静默通过。
- 用工厂构建测试数据：工厂产出有效的默认值，并接受逐测试覆盖。没有测试会改动其他测试共享的 fixture。
  应当以事务回滚、每次运行独立 schema、容器或唯一命名空间实施隔离，并删除无法回滚的内容；留下数据行的测试
  将使下一次运行依赖顺序。断言中应当优先使用显式值而非随机值；随机导致的失败必须打印其种子与输入，否则
  看到该失败的人无法复现。
- 仅在低层看不到缺陷时向上提升。代理应当在能够失败的最廉价层级复现生产 bug，在该层级添加回归测试，并为
  未覆盖的路径最多添加一条端到端防护。在三个层级重复同一断言不会带来信号，只会使维护量增至三倍。应当在
  bug 工单中记录该次提升，包括层级、测试与防护，使下一个类似缺陷沿同一路径处理。
- 每个层级执行运行时间预算。单元套件保持在 2 分钟以内，PR 测试阶段控制在测试层级矩阵的套件预算内；并行
  分片时阶段墙钟最多 20 分钟，串行相加超过 20 分钟的，应当说明并移入单独作业。各层级的逐测试与套件预算
  以 SKILL.md 的测试层级矩阵为唯一口径；超出预算的测试应当先并行分片或拆分，仍超预算的移入单独作业并记录
  理由；确属层级归位的，可移至下一层并记录理由。端到端与属性测试遵循层级矩阵中的逐测试预算。不得容忍一个
  所有人最终均不再运行的套件。应当在 CI 的标准运行器上测量预算，不得在开发者笔记本电脑上测量，因为
  PR 等待的是前者的数字。

按项目类型的默认形状：

| 项目类型 | 主导层 | 支撑层 | 薄层 |
|---|---|---|---|
| 领域服务 | 单元 | 集成、每个依赖的契约 | 关键流程上的端到端 |
| UI 产品 | 组件 | 单元、API 客户端的契约 | 核心旅程上的端到端 |
| 数据管道或批处理作业 | 基于固定数据集的集成 | 转换逻辑的单元、输入与输出上的契约 | 一次完整运行的冒烟 |
| CLI 或库 | 单元 | 公共接口的集成 | 文档化命令上的冒烟 |
| 多服务平台 | 集成与契约 | 逻辑的单元 | 每个服务对的端到端 |

PR 阶段启用哪些层级取自本 skill 的门禁表，预算以测试层级矩阵为准。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 针对固定数据库容器做 repository 测试 | 针对 mock 的 ORM 做 repository 测试 | mock 会掩盖 SQL、约束与迁移失败 |
| 折扣规则用表驱动单元测试 | 每个折扣用例都跑端到端结账 | 规则在它所在的位置失败得最快 |
| 消费方契约在提供方 CI 中验证 | 把共享预发环境当作契约 | 预发会漂移，并因无关原因失败 |
| 边界处一个 fake 支付适配器 | 在服务内部 mock `PaymentClient` | 在单元内部 mock 校验的是 mock，不是扣款 |
| 在最先看到 bug 的层级加回归测试 | 在单元、集成与端到端重复同一断言 | 重复增加维护成本，不增加信号 |

## 2. 质量门禁与覆盖率

门禁是质量不再属于可选项的边界。门禁集合必须小到人人均能够说出，又严格到使绿色运行具有意义；覆盖率是该集合
中最常被误用的成员。

- 按分支定义必需门禁，并使每一项成为必需状态校验。每个 PR 上：格式校验、lint、类型校验、单元测试、涉及
  服务的集成测试、构建、机密扫描、阻塞级别的依赖审查、变更方的契约验证，以及对变更代码的静态应用安全测
  试。在 main 上追加完整端到端测试、完整覆盖率报告、完整契约验证与完整静态应用安全扫描。发布时追加针对
  制品的冒烟测试与关键路径的性能测试。应当写明实现每个门禁的流水线作业，禁止两个作业声称覆盖同一门禁。
- 测量三个覆盖率数字，并逐一据实为每个数字设门禁：行覆盖率用于项目下限，分支覆盖率用于条件涉及资金、权限
  或数据丢失的模块，变更覆盖率用于 diff。变更下限设为新增与修改的可执行行的 80%，项目下限取自实测基线；
  凭雄心设定的下限将使下一个 PR 因自己未触碰的工作而失败。仅当实测覆盖率连续一个完整发布周期高出下限五
  个百分点后，方可上调下限，且任何低于下限的情况均需限定范围的豁免。
- 仅排除生成代码、第三方引入代码、迁移代码与入口粘合代码，并逐项记录路径、原因、负责人与到期时间。排除
  手写逻辑需要豁免，逐文件覆盖率 pragma 需要说明原因。没有上述记录即排除文件的覆盖率运行属于缺陷，因为
  此时数字衡量的是排除而非代码。排除清单应当置于覆盖率配置中，与阈值适用相同的审查路径。
- 将豁免写成记录，不得写成对话。一条豁免写明一个门禁、确切范围、非变更作者的批准人、理由、不超过 90 天
  的到期时间，以及跟踪 issue。单人维护的，批准人由维护者具名自批，并在治理文件记录该自批与补偿控制；代理
  不得自行批准。到期时应当重新审查每条豁免，或修复发现，或以新证据延长；没有证据即续期的豁免属于排除项。
  未关闭的豁免清单应当发布在团队查看构建状态之处，使被豁免的门禁无法在未察觉时变为常态。
- 通过门禁处理失败，不得规避。红色的必需校验将阻塞合并，门禁负责人掌握升级路径、看板与调查。仅已证实的
  基础设施错误允许重试，最多一次，并将首次失败留在记录中；唯一一次绿色运行来自重试的 PR 不算绿色。每月
  审查门禁数据：通过率、时长与豁免数量；通过率下降应当视为门禁或代码的缺陷，不得视为噪声。
- 在用户之前发现不稳定测试：在计划作业中重复运行阻塞性套件，例如 20 次，并记录同一提交上结果不同的每个
  测试。确认的不稳定测试应当按项目豁免程序取得具名批准后，移出阻塞集合、放入计划作业，指定一名负责人与 14 天修复期限，并将隔离测试数
  量限制为五个或套件的 1%，取较小者。生产代码竞态导致的不稳定应当视为生产缺陷，不得视为测试噪声，也不得
  以自动重试替代隔离。
- 将弱化测试视为审查缺陷。为变绿而删除、跳过或放松断言，需要有证据表明该行为变化属于有意为之，且审
  查必须要求补上替代断言。没有负责人、没有 issue 的跳过测试即未被测试的行为，覆盖率报告不会显示该行为。期望
  值必须改变的，应当在测试或变更说明中链接授权新行为的规范或 issue。
- 报告测试套件未证明什么。覆盖率衡量的是执行，不是验证；对承载资金或权限的模块运行变异测试，并在交付中
  说明未验证路径与已知风险，不得将绿色运行当作正确性证明。仅看勾选标记的审查者会假设套件具有其实际没有
  的覆盖，除非缺口被写下来。

按分支的必需门禁：

| 门禁 | PR | main | 发布 |
|---|---|---|---|
| 格式、lint、类型校验 | 必需 | 必需 | 必需 |
| 单元与组件测试 | 必需 | 必需 | 必需 |
| 集成测试 | 涉及的服务必需 | 必需 | 必需 |
| 契约验证 | 变更方必需 | 必需 | 必需 |
| 覆盖率报告 | 变更覆盖率 | 完整报告与下限 | 完整报告与下限 |
| 机密扫描 | 必需，不可豁免 | 必需，不可豁免 | 必需，不可豁免 |
| 依赖审查 | 变更的 manifest 与 lockfile | 完整依赖树，外加夜间 | 完整依赖树 |
| 静态应用安全测试 | 变更代码 | 完整扫描 | 完整扫描 |
| 端到端测试 | 子集 | 完整 | 完整 |
| 冒烟与性能 | 不运行 | 关键路径 | 在制品上必需 |

覆盖率指标及其默认门禁：

| 指标 | 证明什么 | 默认门禁 |
|---|---|---|
| 行覆盖率 | 代码被执行过，不代表已被验证 | 由实测基线推导的项目下限 |
| 分支覆盖率 | 每个条件的两个分支都运行过 | 涉及资金、权限或数据丢失的模块 70% |
| 变更覆盖率 | 新增与修改的可执行行被覆盖 | 每个 PR 80% |
| 变异分数 | 测试能够发现故意注入的缺陷 | 关键模块 60-70%，计划作业 |
| 契约覆盖率 | 每个变更的公共操作都有契约测试 | 变更操作的 100% |

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 下限取自最近一次实测的 main 构建 | 把下限提到理想化的 95% | 第一个 PR 会因旧工作而失败 |
| 覆盖率持续高于下限后才上调 | 为合并回退而下调下限 | 门禁现在保护得比以前少 |
| 带负责人与修复期限的隔离 | 没有 issue 的跳过标记 | 未测试行为变得不可见 |
| 带 90 天到期时间与工单的豁免 | 配置中的永久排除 | 临时规避变为政策 |
| 在 diff 上设变更覆盖率门禁 | 只在整个仓库上设覆盖率门禁 | 旧的绿色代码掩盖未测试的新代码 |
| 支付模块做变异测试 | 把行覆盖率目标提到 100% | 执行过但没有断言的行不足以证明任何内容 |

## 3. 静态分析与依赖校验

静态校验属于廉价证据：其在测试运行前即可发现整类缺陷。输出噪声大到人们直接忽略时，静态校验即不再有用，因此
门禁的质量取决于其严重级别映射。

- 在技术栈支持之处均将类型校验设为门禁：新 Python 模块用 Pyright 或 `mypy --strict`，`tsc --noEmit` 加
  严格选项，Go vet 与 build，Rust `cargo clippy`，Java `-Xlint:all`，C# 分析器。新模块从首次提交起采用
  严格设置，现有模块以迁移工单与负责人建立基线；警告先零新增并审查，按严重级别映射升级为阻塞。仅在编辑器
  中运行的类型校验仅具参考性质；门禁才使其成为规则。
- 在配置中一次性将每个工具的严重级别输出映射到三个桶：错误阻塞合并，警告不得增长且需审查，信息永不阻
  塞。不得按 PR 重新映射级别；级别随作者变化的校验不属于门禁，无人阅读的警告与被抑制的发现没有区别。映
  射应当置于工具配置文件中，使下一位读者能够找到，且审查时能够看到其变化。
- 对变更代码限定复杂度与重复度：每个函数的圈复杂度最多 10，认知复杂度最多 15，重复度低于代码行的 3%，
  最小块为 50 个 token（jscpd 默认值）；3% 上限属于团队阈值。在 diff 上报告上述指标，作为审查意见传
  播，并在代码库达到阈值后升级为阻塞；采用时直接设为阻塞将一次性阻塞所有 PR，一周内该校验即会被关闭。
  生成的数据表与穷举式分派代码应当显式豁免，并在配置中说明理由。
- 每次提交前与 CI 中都扫描工作区中的机密，并按计划扫描历史。任何检出均阻塞流水线，包括很可能是误报的情
  况，误报必须先排查再抑制。确认属于真实发现的，应当立即停止操作、保留证据并报告；调查结束并按 AU-1 取得
  明确同意后，方可轮换凭据与清理历史；仅删除那一行，机密仍留在每个克隆中。扫描器规则集及其版本应当与其余
  工具链一起固定，使规则更新成为受审变更。
- 在两个地方运行依赖审查：PR 上针对变更的 manifest 与 lockfile，夜间针对完整解析后的依赖树。以漏洞策
  略设定的严重级别使门禁失败，并使策略负责人与关闭发现的工程师分离；扫描位置与失败处理以本节与
  `gates.md` 为准，`security-compliance-conventions` 的漏洞策略管辖严重级别、修复期限与例外。任何严于漏洞
  策略的阈值需安全负责人批准并记录为例外。已接受的例外应当记录到具体依赖与版本上，不得记录到整个工具上，使新依赖无法继承该例外。
- 将安全发现交给其负责人，不得给校验改名。静态应用安全测试在 CI 中对变更代码运行；对结果做排查，为每个
  发现指定负责人，并以安全策略设定的严重级别阻塞。抑制像代码一样受审，需有理由与到期时间，不得在未察觉时加入
  基线。需要设计工作的发现应当转给所属团队的待办，并保持门禁结果可见，直至修复落地。
- 将格式化工具作为校验模式下的门禁。CI 运行格式化工具的校验模式，不得在流水线中重写文件；工具选择、版
  本固定与本地自动修复属于 code-style-conventions 的职责。推送前格式化，纯格式化编辑单独提交，使行为审
  查保持可读，工具升级导致的重排亦不得混入功能变更。
- 仅为现有违规保留基线，且仅作为棘轮。以固定工具版本生成一次，审查计数，并提交于工具配置旁。新错误立即
  失败；新警告使零新增警告校验失败并接受审查，按基线采用顺序升级为阻塞。基线计数只减不增，为吸收新违规而
  重新生成基线属于审查缺陷。工具升级后应当在单独变更中重新测量，使新规则作为规则受审，而非作为匿名的基线噪声。

基线采用顺序：

| 阶段 | 启用的内容 | 需要的证据 | 升级规则 |
|---|---|---|---|
| 现有代码 | 校验运行并记录当前违规 | 经审查的基线计数与固定的工具版本 | 从第一天起不允许新增错误；新增警告零新增并审查 |
| 新模块 | 严格设置，无基线条目 | 首次提交即在严格设置下干净运行 | 严格设置在该模块整个生命周期内保留 |
| 变更代码 | diff 上的零新增警告校验 | 警告计数持平或下降 | 连续一个季度无回退后转为阻塞 |
| 整个仓库 | 阻塞门禁 | 基线为零 | 删除基线文件 |

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 新模块从首次提交起通过 `mypy --strict` | 全仓启用严格模式并把 4000 个现有错误放入基线 | 严格规则从不改变行为 |
| 警告计数保持在当前值并接受审查 | 仅因构建通过而无视警告 | 警告噪声会滋长成新缺陷 |
| 带理由与到期时间的抑制 | 没有理由的行内 `# noqa` 或 `// nolint` | 没有解释的抑制会永远存在 |
| 提交前机密扫描加 CI | 发布前只扫一次机密 | 泄漏的凭据已经进入历史 |
| CI 中做格式校验 | CI 运行格式化工具并提交修复 | 受审的 diff 不是被测试的 diff |
| 审查变更的 lockfile 并夜间全量扫描 | 仅在有人记起时审查 | 新增的有漏洞传递依赖在未察觉时通过 |

## 4. 本地开发环境

本地环境是仅有一个用户的产品：下一位开发者。手工搭建需要一天时，人们将采用临时方案，而临时方案产生的结果
CI 无法复现。

- 提供一条命令，从全新克隆到可运行环境：`./scripts/bootstrap`、`make setup` 或项目等价物。该命令应当幂
  等、可安全重跑、缺少前置条件时明确报错，并在结束时打印解析出的工具与服务版本，使第一份 bug 报告即带有
  上述信息。工具链变化时，应当在干净克隆或容器上测试该命令；仅在作者机器上可用的 bootstrap 不算
  bootstrap。
- 将每个版本固定在仓库拥有的文件中：`.python-version`、`.nvmrc` 或 `packageManager`、`.tool-versions`、
  `rust-toolchain.toml`、`global.json`、提交的 lockfile，以及按 digest 或次版本标签指定的容器镜像。CI 读
  取同一批固定文件；流水线或文档中重复的版本字面量最终总会漂移。版本固定值的上调应当像任何依赖变更一样
  受审，并在变更中说明新版本为何对测试矩阵安全。
- 提供 devcontainer 或等价的可复现环境：带 compose 服务的 `devcontainer.json`，或 Nix、Devbox，或文档
  化的操作系统搭建步骤。语言运行时、数据库、队列与缓存的主版本和次版本应当与 CI 一致；任何地方出现浮动
  的 `latest` 均属缺陷，因为其会在未察觉时改变测试所证明的内容。应当优先使用 CI 已在使用的容器镜像，使 CI 失
  败的本地复现无需转换。
- 本地与 CI 之间仅保留一个目标。CI 调用 `make test`，不得在 YAML 中再抄一份命令。允许的差异（例如临时
  数据库或 CI 资源限制）应当逐一列明，并在环境文档中说明。本地通过而 CI 失败时，应当先修一致性缺陷再动
  测试；在证明相反之前，差异即 bug。
- 启动测试依赖时带健康检查，并设有时限地等待就绪。每次运行应当创建专用测试数据库或 schema，执行迁移，结
  束后删除。禁止对共享开发数据库运行销毁性测试，也禁止依赖同事碰巧留在该处的数据。服务无法在本地运行
  的，应当记录替代方案，并将需要真实服务的测试标记为集成测试。
- 提交 `.env.example`，包含每个必需键、假默认值与一行说明；忽略 `.env`。启动时应当校验配置，并以违规键
  快速失败，使缺失变量成为明确错误，而非静默改变行为的默认值。禁止在示例文件、fixture 或默认值中放入机
  密或个人值；使用合成值与 `example.test.invalid` 地址，并扫描仓库中违反该规则的情况。
- 将确定性的种子数据纳入版本控制，使播种操作幂等，并与测试 fixture 分开。种子账户使用合成身份，`reset`
  目标将环境恢复到测试可依赖的已知状态；手工创建的数据不属于 fixture。应当记录哪些种子集可用于演示，哪
  些仅用于使测试套件从已知状态启动。
- 提供健康检查与清理目标：`make doctor` 校验工具、版本、端口与服务健康；`make clean` 停止容器，删除
  卷、缓存与构建制品。CI teardown 中应当运行同样的清理，测试运行后不得留下容器、进程或临时数据库。失败
  的测试运行需要在清理前保留证据，因此在调试会话使用上述服务时，不得运行清理命令。

本地与 CI 一致性矩阵：

| 关注点 | 本地 | CI | 规则 |
|---|---|---|---|
| 运行时版本 | 从固定文件读取 | 从同一固定文件读取 | 每个版本只有一个来源 |
| 数据库 | Compose 服务，固定镜像 | 服务容器，相同固定镜像 | 主版本与次版本相同 |
| 环境变量 | `.env.example` 加本地 `.env` | CI 配置中设置的变量 | 键相同；值仅因环境而异 |
| 测试命令 | `make test` | `make test` | 一份定义，流水线 YAML 中不复制 |
| 测试数据 | 播种数据库加每次运行独立 schema | 只有每次运行独立 schema | 两条路径都使用合成数据 |
| 清理 | `make clean` | teardown 作业 | 容器、卷与缓存都被删除 |

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| README 中记录的 bootstrap 脚本 | 步骤版本不明的六步 wiki 页面 | 脚本能够存续，页面会逐渐失准 |
| 镜像固定为 `postgres:16.4` | `postgres:latest` | CI 与本地可能在未察觉时运行不同引擎 |
| 每次运行创建并删除独立 schema | 共享开发数据库 | 顺序依赖与数据漂移 |
| CI 调用 `make test` | 把测试命令复制进流水线 | 副本会与本地目标漂移 |
| `make doctor` 打印解析后的版本 | “仅在本机通过” | 版本是首先要比对的东西 |
| 种子数据已提交且幂等 | 由某位开发者手工执行一次的 SQL | 之后每个环境都从不同状态启动 |
