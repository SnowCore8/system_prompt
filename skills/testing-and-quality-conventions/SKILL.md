# 测试与质量规范

质量实践存在四种可预见的失效方式：测试不断言任何内容，仅证明进程启动过；门禁在截止压力下被豁免，直至无人
知晓绿色代表何种含义；本地环境与 CI 逐渐漂移，直至一台机器上的构建通过无法说明另一台机器的情况；不稳定
测试被重试或忽略，直至红色套件被视为只能接受的状态。本 skill 规定选择测试层级的单一决策流程、以实测数据为
依据的门禁与阈值集合、静态分析与依赖校验策略，以及使本地环境与 CI 一致的规则集。在生命周期中，它负责 G2 的
测试策略、G3 的增量验证、G4 的验证证据与 G5 的发布前复核输入。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充；同一范围内不得混用策略。

1. 强制性的平台、法律、宿主与全局用户约束。测试运行器、CI 能力、包管理器限制与强制性安全或监管校验均非
   可选事项。
2. 本 skill 的规则。测试层级、门禁、阈值与豁免以本文件与 `references/` 为准。
3. 现有项目配置与约定。自创阈值前先阅读 CI 配置、测试运行器设置、覆盖率配置与 bootstrap 脚本；这些是事实
   输入，依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充。
4. 个人偏好，不得覆盖以上三层。

边界与例外：

- 测试函数、文件、类、fixture 与测试替身的命名归 `naming-conventions`；测试中的注释与文档注释归
  `comment-conventions`。本 skill 所称接缝即测试边界；测试替身（fake、stub、mock、spy）的含义依
  `naming-conventions`，其中 `fake` 指可用的轻量实现，不是 `mock`。
- CI/CD 流水线、环境晋升与可观测性归 `release-operations-conventions`；本 skill 规定必须存在哪些门禁、阈值
  与失败处置，不规定流水线实现。
- 格式化与 linter 的风格规则归 `code-style-conventions`；本 skill 规定哪些静态校验作为门禁及严重级别。
- 依赖漏洞的严重程度与修复期限归 `security-compliance-conventions`；本 skill 规定漏洞扫描的门禁位置、命令与
  阻塞阈值，并管辖“扫描在何处运行、失败如何报告”。
- 契约设计归 `api-and-data-conventions`；本 skill 规定契约变更所需的契约测试与回归覆盖。
- 生成代码、第三方引入代码、迁移脚本与入口粘合代码不受覆盖率与风格门禁约束，每个排除项记录路径、原因、负责人
  与到期时间；保留生成标记，禁止排除手写源码树。
- 单人仓库、无部署仓库与遗留项目的采用方式见 [references/lifecycle.md](references/lifecycle.md) 的“裁剪与
  度量”一节；裁剪只减少工件，不减少验证。
- 阶段划分、门禁判定与风险分级归 `project-lifecycle-governance`；本 skill 提供测试与门禁证据，不自行决定
  Go/No-Go。强制规则冲突时报告用户裁决，不得自行选定。

## 生命周期定位

上游输入：G1 的结果指标与验收标准、G0 记录的风险级别，以及既有 CI 配置、覆盖率基线与不稳定测试清单。

下游交接：测试策略与阈值进入 G2；增量测试与 DoD 检查进入 G3；全量验证证据进入 G4；发布前冒烟、门禁快照与
制品可追溯性进入 G5；逃逸缺陷与门禁复盘进入 S6。

升级与停止：无阈值或无负责人的校验不得作为门禁；需要豁免时必须按程序取得具名批准并记录到期日；出现泄露嫌疑
时按 SP-6 停止并报告；不得为通过门禁删除、跳过或放松测试。门禁阈值争议升级到 G2 决策，由负责人裁定并记录。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S0 受理 | 依风险级别判断该变更需要的测试预算与门禁强度 | 风险级别与测试范围结论 |
| S1 探索 | 确认验收标准可否转化为可判定测试 | 可测性结论、验收标准的测试映射 |
| S2 计划 | 选定层级、定义门禁、阈值、负责人与豁免策略 | 测试策略、门禁清单、DoR 中的测试条件 |
| S3 构建 | 随变更提交测试，维护确定性，执行增量验证 | 增量测试、失败输出、DoD 检查结果 |
| S4 验证 | 运行全量套件与静态校验，整理验证证据 | 测试输出、覆盖率、SARIF、不稳定测试清单 |
| S5 发布 | 复核门禁未被下调、冒烟与制品可追溯 | 门禁快照、冒烟结果、豁免与未运行项 |
| S6 收尾 | 分析逃逸缺陷，回写测试与门禁 | 逃逸分析、门禁改进项与负责人 |

## 门禁与证据

阶段表列出各阶段的出口门；本表只列测试与门禁直接负责证据的门禁，其余由发布与生命周期角色汇总。

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 计划 | 层级矩阵、每道门禁的命令/触发器/阈值/负责人、豁免策略、DoR 测试条件 | Hold：阈值或负责人缺失；Recycle 到 S2：策略覆盖不到验收标准 |
| G3 构建 | 随变更提交的测试、失败输出、DoD 检查、未关闭风险 | Recycle 到 S3：行为变更无对应测试，或测试无法失败 |
| G4 验证 | 全量测试输出与退出码、覆盖率报告、SARIF、静态校验基线、不稳定测试清单 | Hold：证据不完整或来自旧提交；Recycle：删除或弱化测试、下调阈值；No-Go：必需校验持续失败且无有效豁免 |
| G5 发布 | 部署后冒烟结果、门禁快照（未下调阈值）、制品与报告可追溯 | Hold：冒烟未执行或门禁在本版本被放宽且无豁免记录 |
| G6 收尾 | 逃逸缺陷分析、门禁改进项与负责人 | Hold：复盘数据不全不得关闭；Recycle 到 S4：同类逃逸无新增测试或门禁 |

门禁证据必须绑定到具体提交；用本地通过代替 CI 输出、用重试掩盖首次失败、用旧版本的覆盖率报告，均不构成证据。
R0 任务可以合并 G3 与 G4 记录，但必须保留真实命令与输出。

## 工作流

1. 风险分类（S0/S2）。写明该代码失败将破坏什么：资金、个人数据、安全、可用性还是内部便利；支付路径与设置页
   标签不应当得到相同的测试预算。
2. 选择最廉价层级（S2）。优先单元测试，其次集成测试，再次端到端；仅端到端能失败的，在测试或工单中记录该接缝
   为何无法在更低层级测试。
3. 先定义门禁与阈值（S2）。写明命令、触发事件、必需状态校验、阈值与负责人；公布于项目质量策略，使贡献者推送
   前即可读到规则。
4. 使测试具备确定性（S3）。去除墙钟时间、未受控随机、网络访问、顺序依赖、共享状态与环境差异；注入时钟、为
   生成器设种子并打印种子与输入、隔离数据、等待条件而非 sleep；本地运行两次并比对结果。
5. 以同一份定义接入本地与 CI（S3）。把目标加入 bootstrap 或构建脚本，由 CI 调用该目标，确认两条路径读取相同
   的工具版本、环境变量与服务版本。
6. 验证失败路径（S4）。破坏一次代码或断言，确认门禁以可读信息失败；把观察到的失败保留在 PR 中，使门禁具有
   捕获过问题的记录。
7. 整理验证证据（S4）。汇总输出、覆盖率、SARIF 与不稳定测试清单，标注未运行项与已知风险，交独立审查者。
8. 发布前复核（S5）。对发布版本重跑必需门禁，确认未被下调、冒烟可执行、制品与报告可追溯。
9. 记录豁免（全程）。说明谁可以豁免哪道门禁、需要的记录、最长时限，以及由谁审查并在何时移除。

## 核心规则

- **测试必须有能力失败。** 以具体的期望值断言可观察行为。仅断言不抛异常，或仅断言 mock 被调用而不检查结果
  的测试，无法区分正常代码与损坏代码。说不出将捕获哪个错误值的断言，即未在测试行为。
- **在公共接缝处测试行为。** 通过调用方使用的接口调用被测单元；不得直接测试私有辅助函数；不改变行为的重构
  不得使测试套件失败。
- **在进程边界处 mock，禁止在进程内部 mock。** 进程边界指进程外依赖；注入时钟、随机源与项目的 repository
  `fake` 属于允许的替换。替换网络、时钟、随机性、文件系统与第三方服务；无法使用真实持久化的，使用 `fake` 或
  内存内适配器。禁止 mock 被测单元、值对象或项目自身的序列化。需要十几行初始化的 mock，说明测试边界位置错误。
- **每个测试只有一个失败原因。** 每个测试覆盖一种行为，报告一个明确的失败；有十个断言的测试仅报告第一个，
  掩盖其余九个；表驱动用例每个仅保留一个断言。
- **不弱化测试。** 不得自行删除、跳过或放松测试以使构建变绿；应当修复代码或记录缺陷，被弱化的测试将由审查
  驳回。确需豁免的，取得非变更作者的具名批准，记录范围与到期日，并在交付中披露；不得由智能体自行批准。
- **确定性是门禁。** 依赖时间、顺序、网络或共享状态的测试应当被隔离，不得重试；每个测试还应当独立于执行
  顺序与并行分片，使套件增长时可以横向扩展而非仅延长运行时间。结果会变化的测试套件不构成证据。
- **测试随变更提交。** 行为变更必须在同一次变更中新增或更新测试；审查者看不到对应测试的，应当将该变更视为
  不完整。
- **覆盖率是下限，不是目标。** 执行变更覆盖率，以及根据实测基线推导的项目下限；不得追求 100%，也不得为凑
  数字而排除源码。查看数字却不看产生它的命令与工具版本，结果不可复现。
- **每个门禁都有负责人与失败路径。** 写明负责人、阈值以及失败时的处置方式；无人负责的门禁总是最先被豁免。
- **失败阻止合并。** 红色的必需校验将阻塞集成；仅已证实的基础设施错误允许重试一次，并保留首次失败可见；不得
  凭仅靠重试得到的绿色合并。
- **带期限隔离不稳定测试。** 不稳定测试应当具有负责人与修复截止日期；依项目豁免程序取得具名批准后，方可退出
  阻塞性测试套件，并在期限前修复或删除。重试不构成修复。
- **豁免要记录且会到期。** 豁免写明门禁、范围、批准人、理由与到期日；没有到期时间的豁免即排除项，没有负责人
  的排除项即缺陷。
- **静态校验以团队真正会处理的严重级别设门禁。** 错误立即阻塞合并；警告先执行零新增校验并要求审查，按基线
  采用顺序升级为阻塞；现有违规建立基线，基线只缩不增。人人无视的校验比没有校验更糟；校验噪声大时修其配置或
  基线，不得学会无视它。
- **本地与 CI 运行相同命令。** 本地通过而 CI 失败属于一致性缺陷，不属于可接受的差异；先修一致性，再加校验。
- **固定版本并清理测试数据。** 在仓库中固定工具版本、服务镜像与 fixture；使用合成数据，每次运行分配唯一命名
  空间，并清理该次运行创建的内容。
- **GitHub Actions 是门禁实现，不是另一套规则。** 必需工作流置于 `.github/workflows/`，触发器同时覆盖
  `pull_request`、`merge_group` 与主干 `push`；job 名称必须与规则集中的必需校验逐字一致。不得用路径过滤跳过
  必需工作流；确需按路径选择时，保留一个始终运行的汇总 job 作为必需校验。
- **工作流按最小权限与固定依赖运行。** 顶层 `permissions` 默认只读，按 job 提升所需权限；第三方 action 固定到
  完整提交 SHA，并由依赖更新工具维护。PR 工作流不得在执行不可信代码的上下文中获得机密，不得使用
  `pull_request_target` 检出并运行 fork 代码；云部署使用 OIDC 短期凭据，不保存长期密钥。
- **测试结果必须可追溯。** 测试报告、覆盖率与 SARIF 作为制品上传并关联到提交，保留期覆盖一个发布周期；job
  设置超时与并发取消，避免旧运行占用队列；失败以首次运行结果为准。
- **门禁是受审契约。** 修改命令、阈值、范围或排除项，均属于附带说明理由、负责人与关联 issue 的受审变更；禁止
  在导致该门禁失败的同一变更中下调阈值。

## 测试层级矩阵

针对该风险使用能够失败的最廉价层级。速度预算针对标准 CI 运行器上的每个测试与每个套件；超出预算的测试先并行
分片或拆分，仍超预算的移入单独作业并记录理由；确属层级归位的可移至下一层并记录。预算本身视为门禁：超出预算
的测试即使通过，亦属于维护缺陷。

| 层级 | 范围 | 速度预算 | 可以 mock 什么 | 门禁 |
|---|---|---|---|---|
| 单元 | 一个公共函数、类或模块；所有 I/O 都被替换 | 每个测试 100 ms；套件 2 分钟 | 时钟、随机性、网络、文件系统、第三方客户端 | 每次提交与 PR 都必须 |
| 组件 | 一个模块及其真实的进程内协作者：路由、渲染器、序列化器 | 每个测试 1 秒；套件 5 分钟 | 仅第三方网络与平台服务 | PR 上必须 |
| 集成 | 一个真实边界：数据库、队列、缓存，或项目自身服务的网络调用 | 每个测试 5 秒；套件 15 分钟 | 系统边界之外的外部提供方 | 涉及的服务在 PR 上必须 |
| 契约 | 提供方与消费方之间的请求与响应约定 | 每次交互 1 秒；套件 3 分钟 | 另一方，由经验证的契约制品替代 | 变更方在 PR 上必须 |
| 端到端 | 从入口到持久化，运行在类生产栈上 | 每个测试 60 秒；套件 20 分钟 | 外部提供方使用沙箱；内部一律不 mock | main 上必须；PR 上跑子集 |
| 冒烟 | 已部署制品：健康检查、登录、一笔核心交易 | 总计 5 分钟 | 不 mock；使用真实依赖 | 部署后必须，并按计划运行 |
| 性能 | 定义负载相对基线的吞吐量与延迟 | 每个测试有预算；夜间套件 60 分钟 | 不 mock；固定数据集与固定硬件 | 关键路径在 main 上必须，其余为提示性 |
| 属性与模糊 | 生成输入，针对解析器、协议与计算不变式 | 每个属性 30 秒；套件 10 分钟 | 与单元相同；输入由生成器提供 | 夜间运行；变更的解析器在 PR 上另跑 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 没有断言的测试，或 `assert True` | 仅证明代码运行过，行为可能回退而套件仍然绿色 | 对成功与失败两种情形均断言可观察结果 |
| mock 被测类 | 测试校验的是 mock，损坏的单元仍能够通过 | 测试真实对象，仅替换其边界 |
| 过度 mock 所有协作者 | 系统无法启动时套件仍然绿色 | 进程内保留真实协作者，仅 fake I/O 边界 |
| 断言异步工作前先 `sleep()` | 依赖时序且慢；运行器负载高时失败 | 等待条件或事件，并设有时限 |
| 通过排除源码来通过覆盖率 | 数字变好，未测试代码却在增长 | 仅排除生成、第三方引入、迁移与入口粘合代码，并记录 |
| 发布压力下豁免红色门禁 | 一次豁免变成习惯，门禁不再具有约束力 | 记录带负责人与到期时间的豁免；安排修复 |
| 反复重试测试直到通过 | 掩盖真实竞态或损坏的测试，并使失败正常化 | 带负责人与期限隔离，然后修复根因 |
| 断言私有方法被调用 | 锁死实现；无害重构将失败 | 通过公共接口与可观察状态断言 |
| 只用整页快照作断言 | 一处无关改动即导致全部失败，审查者盲目通过 | 断言承载该行为的字段或元素 |
| 针对共享开发数据库测试 | 顺序依赖与数据漂移使失败无法复现 | 每次运行创建独立 schema 或容器，结束后删除 |
| 使用 `latest` 这类浮动工具版本 | 本地与 CI 不一致，旧问题重现 | 在仓库中固定版本，两条路径均读取它 |
| fixture 中含机密或个人信息 | 测试数据随套件分发，下次共享即外泄 | 使用合成值与 `example.test.invalid` 地址 |
| 为落地变更而下调阈值 | 门禁本应捕获的回退现在通过了 | 修复发现，或记录限定范围、有时限的豁免 |
| 跳过不稳定测试且无负责人 | 其覆盖的回退现在无人测试，亦无人知晓 | 隔离、指定负责人并创建跟踪 issue |
| 用端到端测试验证单元规则 | 慢、脆弱，且在错误的层级调试 | 将断言下移，仅保留一条端到端正常路径 |
| 把期望值改成与当前输出一致 | 测试从此认可该 bug，并阻碍修复 | 链接授权新值的规范或 issue，或修复代码 |

## 审查清单

- [ ] 每个测试仅声明一种行为，且能够仅因该原因失败。
- [ ] 断言检查可观察结果、值与错误路径，而不仅检查某次调用有返回；失败输出写明测试、输入、期望与实际。
- [ ] 由足够的最低层级覆盖该行为：组件测试在 PR 上必须，变更覆盖率达标，每个端到端测试均有理由。
- [ ] 仅 mock 进程边界；被测单元与项目自身的契约均为真实。
- [ ] 测试是确定的：注入时钟、随机数带种子、不使用 sleep、不依赖顺序与分片。
- [ ] 测试数据是合成的、每次运行带命名空间，并在运行后清理；工厂构建最小有效状态，没有测试改动共享 fixture。
- [ ] 新测试在 PR 流水线中不超过其层级的速度预算，并在修复前被观察到失败、修复后通过。
- [ ] 每个必需门禁均在 CI 配置中写明命令、负责人与阈值。
- [ ] 必需工作流未被路径过滤跳过，job 名称与规则集一致，并在 `merge_group` 上运行。
- [ ] 工作流权限最小、第三方 action 固定到完整提交，PR 不在有密钥的上下文执行不可信代码。
- [ ] 测试报告、覆盖率与 SARIF 作为制品可追溯；必需状态校验红色时阻止合并，首次失败未被重试掩盖。
- [ ] 覆盖率门禁将变更覆盖率与由实测基线推导的项目下限结合。
- [ ] 本次变更未下调阈值、扩大排除范围或增大基线；门禁改动已作为受审变更记录。
- [ ] 未删除、跳过或放松测试以换取绿色；豁免已按程序记录门禁、范围、批准人、理由、到期日与跟踪 issue。
- [ ] 静态校验的错误立即阻塞，新警告通过零新增校验并受审查，基线未增长。
- [ ] 新增直接依赖通过阻塞级别的审查，机密扫描干净。
- [ ] 本次变更涉及的每个不稳定测试均有负责人与修复截止日期。
- [ ] bootstrap 达到与 CI 相同的工具与服务版本，本地与 CI 运行同一个目标命令而非两份副本。
- [ ] 每个排除项均属于生成、第三方引入、迁移或入口粘合代码之一，并记录路径、原因、负责人与到期时间。
- [ ] 发布复核已重跑必需门禁，冒烟可执行，未运行项与已知风险已标注。

## 示例

<example>
场景：针对发票总额的单元测试。
做法：使用 `assert calculate_total(items) == 1800`，覆盖空、单项与边界用例表。税客户端在边界处被替换；mock
计算本身只会测到 mock，而不是算术。
</example>

<example>
场景：一个不稳定的登录测试。
做法：它单独运行时通过，在完整套件中失败，因为更早的测试留下了一个未关闭的会话。隔离将其移出阻塞集合，并
指定负责人与 14 天期限；修复方式是逐测试隔离，而不是重试循环。
</example>
