# 测试与质量规范

质量实践存在四种可预见的失效方式：测试不断言任何内容，仅证明进程启动过；门禁在截止压力下被豁免，直至无人
知晓绿色代表何种含义；本地环境与 CI 逐渐漂移，直至一台机器上的构建通过无法说明另一台机器的情况；不稳定测试被
重试或忽略，直至红色套件被视为只能接受的状态。每种失效方式均容易引入而难以逆转，因为团队会围绕失效的门
禁重组其习惯。本 skill 规定选择测试层级的单一决策流程、以实测数据为依据的门禁与阈值集合、静态分析与依赖校验策略，以
及使本地环境与 CI 一致的规则集。本 skill 适用于任何语言、测试运行器与 CI 系统，并将测试套件与流水线视为
同一份契约，而非两件互不相关的事务。其服务对象为新增测试的工程师、判断绿色构建的审查者，以及维护流水线可
信度的维护者。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充；同一范围内不得混用策略。

1. 强制性的平台、法律、宿主与用户全局约束。平台与工具链的强制要求（测试运行器、CI 能力、包管理器限制），
   以及强制性的安全或监管校验，均非可选事项。
2. 本 skill 的规则。测试层级、门禁、阈值与豁免以本文件与 `references/` 为准。
3. 现有项目配置与约定。自创阈值前，应当先阅读 CI 配置、测试运行器设置、覆盖率配置与 bootstrap 脚本；
   上述内容属于事实输入，依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖以上三层。

- 测试函数、文件、类、fixture 与测试替身的命名，由 naming-conventions skill 管辖。本 skill 规定存在哪些
  层级、每层断言什么，以及测试套件如何对分支设门禁。
- 测试中的注释与 docstring，由 comment-conventions skill 管辖。本 skill 规定断言、fixture 与失败信息，不
  重述注释规则。
- CI/CD 流水线、环境晋升、可观测性与发布，由 release-operations-conventions skill 管辖。本 skill 规
  定必须存在哪些门禁、其阈值，以及门禁处的失败如何处理。
- 格式化工具与 linter 的风格规则，由 code-style-conventions skill 管辖。本 skill 规定哪些静态校验作为门
  禁，以及以什么严重级别。
- 依赖漏洞策略，由 security-compliance-conventions skill 管辖。本 skill 规定漏洞扫描作为质量门禁在何处、
  何时运行，以及阻塞性发现如何报告。
- 契约设计，由 api-and-data-conventions skill 管辖。本 skill 规定契约变更所需的契约测试与回归测试覆盖。
- 生成代码、第三方引入代码、迁移脚本与入口粘合代码不受覆盖率与风格门禁约束。每个排除项应当记录路径、原
  因、负责人与到期时间；保留生成标记，禁止排除手写的源码树。
- 在遗留项目中采用本规范属于分阶段变更，不属于重写。代理应当以经审查的计数为现有违规建立基线，对每个变
  更文件执行新规则，并随基线缩小删除该基线。一次性将所有门禁设为阻塞级别，必然在一周内被全部关闭。
- 测试套件属于变更的一部分。行为变更必须在同一次变更中新增或更新其测试；审查者看不到行为变更所对应测试
  的，应当将该变更视为不完整。
- 门禁属于一份契约：修改其命令、阈值、范围或排除项，均属于附带说明理由、负责人与关联 issue 的受审变
  更。禁止在导致该门禁失败的同一变更中下调阈值。
- 两条规则冲突的，代理应当说明冲突与所选规则，并将决定记录于项目的质量策略中，使后续变更遵循该决定。
- **单人仓库与无部署仓库。** 单人维护允许自审，但门禁不得因单人维护而整体豁免；确需单条豁免的，仍按第
  7 步与“豁免要记录且会到期”写明具名批准人、到期日与追踪 issue，无第二人时批准人由维护者具名，并在治
  理文件记录该自批与补偿控制；无部署仓库跳过冒烟与性能层级，其余层级照常。

## 流程

1. 代理应当先对风险分类。写明该代码失败将破坏什么：资金、个人数据、安全、可用性，还是内部便利。风险决
   定所需层级，以及门禁是阻塞还是仅报告；支付路径与设置页标签不应当得到相同的测试预算。
2. 选择能够捕获该失败的最廉价层级。优先单元测试而非集成测试，优先集成测试而非端到端测试，参照下述测试
   层级矩阵。仅端到端测试能够失败的，应当在测试或工单中记录该接缝为何无法在更低层级测试，以免下一位审
   查者重新还原该决定。
3. 编写测试之前先定义门禁与阈值。写明命令、触发事件、必需状态校验、阈值与负责人。既无阈值又无负责人的
   校验不产生约束力。应当将门禁公布于项目的质量策略中，使贡献者在推送前即可读到规则。
4. 使测试具备确定性。去除墙钟时间、随机性、网络访问、顺序依赖、共享状态与环境差异；注入时钟、为生成器
   设种子、隔离数据，并等待条件而非 sleep。代理应当在本地运行测试套件两次并比对结果；仅通过一次的测试
   尚未证明确定性。
5. 以同一份定义接入本地与 CI。将目标加入 bootstrap 或构建脚本，由 CI 调用该目标，并确认两条路径读取相
   同的工具版本、环境变量与服务版本。
6. 验证失败路径。破坏一次代码或断言，确认门禁以可读信息失败；不会失败的门禁不属于门禁。应当将观察到的
   失败保留于 PR 中，使门禁具有捕获过问题的记录，而非仅有一句声称。
7. 记录豁免策略。说明谁可以豁免哪个门禁、需要的记录、最长时限，以及由谁审查并在何时移除；没有记录的豁
   免将变为永久排除。

## 核心规则

- **测试必须有能力失败。** 以具体的期望值断言可观察行为。仅断言不抛异常，或仅断言 mock 被调用而不检查
  结果的测试，无法区分正常代码与损坏代码。说不出自己将捕获哪个错误值的断言，即未在测试行为。
- **在公共接缝处测试行为。** 通过调用方使用的接口调用被测单元。不得直接测试私有辅助函数；不改变行为的
  重构不得使测试套件失败。
- **在进程边界处 mock，禁止在进程内部 mock。** 替换网络、时钟、随机性、文件系统与第三方服务。该层无法
  使用真实持久化的，使用 fake 或内存内适配器。禁止 mock 被测单元、值对象或项目自身的序列化。需要十几
  行初始化代码的 mock，说明接缝位置错误。
- **每个测试只有一个失败原因。** 每个测试覆盖一种行为，报告一个明确的失败。有十个断言的测试仅报告第一
  个，掩盖其余九个；表驱动用例每个仅保留一个断言。
- **不弱化测试。** 禁止为使构建变绿而删除、跳过或放松测试。应当修复代码或记录缺陷；被弱化的测试将由审
  查驳回，确需发布的，适用豁免程序。
- **确定性是门禁。** 依赖时间、顺序、网络或共享状态的测试应当被隔离，不得重试。每个测试还应当独立于执
  行顺序与并行分片，使套件增长时可以横向扩展，而非仅延长运行时间。结果会变化的测试套件不构成证据。
- **覆盖率是下限，不是目标。** 执行变更覆盖率，以及根据实测基线推导的项目下限。不得追求 100%，也不得
  为凑数字而排除源码。查看覆盖率数字却不看产生它的命令与工具版本，结果不可复现。
- **每个门禁都有负责人与失败路径。** 写明负责人、阈值以及失败时的处置方式；无人负责的门禁总是最先被豁
  免。
- **失败阻止合并。** 红色的必需校验将阻塞集成。仅已证实的基础设施错误允许重试一次，并保留首次失败可见；
  不得凭仅靠重试得到的绿色合并。
- **带期限隔离不稳定测试。** 不稳定测试应当具有负责人与修复截止日期，退出阻塞性测试套件，并在期限前修
  复或删除。重试不构成修复。
- **豁免要记录且会到期。** 豁免写明门禁、范围、批准人、理由与到期日。没有到期时间的豁免即排除项，没有
  负责人的排除项即缺陷。
- **静态校验以团队真正会处理的严重级别设门禁。** 新违规必须失败；现有违规建立基线，基线只缩不增。人人
  无视的校验比没有校验更糟，因为其训练人员对红色输出不作处置。校验噪声大时，应当修其配置或基线，不得学会无视
  它。
- **本地与 CI 运行相同命令。** 本地通过而 CI 失败属于一致性缺陷，不属于可接受的差异。应当先修一致性，
  再加校验。
- **固定版本并清理测试数据。** 在仓库中固定工具版本、服务镜像与 fixture。使用合成数据，每次运行分配唯
  一命名空间，并清理该次运行创建的内容。

## 测试层级矩阵

针对该风险使用能够失败的最廉价层级。速度预算针对标准 CI 运行器上的每个测试与每个套件；超出预算的测试下移
一层或被拆分。应当将预算本身视为门禁：超出预算的测试即使通过，亦属于维护缺陷。

| 层级 | 范围 | 速度预算 | 可以 mock 什么 | 门禁 |
|---|---|---|---|---|
| 单元 | 一个公共函数、类或模块；所有 I/O 都被替换 | 每个测试 100 ms；套件 2 分钟 | 时钟、随机性、网络、文件系统、第三方客户端 | 每次提交与 PR 都必须 |
| 组件 | 一个模块及其真实的进程内协作者：路由、渲染器、序列化器 | 每个测试 1 秒；套件 5 分钟 | 仅第三方网络与平台服务 | PR 上必须 |
| 集成 | 一个真实边界：数据库、队列、缓存，或项目自身服务的网络调用 | 每个测试 5 秒；套件 15 分钟 | 系统边界之外的外部提供方 | 涉及的服务在 PR 上必须 |
| 契约 | 提供方与消费方之间的请求与响应约定 | 每次交互 1 秒；套件 3 分钟 | 另一方，由经验证的契约制品替代 | 变更方在 PR 上必须 |
| 端到端 | 从入口到持久化，运行在类生产栈上 | 每个测试 60 秒；套件 20 分钟 | 外部提供方使用沙箱；内部一律不 mock | main 上必须；PR 上跑子集 |
| 冒烟 | 已部署制品：健康检查、登录、一笔核心交易 | 总计 5 分钟 | 不 mock；使用真实依赖 | 部署后必须，并按计划运行 |
| 性能 | 定义负载相对基线的吞吐量与延迟 | 每个测试有预算；夜间套件 60 分钟 | 不 mock；固定数据集与固定硬件 | 关键路径在 main 上必须，其余为提示性 |
| 属性与模糊 | 生成输入，针对解析器、协议与计算不变式 | 每个属性 30 秒；套件 10 分钟 | 与单元相同；输入由生成器提供 | 夜间运行；变更的解析器在 PR 上另跑 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 没有断言的测试，或 `assert True` | 仅证明代码运行过，不证明其工作正常；行为可能回退而套件仍然绿色 | 对成功与失败两种情形均断言可观察结果 |
| mock 被测类 | 测试校验的是 mock，损坏的单元仍能够通过 | 测试真实对象，仅替换其边界 |
| 过度 mock 所有协作者 | 系统无法启动时套件仍然绿色 | 进程内保留真实协作者，仅 fake I/O 边界 |
| 断言异步工作前先 `sleep()` | 依赖时序且慢；运行器负载高时失败 | 等待条件或事件，并设有时限 |
| 通过排除源码来通过覆盖率 | 数字变好，未测试代码却在增长 | 仅排除生成、第三方引入、迁移与入口粘合代码，每项记录路径、原因、负责人与到期时间 |
| 发布压力下豁免红色门禁 | 一次豁免变成习惯，门禁不再具有约束力 | 记录带负责人与到期时间的豁免；安排修复 |
| 反复重试测试直到通过 | 掩盖真实竞态或损坏的测试，并使失败正常化 | 带负责人与期限隔离，然后修复根因 |
| 断言私有方法被调用 | 锁死实现；无害重构将失败 | 通过公共接口与可观察状态断言 |
| 只用整页快照作断言 | 一处无关改动即导致全部失败，审查者盲目通过 | 断言承载该行为的字段或元素 |
| 针对共享开发数据库测试 | 顺序依赖与数据漂移使失败无法复现 | 每次运行创建独立 schema 或容器，结束后删除 |
| 使用 `latest` 这类浮动工具版本 | 本地与 CI 不一致，旧问题重现 | 在仓库中固定版本，两条路径均读取它 |
| fixture 中含机密或个人信息 | 测试数据随套件分发，下次共享即外泄 | 使用合成值与 `example.test.invalid` 地址 |
| 为落地变更而下调阈值 | 门禁本应捕获的回退现在通过了 | 修复发现，或记录限定范围、有时限的豁免 |
| 跳过不稳定测试且无负责人 | 其覆盖的回退现在无人测试，亦无人知晓 | 隔离、指定负责人并创建跟踪 issue |
| 用端到端测试验证单元规则 | 慢、脆弱，且在错误的层级调试 | 将断言下移，仅保留一条端到端正常路径 |
| 把期望值改成与当前输出一致 | 测试从此认可该 bug，并阻碍修复 | 链接授权新值的规范或 issue，或修复代码 |

## 审查清单

- [ ] 每个测试仅声明一种行为，且能够仅因该原因失败。
- [ ] 断言检查可观察结果、值与错误路径，而不仅检查某次调用有返回。
- [ ] 由足够的最低层级覆盖该行为，每个端到端测试均有理由。
- [ ] 仅 mock 进程边界；被测单元与项目自身的契约均为真实。
- [ ] 测试是确定的：注入时钟、随机数带种子、不使用 sleep、不依赖顺序。
- [ ] 测试数据是合成的、每次运行带命名空间，并在运行后清理。
- [ ] 工厂构建最小有效状态；没有测试改动共享 fixture。
- [ ] 每个必需门禁均在 CI 配置中写明命令、负责人与阈值。
- [ ] 覆盖率门禁将变更覆盖率与由实测基线推导的项目下限结合。
- [ ] 本次变更未下调阈值、扩大排除范围或增大基线。
- [ ] 静态校验对新违规失败，基线未增长。
- [ ] 新增直接依赖通过阻塞级别的审查，机密扫描干净。
- [ ] 本次变更涉及的每个不稳定测试均有负责人与修复截止日期。
- [ ] bootstrap 达到与 CI 相同的工具与服务版本。
- [ ] 本地与 CI 运行同一个目标命令，而非两份副本。
- [ ] 失败输出写明失败的测试、输入，以及期望值与实际值。
- [ ] 若有豁免，写明门禁、范围、批准人、理由、到期时间与跟踪 issue。
- [ ] 每个排除项均属于生成、第三方引入、迁移或入口粘合代码之一，并记录路径、原因、负责人与到期时间。
- [ ] 新测试在 PR 流水线中不超过其层级的速度预算。
- [ ] 新测试在修复前被观察到失败，修复后通过。

## 示例

<example>
场景：针对发票总额的单元测试。
做法：使用 `assert calculate_total(items) == 1800`，覆盖空、单项与边界用例表。税客户端在边界处被替换；
mock 计算本身只会测到 mock，而不是算术。
</example>

<example>
场景：订单服务的契约测试。
做法：消费方记录 `POST /v1/orders` 的期望，提供方在自己的流水线中验证它们。字段重命名会使提供方在端到端
测试看到之前就失败。
</example>

<example>
场景：变更上的覆盖率。
做法：PR 新增 120 行可执行代码并覆盖了 96 行，因此变更覆盖率为 80%，通过；项目下限 75% 保持不变，因为
实测基线未变。下调下限会掩盖这次下降。
</example>

<example>
场景：一个不稳定的登录测试。
做法：它单独运行时通过，在完整套件中失败，因为更早的测试留下了一个未关闭的会话。隔离将其移出阻塞集合，
并指定负责人与 14 天期限；修复方式是逐测试隔离，而不是重试循环。
</example>

<example>
场景：本地一致性。
做法：`make test` 与 CI 作业针对固定的数据库镜像运行同一个目标，因此本地通过而 CI 失败即指向真实缺陷。在
CI 配置中重新实现测试命令，正是两条路径漂移的原因。
</example>
