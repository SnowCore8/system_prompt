# 代码审查

审查是第二个人判断变更是否正确、安全与可维护的环节，投入的注意力应当与出错代价成正比。失效的审查有两种：
深度与风险脱节（低风险变更过度审查、高风险变更走形式），以及评论不可执行（作者无法区分阻塞与偏好）。本
skill 规定审查深度与风险分级、审查清单与关注点、作者与审查者职责，以及审查门禁与 R1/R2 独立审查要求，
证据接入 G3 构建与 G4 验证门禁。

## 适用范围与优先级

效力按下列层级判断，高层覆盖低层：

1. 平台与组织的强制策略：必需校验、审查要求与签名提交规则。
2. 本 skill 的规则与默认值，见本文件与 `references/`。
3. 项目既有约定：CODEOWNERS、贡献者指南与审查配置属于事实输入。
4. 个人偏好与写作习惯，不得覆盖以上三层。

边界与例外：

- 分支模型、合并方式与代码所有权归 `vcs-collaboration`；本 skill 只规定审查行为本身。
- 测试与门禁阈值归 `testing-quality`；审查者核对测试充分性，不重复运行全部校验。
- 发布批准与回滚归 `release-operations`；热修复的审查要求由本 skill 规定。
- 生成产物与机器产出免于逐行审查：审查生成器输入、重新生成命令与生成标记；手工修改生成产物不享受免审，按普通变更审查。
- 审查记录中不得写入机密或个人信息；发现泄露按 SEC-6 停止并报告。

## 生命周期定位

上游输入：G2 的范围与风险级别；审查级别表由本 skill 在 S2 形成。本 skill 在 S3 准备请求并执行审查，在 S4
提供批准与独立审查证据，在 S5 覆盖热修复审查。
下游交接：审查结论交给合并门禁与发布角色；分歧决定记录进入请求或 ADR。
升级与停止：阻塞线程未解决不得合并；分歧升级归属团队决策负责人；审查者不可达时改派回退审查者；批准过期
的请求回到审查状态。

| 阶段 | 职责 | 产出与证据 |
|---|---|---|
| S2 设计 | 按风险级别确定审查深度、审查者构成与周转预期 | 审查级别表、审查者分派 |
| S3 构建 | 准备体量合规的请求、完成自审并按风险请求审查 | 请求记录、自审结果 |
| S4 验证 | 确认批准有效、阻塞线程解决、独立审查结论齐备 | 批准记录、审查结论、R1/R2 审查证据 |
| S5 发布 | 审查热修复与向前移植，核对发布路径审查 | 热修复审查记录 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G3 构建 | 体量合规的请求、描述与自审、必需校验在合并结果上通过 | 退回修改，不得合入 |
| G4 验证 | 归属审查者的批准、阻塞评论已解决；R1 至少一名非作者审查，R2 两名独立审查且执行者不自批 | Hold，重新审查增量 |

R0 变更以自审记录与必需校验代替人工批准；R1 的 G4 需要至少一名非作者审查；R2 需要两名独立审查者（其中
一名为领域或安全审查者），且执行者不得担任批准者。批准与提交绑定，实质性推送后批准过期。
