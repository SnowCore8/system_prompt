# 项目生命周期治理

项目失效通常不是因为文档太少，而是因为决策没有证据、阶段被跳过、角色没有决策权、交付节奏与治理脱节。
Stage-Gate 提供承诺与投资决策点，Agile 提供短反馈循环；两者组合成一条生命周期，既能约束高风险项目，
也能让日常任务保持轻量。本 skill 定义阶段、门禁、风险分级、角色、工件、度量、组合与裁剪方式，使智能体
任务、软件交付与组织级项目管理使用同一套语言。具体代码、架构、测试、安全与发布规则仍由各专业 skill
负责；本 skill 决定何时应用它们、以什么证据通过门禁、谁对结果负责。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 宿主、法律、平台与 `rules/global-user-constraints.md` 的强制约束。授权、保密、不可逆、诚实与意图
   规则不得因项目进度、阶段门或敏捷节奏而放松。
2. 本 skill 的生命周期模型、门禁判定、风险分级、角色、工件、度量与组合规则。
3. 各专业 skill 的技术规则。它们在本 skill 确定的阶段与门禁内执行，具体阈值与做法以各自 skill 为准。
4. 既有项目约定与事实。项目约定仅在本 skill 未规定时补充，不得覆盖上述三层。

本 skill 管辖：阶段划分、门禁决定、风险分级、裁剪、角色与决策权、阶段工件、生命周期度量、组合与依赖。
本 skill 不管辖：代码风格（`code-style-conventions`）、命名（`naming-conventions`）、注释
（`comment-conventions`）、架构（`architecture-and-design-conventions`）、目录与包（`project-structure-conventions`）、
接口与数据（`api-and-data-conventions`）、并发（`concurrency-conventions`）、性能（`performance-conventions`）、
调试（`debugging-conventions`）、测试实现与门禁阈值（`testing-and-quality-conventions`）、安全控制
（`security-compliance-conventions`）、发布操作（`release-operations-conventions`）、版本控制与工作树
（`vcs-collaboration-conventions`、`worktree-collaboration-conventions`）、文档格式（`documentation-conventions`）、
提示词与 skill 包（`prompt-authoring`、`system-prompt-authoring`、`skill-authoring`）、仓库治理
（`repository-governance-conventions`）。上述 skill 的规则与本 skill 冲突时，安全、授权与不可逆约束优先；
其余冲突按第 1 节的效力顺序处理。

## 生命周期定位

本 skill 是生命周期的主持者，不替代专业判断。它在 S0 固定请求与风险，在 S1/S2 组织承诺，在 S3/S4 检查
证据，在 S5/S6 组织发布与收益复盘。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S0 受理 | 分类、授权、风险分级、停止条件与负责人 | 受理记录、风险依据、下一门禁 |
| S1 探索 | 组织问题、用户、结果指标、选项与收益基线 | 章程或探索简报、G1 建议 |
| S2 计划 | 固定范围、验收、设计、依赖、测试与回滚 | 计划基线、风险登记、G2 记录 |
| S3 构建 | 维护迭代目标、DoR/DoD、WIP 与交接 | 迭代记录、增量证据、例外与升级 |
| S4 验证 | 组织独立审查与验收，检查证据完整性 | 验证证据包、G4 结论 |
| S5 发布 | 组织发布准备、回滚与通告，确认生产授权 | 发布记录、G5 决定 |
| S6 收尾 | 对照收益、复盘、归档、交接与退出 | 收尾报告、行动项、G6 记录 |

上游：用户、发起人、产品负责人、各专业 skill 的事实与结论。下游：交付团队、运营、审查者与组合委员会。
停止条件：授权不清、风险级别无法确定、关键依赖未确认、证据缺失、出现安全或不可逆风险时，停止推进并
报告；不得用“先做一点”绕过门禁。

## 生命周期总览

| 阶段 | 核心问题 | 主要活动 | 出口门 |
|---|---|---|---|
| S0 受理 | 请求是什么，谁授权，风险多大？ | 分类、授权、风险分级、停止条件、负责人 | G0 受理门 |
| S1 探索 | 问题是否真实，谁受益，成功标准是什么？ | 用户与问题、约束、选项、建议、收益基线 | G1 立项门 |
| S2 计划 | 做什么，不做什么，如何验收？ | 范围、设计、任务、依赖、风险、测试与发布计划 | G2 计划门 |
| S3 构建 | 能否以小步增量交付？ | 迭代、实现、测试、文档、评审、集成 | G3 构建门 |
| S4 验证 | 是否满足验收与质量要求？ | 测试、安全、性能、并发、文档、独立审查 | G4 验证门 |
| S5 发布 | 能否安全上线并回滚？ | 版本、变更记录、部署、回滚、可观测性、通告 | G5 发布门 |
| S6 运营与收尾 | 是否产生预期价值，留下什么？ | 监控、事故、收益、偏差、复盘、归档、交接 | G6 收尾门 |

阶段不是日历上的串行瀑布。R0 可以合并记录与门禁，R1 可以精简工件，R2 必须独立审查；S3/S4 以迭代循环
推进，但迭代不能替代门禁。每个阶段都要有入口条件、可核验输出与明确出口决定；没有出口决定的阶段视为
未结束。详细活动、输入输出与裁剪见 `references/stages.md`。

## 风险分级与裁剪

| 级别 | 典型情形 | 门禁要求 | 工件与批准 |
|---|---|---|---|
| R0 轻量 | 可逆、局部、无共享状态、无生产影响；单文件修改、只读查询、措辞修正 | G0 与 G2 合并，G4 与 G5 合并；仍须验证 | 一页任务记录；执行者自检；无需独立批准 |
| R1 标准 | 多文件、共享分支或 PR、依赖变更、一般业务影响；功能开发、重构、测试调整 | G0–G5 轻量执行；G4 独立审查 | 精简章程、计划、验证证据、发布记录 |
| R2 关键 | 生产、数据迁移、安全或凭据、合规、跨团队、不可逆；部署、权限变更、发布 | G0–G6 全阶段独立审查；G4 与 G5 不得合并 | 完整章程、设计、验证、回滚演练、门禁记录 |

- 在 G0 记录风险级别与判断依据；范围、影响、授权或依赖变化时重新分级，不得沿用旧级别。
- 裁剪只减少工件与会议，不减少证据、审查、安全控制与授权。R0 可以合并门禁记录，但不得跳过验证；R1
  可以使用精简模板，但不得省略独立审查；R2 不得自批、不得省略回滚演练、不得在证据缺失时 Go。
- 无法判断级别时取较高一级。以“任务很小”为由跳过 G0 或 G4，属于治理缺陷。
- 裁剪矩阵、合并方式与不可裁剪项见 `references/stages.md` 与 `references/gates.md`。

## 门禁判定

- 决定只有六种：Go（进入下一阶段）、Conditional Go（带条件进入）、Hold（证据不足暂停）、Recycle
  （退回指定阶段返工）、No-Go（停止或关闭）、Defer（组合层延期，项目层不得使用）。
- Conditional Go 必须写明条件、负责人、到期日与验证证据；条件未关闭的，不得进入下一阶段。条件不得
  包含“补做安全审查”或“补做验收测试”一类本应在当前门禁完成的证据。
- 每个门禁留下一条记录：门禁编号、日期、负责人、风险级别、证据链接、决定、条件、下一门禁。记录模板
  见 `references/templates.md`。
- 门禁证据必须可核验：测试输出、审查结论、演练记录、指标数据、签字或明确批准。口头保证、计划中的
  工作与“应该没问题”不构成证据。
- 紧急事件按 `AU-5` 先止损，事后补门禁记录与复盘；补记不得改写已发生的事实，也不得把例外变成常态。
- 组合层使用 Defer 管理队列；项目层使用 Recycle 返工。不得用 Defer 掩盖 No-Go，也不得用 Recycle
  无限循环。
- 决策权限、法定人数、R2 的独立审查与升级路径见 `references/gates.md`。

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G0 | 请求复述、授权依据、风险级别、停止条件、负责人 | 澄清或 Hold；不得开始修改 |
| G1 | 问题、用户、结果指标、收益基线、选项比较 | Recycle 到探索或 No-Go |
| G2 | 范围与非范围、验收标准、风险登记、依赖、回滚计划 | Hold 或 Recycle；不得带缺口构建 |
| G3 | DoR/DoD 检查、迭代目标、WIP、增量与交接记录 | Recycle 到构建 |
| G4 | 证据完整性、独立审查、验收结论、未验证项 | Recycle 或 Hold；不得放行 |
| G5 | 发布准备度、回滚演练、生产授权、通告与观测 | Hold；不得上线 |
| G6 | 收益对照、偏差、复盘行动、归档与交接 | 补充证据或转入运营改进 |

本 skill 不代替专业 skill 出具技术结论；它只确认证据是否齐全、决定是否成立、责任人是否明确。证据缺失
或责任人缺失时，决定为 Hold 或 Recycle，不得以“已经开会”代替。

## 敏捷交付

- 构建与验证阶段以迭代交付：每个迭代有目标、有序条目、WIP 上限、评审与回顾。人类团队通常以一至两周
  为迭代；智能体任务以一次可验收增量为迭代，不套用固定日历。
- 进入迭代前满足 Definition of Ready：结果、验收标准、依赖、负责人、估算、测试方式、风险级别与回滚
  方式均已明确。完成时满足 Definition of Done：实现、测试、文档、安全与依赖检查、审查、发布说明与
  已知缺陷处理均已完成。
- Stage-Gate 与 Agile 的分工：门禁做承诺、投资与风险决策；迭代做交付与反馈。不得用迭代评审替代门禁，
  也不得用门禁绕过迭代中的测试与审查。
- 度量以流动与结果为主：前置时间、周期时间、吞吐、在制品、可预测性、逃逸缺陷、变更失败率与收益实现。
  度量用于改进，不用于排名或施压。
- 迭代节奏、WIP 上限、DoR/DoD、评审与回顾的操作细节见 `references/agile.md`；指标定义与反作弊规则见
  `references/metrics.md`。

## 角色与决策权

| 角色 | 组织级 | 项目级 | 智能体任务级 | 主要决策 |
|---|---|---|---|---|
| 发起人 / 组合委员会 | 资助、优先级、组合门禁 | 章程批准、R2 门禁 | 用户 | Go/No-Go、预算与范围变更 |
| 产品负责人 | 收益与组合对齐 | 结果、待办、验收 | 用户或委托方 | 验收标准与优先级 |
| 项目负责人 | 组合协调 | 计划、执行、风险、门禁准备 | 主智能体 | 计划与资源取舍 |
| 架构负责人 | 组合架构标准 | 边界、关键技术、ADR | 主智能体 + 专业 skill | 架构方案与例外 |
| 交付团队 | 跨项目依赖 | 实现、测试、文档、评审 | 子智能体与工具 | 技术方案与任务拆分 |
| 质量 / 审查 | 组合质量指标 | 独立审查、G4 证据 | 自动校验 + 人工审查 | 质量结论与返工 |
| 安全 / 合规 | 组织风险 | 威胁、隐私、许可证 | 安全 skill 与人工 | 安全门禁与例外 |
| 运营 / SRE | 运营标准 | 发布、回滚、值守 | 发布 skill 与人工 | G5 发布准备度 |
| PMO | 流程、日历、度量 | 门禁日历与模板 | 不设独立角色 | 流程支持，不代替决策 |

角色可以兼任，但 R2 的独立审查与批准不得由同一人完成。智能体任务中，用户承担发起人与产品负责人，
主智能体承担项目负责人，子智能体承担交付团队；R2 的人工批准不得由智能体代替。角色、职责、决策权、
法定人数与升级路径的完整表见 `references/roles.md`。

## 工件与度量

| 工件 | 最小内容 | 负责人 | 门禁 |
|---|---|---|---|
| 受理记录 | 请求、分类、授权、风险级别、停止条件 | 项目负责人 | G0 |
| 章程 / 探索简报 | 问题、用户、结果指标、约束、选项、建议、收益基线 | 产品负责人 | G1 |
| 计划 / 待办 | 范围、验收、任务、依赖、风险、测试、发布与回滚 | 项目负责人 | G2 |
| 设计与 ADR | 边界、决定、替代方案、后果、状态 | 架构负责人 | G2/G3 |
| 验证证据 | 测试、审查、安全、性能、并发、验收结论 | 质量与安全 | G4 |
| 发布记录 | 版本、变更、部署、回滚、可观测性、通告 | 运营 | G5 |
| 收尾报告 | 收益对照、偏差、教训、归档与交接 | 项目负责人 | G6 |

度量分为结果、流动、质量、治理与能力五类；指标定义、计算方式、审查节奏与反作弊规则见
`references/metrics.md`。不得用单一指标替代门禁判断；指标恶化时先查根因，不得直接调整目标。工件厚度
随风险裁剪，但每项事实只保留一个权威归属，证据必须可由未参与者复核。

## 组合、依赖与容量

- 组合层以价值、风险、战略契合、容量与依赖排序；不以先来后到、职位或声音大小排序。
- 受理漏斗、组合登记、门禁日历与容量视图由 PMO 维护；投资、优先级、Defer 与退出由组合委员会决定。
- 依赖分为技术、数据、团队、供应商与合规五类；G1/G2 登记接口、负责人、窗口、验证与失败回退。
- 关键依赖未确认时，门禁为 Hold 或 Recycle；不得把“预计可用”写成承诺。
- 容量包括人员、预算、环境、审查与运维能力；瓶颈在审查或运维时，增加开发吞吐只会扩大在制品。
- 项目退出、移交或退役必须有 G6 记录、数据与制品处置、用户通告与归档；不得以“自然结束”代替收尾。
- 组合节奏、排序模型、依赖图与容量规划见 `references/portfolio.md`。

## 三视角

同一生命周期适用于三种场景，差异只在工件厚度、决策权限与时间尺度。

- **智能体任务**：每个请求视为微项目，默认 R0；G0 必须确认授权与停止条件，G4 必须有验证证据。多文件、
  共享分支或不可逆操作升为 R1/R2。
- **软件交付**：以产品待办与发布为核心，G1 确认结果与收益基线，G2 固定验收与回滚，G3/G4 以迭代增量
  推进，G5 以发布记录结束。
- **组织级项目管理**：以组合管道、商业论证、容量与依赖为核心；组合委员会在 G0/G1/G2/G5 做投资与
  优先级决策，PMO 维护门禁日历与度量，不代替项目负责人。

三种场景共用阶段编号、门禁决定与证据标准，使任务、项目与组合的报告可以互相对照。跨场景映射与 21 个
skill 的阶段归属见 `references/mappings.md`。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 门禁剧场 | 开会但不看证据，决定与风险无关 | 每个门禁只留可核验证据与明确决定 |
| 瀑布化 Stage-Gate | 阶段之间大爆炸交付，反馈过晚 | 在 S3/S4 使用迭代增量，门禁只做承诺决策 |
| 无门禁 Agile | 以速度为由跳过设计与验证 | 保留 G2 验收与 G4 证据，迭代不得绕过 |
| 工件膨胀 | 文档无人阅读，维护成本高于收益 | 按风险裁剪，R0 一页记录，R2 才用完整模板 |
| 风险级别漂移 | 为省流程把 R2 降为 R0 | G0 记录依据，范围变化时重新分级 |
| 自批 | 执行者同时批准自己的 R2 门禁 | 独立审查与批准，智能体不得代替人工 |
| 跳过 G4 | 以“改动很小”直接发布 | 任何发布前保留验证证据；R0 也须验证 |
| 指标游戏 | 关闭门禁数量替代结果 | 以收益、质量与流动指标共同判断 |
| PMO 微管理 | 流程替代团队决策 | PMO 提供日历、模板与度量，决策归角色 |
| 依赖口头承诺 | 跨团队窗口未登记，集成时才暴露 | 依赖图、接口契约、负责人与失败回退 |

## 审查清单

- [ ] 风险级别已在 G0 记录，并随范围变化重新评估。
- [ ] G0 已确认授权、对象、停止条件与负责人。
- [ ] G1 已写明问题、用户、结果指标、约束、选项与收益基线。
- [ ] G2 已写明范围、验收标准、设计、依赖、风险、测试与回滚计划。
- [ ] G3 有可运行增量、评审结论、DoR/DoD 检查与更新的设计决策。
- [ ] G4 有测试、安全、性能与验收证据；R2 有独立审查。
- [ ] G5 有版本、变更记录、部署与回滚方案、可观测性与通告。
- [ ] G6 有收益对照、偏差、教训、归档与交接。
- [ ] Conditional Go 的条件已关闭，或有负责人与到期日。
- [ ] 授权、保密、不可逆、诚实与意图约束未被裁剪。
- [ ] 角色、决策权、依赖与容量已记录；关键依赖有失败回退。
