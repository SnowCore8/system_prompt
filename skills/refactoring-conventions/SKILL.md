# 重构规范

重构工作存在四类可预见的失效情形：将行为变更伪装为重构提交，使审查者误认为仅调整结构，从而引入缺陷；在缺少
测试保护的危险区域实施大规模改动，以致缺陷无法察觉；在单次提交中并入数十处机械改动，致使任何一步出错均无法
定位；以及在不宜重构时实施重构，将发布前压力或范围蔓延作为重构理由。上述失效情形均易引入而难以逆转，因为团
队将围绕失效的重构习惯重组其对变更的信任。本 skill 规定重构与修复的判定标准、安全手法、小步提交纪律，以及重
构与不重构的边界。本 skill 适用于任何语言，并将“外部行为不变方构成重构、有测试保护方可改动危险区域、一次提
交仅实施一步等价变换”作为不可跳过的顺序。其服务对象为整理代码的工程师、判断 refactor 提交是否夹带行为变更
的审查者，以及决定重构时机的维护者。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充：

1. 平台、工具链与语言的强制要求，以及宿主与用户全局约束。语言提供的自动重构、编译器与既有测试套件，均非可
   选事项。
2. 本 skill 的规则与默认值。
3. 既有项目约定与事实。代理提出规则之前，应当先阅读代码、测试与提交历史，查明团队拆分重构与修复的方式；项
   目约定仅在本 skill 未规定时补充；现有代码、测试、提交历史与工具链属于事实输入，依本 skill 的规则处理；项
   目约定不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- 命名，包括标识符、文件、目录、大小写与命名表，由 `naming-conventions` skill 管辖。重命名属于安全重构手法，
  具体名称由该 skill 裁定。
- 代码风格，包括格式化、布局、错误与日志策略，由 `code-style-conventions` skill 管辖。重构不得顺带变更风格；
  风格迁移属于独立变更。
- 提交拆分，包括 commit 粒度、提交消息与 PR 流程，由 `vcs-collaboration-conventions` skill 管辖。本 skill 仅
  规定重构与行为变更分开提交这一纪律。
- 修复与功能变更是否属于行为变更，由本 skill 判定：行为发生变更的，属于 fix/feat，不属于重构。
- 同一效力层级的两项强制规则冲突的，代理应当报告用户裁决；仅非强制的项目约定之间的冲突，方可记录所选约定并
  说明理由。

## 流程

1. 判定性质。代理应当判定外部行为是否变更：行为不变的，属于重构；行为变更的，属于 fix/feat，依测试与提交的
   对应流程处理。
2. 确认保护。拟改动区域没有覆盖当前行为的测试的，应当先补充特征测试，锁定现状；无法补充的，不得实施
   重构；确需例外的，须取得用户明确同意并记录风险。
3. 选择手法。代理应当自安全手法目录中选择一项（提取方法或类、内联、移动、重命名、替换魔法数），一次仅实施一
   项。
4. 小步提交。每实施一项手法，代理应当运行测试，使测试套件保持通过；每一步等价变换对应一次提交，不得夹带行为
   变更。
5. 复核。代理应当阅读完整 diff，确认未混入行为变更，亦无顺带改动，且被替换的旧实现与兼容层均已删除。

## 核心规则

- **外部行为不变方构成重构。** 重构不改变可观察行为：既有测试保持通过，API、返回结构、错误语义、副作用与性能
  特征不变。行为变更的，属于 fix/feat，应当新增或修改测试，提交类型使用 fix/feat，不使用 refactor。判定标准：
  测试通过仅为必要条件，代理还应当核对上述可观察行为；测试未覆盖的，应当先补充特征测试，仍无法判定的，按行
  为变更处理。
- **没有测试保护的危险区域，应当先补充特征测试再实施重构。** 拟重构代码没有覆盖其当前行为的测试的，应当先编
  写特征测试锁定现状，再实施改动；没有测试覆盖且无法补充特征测试的，不得改动。确需例外的，须取得用户明确同意
  并记录风险。
- **一次重构提交不得夹带行为变更。** 重构与修复、功能应当分提交。审查者发现 refactor 提交中既有测试失败，或
  新增、修改行为断言的，应当驳回并要求拆分。
- **小步提交，每一步可测试。** 每一次仅实施一项安全手法，每一步之后测试套件保持通过；禁止一次大规模改动后再
  行修复。判定标准：单条提交的 diff 仅包含一项手法的等价变换。
- **使用安全手法，不得以手工重写代替。** 代理应当使用具有可逆小步骤的手法（提取方法或类、内联、移动、重命名、替换魔
  法数），每一步保持等价；手工实施大段重写将破坏每一步的可验证性，不构成重构。
- **替换后应当删除旧实现，不得保留并存路径。** 提取、内联、移动或替换后，旧实现、调用点、开关与兼容层应当在
  同一提交中删除；需要迁移窗口的，应当记录移除条件与期限，到期清理；交付前应当列出无法当场清理的残留，禁止
  仅保留 TODO。判定标准：搜索旧名称无引用，diff 中不存在新旧两套实现。
- **代码异味触发重构，压力不触发重构。** 代理应当依代码异味清单决定何时重构（重复、长函数、长参数列表、数据
  泥团、开关语句）；没有测试覆盖且无法补充特征测试、处于发布冻结窗口、范围蔓延时，不得重构；测试缺口的
  例外须取得用户明确同意并记录风险。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 将行为变更塞入 refactor 提交 | 审查者为“仅系重构”所误导，缺陷混入难以回滚的结构改动 | 行为变更的，使用 fix/feat，分开提交 |
| 无测试保护即重构危险区域 | 改动损坏后无人察觉，回退亦无从判断 | 先补充特征测试锁定现状 |
| 一次提交包含数十处机械改动 | 任何一步出错均无法定位，审查亦无法逐条复核 | 每步一项手法，单独提交 |
| 以手工大段重写冒充重构 | 每一步不可验证，等价性无从证明 | 仅使用具有可逆小步骤的安全手法 |
| 替换后保留旧实现或兼容层 | 新旧两套并存，行为分叉且均须维护 | 同一提交删除旧路径；迁移窗口记录移除条件与期限 |
| 发布冻结窗口内顺带重构 | 与发布风险叠加，发生事故时分不清责任 | 冻结窗口内不实施结构改动 |
| 重构夹带格式化或重命名 | 无法分辨等价变换与行为变更 | 风格由 `code-style-conventions` 管辖，命名由 `naming-conventions` 管辖，分开提交 |
| 在无代码异味的代码上滥用提取 | 为提取而提取，反而增加间接层 | 依代码异味清单触发，不凭感觉 |

## 审查清单

- [ ] 判定写明“外部行为不变”，既有测试在重构后保持通过。
- [ ] 行为变更使用 fix/feat 提交，并新增或修改测试，未冒充 refactor。
- [ ] 危险区域重构前已有特征测试锁定现有行为；无法补充特征测试的，未实施重构。
- [ ] 单条提交仅含一项安全手法，diff 无行为变更。
- [ ] 手法出自安全目录（提取、内联、移动、重命名、替换魔法数），不属于手工重写。
- [ ] 被替换的实现、调用点、开关与兼容层已删除，搜索旧名称无引用。
- [ ] 重构未夹带格式化、重命名或其他 skill 的变更。
- [ ] 仅在触发代码异味清单条目时重构；没有测试覆盖且无法补特征测试、发布冻结窗口与范围蔓延时不动。
- [ ] 重构后测试套件通过，无被跳过或弱化的测试。
