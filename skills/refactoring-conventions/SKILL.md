# 重构规范

重构存在四类可预见的失效：把行为变更伪装为重构提交，使审查者误认为只调整了结构；在没有测试保护的区域大改，
缺陷无法察觉；在单次提交中并入数十处机械改动，任何一步出错都无法定位；在不该重构时重构，把发布压力或范围
蔓延当作理由。本 skill 规定重构与修复的判定、安全手法、小步纪律与重构边界，适用于任何语言，并把“外部行为
不变方构成重构、有测试保护方可改动危险区域、一次提交仅一步等价变换”作为不可跳过的顺序。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 平台、工具链与语言的强制要求，以及宿主与全局用户约束。语言提供的自动重构、编译器与既有测试套件均非
   可选事项。
2. 本 skill 的规则与默认值。
3. 既有项目约定与事实。提出规则前先读代码、测试与提交历史，查明团队拆分重构与修复的方式；项目约定仅在本
   skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

管辖与边界：

- 本 skill 判定一次改动是否属于重构，并规定安全手法、小步提交纪律、代码异味触发条件与替换后的清理。
- 行为变更属于 fix/feat，由本 skill 判定；缺陷的复现、二分与根因诊断归 debugging-conventions。
- 命名（标识符、文件、目录、大小写、命名表）归 naming-conventions；重命名属于安全手法，具体名称由该 skill 裁定。
- 代码风格（格式化、布局、错误与日志策略）归 code-style-conventions；重构不得顺带变更风格。
- 提交拆分、提交消息、PR 流程与合并门禁归 vcs-collaboration-conventions；本 skill 只规定重构与行为变更分开提交。
- 测试策略、覆盖阈值与豁免归 testing-and-quality-conventions；本 skill 只要求危险区域先有特征测试。
- 同一效力层级的强制规则冲突时报告用户裁决；非强制约定冲突时记录所选约定并说明理由。

## 生命周期定位

上游输入来自 S2 的范围、验收标准与代码异味清单：哪些异味纳入本次改造、行为保持如何判定、特征测试补在哪里；
下游交接给 S3 的分步实现、S4 的独立审查与回归、S5 的发布隔离。

- 升级与停止：重构范围扩大、需要改变外部行为或接口时退回 G2；发布冻结窗口内不启动重构；无测试且无法补充
  特征测试时停止，报告风险与替代方案。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S2 计划 | 依异味清单确定重构范围与顺序，写明行为保持验收与回滚点 | 重构任务清单、验收标准、特征测试计划 |
| S3 构建 | 一次一项安全手法，每步运行测试并单独提交；同步清理旧实现 | 手法提交、测试输出、旧名搜索记录 |
| S4 验证 | 核对 diff 无行为变更，审查测试是否被弱化，确认兼容层已删除 | 审查结论、全量测试结果、清理证据 |
| S5 发布 | 确认未完成的重构不进入发布，冻结窗口内无结构改动 | 发布范围清单、冻结窗口记录 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 计划 | 重构范围与异味依据、行为保持验收、特征测试与回滚方案 | 范围或验收未定时 Hold，退回 S1/S2 |
| G3 构建 | 每步测试通过记录、单手法 diff、旧实现清理与旧名搜索结果 | Recycle 到 S3，拆分提交后重验 |
| G4 验证 | 行为保持结论、独立审查、全量测试输出、无被弱化的测试 | 修复或 Recycle；refactor 提交夹带行为变更时按 No-Go 驳回 |
| G5 发布 | 冻结窗口记录、未完成重构的隔离清单 | Hold 发布，隔离未完成项后再过门 |

证据必须可复核：测试命令与退出码、提交逐条 diff、旧名搜索命令；口头声明“只是重构”不构成证据。

## 工作流

1. 判定性质：核对 API、返回结构、错误语义、副作用与性能特征是否变化；行为不变的属于重构，变化的属于 fix/feat。
2. 确认保护：拟改动区域缺少覆盖当前行为的测试时，先补特征测试锁定现状；无法补充的不得重构，确需例外须取得
   用户明确同意并记录风险。
3. 选择手法：从安全手法目录选一项（提取方法或类、内联、移动、重命名、替换魔法数），一次只实施一项。
4. 小步提交：每实施一项手法就运行测试并保持通过，每一步等价变换对应一次提交，不夹带行为变更。
5. 复核：阅读完整 diff，确认没有混入行为变更与顺带改动，被替换的旧实现、调用点、开关与兼容层已删除。

## 核心规则

- **外部行为不变方构成重构。** 既有测试保持通过，API、返回结构、错误语义、副作用与性能特征不变。测试通过仅
  为必要条件；测试未覆盖的先补特征测试，仍无法判定的按行为变更处理。
- **没有测试保护的危险区域先补特征测试。** 无测试且无法补充特征测试的不得改动；确需例外须取得用户明确同意
  并记录风险。
- **一次重构提交不得夹带行为变更。** 重构与修复、功能分提交；审查者发现 refactor 提交中测试失败或行为断言被
  新增、修改的，应当驳回并要求拆分。
- **小步提交，每一步可测试。** 每次只实施一项安全手法，每步之后测试套件保持通过；禁止一次大规模改动之后再
  行修复。判定标准：单条提交的 diff 仅包含一项手法的等价变换。
- **使用安全手法，不得以手工重写代替。** 手法须具有可逆小步骤，每步保持等价；手工大段重写破坏每步的可验证性。
  优先使用语言或 IDE 的自动重构，手工重命名须核对全部引用。
- **替换后删除旧实现，不得保留并存路径。** 旧实现、调用点、开关与兼容层在同一提交中删除；需要迁移窗口的记录
  移除条件与期限，到期清理；交付前列出无法当场清理的残留，禁止仅保留 TODO。
- **代码异味触发重构，压力不触发重构。** 依异味清单决定何时重构（重复、长函数、长参数列表、数据泥团、开关
  语句）；无测试覆盖且无法补特征测试、发布冻结窗口、范围蔓延时不得重构。

## 反模式

| 阶段 | 反模式 | 失败原因 | 修复 |
|---|---|---|---|
| S2 | 在无代码异味的代码上滥用提取 | 为提取而提取，反而增加间接层 | 依代码异味清单触发，不凭感觉 |
| S2 | 无测试保护即重构危险区域 | 改动损坏后无人察觉，回退亦无从判断 | 先补充特征测试锁定现状 |
| S3 | 将行为变更塞入 refactor 提交 | 审查者为“仅系重构”所误导，缺陷混入难以回滚的结构改动 | 行为变更的，使用 fix/feat，分开提交 |
| S3 | 一次提交包含数十处机械改动 | 任何一步出错均无法定位，审查亦无法逐条复核 | 每步一项手法，单独提交 |
| S3 | 以手工大段重写冒充重构 | 每一步不可验证，等价性无从证明 | 仅使用具有可逆小步骤的安全手法 |
| S3 | 替换后保留旧实现或兼容层 | 新旧两套并存，行为分叉且均须维护 | 同一提交删除旧路径；迁移窗口记录移除条件与期限 |
| S3 | 重构夹带格式化或重命名 | 无法分辨等价变换与行为变更 | 风格与命名分开提交，由对应 skill 裁定 |
| S5 | 发布冻结窗口内顺带重构 | 与发布风险叠加，发生事故时分不清责任 | 冻结窗口内不实施结构改动 |

## 审查清单

计划与保护（G2）：

- [ ] 重构范围来自代码异味清单，写明触发条目与预期收益。
- [ ] 行为保持的判定方式与验收标准已写明；危险区域已有特征测试，或已记录无法补充的例外与风险。
- [ ] 回滚点与提交拆分方案已确定。

构建（G3）：

- [ ] 每次提交仅含一项安全手法，来自安全目录，不属于手工重写。
- [ ] 每一项手法之后测试套件保持通过；未运行项已标注。
- [ ] 被替换的实现、调用点、开关与兼容层已删除，搜索旧名称无引用。
- [ ] 未夹带格式化、重命名或本次范围之外的改动。

验证与发布（G4/G5）：

- [ ] diff 中不存在行为变更；行为变更使用 fix/feat 并配测试，未冒充 refactor。
- [ ] 测试无删除、跳过或弱化；全量测试已运行并给出结果。
- [ ] 审查确认没有遗留的新旧并存路径与未跟踪的 TODO。
- [ ] 未完成的重构不进入发布，冻结窗口内没有结构改动。

## 示例

<example>
场景：把函数返回值由字典改为对象，并更新全部调用方。
判定：外部行为已经变更，属于 fix，不属于重构；应当新增或修改断言新返回结构的测试，并以 fix 提交。
</example>

<example>
场景：一个 400 行的函数需要提取方法，但该函数没有测试。
做法：先编写特征测试锁定其当前输入与输出，再实施小步提取；每完成一步提取即运行测试并保持通过，每次提取单独提交。
</example>
