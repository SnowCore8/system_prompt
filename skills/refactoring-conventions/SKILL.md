# 重构规范

重构会以四种可预见的方式失效：把行为变更伪装成重构提交，让审查者以为「只是动了结构」却引入缺陷；在没有测试
保护的危险区域大刀阔斧地改，改坏了也没人知道；一次提交塞进几十处机械改动，任何一步出错都无法定位；以及在不该
重构的时候重构，把发布前或范围蔓延的压力当成重构的理由。每种失效都容易引入、难以逆转，因为团队会围绕失效的
重构习惯重组自己对变更的信任。本 skill 给出重构与修复的判定标准、安全手法、小步提交纪律，以及何时重构与何时
不重构的边界。它适用于任何语言，把「外部行为不变才算重构、有测试保护才动危险区域、一次提交只做一步等价变换」
作为不可跳过的顺序。它服务于整理代码的工程师、判断一条 refactor 提交是否夹带行为变更的审查者，以及决定何时
才值得重构的维护者。

## 适用范围与优先级

采用第一条适用的规则，同一范围内不要混用标准：

1. 平台、工具链与语言的强制要求。语言提供的自动重构、编译器与既有测试套件不是可选项。
2. 既有项目约定。发明规则之前先读代码、测试与提交历史，看团队如何拆分重构与修复。
3. 本规范的默认值，在前两层未作规定时适用。
4. 个人偏好，永远不能覆盖上述三层。

- 命名（标识符、文件、目录、大小写与命名表）归 naming-conventions skill 管。重命名是一种安全重构手法，但改成
  什么名字由那个 skill 裁定。
- 代码风格（格式化、布局、错误与日志策略）归 code-style-conventions skill 管。重构不顺手改风格；风格迁移是
  一次独立变更。
- 提交拆分（commit 粒度、提交消息、PR 流程）归 vcs-collaboration-conventions skill 管。本 skill 只管「重构与
  行为变更分开提交」这条纪律。
- 修复与功能变更是否算行为变更由本 skill 判定：行为变了就是 fix/feat，不是重构。
- 两条规则冲突时，说明冲突与所选规则，并把决定记录在项目约定中。

## 流程

1. 判定性质。问「外部行为变了吗？」行为不变是重构；行为变了是 fix/feat，走测试与提交的对应流程。
2. 确认保护。要动的区域有没有测试覆盖当前行为？没有就先补特征测试，锁定现状。
3. 选手法。从安全手法目录里选一个（提取方法/类、内联、移动、重命名、替换魔法数），一次只做一个。
4. 小步提交。每做一个手法就跑测试，套件保持绿；一步等价变换一个提交，不夹带行为变更。
5. 复核。读完 diff，确认没有行为变更混进来，也没有顺手改动，且被替换的旧实现与兼容层已删除。

## 核心规则

- **外部行为不变才算重构。** 重构不改变可观察行为：既有测试保持绿，API、返回结构、错误语义不变。行为变了就是
  fix/feat，要加或改测试，提交类型用 fix/feat，不用 refactor。判定：跑既有测试，绿=重构，红=行为变更。
- **没有测试保护的危险区域先补特征测试再重构。** 要重构的代码没有覆盖其当前行为的测试时，先写特征测试锁定
  现状，再动手。判定：重构前该区域有测试锁定其现有行为；没有就不动。
- **一次重构提交不夹带行为变更。** 重构与修复、功能分提交。审查者看到 refactor 提交里既有测试失败，或新增、
  修改了行为断言，就驳回要求拆分。
- **小步提交，每步可测试。** 每次只做一个安全手法，每步之后测试套件保持绿；禁一次大改后再修。判定：单条提交
  的 diff 只包含一个手法的等价变换。
- **用安全手法，不用手改重写。** 用有可逆小步骤的手法（提取、内联、移动、重命名、替换魔法数），每步等价；
  手改大段重写破坏了每步可验证性，不叫重构。
- **替换后删除旧实现，不保留并存路径。** 提取、内联、移动或替换后，旧实现、调用点、开关与兼容层在同一提交里
  删除；需要迁移窗口时记录移除条件与期限，到期清理；交付前列出无法当场清理的残留，禁止只留 TODO。判定：搜索
  旧名称零引用，diff 里没有新旧两套实现。
- **异味触发重构，压力不触发。** 按代码异味清单决定何时重构（重复、长函数、长参数列表、数据泥团、开关语句）；
  没有测试覆盖、发布前、范围蔓延时不重构。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 把行为变更塞进 refactor 提交 | 审查者被「只是重构」误导，缺陷混入难回滚的结构改动 | 行为变了用 fix/feat，分开提交 |
| 无测试保护就重构危险区域 | 改坏了没人知道，回退也无从判断 | 先补特征测试锁定现状 |
| 一次提交几十处机械改动 | 任何一步出错都无法定位，审查也无法逐条复核 | 每步一个手法，单独提交 |
| 手改大段重写冒充重构 | 每步不可验证，等价性无从证明 | 只用有可逆小步骤的安全手法 |
| 替换后保留旧实现或兼容层 | 新旧两套并存，行为分叉且都要维护 | 同一提交删除旧路径；迁移窗口记录移除条件与期限 |
| 发布前顺手重构 | 与发布风险叠加，出了事分不清是谁 | 发布前冻结结构改动 |
| 重构夹带格式化或重命名 | 无法分辨哪些是等价变换、哪些是行为变更 | 风格归 code-style-conventions，命名归 naming-conventions，分开提交 |
| 无味的代码上滥用提取 | 为提取而提取，反而增加间接层 | 按代码异味清单触发，不凭感觉 |

## 审查清单

- [ ] 判定写清「外部行为不变」，既有测试在重构后保持绿。
- [ ] 行为变更用 fix/feat 提交，并加了或改了测试，没有冒充 refactor。
- [ ] 危险区域重构前有特征测试锁定现有行为。
- [ ] 单条提交只含一个安全手法，diff 无行为变更。
- [ ] 手法来自安全目录（提取、内联、移动、重命名、替换魔法数），不是手改重写。
- [ ] 被替换的实现、调用点、开关与兼容层已删除，搜索旧名称零引用。
- [ ] 重构没有夹带格式化、重命名或其他 skill 的变更。
- [ ] 触发了代码异味清单中的条目才重构，无测试保护、发布前、范围蔓延时不动。
- [ ] 重构后测试套件通过，无被跳过或弱化的测试。
