# 重构维度

本文件与 SKILL.md 配合使用。每一节给出一个重构维度的决策、示例与边界情况。项目约定与事实作为输入；
本 skill 的规则优先，项目约定只在本 skill 未规定时补充。本文件提供默认值与理由。只读与你要做的重构相匹配的那一节。

## 1. 重构与修复的判定

外部行为是否改变是唯一标准，不是改动规模。

- 可观察行为包括：API 与返回结构、错误语义、输出、副作用、性能特征。任何一项变了都不是重构。
- 判定流程：跑既有测试；绿只是必要条件，还要逐项核对 API、返回结构、错误语义、副作用与性能特征是否变化。
  全部不变才是重构；红或有任一项变化就是行为变更，用 fix/feat 并加或改测试。测试未覆盖当前行为时先补特征测试；
  补齐后仍无法判定，按行为变更处理。
- 既没有测试也没有可对照行为时，先补特征测试锁定现状，再决定是重构还是修复。
- 提交类型是判定结果不是原因：先判定行为，再选 refactor 或 fix/feat，禁止为了用 refactor 而改动行为。

## 2. 安全重构手法

安全手法是每个小步骤保持等价的变换；手法目录见 catalog.md。

- 一次只做一个手法。提取方法/类、内联、移动、重命名、替换魔法数，每个变换单独一步、单独提交。
- 每个手法有明确的反向手法（提取对偶内联、重命名对偶重命名），出问题可逆回。
- 用语言或 IDE 提供的自动重构优先，因为它保证引用同步更新；手工重命名要确认全部引用，包括测试、文档、
  配置与序列化字段。
- 禁止手改大段重写冒充重构：没有等价步骤就无法验证，出错也无法定位到单步。

## 3. 小步提交

重构的价值在于每步可验证、可回滚。

- 单条提交只含一个手法，diff 里没有行为变更。审查者逐条复核等价性，任何一步失败都能单独回滚。
- 每步之后跑测试，套件保持绿。先做机械安全的步骤，再做引入风险的结构调整。
- 重构与行为变更、风格迁移、重命名分开提交；混在一起的分提交。
- 提交消息用 refactor(scope): 说明做的是什么手法、为什么，不夹带行为变更；提交拆分的完整规则归
  vcs-collaboration-conventions skill 管。

## 4. 何时重构与何时不重构

重构由代码异味触发，不由压力触发。

- 触发重构：重复、长函数、长参数列表、数据泥团、开关语句；完整清单与阈值见 catalog.md。
- 不重构：没有测试覆盖且无法补特征测试的危险区域；发布前的冻结窗口；范围蔓延（顺手动到本次任务之外）。
- 遗留项目分阶段改：为现有违规建立基线，对每个变更文件执行新结构，随基线缩小删除它；一次性大重构必然
  半途而废。
- 重构与修缺陷同时出现时先修缺陷再重构，或先补测试再重构；两者分开提交。
