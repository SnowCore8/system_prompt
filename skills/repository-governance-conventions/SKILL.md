# 仓库治理规范

仓库治理的失效通常没有明显信号。缺少许可证的仓库外观仍然完整，直到有人无法合法使用它；无人负责的目录
会连续数月合并未经审查的变更；某个包只在一位维护者的机器上构建成功，换到干净环境便失败；项目已经终止，
页面却仍公开，issue 保持开放，发布徽章照常显示。这些失效都不会出现在 diff 中，而且每一种被发现时都代价
高昂。本 skill 规定一套流程与完整规则，覆盖仓库的必需文件与元数据、仓库卫生、决策流程，以及仓库发布时的
打包与分发。治理在创建时成本低、事后补救成本高：缺少许可证会在项目流行后引发一次法务审查，而第一天补上
只需一个文件与一个决定。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充；同一范围内不得混用标准。

1. 强制的平台、法律、宿主与用户全局约束。每个仓库所受的托管平台设置、法律模板、包仓库规则与公司政策
   约束，均非可选事项；与这些约束矛盾的仓库级文件属于缺陷，不构成仓库内的例外。
2. 本 skill 的规则。必需文件、元数据、治理、打包与分发的规则，以本文件与 `references/` 为准。
3. 既有仓库约定与事实。制定政策前，应当先阅读当前文件清单、元数据、分支模型与 manifest；这些内容属于
   事实输入，依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层；偏好也不得为缺失的必需文件提供正当理由。

- 必需文件及其元数据由本 skill 管辖：哪些文件必须存在、置于何处，以及携带哪些元数据字段。README、
  CONTRIBUTING 指南、决策记录与其他文档的内容、模板、结构与语气，由 `documentation-conventions` 管辖；
  本 skill 要求文件位于被认可的路径，并能够从仓库入口到达。许可证政策与安全文件的内容由
  `security-compliance-conventions` 管辖；本 skill 管辖文件是否存在及其必需的元数据字段。
- 仓库必需文件的路径、元数据与卫生由本 skill 管辖；代码与资源目录布局由 `code-style-conventions` 管辖；
  仓库、包与文件命名由 `naming-conventions` 管辖。分支、PR、审查、审查者数量与 CODEOWNERS 机制由
  `vcs-collaboration-conventions` 管辖；本 skill 管辖这些机制所执行的角色与治理决策。版本号、发布时机与
  按发布类型的审批由 `release-operations-conventions` 管辖；发布说明文档由 `documentation-conventions`
  管辖；manifest 元数据、分发渠道以及归档或转移，由本 skill 管辖。
- 支撑 CI 门禁的仓库设置与模板由本 skill 管辖；门禁定义与通过标准由 `testing-and-quality-conventions`
  管辖。无法运行自身必需校验的仓库，除测试缺陷外还存在治理缺陷；因此应当在此报告缺口，并与门禁所有者
  共同修复。
- 仓库属于产品界面。README、许可证、模板、包元数据与默认分支会被用户与工具阅读；因此治理变更应当作为
  产品变更审查，不得当作杂务处理。
- 发生冲突时，组织级政策优先。托管设置或公司规则与仓库文件不一致的，应当说明差异，遵循组织政策，并修复
  仓库文件，使下一位读者只看到一条规则。
- 生成的元数据不得手工编辑：生成的 manifest 字段、同步的模板与 lock 文件，均应当在真源修改、重新生成并
  验证。
- 同一效力层级的强制规则冲突的，应当报告用户裁决；只有非强制的项目约定冲突，才可以记录所选约定及其
  理由，写入 `GOVERNANCE.md` 或决策记录，使下一次变更遵循该决定。
- **单人仓库与双许可。** 记录单点与补偿控制（保护分支、必需 CI、发布留痕）后，可以仅设一名管理员；第二人
  属于目标，而非当前门槛；治理与归属变更由维护者自行批准并记录。双许可仓库以 `LICENSE` 说明加各许可证
  全文文件满足“完整文本”；不提供行为准则的，应当在治理文件中记录理由、替代联系方式与补偿控制（如响应
  时限与升级路径）。

## 流程

1. 将仓库分类为公开库、应用、内部服务、仅文档项目或归档项目。应当记录类型：类型决定必需清单、元数据与
   审查深度。每次审查均须重新分类，因为获得外部用户或停止交付的项目会改变类型。
2. 变更前应当先阅读当前状态：根文件、托管设置、受保护分支规则、环境机密、manifest、包仓库链接与归档
   状态。应当写明已有内容与缺失内容。无法读取托管设置的，记录缺口，以仓库内配置为准，并请求有权限者
   核对；不得猜测设置值。
3. 仓库应当与所属类型的必需清单比对。应当列出缺失、位置错误、过时与无效的文件及元数据，并为每一项指定
   负责人与到期动作。文件存在但必需字段为空的，按缺失处理。
4. 应当先修复卫生：被跟踪与被忽略的文件、大型与生成产物、过时分支与标签、子模块、第三方引入代码与
   工作区布局。卫生决定之后每次审查所见的内容，因此应当记录每次删除及其原因。
5. 建立治理：角色与权限阶梯、决策模型、路由至各所有者 skill 的审批规则、提案路径、行为准则执行途径与
   发布权。上述内容应当记录于 `GOVERNANCE.md`；确认每条可合并路径均指向可问责角色，并核对角色与托管
   平台实际授予的权限一致。
6. 修复打包与分发：manifest 元数据、包仓库渠道、随包的 SBOM 与署名声明、安装验证，以及已发布版本的
   撤回与弃用路径。安装测试应当自包仓库实施，不得自工作区实施。
7. 验证结果：运行清单与元数据校验，自干净环境安装，确认归档或转移状态，并记录证据与下一次审查日期。
   某项当前无法修复的，应当记录负责人与到期日，将仓库标注为不合规，并报告每个未关闭项。

## 核心规则

- **必需意味着有效，而非仅存在。** 每个必需文件都应当置于托管平台与工具认可的路径，并填写其携带的元数据
  字段；`SECURITY.md` 放在未被认可的路径上，对每个工具而言都等同于缺失；未写明负责人的必需文件，只是
  位置正确的占位。
- **首次公开推送之前须具备许可证。** 应当将完整许可证文本置于名称精确为 `LICENSE` 的文件中，确认托管
  平台识别同一许可证，并将标识符镜像至包 manifest。许可证变更应当作为所有者的法律决定，因为无许可证的
  仓库不授予任何复用权利；多许可证仓库可以将各许可证全文拆分为独立文件，由 `LICENSE` 说明各文件适用的
  许可证。
- **每条可合并路径均须有可问责角色。** 每个顶层目录与发布关键文件均须指向活跃角色；CODEOWNERS 的映射与
  校验机制由 `vcs-collaboration-conventions` 管辖；未分配的路径属于治理失败，因为它会在没有负责审查者的
  情况下合并。
- **决策模型应当以书面形式载明。** `GOVERNANCE.md` 应当说明决策属于维护者主导、惰性共识还是投票，评论窗口
  持续多久，以及批准的构成；只留在记忆中的模型会阻碍每一位新贡献者，并在第一次有争议的变更上引发争执。
- **路由审批，不得重新定义审批。** 代码变更的审查者数量取自 `vcs-collaboration-conventions`；按发布类型的
  审批取自 `release-operations-conventions`；本 skill 仅补充自身规则：治理或归属变更须有两名批准者；与
  所有者 skill 矛盾的本地阈值属于缺陷。
- **保护失效即治理失效。** 未受保护的默认分支、未经审查的合并或被重写的历史，均属于治理缺陷；保护与历史
  修复机制由 `vcs-collaboration-conventions` 定义。
- **被跟踪文件与被忽略文件互不相交。** 全新克隆并构建后，不得有已跟踪文件被修改，也不得有运行所需的文件
  被忽略；本地配置、凭据、可由 CI 重建的构建输出与编辑器状态应当保持被忽略。
- **可由 CI 重建的构建输出不得提交；必须跟踪的生成代码、编译产物与生成的 manifest，在记录来源、命令与
  版本时可以跟踪。** 无法由 CI 重建但仍须随包分发的产物，同样记录来源、命令与版本后方可跟踪；其余应当由
  CI 生成并忽略。工具要求时，lock 文件属于输入，因此仅依该规则提交，不得于其他位置提交。
- **资产应当具备大小策略。** 应当设定大小阈值；超过阈值的文件与逐构建二进制，应当放入 Git LFS 或制品库，
  并在 `.gitattributes` 中按模式跟踪；不得依赖重写历史来修复缓慢的克隆。
- **依赖更新应当有策略。** 应当以依赖更新工具（Dependabot、Renovate）按固定频率生成小批量更新，并按
  主版本、次版本与补丁分级：补丁走轻量审查，次版本走标准审查，主版本走高风险管理路径，审查人数取自
  `vcs-collaboration-conventions` 的审查级别表。安全修复优先，并须满足 `security-compliance-conventions`
  的修复期限与 `testing-and-quality-conventions` 的依赖门禁，不得以较低的审查门槛绕开上述门禁。应当按
  来源或生态对更新分组，以限制同时变更的范围；每次更新均须记录升级依据、兼容性结论与具名负责人。更新
  请求仍依 `vcs-collaboration-conventions` 经审查与门禁；自动合并仅在必需批准与必需校验齐备时启用。
- **按计划清理分支与标签。** 已合并分支应当在声明窗口内删除；删除远端分支或标签前，须取得 AU-1 明确
  同意。被放弃的分支与长期分支应当指定负责人与退出日期；从未成为发布的标签应当删除；已发布标签的不可变
  与保护由 `vcs-collaboration-conventions` 定义。
- **打标签、过门禁与发布由发布流程驱动。** 打标签、门禁顺序、制品签名与哈希、制品晋级与不可变，由
  `release-operations-conventions` 定义；本 skill 管辖发布制品一侧：manifest 元数据、随包的许可证与必需
  文件、随包的 SBOM 与署名声明、自包仓库安装并验证、撤回与弃用经已发布路径实施；不得自工作区直接发布。
- **以撤回或弃用处理不当发布，不得删除。** 撤回或弃用适用于安全缺陷、不可安装的产物或法律问题；应当说明
  原因，使被撤回版本对固定版本的用户仍可解析；弃用应当写明替代方案与移除日期；不得删除已发布的版本。版本
  号不得重用、重打或覆盖，由 `release-operations-conventions` 维护。
- **继任安排应当在需要之前记录。** 目标为至少两名维护者持有管理权限；单人仓库在记录单点与补偿控制后，
  可以仅设一名管理员；第二人属于目标，而非当前门槛；治理与归属变更由维护者自行批准并记录。
  `MAINTAINERS.md` 应当指定继任者；维护者离开时应当移除权限；长期不活跃的维护者应当经通知转为荣休。
  权限应当按计划并在每次离开后审查。
- **应当归档，不得抛弃。** 项目停止时，应当设置归档标志、在 README 添加横幅、关闭或重定向 issue 与支持
  路径、保持发布与许可证可用、指定管理员，并移除不再服务该项目的 CI 机密与 webhook。

## 文件清单矩阵

`references/playbooks.md` 中按类型划分的清单为上述条件的权威来源。“负责人”指对存在性与元数据负责的角色；
文档内容与模板遵循文档角色；安全策略内容遵循安全与合规角色。

| 文件或设置 | 用途 | 适用于 | 负责人 |
|---|---|---|---|
| `README.md` | 作为用户与工具认可的入口。 | 所有活跃类型；归档类型保留横幅。 | 仓库所有者 |
| `LICENSE` | 以许可证文本授予复用条款。 | 库、应用与仅文档项目；对外交付的内部项目；归档类型保留。 | 仓库所有者，经法务审查 |
| `CONTRIBUTING.md` | 开启贡献者路径。 | 库、应用与仅文档项目；内部服务推荐。 | 维护者 |
| `CODE_OF_CONDUCT.md` | 说明预期行为与执行途径。 | 库与应用；仅文档项目推荐。 | 社区管理者 |
| `SECURITY.md` | 使安全报告路径可被发现；内容由安全角色管辖。 | 所有活跃类型；归档类型保留。 | 安全负责人 |
| `SUPPORT.md` | 公布支持路径。 | 库与应用；内部服务与仅文档项目可选。 | 维护者 |
| `THIRD-PARTY-NOTICES.md` | 随包发布第三方组件的许可证与署名声明；内容由安全角色管辖。 | 含第三方引入代码的库与应用；其他类型可选。 | 维护者，经法务审查 |
| `CHANGELOG.md` | 记录每次发布中用户必须知晓的内容。 | 库与应用；内部服务推荐。 | 发布管理者 |
| `CODEOWNERS` | 使每条可合并路径指向可问责角色；机制由 VCS 角色管辖。 | 库、应用与内部服务；仅文档项目推荐。 | 维护者 |
| `.github/ISSUE_TEMPLATE/` | 规范报告的收集。 | 库与应用；内部服务与仅文档项目可选。 | 维护者 |
| `.github/PULL_REQUEST_TEMPLATE.md` | 要求审查者所需的证据。 | 库、应用与仅文档项目；内部服务推荐。 | 维护者 |
| `.editorconfig` | 统一仓库内编辑器默认值。 | 所有活跃类型；归档类型冻结。 | 维护者 |
| `.gitignore` 与 `.gitattributes` | 使本地产物不被跟踪，并设定行尾与 LFS 行为。 | `.gitignore` 适用于所有活跃类型；`.gitattributes` 适用于代码仓库，仅文档项目推荐。 | 维护者 |
| `.github/FUNDING.yml`、`GOVERNANCE.md`、`MAINTAINERS.md`、`CITATION.cff` | 记录赞助、角色、继任与引用。 | `GOVERNANCE.md` 与 `MAINTAINERS.md` 在代码仓库中推荐，仅文档项目可选；FUNDING 可选；CITATION 用于研究产出。 | 维护者 |
| 仓库元数据 | 设置描述、主题、主页、默认分支、可见性、发布与讨论。 | 所有活跃类型；归档类型保留描述与主页。 | 仓库所有者 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| `LICENSE.md` 中仅有许可证名称而无许可证文本 | 托管平台识别与法务审查均将失败，消费者无法依赖该条款。 | 将完整文本放入 `LICENSE`，并确认托管平台识别。 |
| `CODEOWNERS` 指称已不存在的角色 | 受影响路径无可问责审查者，将在无主状态下合并。 | 按活跃角色重新校验分配；映射与复核节奏由 `vcs-collaboration-conventions` 裁定。 |
| 公开仓库的 README 为空 | 用户将提交 issue，等待一个不存在的产品。 | 在首个可用发布之前保持仓库私有或归档。 |
| 提交构建输出 | 历史膨胀、克隆变慢，过时的二进制将自树中发布。 | 忽略输出，在 CI 中构建，并将产物附加至发布。 |
| 大型二进制“仅提交一次” | 每次克隆与镜像均将永久携带该文件。 | 在首次推送前移至 LFS 或制品库。 |
| 已合并分支无限保留 | 分支列表掩盖活跃工作，并引发自过时分支头的 cherry-pick。 | 合并后删除，并为长期分支保留命名规则。 |
| 缺少默认分支保护 | 历史重写与未经审查的合并将摧毁已审查的工作。 | 强制执行 VCS 保护规则，并将该合并视为未经审查。 |
| 一名维护者拥有全部权限 | 该人员离开时，仓库将停止运转或丢失。 | 单人仓库在记录单点与补偿控制后可以仅有一名管理员；第二人属于目标，而非当前门槛；治理与归属变更由维护者自行批准并记录，同时指定继任者。 |
| `SECURITY.md` 缺失或不在被认可的路径 | 报告者无法找到报告路径，可能提交公开 issue。 | 将文件置于被认可的路径并记录负责人；内容由安全角色管辖。 |
| 未经打标签与门禁的构建即发布 | 产物的输入未知且无法重建。 | 仅发布自已批准标签构建、通过全部门禁的 CI 产物。 |
| 不当发布后重新发布同一版本 | 缓存与 lock 文件将继续在同一版本下提供不同内容。 | 说明原因后撤回，随后发布补丁版本。 |
| 归档仓库仍完全可写 | 用户误认为其仍在维护，并提交无人答复的 issue。 | 归档该仓库、为 README 添加横幅，并重定向支持。 |
| 转移未更新重定向与元数据 | 旧链接、克隆与包页面均将失效。 | 使用托管平台重定向，并更新 manifest、文档与包元数据。 |
| 托管平台与 manifest 的描述不一致 | 搜索结果与包页面将描述不同项目。 | 保持单一来源，并在 CI 中校验镜像。 |

## 审查清单

- [ ] 已记录项目类型，并与必需文件清单中的某一行匹配。
- [ ] 对于所需项目类型，`README.md`、`LICENSE` 与 `SECURITY.md` 已位于被认可的路径。
- [ ] `LICENSE` 包含完整文本，且托管平台识别同一许可证。
- [ ] `CONTRIBUTING.md` 覆盖自全新克隆开始的环境搭建、测试与提交路径。
- [ ] `CODE_OF_CONDUCT.md` 已写明执行联系人及升级途径。
- [ ] `SECURITY.md` 已位于被认可的路径并记录负责人。
- [ ] 含第三方引入代码时，`THIRD-PARTY-NOTICES.md` 已位于被认可的路径并随包发布。
- [ ] 每条可合并路径均指向可问责角色，分配仅写活跃角色。
- [ ] issue 与 PR 模板要求分诊者与审查者所需的字段。
- [ ] `.gitignore` 已覆盖本地配置、凭据与构建输出。
- [ ] `.gitattributes` 在需要处设定行尾、LFS 模式与生成文件标记。
- [ ] 依赖更新工具按固定频率运行；升级按主/次/补丁分级并有具名负责人；安全修复优先，并经过与其他变更相同的门禁。
- [ ] 无被跟踪文件超过大小策略；大型资产使用 LFS 或制品库。
- [ ] 生成文件与第三方引入文件均带有标记及其来源或版本。
- [ ] 过时分支与未发布标签已删除，或带有负责人与日期。
- [ ] 默认分支、发布分支与发布标签受保护，且不存在未记录的绕过或强制推送。
- [ ] `GOVERNANCE.md` 或 `MAINTAINERS.md` 已写明角色、决策模型、路由的审批规则与继任。
- [ ] manifest 元数据与仓库元数据及当前版本一致。
- [ ] 包仅使用已发布制品，并在干净环境中安装并运行。
- [ ] 发布制品包含许可证、`THIRD-PARTY-NOTICES`、SBOM 与必需文件，并已自包仓库安装验证。
- [ ] 归档仓库只读、带横幅，并自活跃文档中取消链接。
- [ ] 权限按计划审查；已离开的维护者不持有任何权限。
- [ ] 清单审查与元数据审查均有负责人与计划日期。

## 示例

<example>
公开仓库缺少许可证。应当将完整许可证文本添加为 `LICENSE`，确认托管平台识别一致，将标识符镜像至包
manifest，自 README 链接许可证，为该节指定负责人，并在每次发布时审查。
</example>

<example>
`CODEOWNERS` 设有兜底回退，但 `infra/` 无可问责角色。应当为 `infra/` 指定可问责角色，由 VCS 负责人在
一次测试 PR 上校验映射及回退，随后重新检查每个顶层目录。
</example>

<example>
在笔记本上构建的发布版本在干净容器中导入失败，因为有一项依赖未声明。应当添加该依赖，在 CI 中构建，在空
环境中安装生成的产物，随后发布补丁版本并在变更日志中说明修复；不得重用失败的版本。
</example>

<example>
项目停止。应当设置归档标志，在 README 中放置横幅与最后支持版本，关闭 issue 与讨论，保持发布与许可证
可用，并指定负责答复安全报告的管理员。
</example>

<example>
仓库迁移至新组织。应当使用托管平台重定向，更新 manifest 的 repository 与 homepage 字段、包元数据、
CODEOWNERS、CI 机密与文档链接，验证旧克隆 URL 仍会重定向，随后自新位置发布。
</example>
