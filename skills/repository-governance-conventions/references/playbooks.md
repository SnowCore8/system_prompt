# 仓库治理操作手册

应当将本文件与 `SKILL.md`、`dimensions.md` 配合使用。每份操作手册对应一项治理任务的有序检查；
`dimensions.md` 陈述规则，本文件将规则转化为步骤。应当适用与仓库项目类型匹配的操作手册，为每一项记录证据，
并将例外保留于 `GOVERNANCE.md`。不适用的操作手册项应当记录为“不适用”及原因，不得静默跳过。

正文“审查清单”为设计期权威；本文件仅载建仓、发布与安装验证时点的工作表与正文未展开的条件。

## 新仓库清单

仓库应当依下列顺序创建，使首次推送即合规；事后补上上述各项，将付出历史记录与一次迁移的代价。

- 创建任何内容之前，应当确认负责团队、以一句话表述的用途、项目类型与可见性。
- 应当在存续时间将超过项目的组织下创建，不得在个人账号下创建，并记录经 `naming-conventions` 批准的仓库名
  与包名。
- 应当在托管设置中设定描述、主题与主页；不得保留任何默认值字段。
- 应当记录所有者与法务审查者作出的许可证决定，随后将批准的文本添加为 `LICENSE`。
- 应当在被认可的根路径添加 README 入口文件；其内容与结构由文档角色管辖。
- 应当在首次提交前添加 `.gitignore`、`.editorconfig` 与 `.gitattributes`，包含项目所需的语言与平台类别。
- 应当通过 `vcs-collaboration-conventions` 的保护规则与审查者数量保护默认分支；记录治理后果：每次合并均
  指向可问责角色。
- 应当为每条可合并路径添加 `CODEOWNERS`；其语法、回退与校验机制由 `vcs-collaboration-conventions` 管辖。
- 仓库公开之前，应当于被认可的路径添加 `SECURITY.md`；其内容与响应承诺由安全角色管辖。
- 应当在项目类型清单要求之处添加 `CONTRIBUTING.md` 与 `CODE_OF_CONDUCT.md`；issue 跟踪器作为支持路径的，
  应当添加 `SUPPORT.md`。
- 应当在项目类型清单要求之处添加 issue 表单与 PR 模板。
- 首次发布前应当预留包名与包仓库坐标；名称本身由 `naming-conventions` 管辖。
- 应当在默认分支上启用依赖更新与告警、机密扫描与必需状态校验。
- 应当安排首次权限审查与清单审查，并记录两个日期。

## 仓库元数据设置

每个字段应当设置一次，自仓库外部校验，并且仅在经过审查的变更中修改。

| 设置 | 必需值 | 校验位置 |
|---|---|---|
| 描述 | 一句说明工作的句子；不得使用口号，不得留空。 | 托管设置与包 manifest。 |
| 主题 | 用户实际输入的搜索词；不超过十个。 | 托管设置。 |
| 主页 | 文档或产品入口，且可解析。 | 托管设置与 manifest。 |
| 默认分支 | CI 与分支保护所指向的受保护分支。 | 分支保护。 |
| 可见性 | 仅在许可证、安全与行为准则文件就绪时公开；单人仓库按 `SKILL.md` 记录理由、替代联系方式与补偿控制后，可以在不提供行为准则时公开。 | 权限审查。 |
| 许可证识别 | 与 `LICENSE` 文件及 manifest 的 SPDX 标识符一致。 | 托管平台许可证识别与 manifest。 |
| 发布 | 启用；版本管理、时机与标签遵循 `release-operations-conventions`。 | 发布列表。 |
| 讨论 | 仅在有负责人与响应预期时启用。 | 托管设置。 |
| issue 跟踪器 | 启用并配置模板，或重定向至支持路径。 | 托管设置。 |
| 合并策略 | 与分支模型匹配的单一允许方法。 | 分支保护。 |
| 安全功能 | 在可用处启用依赖告警、机密扫描与代码扫描。 | 安全设置。 |
| 归档标志 | 仅在归档清单完成后设置。 | 托管设置。 |

## 卫生审查清单

应当按计划并在转移、重大发布或仓库拆分之前运行本审查；为每项结果记录产生它的命令，以及任何例外的负责人。

- [ ] 全新克隆并执行文档化的构建后，工作树干净。
- [ ] `.gitignore` 覆盖本地配置、凭据、构建输出、缓存与编辑器状态。
- [ ] 无已跟踪文件匹配忽略规则，亦无运行项目所需的被忽略文件。
- [ ] 每个超过大小阈值的已跟踪文件均位于 LFS 或产物库中。
- [ ] 每个需要 LFS 的 CI 任务均在检出前安装 LFS。
- [ ] 无生成文件在缺少来源、命令、版本与生成器标记的情况下被跟踪；可由 CI 重建的，重新生成不产生 diff。
- [ ] 无第三方引入目录缺少上游版本、许可证与补丁列表。
- [ ] 每个子模块均指向可达提交，并说明其用途。
- [ ] 依赖更新工具按固定频率运行；升级按主/次/补丁分级并有具名负责人；安全修复优先；更新请求经过与其他变更相同的门禁。
- [ ] 超过保留窗口的已合并分支已删除。
- [ ] 长期分支带有负责人与退出日期。
- [ ] 未发布标签已移除，已发布标签不可变。
- [ ] monorepo 各包能够独立构建与测试，CI 依变更路径选择。
- [ ] 默认分支已应用 `vcs-collaboration-conventions` 的保护规则。
- [ ] 机密扫描发现已报告且有负责人；未经负责人决定，不得开始重写历史。
- [ ] 归档或活跃状态与 README、支持页与元数据一致。

## 维护者阶梯与权限

能力应当通过托管平台团队授予，不得通过个人账号授予；授予应当按权限审查计划审查。

| 角色 | 可以 | 不可以 | 授予方式 |
|---|---|---|---|
| 贡献者 | 报告 issue、打开 PR、对提案发表评论。 | 合并、发布、更改设置或权限。 | 平台账号。 |
| 审查者 | 批准范围明确的变更、请求修改、分诊已标注区域。 | 合并默认分支、发布、管理权限。 | 维护者提名。 |
| 提交者 | 合并非默认分支、为 issue 添加标签并分配、关闭过时 issue。 | 发布版本、更改保护、添加成员。 | 维护者投票。 |
| 维护者 | 合并默认分支、发布与撤回版本、管理团队与设置、任命角色。 | 单独更改治理；单独删除或转移。 | 维护者决定加组织所有者。 |
| 组织所有者 | 转移、归档、删除并设定组织级政策。 | 未经维护者同意覆盖日常代码决策。 | 组织任命。 |
| 荣休维护者 | 保留荣誉与顾问发言权。 | 批准、发布或持有任何权限。 | 不活跃通知后的维护者决定。 |

## RFC 流程步骤

公开接口变更、破坏性变更、影响广泛的新外部依赖、仓库拆分或合并、治理变更、许可证变更或发布模型变更，应当
使用提案。

1. 检查变更是否需要提案；不需要的，应当将决定记录于 PR 中。
2. 复制提案模板并分配下一个编号；不得重用编号。
3. 填写问题、目标与非目标、提案、备选方案、风险、上线与未决问题；写明受影响的项目类型与用户。
4. 应当在贡献者能够阅读与评论之处打开提案，并在声明的渠道上公告。
5. 应当举行评论窗口，并在文档中回应反对意见，不得仅在评论线程中回应。
6. 应当进入具有明确结束时间的最终评论期；仍有未解决阻塞性反对的提案不得推进。
7. 应当按记录的决策模型与指定的批准者决定，并记录接受、拒绝或撤回及其理由。
8. 应当链接实现该变更的 PR 与发布，并更新文档索引。
9. 被拒绝的提案应当连同原因保留于记录中；仅在出现新证据时方可重新打开。

## 归档与转移清单

项目停止时归档；归属转移时转移。两者均具有足够的不可逆性，须经所有者批准并作书面记录。

### 归档

- 应当在项目渠道与 README 横幅中公告归档，写明最后支持版本与日期。
- 应当设置归档标志，并确认 issue、PR 与讨论不接受新条目。
- 应当以声明的原因关闭未关闭的 issue 与 PR，并在存在时指向维护中的 fork 或支持路径。
- 应当保持发布、标签与许可证可用，并说明固定版本仍可安装。
- 应当询问安全角色是否仍接受报告，记录答复及其截止日期，并为归档通知标注日期。
- 应当移除或轮换 CI 机密、webhook、部署密钥与发布 token。
- 应当指定负责归档仓库及其年度审查的管理员。
- 应当保持描述、主页与主题准确；归档仓库仍会被搜索找到。

### 转移

- 应当确认接收组织拥有该名称并接受维护义务。
- 迁移前应当审查权限、应用、webhook、部署密钥与包发布权。
- 应当在启用重定向的情况下实施转移，并验证旧克隆与 Web URL 仍能够解析。
- 应当更新 manifest 的 repository 与 homepage 字段、包元数据、CODEOWNERS 与文档链接。
- 应当在新位置重新运行 CI，重新添加机密，并轮换所有接触过旧组织的 token。
- 应当在新所有者下验证发布，并确认包仓库显示新的仓库 URL。
- 应当公告转移，并在托管平台允许的范围内保持旧名称被占用或重定向。
- 重定向与发布检查通过后，应当移除旧组织的权限。

## 打包与发布清单

打标签、门禁、签名与校验和、制品晋级，由 `release-operations-conventions` 的发布就绪检查清单管辖；本清单
管辖打包与分发一侧；下列每一项均为证据，证明产物内容与渠道符合预期。

- [ ] 版本已在唯一来源中提升，且无其他副本不一致。
- [ ] 变更日志条目已说明用户可见变更与升级动作。
- [ ] manifest 元数据完整，且对包仓库有效。
- [ ] 安装测试已在空环境中自预发包仓库通过。
- [ ] 已检查产物内容；其中无本地路径、测试数据或开发依赖。
- [ ] 许可证、README、`THIRD-PARTY-NOTICES` 与必需文件已存在于产物中。
- [ ] SBOM 已生成，发布记录已引用。
- [ ] 发布使用来自受保护发布环境的包作用域 token 运行。
- [ ] 文档角色管辖的发布说明文档链接变更日志与产物摘要。
- [ ] 发布后自消费者账号重新核对包仓库元数据。
- [ ] 文档、支持页与公告反映该发布。
- [ ] 失败的发布经撤回或弃用路径处理，并保留给固定版本的用户。

## 安装验证脚本大纲

发布后应当于一次性容器或虚拟环境中运行本大纲；此处以 Python 作为具体工具链示例，应当替换为所在生态的安装
与冒烟命令。退出码与打印的版本，应当与已测试运行时矩阵一并记录，作为证据。

```bash
#!/usr/bin/env bash
set -euo pipefail

package="example-package"
version="1.2.3"
work="$(mktemp -d)"
trap 'rm -rf "$work"' EXIT

# Start from an empty environment: no project checkout, no local path override.
python3 -m venv "$work/venv"

# Install only the published artifact, pinned to the released version.
"$work/venv/bin/python" -m pip install --no-cache-dir "${package}==${version}"

# Assert the resolved version and that the public entry point loads.
"$work/venv/bin/python" -c "import importlib.metadata as m; print(m.version('example-package'))"
"$work/venv/bin/python" -c "import example_package; print(example_package.__name__)"

# List installed distributions to catch development dependencies that leaked in.
"$work/venv/bin/python" -m pip freeze
```

- 应当在受支持矩阵中的每个运行时与操作系统上重复该大纲。
- 对于命令行包，应当将导入检查替换为帮助命令与一次文档化的示例调用。
- 应当将安装后的产物摘要与已发布摘要比对；不一致的，停止公告并启动事故处理。
