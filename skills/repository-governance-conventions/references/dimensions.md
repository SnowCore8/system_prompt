# 仓库治理维度

本文件与 `SKILL.md` 配合使用。每一节规定一个治理维度的规则、好坏示例与边缘情况。组织政策与全局用户约束位于
第 1 层；既有仓库约定与事实作为输入，依 `SKILL.md` 的规则审查与处理，仅当 `SKILL.md` 未规定时补充，不得
覆盖本 skill。本文件提供默认值与理由。章节编号与 `SKILL.md` 中的维度索引一致；`playbooks.md` 将每个维度
转化为有序校验。应当阅读与当前仓库决策相匹配的节。维度自读者最先看到的内容延伸至消费者安装的内容，因此应当
先修复靠前的维度，再信任靠后的维度：缺失负责人或错误的忽略规则将掩盖审查的其余部分。

## 1. 必需的社区文件与元数据

必需文件仅在位于被认可的路径并携带其用途所需字段时方为有效；仅存在者只是一个文件名，不构成治理。项目类型
决定哪些行适用；`playbooks.md` 中的清单解决类型冲突。

- 应当将每个必需文件置于托管平台与工具查找的位置：`README.md`、`LICENSE`、`SECURITY.md`、
  `CONTRIBUTING.md`、`CHANGELOG.md` 与 `CODEOWNERS` 置于根目录或托管平台文档化的替代位置；issue 与 PR
  模板置于 `.github/` 下；文档索引置于 `docs/README.md` 或文档根目录。命名正确但置于其他目录的文件，对
  每个使用它的工具而言均等同于缺失。README 应当存在于被认可的路径，并能够自仓库入口到达；其内容、结构与
  文笔遵循文档角色。
- 单许可证与多许可证仓库的许可证文本、`LICENSE` 名称与 SPDX 镜像规则见 `SKILL.md` 核心规则「首次公开推送之前须具备许可证」。仅有名称而无条款，或 README 中一句“MIT”而无文件，将使消费者与许可证扫描器无法取得条款；许可证变更属于所有者的决定，不构成一次编辑。
- 双许可或多许可证仓库应当以 `LICENSE` 说明各许可证适用的文件与选择方式，各许可证全文分别置于独立文件中；
  此与 `SKILL.md` 中“单人仓库与双许可”的规则一致；仅有许可证名称不构成条款。
- 随包分发第三方组件的署名声明：`THIRD-PARTY-NOTICES.md` 应当记录第三方引入代码与依赖的许可证与来源，并随
  发布制品一并打包。内容与署名完整性由 `security-compliance-conventions` 规定；本维度仅要求文件存在、可到达
  并随包。
- CONTRIBUTING、CODE_OF_CONDUCT 与 SUPPORT 应当作为一份贡献者契约：CONTRIBUTING 规定环境搭建、测试与提交
  步骤；CODE_OF_CONDUCT 说明预期行为与私下执行联系人；SUPPORT 说明支持范围，并将安全报告引向安全文件。
  复制的行为准则保留空白联系人行，比没有更糟，因其承诺了一条不存在的途径。
- 本 skill 仅管辖 SECURITY.md 的存在、位置与基本元数据：文件位于被认可的路径、可到达、写明负责人，并带有
  审查日期。其必需内容、报告承诺与响应窗口由 `security-compliance-conventions` 管辖；结构与文笔由
  `documentation-conventions` 管辖。内部服务仍然需要该文件，因其报告亦不得转为公开 issue。
- 审查与收集应当按后果路由：每条可合并路径均须指向可问责角色；CODEOWNERS 映射与校验机制由
  `vcs-collaboration-conventions` 管辖，并由其负责 issue 与 PR 模板的必需字段。仅应要求分诊者或审查者会
  使用的字段，因未使用的字段将使贡献者习惯于跳过全部字段。
- 其余项目记录应当保留，并携带其用途所需的字段：CHANGELOG 按版本列出用户可见变更及每项所需的升级动作；
  GOVERNANCE 说明决策模型与阈值；MAINTAINERS 写明活跃维护者与继任者；CITATION.cff 携带标题、作者、版本、
  日期、许可证与仓库；`.github/FUNDING.yml` 列出赞助渠道；文档索引将读者任务映射至核心页面。
- 仓库级文件行为应当在根目录点文件中统一：`.editorconfig` 设定 UTF-8、LF、末尾换行、去除行尾空白与缩进；
  `.gitignore` 覆盖本地配置、凭据、构建输出、缓存与编辑器状态；`.gitattributes` 设定行尾规范化、LFS 模式
  以及生成文件或导出标记。
- 仓库元数据应当作为必需字段：描述为一句说明工作的句子；主题为用户搜索的术语；主页为产品或文档入口；默认
  分支为保护与 CI 的目标；可见性、发布与讨论均为有意设置。描述与主页应当镜像至包 manifest，使仓库页面与
  包页面无法不一致。

### GitHub 托管设置

仓库使用 GitHub 时，下列设置属于本维度的必需项。每项应当记录当前值、核对日期与负责人；无法读取设置的，
记录缺口，以仓库内配置文件为准，并请求有权限者核对，不得猜测设置值。

| 设置 | 必需状态 | 证据 |
|---|---|---|
| 默认分支 | 由规则集保护，合并需批准与必需校验；机制由 `vcs-collaboration-conventions` 管辖。 | 规则集页面或 API 导出。 |
| Actions 权限 | `GITHUB_TOKEN` 默认只读；工作流按需提升单个作业的权限；禁止将写权限设为全局默认。 | 仓库 Actions 设置。 |
| Actions 准入 | 仅允许 GitHub 维护的 action、已验证创建者或白名单；其余固定到全 SHA 或使用工作流依赖锁文件。 | 允许列表与工作流 diff。 |
| Actions PR 权限 | 禁止 Actions 创建或批准 pull request；需要自动化的，使用独立的机器人身份并记录审查路径。 | 仓库 Actions 设置。 |
| fork 构建 | 首次贡献者的 fork PR 需批准后运行；fork 构建不获得仓库机密；不得在 `pull_request_target` 中检出并执行不可信代码。 | 工作流事件与机密作用域。 |
| 自托管运行器 | 公开仓库不使用自托管运行器；私有仓库使用隔离、短生命周期或 JIT 运行器，并按组限制访问。 | 运行器组设置。 |
| 环境 | 生产与预发布使用受保护环境，配置必需审查者、等待计时器与允许的部署分支或标签；环境机密仅在批准后可用。 | 环境设置与部署记录。 |
| 依赖图与告警 | 启用依赖图、Dependabot 告警与安全更新；版本更新由 `.github/dependabot.yml` 按生态与频率配置。 | 安全设置与依赖清单。 |
| 机密扫描 | 在套餐支持处启用机密扫描与推送保护，并为自有令牌格式配置自定义模式；推送保护不得被例行绕过。 | 安全设置与绕过记录。 |
| 代码扫描 | 启用 CodeQL 默认设置或等价的高级设置；风险分支的规则集要求代码扫描结果。 | 代码扫描配置与规则集。 |
| 私有漏洞报告 | 启用私有漏洞报告，并在 `SECURITY.md` 中指向该入口；公告通过仓库安全公告发布。 | 安全设置与公告。 |
| 不可变发布 | 在仓库或组织级启用不可变发布；已发布标签与资产不可改写，发布证明随发布生成。 | 发布设置与证明。 |
| 文档站 | 使用 GitHub Pages 时，发布源分支受保护，构建由 Actions 执行，部署权限仅授予发布工作流。 | Pages 设置与工作流。 |

功能受套餐限制时，应当记录不可用项、影响与补偿控制。公开仓库通常可以使用依赖图、Dependabot、机密扫描
与代码扫描；私有仓库的依赖审查、代码扫描与机密扫描需要组织套餐与相应安全产品授权。不可用不构成跳过
其余控制的理由。

### 第三方审计

OpenSSF Scorecard 提供仓库外部可验证的检查项：分支保护、代码审查、CI 测试、危险工作流、依赖更新工具、
许可证、依赖固定、SAST、安全策略、签名发布、令牌权限与已知漏洞。应当按周或按发布运行 Scorecard 工作流，
将 SARIF 结果上传至代码扫描，并为每项发现指定负责人与到期日。Scorecard 检查的是可自动观测的信号，不替代
本 skill 的必需文件、各 owner 的规则或人工审查；低分应当解释，不得以“工具未检测到”关闭发现。

| 好 | 坏 | 为什么 |
|---|---|---|
| 单许可证仓库的 `LICENSE` 包含完整文本，manifest 包含其 SPDX 标识符。 | `LICENSE.md` 仅包含许可证名称。 | 识别、法务审查与扫描器均需要条款与标识符。 |
| 双许可仓库的 `LICENSE` 说明适用文件，各许可证全文置于独立文件中。 | 双许可仅在 README 写“MIT 或 Apache-2.0”，而无全文。 | 消费者与扫描器需要可识别的完整条款；说明与全文缺一不可。 |
| `SECURITY.md` 位于被认可的路径并记录负责人。 | 安全路径仅存在于 README 的一段文字中。 | 工具与报告者将查找该文件；承诺由安全角色管辖。 |
| `README.md` 位于被认可的路径并链接入口。 | 入口文档仅存在于 wiki。 | 工具与读者自被认可的文件开始；其内容由文档角色管辖。 |
| 每条可合并路径均指向可问责角色。 | 未分配角色的路径在无审查者的情况下合并。 | 无主路径即治理失败；映射机制由 `vcs-collaboration-conventions` 管辖。 |
| issue 表单要求版本、环境、复现与日志。 | 启用空白 issue，未设模板。 | 分诊者须在第一次回复中收集基本信息。 |
| `.editorconfig` 设定 UTF-8、LF 与末尾换行。 | 编辑器混写 CRLF 与 LF。 | diff 噪声大，脚本将把回车当作数据。 |
| `.gitattributes` 标记 LFS 模式、生成文件与导出过滤器。 | 以 `.gitignore` 隐藏已跟踪的二进制。 | 忽略规则不会作用于已跟踪文件。 |
| CHANGELOG 按影响分组并说明必需的升级动作。 | 变更日志为提交日志的堆砌。 | 读者无法找到需要升级步骤的变更。 |
| CITATION.cff 携带标题、作者、版本、日期、许可证与仓库。 | README 仅以一句话提示“引用本项目”。 | 引用工具需要结构化字段。 |
| GOVERNANCE.md 写明决策模型、评论窗口与平局裁决者。 | 仅称“维护者决定”。 | 有争议的变更将停滞，因无规则说明如何收尾。 |
| CONTRIBUTING 自全新克隆至测试通过仅有一条路径。 | CONTRIBUTING 仅列风格规则。 | 新贡献者无法复现构建。 |
| 行为准则写明私下执行联系人。 | 复制的模板保留空白联系人。 | 报告无处提交，执行流于形式。 |
| 托管平台描述与 manifest 描述为同一句话。 | 仓库页面与包页面描述不同项目。 | 用户与搜索结果看到两个项目。 |
| 默认分支为 CI 与托管设置所指向的受保护分支。 | 默认分支未受保护，且在某一工具中被重命名。 | 未经审查的变更将到达消费者安装的内容。 |
| 文档索引将读者任务映射至核心页面。 | `docs/` 下有数十个未链接的文件。 | 读者无法到达本可帮助其解决问题的页面。 |
| MAINTAINERS.md 写明当前维护者与继任者。 | 管理权限为“谁在维护”的唯一记录。 | 权限不构成名册，继任因此未知。 |

## 2. 仓库卫生

卫生决定之后每次审查所见内容：文件树、历史与分支列表或者支持审查，或者掩盖真相。应当按计划并在任何转移
之前审查，因上述事实在早期检查成本低，待用户依赖后再修复则成本高。

- 应当保持被跟踪文件与被忽略文件互不相交：全新克隆并构建后，不得有已跟踪文件被修改，亦不得有运行所需的
  文件被忽略。本地配置、凭据、构建输出、缓存与编辑器状态应当被忽略；并以干净检出验证结果，不得信任模式
  列表。
- 可由 CI 重建的构建输出不得提交；必须跟踪的生成产物及其来源、命令与版本条件见 `SKILL.md` 核心规则「可由 CI 重建的构建输出不得提交」。文件头须带生成器名称与版本；CI 校验应当重新生成并比对；不得手工编辑。无法由 CI 重建但仍须随包分发的产物，按同一条件记录后方可跟踪。工具要求时，lock 文件属于输入；应当说明该规则并在每个包中遵循。
- 应当在历史增长前设定大小与资产策略：默认阈值约 10 MB；超过该阈值的文件须有 `.gitattributes` 模式；每个
  克隆与 CI 任务均须能够使用 LFS；发布二进制应当附加至发布，不得置于树中；运行时媒体应当在提交前优化；
  设计源文件应当保留于设计工具或 LFS；每个资产应当记录许可证与来源；并以 `export-ignore` 将源资产排除出包。
  迁移已有大对象将重写历史，因此应当作为需要克隆冻结的协同变更提出，不得单方面执行；无来源的资产视为不可
  发布。
- 应当按计划清理分支与标签：已合并分支应当在声明窗口内删除；长期分支应当在描述中指定负责人与退出日期；在
  声明过时期间内无提交的分支应当移除；从未成为发布的标签应当删除。打标签时机与标签指向由
  `release-operations-conventions` 定义，标签命名的语法由 `naming-conventions` 确定，已发布标签的不可变与保护由
  `vcs-collaboration-conventions` 负责。
- 子模块与第三方引入代码应当固定：子模块应当指向一个提交，在父仓库中说明用途，并自 CI 可达；第三方引入目录
  应当携带上游版本、许可证与补丁列表，使后续更新成为可重复流程。应当优先使用包依赖而非复制；不得跟踪移动
  分支，不得静默编辑第三方引入文件。
- 依赖更新的工具、分级、审查人数、安全修复优先级与门禁见 `SKILL.md` 核心规则「依赖更新应当有策略」；不得将自动更新作为绕过审查与门禁的通道。
- monorepo 应当组织为工作区：一个根 manifest 与 lock 文件；每个包目录一个包 manifest；共享工具配置置于根；
  使用显式包边界，不得使用深层相对导入；在 CODEOWNERS 中按包归属；CI 应当依变更路径选择受影响的包。无边界
  monorepo 仅为具有多个目录的单一项目。
- 已终止项目应当适用归档策略：设置归档标志，使仓库只读；在 README 横幅中写明最后支持版本与原因；关闭或
  重定向 issue 与讨论；保持发布与许可证可用；说明是否仍接受安全报告；并指定管理员。归档应当每年审查；仅当
  维护中的 fork 为独立且清楚标识的项目时，方可链接。
- 转移、重命名、镜像与 fork 应当作为协同变更：转移至接收组织并使用托管平台重定向，随后更新 manifest、包
  元数据、CODEOWNERS、CI 机密、webhook 与文档链接，并验证旧克隆 URL 仍会重定向。镜像应当声明权威仓库与
  同步方向；fork 应当作为副本；除项目明确说明外，fork 既不是备份，也不是分发渠道。

| 好 | 坏 | 为什么 |
|---|---|---|
| `.gitignore` 列出 `.env`、`dist/`、`.cache/` 与编辑器目录。 | 宽泛的 `*.json` 忽略隐藏已跟踪配置。 | 宽泛模式将使必需文件对整个团队不可见。 |
| 全新克隆并构建后工作树干净。 | 构建重写已跟踪的生成 manifest。 | 已跟踪输出将制造持续的不相关变更。 |
| 200 MB 的媒体文件置于 LFS 或发布页。 | 视频曾被提交至历史一次。 | 每次克隆与镜像均须永久承担该代价。 |
| 生成代码在文件头带有生成器与版本。 | 生成的客户端被就地手工编辑。 | 下次重新生成将静默移除编辑。 |
| 已合并分支在声明窗口内删除。 | 数百个已合并分支被保留。 | 分支列表掩盖活跃工作，并引发过时 cherry-pick。 |
| 附注标签标记发布提交。 | 标签指向此后一个不相关的提交。 | 安装者自未经测试的树构建。 |
| 子模块固定至提交并记录用途。 | 子模块跟踪移动分支。 | 构建每天不同，无法复现。 |
| 第三方引入目录具有上游版本、许可证与补丁。 | 上游 `main` 的副本带有本地编辑。 | 来源与更新路径未知。 |
| monorepo 具有根工作区 manifest 与包 manifest。 | 包通过深层相对路径导入。 | 边界被破坏，CI 无法选择受影响的包。 |
| 归档仓库只读，带横幅与最后版本。 | 仅设置归档标志，issue 仍然开放。 | 用户误认为仍在维护，却得不到答复。 |
| 转移保留重定向并更新元数据与链接。 | 旧链接、克隆与包页面停止工作。 | 迁移后用户无法找到项目。 |
| fork 记录权威仓库与同步方向。 | fork 带有独有修复并被四处传递。 | 用户安装过时或分叉的副本。 |
| CI 在检出前安装 LFS。 | CI 将 LFS 指针作为文本检出。 | 构建失败或发布损坏文件。 |
| 发布二进制附加至发布。 | 二进制被提交于 `dist/` 下。 | 历史膨胀，过时产物自树中发布。 |
| `.gitattributes` 规范化文本，并将源资产排除出包。 | 混合行尾与设计源文件被打入包。 | diff 与包行为因平台而异。 |
| 死代码在检查引用后删除。 | 批量删除未经引用检查即运行。 | 清理之后方暴露坏链与坏导入。 |

## 3. 治理与决策流程

治理是对“谁作出决定、如何作出决定，以及当前维护者离开后谁继承仓库”的书面回答。应当在发生争议之前写成
书面形式，因在争执中发明的规则读起来像利益，而非政策。

- 角色阶梯应当按能力而非头衔定义：贡献者提出变更；审查者批准范围明确的变更；提交者合并非默认分支并分诊
  issue；维护者合并默认分支、发布版本、管理权限并任命其他角色。每项能力应当记录于 `GOVERNANCE.md`，并
  通过托管平台团队授予，不得通过个人账号授予。
- 决策模型应当声明：单团队项目采用维护者主导；社区项目采用带明确窗口的惰性共识；共享治理采用带法定人数、
  多数与平局裁决的正式投票。应当写明何种模型适用于何类变更，并记录每个决策及其理由与已考虑的备选方案。
- 提案应当经由明确路径：为提案编号；使用固定模板（问题、目标与非目标、提案、备选方案、风险、上线与未决
  问题）；保留评论窗口；以最终评论期收尾；并记录接受或拒绝的结果。在聊天线程中决定的设计，一旦线程滚出
  视野即丢失理由。
- 审批应当路由，不得自行设定：代码变更的审查者数量来自 `vcs-collaboration-conventions`；按发布类型的审批
  来自 `release-operations-conventions`；本维度仅补充自身治理规则：治理或归属变更须有两名批准者；作者不得
  批准自身的治理或归属变更；单人仓库的批准例外见 `SKILL.md` 核心规则「继任安排应当在需要之前记录」。路由后
  的规则应当记录于 `GOVERNANCE.md`，使读者看到一套政策。
- 继任与巴士因子应当纳入计划：维护者人数、单点与补偿控制以及 `MAINTAINERS.md` 的继任者记录要求见
  `SKILL.md` 核心规则「继任安排应当在需要之前记录」；托管访问权限应当由组织托管或可由组织恢复；不活跃
  维护者应当经通知转为荣休；权限应当每季度及每次离开后审查。仅有一名管理员的仓库，距离丢失仅差一次缺席。
- 冲突应当依规则解决：在提案中讨论；升级至维护者；再升级至指定的平局裁决者；并记录决定与反对意见。决定
  被记录前应当保持现状；不得合并仍有争议的变更；个人行为问题应当路由至行为准则流程，不得于技术线程处理。
- 行为准则应当具备可执行性：报告经由私下渠道提交；至少两名响应者处理；与事件存在利益冲突的响应者应当
  回避；应当说明保密性；结果自警告至临时或永久封禁；结果应当在不含个人数据的前提下记录；并应当存在申诉
  途径。为展示执行而公开事件细节，将伤害该流程本应保护的人员。
- 发布权应当明确：写明谁可以打标签、发布与撤回；按发布类型的审批规则交由 `release-operations-conventions`
  管辖；重大发布应当分离作者角色与发布者角色；签名密钥的存放与轮换由 `security-compliance-conventions` 管辖；紧急发布路径应当指定权限与强制
  复盘。每名维护者笔记本上各有一个包 token 的，将使每个被攻陷的账号均成为发布风险。

| 好 | 坏 | 为什么 |
|---|---|---|
| 角色阶梯列出能力与授予该能力的托管平台团队。 | 角色为无权限映射的职位名称。 | 期望与权限均未定义。 |
| 惰性共识声明窗口，并要求明确反对。 | 对每个变更均“沉默即批准”。 | 无人查看线程的有争议变更将被通过。 |
| 编号 RFC 记录决策、理由与被否决的选项。 | 设计于聊天线程中决定。 | 理由丢失，同一争论将再次出现。 |
| 审批规则路由至所有者 skill；治理与归属变更须有两名批准者。 | 一个本地阈值覆盖所有变更。 | 本地数量与所有者 skill 矛盾，导致拖慢或审查不足。 |
| 存在两名管理员与指定继任者。 | 一名所有者持有全部权限。 | 该人员离开时，项目将丢失。 |
| 长期不活跃维护者经通知转为荣休。 | 不活跃账号继续持有管理权限。 | 休眠凭据仍可被利用。 |
| 冲突升级至维护者，再至指定平局裁决者。 | 无休止的线程没有决策规则。 | 项目停滞，贡献者离开。 |
| 行为准则报告进入私下响应小组。 | 报告在公开 issue 跟踪器中处理。 | 报告者与报告均被暴露。 |
| 执行结果在不含个人数据的情况下记录。 | 完整事件细节被复制至公开日志。 | 记录将伤害其本应保护的人员。 |
| 按发布类型的审批来自 `release-operations-conventions`。 | 任何维护者均可批准自身的发布。 | 本地发明的审批规则与发布操作手册冲突。 |
| 作者不得批准自身的治理或归属变更。 | 作者批准自身的治理变更。 | 独立批准防止规则被自私编辑。 |
| 治理或归属变更须有两名维护者批准。 | 一名维护者于一个提交中编辑治理文件。 | 两名独立批准者防止规则被单方面编辑。 |
| 被拒绝的提案连同原因记录。 | 被拒绝的提案未经决定即消失。 | 同一提案每季度重新出现。 |
| 权限每季度及每次离开后审查。 | 权限于入职时授予，永不移除。 | 权限累积并超出其正当理由。 |
| 紧急发布路径具有指定权限与审查。 | 紧急路径静默绕过所有门禁。 | 速度得以保持，但绕过从未受审查。 |
| 发布权属于角色，不属于个人。 | 仅有一个人的 token 能够发布。 | 一次休假或离开将阻塞所有发布。 |

## 4. 打包与分发

打包属于治理的最后一环：正确的仓库若发布不可验证或不可安装的产物，仍然辜负用户。每条规则均应当自消费者
一侧判断，因仅在陌生人能够安装并检查产物时，该规则方为满足。

- 首次发布前应当预留包名与作用域，每个名称仅保留一个产物；包与仓库的命名本身由 `naming-conventions` 管辖。
  发布权归组织团队，不归个人账号；重命名时应当以新名称发布，并自旧名称提供一条弃用指针。
- manifest 应当精确：名称、版本、描述、SPDX 许可证、仓库 URL、主页、关键词、作者或维护者、支持的运行时
  范围与文件允许列表。发布前应当以包仓库自身的工具校验，自一个来源推导版本，并将本地路径、凭据与开发依赖
  排除出发布制品。
- 分发渠道应当声明：一个主包仓库为 `release-operations-conventions` 所定义版本的权威渠道；私有或预发包
  仓库服务于内部晋升；镜像应当说明同步方向；包可见性属于有意的公开或私有设置。凭据应当仅存放于 CI 环境
  中；自预发晋升至生产应当重复同一安装测试，不得复制信任。
- 产物签名、校验和与来源证明，由 `release-operations-conventions` 的 CI/CD 规则生成与校验，本维度不予复制。
  本维度要求发布记录引用 SBOM 与署名声明，并确认其随产物发布；SBOM 与署名声明的内容由
  `security-compliance-conventions` 规定。
- 安装应当自空环境验证：一个不含项目检出、本地路径覆盖与缓存的全新容器或虚拟环境；自包仓库安装精确的已
  发布版本；确认解析出的版本；通过公共入口运行一次冒烟测试；确认许可证、`THIRD-PARTY-NOTICES` 与必需文件
  随产物发布；并记录输出与测试过的运行时版本。
- 发布应当依 `release-operations-conventions` 定义的顺序实施：打标签、门禁、签名与校验和、制品晋级与不可变
  均在该处定义，本维度不予复制。本维度补充打包侧要求：发布前检查产物内容（无本地路径、测试数据或开发
  依赖）；将文档角色管辖的发布说明文档链接至产物摘要；并确认 SBOM 与署名声明随产物发布。
- 撤回与弃用路径应当定义：适用条件、原因说明与公告要求见 `SKILL.md` 核心规则「以撤回或弃用处理不当发布，不得删除」；包仓库支持时，应当阻止新安装。删除版本将摧毁每个固定过该版本的用户的可复现性。
- 项目发布容器镜像时应当采用同一纪律：包仓库命名空间由组织拥有；不可变摘要加版本标签；生产不得引用
  `latest`；自 CI 实施多架构构建，并带源与修订标签；定期重建基础镜像；发布前实施漏洞扫描；并由部署平台
  校验签名。SBOM 内容由 `security-compliance-conventions` 管辖；本维度要求流水线生成，并要求发布记录引用。

| 好 | 坏 | 为什么 |
|---|---|---|
| 首次发布前预留包名。 | 首次发布选用已被占用的名称。 | 将在最不利的时刻阻塞发布。 |
| 发布权归组织团队。 | 一个人的账号持有唯一发布 token。 | 该人员不在时，包无法发布。 |
| manifest 携带 SPDX 许可证、仓库、运行时范围与文件。 | manifest 字段依靠猜测或留空。 | 包仓库与扫描器无法分类或验证包。 |
| 版本仅有一个来源，并由构建复制。 | 版本在三个文件中分别提升。 | 发布出的版本不一致。 |
| 声明主包仓库并记录晋升。 | 产物被手工上传至多个包仓库。 | 一个渠道可能提供不同的构建。 |
| SBOM 与署名声明随产物发布。 | 包中仅有二进制，无许可证或署名声明。 | 消费者无法归因或满足许可证义务。 |
| 安装测试自空环境与包仓库开始。 | 在项目检出中检查安装。 | 未声明依赖与本地路径将被遗漏。 |
| 仅在全部门禁通过后发布；门禁失败且标签未公开、取得 AU-1 明确同意后，方可删除标签。 | 门禁尚未结束即发布制品。 | 失败的门禁不得留下已发布版本。 |
| 在已批准的发布提交上创建标签，并自该标签构建产物。 | 发布后移动标签。 | 标签不再标识已交付的树。 |
| 文档角色管辖的发布说明文档链接产物摘要。 | 发布正文为生成的提交列表。 | 用户需要成文的升级动作，而非提交列表。 |
| 冒烟测试覆盖声明的运行时与操作系统矩阵。 | 仅测试一个运行时、一个操作系统。 | 安装将在受支持平台上失败。 |
| 被撤回的版本说明原因与替代方案。 | 自包仓库删除损坏版本。 | 固定版本的用户无法复现构建。 |
| 弃用写明继任者与移除日期。 | 弃用说明无替代方案。 | 用户无法规划升级。 |
| 生产容器固定不可变摘要。 | 生产引用 `latest` 标签。 | 新推送将静默改变运行内容。 |
| 多架构镜像在 CI 中构建，并带源标签。 | 镜像在笔记本上手工构建。 | 镜像不可复现且无来源证明。 |
| 基础镜像按计划重建并扫描。 | 为求便利保留旧基础镜像。 | 已知漏洞将随每个新镜像发布。 |
| 内部包在安装测试后自预发晋升。 | 自开发包仓库安装内部构建。 | 未验证产物到达生产。 |
