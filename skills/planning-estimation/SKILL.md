# 计划与估算

计划失效有三种典型形态：任务按技术层拆分，谁都说不出做完能给用户什么；估算没有依据，日期靠拍脑袋承诺；基线和风险没登记，一有风吹草动就静默改目标。本 skill 管辖 S2 设计阶段的计划部分：把 G1 确认的需求与验收标准拆成可验收的任务，用带依据的估算排出关键路径，登记风险与跨团队依赖，最后固定一份计划基线，供 S3 跟踪与 S7 复盘对照。
它回答“先做什么、做多久、靠什么保证”，不回答“怎么设计”——后者归 `architecture-design`。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制约束。授权（AUT）、诚实（HON）与变更（CHG）条款优先；不得以计划名义提前执行未授权的操作，也不得把推测写成承诺。
2. 本 skill 的规则。任务拆分、估算、排期、风险登记、依赖登记与基线变更，以本文件与 `references/` 为准。
3. 项目约定与事实。既有待办、里程碑、容量数据与依赖关系是事实输入，先阅读再计划；项目约定仅在本 skill 未规定时补充。

本 skill 管辖：任务拆分、估算与依据、关键路径与排期、风险登记、跨团队依赖登记、计划基线。本 skill 不管辖：需求与验收标准（`requirements-engineering`）、模块边界与分层（`architecture-design`）、实现与提交（`implementation-practices`）、发布与回滚计划的执行操作（`release-operations`）。

## 生命周期定位

上游：G1 的需求、验收标准与收益基线。下游：S3 构建的任务清单与里程碑，S7 收尾的复盘基准。停止条件：关键依赖未确认、估算依据缺失、基线无法固定时停止计划并报告，不得带着缺口排期。

| 阶段 | 职责 | 产出与证据 |
|---|---|---|
| S1 需求 | 核对需求、验收标准与收益基线可作为计划输入，登记初步风险与依赖 | 计划输入清单、初步风险与依赖 |
| S2 设计 | 拆分任务并估算，排关键路径与里程碑，登记风险与跨团队依赖，固定计划基线 | 任务清单、估算与排期、风险登记、依赖登记、G2 证据 |
| S3 构建 | 跟踪任务状态与偏差，更新风险与依赖，变更走重新过门 | 进度记录、偏差报告、变更请求 |
| S7 收尾 | 对照计划基线复盘估算、进度与范围偏差，沉淀行动项 | 复盘结论、行动项与负责人 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G1 需求 | 计划输入核对结论：需求可判定、验收标准存在、收益基线可衡量 | Hold：输入缺失；Recycle 到 S1 |
| G2 设计 | 任务清单与估算依据、关键路径与里程碑、风险登记、依赖登记、计划基线 | Hold：估算无依据或关键依赖未确认；Recycle 到 S1/S2 |
| G3 构建 | 进度与基线的对照记录、偏差说明、变更请求 | Hold：状态未更新；Recycle 到 S2：基线变更未重新过门 |

## 核心规则

- 任务按可验收增量拆分。每个任务做完有一个可演示的结果，纯技术层任务不得单独成为条目。
- 估算必须写明依据。用相对估算或历史数据，说明假设与不确定性；无依据时只给区间，不承诺点日期。
- 关键路径按依赖排序。关键路径上的延误必须当天处理；里程碑必须可核验，不得以“完成 80%”充当。
- 关键依赖未确认不得承诺日期。跨团队依赖没有接口、窗口与失败回退的，计划对相应部分标注未承诺。
- 基线变更必须重新过门。范围、验收、日期或风险变化时，先写变更请求与影响评估，不得静默改目标。
