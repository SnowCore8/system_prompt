# 发布与运维各维度

本文件与 `SKILL.md` 配合使用。每一节规定一个维度的规则、示例与边界情况；各节的“好 | 坏 | 原因”表展示规则
背后的判断依据。项目约定与事实作为输入；项目发布策略、流水线与告警配置，依本 skill 的规则处理。本 skill 的
规则优先；项目约定仅在本 skill 未规定或明确授权时补充。本文件提供默认值与理由。各节编号与 `SKILL.md` 中的
维度索引一致；`playbooks.md` 承载应用上述规则的过程。

## 1. 版本与发布

- 应当将语义化版本视为兼容性声明，不得将其视为营销数字：主版本变更公共契约；次版本增加能力而不破坏契约；
  补丁版本修复行为而不变更契约。递增应当依发布中影响最大的变更推导，不得依提交数量推导，亦不得由发布日期
  决定。
- 语义化版本在 1.0 之前不作任何承诺；本项目的 1.0 之前策略提供该承诺。在 1.0 之前，次版本可以承载破坏性
  变更；补丁版本必须在其所属次版本内保持兼容，因策略如此规定。每个破坏性次版本均须连同迁移路径一并公告；
  `1.0.0` 保留给项目正式承诺契约之时。
- 仅应保留一个版本来源。应当自发布提交设定版本、将其嵌入制品，并使每个环境报告同一值；晋级不得重写该值。
  部署时自分支计算出的版本将因环境而异，并使仪表盘、支持答复与缺陷报告失效。
- 版本号不得重用、重打或覆盖：一个版本号仅对应一个已发布制品；不当发布应当以撤回、弃用或补丁版本处理，
  不得重新构建同一版本。
- 公布节奏与截止点。发布列车按计划发车；错过截止点的功能等待下一班列车，不得推迟发布。服务的持续交付仍
  须切出一份带版本的发布记录，因变更日志、支持答复与回滚目标均需要该记录。
- 为已批准的发布提交打标签，随后自标签构建制品。推送标签及已公开标签的变更属于 AU-1 发布动作，须取得用户明确
  同意；本地标签创建与未公开本地标签删除，在已批准的发布任务内直接执行并留痕，执行者须具备 vcs 规定的标签
  创建权限。标签语法与制品名由 `naming-conventions` 管辖；本流程决定标签的创建时点、指向的提交以及标识的制品摘要。
  应当于已批准的发布提交
  上创建标签，在干净检出中构建并运行门禁；仅当门禁通过且核实制品与标签匹配后，方可发布；门禁失败且标签尚未
  公开的，可在该发布任务内删除并留痕；删除后修复的，应当重新批准并重跑门禁，以新的、经批准的发布提交重建标签，
  且仅在该版本尚未发布时方可重建；已公开标签不得删除，已发布制品必须能够追溯至通过门禁的标签。
- 应当按发布类型写明批准者，公布冻结窗口（财务结算、旺季、节假日），并写明例外审批权限以及冻结期内仍允许
  的变更类别。冻结期内可以实施热修复，但须有例外记录，不得静默绕过。
- 确定发布说明的所有权与时机。发布说明与变更日志文档由 `documentation-conventions` 管辖；本流程要求在批准
  前写好用户可见行为、必需的迁移步骤、已移除的弃用项与已知问题，并使最终发布的说明与交付制品一致。部署后
  方撰写的说明无法为 go/no-go 决定提供依据。
- 公布兼容性承诺：受支持的版本、修复窗口（API 版本的支持窗口由 `api-and-data-conventions` 定义，产品级修复
  窗口应与之一致）、最短弃用通知期以及升级路径。承诺即约束；无法兑现的，应当在发布前以书面形式修订，不得待
  客户询问后方处理。

| 好 | 坏 | 原因 |
|---|---|---|
| 为新可选端点使用 `1.4.0` | 为新端点使用 `1.4.1` | 增加能力的补丁将破坏消费方读取的约束。 |
| 带迁移指南与移除日期的 `2.0.0` | 标注为“小破坏性变更”的 `1.9.9` | 破坏性变更必须在落地前到达消费方。 |
| 于已批准提交上打标签，自标签构建制品 | 先构建制品后补标签 | 标签必须指向通过门禁的那一提交。 |
| 冻结日期连同例外批准者一并公布 | 冻结仅发布经理知晓 | 未获知冻结的团队会将工作安排进入冻结期。 |
| 发布说明随发布一并批准 | 部署后方撰写说明 | 说明无法为所描述的 go 决定提供依据。 |
| 发布策略写明受支持版本与修复窗口 | “永远升级至最新版” | 消费方无法依一句口号规划修复窗口。 |

节奏取决于产品与受众；发布策略应当写明所选节奏及其版本行为：

| 节奏 | 适用场景 | 版本行为 | 批准 |
|---|---|---|---|
| 持续部署 | 具备功能开关与快速回滚的服务；用户经常看到小变更 | 每次部署均为不可变制品；为变更日志与支持自列车切出版本 | 自动化门禁加值班负责人 |
| 每周列车 | 具备用户可见变更日志且贡献者众多的产品 | 每班列车自截止提交切出一个版本 | 发布所有者 |
| 每月或每季度 | 移动应用、受监管产品或长时间外部测试周期 | 更长的观察期、更宽的冻结与正式签核 | 产品所有者加发布所有者 |
| 长期支持线 | 具备外部消费方的库或平台 | 仅出补丁；新功能进入下一主版本 | 安全所有者加发布所有者 |

发布策略应当记录语义化版本规则、所选节奏行、冻结日历、支持窗口以及每种发布类型的批准者；仓库入口应当链接
该策略。仅存在于发布经理日历中的规则，无法适用于下一次发布。

## 2. 变更管理

- 合并时应当将每项变更分为破坏性、行为改变或内部变更，并将分类记录于发布工具读取之处。版本号递增、通知
  窗口与批准级别均依类别推导，不得依作者信心推导；一次发布应当尽可能仅承载一个类别的变更，因捆绑将扩大
  回滚范围。
- 下列情形视为破坏性：删除或重命名公共名称；改变必填参数、默认值或响应结构；改变事件 schema；改变权限、
  配额或速率限制；以及改变已写入文档的工作流行为。应当在同一变更中更新断言旧行为的测试；静默删除该测试，
  将使有意破坏变为意外。
- 应当按面设定最短通知期：公共 API 为一个主版本与六个月中的较长者；CLI 开关为一个次版本；内部服务契约为一个发布；
  配置默认值为一个发布。弃用路径应当继续可用、接收关键修复，并在使用时告警；提前移除该路径，构成未经通知
  的破坏性变更。
- 应当自三条路径公告：使用旧路径之处（运行时告警、界面提示、旧路径的文档）；用户规划升级之处（发布说明与
  迁移指南）；以及直接通知必须采取行动、承担契约的消费方。应当为每条路径选择受众与渠道；仅依赖一个渠道
  属于假设，不构成沟通计划。
- 每个功能开关均须具备所有者、目的、默认值与移除版本。新行为默认关闭；开关不得替代权限检查，不得嵌套，
  名称不得重用。名称格式由 `naming-conventions` 管辖；本流程管辖生命周期；删除属于放量完成那一发布的一部分。
- 每项破坏均须附带迁移路径：自旧名称、字段或行为至新名称、字段或行为的映射；可行时的机械步骤；迁移自身的
  回滚；以及在与生产同形数据上的演练。要求用户重写客户端，不构成迁移路径。
- 安排沟通时间：公告日期、中点提醒与移除日期；并应当将提醒设为流程步骤，因受众会遗忘。触达应当以回复与
  支持工单衡量，不得以已发送消息数衡量；未衡量触达的通知仅为愿望。
- 部署前应当写好回滚标准：错误率、延迟、业务转化、数据损坏证据与支持量。原因未知且上一版本健康的，优先
  回滚；回滚将逆转已完成数据迁移的，优先前向修复。应当限制自触发至行动的时长，并写明决策主体。

| 好 | 坏 | 原因 |
|---|---|---|
| 合并前在变更上记录分类 | 审查中称“大概不是破坏性变更” | 递增与通知均取决于类别。 |
| 弃用的开关在一个次版本内于使用时告警 | 下一个补丁即移除开关 | 用户将在没有规划窗口的情况下失去一条路径。 |
| 三条公告路径且受众具名 | 破坏性 API 变更仅在变更日志中写一行 | 大多数受影响用户从不阅读变更日志。 |
| 开关与其旧代码路径在同一发布中删除 | 上线后“以防万一”保留开关 | 第二条路径继续处于未测试、无人维护状态。 |
| 迁移映射表与演练记录 | “自行更新集成” | 映射即用户必须实施的工作。 |
| 部署前写好回滚触发条件与权限 | 事故中争论是否回滚 | 压力下作出的决定更慢且质量更低。 |

按变更类别的默认通知期如下；本 skill 授权项目发布策略延长通知期；缩短的，须记录例外及其授权依据，且不得低于
法律或合同所定下限：

| 变更类别 | 通知窗口 | 用户行动 | 公告证据 |
|---|---|---|---|
| 破坏性公共 API 或数据格式 | 一个主版本与六个月中的较长者 | 修改代码或配置 | 弃用通知、运行时告警与迁移指南链接 |
| 输出可见的行为变更 | 一个次版本 | 复查并调整预期 | 发布说明与受影响的文档 |
| 移除 CLI 开关或配置键 | 一个次版本 | 更新脚本或配置 | CLI 告警加参考页更新 |
| 内部服务契约变更 | 一个发布，并在消费方之间协调 | 调整部署顺序或更新客户端 | 面向内部消费方的变更日志条目 |
| 带回填的数据模型变更 | 适用的最长弃用窗口 | 数据迁移 | 迁移指南与演练记录 |

变更台账应当记录每项变更的类别、所需通知窗口、公告日期、弃用页面以及每次发布的回滚标准。类别仅为作者
所知的变更，既无通知，亦无迁移路径。

## 3. CI/CD

- 固定流水线阶段及其必需顺序：干净检出带标签的发布提交、静态校验、一次记录制品摘要的构建、针对该制品的
  测试、集成与端到端校验、带签名与物料清单的发布、部署至开发环境、晋级至 staging、验收校验、记录批准、
  部署至生产、部署后验证。独立阶段并行运行；构建始终先于测试；发布出去的制品即被测试的制品。
- 阶段应当按最早暴露失败优先排序：成本低且确定性的校验先于缓慢、依赖环境的校验；失败阶段将停止其后的全部
  阶段。应当修复不稳定阶段，或连同负责人与到期日一并隔离；以重试取得通过，将使缺陷变为噪声，并使团队习惯
  于绕过流水线。
- 使构建封闭：固定工具链与依赖版本；使用指向权威包仓库的锁文件；拒绝访问该包仓库之外的网络；并自无本地
  状态的干净检出构建。应当将提交、工具链与锁文件随制品一并记录，并明确说明构建在哪些环节并非逐位可复现。
- 应当将每个制品发布至不可变包仓库，记录其摘要，并不得修改或删除已记录发布所指向的制品。标签创建权限与
  不可变保护由 `vcs-collaboration-conventions` 裁定。每个生产制品应当至少保留至回滚与支持窗口结束；预发布
  制品应当保留至足以调试其来源发布；制品保留期短于回滚窗口的，将使写入文档的回滚无法执行。仅应缓存按锁
  文件哈希键控的不可变依赖，不得跨提交缓存构建输出或测试结果。
- 应当为每个制品生成校验和，并以存放于仓库之外的密钥签名：发布页公布校验和（如 SHA-256）；消费者按摘要
  验证；签名在晋级过程中保持不变。校验和与签名应当在发布阶段生成，并成为制品不可变记录的一部分。
- 同一制品应当经开发、staging 与生产晋级；环境定义应当保存于版本控制中，列出并审查其差异。staging 必须与
  生产同形：数据应当匿名化；可行时，拓扑与依赖也应当一致。晋级至生产须有针对特定摘要的书面批准；任何手工
  配置修改均不得绕过该批准。
- 应当按风险与状态选择部署策略：具备 N-1 兼容性的无状态服务，使用滚动部署；具备双倍容量且需要快速切换与
  回滚的，使用蓝绿部署；具备成功指标与足以发现不当发布的流量的，使用金丝雀。部署前应当写好比例、时长、成功
  指标与中止标准；每种策略均须具备重新部署已保留制品而非重新构建的回滚。
- 数据库迁移应当与回滚兼容：扩展、迁移、收缩，使上一应用版本能够在整个上线期间针对新 schema 运行。与代码
  变更在同一发布中删除或重命名列的迁移，将消除回滚选项，必须按不可逆变更批准。
- 流水线应当消费安全流程管辖的凭据，不得暴露该凭据；不得在配置 diff、日志、制品标签或测试输出中打印凭据。
  对流水线配置或部署权限的变更属于特权变更，须经与代码相同的审查。

| 好 | 坏 | 原因 |
|---|---|---|
| 测试针对构建出的制品运行 | 测试针对工作树运行，随后另做一次构建用于交付 | 交付的字节从未经过测试。 |
| 摘要连同批准记录晋级至生产 | 自重新构建的分支部署生产 | 部署的制品并非经审查的制品。 |
| 锁文件固定、包仓库受限 | 构建时方解析浮动依赖版本 | 依赖变更未经审查即落地。 |
| 制品保留至支持窗口结束 | 上一发布在包仓库中被覆盖 | 写入文档的回滚没有目标。 |
| staging 使用匿名化的生产同形数据 | staging 使用不同的数据库引擎 | 发布仅在其被调优过的环境上通过。 |
| 回滚任务部署已保留的摘要 | 回滚需要重新运行构建 | 回滚不应当依赖构建此时仍可复现。 |

阶段契约如下；无法产出其证据的阶段不视为通过：

| 阶段 | 必需结果 | 失败条件 | 记录的证据 |
|---|---|---|---|
| 校验 | 格式、lint 与类型校验通过 | 任何校验报告发现项 | 报告加退出码 |
| 构建 | 一个带摘要与物料清单的制品 | 输入未固定或制品不确定 | 摘要与输入清单 |
| 验证 | 针对制品的单元、集成与端到端校验通过 | 针对制品的校验失败 | 测试报告 |
| 发布 | 不可变、已签名的包仓库条目 | 标签被修改或签名缺失 | 签名与保留条目 |
| 晋级 | 同一摘要连同已应用的环境配置部署 | 发生重新构建或手工配置修改 | 批准与配置 diff |
| 验证生产 | 冒烟校验与成功指标保持于阈值内 | 观察期内有指标越出写明范围 | 部署记录与仪表盘快照 |

流水线定义应当记录阶段、其顺序、制品摘要规则、保留窗口、环境差异与机密来源。缺乏文档的流水线，将在第一次
平台变更时依靠猜测重建。

## 4. 可观测性

- 生产日志事件的结构、类型与取值 schema、采样、存储、保留与告警由本流程管辖；日志字段名由
  `naming-conventions` 管辖；日志级别的定义与大小写（ERROR、WARN、INFO、DEBUG）以及日志内容策略由
  `code-style-conventions` 管辖。每个请求或状态转换应当输出一条结构化日志事件，携带时间、级别、服务、版本、
  事件、关联 ID 与错误码等稳定字段。
- 每个服务应当埋点四大信号（流量、错误、延迟、饱和度），并为每条关键用户旅程增加一个业务指标。应当限制
  基数：不得以用户 ID、请求 ID、电子邮件地址或原始 URL 作为指标标签，并使用带显式分桶的直方图而非平均值。
  指标与字段名由 `naming-conventions` 管辖；设计、单位与标签策略由本流程管辖。
- 关联 ID 应当自边缘传播，经过每个同步与异步跳，放入日志与错误响应，并返回给用户以供支持。应当对每个错误
  和一定比例的成功请求采样；追踪属性不得含机密与个人数据；丢弃该 ID 的边界视为缺陷。
- SLI 应当自用户体验定义：有效请求的成功比例、体验所要求的百分位延迟，以及关键旅程的可用性。每个服务应当
  设定一到三个 SLO，带有目标与滚动窗口，推导错误预算，并每季度及每次事故后复查目标。
- 错误预算策略应当在预算耗尽前写好：写明预算被消耗时会发生的事项（功能发布冻结、可靠性工作优先、受影响
  服务的部署批准级别升高）。没有后果的 SLO 仅为仪表盘装饰；无人测量的预算亦无法辩护。
- 应当对用户可见的征兆或 SLO 的燃烧率告警，不得对原始资源值告警；每条告警均须具备严重级别、所有者、运行
  手册与预期行动。应当删除或降级无人响应的告警；按严重级别路由，使 warning 不得在夜间呼叫人工。
- 仪表盘应当作为代码管理：每个仪表盘均须版本管理、像代码一样审查、自流水线供给；每个服务应当具备一个
  仪表盘，包含四大信号、SLO 状态、已部署版本与依赖健康状况。手工编辑的仪表盘将在下次供给时丢失；不含已
  部署版本的仪表盘无法解释一次变更。
- 应当依事故、审查与成本需求为每种信号设定保留期。每种信号均须保留至足以诊断发现较晚的事故：例如 30 天
  日志、13 个月 SLO 聚合、以天计的追踪窗口。保留窗口短于发现窗口的，即为缺陷；审查日志的保留遵循安全角色
  管辖的保留策略。

| 好 | 坏 | 原因 |
|---|---|---|
| SLO 基于成功的用户请求 | SLO 基于进程正常运行时间 | 进程可以正常，而每个请求均失败。 |
| 通过发布成功指标观察金丝雀 | 以“日志中无错误”判断金丝雀 | 信号缺失不等于通过信号。 |
| 告警写明运行手册与预期行动 | 告警仅称“CPU 高”而不给出行动 | 响应者无法决定应实施何种操作。 |
| 将关联 ID 返回给用户 | 支持工单仅能够索要时间戳 | 没有 ID，支持无法找到该请求。 |
| 仪表盘自仓库供给 | 仅在 UI 中编辑仪表盘 | 下次供给将还原该仪表盘，且无人注意。 |
| 日志行离开进程前完成脱敏 | 电子邮件地址写入日志，搜索时方脱敏 | 数据已进入存储，无法收回。 |

信号契约如下；某种信号无法回答其问题的，应当在发布前重新设计：

| 信号 | 它回答的问题 | 示例 | 缺失时的失效模式 |
|---|---|---|---|
| 日志事件 | 该请求发生了什么 | 带关联 ID 与错误码的 `order.create.failed` | 调试自猜测重新开始 |
| 指标 | 服务当前是否健康 | 按端点统计的错误率与延迟直方图 | 无法评判上线结果 |
| 追踪 | 时间消耗于何处 | 自边缘至数据库的 span 树 | 缓慢的依赖隐藏数天 |
| 业务指标 | 用户是否成功 | 每次发布的结账成功率 | 技术健康掩盖产品失败 |

可观测性文档应当记录 SLI、目标、窗口、错误预算策略、告警严重级别与所有者、仪表盘的权威来源，以及每种信号
的保留期。仅存在于工具中的仪表盘，既无审查，亦无历史。

## 5. 事故响应

- 严重级别应当按用户影响确定，不得按原因确定：全面中断、数据丢失或正被利用的安全问题为 SEV1；主要功能或
  大量用户子集降级且无变通方案为 SEV2；影响相同但存在变通方案为 SEV3；轻微影响为 SEV4；无服务影响的请求
  为 SEV5。应当在分诊时确定严重级别，按 `playbooks.md` 的呼叫矩阵呼叫，仅新证据方可变更，并记录
  变更及其时间。
- 每次轮值均须安排具名的主值班与备值班，公布排班与交接记录，并定义带超时的升级链；无人确认的呼叫应当自动
  升级。应当每月审查告警量与值班负载，因被噪声呼叫的轮值将不再查看呼叫。
- 每个 SEV1 与 SEV2 均须指定一名事故指挥官。该人员负责协调、决策与沟通，不承担调试工作；角色包括事故
  指挥官、运维负责人、沟通负责人与记录员。指挥官应当宣布严重级别、批准用户可见声明并关闭事故。
- 沟通应当按计划实施：首次更新须在该严重级别的策略目标内（SEV1 与 SEV2 常见默认为 15 分钟），此后每 30
  分钟一次，直至解决。内容应当说明影响、正在尝试的措施以及下次更新时间，不得作猜测；由沟通负责人起草，经
  指挥官批准后方可对用户发布。
- 应当先缓解后分析根因：以回滚、开关、扩容、故障转移或限流先行止住损害。在缓解破坏证据之前，应当保存证据：
  快照日志、捕获失败请求、记录时间；证据得以保留的，掩盖原因的缓解在修复原因期间可以接受。
- 每个 SEV1、SEV2、数据丢失与安全事故均须具备事故复盘。应当在五个工作日内完成并提交，覆盖影响、时间线、
  发现过程、促成原因、有效做法与行动项；模板由 `documentation-conventions` 管辖；要求、期限与审查会议由
  本流程管辖。
- 每个行动项均须带有负责人、截止日期、跟踪条目与验证步骤；并应当在每次发布与下次事故时审查未完成行动项。
  重复发生事故的行动项应当以更高优先级重开；未验证的行动项不视为完成。
- 应当执行无责策略：推定人员在其当时的信息、工具与时间条件下已作出合理行为。原因应当归于系统原因，不得
  归于个人；问责适用于行动项的落实与对时间线的如实报告，不得用于惩罚人为错误。故意违反策略仍属管理问题，
  但仍不构成技术根因。

| 好 | 坏 | 原因 |
|---|---|---|
| 分诊时按矩阵确定严重级别 | 修复后因难堪而抬高严重级别 | 呼叫与沟通级别事后漂移。 |
| 指挥官协调，工程师调试 | 调试的工程师同时负责沟通 | 两项工作均变慢，更新亦停止。 |
| 状态更新说明影响与下次更新时间 | 仅称“正在排查”而不给出时间 | 用户无法决定是否等待。 |
| 先回滚，缓解后再查根因 | 中断持续时先寻找根因 | 用户承担调查的代价。 |
| 行动项带负责人、日期与验证 | 事故复盘以“经验教训”收尾 | 一切照旧，事故重演。 |
| 事故复盘描述缺失的护栏 | 事故复盘点名部署的工程师 | 点名个人将掩盖系统原因。 |

事故角色如下；应当明确指定人员，不得推定团队自组织：

| 角色 | 负责 | 不负责 | 何时必须 |
|---|---|---|---|
| 事故指挥官 | 决策、严重级别、协调、关闭 | 调试系统或编写代码 | SEV1 与 SEV2 |
| 运维负责人 | 技术缓解与修复 | 用户沟通 | SEV1 与 SEV2 |
| 沟通负责人 | 状态页、内部频道与更新节奏 | 技术决策 | SEV1；SEV2 且用户受影响时 |
| 记录员 | 时间线、决策、行动项与证据引用 | 任何决策 | SEV1 与 SEV2 |
| 高管发起人 | 对外承诺与人员配置 | 运营选择 | SEV1 且存在对外承诺时 |

事故策略应当记录严重级别矩阵、呼叫目标、轮值与升级路径、更新节奏以及事故复盘期限。仅存在于聊天消息中的
严重级别表，将在下一次事故中被重新发现。

## 6. 备份与恢复

- 每个无法重建的数据存储均须备份，包括主数据库、对象存储以及丢失即改变状态的消息数据。不在版本控制中的
  配置与基础设施状态，以及解密与恢复数据所需的元数据，也应当纳入备份。派生数据在重建时间符合 RTO 时可以
  重建；该选择应当随 RTO 一并记录。
- 备份频率应当按 RPO 设定；并应当适用保留策略要求的保留期，覆盖恢复窗口、回滚窗口与合规义务。至少须保留
  一份不可变的异地副本，使删除、凭据失陷或区域故障无法毁掉全部副本。在下次演练之前即到期的保留期无法
  测试，因此不构成恢复计划。
- 应当按数据类别公布恢复点目标（恢复最多可丢失的最新数据）与恢复时间目标（恢复最长可耗时多久）；按数据
  类别表所列频率实施恢复演练（无论类别如何至少每年一次），并在每次变更备份范围后追加一次；恢复至隔离环境，
  对照目标测量实际耗时。应当记录结果、失败步骤与差距；仅恢复部分数据的演练，只测试了计划的一部分。
- 应当验证恢复，不得仅验证备份任务：比对校验和或行数，运行应用级冒烟查询，确认加密密钥对恢复目标可用，
  并检查恢复后的状态属于预期时间点。备份任务成功不构成恢复可用的证据；未经验证的备份仅为假设。
- 备份应当在静态与传输中均加密；密钥与数据应当分开存储；恢复权限应当仅授予具名角色；每次恢复均须记录。
  不得将生产数据复制至未加密的临时环境；密钥策略与访问审查由 `security-compliance-conventions` 管辖；本
  流程在演练中执行上述策略。
- 应当定义时间点恢复的窗口与粒度，测试恢复至错误写入之前与之后的时间戳，并记录 PITR 无法逆转的操作。
  PITR 窗口短于发现数据损坏所需时间的，即为无用；发现时间来自可观测性规则。
- 应当指定灾难恢复负责人、联系人树、故障转移标准、备用区域以及区域故障的数据丢失声明。该计划应当每年
  以及任何基础设施变更后演练；计划文档由 `documentation-conventions` 管辖；其内容、审查日期与演练由本流程
  管辖。
- 数据删除与备份保留的冲突应当以书面形式解决：删除或者传播至备份，或者由策略写明被删除记录在备份中最多
  存续多久。保留策略与法律义务由 `security-compliance-conventions` 管辖；删除机制由
  `api-and-data-conventions` 管辖；同时满足两者的备份计划与恢复路径由本流程管辖。恢复将覆盖线上数据，
  因此须取得销毁性变更的权限：先归档当前状态，并在开始前批准验证计划。

| 好 | 坏 | 原因 |
|---|---|---|
| 每季度实施带 RTO 实测的恢复演练 | 备份仪表盘全部正常却从不尝试恢复 | 任务全部正常无法证明数据可读、完整。 |
| 第二区域的不可变副本 | 同一账户、同一区域仅有一份副本 | 一次凭据失陷或区域故障将毁掉两者。 |
| 删除策略写明备份到期时间 | 已删除记录自六个月前的备份中重新出现 | 用户要求删除，却未得到执行。 |
| 恢复至生产属于销毁性变更 | 发现脚本者即实施恢复 | 当前数据可能在未获批准时被覆盖。 |
| 在错误写入前后测试 PITR | 已启用 PITR 却从未演练 | 窗口与粒度仅为假设。 |
| DR 计划每年演练且具备具名负责人 | 计划写一次即归档 | 联系人树与故障转移步骤已经过期。 |

按数据类别的恢复目标如下；没有目标的数据类别，其背后没有备份决策：

| 数据类别 | RPO | 备份方式 | 保留 | 恢复测试 |
|---|---|---|---|---|
| 事务型存储 | 分钟级 | 持续日志传送加每日全量 | 支持窗口加一个季度 | 每季度全量恢复 |
| 对象存储与用户文件 | 一小时 | 版本控制加跨区域复制 | 按策略的版本窗口 | 每季度抽样恢复 |
| 配置与基础设施状态 | 已版本化则为零 | 版本控制加状态快照 | 无限期历史 | 变更时恢复至临时环境 |
| 审查与合规记录 | 不接受丢失 | 只追加存储加导出 | 按合规策略 | 每年恢复检查 |
| 派生与分析数据 | 一天 | 自权威来源重建 | 重建窗口 | 重建而非恢复 |

恢复计划应当记录范围、按数据类别的 RPO 与 RTO、保留、密钥所有权、演练计划与结果、灾难恢复负责人，以及
删除策略在备份上的适用方式。无人演练过的计划，仅为一个有文件名的假设。
