# 发布与运维规范

发布与运维失效是项目代价最高的缺陷：一次不当部署会损害未曾接触该变更的用户；一次未被发现的事故会持续到
客户上报；一次未经验证的恢复会把可恢复的中断变成永久数据丢失。这些失效都是流程缺口，不是编码错误，用
明确的流程预防成本低廉，事后修复代价高昂。本 skill 规定版本与批准、变更公告与弃用、单一制品的构建与晋级、
发布成功的遥测证明、事故指挥，以及恢复可行性的证明，并把发布流程接入 G2、G5 与 G6 门禁。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 法律、法规、合同与平台的强制要求，以及宿主与全局用户约束。数据删除义务、许可证义务、已签署的支持
   窗口与托管平台的部署接口均非可选事项，应当记录于发布流程读取之处。
2. 本 skill 的规则与默认值。
3. 项目已写入文档的发布策略，以及实际运行的流水线、环境、运行手册与告警配置等事实。制定规则前先阅读
   版本来源、CI 配置、环境定义与最近两次事故记录；项目约定仅在本 skill 未规定或明确授权时补充，明确
   授权的收紧与例外按授权范围记录并执行。
4. 个人偏好、团队习惯与当前工具链的便利性，不得覆盖以上三级。

- 版本名与标签：发布标签、指标名、日志与事件字段名以及版本标识符的命名由 `naming-conventions` 管辖；
  标签的创建时点、指向与类型由本 skill 决定，发布标签默认使用附注标签，轻量标签仅用于本地临时标记；
  标签的不可变与保护由 `vcs-collaboration-conventions` 管辖。
- 发布文档：变更日志、发布说明、运行手册与事故复盘文档及其模板由 `documentation-conventions` 管辖；
  本 skill 管辖必须记录的内容，以及上述文档在发布与事故流程中的更新时点。
- 自变更至发布：分支、PR、审查与所有权由 `vcs-collaboration-conventions` 管辖；已审查变更如何形成发布，
  包括把关的批准与冻结，由本 skill 管辖。
- 门禁与阶段：门禁阈值与覆盖率策略由 `testing-and-quality-conventions` 管辖；流水线阶段、其必需顺序、
  环境晋级、制品与上线控制由本 skill 管辖。
- 产品版本与 API 版本：API 版本管理与 schema 安全由 `api-and-data-conventions` 管辖；产品版本、兼容性
  承诺与发布节奏由本 skill 管辖，交付某一 API 版本的发布同时遵循两者。
- 访问与权限：凭据、机密存储、披露、保留策略与合规由 `security-compliance-conventions` 管辖；部署权限
  与回滚决策权由本 skill 管辖，并消费安全流程签发的凭据。
- 仓库必需文件与分发：必需文件、元数据、manifest 与分发渠道由 `repository-governance-conventions` 管辖；
  版本策略、发布流程与审批、上线与回滚由本 skill 管辖。
- 由基础设施托管的设置不属于本 skill 的范围。平台执行的保留、复制、自动伸缩与备份调度归平台所有者管辖；
  应当引用平台合同，不得把取值抄入项目，并在运行手册中记录该边界。
- 发布默认不可逆。每项不可逆操作均须具备经过测试的回滚路径，或具备明确记录的已接受风险；无法回滚的
  提高批准级别并收窄上线范围。本 skill 的批准均为项目角色批准，不替代用户对部署、回滚与迁移的明确同意。
- 同一效力层级的强制规则冲突时报告用户裁决，不得自行选定；非强制的项目约定冲突，说明冲突与所选约定，
  记录于发布策略，并在下一次发布沿用同一选择。

## 生命周期定位

上游输入是 G4 验证结论（测试、安全与验收证据）与已批准的变更；本 skill 在 S2 固定发布与回滚计划，在 S5
执行发布与观察，在 S6 完成事故复盘、恢复验证与发布收尾。发布记录与运行手册交给运营与文档角色；回滚方案
缺失在 G2 Recycle，缺少 G4 证据的发布停在 G5，不得上线；发布后指标越界时按预案回滚并在 S6 复盘；授权、
披露或回滚冲突升级用户与安全负责人。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S2 计划 | 确定版本策略、发布类型、批准人、部署与回滚方案、观察指标与冻结窗口 | 发布计划、回滚方案、发布策略 |
| S5 发布 | 构建一次并晋级制品，执行受保护环境部署，观察成功指标与告警 | CI/CD 记录、制品摘要、回滚演练、观察快照 |
| S6 收尾 | 按严重级别复盘事故，跟踪行动项，证明备份可恢复，更新运行手册 | 事故复盘、行动项、恢复演练记录 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 计划 | 版本与兼容性结论、发布类型与批准人、回滚方案与数据影响、观察指标与阈值 | Recycle 至设计，补齐方案 |
| G5 发布 | 制品摘要与构建记录、必需门禁结果、回滚演练、可观测性就绪、逐次授权 | Hold，不得部署 |
| G6 收尾 | 收益与 SLO 对照、事故复盘与行动项、恢复演练结果、运行手册更新 | 补充证据后关闭 |

G2 证据不足时 Recycle 至设计；G5 证据缺失、回滚不可执行或授权未取得时 Hold；发布目标不成立、披露时间冲突
或方案不可回滚且风险不可接受时 No-Go。Conditional Go 的条件不得是“发布前补做验证”；回滚后重新发布须重新
取得 G5 证据。决定语义与批准角色见 `project-lifecycle-governance`。

## 工作流

1. 对变更与发布分类：写明制品、受影响用户、兼容性影响与发布类型；触及数据、凭据或 schema 的变更写明安全
   所有者与数据所有者。
2. 阅读当前状态：版本来源、流水线配置、环境定义、SLO、告警规则、运行手册与最近一次事故记录。无法读取
   流水线或环境设置的记录缺口，以仓库内配置为准并请求有权限者核对，不得猜测设置值。
3. 确定版本与兼容性承诺：适用版本递增规则，写明必须继续受支持的上一版本，为破坏性变更与弃用标注移除版本。
4. 汇集证据：确认必需门禁已通过、制品可复现、上线与回滚方案成文，且证明成功的遥测已经存在。
5. 在同一变更中更新记录：记录发布内容、批准、上线计划与回滚触发条件；更新因该变更过期的运行手册、仪表盘、
   告警与文档。
6. 演练未经验证的事项：以与生产同形的流量与数据经 staging 晋级；触及存储数据的实施恢复演练；发布不可逆
   的实际执行一遍回滚路径。
7. 发布、观察与收尾：部署已批准制品并在整个观察期监视成功指标；紧急情形按 AU-5 先止损并立即报告，其余
   回滚在取得明确同意后实施，并在下一次发布前记录结果与行动项。

## 核心规则

- **只构建一次，晋级制品。** 通过 staging 的字节即为到达生产的字节；按环境重新构建会重新引入未测试的
  差异，并使回滚目标模糊。
- **按影响定版本，不按活动量。** 补丁修复行为而不变更契约；次版本增加能力而不破坏契约；主版本变更契约；
  版本与内容不符时，所有读取该版本的依赖约束都会失效。
- **使每次发布可逆，或明确标注为单向。** 部署前定义回滚路径、数据影响与决策权限；既无回滚方案又无已接受
  风险的发布不予批准。
- **公布冻结窗口并强制执行。** 冻结写明日期、例外审批权限与仍允许的变更类别；未声明的冻结会由冻结期间
  失败的部署暴露出来。
- **自动化标准路径，为例外设置门禁。** 流水线对每次发布运行相同阶段；人工覆盖须有批准者、原因与偏离标准
  路径的书面记录。
- **公布兼容性承诺。** 写明哪些版本获得修复、弃用路径保留期限与升级所需操作；一次发布作出的承诺对之后
  每个发布构成约束。
- **在用户可见旧路径之处公告弃用。** 变更日志触达范围过小；应当发出运行时告警、更新展示旧路径的页面，
  并写明移除版本与日期。
- **将开关视为临时机制。** 每个开关须有所有者、默认值、移除触发条件与清理版本；存续超过一个发布的开关
  会变为未测试的分支与永久的第二条代码路径。
- **以支持决策的信号实施观察。** 写明证明发布成功的成功指标、错误率、延迟与业务信号，并定义将每一项转为
  回滚触发条件的阈值。
- **仅对需要行动的征兆告警。** 仅在人员能够处置且具备运行手册时呼叫值班人员；噪声告警会让轮值人员习惯
  忽略真正重要的告警。
- **每个事故按时钟运行。** 以分钟记录首次告警、确认、缓解与解决；缺乏时间线的事故复盘无法区分发现与响应。
- **记录每次严重事故并从中学习。** 严重级别决定响应方式、沟通节奏与是否复盘；行动项带负责人与日期，并在
  下一次发布时审查。
- **以恢复证明备份。** 未测试的备份仅为假设；按数据类别频率（至少每年一次）并在每次变更备份范围时实施
  恢复演练，记录实测的 RPO 与 RTO。
- **将环境一致性表述为风险。** staging 与生产在数据、规模与配置上存在差异；发布计划写明接受哪些差异以及
  每项差异的测试方式。
- **GitHub Release 是发布记录与制品的入口。** 使用附注标签与 Release，先建草稿、附上制品与验证证据，再
  发布；发布说明由 `.github/release.yml` 分类生成并人工补充破坏性变更、迁移步骤与已知问题，预发布标记为
  pre-release；标签、资产与发布说明指向同一提交与摘要。
- **发布作业在受保护环境中取得权限。** 生产部署作业声明 `environment:`，由必需审查者、等待计时器与允许的
  分支或标签控制，环境机密只在该作业可用；工作流以 `release: published` 或携带版本输入的
  `workflow_dispatch` 触发，用 `concurrency` 阻止重叠部署，云访问使用 OIDC 短期凭据。权限与回滚实现见
  `references/lifecycle.md`。
- **构建证明与物料清单随制品发布。** 发布作业为制品生成来源证明与 SBOM，将签名、校验和与证明附在 Release
  上；消费者以 `gh attestation verify` 与公布的摘要核对；不可变发布设置在可用处启用，其存在性由仓库治理
  skill 核查。
- **部署与回滚以提交和摘要关联。** 部署作业写入 Deployment 与环境 URL，观察期读取该环境的成功指标；回滚
  重新部署上一保留摘要，不移动标签或改写 Release；失败发布以新的补丁版本与前向修复处理。

## 发布模型矩阵

应当选择与变更影响相符的行，不得选择与请求紧急程度相符的行。本矩阵为默认值；项目发布策略可以收紧，不得
放宽回滚列或批准列；收紧与例外均须记录授权依据。同一变更匹配多行的，按批准与回滚要求更严的行执行；无法
匹配任何行的，按影响最接近的行执行并记录理由。“配置或开关变更”行仅适用于不改变用户可见行为的变更。

| 发布类型 | 版本号递增 | 批准 | 上线 | 回滚 | 沟通 |
|---|---|---|---|---|---|
| 主版本，破坏契约 | 主版本 | 发布所有者与各消费面所有者；数据或访问变更时加安全负责人 | 先金丝雀后全量，上线前公布迁移窗口 | 重新部署上一主版本并反向迁移，两者均经测试 | 发布说明，含升级步骤、弃用清单与支持窗口 |
| 次版本，向后兼容的功能 | 次版本 | 发布所有者与服务所有者 | 按部署策略选择，默认可滚动部署晋级后的制品 | 重新部署上一版本，无需反向数据 | 发布说明与变更日志，用户无需操作 |
| 补丁，向后兼容的修复 | 补丁 | 发布所有者 | 滚动部署 | 重新部署上一补丁 | 变更日志；仅用户可见修复写发布说明 |
| 预发布，alpha、beta 或候选版 | 预发布后缀 | 仅发布所有者 | 自愿加入渠道，不得作为默认受众 | 丢弃预发布版，不承诺回滚 | 公告，写明晋级标准 |
| 生产缺陷的热修复 | 补丁 | 值班负责人与发布所有者；缺陷可被利用时加安全负责人 | 最快的安全路径，触及数据时用金丝雀 | 重新部署上一版本，修复保留在其分支 | 先更新事故频道，随后发布说明 |
| 安全修复 | 补丁；破坏契约时用主版本 | 安全所有者与发布所有者，并与披露时间表协调 | 分阶段上线，披露日期待制品可用后确定 | 默认向前滚动；仅当上一构建不易受攻击时回滚 | 安全公告与发布说明，依披露时间线 |
| 回滚部署 | 无 | 值班权限；数据回滚须事故指挥官与数据所有者 | 立即作用于受影响范围 | 无需进一步回滚，随后以前向修复作为新发布 | 更新状态页与事故说明；前向修复写变更日志 |
| 配置或开关变更 | 无 | 服务所有者 | 分阶段按比例放量 | 翻转开关或恢复上一取值 | 发布记录备注；行为可见时面向用户 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 按环境重新构建制品 | 测试字节与交付字节不同，回滚目标不明 | 只构建一次，按摘要晋级，不为生产重建同一提交 |
| 冻结期内无例外记录即部署 | 冻结失去意义，例外无法审查 | 记录例外、审批权限、原因与回滚计划 |
| 仅称“需要即回滚”而未备命令 | 撤销方案须在事故中设计 | 部署前写好回滚步骤、数据影响与验证方式 |
| 打完标签后才决定版本递增 | 递增反映发布日期而非兼容性 | 合并前依变更分类确定递增 |
| 以提交日志拼合变更日志 | 用户找不到需要行动的变更 | 记录用户可见变更与所需行动 |
| 全量上线后保留开关 | 遗留两条代码路径，其中一条未测试 | 为每个开关设定移除版本，放量后删除 |
| 仅在变更日志公告弃用 | 用户升级时才见移除，规划窗口已关闭 | 在使用旧路径处公告，附日期与替代方案 |
| 将流水线凭据打印至日志 | 凭据暴露给所有可读日志者 | 不在日志、制品或输出中暴露凭据 |
| 对每个错误均告警 | 轮值人员忽略呼叫，错过重要告警 | 仅对附带运行手册且绑定 SLO 的征兆告警 |
| SLO 无负责人亦无审查 | 目标偏离用户体验而无人察觉 | 指定所有者、审查节奏与错误预算策略 |
| 事后确定严重级别 | 呼叫与沟通随响应者情绪漂移 | 分诊时依矩阵确定，仅新证据可变更 |
| 事故复盘未跟踪行动项 | 同一事故重演，文档只记录遗憾 | 提交带负责人与日期的行动项并复审 |
| 仅统计备份而不实施恢复 | 备份可能损坏、不完整或不可读取 | 演练恢复，测量 RPO 与 RTO 并记录 |
| 以个人凭据实施部署 | 部署无法关联角色，回滚权限不清 | 使用基于角色的部署身份并记录批准者与操作者 |
| 以仅配置的发布交付可见变更 | 行为变更绕过版本管理与发布说明 | 按用户影响分类并使用匹配的发布类型 |

## 审查清单

- [ ] 版本号递增与变更的兼容性影响相匹配，上一版本与支持窗口已写明。
- [ ] 发布类型、批准与上线方式与发布模型矩阵匹配；冻结窗口与例外权限已公布。
- [ ] 破坏性变更与弃用已写明移除版本、日期与迁移路径，并在用户可见处公告。
- [ ] 流水线仅构建一次，并将同一制品按摘要晋级至每个环境。
- [ ] 构建输入已固定，锁文件与工具链版本随制品记录，制品可从干净检出复现。
- [ ] 各阶段按失败成本自低至高运行，必需门禁在晋级前通过。
- [ ] 流水线消费安全流程管辖的凭据，未在日志、制品或输出中暴露。
- [ ] GitHub Release 的标签、资产与说明指向同一提交与摘要；预发布已标记且说明含迁移步骤。
- [ ] 生产作业使用受保护环境与 OIDC 短期凭据，环境机密未暴露给其他作业。
- [ ] 构建证明与 SBOM 已生成并可验证；回滚部署上一保留摘要，而非重建或移动标签。
- [ ] 回滚与已写入文档的步骤一致，并已在 staging 演练；每个不可逆步骤有回滚或已接受风险。
- [ ] 成功指标、阈值与观察期已在部署前写好，观察期内持续读取。
- [ ] 告警仅对可处置且关联 SLO 的征兆呼叫，每条告警附运行手册与所有者。
- [ ] 仪表盘按代码管理并写明所部署的服务；日志、指标与追踪携带关联 ID 并通过脱敏。
- [ ] 值班负责人、升级路径与事故指挥官角色保持最新。
- [ ] 备份范围、保留与加密与数据分类匹配；恢复演练达到频率并在保留窗口内通过。
- [ ] 发布说明、变更日志、运行手册与事故复盘的所有权与更新时机已记录。
- [ ] 每个开关具备所有者、默认值与移除版本，清理时已从清单移除。
- [ ] 严重事故均已按级别复盘，行动项带负责人与日期。
- [ ] staging 与生产的已知差异已写入发布计划并写明测试方式。
