# 发布与运维规范

发布与运维失效是项目代价最高的缺陷：一次不当部署会损害未曾接触该变更的用户；一次未被发现的事故会持续到客户上
报；一次未经验证的恢复会把可恢复的中断变成永久数据丢失。上述失效用明确的流程预防，成本低廉；事后修复，成本高
昂；而且它们都属于流程缺口，不是编码错误。本 skill 规定上述流程，包括版本的选择与发布批准、变更的公告与弃用、
同一制品的构建与晋级、发布成功的遥测证明、事故的指挥，以及恢复可行性的证明。本 skill 管辖发布流程、版本策略以及
遥测与恢复的设计，并把不属于自身管辖的每份制品交由管辖该制品的 skill 处理。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充：

1. 法律、法规、合同与平台的强制要求，以及宿主与全局用户约束。数据删除义务、许可证义务、已签署的支持窗口与
   托管平台的部署接口，均非可选事项；上述各项应当记录于发布流程读取之处。
2. 本 skill 的规则与默认值。
3. 项目已写入文档的发布策略，以及实际运行的流水线、环境、运行手册与告警配置等事实。制定规则前，应当先阅读
   版本来源、CI 配置、环境定义与最近两次事故记录；项目约定仅在本 skill 未规定或明确授权时补充，本 skill 明
   确授权的收紧与例外按授权范围记录并执行；上述事实作为输入，依本 skill 的规则处理，不得覆盖本 skill。
4. 个人偏好、团队习惯与当前工具链的便利性，不得覆盖以上三级。

- 版本名与标签。发布标签、指标名、日志与事件字段名以及版本标识符的命名，由 `naming-conventions` 管辖；标签
  的创建时点、指向与类型由本 skill 决定：发布标签默认使用附注标签，轻量标签仅用于本地临时标记；标签的不可变
  与保护由 `vcs-collaboration-conventions` 管辖；发布流程、版本策略与遥测设计，由本 skill 管辖。命名问题交由
  naming 处理，流程问题由本 skill 处理。
- 发布文档。变更日志、发布说明、运行手册、事故复盘文档及其模板，由 `documentation-conventions` 管辖；本 skill
  管辖必须记录的内容，以及上述文档在发布与事故流程中的更新时点。
- 自变更至发布。分支、PR、审查与所有权，由 `vcs-collaboration-conventions` 管辖；已审查变更如何形成发布，包
  括把关的批准与冻结，由本 skill 管辖。
- 门禁与阶段。门禁阈值与覆盖率策略，由 `testing-and-quality-conventions` 管辖；流水线阶段、其必需顺序、环境
  晋级、制品与上线控制，由本 skill 管辖。
- 产品版本与 API 版本。API 版本管理与 schema 安全，由 `api-and-data-conventions` 管辖；产品版本、兼容性承诺
  与发布节奏，由本 skill 管辖。交付某一 API 版本的发布，同时遵循两者。
- 访问与权限。凭据、机密存储、披露、保留策略与合规，由 `security-compliance-conventions` 管辖；部署权限与回
  滚决策权由本 skill 管辖，并消费安全流程签发的凭据。
- 仓库必需文件与分发。必需文件、元数据、manifest 与分发渠道，由 `repository-governance-conventions` 管辖；版
  本策略、发布流程与审批、上线与回滚，由本 skill 管辖。
- 由基础设施托管的设置不属于本 skill 的范围。托管平台执行的保留、复制、自动伸缩与备份调度，仍归平台所有者管
  辖；应当引用平台合同，不得将其取值抄入项目，并在服务运行手册中记录该边界。
- 发布默认不可逆。每项不可逆操作均须具备经过测试的回滚路径，或具备明确记录的已接受风险；无法回滚的，应当提
  高批准级别并收窄上线范围。本 skill 的批准均为项目角色批准，不替代宿主与全局用户约束要求的同意：代理实施部
  署、回滚、数据库迁移等操作前，仍须取得用户明确同意。
- 同一效力层级的强制规则冲突时，代理应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与所
  选约定，记录于发布策略，并在下一次发布沿用同一选择。
- **无部署仓库与单人维护。** 库、规范与 CLI 项目实际跳过下列项：`references/dimensions.md` 第 3 节的环境
  晋级段、第 5 节的值班轮值与呼叫、第 6 节的备份与恢复演练；`references/playbooks.md` 的“事故严重级别与
  呼叫矩阵”中的呼叫与轮值条款，以及“备份与恢复演练检查清单”。跳过项之外不得扩大豁免：版本号、一次构建、
  制品与回滚仍适用；严重级别分诊、事故指挥官、沟通与复盘仍适用；维度第 1 节的发布记录仍适用。单人维护时，
  批准人与执行人可以为同一人，但必须在发布记录中具名。

## 流程

1. 对变更与发布分类。应当写明制品、受影响的用户、兼容性影响，以及发布模型矩阵中的发布类型；触及数据、凭据
   或 schema 的变更，还应当写明其安全所有者与数据所有者。
2. 阅读当前状态。作出任何决定前，应当查阅版本来源、流水线配置、环境定义、SLO、告警规则、运行手册与最近一
   次事故记录；现有流程会约束应有的流程。无法读取流水线或环境设置的，记录缺口，以仓库内配置为准，并请求有权限
   者核对；不得猜测设置值。
3. 确定版本与兼容性承诺。应当适用版本号递增规则，写明必须继续受支持的上一版本，并为每项破坏性变更与弃用标
   注移除版本。
4. 汇集证据。首次部署前，应当确认必需门禁已通过、制品可复现、上线与回滚方案已成文，且能够证明成功的遥测已
   经存在。
5. 在同一变更中更新记录。应当记录发布内容、批准、上线计划与回滚触发条件；更新因该变更而过期的每份运行手册、
   仪表盘、告警与文档。
6. 演练未经验证的事项。应当以与生产同形的流量与数据经 staging 晋级；变更触及存储数据的，实施一次恢复演练；
   发布不可逆的，实际执行一遍回滚路径。
7. 发布、观察与收尾。应当部署已批准的制品，在整个观察期内监视成功指标；触及 AU-5 列明的四类紧急情形的，依
   AU-5 先实施最小止损并立即报告；其余回滚在取得 AU-1/AU-2 明确同意后实施，并在下一次发布前记录结果与行动
   项。

## 核心规则

- **只构建一次，晋级制品。** 通过 staging 的字节即为到达生产的字节；按环境重新构建会重新引入未测试的差异，
  并使回滚目标模糊。
- **按影响定版本，不按活动量。** 补丁修复行为而不变更契约；次版本增加能力而不破坏契约；主版本变更契约。版本与
  内容不符时，所有读取该版本的依赖约束都会失效。
- **使每次发布可逆，或明确标注为单向。** 部署前应当定义回滚路径、其数据影响与决策权限；既无回滚方案又无已接
  受风险的发布，不予批准。
- **公布冻结窗口并强制执行。** 冻结应当写明日期、例外审批权限与仍允许的变更类别；未声明的冻结，会由冻结期间
  失败的部署暴露出来。
- **自动化标准路径，为例外设置门禁。** 流水线对每次发布运行相同的阶段；人工覆盖应当具备批准者、原因，以及对
  偏离标准路径的书面记录。
- **公布兼容性承诺。** 应当写明哪些版本获得修复、弃用路径保留期限，以及升级所需操作；在某一发布中作出的承
  诺，对之后每个发布均构成约束。
- **在用户可见旧路径之处公告弃用。** 变更日志条目的触达范围过小；应当发出运行时告警、更新展示旧路径的页面，
  并写明移除版本与日期。
- **将开关视为临时机制。** 每个开关均须具备所有者、默认值、移除触发条件与清理版本；存续时间超过发布的开关，
  将变为未测试的分支与永久的第二条代码路径。
- **以支持决策的信号实施观察。** 应当写明能够证明发布成功的成功指标、错误率、延迟与业务信号，并定义将每一项
  转为回滚触发条件的阈值。
- **仅对需要行动的征兆告警。** 仅在人员能够处置且具备运行手册时呼叫值班人员；噪声告警将使轮值人员习惯于忽略
  真正重要的告警。
- **每个事故均按时钟运行。** 应当以分钟记录首次告警、确认、缓解与解决；缺乏时间线的事故复盘无法区分发现与响
  应。
- **记录每次严重事故并从中学习。** 严重级别决定响应方式、沟通节奏以及是否需要进行事故复盘；行动项应当带有负
  责人与日期，并在下一次发布时审查。
- **以恢复证明备份。** 未测试的备份仅为假设；应当按数据类别表的频率（至少每年一次）并在每次变更备份范围时实
  施恢复演练，记录实测的 RPO 与 RTO。
- **将环境一致性表述为风险。** staging 与生产在数据、规模与配置上存在差异；发布计划应当写明接受哪些差异以及
  每项差异的测试方式。

## 发布模型矩阵

应当选择与变更影响相符的行，不得选择与请求紧急程度相符的行。本矩阵为默认值；依本 skill 的层级授权，项目发布
策略可以收紧本矩阵，不得放宽回滚列或批准列；收紧与例外均须记录其授权依据。

同一变更匹配多行的，按批准与回滚要求更严的行执行；无法匹配任何行的发布类型，按影响最接近的行执行并记录理由。
“配置或开关变更”行仅适用于不改变用户可见行为的变更。

| 发布类型 | 版本号递增 | 批准 | 上线 | 回滚 | 沟通 |
|---|---|---|---|---|---|
| 主版本，破坏契约 | 主版本 | 发布所有者及各消费面所有者；数据或访问变更时增加安全负责人 | 先金丝雀后全量，上线前公布迁移窗口 | 重新部署上一主版本并反向迁移，两者均已经过测试 | 发布说明，含升级步骤、弃用清单与支持窗口 |
| 次版本，向后兼容的功能 | 次版本 | 发布所有者及服务所有者 | 按维度第 3 节的部署策略选择，默认可滚动部署晋级后的制品 | 重新部署上一版本；无需反向数据 | 发布说明与变更日志条目；用户无需操作 |
| 补丁，向后兼容的修复 | 补丁 | 发布所有者 | 滚动部署 | 重新部署上一补丁 | 变更日志条目；仅当修复对用户可见时写发布说明 |
| 预发布，alpha、beta 或候选发布版 | 预发布后缀 | 仅发布所有者 | 自愿加入的渠道，不得作为默认受众 | 丢弃预发布版；不承诺回滚 | 公告，写明晋级标准 |
| 生产缺陷的热修复 | 补丁 | 值班负责人与发布所有者；缺陷可被利用时增加安全负责人 | 最快的安全路径，缺陷触及数据时使用金丝雀 | 重新部署上一版本；修复保留在其分支上供重试 | 先更新事故频道，随后发布说明；严重的补充事故复盘 |
| 安全修复 | 补丁；修复破坏契约时使用主版本 | 安全所有者与发布所有者，并与披露时间表协调 | 分阶段上线，披露日期待修复制品可用后确定 | 默认向前滚动；仅当上一构建不属于易受攻击版本时回滚 | 安全公告与发布说明，依披露时间线发送 |
| 回滚部署 | 无 | 值班权限（不涉及数据逆转或恢复），决定后记录；数据回滚须事故指挥官与数据所有者 | 立即作用于受影响范围 | 无需进一步回滚；上一制品已上线，随后以前向修复作为新发布 | 更新状态页与事故说明；仅前向修复需写变更日志 |
| 配置或开关变更 | 无 | 服务所有者 | 分阶段按比例放量 | 翻转开关或恢复上一取值 | 在发布记录中备注；仅当行为可见时面向用户 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 按环境重新构建制品 | 测试过的字节与交付的字节不同，回滚目标亦不明确 | 只构建一次，按摘要晋级，不得为生产重新构建同一提交 |
| 于冻结期内无例外记录即部署 | 冻结失去意义，例外亦无法审查 | 记录例外、其审批权限、原因与回滚计划 |
| 仅称“需要即回滚”而未备命令 | 撤销方案须在事故中设计，而事故为最不利时机 | 部署前写好回滚步骤、数据影响与验证方式 |
| 打完标签后方决定版本号递增 | 递增反映发布日期，而非兼容性变化 | 合并前依变更分类确定递增 |
| 以提交日志拼合变更日志 | 用户无法找到需要自行行动的那项变更 | 记录用户可见变更与所需行动；提交日志不构成变更记录 |
| 全量上线后继续保留开关 | 遗留两条代码路径，其中一条未测试且无人维护 | 为每个开关设定移除版本，放量完成后删除 |
| 仅在变更日志内公告弃用 | 用户至升级时方见移除，此时规划窗口已经关闭 | 在使用旧路径之处公告，并附日期与替代方案 |
| 将流水线凭据打印至日志 | 经流水线暴露的凭据，即暴露给所有可读取日志的人员 | 不得在流水线日志、制品或输出中暴露凭据；凭据来源归安全角色管辖 |
| 对每个错误均告警 | 轮值人员将忽略呼叫，错过真正重要的一次 | 仅对附带运行手册且阈值绑定 SLO 的征兆告警 |
| SLO 无负责人亦无审查 | 目标偏离用户体验，而无人察觉 | 指定所有者、审查节奏与错误预算策略 |
| 事后方确定严重级别 | 呼叫与沟通随响应者的主观情绪漂移 | 在分诊时依矩阵确定严重级别，仅新证据方可变更 |
| 事故复盘未跟踪行动项 | 同一事故重演，而文档仅记录遗憾 | 提交带负责人与日期的行动项，并在下一次发布时审查 |
| 仅统计备份而不实施恢复 | 备份可能损坏、不完整或不可读取 | 实施恢复演练，测量 RPO 与 RTO，并记录结果 |
| 以个人凭据实施部署 | 部署无法关联至角色，回滚权限亦不清晰 | 使用基于角色的部署身份，并记录批准者与操作者 |
| 以仅配置的发布交付可见变更 | 行为变更绕过了版本管理、兼容性审查与发布说明 | 按用户影响对变更分类，并使用匹配的发布类型 |

## 审查清单

- [ ] 版本号递增与变更的兼容性影响相匹配。
- [ ] 发布类型、批准与上线方式与发布模型矩阵相匹配。
- [ ] 已写明上一版本及其支持窗口。
- [ ] 破坏性变更与弃用已写明移除版本、日期与迁移路径。
- [ ] 流水线仅构建一次，并将同一制品晋级至每个环境。
- [ ] 构建输入已固定，制品可从干净检出复现。
- [ ] 各阶段按失败成本自低至高运行，必需门禁在晋级前通过。
- [ ] 流水线消费安全流程管辖的凭据，不得在日志或制品中暴露。
- [ ] 回滚与已写入文档的步骤一致，并已在 staging 演练。
- [ ] 每个不可逆步骤均有经过测试的回滚，或有记录的已接受风险。
- [ ] 成功指标、阈值与观察期已在部署前写好。
- [ ] 告警仅对可处置且关联 SLO 的征兆呼叫，且每条告警均附运行手册。
- [ ] 仪表盘按代码方式版本管理，并写明所部署的服务。
- [ ] 日志、指标与追踪均携带关联 ID，并通过脱敏规则。
- [ ] 值班负责人、升级路径与事故指挥官角色保持最新。
- [ ] 备份范围、保留与加密与数据分类相匹配。
- [ ] 恢复演练按数据类别表的频率实施（至少每年一次），在保留窗口内通过，且已测量 RPO 与 RTO。
- [ ] 发布说明、变更日志、运行手册与事故复盘的所有权与更新时机均已记录。
- [ ] 每个开关均具备所有者、默认值与移除版本；清理时已从开关清单移除。
- [ ] 严重事故均已按严重级别复盘，行动项带负责人与日期。
- [ ] staging 与生产的已知差异已写入发布计划，并写明每项差异的测试方式。
- [ ] 发布期间的冻结窗口与例外审批权限已公布。

## 示例

<example>
以次版本交付结账变更：制品只构建一次；该服务的发布策略选择金丝雀（矩阵默认为滚动），因此将 staging 的摘要经
5% 金丝雀晋级；对照上一小时观察 `checkout_success_ratio` 与错误率；观察期结束前保持不全量。触及已写明阈值的，
应当中止，而非在频道内争论。
</example>

<example>
处于 0.x 的库为公共函数增加必填参数。依本项目的 1.0 之前策略，次版本可以承载该破坏性变更，但不得静默实施：
升级至 `0.8.0`，以弃用告警使旧签名继续可用；在 `0.9.0` 公告将在下一个次版本移除，并在该移除版本中删除旧路
径。
</example>

<example>
某一开关控制新的税额计算。创建时默认关闭，并带有所有者与移除版本；按租户组分批放量；在某一发布中保持 100%；
然后在下一个次版本中删除旧路径与开关，并从开关清单中移除该行。
</example>

<example>
结账错误率于 02:10 越过 SLO 燃烧阈值。值班人员在四分钟内确认，判定为 SEV-2，指定事故指挥官，并每 30 分钟发
布一次更新；以回滚至上一制品实施缓解，随后前向修复，最后在五个工作日内完成并提交事故复盘，每个行动项均带负责
人。
</example>

<example>
一次迁移新增一张表。发布前将最新备份恢复至临时实例，运行迁移，比对行数与校验和，并记录恢复耗时 40 分钟、对
照一小时的 RTO；演练通过前发布保持等待，因为恢复属于发布标准，而非独立项目。
</example>
