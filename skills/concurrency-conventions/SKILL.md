# 并发与并行规范

并发程序以四种可预见的方式失效：共享可变状态在没有同步的情况下被并发读写，产生时有时无的数据竞争；锁的顺序
不一致让两个执行流互相等待，卡成死锁；无界地复制数据而不是共享，把锁竞争藏成性能问题；测试只证明"这次没崩"，
因为竞态是概率性的。每种失效都难以复现、难以在代码审查中发现，却容易在负载升高或重构之后突然暴露。本 skill 给
出从"能否不共享"开始的单一决策流程、按场景选择同步原语的规则、死锁与活锁的排查方法，以及让并发缺陷在测试阶段
而非生产阶段暴露的手段。它服务于引入或修改共享状态的工程师、评判并发 diff 的审查者，以及排查死锁与竞态的值班者。

## 适用范围与优先级

采用第一条适用的规则，同一范围内不要混用标准：

1. 平台、语言运行时与硬件的强制约束。内存模型、语言提供的同步原语、运行时的调度器以及 CPU 的缓存一致性，都不是
   可选项。
2. 既有项目的并发模型与约定。在发明规则之前，先读项目的并发文档、已有的锁、通道与线程池，以及既有的同步工具类。
3. 本规范的默认值，在前两层未作规定时适用。
4. 个人偏好，永远不能覆盖以上三层。

- **锁竞争的性能诊断与优化归 `performance-conventions`。** 本 skill 管并发正确性：数据竞争、可见性、死锁与活锁；
  吞吐与延迟的瓶颈定位、基准与优化手法归性能 skill，两处不互相移交同一主题。
- **通用测试策略归 `testing-and-quality-conventions`。** 本 skill 管并发正确性特有的验证：竞态检测器、压力测试与确定性
  的难处；测试层级、门禁与 CI 归测试 skill。
- **API 幂等与重试归 `api-and-data-conventions`。** 本 skill 管进程内共享与同步，不重述跨服务重试、幂等键与退避。
- **名称归 `naming-conventions`。** 锁、通道、协程、任务等标识符的命名由它裁定；本 skill 不另造词汇。
- **代码注释归 `comment-conventions`。** 本 skill 管"锁与不变式必须写在哪里"，注释的写法由它裁定。
- **共享可变状态是唯一的审查对象。** 不共享的数据、只被单个执行流访问的数据，以及不可变数据，不适用本 skill 的同步
  规则；但"为什么它能不共享"仍要写清。
- **两条规则冲突时，说明冲突与所选规则。** 把决定记录在项目的并发策略或 ADR 中，让后续变更遵循它。

## 流程

1. 先区分并发与并行，并找出共享可变状态。并发是同时处理多件事的结构，并行是同时做多件事的执行；单核也能并发，
   多核才并行。列出所有被多个执行流读写的变量、字段与容器；只读共享不需要锁，只在单个执行流内可变的不需要锁。
2. 尽量消除共享。能不可变就不共享：把可变状态变成不可变值，或用消息传递（通道/队列）让数据只有一个所有者。
   写不出"为什么不能不可变或不能传递"的理由时，先改写，再加锁。
3. 必须共享时选同步原语。按"保护什么、读写比例、等待还是轮询"选互斥锁、读写锁、信号量、条件变量或原子操作，
   见 `references/checklist.md` 的原语决策表。加锁要覆盖读写两侧，锁住整个不变量而非单个字段。
4. 控制锁粒度与顺序。锁的持有区间要小，持锁期间不回调、不做 I/O、不申请别的锁；需要多把锁时，按全局一致的顺序
   申请，或用超时与 try-lock 打破死锁。
5. 验证。跑竞态检测器与压力测试，见 `references/dimensions.md` 第 5 节；发现死锁时先画资源等待图，见
   `references/checklist.md` 的死锁诊断工作表。
6. 记录不变式。把每把锁保护的数据、不变式与申请顺序写进代码与并发文档，让下一位审查者无需重做分析。

## 核心规则

- **共享可变状态必须有显式同步，能不可变就不共享。** 被多个执行流并发读写、且至少一个写，却没有同步的变量就是数据
  竞争。同步必须覆盖读与写两侧；原子性只保护单个操作，多个字段组成的不变量要由锁整体保护。
- **锁住不变量，不是锁住字段。** 一把锁保护一组必须同时成立的字段；任何读或写其中一部分的路径都要持同一把锁。
  只锁住其中一两个字段的路径，就是破坏不变量的竞争。
- **锁的持有区间要小，持锁期间不回调、不 I/O、不申请别的锁。** 把回调、日志、网络与磁盘操作移出临界区；持锁调用
  外部代码会把锁的顺序和生命周期交给别人，是死锁与长等待的主要来源。
- **多把锁按全局一致的顺序申请，拿不到就释放并重试或超时。** 任何两个执行流以相反顺序申请同一组锁，都可能死锁；
  无法统一顺序时，用 try-lock 加超时打破循环，而不是无限等待。
- **能原子操作就不用锁；原子操作不保护多个字段。** 单个标量的读改写用原子类型；一旦涉及两个以上字段或先读后写
  的复合判断，就回到锁。
- **不可变优先，消息传递减少共享。** 尽量返回不可变值、冻结可变对象；数据只被一个所有者拥有，经通道/队列传递，
  而不是多所有者共享同一份内存。
- **有运行期竞态检测器的语言，跑并发测试时必须开检测器。** Go 用 `-race`，C/C++ 用 ThreadSanitizer，Rust 用
  `loom` 或 Miri；检测器没跑过，就不能声称无数据竞争。没有运行期检测器的语言（如 Java、Python）用压力测试、
  静态工具与审查替代，并记录覆盖缺口。检测器只覆盖执行过的路径，不覆盖没跑到的交错。
- **死锁排查先画资源等待图。** 把每个执行流、它持有的锁与等待的锁画成图，找环；环就是死锁，破环的办法是统一顺序、
  引入超时或减少锁的数量。详见 `references/checklist.md`。
- **不把测试通过当作并发正确的证明。** 竞态是概率性的，一次绿色说明不了什么；用压力测试提高交错覆盖率，并说明
  覆盖不到的交错。详见 `references/dimensions.md` 第 5 节。
- **并发不是并行的同义词，也不要为了用并发而并发。** 先有可判定的收益（响应性、吞吐或资源利用）再引入并发；
  无收益的并发只增加复杂度与缺陷面。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 无同步地读写共享字段 | 数据竞争，结果是内存模型允许的任意值，且只在特定交错下复现。 | 加锁或用原子类型；或改成不可变/单所有者。 |
| 只锁写不锁读 | 读到一个写了一半的中间状态。 | 读与写持同一把锁。 |
| 用一把大锁包住整个请求 | 串行化消灭并发，锁竞争成为新瓶颈。 | 缩小临界区，只锁不变量。 |
| 持锁调用回调或 I/O | 锁的顺序交给外部代码，可能反向申请造成死锁。 | 把回调与 I/O 移出临界区。 |
| 两处代码按相反顺序加锁 | 两个执行流互相等待，死锁。 | 统一全局锁顺序，或用 try-lock 加超时。 |
| 无超时地等待锁或条件变量 | 一次等待卡住整个执行流，死锁或活锁无从恢复。 | 原语支持超时就用超时，超时后释放并重试或上报；不支持时用可取消等待、看门狗或带超时的 select/channel，并记录例外。 |
| 忙等自旋替代条件变量 | 空转烧 CPU，且可能活锁。 | 用条件变量/信号量等待，或退避。 |
| 在事件循环里做阻塞 I/O | 阻塞整个事件循环，其它任务全部卡住。 | 交给线程池或异步 API。 |
| 并发测试只跑一次且不开检测器 | 概率性竞态漏网，绿色不证明正确。 | 开检测器加压力测试。 |
| 把 `-race` 跑绿当作充分证明 | 检测器只覆盖执行到的交错。 | 说明未覆盖的交错，用压力测试与模型检查。 |

## 审查清单

- [ ] 列出全部共享可变状态；只读共享与单执行流状态已注明不需要同步。
- [ ] 每条共享可变状态都有同步，且读与写两侧都被覆盖。
- [ ] 每把锁保护一个写清的不变量；不存在只锁部分字段的路径。
- [ ] 临界区只含必要操作，持锁期间无回调、I/O 或锁嵌套。
- [ ] 多把锁按全局一致的顺序申请，或用 try-lock 加超时打破循环。
- [ ] 单个标量用原子操作，多字段复合判断用锁而非原子。
- [ ] 能不可变或消息传递的地方没有退化为多所有者共享。
- [ ] 事件循环内无阻塞调用；阻塞工作已交给线程池或异步 API。
- [ ] 有运行期检测器的语言跑了检测器，并记录覆盖到的交错；其余语言记录了压力测试、静态工具与审查的替代验证及覆盖缺口。
- [ ] 死锁已通过资源等待图排查；等待在支持超时的原语上都带超时，不支持时使用了可取消等待、看门狗或带超时的 select/channel，并记录例外。
- [ ] 并发变更是有收益的：响应性、吞吐或资源利用有可判定目标。
- [ ] 每把锁的数据、不变式与申请顺序都写进了代码与并发文档。

## 示例

<example>
一个计数器被多个 goroutine 并发自增：`count++` 是读改写，无同步就会数据竞争。单个标量改成 `atomic.AddInt64`；
如果计数器还要与另一个字段一起组成"计数加总计"的不变量，就回到同一把互斥锁保护两个字段，而不是各用各的原子。
</example>

<example>
服务里两段代码分别持有锁 A 再申请锁 B、持有锁 B 再申请锁 A。把它们统一为"总是先 A 后 B"；无法统一时，第二把锁
用 try-lock 加超时，拿不到就释放已有锁并重试，避免两个执行流互相卡死。
</example>

<example>
一个异步 Web 处理器在事件循环里调用同步阻塞的数据库驱动，导致其它请求全部卡住。改成异步驱动，或把该调用交给
线程池执行器，并确保回调里不持有锁。
</example>

<example>
一个并发测试只 `go test` 不带 `-race` 且只跑一遍。改到 CI 里跑 `go test -race`，并对同一路径做压力测试提高交错
覆盖；仍然要说明：检测器只证明执行过的交错无竞争，不是全部交错。
</example>
