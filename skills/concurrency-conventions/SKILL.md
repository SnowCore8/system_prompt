# 并发与并行规范

并发程序有四类可预见的失效：共享可变状态未经同步就被并发读写，产生时有时无的数据竞争；锁的申请顺序不一致，两个执行流互相等待，形成死锁；用无界复制代替共享，把锁竞争掩盖成性能问题；测试只证明“本次未崩溃”，而竞态具有概率性。
这些失效都难以复现，也难以在代码审查中发现，却容易在负载升高或重构之后显现。
本 skill 规定一条以“是否可以不共享”为起点的决策流程、按场景选择同步原语的规则、死锁与活锁的排查方法，以及让并发缺陷在测试阶段而非生产阶段暴露的手段。
读者是引入或修改共享状态的工程师、评判并发 diff 的审查者，以及排查死锁与竞态的值班者。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。
   内存模型、语言提供的同步原语、运行时的调度器以及 CPU 的缓存一致性，都不是可选项。
2. 本 skill 的规则。
   共享状态、同步原语、死锁与并发模型、并发测试的规则，以本文件与 `references/` 为准。
3. 既有项目约定与事实。
   智能体应当先阅读项目的并发文档、既有的锁、通道与线程池，以及既有的同步工具类；这些是事实输入，按本 skill 的规则处理。
   项目约定只在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- **锁竞争的性能诊断与优化由 `performance-conventions` 管辖。** 本 skill 管辖并发正确性，包括数据竞争、可见性、死锁与活锁；吞吐与延迟的瓶颈定位、基准与优化手法归性能 skill 管辖。两处不得就同一主题相互移交。
- **通用测试策略由 `testing-and-quality-conventions` 管辖。** 本 skill 管辖并发正确性特有的验证，包括竞态检测器、压力测试与确定性的难处；测试层级、门禁与 CI 归测试 skill 管辖。
- **API 幂等与重试由 `api-and-data-conventions` 管辖。** 本 skill 管辖进程内共享与同步，不重复规定跨服务重试、幂等键与退避。
- **名称由 `naming-conventions` 管辖。** 锁、通道、协程、任务等标识符的命名，由该 skill 裁定；本 skill 不另行创制词汇。
- **代码注释由 `comment-conventions` 管辖。** 本 skill 规定锁与不变式的书写位置；注释的写法由该 skill 裁定。
- **共享可变状态是唯一的审查对象。** 不共享的数据、仅由单个执行流访问的数据以及不可变数据，不适用本 skill 的同步规则；但其为何可以不共享，仍应当写明。
- **同一效力层级的强制规则冲突的，智能体应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与所选约定；跨层冲突依全局用户约束 §3.3 处理。**
  所选约定应当记录于项目的并发策略或 ADR 中，使后续变更遵循该决定。
- 生命周期：并发正确性主责 S3 构建（G3）与 S4 验证（G4），竞态证据随验证提交；阶段门禁与证据见 `project-lifecycle-governance`。

## 流程

1. 区分并发与并行，并确定共享可变状态。
   并发指同时处理多项事务的结构，并行指同时实施多项事务的执行；单核可以实现并发，多核方可实现并行。
   智能体应当列出所有被多个执行流读写的变量、字段与容器；只读共享无需加锁，仅在单个执行流内可变的，无需加锁。
2. 应当尽可能消除共享。
   可变状态默认不共享；可以改为不可变值的，应当改为不可变值（不可变值可安全共享）；否则以消息传递（通道/队列）使数据仅有一个所有者，或加锁共享。
3. 必须共享的，应当选择同步原语。
   依“保护对象、读写比例、等待还是轮询”，选择互斥锁、读写锁、信号量、条件变量或原子操作，见 `references/checklist.md` 的原语决策表。
   加锁应当覆盖读与写两侧，锁住整个不变量，而非单个字段。
4. 控制锁的粒度与顺序。
   锁的持有区间应当较小；持锁期间不得回调、不得实施 I/O、不得申请顺序未知的锁。
   需要多把锁的，应当按全局偏序申请，自第二把起采用 try-lock 加超时，并记录锁数与超时。
5. 验证。
   存在运行期竞态检测器的语言，应当运行检测器与压力测试；未提供的，应当以压力测试、静态工具与审查替代并记录覆盖缺口，见 `references/dimensions.md` 第 5 节；发现死锁的，应当先绘制资源等待图，见 `references/checklist.md` 的死锁诊断工作表。
6. 记录不变式。
   智能体应当把每把锁所保护的数据、不变式与申请顺序写入代码与并发文档，使后续审查者无需重复分析。

## 核心规则

- **可变状态默认不共享；确需共享的，必须具有显式同步。可以改为不可变值的，应当改为不可变值（不可变值可安全共享）；否则以消息传递或加锁。** 被多个执行流并发读写，且至少存在一个写入，却未经同步的变量，即为数据竞争。
  同步必须覆盖读与写两侧；原子性仅保护单个操作，多个字段组成的不变量，应当由锁整体保护。
- **锁定的对象为不变量，而非字段。** 一把锁保护一组必须同时成立的字段；任何读取或写入其中一部分的路径，均应当持有同一把锁。仅锁定其中一两个字段的路径，属于破坏不变量的竞争。
- **锁的持有区间应当较小；持锁期间不得回调、不得实施 I/O、不得申请顺序未知的锁。** 回调、日志、网络与磁盘操作，应当移出临界区；持锁调用外部代码，会使锁的顺序与生命周期由外部代码决定，成为死锁与长时间等待的主要来源。
- **多把锁应当按全局偏序申请；自第二把起采用 try-lock 加超时，并记录锁数与超时。** 任何两个执行流以相反顺序申请同一组锁，都可能形成死锁；无法取得的，应当释放并重试，或者等待超时，不得无限等待。
- **可以采用原子操作的，不使用锁；原子操作不保护多个字段。** 单个标量的读改写，应当采用原子类型；涉及两个以上字段，或先读后写的复合判断的，应当改用锁。
- **不可变优先；以消息传递减少共享。** 智能体应当尽可能返回不可变值、冻结可变对象；数据应当仅由一个所有者拥有，并经通道/队列传递，不得由多个所有者共享同一份内存。
- **语言提供运行期竞态检测器的，运行并发测试时必须启用检测器。** Go 使用 `-race`，C/C++ 使用 ThreadSanitizer 等；Rust 的 Miri 属受限解释器检测，Loom 属模型检查（对关键协议改写测试）。
  二者不可用或无法覆盖全部测试的，应当记录覆盖缺口，不强制全量。未提供运行期检测器的语言（例如 Java、Python），应当以压力测试、静态工具与审查替代，并记录覆盖缺口。
  检测器仅覆盖已执行的路径，不覆盖未执行的交错。
- **死锁排查应当先绘制资源等待图。** 智能体应当把每个执行流、其持有的锁与等待的锁绘制为图，并查找环；存在环即为死锁。破环方法为统一顺序、引入超时或减少锁的数量。详见 `references/checklist.md`。
- **不得以测试通过作为并发正确的证明。** 竞态具有概率性，一次通过不构成证明；智能体应当以压力测试提高交错覆盖率，并说明未能覆盖的交错。详见 `references/dimensions.md` 第 5 节。
- **并发并非并行的同义词；不得为使用并发而引入并发。** 引入并发前，应当先确定可判定的收益（响应性、吞吐或资源利用）；无收益的并发仅增加复杂度与缺陷面。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 未经同步即读写共享字段 | 构成数据竞争；结果为内存模型允许的任意值，且仅在特定交错下复现。 | 加锁或采用原子类型；或者改为不可变/单一所有者。 |
| 仅锁定写侧，未锁定读侧 | 读取到写入一半的中间状态。 | 读与写应当持有同一把锁。 |
| 以单一大锁覆盖整个请求 | 串行化消除并发，锁竞争成为新的瓶颈。 | 缩小临界区，仅锁定不变量。 |
| 持锁调用回调或实施 I/O | 锁的顺序交由外部代码决定，可能因反向申请形成死锁。 | 将回调与 I/O 移出临界区。 |
| 两处代码以相反顺序加锁 | 两个执行流互相等待，形成死锁。 | 按全局偏序申请；自第二把锁起采用 try-lock 加超时，并记录锁数与超时。 |
| 无超时地等待锁或条件变量 | 一次等待将阻塞整个执行流，死锁或活锁无从恢复。 | 必须设定超时；超时后释放并重试或上报。原语不支持超时的，应当采用可取消等待、看门狗或带超时的 select/channel，并记录替代方案与例外。 |
| 以忙等自旋替代条件变量 | 空转消耗 CPU，且可能形成活锁。 | 采用条件变量/信号量等待，或者退避。 |
| 在事件循环内实施阻塞 I/O | 阻塞整个事件循环，其他任务全部停滞。 | 交由线程池或异步 API 处理。 |
| 并发测试仅运行一次，且未启用检测器 | 概率性竞态未被检出；通过结果不构成正确性证明。 | 启用检测器并施加压力测试。 |
| 以 `-race` 通过作为充分证明 | 检测器仅覆盖已执行的交错。 | 说明未覆盖的交错，并采用压力测试与模型检查。 |

## 审查清单

- [ ] 已列出全部共享可变状态；只读共享与单执行流状态已注明无需同步。
- [ ] 每项共享可变状态均具有同步，且读与写两侧均被覆盖。
- [ ] 每把锁保护一项已写明的不变量；不存在仅锁定部分字段的路径。
- [ ] 临界区仅包含必要操作；持锁期间无回调、无 I/O、无无序锁嵌套。
- [ ] 多把锁按全局偏序申请，自第二把起采用 try-lock 加超时，并记录锁数与超时。
- [ ] 单个标量采用原子操作；多字段复合判断采用锁，不采用原子操作。
- [ ] 可以实现不可变或消息传递的，未退化为多所有者共享。
- [ ] 事件循环内无阻塞调用；阻塞工作已交由线程池或异步 API 处理。
- [ ] 提供运行期检测器的语言已运行检测器，并记录检测器命令、测试路径、执行范围与未覆盖缺口；其余语言已记录替代验证及覆盖缺口。
- [ ] 死锁已通过资源等待图排查；所有等待均设定超时，原语不支持超时的已采用可取消等待、看门狗或带超时的 select/channel，并记录替代方案。
- [ ] 并发变更具有收益：响应性、吞吐或资源利用存在可判定目标。
- [ ] 每把锁的数据、不变式与申请顺序均已写入代码与并发文档。

## 示例

<example>
多个 goroutine 并发递增同一计数器：`count++` 属于读改写，未经同步即构成数据竞争。
单个标量应当改用 `atomic.AddInt64`；计数器还需与另一字段共同构成“计数加总计”不变量的，应当改用同一把互斥锁保护两个字段，不得分别采用各自的原子操作。
</example>

<example>
服务中的两段代码，一段持有锁 A 后申请锁 B，另一段持有锁 B 后申请锁 A。
应当将其统一为“始终先 A 后 B”的全局偏序；自第二把锁起采用 try-lock 加超时，无法取得的，应当释放已有锁并重试，并在并发文档记录锁数与超时。
</example>

<example>
异步 Web 处理器在事件循环内调用同步阻塞的数据库驱动，导致其他请求全部停滞。
应当改用异步驱动，或者把该调用交由线程池执行器处理，并确保回调不持有锁。
</example>

<example>
并发测试仅运行 `go test`，未启用 `-race`，且仅运行一次。
应当改为在 CI 中运行 `go test -race`，并对同一路径施加压力测试以提高交错覆盖；同时应当说明：检测器仅证明已执行的交错不存在竞争，并非全部交错。
</example>
