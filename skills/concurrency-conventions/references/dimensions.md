# 并发与并行维度

本文件与 `SKILL.md` 配合使用。每一节规定一个并发维度的决策、示例与边界情况。项目已有并发策略的，代理应当
先行阅读，并将其作为事实输入；本 skill 的规则优先，项目约定仅在本 skill 未规定时补充。本文件提供默认值与理由。
代理仅应阅读与待修改的共享状态、待选择的同步原语或待排查的故障相匹配的节。

## 1. 共享状态与数据竞争

数据竞争的定义可以判定：两个或更多执行流并发访问同一内存位置，其中至少一个为写入，且未建立“先发生”关系的
同步，则该次访问构成数据竞争。竞争的结果为内存模型允许的任意值：程序可能崩溃、读取到中间状态，或者在无报错
的情况下给出错误结果，且仅在特定调度下复现。本节处理竞争的三种根源：原子性、可见性与加锁粒度。

- 应当以同步建立先发生关系，不得以 sleep 或偶然性替代。任何读改写（例如 `count++`、先检查后行动），均必须
  采用原子操作或持锁；读侧与写侧应当持有同一把锁。仅锁定写侧而未锁定读侧的，读取到的仍为写入一半的中间状态。
- 原子性仅保护单个操作。多个字段共同构成“始终同时成立”的不变量的，应当以一把锁整体保护；任何读取或写入其中
  一部分的路径，均应当持有同一把锁。分别以原子类型保护每个字段的，不变量仍可被并发打破。
- 可见性不因加锁而自动解决读侧。线程或 CPU 核心可能缓存变量；使一个线程的写入对另一线程可见，需要锁、原子
  操作或内存屏障建立 happens-before。`volatile` 仅保证可见性，不保证原子性；`i++` 采用 `volatile` 仍属于竞争。
- 锁定的对象为不变量，而非方法。应当依数据划分锁：同一把锁保护“哪些字段必须一致”，而非“哪个方法正在修改”。
  字段分布于两把锁之下，却在语义上必须一致的，即构成潜在的竞争。
- 复杂不变量应当优先以消息传递或不可变值消解，不得以增加锁的数量处理。锁的数量越多，顺序与死锁的推理越难；
  可以退化为单一所有者或不可变数据的，应当先行退化。
- 竞争并非唯一应当修复的问题。加锁后的顺序依赖、优先级反转与锁顺序不一致，均不表现为数据竞争，但同样会导致
  失效；上述问题归第 3 节的死锁与活锁管辖。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 读与写持有同一把锁 | 仅锁定写侧，读侧不加锁 | 读侧将看到写入一半的中间状态 |
| 一把锁保护整个不变量 | 每个字段各设一个原子类型 | 复合不变量仍可被并发打破 |
| 以锁或原子操作建立 happens-before | 以 sleep 等待另一线程的写入 | 可见性不因时间流逝而获得保证 |
| 依数据划分锁 | 依方法划分锁 | 语义一致的字段被不同的锁分别保护 |
| 竞争修复后运行检测器验证 | 修复后仅运行一次普通测试 | 概率性竞争无法由一次通过证明 |

## 2. 同步原语选择

原语选择错误，将使正确的代码变慢，或使简单问题复杂化。选择依据为：保护对象、读写比例、等待方式，以及是否需
要公平或可重入。代理应当先回答“是否可以不共享”，再回答“采用哪一种”；决策表见 `checklist.md`。

- 互斥锁（mutex）为默认选项：保护一段临界区，任何时刻仅允许一个执行流进入。适用于写多读多、临界区较短且无
  等待的场景。可重入锁（reentrant lock）可以避免同一线程重复加锁导致自我死锁，但会掩盖锁设计问题；应当优先
  采用不可重入锁并修正结构。
- 读写锁（read-write lock）仅在读远多于写时适用：读并发，写互斥。写入频繁的，其开销大于互斥锁，且可能使写者
  饥饿；代理应当先测量读写比例，不得凭直觉采用读写锁。
- 信号量（semaphore）用于限量：限制同时访问某项资源的执行流数量，或者作为有界缓冲区的容量信号。信号量不保
  护临界区内的状态，仅实施计数；保护状态仍应当采用互斥锁。
- 条件变量（condition variable）用于等待状态变化：在互斥锁之上“等待直至谓词为真”，以避免忙等。等待应当以
  循环重查谓词（防止虚假唤醒）；通知应当采用 `notify`，不得假定被通知者恰好醒来。原语支持超时的，必须设定超
  时；不支持超时的，应当改用可取消等待、看门狗或带超时的 select/channel，并将例外记录于并发文档。
- 原子操作（atomic）用于单个标量的读改写：计数、标志、无锁的比较并交换（compare-and-swap）。原子操作不保护
  多个字段，亦不保证复合判断的原子性；涉及两个以上内存位置的，应当改用锁。
- 不得以忙等自旋替代条件变量或信号量。短时自旋可以采用；无界自旋将消耗 CPU，且可能形成活锁；应当采用退避或
  挂起等待。
- 原语并非语言无关。同一概念在不同语言中的能力不同（例如 Go 的 channel 优先于显式锁，Rust 以类型系统禁止竞
  争）；对照表见 `checklist.md`。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 写多读多采用互斥锁 | 写入频繁仍采用读写锁 | 写者互斥的开销超过互斥锁 |
| 读多写少采用读写锁 | 以单一大互斥锁串行化全部读取 | 读并发被消除 |
| 限量与容量采用信号量 | 以互斥锁模拟计数上限 | 混入互斥语义，难以推理 |
| 等待状态变化采用条件变量 | 以忙等自旋轮询标志 | 空转消耗 CPU，可能形成活锁 |
| 单个标量读改写采用原子操作 | 多字段不变量采用多个原子操作 | 复合不变量仍可被并发打破 |

## 3. 死锁与活锁

死锁指下列四个条件同时成立：互斥、持有并等待、不可抢占、循环等待。破坏任意一项即可消除死锁。活锁属于另一情
形：执行流仍在活动，在让渡与重试之间往返，但无任何执行流前进。二者均表现为“停滞”，但排查与修复方法不同。

- 统一锁顺序为首选。应当为全局锁集合确定一个偏序，任何执行流均按同一顺序申请；两段代码以相反顺序申请同一组
  锁，即构成死锁的充分条件，亦为审查中最易发现的信号。
- 无法取得锁的，应当采用 try-lock 加超时，不得无限等待。第二把及其后的锁应当采用 try-lock；无法取得的，应当
  释放已持有的锁并重试，或者在超时后上报。超时必须设定上限与重试上限；否则仅为将死锁转化为无限重试。
- 持锁期间不得申请其他锁、不得回调、不得实施 I/O。锁嵌套将顺序交由外部代码；在回调中反向申请的，即形成死锁。
  应当将依赖移出临界区，或者将回调改为先释放锁、再调用。
- 减少锁的数量与粒度。单一把大锁不产生死锁（无第二把锁可等待），但会消除并发；依不变量拆分锁的，应当同时规
  定全局顺序。
- 排查应当先绘制资源等待图：每个执行流对应一个节点，边表示“持有 X 并等待 Y”。存在环即为死锁；环上的任意一
  条边均为破环点。工作表见 `checklist.md`。
- 活锁应当以让渡与重试上限修复。双方以相同节奏重试并让渡的，将往返空转；应当引入随机退避、不对称延迟或最终
  失败上报，保证至少一方前进。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 全局一致的锁顺序 | 两处代码以相反顺序加锁 | 相反顺序构成循环等待 |
| try-lock 加超时 | 无限等待第二把锁 | 死锁转化为永久停滞 |
| 持锁期间不回调、不嵌套 | 持锁调用外部代码 | 锁顺序交由外部代码决定 |
| 以资源等待图查找环 | 逐线程查阅栈帧推测死锁 | 未发现环，即无法确定破环点 |
| 以随机退避结束活锁 | 双方以同步节奏重试与让渡 | 任何一方均不前进 |

## 4. 异步与并发模型

模型决定“何者在何时被调度、阻塞发生于何处”。模型选择错误的，将使阻塞扩散至不应阻塞之处，或者使共享状态失去
清晰边界。

- 线程为抢占式调度的执行流，共享同一进程内存。适用于 CPU 密集任务与独立的阻塞任务；代价为栈与调度开销，并
  且必须采用锁或原子操作同步共享内存。线程数量应当接近可并行资源数量，不得无界创建。
- 协程与 async/await 为协作式调度，在显式等待点让出。适用于大量 I/O 密集、低时延的任务；代价为单线程事件循
  环上的一个阻塞调用将使全部任务停滞。阻塞工作应当交由线程池处理，或者改用真正的异步 API。
- 事件循环为单线程调度器，将回调与异步任务排队执行。规则为“不得阻塞”：任何同步阻塞 I/O、长时间计算与持锁
  的慢操作，均不得进入事件循环；违反的，其他任务将全部排队等待。
- 线程池用于隔离阻塞任务与 CPU 任务：阻塞 I/O 与长时间计算应当交由池中的工作线程处理，事件循环仅实施调度与
  快速路径。池的大小应当与任务类型匹配（CPU 密集按核数确定，I/O 密集可以更多），并应当设定队列上限与拒绝
  策略。
- 模型之间应当明确边界。跨线程共享应当采用锁或消息传递；协程之间在同一线程内以 await 交替执行的，仍应当处理
  共享状态的数据竞争（单线程且无交错的除外）。
- 记录每个执行流可以访问的状态。线程、协程、任务各自的可见状态，应当写入文档；“该回调于哪个线程运行、可以
  访问什么”必须可以回答；否则共享状态无从审查。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| I/O 密集采用 async/协程 | 在事件循环内同步阻塞 I/O | 一个调用使全部任务停滞 |
| 阻塞工作交由线程池 | 以协程执行长时间 CPU 计算 | 协作式让出点之间无法抢占 |
| CPU 密集按核数确定线程池 | 无界创建线程 | 上下文切换与内存耗尽 |
| 记录执行流的可见状态 | 未写明回调所在线程 | 共享状态无从审查 |
| 跨线程采用锁或消息传递 | 跨线程直接共享且未同步 | 数据竞争 |

## 5. 并发正确性的测试

并发缺陷具有概率性：同一交错本次通过、下次崩溃。普通测试无法证明并发正确，因为测试运行器不探索交错。本节规
定使竞争在测试阶段暴露的手段及其边界。

- 涉及共享状态的测试，在提供运行期竞态检测器的语言中必须运行检测器：Go 使用 `go test -race`，C/C++ 使用
  ThreadSanitizer（TSan），Rust 使用 `loom` 或 Miri；命令表见 `checklist.md`。未内置检测器的语言，应当以压力
  测试、静态工具与审查替代，并记录覆盖缺口；检测器未运行的，不得声称不存在数据竞争。
- 检测器仅覆盖已执行的交错，不覆盖未执行的交错。检测器通过并不等于正确；其仅为对“该段执行历史”的证明。扩大
  覆盖的，应当以压力测试与注入触发更多交错。
- 压力测试提高交错覆盖：同一操作并发运行大量迭代，采用不同线程数与随机调度，使竞争路径更可能被触发。压力测
  试不替代正确性推理，仅提高发现概率。
- 确定性应当依靠注入，不得依靠偶然性。向关键点注入延迟、栅栏与屏障，或者记录并重放调度，使某次失败可以复现；
  随机失败必须打印种子与输入，否则无法复现。
- 以模型检查补足：Loom（Rust）、TLA+ 等工具显式枚举交错，可以在小范围内证明“所有交错均无竞争”。适用于锁
  顺序与协议等有限状态问题。
- 失败的并发测试属于缺陷，并非噪声。生产竞态导致的不稳定测试，应当视为生产缺陷并予以修复，不得重试或跳过；
  该点与 testing-and-quality-conventions 的不稳定测试规则一致。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| CI 中运行 `go test -race` | 并发测试仅运行普通模式 | 竞争不会被检测 |
| 以压力测试提高交错覆盖 | 并发路径仅运行一次 | 概率性竞争未被检出 |
| 注入延迟使失败可以复现 | 以 sleep 稳定时序 | 时序仍不确定 |
| 记录种子与输入 | 随机失败未打印种子 | 无法复现 |
| 以模型检查验证锁顺序 | 将锁顺序交由手工推理 | 交错空间过大，人工推理不可行 |

## 6. 并发与并行

并发与并行常被混用；区分二者，决定“是否应当引入并发”以及“并发可以带来何种收益”。

- 并发属于结构：将任务拆分为可以独立推进的多个执行流，单核上亦可通过交错实现。并行属于执行：多个任务真正同
  时运行，需要多核或多处理器。
- 单核可以实现并发，无法实现并行；并行需要并发结构并具备足够的硬件。因此，“采用多线程”并不等于“更快”：单
  核上的多线程仅增加切换开销。
- 引入并发的理由必须可以判定：响应性（界面/服务不被阻塞）、吞吐（重叠 I/O 等待）或资源利用（多核）。无上述
  三者之一的，不得引入并发。
- 判断收益应当依据测量，不得依据直觉。加锁、切换与内存同步均有成本；应当在目标硬件上测量吞吐与延迟；收益不
  成立的并发属于纯负债。
- 并发不解决单线程算法低效的问题。应当先优化算法与数据结构，再考虑并发；将串行低效的问题并发化，仅使低效扩
  展至多核。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 依响应性/吞吐/利用率引入并发 | “并发即更快”的直觉 | 单核多线程仅增加开销 |
| 先优化算法，再实施并发化 | 以并发化掩盖算法低效 | 低效被复制到多核 |
| 在目标硬件上测量收益 | 凭直觉判断收益 | 锁与切换具有实际成本 |
| 区分结构与执行 | 将并发视为并行 | 判断收益时前提即已错误 |

## 7. 不可变性与消息传递

最可靠的并发正确性为“不存在共享可变状态”。本节的默认顺序为：先不可变，再消息传递，最后加锁。

- 不可变值不产生数据竞争：一经创建即不改变，任何执行流并发读取均安全。采用不可变数据结构、冻结可变对象、仅
  返回副本或防御性拷贝，可以消除整类竞争。
- 消息传递使数据仅有一个所有者：数据在创建者处可变，通过通道/队列将所有权移交给接收者，任何时刻仅一个执行流
  可以访问。传递后创建者不得再读取；应当以类型系统或约定强制所有权转移。
- 通道/队列本身需要同步，但传递的对象为所有权，而非共享。发送与接收之间为同步边界；不得在传递后使两个执行流
  同时持有引用。
- 冻结与拷贝的取舍：大对象拷贝具有成本，但可换取零竞争；热路径上可以共享不可变部分，仅拷贝可变部分。
- 不可变为默认，加锁为例外。无法写出“为何必须共享可变状态”的理由的，应当先以不可变或消息传递改写。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 返回不可变值或防御性拷贝 | 直接暴露内部可变对象 | 调用方与内部共享，绕过同步 |
| 以通道传递所有权 | 传递引用后双方继续使用 | 所有权不清晰，仍属共享 |
| 冻结可变对象以消除竞争 | 处处加锁保护同一份数据 | 锁越多，推理越难 |
| 共享不可变部分，拷贝可变部分 | 为节省拷贝而整体共享 | 为较小收益引入较大风险 |
