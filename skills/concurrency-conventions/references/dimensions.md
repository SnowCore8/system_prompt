# 并发与并行维度

本文件与 `SKILL.md` 配合使用。每一节给出一个并发维度的决策、示例与边界情况。项目已有并发策略时，先读策略并执行
效力更高的规则；本文件提供默认值与理由。只读与你要改的共享状态、要选的同步原语或要排查的故障相匹配的那一节。

## 1. 共享状态与数据竞争

数据竞争的定义是可判定的：两个或更多执行流并发访问同一内存位置，其中至少一个是写，且没有建立"先发生"关系的同步，
那么这一次访问就是数据竞争。竞争的结果是内存模型允许的任意值——程序可能崩溃、读到中间状态或悄悄给出错误结果，
而且只在特定调度下复现。这一节处理竞争的三种根源：原子性、可见性与加锁粒度。

- 用同步建立先发生关系，而不是用 sleep 或运气。任何读改写（`count++`、先检查后行动）都必须是原子操作或持锁，
  读侧与写侧持同一把锁。只锁写不锁读，读到的仍是写了一半的中间状态。
- 原子性只保护单个操作。多个字段组成"总是一起成立"的不变量时，用一把锁把它们整体保护，任何读或写其中一部分的
  路径都持同一把锁；分别用原子类型保护每个字段，不变量仍然可以被并发打破。
- 可见性不因加锁而自动解决读侧。线程或 CPU 核心可能缓存变量；要让一个线程的写对另一个线程可见，需要锁、原子操作
  或内存屏障建立 happens-before。`volatile` 只保证可见性不保证原子性，`i++` 用 `volatile` 仍是竞争。
- 锁住不变量，而不是锁住方法。按数据划分锁：同一把锁保护"哪些字段必须一致"，而不是"哪个方法在修改"。字段分布在
  两把锁下、却在语义上必须一致时，就是潜在的竞争。
- 复杂不变量优先用消息传递或不可变值消解，而不是加更多锁。锁越多，顺序与死锁的推理越难；能退化为单所有者或
  不可变数据的，先退。
- 竞争不是唯一要修的问题。加锁后的顺序依赖、优先级反转、锁顺序不一致都不表现为数据竞争，但同样会失效；这些归
  第 3 节的死锁与活锁。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 读与写持同一把锁 | 只锁写、读不加锁 | 读会看到写了一半的中间状态 |
| 一把锁保护整个不变量 | 每个字段一个原子类型 | 复合不变量仍可被并发打破 |
| 用锁或原子建立 happens-before | 用 sleep 等待另一个线程的写 | 可见性不因时间流逝而保证 |
| 按数据划分锁 | 按方法划分锁 | 语义一致却被不同锁分开保护 |
| 竞争修复后跑检测器验证 | 修完只跑一次普通测试 | 概率性竞争无法由一次通过证明 |

## 2. 同步原语选择

原语选错会让正确代码变慢、让简单问题变复杂。选择依据是：保护什么、读写比例、等待方式，以及是否需要公平或可重入。
先回答"能不能不共享"，再回答"用哪一种"；决策表见 `checklist.md`。

- 互斥锁（mutex）是默认项：保护一段临界区，任何时刻只允许一个执行流进入。适用写多读多、临界区短且无等待的场景。
  可重入锁（reentrant lock）能避免同一线程重复加锁自我死锁，但会掩盖锁设计问题；优先用不可重入锁并修正结构。
- 读写锁（read-write lock）只在读远多于写时值得用：读并发、写互斥。写频繁时其开销大于互斥锁，且可能饿死写者；
  先测量读写比例，别凭感觉加读写锁。
- 信号量（semaphore）用于限量：限制同时访问某资源的执行流数量，或作为有界缓冲区的容量信号。它不保护临界区内的
  状态，只做计数；保护状态仍要互斥锁。
- 条件变量（condition variable）用于等待状态变化：在互斥锁之上"等待直到谓词为真"，避免忙等。等待用循环重查谓词
  （防虚假唤醒），通知用 `notify` 而非假设刚好醒来；原语支持超时时必须带上，不支持时改用可取消等待、看门狗，或
  带超时的 select/channel，并把例外记录在并发文档中。
- 原子操作（atomic）用于单个标量的读改写：计数、标志、无锁的比较并交换（compare-and-swap）。它不保护多个字段，
  也不保证复合判断的原子性；一旦涉及两个以上内存位置，回到锁。
- 不要用忙等自旋替代条件变量或信号量。短自旋可以，但无界自旋烧 CPU 且可能活锁；用退避或挂起等待。
- 原语不是语言无关的。同一概念在不同语言里能力不同（如 Go 的 channel 优先于显式锁，Rust 用类型系统禁止竞争）；
  对照表见 `checklist.md`。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 写多读多用互斥锁 | 写频繁还用读写锁 | 写者互斥开销反超互斥锁 |
| 读多写少用读写锁 | 用大互斥锁串行化全部读取 | 读并发被消灭 |
| 限量与容量用信号量 | 用互斥锁模拟计数上限 | 混入互斥语义，难以推理 |
| 等待状态变化用条件变量 | 用忙等自旋轮询标志 | 空转烧 CPU，可能活锁 |
| 单个标量读改写用原子 | 多字段不变量用多个原子 | 复合不变量仍被并发打破 |

## 3. 死锁与活锁

死锁是四个条件同时成立：互斥、持有并等待、不可抢占、循环等待。破坏任意一个就能消除死锁。活锁是另一回事：执行流
仍在活动、在让渡与重试之间来回，但没有一个前进。两者都表现为"卡住"，但排查与修复不同。

- 统一锁顺序是首选。给全局锁集合定一个偏序，任何执行流都按同一顺序申请；两段代码以相反顺序申请同一组锁就是
  死锁的充分条件，也是审查中最容易发现的信号。
- 拿不到就用 try-lock 加超时，而不是无限等待。第二把及以后的锁用 try-lock；拿不到就释放已持有的锁并重试，或等
  一个超时后上报。超时必须有上限与重试上限，否则只是把死锁换成无限重试。
- 持锁期间不申请别的锁、不回调、不做 I/O。锁嵌套把顺序交给外部代码，回调里反向申请就是死锁；把依赖移出临界区，
  或把回调改成先释放锁再调用。
- 减少锁的数量与粒度。一把大锁不产生死锁（没有第二把锁可等），但消灭并发；按不变量拆锁时要同时规定全局顺序。
- 排查先画资源等待图：每个执行流一个节点，边表示"持有 X 等待 Y"。有环就是死锁，环上的任意一条边都是破环点。
  工作表见 `checklist.md`。
- 活锁靠让渡与重试上限修复。双方都以相同节奏重试又让渡就会来回空转；引入随机退避、不对称延迟或最终失败上报，
  保证至少一方前进。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 全局一致的锁顺序 | 两处代码相反顺序加锁 | 相反顺序构成循环等待 |
| try-lock 加超时 | 无限等待第二把锁 | 死锁变成永久卡死 |
| 持锁不回调不嵌套 | 持锁调用外部代码 | 锁顺序被交给别人 |
| 资源等待图找环 | 逐个线程翻栈猜死锁 | 看不到环就看不到破环点 |
| 随机退避结束活锁 | 双方同步节奏重试让渡 | 谁也不前进 |

## 4. 异步与并发模型

模型决定"谁在何时被调度、阻塞发生在哪里"。选错模型会让阻塞泄漏到不该阻塞的地方，或让共享状态失去清晰的边界。

- 线程是抢占式调度的执行流，共享同一进程内存。适合 CPU 密集与独立阻塞任务；代价是栈与调度开销，以及必须用锁或
  原子同步共享内存。线程数量应当接近可并行资源，而不是无界创建。
- 协程与 async/await 是协作式调度，在显式等待点让出。适合大量 I/O 密集、低时延的任务；代价是单线程事件循环上的
  一个阻塞调用会卡住全部任务。阻塞工作交给线程池，或改用真正的异步 API。
- 事件循环是单线程调度器，把回调与异步任务排队执行。规则是"不阻塞"：任何同步阻塞 I/O、长时间计算、持锁的慢操作
  都不进事件循环；违反时其它任务全部排队等待。
- 线程池隔离阻塞与 CPU 任务：把阻塞 I/O 与长时间计算交给池中的工作线程，事件循环只做调度与快速路径。池的大小
  与任务类型匹配（CPU 密集按核数，I/O 密集可更多），并设队列上限与拒绝策略。
- 模型之间要明确边界。跨线程共享用锁或消息传递；协程之间在同一个线程内用 await 交错的顺序，仍要处理共享状态的
  数据竞争（除非单线程且无交错）。
- 记录每个执行流能访问哪些状态。线程、协程、任务各自的可见状态写进文档；"这个回调在哪个线程跑、能碰到什么"必须
  可回答，否则共享状态无从审查。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| I/O 密集用 async/协程 | 在事件循环里同步阻塞 I/O | 一个调用卡住全部任务 |
| 阻塞工作交给线程池 | 用协程跑长 CPU 计算 | 协作式让出点间无法抢占 |
| CPU 密集按核数定线程池 | 无界创建线程 | 上下文切换与内存耗尽 |
| 记录执行流可见状态 | 回调线程不写清 | 共享状态无从审查 |
| 跨线程用锁或消息 | 跨线程裸共享无同步 | 数据竞争 |

## 5. 并发正确性的测试

并发缺陷是概率性的：同一次交错这次过、下次崩。普通测试证明不了并发正确，因为运行器不探索交错。这一节给的是让
竞争在测试阶段暴露的手段，以及它们的边界。

- 涉及共享状态的测试，在有运行期竞态检测器的语言里必须跑检测器：Go 用 `go test -race`，C/C++ 用
  ThreadSanitizer（TSan），Rust 用 `loom` 或 Miri；命令表见 `checklist.md`。没有内置检测器的语言用压力测试、
  静态工具与审查替代，并记录覆盖缺口；检测器没跑过，就不能声称无数据竞争。
- 检测器只覆盖执行到的交错，不覆盖没跑到的。检测器通过不等于正确；它是对"这段执行历史"的证明。要扩大覆盖，用
  压力测试与注入去触发更多交错。
- 压力测试提高交错覆盖：同一操作并发跑大量迭代、用不同线程数与随机调度，让竞争路径更可能被踩中。压力测试不
  替代正确性推理，只是提高发现概率。
- 确定性靠注入，不靠运气。注入延迟、栅栏与屏障到关键点，或记录并重放调度，让某次失败可复现；随机失败必须打印
  种子与输入，否则无法复现。
- 用模型检查补足：Loom（Rust）、TLA+ 等显式枚举交错，能在小范围内证明"所有交错无竞争"。适用于锁顺序与协议这类
  有限状态问题。
- 失败的并发测试是缺陷，不是噪声。生产竞态导致的不稳定测试应视为生产缺陷并修复，而不是重试或跳过；这一点与
  testing-and-quality-conventions 的不稳定测试规则一致。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| CI 跑 `go test -race` | 并发测试只跑普通模式 | 竞争根本不被检测 |
| 压力测试提高交错覆盖 | 只跑一遍并发路径 | 概率性竞争漏网 |
| 注入延迟让失败可复现 | 靠 sleep 稳定时序 | 时序仍不确定 |
| 记录种子与输入 | 随机失败不打印种子 | 无法复现 |
| 模型检查锁顺序 | 把锁顺序交给手工推理 | 交错空间太大，人算不过来 |

## 6. 并发与并行

并发与并行常被混用，但区分它们决定"要不要引入并发"以及"并发能带来什么"。

- 并发是结构：把任务拆成可独立推进的多个执行流，单核上也能通过交错实现。并行是执行：多个任务真正同时运行，需要
  多核或多处理器。
- 单核也能并发，不能并行；并行需要并发的结构加足够的硬件。因此"用了多线程"不等于"更快"——单核上的多线程只增加
  切换开销。
- 引入并发的理由必须是可判定的：响应性（界面/服务不被阻塞）、吞吐（重叠 I/O 等待）、资源利用（多核）。没有这三个
  之一，就别引入并发。
- 判断收益用测量，不用直觉。加锁、切换与内存同步都有成本；在目标硬件上测吞吐与延迟，收益不成立的并发是纯负债。
- 并发不解决单线程算法慢的问题。先优化算法与数据结构，再考虑并发；把串行慢的问题并发化，只是把慢放大到多核。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 按响应性/吞吐/利用引入并发 | "并发就是更快"的直觉 | 单核多线程只增开销 |
| 先优化算法再并发化 | 并发化掩盖算法慢 | 慢被复制到多核 |
| 在目标硬件测量收益 | 凭感觉判断收益 | 锁与切换有真实成本 |
| 区分结构与执行 | 把并发当并行 | 判断收益时前提就错 |

## 7. 不可变性与消息传递

最可靠的并发正确性是"没有共享可变状态"。这一节的默认顺序是：先不可变，再消息传递，最后才加锁。

- 不可变值不产生数据竞争：一旦创建就不改变，任何执行流并发读都安全。用不可变数据结构、冻结可变对象、只返回副本
  或防御性拷贝，消除整类竞争。
- 消息传递让数据只有一个所有者：数据在创建者处可变，通过通道/队列把所有权交给接收者，任何时刻只有一个执行流能
  访问。传递后创建者不再读，用类型系统或约定强制所有权转移。
- 通道/队列本身要同步，但传递的是所有权而不是共享。发送与接收之间是同步边界；不要在传递后再让两个执行流同时
  持有引用。
- 冻结与拷贝的取舍：大对象拷贝有成本，但换来零竞争；热路径上可以共享不可变部分、只拷贝可变部分。
- 不可变是默认，加锁是例外。写不出"为什么必须共享可变状态"的理由，就先用不可变或消息传递改写。

| 好做法 | 坏做法 | 原因 |
|---|---|---|
| 返回不可变值或防御性拷贝 | 把内部可变对象直接暴露 | 调用方与内部共享，绕过同步 |
| 通道传递所有权 | 传引用后双方都继续用 | 所有权不清，仍是共享 |
| 冻结可变对象消除竞争 | 处处加锁保护同一份数据 | 锁越多推理越难 |
| 共享不可变部分、拷贝可变部分 | 为省拷贝整体共享 | 为小收益引入大风险 |
