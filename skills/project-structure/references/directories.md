# 项目结构：目录与包边界

目录是边界的物理表达：模块、包、应用与平台配置各占其位，一眼可见。目录乱序会诱导依赖乱序。

## 1. 目录形态

- 每个代码顶层目录对应一个模块或包，具有单一职责与明确所有者；同一层只沿一套轴组织，功能与层不混用。
- `utils`、`common`、`misc` 等无边界目录不得保留：按领域拆入对应模块，真正通用的进入有所有者的共享包。
- 项目形态四选一：单包应用、可复用库、多包工作区与 monorepo；不得把不同形态的目录约定混用。

## 2. 包与工作区

- 每个包有 manifest、公开入口、测试与版本策略或私有标记；工作区根只做编排与共享配置，不承载业务实现。
- 应用只依赖包的公开入口；应用之间不得互相导入；包之间依赖更稳定的包。
- 新增或移动包时，在同一次变更中更新所有者映射与依赖它的工作流。

## 3. 非代码目录

- `docs`、`tools`、`generated`、`vendor` 与平台目录按用途单列，写明所有者与只读或生成规则。
- `.github/` 是托管平台保留层，承载 workflows、actions 与模板，不得存放业务代码。
- 构建产物与缓存不得进入源码树；测试靠近模块或镜像模块目录，跨模块测试只经公开面。
