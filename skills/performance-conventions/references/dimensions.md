# 性能维度

把本文件与 `SKILL.md` 一起使用。每个章节给出一个维度的规则、边界情况与失败模式。当项目已有性能目标、预算或基准
时，先阅读并应用更高优先级的规则；本文件提供默认值与理由。章节编号与 `SKILL.md` 中的维度索引对应。

## 1. 测量与剖析

性能工作的第一事实是数字，第二事实是数字的来源。没有可复现的基准与剖析，一切优化都无法证明收益。

- **先建基准，再动手。** 基准（benchmark）是固定输入下重复测得的一组指标（延迟、吞吐、内存），必须可复现：同一脚本、
  同一输入、同一环境、同一口径。动手优化前先跑基准拿到基线数字；没有基线，就没有「变快了还是变慢了」的对照。
- **用剖析定位热点。** 剖析（profiling）指出时间、分配或锁主要花在哪里。用 perf、pprof 或等价工具按抽样或插桩定位热点，
  而不是靠读代码猜热点。判据：优化目标必须是剖析结果里出现的真实热点，而不是「看起来慢」的函数。
- **基准与剖析脚本留在仓库。** 脚本、输入集与结果记录随代码提交，让下次优化能复现对照；只留在本地的基准无法被审查、
  复现或作为门禁。把基准接入 CI 的机制归 `testing-and-quality-conventions`。
- **区分测量误差与真实差异。** 结果要有足够样本并报告波动（多次运行的最小值/中位数，而非单次值）；差值小于噪声时，
  结论是「无显著差异」而不是「有收益」。用同一套基准对比前后，环境、输入或口径一变，数字就不可比。
- **测生产要务实的，测开发要可复现的。** 开发期的微基准定位热点与复测局部改动；生产环境的真实负载与可观测性归
  `release-operations-conventions`。两者的结论不能互相替代。

| 正例 | 反例 | 原因 |
|---|---|---|
| 跑剖析定位到 80% 时间在 `get_user` | 凭感觉重写「看起来慢」的排序 | 前者有热点证据，后者可能是冷路径。 |
| 基准跑 1000 次报告中位数与波动 | 跑一次取耗时当作结论 | 单次值淹没在噪声里，无法判断收益。 |
| 基准脚本与结果随代码提交 | 基准只存在于某人的本地脚本 | 别人无法复现或审查结论。 |

| 工具类别 | 用途 | 何时用 |
|---|---|---|
| 微基准 | 测单函数/单路径的局部指标 | 测量一次局部改动的收益 |
| 抽样剖析 | 找出时间/分配/锁的热点 | 定位该优化什么 |
| 插桩剖析 | 精确计数与调用图 | 抽样不够细时补细节 |
| 负载测试 | 测端到端吞吐与延迟 | 确认系统级目标是否达成 |

## 2. 目标与预算

目标是停止条件：没有阈值，就不知道何时优化、何时停手、何时算过度。

- **先定目标再优化。** 为延迟、吞吐、内存与启动时间写清阈值与测量口径（如「p95 延迟 ≤ 100ms」「每秒 ≥ 1000 请求」），
  才开始优化。目标未达成的路径才优化；已达成的路径不动。
- **目标与预算写清口径。** 明确是 p50、p95 还是 p99，是平均还是峰值，是稳态还是突发；同一指标不同口径不可比。内存预算
  写清是峰值常驻还是总分配。阈值见性能目标文档或 SLO，它们由项目而非本 skill 裁定。
- **预算约束资源，而非束缚正确性。** 用预算给每条路径设上限，超限就是未达标；但不要为压预算牺牲正确性，正确性问题的
  修复优先于性能（并发正确性归 `concurrency-conventions`）。
- **未达标的才优化，达标的别动。** 达到目标的路径即使「还能更快」也不再优化；把投入留给真正超标的路径。可判定：一个
  优化必须对应一条未达标的目标；没有对应目标的优化是过度优化。

| 正例 | 反例 | 原因 |
|---|---|---|
| 「p95 登录延迟 ≤ 200ms」写清再优化 | 「让登录更快一点」就开始改 | 前者有停止条件，后者不知何时停。 |
| 只优化超标 10 倍的报表查询 | 反复优化已达 50ms 的首页 | 前者对应未达标目标，后者无回报。 |
| 内存预算写「峰值常驻 ≤ 512MB」 | 只写「内存别太高」 | 前者可测，后者不可判定。 |

| 指标 | 常见口径 | 说明 |
|---|---|---|
| 延迟 | p50 / p95 / p99 | 写清分位；平均值掩盖尾延迟。 |
| 吞吐 | 每秒请求 / 每秒事务 | 写清稳态还是突发。 |
| 内存 | 峰值常驻 / 总分配 | 写清测量口径。 |
| 启动 | 冷启动 / 热启动耗时 | 写清是否含依赖加载。 |

## 3. 常见瓶颈

热点通常落在少数几类模式里。先归类，再对症；归类错了，优化方向就错了。

- **N+1 查询。** 循环里逐条查询，把一次能查的数据拆成 N+1 次往返。修复是批量查询、联表或预取，把往返从 N 次降到常
  数次。判据：循环体内有查询调用，且循环次数随数据量增长。
- **不必要的 IO。** 重复读同样的数据、读远多于需要的数据、在热路径上做同步网络或磁盘访问。修复是消除重复、按需取数、
  异步化或缓存（见第 5 节）。判据：同一数据在短时间内被多次读取，或一次读取的量远大于实际使用量。
- **锁竞争。** 多个线程争抢同一把锁或共享结构，串行化本可并行的路径。归属 `concurrency-conventions`：本维度只负责在剖析
  发现锁竞争时把它移交过去，不在此改并发结构。
- **内存分配。** 热路径上频繁分配，触发 GC 压力或分配器开销。修复是复用缓冲、减少临时对象或改用栈上结构。判据：剖析
  显示分配次数与大小集中在热路径。
- **算法复杂度。** 用第 6 节的复杂度分析判断伸缩性；数据量增长时，O(n²) 会在某个规模突然崩坏。修复是换算法或数据结构。

| 瓶颈 | 症状 | 典型修复 |
|---|---|---|
| N+1 查询 | 延迟随记录数线性增长，日志满是单条查询 | 批量查询、联表、预取 |
| 不必要的 IO | 同一数据重复读，或读远多于用 | 去重、按需取数、缓存 |
| 锁竞争 | CPU 不高但吞吐上不去，等待时间长 | 移交 `concurrency-conventions` |
| 内存分配 | GC 停顿频繁，分配量大 | 复用缓冲、减少临时对象 |
| 算法复杂度 | 数据量一涨延迟陡增 | 换算法或数据结构 |

## 4. 优化纪律

优化的价值来自可归因、可复现、可回滚；没有纪律的优化，是改了一堆不知道有没有用的代码。

- **一次只改一处。** 每次变更只动一个变量，立即重新测量；同时改多处会让收益无法归因，也无法单独回滚。判据：一次
  变更只改一个逻辑点，其余不动。
- **改后重新测量。** 每次变更后用同一套基准重测并记录；不重新测量就声称有收益，是编造。前后数字都留档，供审查与
  回滚。
- **保留基准作为对照。** 优化前保存基线结果，优化后与基线对比；没有基线的「优化」无法证明任何东西。
- **无效的优化要回滚。** 测量显示无显著收益的改动，回滚而不是留下；留下无效改动会污染代码并误导后续判断。回滚是
  重构或修复，按行为变化归 `refactoring-conventions` 或测试门禁。
- **优化用证据归因，不用猜测。** 改动必须对应剖析结果里的热点；没有剖析支持的重写是重写，不是优化，不宣称有性能收益。

| 正例 | 反例 | 原因 |
|---|---|---|
| 改连接池大小，重测，记录前后 p95 | 一次改序列化、连接池、索引三处 | 前者可归因，后者收益来源不明。 |
| 测量无收益就回滚改动 | 无效改动留着「反正没坏」 | 前者干净，后者误导后续判断。 |
| 优化对应剖析里的热点 | 没剖析就重写「可能慢」的模块 | 前者有证据，后者是猜测。 |

## 5. 缓存与索引

缓存与索引用空间换时间，但都带来一致性与维护成本。它们是取舍，不是免费的加速。

- **缓存前先定失效与一致性策略。** 缓存引入第二份数据，就必须回答：何时失效、谁失效、不一致窗口多大、不一致时能否
  接受。没有失效策略的缓存是数据错误源，不是优化。判据：任何缓存都能说清失效触发与不一致上限。
- **缓存命中不了的缓存不设。** 先测量命中率与收益，再决定是否引入；命中率低、失效频繁或键空间过大的缓存，成本大于
  收益。判据：有测量支持的命中率，而不是「缓存总比不缓存快」的假设。
- **索引按查询加，权衡写入成本。** 为外键、热过滤与连接加索引；每个索引都让写入付代价，重复或未使用的索引只增负
  担。判据：每个索引都对应一条真实查询，且已权衡写入放大。索引的 schema 约束与锁影响归 `api-and-data-conventions`。
- **缓存与索引都不改变正确性。** 缓存与索引是性能层，正确性不依赖它们存在；清空缓存、删掉索引后系统仍应正确（只
  是变慢）。把正确性建立在缓存存在上的系统，一失效就出错。

| 正例 | 反例 | 原因 |
|---|---|---|
| 缓存带 TTL 与按事件失效 | 「先加缓存，失效以后再说」 | 后者缓存成为数据错误源。 |
| 按查询加索引并权衡写入 | 给每列都建索引「以防万一」 | 后者写入放大，收益未证。 |
| 命中率测量后再决定缓存 | 默认「缓存总比不缓存快」 | 低命中缓存成本大于收益。 |

## 6. 复杂度分析

复杂度回答「数据量增长时会怎样」，而不是「现在有多慢」。它决定伸缩性，剖析决定热点；两者分工，不互相替代。

- **用大 O 判断伸缩性。** 时间与空间复杂度描述算法随输入规模增长的行为；O(1)、O(log n)、O(n)、O(n log n)、O(n²) 等
  在数据量增长时的差别是数量级的。判据：能说出算法在最坏与常见情况下的时间与空间大 O。
- **复杂度差是设计问题，先于局部优化。** 一个 O(n²) 的算法，微调常数因子救不了数据量增长后的崩坏；先换算法或数据结构
  （O(n log n) 或更低），再谈常数优化。判据：数据量会增长时，优先处理复杂度，而不是常数。
- **剖析定位当前热点，复杂度判断未来伸缩。** 剖析告诉你「现在慢在哪」，复杂度告诉你「大了会不会崩」。只信其一都会
  误判：复杂度低未必现在不慢，当前不慢未必数据量翻倍后不崩。
- **常数优化只在热点上做。** 复杂度已经够低后，常数优化只对剖析确认的热点有意义；在非热点路径上抠常数是浪费。

| 正例 | 反例 | 原因 |
|---|---|---|
| O(n²) 嵌套循环换成哈希或排序 | 在 O(n²) 上微调循环展开 | 后者救不了数据量增长后的崩坏。 |
| 数据量会增长，先换算法 | 数据量恒定，仍强求 O(log n) | 后者为不存在的伸缩付成本。 |
| 热点用剖析定位，伸缩用大 O 判断 | 只看大 O 决定「改哪一行」 | 大 O 不管当前热点在哪。 |
