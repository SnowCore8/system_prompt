# 性能维度

本文件与 `SKILL.md` 配合使用。每一节规定一个性能维度的规则、边界情况与失败模式。项目约定与事实作为输入，性
能目标、预算与基准依本 skill 的规则处理；本 skill 的规则优先，项目约定仅在本 skill 未规定时补充。本文件提供
默认值与理由。章节编号与 `SKILL.md` 中的维度索引对应。

## 1. 测量与剖析

性能工作的第一事实为数字，第二事实为数字的来源。无可复现的基准与剖析，一切优化均无法证明收益。

- **先建立基准，再实施优化。** 基准（benchmark）指固定输入下重复测得的一组指标（延迟、吞吐、内存），必须可
  复现：同一脚本、同一输入、同一环境、同一口径。代理在优化前应当先运行基准并取得基线数字；无基线的，即无
  「变快或变慢」的对照。
- **以剖析定位热点。** 剖析（profiling）指出时间、分配或锁的主要所在。代理应当以 perf、pprof 或等价工具按
  抽样或插桩定位热点，不得依靠阅读代码猜测热点。判据：优化目标必须为剖析结果中出现的真实热点，而非「看起
  来慢」的函数。
- **基准与剖析脚本应当留存于仓库。** 脚本、输入集与结果记录应当随代码提交，使下一次优化能够复现对照；仅留
  存于本地的基准无法被审查、复现或作为门禁。将基准接入 CI 的机制由 `testing-and-quality-conventions` 管辖。
- **区分测量误差与真实差异。** 结果应当具有足够样本并报告波动（多次运行的最小值与中位数，而非单次值）；差
  值小于噪声的，结论为「无显著差异」，而非「有收益」。对比前后应当使用同一套基准；环境、输入或口径一经变
  更，数字即不可比。
- **生产测量应当务实，开发测量应当可复现。** 开发期的微基准用于定位热点与复测局部改动；生产环境的真实负载
  与可观测性由 `release-operations-conventions` 管辖。两者的结论不得相互替代。

| 正例 | 反例 | 原因 |
|---|---|---|
| 运行剖析定位到 80% 时间消耗于 `get_user` | 凭主观判断重写疑似缓慢的排序 | 前者具有热点证据，后者可能属于冷路径。 |
| 基准运行 1000 次，报告中位数与波动 | 运行一次即以耗时作为结论 | 单次值淹没于噪声，无法判断收益。 |
| 基准脚本与结果随代码提交 | 基准仅存于某人的本地脚本 | 他人无法复现或审查结论。 |

| 工具类别 | 用途 | 使用时机 |
|---|---|---|
| 微基准 | 测量单函数或单路径的局部指标 | 测量一次局部改动的收益 |
| 抽样剖析 | 找出时间、分配或锁的热点 | 定位应当优化的对象 |
| 插桩剖析 | 精确计数与调用图 | 抽样精度不足时补充细节 |
| 负载测试 | 测量端到端吞吐与延迟 | 确认系统级目标是否达成 |

## 2. 目标与预算

目标属于停止条件：无阈值，即无从判断何时优化、何时停止、何时构成过度优化。

- **先定目标，再优化。** 代理应当为延迟、吞吐、内存与启动时间写明阈值与测量口径（例如「p95 延迟 ≤ 100ms」
  「每秒 ≥ 1000 请求」），此后方可开始优化。仅应优化未达成目标的路径；已经达成的路径不得变更。
- **目标与预算应当写明口径。** 应当明确采用 p50、p95 或 p99，平均值或峰值，稳态或突发；同一指标的不同口径
  不可比。内存预算应当写明峰值常驻或总分配。阈值见性能目标文档或 SLO，由项目而非本 skill 裁定。
- **预算约束资源，不得束缚正确性。** 预算为每条路径设定上限，超限即为未达标；但不得为压缩预算而牺牲正确
  性，正确性问题的修复优先于性能（并发正确性由 `concurrency-conventions` 管辖）。
- **仅应优化未达标的路径，已经达成的不得变更。** 达到目标的路径即使「还能更快」也不再优化；投入应当保留给
  实际超标的路径。判定标准：一项优化必须对应一条未达标的目标；没有对应目标的优化属于过度优化。

| 正例 | 反例 | 原因 |
|---|---|---|
| 写明「p95 登录延迟 ≤ 200ms」后再优化 | 以「让登录更快一点」为起点实施改动 | 前者具有停止条件，后者不知何时停止。 |
| 仅优化超标 10 倍的报表查询 | 反复优化已经达到 50ms 的首页 | 前者对应未达标目标，后者没有回报。 |
| 内存预算写为「峰值常驻 ≤ 512MB」 | 仅写「内存不应过高」 | 前者可测，后者不可判定。 |

| 指标 | 常见口径 | 说明 |
|---|---|---|
| 延迟 | p50 / p95 / p99 | 应当写明分位；平均值掩盖尾延迟。 |
| 吞吐 | 每秒请求 / 每秒事务 | 应当写明稳态或突发。 |
| 内存 | 峰值常驻 / 总分配 | 应当写明测量口径。 |
| 启动 | 冷启动 / 热启动耗时 | 应当写明是否包含依赖加载。 |

## 3. 常见瓶颈

热点通常归属于少数几类模式。代理应当先行归类，再对症处理；归类错误的，优化方向亦将错误。

- **N+1 查询。** 循环内逐条查询，将一次可查的数据拆为 N+1 次往返。修复方式为批量查询、联表或预取，将往返
  次数由 N 次降至常数次。判据：循环体内存在查询调用，且循环次数随数据量增长。
- **不必要的 IO。** 重复读取相同数据、读取量远大于所需、在热路径上实施同步网络或磁盘访问。修复方式为消除
  重复、按需取数、异步化或缓存（见第 5 节）。判据：同一数据在短时间内被多次读取，或一次读取量远大于实际
  使用量。
- **锁竞争。** 多个线程争抢同一锁或共享结构，将本可并行的路径串行化。锁竞争造成的吞吐与延迟问题由本 skill
  定位与优化；锁语义、数据竞争与死锁的正确性由 `concurrency-conventions` 管辖。本维度不变更并发结构。
- **内存分配。** 热路径上频繁分配，触发 GC 压力或分配器开销。修复方式为复用缓冲、减少临时对象或改用栈上结
  构。判据：剖析显示分配次数与分配量集中于热路径。
- **算法复杂度。** 以第 6 节的复杂度分析判断伸缩性；数据量增长时，O(n²) 将在某一规模突然崩坏。修复方式为更
  换算法或数据结构。

| 瓶颈 | 症状 | 典型修复 |
|---|---|---|
| N+1 查询 | 延迟随记录数线性增长，日志中充满单条查询 | 批量查询、联表、预取 |
| 不必要的 IO | 同一数据重复读取，或读取量远大于使用量 | 去重、按需取数、缓存 |
| 锁竞争 | CPU 占用不高但吞吐不足，等待时间长 | 定位争用点并优化；正确性问题移交 `concurrency-conventions` |
| 内存分配 | GC 停顿频繁，分配量大 | 复用缓冲、减少临时对象 |
| 算法复杂度 | 数据量增长时延迟陡增 | 更换算法或数据结构 |

## 4. 优化纪律

优化的价值来自可归因、可复现与可回滚；缺乏纪律的优化，属于变更一批效用不明的代码。

- **一次仅变更一处。** 每次变更仅应变更一个变量，并立即重新测量；同时变更多处将使收益无法归因，亦无法单独
  回滚。判据：一次变更仅涉及一个逻辑点，其余内容不变。
- **变更后重新测量。** 每次变更后应当以同一套基准重测并记录；未重新测量即声称有收益的，属于编造。前后数字
  均应当留档，供审查与回滚。
- **保留基准作为对照。** 代理应当在优化前保存基线结果，优化后与基线对比；无基线的「优化」无法证明任何事
  项。
- **无效的优化应当回滚。** 测量显示无显著收益的改动，应当回滚，不得保留；保留无效改动将污染代码并误导后续
  判断。回滚属于重构或修复，依行为变化由 `refactoring-conventions` 或测试门禁管辖。
- **优化应当以证据归因，不得以猜测归因。** 改动必须对应剖析结果中的热点；无剖析支持的重写属于重写，不属于
  优化，不得宣称具有性能收益。

| 正例 | 反例 | 原因 |
|---|---|---|
| 变更连接池大小，重测，记录前后 p95 | 一次变更序列化、连接池与索引三处 | 前者可归因，后者收益来源不明。 |
| 测量无收益即回滚改动 | 无效改动以「反正未造成损害」为由保留 | 前者保持整洁，后者误导后续判断。 |
| 优化对应剖析中的热点 | 未剖析即重写「可能慢」的模块 | 前者具有证据，后者属于猜测。 |

## 5. 缓存与索引

缓存与索引用空间换取时间，但均带来一致性与维护成本。两者属于取舍，而非免费的加速。

- **引入缓存前应当先定失效与一致性策略。** 缓存引入第二份数据，代理必须回答：何时失效、由谁失效、不一致窗
  口多大、不一致是否可以接受。无失效策略的缓存属于数据错误源，不属于优化。判据：任何缓存均能够说明失效触
  发条件与不一致上限。
- **无法命中的缓存不得设置。** 代理应当先测量命中率与收益，再决定是否引入；命中率低、失效频繁或键空间过大
  的缓存，成本大于收益。判据：存在测量支持的命中率，而非「缓存总比不缓存快」的假设。
- **索引应当按查询增设，并权衡写入成本。** 应当为外键、热过滤与连接增设索引；每个索引均使写入付出代价，重
  复或未使用的索引只会增加负担。判据：每个索引均对应一条真实查询，且已经权衡写入放大。索引的 schema 约束
  与锁影响由 `api-and-data-conventions` 管辖。
- **缓存与索引均不改变正确性。** 缓存与索引属于性能层，正确性不得依赖其存在；清空缓存、删除索引后，系统仍
  应正确（仅变慢）。将正确性建立在缓存存在之上的系统，一经失效即出错。

| 正例 | 反例 | 原因 |
|---|---|---|
| 缓存具有 TTL 并按事件失效 | 「先增设缓存，失效以后再说」 | 后者使缓存成为数据错误源。 |
| 按查询增设索引并权衡写入 | 为每列建立索引「以防万一」 | 后者造成写入放大，收益未获证明。 |
| 命中率测量后再决定缓存 | 默认「缓存总比不缓存快」 | 低命中缓存的成本大于收益。 |

## 6. 复杂度分析

复杂度回答「数据量增长时会如何」，而非「当前有多慢」。复杂度决定伸缩性，剖析决定热点；两者分工，不得相互
替代。

- **以大 O 判断伸缩性。** 时间与空间复杂度描述算法随输入规模增长的行为；O(1)、O(log n)、O(n)、O(n log n)、
  O(n²) 等在数据量增长时的差别属于数量级。判据：能够说明算法在最坏情况与常见情况下的时间与空间大 O。
- **复杂度差距属于设计问题，应当先于局部优化处理。** O(n²) 的算法，微调常数因子无法挽救数据量增长后的崩
  坏；应当先更换算法或数据结构（O(n log n) 或更低），再讨论常数优化。判据：数据量将增长时，应当优先处理复
  杂度，而非常数。
- **剖析定位当前热点，复杂度判断未来伸缩。** 剖析指出「当前慢在何处」，复杂度指出「规模增大后是否会崩坏」。
  仅采信其一将导致误判：复杂度低未必当前不慢，当前不慢未必数据量翻倍后不崩坏。
- **常数优化仅应在热点上实施。** 复杂度已经足够低后，常数优化仅对剖析确认的热点具有意义；在非热点路径上追
  求常数属于浪费。

| 正例 | 反例 | 原因 |
|---|---|---|
| O(n²) 嵌套循环改为哈希或排序 | 在 O(n²) 上微调循环展开 | 后者无法挽救数据量增长后的崩坏。 |
| 数据量将增长，先更换算法 | 数据量恒定，仍强求 O(log n) | 后者为不存在的伸缩付出成本。 |
| 热点以剖析定位，伸缩以大 O 判断 | 仅以大 O 决定「修改哪一行」 | 大 O 不指示当前热点所在。 |
