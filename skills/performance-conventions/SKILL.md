# 性能规范

性能工作最严重的失败，不是没有实施优化，而是未测量就优化、没有目标就优化，或者优化已经达标的路径。无基准的
优化无法证明收益；无目标的优化没有停止条件；一次变更多处的优化无法归因。本 skill 规定先测量、再定目标、后优
化的程序，常见瓶颈的识别方式，以及使优化可判定、可回滚、可复现的规则。它服务三类读者：建立基准与剖析的工程
师、定位热点的优化者，以及审查过早优化与无效优化的审查者；在生命周期中，它为 G1 提供目标基线、为 G2 提供预算
与测量方案、为 G4 与 G5 提供前后可比的数据。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的运行时、语言、平台、宿主与全局用户约束。编译器的优化行为、运行时调度、存储引擎与网络的物理上限
   均非可选事项。
2. 本 skill 的规则与默认值。目标口径、测量方法与优化纪律以本文件与 `references/` 为准。
3. 既有性能目标、预算、已记录的基准与项目事实。SLO、基准脚本与历史剖析结果属于输入，依本 skill 的规则处理；
   项目约定仅在本 skill 未规定时补充，不得覆盖本 skill。智能体不得把暂定目标冒充项目承诺。
4. 个人偏好，不得覆盖上述三层。

边界：

- 并发正确性（锁语义、数据竞争、死锁）归 `concurrency-conventions`；锁竞争造成的吞吐下降与延迟升高由本 skill
  定位与优化，两者不得就同一主题相互移交。
- 测试与门禁归 `testing-and-quality-conventions`：该 skill 管辖把基准接入 CI 的机制、阈值与告警策略；本 skill
  管辖基准与剖析的方法论，不规定运行它们的工具。
- 可观测性归 `release-operations-conventions`：生产遥测、指标采集与告警由该 skill 负责；本 skill 只管辖开发期
  的基准与剖析，两者的结论不得相互替代。
- 索引的 schema 约束、迁移与锁影响归 `api-and-data-conventions`；本 skill 只判定是否值得为该查询增设索引。
- 阶段划分、门禁判定与风险分级归 `project-lifecycle-governance`；本 skill 提供性能证据，不自行决定 Go/No-Go。
- 强制规则冲突时报告用户裁决，不得自行选定；非强制的项目约定冲突可以说明所选约定，并记录于性能目标或基准
  文档，使下一次优化遵循同一决定。

## 生命周期定位

上游输入：S1 的结果指标与收益基线、已有 SLO、历史剖析结果与基准脚本，以及 G0 记录的授权与风险级别。

下游交接：目标与预算进入 G2 计划；基准与剖析方法进入 S3 迭代；前后对比数据作为 G4 验证证据；发布前回归比对
与回滚阈值交给 G5；收益对照与残留瓶颈交给 S6。

升级与停止：没有可复现基准时停止优化并先建基线；目标缺失且无法从上下文推定影响范围、预算或验收标准时，请求
用户确认；锁竞争的正确性线索、索引的 schema 约束分别移交 `concurrency-conventions` 与 `api-and-data-conventions`；
测量显示无显著收益时回滚改动，不得保留。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S1 探索 | 判断性能是否为真实问题，建立现状基线与结果指标口径 | 基线数字、口径说明、收益或成本判断 |
| S2 计划 | 固定性能目标、预算、测量方案与基准脚本位置 | 目标与预算表、基准计划、停止条件 |
| S3 构建 | 建立基线、剖析定位热点，按单点变更实施并复测 | 剖析输出、单点变更记录、逐次复测数据 |
| S4 验证 | 以同一套基准取得前后对比，判定收益与回归 | 前后对比表、噪声说明、回归结论 |
| S5 发布 | 复核关键路径指标、发布前后比对与回滚阈值 | 发布前基线快照、回滚触发条件、接受记录 |
| S6 收尾 | 对照目标评估收益，记录残留瓶颈与后续项 | 收益对照、残留瓶颈清单、后续优化项 |

## 门禁与证据

阶段表列出各阶段的出口门；本表只列本 skill 出具证据的门禁，生命周期与其他专业 skill 汇总其余证据。

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G1 立项 | 现状基线、指标口径（p50/p95/p99、稳态或突发）与“不优化”的后果 | Hold：问题与指标不可测时不得立项；缩小范围或 No-Go |
| G2 计划 | 目标与预算、基准脚本与输入集位置、测量环境、停止条件 | Recycle 到 S2：目标缺口径或基准不可复现；无预算不得进入构建 |
| G4 验证 | 前后对比数据、样本量与波动、剖析热点与改动对应关系 | Hold：环境或口径变化使数字不可比；Recycle：改动不对应热点 |
| G5 发布 | 关键路径发布前快照、回归比对结论、回滚阈值与触发条件 | Hold：关键路径无基线或回归超阈值且无接受记录；由发布负责人判定 No-Go |
| G6 收尾 | 目标达成情况、无效优化回滚记录、残留瓶颈与负责人 | Hold：复盘数据不全不得关闭；Recycle 到 S4：优化记录缺前后对比 |

优化前的基线、优化后的复测与前后对比必须使用同一脚本、同一输入与同一环境；任一条件变化，数字即不可比，不得
据此判定收益。R0 任务可以复用已有基准脚本，但不得省略复测。

## 工作流

1. 受理与分类（S0/S1）。确认请求是性能问题而非正确性问题；判定风险级别与授权，涉及生产环境时按 AU-1 第 3
   级处理；无测量请求的，先说明将建立基线而不是直接改代码。
2. 建立基线（S1/S2）。运行现有基准或新写基准，记录延迟、吞吐与内存的当前数字与口径；无脚本的，先补脚本并随
   代码提交。
3. 确定目标与预算（S2）。阈值来自项目承诺或 SLO；缺失时基于基线提出标注假设的暂定目标；写明指标口径、测量
   环境与停止条件。
4. 剖析并归类瓶颈（S3）。以 perf、pprof 或等价工具定位热点，归入 N+1 查询、不必要 IO、锁竞争、内存分配或算法
   复杂度；锁竞争的正确性问题移交 `concurrency-conventions`。
5. 单点变更并复测（S3）。每次只改一个变量，保存改动前基线，改动后立即以同一套基准重测并记录；依赖项作为一组
   落地时，记录依赖关系并保持可归因、可回滚。
6. 归因与审查（S4）。把改动对应到剖析热点，裁掉无显著收益的部分；运行“审查清单”，确认基准、目标、单点变更
   与可比性齐备。
7. 发布前复核（S5）。对关键路径取发布前快照，写明回归阈值与回滚触发条件，交由发布负责人判断。
8. 收尾（S6）。对照 G1 基线评估收益与成本，记录残留瓶颈、后续优化项与负责人；无效改动已回滚的，一并记录。

## 核心规则

- **无基准数据的，不得优化。** 实施优化前，必须存在可复现的基准；剖析用于定位热点，不能替代基线；“主观认为
  缓慢”不属于数据，禁止凭主观判断实施优化。
- **优化前后必须使用同一套基准对比。** 同一脚本、同一输入、同一环境；变更环境、输入或口径后，对比所得的数字
  无效。结论只能是“未验证，需复测”，不得以新环境的数字声称收益。
- **默认仅优化未达成性能目标的路径。** 优化对象应当对应一项未达成的目标；已达标的路径即使“还能更快”也不默认
  优化。用户明确要求，或改动用于降低风险、维护性时，可以实施，但须记录无收益预期、基准与回滚方式。
- **一次仅变更一处，变更后重新测量。** 每次变更只改动一个变量并立即重测；改动之间存在依赖的，可以作为一组
  落地，但须记录依赖关系并保持可归因、可回滚；其余多处变更将使收益无法归因。
- **先定目标或暂定目标，再优化。** 阈值与测量口径应当来自项目承诺或 SLO；没有目标的，先建立基准并提出标注
  假设的暂定目标；暂定目标不得冒充项目承诺；仅当目标会改变范围、预算或验收标准且无法从上下文推定时，才请求
  用户确认。阈值见 `references/dimensions.md` 第 2 节。
- **基准与优化脚本应当留存于仓库。** 基准脚本、输入集与结果记录随代码提交，使下一次优化能够复现对照；仅留存
  于本地的基准无法被审查或复现，也不能作为门禁。
- **优化应当以证据归因，不得以猜测归因。** 剖析结果指出热点，改动应当对应热点；没有剖析支撑的改写只能算普通
  重构，不得称为优化，也不得宣称带来收益。
- **无效的优化应当回滚。** 测量显示无显著收益的改动应回滚，不得以“反正未造成损害”为由保留；保留无效改动会
  污染代码并误导后续判断。
- **缓存与索引属于取舍。** 引入缓存前先定失效与一致性策略，命中率未经测量不得设置；索引按查询增设并权衡写入
  成本。清空缓存或删除索引后系统仍应正确，仅变慢。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 未测量即优化 | 收益无法证明，可能优化了冷路径 | 先建立基准与剖析，再实施优化 |
| 无目标地优化 | 没有停止条件，容易过度优化 | 先取得项目承诺/SLO，或基于基准提出暂定阈值 |
| 一次变更多处 | 收益无法归因，亦无法回滚 | 一次一个变量，逐个测量 |
| 前后基准不一致 | 变更环境或口径后数字不可比 | 同一脚本、同一输入、同一环境 |
| 优化已经达标的路径 | 投入没有回报，且引入新风险 | 默认仅优化未达标路径；例外须记录无收益预期与回滚 |
| 缓存没有失效策略 | 失效设计缺位的缓存将成为数据错误源 | 引入缓存前先定失效与一致性 |
| 盲目增设索引 | 每个索引均使写入付出代价，未必换取读取收益 | 按查询增设索引，权衡写入成本 |
| 以复杂度掩盖真实瓶颈 | 大 O 判断伸缩性，并不指示当前热点 | 以剖析定位热点，以复杂度判断伸缩 |
| 无收益仍保留改动 | 代码变复杂，后续判断被误导 | 测量无显著收益即回滚，并记录结论 |

## 审查清单

- [ ] 存在可复现的基准且热点已经定位；剖析结果可作定位依据，但不替代基线。
- [ ] 存在明确的延迟/吞吐/内存目标与测量口径，且阈值来自项目承诺、SLO 或标注假设的暂定目标。
- [ ] 优化对象对应一项未达标目标，或属于已记录例外。
- [ ] 优化前后使用同一套基准对比，样本量足以区分噪声，数字可比。
- [ ] 一次仅变更一处；依赖项打包时已记录依赖关系，收益可归因。
- [ ] 基准脚本与结果随代码提交，可复现；本次优化记录写明改动、前后数字与结论。
- [ ] 锁竞争已经以基准定位至具体热点，并发正确性问题已经移交 `concurrency-conventions`。
- [ ] 缓存具有失效与一致性策略，索引按查询增设且已经权衡写入成本。
- [ ] 未默认优化已经达标的路径；例外已记录基准、无收益预期与回滚方式。
- [ ] 无效的优化已经回滚，未以“未造成损害”为由保留。
- [ ] 复杂度分析用于判断伸缩性，热点以剖析定位。
- [ ] 发布前复核已取关键路径快照，写明回归阈值与回滚触发条件。

## 示例

<example>
场景：某列表接口被报告为“响应缓慢”，拟先行增设缓存。
问题：没有基准与剖析，无法确定慢点所在；增设缓存可能掩盖真正的 N+1 查询。
修复：先建立基线并运行剖析，定位到每行订单触发额外的用户查询；修复 N+1 后以同一基准重新测量。仍不达标的，
再考虑缓存，并按 G2 的预算与失效策略评估。
</example>

<example>
场景：某查询已经满足 100ms 的延迟目标，但拟“再快一点”。
问题：目标已经达成的路径，继续优化没有回报，且可能引入新风险。
修复：默认不为性能目的变更该路径，注意力保留给实际超标的路径；用户明确要求，或用于降低风险/维护性时，按例外
记录基准、无收益预期与回滚方式。
</example>

<example>
场景：一次变更同时改动序列化方式、连接池大小与索引三处，延迟下降。
问题：收益无法归因至具体改动，后续无法决定保留哪一项。
修复：拆分为三次变更，每次变更一处并重新测量；保留有据可查的改动，回滚无效的改动，并在优化记录中写明三次
复测的数字。
</example>
