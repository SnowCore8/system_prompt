# 性能规范

性能工作最大的失败不是没优化，而是没测量就优化、没有目标就优化、或优化了已经达标的路径。没有基准的优化无法证明
收益；没有目标的优化不知道何时停；一次改多处的优化无法归因。本 skill 定义如何先测量、再定目标、再优化，如何识别
常见瓶颈，以及如何让优化可判定、可回滚、可复现。它服务于建立基准与剖析的工程师、定位热点的优化者，以及审查过早
优化与无效优化的审查者。

## 适用范围与优先级

采用第一条适用的规则，同一范围内不要混用标准：

1. 强制的运行时、语言与平台约束。编译器的优化行为、运行时调度、存储引擎与网络的物理上限都不是可选项。
2. 既有性能目标、预算与已记录的基准。发明阈值之前，先读性能目标、SLO、基准脚本与历史剖析结果，以及项目已承诺的
   延迟/吞吐/内存预算。
3. 本 skill 的默认值，在前两层未作规定时适用。
4. 个人偏好，永远不能覆盖上述三层。

分工边界：

- **并发正确性属于 `concurrency-conventions`。** 锁语义、数据竞争、死锁与共享状态安全归它；锁竞争造成的吞吐
  下降与延迟升高归本 skill 定位与优化，两处不互相移交同一主题。
- **测试与门禁属于 `testing-and-quality-conventions`。** 它拥有把基准作为 CI 门禁的机制、阈值与告警策略；本 skill 拥有
  基准与剖析的方法论，不拥有运行它们的工具。
- **可观测性属于 `release-operations-conventions`。** 它拥有生产遥测、指标采集与告警；本 skill 拥有开发期的基准与剖析，
  生产环境的性能观测归它。
- **当两条规则冲突时，说明冲突与所选规则。** 把决定记录在性能目标或基准文档中，让下一次优化遵循它，而不是重炒同一个
  问题。

## 流程

1. 先测量，再判断要不要优化。建立或复现基准与剖析（perf/pprof 或等价工具），定位热点并记录数字；没有基准数据时，
   禁止动手优化。
2. 定目标与预算。为延迟、吞吐、内存与启动时间写清阈值与测量口径；目标未达成的路径才优化，已达成的不动。阈值见
   `references/dimensions.md` 第 2 节。
3. 定位瓶颈类别。按 N+1 查询、不必要 IO、锁竞争、内存分配、算法复杂度归类热点；锁竞争的性能诊断与优化归本 skill，并发正确性移交 `concurrency-conventions`。
4. 一次只改一处，改后重新测量。保存优化前的基准作为对照，用同一套基准、同一环境对比前后数字；无法对比的优化不做。
5. 审查：运行 `references/checklists.md` 中的清单，确认有基准、有目标、单一变更、前后可比，且没有优化已达标的路径。

## 核心规则

- **没有基准数据不优化。** 动手前必须先有可复现的基准或剖析结果；「感觉慢」不是数据，禁止凭感觉优化。
- **优化前后必须用同一套基准对比。** 同一脚本、同一输入、同一环境；改环境、改输入或改口径后对比的数字无效。
- **性能目标未达成的才优化，达成的别动。** 优化对象必须对应一条未达成的目标；达到目标的路径即使「还能更快」也不再
  优化，把注意力留给真正超标的路径。
- **一次只改一处，改后重新测量。** 每次变更只动一个变量，立即重新测量；同时改多处会让收益无法归因，也无法回滚。
- **先定目标再优化。** 延迟/吞吐/内存的阈值与测量口径写清之后才开始优化；没有目标就没有停止条件。
- **把基准与优化脚本留在仓库。** 基准脚本、输入集与结果记录随代码提交，让下次优化能复现对照；只留在本地的基准无法
  被审查或复现。
- **优化用证据归因，不用猜测。** 剖析结果指出热点，改动对应热点；没有剖析支持的重写是重写，不是优化。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 没测量就优化 | 收益无法证明，可能优化了冷路径。 | 先建基准与剖析，再动手。 |
| 没有目标地优化 | 不知道何时停，容易过度优化。 | 先写阈值，再优化。 |
| 一次改多处 | 收益无法归因，也无法回滚。 | 一次一个变量，逐个测量。 |
| 前后基准不一致 | 换环境或换口径后数字不可比。 | 同一脚本、同一输入、同一环境。 |
| 优化已达标的路径 | 投入没有回报，还引入新风险。 | 只优化未达标路径。 |
| 缓存没有失效策略 | 缓存一旦失效设计缺位，就变成数据错误源。 | 缓存前先定失效与一致性。 |
| 盲目加索引 | 每个索引都让写入付代价，未必换来读取收益。 | 按查询加索引，权衡写入成本。 |
| 用复杂度掩盖真实瓶颈 | 大 O 看的是伸缩性，不是当前热点。 | 剖析定位热点，复杂度判断伸缩。 |

## 审查清单

- [ ] 有可复现的基准或剖析结果，热点有定位。
- [ ] 有明确的延迟/吞吐/内存目标与测量口径。
- [ ] 优化对象对应一条未达标的目标。
- [ ] 优化前后用同一套基准对比，数字可比。
- [ ] 一次只改一处，收益可归因。
- [ ] 基准脚本与结果随代码提交，可复现。
- [ ] 锁竞争已用基准定位到具体热点，并发正确性问题已移交 `concurrency-conventions`。
- [ ] 缓存有失效与一致性策略，索引按查询且权衡了写入成本。
- [ ] 没有优化已达标的路径，没有过早优化。
- [ ] 复杂度分析用于判断伸缩性，热点用剖析定位。

## 示例

<example>
场景：某列表接口「感觉慢」，想先给它加缓存。
问题：没有基准与剖析，不知道慢在哪，加缓存可能掩盖真正的 N+1 查询。
修复：先跑剖析，定位到每行订单触发了额外的用户查询；修掉 N+1，重新测量。若仍不达标，再考虑缓存。
</example>

<example>
场景：某个查询已满足 100ms 的延迟目标，但想「再快一点」。
问题：目标已达成的路径，继续优化投入没有回报，还可能引入新风险。
修复：不改它；把注意力留给真正超标的路径，如另一个 2s 超时的报表查询。
</example>

<example>
场景：一次改了序列化方式、连接池大小和索引三处，延迟下降了。
问题：收益无法归因到具体改动，后续无法决定保留哪个。
修复：拆成三次变更，每次改一处并重新测量；保留有据可查的改动，回滚无效的改动。
</example>
