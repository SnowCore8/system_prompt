# 性能规范

性能工作最严重的失败，并非未实施优化，而是未测量即优化、无目标即优化，或优化已经达标的路径。无基准的优化
无法证明收益；无目标的优化没有停止条件；一次变更多处的优化无法归因。本 skill 规定先测量、再定目标、后优化
的程序，常见瓶颈的识别方式，以及使优化可判定、可回滚、可复现的规则。本 skill 的服务对象为建立基准与剖析的
工程师、定位热点的优化者，以及审查过早优化与无效优化的审查者。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充：

1. 强制性的运行时、语言、平台、宿主与用户全局约束。编译器的优化行为、运行时调度、存储引擎与网络的物理上
   限，均非可选事项。
2. 本 skill 的规则与默认值。
3. 既有性能目标、预算、已记录的基准与项目事实。代理不得发明阈值，应当先阅读性能目标、SLO、基准脚本与历
   史剖析结果，以及项目已承诺的延迟/吞吐/内存预算；项目约定仅在本 skill 未规定时补充，上述事实作为输入，
   依本 skill 的规则处理，不得覆盖本 skill。
4. 个人偏好不得覆盖上述三层。

分工边界如下：

- **并发正确性由 `concurrency-conventions` 管辖。** 该 skill 管辖锁语义、数据竞争、死锁与共享状态安全；锁竞
  争造成的吞吐下降与延迟升高，由本 skill 定位与优化。两者不得就同一主题相互移交。
- **测试与门禁由 `testing-and-quality-conventions` 管辖。** 该 skill 管辖将基准作为 CI 门禁的机制、阈值与告
  警策略；本 skill 管辖基准与剖析的方法论，不管辖运行它们的工具。
- **可观测性由 `release-operations-conventions` 管辖。** 该 skill 管辖生产遥测、指标采集与告警；本 skill 管
  辖开发期的基准与剖析，生产环境的性能观测由该 skill 负责。
- **两项规则冲突的，代理应当说明冲突与所选规则。** 决定应当记录于性能目标或基准文档，使下一次优化遵循该
  决定，避免重复争论同一问题。

## 流程

1. 先测量，再判断是否应当优化。代理应当建立或复现基准与剖析（perf/pprof 或等价工具），定位热点并记录数
   字；无基准数据的，禁止实施优化。
2. 确定目标与预算。阈值与测量口径应当来自项目承诺或 SLO；无目标的，代理应当停止并请求目标，不得臆造。仅
   应优化未达成目标的路径；已达标的路径不得为性能目的变更。阈值见 `references/dimensions.md` 第 2 节。
3. 定位瓶颈类别。代理应当按 N+1 查询、不必要 IO、锁竞争、内存分配与算法复杂度归类热点；锁竞争的性能诊断
   与优化由本 skill 管辖，并发正确性移交 `concurrency-conventions`。
4. 一次仅变更一处，变更后重新测量。代理应当保存优化前的基准作为对照，以同一套基准、同一环境对比前后数
   字；环境、输入或口径不一致的，不得判定收益，结论为未验证并需复测；无法对比的优化不得实施。
5. 审查。代理应当运行本文件的“审查清单”，确认存在基准、存在目标、变更为单一变更、前后可比，且未优化已
   经达标的路径。

## 核心规则

- **无基准数据的，不得优化。** 实施优化前必须存在可复现的基准；剖析用于定位热点，不能替代基线；“主观认
  为缓慢”不属于数据，禁止凭主观判断实施优化。
- **优化前后必须使用同一套基准对比。** 同一脚本、同一输入、同一环境；变更环境、输入或口径后对比所得的
  数字无效。
- **仅应优化未达成性能目标的路径；已达标的路径不得为性能目的变更。** 优化对象必须对应一项未达成的目标；
  达到目标的路径即使“还能更快”也不再优化，注意力应当保留给实际超标的路径。
- **一次仅变更一处，变更后重新测量。** 每次变更仅应变更一个变量，并立即重新测量；一处依赖另一处方能生效
  的，可作为一组变更落地，但须记录依赖并保持可归因、可回滚；其余多处变更将使收益无法归因。
- **先定目标，再优化。** 阈值与测量口径应当来自项目承诺或 SLO；无目标的，应当停止并请求目标，不得臆造；
  无目标即无停止条件。
- **基准与优化脚本应当留存于仓库。** 基准脚本、输入集与结果记录应当随代码提交，使下一次优化能够复现对
  照；仅留存于本地的基准无法被审查或复现。
- **优化应当以证据归因，不得以猜测归因。** 剖析结果指出热点，改动应当对应热点；无剖析支持的重写属于重
  写，不属于优化。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 未测量即优化 | 收益无法证明，可能优化了冷路径。 | 先建立基准与剖析，再实施优化。 |
| 无目标地优化 | 没有停止条件，容易过度优化。 | 先取得项目承诺或 SLO 中的阈值，再实施优化。 |
| 一次变更多处 | 收益无法归因，亦无法回滚。 | 一次一个变量，逐个测量。 |
| 前后基准不一致 | 变更环境或口径后数字不可比。 | 同一脚本、同一输入、同一环境。 |
| 优化已经达标的路径 | 投入没有回报，且引入新风险。 | 仅优化未达标的路径。 |
| 缓存没有失效策略 | 失效设计缺位的缓存将成为数据错误源。 | 引入缓存前先定失效与一致性。 |
| 盲目增设索引 | 每个索引均使写入付出代价，未必换取读取收益。 | 按查询增设索引，权衡写入成本。 |
| 以复杂度掩盖真实瓶颈 | 大 O 判断伸缩性，并不指示当前热点。 | 以剖析定位热点，以复杂度判断伸缩。 |

## 审查清单

- [ ] 存在可复现的基准且热点已经定位；剖析结果可作定位依据，但不替代基线。
- [ ] 存在明确的延迟/吞吐/内存目标与测量口径，且阈值来自项目承诺或 SLO。
- [ ] 优化对象对应一项未达标的目标。
- [ ] 优化前后使用同一套基准对比，数字可比。
- [ ] 一次仅变更一处；依赖项打包时已记录依赖关系，收益可归因。
- [ ] 基准脚本与结果随代码提交，可复现。
- [ ] 锁竞争已经以基准定位至具体热点，并发正确性问题已经移交 `concurrency-conventions`。
- [ ] 缓存具有失效与一致性策略，索引按查询增设且已经权衡写入成本。
- [ ] 未优化已经达标的路径，不存在过早优化。
- [ ] 复杂度分析用于判断伸缩性，热点以剖析定位。

## 示例

<example>
场景：某列表接口被报告为“响应缓慢”，拟先行增设缓存。
问题：没有基准与剖析，无法确定慢点所在；增设缓存可能掩盖真正的 N+1 查询。
修复：先建立基线并运行剖析，定位到每行订单触发额外的用户查询；修复 N+1 后以同一基准重新测量。仍不达标的，再考虑缓存。
</example>

<example>
场景：某查询已经满足 100ms 的延迟目标，但拟“再快一点”。
问题：目标已经达成的路径，继续优化没有回报，且可能引入新风险。
修复：不得为性能目的变更该路径；注意力应当保留给实际超标的路径，例如另一项 2s 超时的报表查询。
</example>

<example>
场景：一次变更序列化方式、连接池大小与索引三处，延迟下降。
问题：收益无法归因至具体改动，后续无法决定保留哪一项。
修复：拆分为三次变更，每次变更一处并重新测量；保留有据可查的改动，回滚无效的改动。
</example>
