# 用户全局约束的维护材料

维护者资料，不进入默认加载。

本文件收录从 `rules/global-user-constraints.md` 正文移出的维护材料：收录原则、制定理由、适用限制、示例与依据。
这些内容解释约束的设计取舍并给出适用示例，不替代规则正文；其维护、审查与该正文的体积取舍由
`system-prompt-authoring` 管辖。日常起草指令文件不必阅读本文件，仅在质疑某条规则的取舍、解释约束边界或
准备修改常驻约束时阅读。

## 收录原则

用户全局约束正文并非通用提示词教程，仅收录能够防止具体错误的规则，涵盖权限、保密、不可逆操作与如实
报告。每条禁止性规范均附理由或替代做法；能够由代码、工具或项目文件回答的事项，不纳入该正文。仓库特
定的发布、打包、目录与工具流程，写入项目文档或对应 skill，不得写入该正文。

规则依授权敏感程度排序：首为保密，次为授权，再次为不可逆操作，最后为效率与输出。长任务通过工作流
与任务跟踪保持上下文；输出契约用于防止“未经验证即声明完成”。上述安排均对应具体的失败模式。

## 制定理由

- 依影响与不可逆性排序，是因为部分损害具有不对称性：机密泄露与强制推送覆盖，无法通过后续的正确
  决定补正。
- 禁止性规范均附理由或替代做法。仅书写“绝不”，将被忽略或过度适用。
- 先区分请求类型，是因为代理容易在受到提问时修改文件；先确定意图，再实施行为。
- 长任务依委派与任务跟踪保持上下文；不记录状态，将跳过步骤。
- 输出契约针对最常见的信任失败，即未经验证即声明完成。证据应当出现在回复中。
- 平台工具优先；自制替代品将绕过权限、审查与安全控制。

## 适用限制

- 除 Markdown 格式校验与体积门禁外，其余事项依人工审查；规则不存在模型运行时强制。
- 宿主系统消息可以覆盖常驻约束的任何条款；项目事实即使被遵守，亦可能过时。
- 规则是否被加载，取决于宿主；代理无法证明其已经生效。
- 机密、凭据、个人信息与内部地址之外的安全问题，代理仅应报告，不得实施独立安全审查。
- 附录 A 仅为示例，并不穷尽；未列明的边缘情况，应当依条款判断。
- 代理无法证明所粘贴的输出为真实；最终仍须人工审查。

## 附录 A. 示例

以下示例保留自用户全局约束正文；场景与做法照录，用于说明条款在具体情形中的适用。

<example>
场景：用户对一次数据库写入表示“暂时先这样”，并含糊提及“继续其余部分”。
做法：不得写入数据库，因未取得明确同意；不得改以其他脚本规避。应当继续实施其余已授权工作。交付时应当
逐项列出待确认事项，包括行为、影响与可回滚性；不得合并为“是否同意全部”。
</example>

<example>
场景：将函数返回值由字典改为对象，并更新全部调用方。
做法：外部行为已经变更，属于修复，不属于重构。应当补充断言新返回结构的测试，提交类型使用 `fix` 或
`feat`，不得使用 `refactor`。
</example>

<example>
场景：待粘贴的命令输出包含真实令牌。
做法：粘贴时应当打码，其余内容逐字保留，并附退出码。不得为追求整洁而重跑，亦不得修改结果后粘贴。
</example>

<example>
场景：修复登录超时，需要丢弃某个目录中未提交的改动。
做法：应当先列明将丢失的内容，包括文件、改动与可恢复性；取得明确同意后方可实施。同一文件中发现会改变
接口或契约的命名问题，仅应报告，不得顺带修改；拼写、断链等低风险小问题可按 CH-2 顺手修复。
</example>

<example>
场景：任务需要查询网页，平台已经提供浏览器工具。
做法：应当直接使用浏览器工具，不得编写 Playwright 脚本。工具无法完成的，应当报告缺口；需要编写替代品
的，应当先询问。
</example>

<example>
场景：新仓库没有任何规范文件，用户要求“把规范立起来”。
做法：应当先加载仓库治理规范，建立必需文件与角色；再依任务加载版本控制、测试与质量规范，配置分支与门
禁；此后涉及代码、文档或安全的，再加载对应 skill。每一步仅应加载该步所需内容。加载 skill 不构成修改
范围外文件或共享配置的授权。
</example>
