# PR 与代码审查

## 1. PR 与审查
- 一个请求承载一个逻辑变更：重命名、格式化等机械性改动与行为变更分开提交，使每部分都能独立审查与回退。
- 标题说明结果，描述说明问题、做法、风险与验证证据，并链接关联条目与推迟的后续工作。
- 校验未通过、自审未完成时保持草稿状态；草稿不进入合并审查。
- 必需校验全部在合并结果上通过、自审完成并填写模板后，才标记为就绪。
- 生成文件与第三方引入文件应重新生成并审查生成器输入；手工修改生成产物不视为经过审查。

## 2. 代码审查

- 审查深度取决于风险：认证、支付、权限、数据迁移与公共接口适用高风险路径并配置第二名审查者。
- 每条评论标注级别：阻塞、非阻塞、Nit 或疑问；作者以回复或关联修复解决每个阻塞项，沉默不构成同意。
- 实质性推送使先前批准过期，必须重新审查增量；批准仅对批准时的提交有效。
- 机器人执行门禁，人实施判断：可判定的项自动化（构建、测试、lint、类型、机密扫描），判断性项（正确性、设计取舍、测试充分性）由人实施。
- 单人仓库或无第二人的，必需批准设为 0，以自审记录与必需 CI 替代，并把该缺口记录于治理文件。
