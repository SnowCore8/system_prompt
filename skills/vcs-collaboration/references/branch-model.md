# 分支模型与分支生命周期

## 1. 分支模型

- 从发布流程允许的最轻模型中选择：较轻指分支类别更少、每类一种合并方式、发布与热修复路径更短。
- 主干开发（无发布分支）：小型团队与单一可部署服务，压缩合并进主干，发布即主干上的标签，依赖功能开关与强 CI。
- 主干开发带发布分支：冻结时从主干切出，发布提交打标签，热修复在发布分支上做并向前移植到主干。
- 发布列车：按计划发布、长 QA 或多个受支持版本，候选分支晋级用合并提交，修复走 cherry-pick 并移植。
- fork-and-pull：公开仓库或无写权限的贡献者，维护者审查后快进或压缩合并。
- 模型的选择、日期与下次复查的触发条件写入贡献者指南，并在平台设置中强制执行。

## 2. 分支生命周期

- 每个分支只承载一个逻辑变更；体量超出预算的拆成堆叠分支或以功能开关隐藏。
- 可审查 diff 预算约 400 行；400 至 800 行的记录设计说明并配置第二名审查者；无法拆到开关之后的变更属于设计信号，不构成例外。
- 主题分支应在三个工作日内集成；存续更久的每日变基到主干。
- 已合并的主题分支即删除，使分支列表只反映未完成工作。
- 每类分支只用一种合并方式：功能分支压缩合并，发布晋级用合并提交，仅对未共享的分支变基。
- 已发布的错误以 revert 或后续提交修复；不重写他人已在其上开展工作的提交。
