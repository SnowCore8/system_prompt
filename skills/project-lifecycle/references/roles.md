# 角色与决策权

## 1. 角色与决策权
角色解决“谁对结果负责”，决策权解决“谁能说不”。只有角色没有权限，门禁会退化为状态汇报；只有权限
没有责任，风险会被推给下一位执行者。角色可以兼任，但 R2 门禁的独立审查与批准不得由执行者兼任。

| 角色 | 核心职责 | 主要产出 | 典型决策 |
|---|---|---|---|
| 发起人 | 提供目标、资源与组织授权 | 章程批准、资源承诺 | 是否立项、是否继续投资 |
| 组合委员会 | 在组合层排序与分配容量 | 组合登记、投资决定 | Go/No-Go/Defer、优先级 |
| 产品负责人 | 定义需求、用户价值与验收 | 结果指标、待办、验收结论 | 验收标准、优先级、范围取舍 |
| 项目负责人 | 组织计划、执行、风险与门禁 | 计划、风险登记、门禁记录 | 计划取舍、风险升级、门禁准备 |
| 架构负责人 | 维护边界、关键技术决策与 ADR | 架构方案、ADR、例外建议 | 架构方案、技术例外 |
| 交付团队 | 实现、测试、文档、评审与集成 | 可运行增量、测试、文档 | 技术方案、任务拆分、DoD 自检 |
| 质量 / 审查 | 定义质量策略与验证证据 | 测试策略、验证结论 | G4 质量结论、返工要求 |
| 安全 / 合规 | 识别威胁、隐私、许可证与供应链风险 | 安全评估、例外记录 | 安全门禁、例外建议 |
| 运营 / SRE | 保障发布、运维、回滚、可观测性与值守 | 发布记录、回滚演练、事故复盘 | G5/G6 发布与运维准备度 |
| PMO | 维护流程、门禁日历、模板与度量 | 日历、模板、组合数据 | 流程支持与数据质量 |
| 主智能体 | 受理、计划、任务树、执行、验证与交付 | 任务树、证据、交付说明 | 授权范围内的技术取舍 |
| 子智能体 | 执行被分配的独立工作流 | 局部改动、测试、报告 | 其边界内的实现选择 |
| 人工批准者 | 对 R2、生产、安全例外与不可逆操作作决定 | 明确同意或拒绝 | 逐次批准、条件与到期日 |

角色清单不要求每个项目都设专职人员。小项目可以合并角色，但必须明确谁承担发起、验收、质量、安全与运营
责任；不能因为“人少”而让执行者同时批准自己的高风险变更。

## 2. 决策权矩阵

| 事项 | 建议者 | 决定者 | 必须咨询 | 记录 |
|---|---|---|---|---|
| 风险级别 | 项目负责人 | 项目负责人；R2 由发起人确认 | 安全、架构、运营 | 受理记录 |
| 范围与验收 | 产品负责人 | 产品负责人；R2 由发起人确认 | 项目负责人、质量 | 计划基线 |
| 架构与关键技术 | 架构负责人 | 架构负责人；R2 需独立评审 | 安全、交付团队 | ADR |
| 测试策略与质量门禁 | 质量负责人 | 质量负责人 | 交付团队、运营 | 测试策略 |
| 安全例外 | 安全负责人 | 发起人或授权委员会 | 项目负责人、法务（如需） | 例外记录 |
| 发布准备度 | 运营负责人 | 运营负责人；R2 由发起人批准 | 质量、安全、产品 | 发布记录 |
| 收益与退出 | 产品负责人 | 发起人或组合委员会 | 项目负责人、运营 | 收尾报告 |
| 流程与模板 | PMO | 维护者 | 项目负责人 | 流程文档 |

矩阵中的“决定者”是批准角色，不是会议规模。决定必须在门禁记录中留痕；没有记录的决定视为未发生。建议者
与决定者可以是同一人，但 R2 的独立审查、生产批准与安全例外不得由执行者自批。

## 3. 独立性与利益冲突

- 独立审查者不得是增量作者、同一子智能体的调用者，或直接依赖该变更交付的人。
- R2 的架构、安全与合规结论至少有一项来自交付团队之外；无法满足时，升级为 Hold。
- 审查者发现自身存在利益冲突、缺乏专业能力或时间不足时，应当回避并推荐替代者，不得出具形式审查。
- 智能体可以收集证据、起草结论与检查清单，但不得冒充人工批准者，也不得把用户的沉默解释为同意。
- 例外批准必须写明补偿控制、到期日与复核人；批准者不得同时是例外的执行者。

## 4. 智能体与人工的分工

智能体任务中，用户承担发起人与产品负责人，主智能体承担项目负责人，子智能体承担交付团队。这个映射只
转移执行与记录职责，不转移不可替代的人类决定：

- 生产部署、生产数据写入、凭据轮换、不可逆删除与共享配置变更需要人类逐次明确同意（AUT-1 第 3 级）。
- R2 门禁、安全例外、合规判断与最终验收需要人类批准。
- 智能体可以建议风险级别与门禁决定，但必须说明依据、证据与替代方案。
- 用户不在场时，智能体只能推进可逆、已授权的本地工作；需要批准的事项保持 Hold。

## 5. 升级路径

升级不是失败，而是把超出权限或证据不足的事项交给有权限的人。触发条件包括：风险级别上升、关键依赖未
确认、连续两次 Recycle、同一风险超过复审日期、证据冲突、出现安全或不可逆风险、角色缺位。升级记录至少
写明：未解决项、已尝试方案、影响、可选决定、建议与最晚决定时间。升级期间停止受影响的工作，可以并行
处理不受影响的任务；不得用“等待回复”掩盖停滞。
