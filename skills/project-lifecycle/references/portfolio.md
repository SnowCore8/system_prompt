# 依赖治理

## 1. 依赖治理

依赖分为技术、数据、团队、供应商与合规五类。每个依赖登记：提供者、消费者、接口、数据、交付窗口、验证
方式、负责人、失败回退与升级路径。依赖图在 G1/G2 建立，在 G3 检查，在 G4 前确认，在 G7 交接。

- 提供者未书面确认依赖时，相关门禁不得判为 Go，只能选择 Hold 或 Recycle；预计时间不构成承诺。
- 跨团队接口必须有契约与验证责任；口头承诺不构成依赖确认。
- 共享数据库、共享环境、共享发布窗口与共享凭据必须有单一负责人。
- 依赖延迟时，先评估替代方案、缩小范围或调整顺序；不得静默挤压测试与安全。
- 依赖变化触发风险重评与计划更新；受影响的门禁重新评审。

## 2. 受理漏斗与排序

组合治理解决“做哪些、先做哪些、什么时候停”。项目层解决“如何交付”，组合层解决“是否值得继续投入”。
两者共用阶段与门禁编号，但组合层使用 Defer 管理队列，项目层使用 Hold、Recycle 与 No-Go。

| 层级 | 目的 | 最小记录 | 决定 |
|---|---|---|---|
| 想法 | 收集问题与机会 | 问题、提出者、初步价值 | 进入评估或丢弃 |
| 评估 | 判断价值、风险与容量 | 用户、收益假设、粗略成本、风险 | 进入立项或暂缓 |
| 立项 | 形成商业论证与交付选项 | 收益基线、选项、依赖、容量 | Go/No-Go/Defer |
| 交付 | 按项目生命周期执行 | 章程、计划、门禁记录 | 继续、转向或停止 |
| 收益 | 对照基线评估结果 | 收益、成本、偏差、教训 | 关闭、扩展或移交 |

排序依据至少包括：战略契合、用户价值、收益确定性、风险、依赖、容量、学习价值与退出成本。排序不是一次
性的；每季度或当外部条件变化时重新评估。不得只按提出者职位、先来后到或声音大小排序；不得用“已经投入
很多”作为继续的理由；不得在容量不足时承诺日期。高不确定性提案先做小规模验证，不以完整交付作为学习
成本。

## 3. 组合门禁与节奏

组合层在 G0/G1/G2/G5 做投资与优先级决定，在 G7 确认收益与退出。组合门禁可以复用项目证据，但不得替代
项目门禁；项目仍需保留完整记录。组合节奏通常按月或按季度：

- 月度：审查在途项目、依赖、风险与容量；处理 Hold 与升级。
- 季度：重排优先级、评估收益、决定继续、缩小、转向或退出。
- 按需：重大外部变化、事故、合规要求或关键依赖失效时召开临时评审。

组合决定使用 Go/No-Go/Defer；项目层使用 Hold/Recycle/No-Go。组合层不得代替项目负责人批准技术方案，
也不得绕过安全、授权与不可逆约束。

## 4. 容量与瓶颈

容量包括人员、预算、环境、审查、运维与支持能力。组合层应当维护容量视图，识别瓶颈在开发、审查、环境、
发布还是运营。瓶颈不在开发时，增加开发吞吐只会扩大在制品与等待时间。

- 在制品超过容量时，先完成、评审或清理，不启动新项目。
- 关键角色只有一个可维护者时，登记知识集中度风险，并安排交接或备份。
- 环境与数据准备是交付前置条件，不得假设随时可用。
- 审查与运维容量应当计入计划；没有审查容量的日期承诺不成立。
- 容量变化时重新排序，不通过加班或降低质量吸收长期缺口。

## 5. 退出、移交与收益

项目退出是正常治理结果，不是失败。退出条件包括：收益实现、目标不再成立、风险不可接受、成本超过收益、
外部要求变化或出现更优替代。退出决定必须写明：

- 已实现与未实现的收益，以及对照基线的偏差。
- 代码、数据、制品、环境、访问权限与文档的处置或移交。
- 用户、依赖方与运营的通告与支持安排。
- 未关闭风险、缺陷与行动项的负责人和到期日。
- 合同、许可证、供应商与合规义务的结束方式。

移交必须有接收方确认与运行责任；不得留下无主服务、无主数据或无主接口。收益评估在退出后按约定周期复核，
不能只在项目结束时看一次。收益未实现时，分析假设、执行与环境原因，决定继续、转向或关闭；不得用活动量
替代收益。
