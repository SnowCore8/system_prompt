# 门禁决定

## 1. 门禁决定
门禁是阶段之间的承诺点。每个门禁只回答一个问题：现有证据是否足以承担下一阶段的风险。证据不足时，
正确的决定是 Hold 或 Recycle，而不是用计划、口头保证或“应该没问题”补位。门禁决定只有六种：

- **Go**：证据满足当前门禁，进入下一阶段。Go 不构成对后续不可逆操作的授权；需要逐次明确同意的行为仍须
  逐次同意（AUT-1 第 3 级）。
- **Conditional Go**：主体工作可继续，但附有条件。条件必须可验证、有负责人与到期日，并写明关闭证据；
  条件不得是当前门禁本应完成的证据。
- **Hold**：证据缺失或外部依赖未就绪。Hold 期间不得推进受影响的工作，可以并行处理不受影响的任务。
- **Recycle**：退回指定阶段返工。记录必须写明返工项、重新评审的门禁与影响范围；不得只写“再改改”。
- **No-Go**：停止、关闭或转向。记录理由、已产生成本、剩余资产与归档方式；不得把 No-Go 伪装成延期。
- **Defer**：仅用于组合层，把提案放回队列。项目层不得用 Defer 替代 Hold、Recycle 或 No-Go。

## 2. 门禁矩阵

| 门禁 | 要回答的问题 | 最低证据 | 不通过时 |
|---|---|---|---|
| G0 受理门 | 请求、授权、风险与停止条件是否清楚？ | 请求复述、授权依据、风险级别、停止条件、负责人 | 澄清或 Hold；不得先做一点 |
| G1 立项门 | 需求是否真实，是否值得做？ | 需求与用户、结果指标、收益基线、选项比较、初步安全与隐私判断 | Recycle 到 S1 或 No-Go |
| G2 计划门 | 范围、方案、验收与回滚是否成立？ | 范围与非范围、验收标准、设计或 ADR、任务拆分、测试策略、风险登记、回滚计划 | Hold 或 Recycle；不得带缺口构建 |
| G3 构建门 | 增量是否可运行、可验证、可回滚？ | 可运行增量、相关测试、评审结论、DoD 检查、文档更新 | Recycle 到 S2 或 S3；不得以“后面补测试”通过 |
| G4 验证门 | 是否满足验收与质量要求？ | 测试输出、安全与合规结论、性能与并发证据、验收结论、独立审查 | Recycle 到构建或 Hold；不得删除测试或弱化断言 |
| G5 发布门 | 能否安全上线并回滚？ | 版本与制品、CI/CD 记录、回滚演练、可观测性、通告、生产授权 | Hold；不得以“先上线再看”通过 |
| G6 运维门 | 服务是否可观测、可恢复、有人值守？ | 监控告警、值守升级、恢复演练、事故记录与改进项 | Recycle 到运维；不得无人值守上线 |
| G7 收尾门 | 是否产生价值，是否留下证据？ | 收益对照、偏差、复盘行动、退役与归档、交接、未关闭风险 | 继续整改或转为运维改进 |

批准角色按风险级别取：R0 由执行者自检并记录；R1 由项目负责人批准，G2/G3/G4 至少一名独立审查者；
R2 由发起人或组合委员会批准，G2 增加架构与安全评审，G4 增加独立验证，G5 增加运营与安全批准。R1 的
独立审查者不得是增量作者；R2 的安全与合规结论不得由交付团队自行出具。角色是决策权归属，不是会议
规模；详细权限与升级见第 4 节。

## 3. 证据标准

可接受的证据：

- 测试命令与真实输出、退出码、覆盖率或等价质量数据。
- 审查记录、签字、批准邮件或平台审批记录。
- 压测、故障注入、回滚演练与恢复验证记录。
- 安全扫描、依赖审计、许可证与 SBOM 结论。
- 监控截图、指标查询链接、发布与部署记录。
- 收益基线、结果指标与对照数据。

不可接受的证据：

- 计划中的工作、未运行的测试、他人的口头保证。
- “通常会通过”“应该没问题”“和上次一样”。
- 只有文档描述、没有执行记录的验证。
- 由执行者自行出具并自行批准的 R2 安全结论。

## 4. 决策权限与升级

- R0：执行者自检并记录；涉及安全、凭据、生产或不可逆时立即升级为 R1/R2。
- R1：项目负责人批准；G2/G3/G4 至少一名独立审查者；跨模块或依赖变更增加对应模块负责人。
- R2：发起人或组合委员会批准；G2 增加架构与安全评审；G4 增加独立验证；G5 增加运营与安全批准。
- 连续两次 Recycle 或同一风险超过复审日期未处理时，升级到更高决策层；升级记录写明未解决项与可选方案。
- 智能体不得代替人工批准 R2 门禁，也不得把用户的沉默视为批准。

## 5. 门禁记录

每次门禁至少记录：门禁编号与阶段名、日期与负责人、风险级别与依据、证据链接、决定、条件（负责人、
到期日与关闭证据）、下一门禁。记录应当可被未参与评审的人复核；没有记录的决定视为未发生。记录只追加，
不覆盖；纠错以新增记录说明，不得改写已作出的决定。

## 6. 紧急路径

- 服务中断、数据损坏、漏洞正在被利用或凭据确认泄露时，按 AUT-5 先实施最小止损，再报告。
- 止损后补 G0/G4/G5 记录，写明当时已知事实、采取的动作、影响范围与后续验证；不得改写时间线。
- 紧急发布不豁免 G4；无法完整验证时，记录未验证部分、风险接受人与回滚条件。
- 事故复盘按 S6 执行；复盘行动项进入待办并指定负责人与到期日。

## 7. 例外与豁免

例外是对规则的具名偏离，不是对门禁的跳过。任何例外必须写明：适用对象、范围与期限（到期自动失效）；
理由、影响、替代方案与不批准时的后果；补偿控制、监控方式与回滚条件；批准人、记录人与复核日期。与安全、
授权、不可逆或合规相关的例外，必须由对应负责人批准。智能体不得自批例外，不得把例外写成项目约定；例外
关闭时记录实际结果与遗留风险，未关闭的例外进入风险登记并在下一次门禁复核。

## 8. 门禁反模式

| 反模式 | 表现 | 纠正 |
|---|---|---|
| 默认通过 | 没人反对就 Go | 明确记录决定、证据与责任人 |
| 条件堆积 | Conditional Go 条件长期不关闭 | 到期复核，未关闭转 Hold |
| 证据替代 | 用会议纪要或计划代替测试输出 | 只接受可复核证据 |
| 权限漂移 | 执行者逐步获得自批权 | 按角色矩阵重新确认，R2 独立审查 |
| 例外常态化 | 同一例外反复延期 | 分析根因，修改规则或停止工作 |
