# 敏捷迭代

## 1. 敏捷迭代
DoR 决定什么条目可以进入迭代，DoD 决定什么增量算完成；两者是 G3/G4 的最低证据，不是团队自愿声明。

Definition of Ready，条目进入迭代前必须满足：

- 结果与用户价值清楚，验收标准可判定。
- 依赖已识别，外部依赖有可用时间或替代方案。
- 负责人、估算与风险级别已确定。
- 测试方式与所需环境已明确。
- 回滚或退出方式已明确。
- 设计决策达到可实施程度；未决的架构问题先过 G2。

Definition of Done，增量交付时必须满足：

- 实现可构建、可运行，代码已合并或处于可合并状态。
- 相关测试已编写并通过；未运行项明确标注。
- 文档、运行手册与变更记录同步。
- 安全、依赖、许可证与隐私检查完成。
- 独立审查通过；审查意见已处理或明确接受。
- 发布说明、迁移与弃用说明已准备。
- 已知缺陷有处理结论，阻塞级缺陷为零。

裁剪 DoD 必须说明理由、风险与补偿控制，并由相应风险级别的角色批准；未满足 DoR 的条目留在待办，强行
进入迭代会把不确定性转成返工。

## 2. 待办与排序

敏捷不是省略治理的理由。迭代把大块工作拆成短反馈循环，使问题在成本较低时暴露；门禁保留承诺与风险的
决策点。分工是：门禁决定“是否继续投入”，迭代决定“如何交付并学习”。

- 待办按价值、风险、依赖与学习速度排序；不得只按提出者职位或先来后到排序。
- 每个条目写清结果、验收标准、依赖、负责人、估算、风险级别与回滚方式。
- 大条目在进入迭代前拆分；拆分后仍应保留端到端可验收的增量，不得只交付技术层。
- 待办顶部保持清晰目标；目标外的插入须重新评估 WIP 与承诺。
- 缺陷、事故与安全问题可以插队，但必须记录对原目标的影响；不得静默挤压测试与文档。

## 3. 迭代节奏与 WIP

| 场景 | 迭代长度 | 评审 | 回顾 |
|---|---|---|---|
| 人类团队 | 一至两周 | 每个迭代末演示增量并收集反馈 | 每个迭代或每两个迭代 |
| 多智能体任务 | 一次可验收增量 | 集成前由领导者评审 | 任务结束后简短回顾 |
| 单智能体小任务 | 一次交付 | 自检加自动化验证 | 仅在出现意外或返工时 |

- 迭代开始前确认目标、容量与依赖；迭代中控制 WIP；迭代结束展示可运行增量，而不是完成百分比。
- 每个执行者同时进行的条目数设上限；到达上限时先完成、评审或清理，不启动新条目。
- 阻塞项单独标记，写明阻塞原因、责任人与解除条件；超过复审时间升级。
- 未完成的条目回到待办，不得用“完成了 80%”作为交付。

## 4. 评审与回顾

评审：

- 展示可运行增量与验收结果，不以幻灯片代替功能。
- 收集用户、运营、安全与维护者的反馈；反馈进入待办并排序。
- 对照 G2 的验收标准逐项确认；未通过项写明修复或接受理由。

回顾：

- 讨论什么有效、什么无效、意外是什么、下一次改变什么。
- 每次最多保留三到五项行动，每项有负责人、到期日与验证方式。
- 行动进入待办；下一次回顾先检查上次行动的关闭情况。
- 事故复盘与迭代回顾分开：事故复盘关注事实、根因与系统性改进，不追究个人。

## 5. 多智能体迭代

- 领导者智能体维护迭代目标、任务树、集成队列与证据；协作者只在分配的工作树或目录内写入（EXE-16）。
- 每个工作树从已提交基线创建；依赖、端口、数据库与缓存隔离；集成前先同步基线。
- 迭代目标按可验收增量定义，不按文件数或提交数定义；协作者交付提交、测试与交接说明。
- 集成顺序按依赖排序；冲突由领导者处理，协作者不得直接改写他人工作树。
- 每个增量至少一次独立复核；高风险变更增加专业 skill 或人工审查。
- 工作树清理、恢复与强制移除按 AUT-1、IRR-1、IRR-6 与 `vcs-collaboration` 执行。
