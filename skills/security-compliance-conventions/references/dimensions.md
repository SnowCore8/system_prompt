# 安全与合规维度

本文件与 `SKILL.md` 配合使用。每一节覆盖本规范的一个维度：项目采用的控制措施、每项控制措施所防止的失效，
以及审查人期望的证据。应当阅读与本次变更匹配的一节；项目首次安全审查之前、编写 `SECURITY.md` 内容时，或
建立数据清单时，应当阅读全部五节。下列规则为团队所采用的默认值，不构成法律结论：决定取决于法律条文、合同
或司法管辖区的，应当将问题交由法务，并连同负责人记录答复。

## 1. 安全开发

安全首先是设计的属性，其次才是扫描的属性。功能跨越信任边界、出现新接口、新权限或新数据类别、依赖进入构建
时，应当适用本维度；产出为威胁模型说明、代码中的控制措施与审查记录。

- **对每个功能实施轻量威胁建模。** 应当以 30-60 分钟撰写一页说明：资产及其价值、入口点、信任边界、滥用
  场景、现有控制措施、残余风险与负责人。不跨越任何边界的功能，应当记录一行说明。入口点、数据类别或信任
  边界变化时，应当更新该说明；首版留下的模型仅能够证明历史，无法证明当前设计。
- **选择安全默认值。** 拒绝、私有、关闭与认证的默认值见 `SKILL.md` 核心规则「默认拒绝并失效关闭」。应当设置安全的 cookie 标志，要求 TLS，将 CORS 限制至具名来源，启用速率限制，并在生产环境关闭调试输出与详细错误。忘记配置系统的运维者也必须得到安全行为，而非暴露行为。
- **在每个边界校验。** 应当在服务端校验允许列表中的类型、长度、范围、格式与编码；先规范化，再校验；限制
  请求体与上传大小；按内容而非扩展名校验文件类型；在敏感端点上拒绝未知字段。服务端根据用户输入发起出站
  请求的，应当以允许列表防止服务端请求伪造。客户端校验仅为便利，修改请求即可绕过。
- **按上下文编码输出。** 应当分别对 HTML 文本、属性、JavaScript、CSS、URL 与 shell 参数编码；依赖框架
  自动转义，不得手工转义；对 SQL 使用参数化查询或 ORM；不得将用户输入传给 `eval`、动态 import 或 shell
  字符串。同一值在文本节点中可能安全，在属性或 URL 中可能不安全，因此编码方式由输出位置决定，不由来源
  决定。
- **认证与授权应当分离。** 认证确认调用者身份；授权决定调用者可以触及的对象与操作。每个请求均须在服务端
  执行该决定，包括直接 API 调用与内部服务调用；在查询中按租户过滤；记录拒绝日志；对管理操作、权限变更与
  销毁性操作要求更强的认证因素。将控件隐藏于界面中不构成授权边界。
- **控制依赖与供应链。** 新增依赖之前，应当检查维护活跃度、已知漏洞、许可证、传递依赖数量、原生代码与
  安装脚本；固定、来源审查与安装脚本规则见 `SKILL.md` 核心规则「依赖应当视为待分发的代码」。应当自动
  生成更新，测试通过后再合并；删除未使用的依赖；自最小容器镜像重建；在生态支持时验证签名或来源证明（如
  SLSA 证明），使制品能够追溯至经审查的源码与构建配置。包名仅差一个字符即构成一种可用的攻击。
- **依赖漏洞扫描应当设为合并门禁。** 应当在 PR 与夜间对解析后的依赖树运行漏洞扫描。门禁的阻塞条件与各语言
  生态（Go、Rust、Java、C# 等）的阈值只在 `testing-and-quality-conventions` 的依赖门禁文件中定义，
  本维度不重复，以免两处阈值分叉。本维度管辖严重程度与修复期限：严重 7 个自然日、高危 30 个自然日、中危 90
  个自然日、低危取 180 个自然日与下一个计划的小版本中的先到者（起算点见第 5 节）。无修复方案或不可利用的发现，按 `SKILL.md` 核心规则执行 VEX 评估、豁免与到期管理；不可利用的传递依赖不应当无限期阻塞发布。扫描命令、位置与门禁失败行为同样由测试与质量角色的 gates 定义。
- **合并前应当按触发条件分派安全审查。** 涉及认证或权限、密码学、支付、文件处理、新外部接口、管理工具、
  个人数据字段、处理者、基础设施身份或网络规则、反序列化、机密处理以及新增原生依赖的变更，均要求审查。
  审查人与决定应当记录于变更中；部署之后实施的审查属于事件审查，不构成门禁。
- **安全债务应当设定到期日并跟踪。** 每个已接受风险均须具备登记册条目：描述、影响、负责人、补偿性控制
  措施、审查日期与跟踪标识符。至少每季度以及在所有权变更时重新审查登记册；未经审查即过期的例外将变为
  未审查的风险。不得在聊天线程中接受风险，下一位审查人在该处无法找到记录。

| 好 | 坏 | 原因 |
|---|---|---|
| 默认拒绝权限并逐资源检查 | 在界面中隐藏按钮 | 直接 API 调用将跳过展示逻辑。 |
| 带大小上限的允许列表校验 | 仅实施客户端校验 | 客户端由攻击者控制。 |
| 参数化查询 | 手工转义引号 | 手工转义将遗漏编码与上下文。 |
| 按服务限定范围的凭据 | 共享管理员令牌 | 一次泄露将在各处升级，且无法归因。 |
| 带审查门禁的固定锁文件 | 安装时解析的开放版本范围 | 构建可能选中未经审查的包。 |
| 随边界更新威胁模型 | 启动时撰写一次模型 | 设计已经变更，模型未变更。 |
| 有到期日的风险登记册条目 | 在聊天线程中接受风险 | 无负责人、无期限、无记录。 |

审查人在阅读代码之前检查的默认值如下：

| 控制措施 | 安全默认值 | 放任时的失效模式 |
|---|---|---|
| 访问决定 | 除非有权限授予该操作，否则拒绝 | 被遗忘的检查将变为开放端点。 |
| 新数据字段 | 私有，自 API 与日志中排除 | 为某一功能添加的字段将在各处暴露。 |
| 功能开关 | 在有意启用之前保持关闭 | 未完成的代码将到达所有用户。 |
| 错误响应 | 通用消息加关联标识符 | 堆栈跟踪、查询与内部主机将泄露。 |
| 会话 cookie | `HttpOnly`、`Secure`、`SameSite=Lax` 或更严格 | 脚本访问与跨站请求将被启用。 |
| 管理路由 | 已认证、已授权、有限速且已审计 | 内部工具将成为最易进入的入口。 |
| 资源限制 | 请求大小、时间与速率均有上限 | 一个客户端即会耗尽所有人的服务。 |

## 2. 凭据与机密

机密属于项目持有的最小、价值最高的对象：一个可读取的值即能够授予其范围允许的全部操作。本维度覆盖完整生命
周期，自分类、存储至轮换与泄露响应，适用于应用凭据、CI 令牌、签名密钥与本地开发值。

- **区分机密与公开标识符。** 机密为密码、私钥、API 密钥、会话令牌、webhook 签名值，或内嵌凭据的连接
  字符串。公钥、可发布密钥、OAuth 客户端标识符或应用标识符并不天然公开：应当先确认暴露安全，再按来源、
  范围或速率限制加以限制。范围不受限制的可发布密钥在实践中即为机密。
- **机密应当存放于仓库之外。** 值应当保存于机密管理器或平台机密存储中，并在运行时通过环境变量、挂载文件
  或运行时 API 注入。代码中仅应保留名称，不得保留值；`.env.example` 仅应包含变量名与不可用的假值。
  Kubernetes 的 `Secret` 对象仅为 base64 编码，不构成加密，因此应当为生产值启用静态加密，或使用外部存储。
- **应当应用最小权限与限定范围的令牌。** 每个服务、任务与环境各签发一个凭据，仅授予其所需的资源与操作；
  读与写、测试与生产应当分开。平台支持时，应当使用带受众限制的短期令牌，并使人工访问经过单点登录，同时
  保留有日志的紧急访问通道。被多个服务共享的凭据无法安全地轮换、归因或限定范围。
- **轮换节奏应当设定，并指定唯一负责人。** 每个凭据在清单中均须具有负责人、轮换间隔与下次轮换日期；应当
  按计划轮换，在角色或人员变更时轮换，并在任何怀疑暴露时轮换。应当在重叠窗口内保留两个有效密钥，部署新值，
  验证流量，随后停用旧值。在客户端重新加载之前即删除旧密钥的轮换，将破坏生产环境，并使团队习惯于跳过轮换。
- **CI 机密暴露应当受控。** CI 机密应当在运行时自 CI 机密存储注入，在日志中打码，并且不提供给不受信任的
  fork 构建；部署凭据应当限定至一个环境与一个操作。应当优先使用短期身份联合，而非静态云密钥；将第三方
  action 固定至已审查的版本；不得使机密进入制品、缓存与测试报告。工具打印出的任何值均视为已暴露，应当
  轮换。
- **本地开发机密应当留存于本地。** 开发凭据应当与生产分离，限定至开发数据，并存放于被 git 忽略的文件或
  本地机密存储中；不得将个人令牌作为团队凭据共享，不得使开发环境指向生产数据。以假值记录每个变量的
  `.env.example`，能够使贡献者无需查看真实机密即可开始工作。
- **泄露的检测与响应应当依正确顺序实施。** 应当扫描提交、拉取请求、历史、构建日志与发布制品中的机密模式。
  命中时，应当在取得 AU-1/AU-2 明确同意后于 24 小时内吊销或轮换；生产关键凭据已确认正在被利用的，依 AU-5
  先实施最小止损并立即报告。随后审计其使用情况、保留证据；调查结束并按 AU-1 取得明确同意后，方可自制品与日志中
  移除该值，并记录事件。在密钥仍然有效时删除提交，仅会抹掉证据并使暴露继续存在。
- **机密清单应当维护。** 应当登记每个机密的用途、负责人、存储位置、范围、轮换间隔与依赖服务；每季度审查
  登记册。不在登记册中的值既无负责人，亦无轮换日期，因此或者登记，或者停用，不得放任其继续运行。

| 好 | 坏 | 原因 |
|---|---|---|
| 自机密管理器在运行时注入 | 值写于已提交的配置文件中 | 仓库读者与历史均将保留该值。 |
| 按服务限定范围的令牌 | 共享管理员凭据 | 一次泄露将波及每个服务。 |
| 带重叠窗口的轮换 | 立即删除旧密钥 | 正在处理的客户端将失败，团队随后回退。 |
| 短期 CI 身份联合 | 长期静态部署密钥 | 静态密钥的寿命超过流水线被攻陷的时间。 |
| 含名称与假值的 `.env.example` | 含真实开发值的示例文件 | 示例文件将被提交并被复制。 |
| 保留证据并报告，取得同意后轮换，调查结束再清理 | 先删除提交 | 凭据仍然有效，证据却已消失。 |

## 3. 许可证与合规

每个依赖与每次分发均附带许可证义务。本维度定义项目如何接纳第三方代码、如何选择自身许可证、如何记录所
分发的内容，以及如何分派属于法务的问题。

- **入站许可证应当分为允许、审查与禁止三类。** 允许的例子有 MIT、BSD-2-Clause、BSD-3-Clause、ISC、0BSD
  与 Apache-2.0，但须遵守署名与声明义务；审查的例子包括 MPL-2.0、LGPL-2.1、LGPL-3.0、EPL-2.0、CDDL-1.0，
  以及专利条款不清晰的公有领域声明；禁止的包括在分发代码中使用 GPL-2.0 与 GPL-3.0，在网络服务代码中额外
  包括 AGPL-3.0，以及 SSPL、BUSL-1.1、Commons Clause、仅限非商业使用的条款与无许可证代码。未知许可证在
  人工识别并记录决定之前一律禁止。
- **应当检查整棵依赖树，不得仅检查顶层。** SPDX 标识符应当自包元数据与许可证文件中读取，随后检查直接与
  传递组件、构建工具、容器基础镜像与内置代码。copyleft 义务可能隐藏于多层之下；双许可证包将迫使项目作出
  明确选择。应当按组件记录解析出的许可证，不得记录日后无法审计的摘要。
- **出站许可证应当有意识地选择。** 可复用库默认采用宽松许可证，项目能够接受时附带专利授权；仅在法务参与
  并作为明确产品决策时，方可选择 copyleft。许可证文件的名称、位置与包元数据字段由
  `repository-governance-conventions` 管辖；生态期望的源码文件头声明按本维度保留。应当确认出站条款与
  入站许可证及实际使用的贡献兼容。许可证变更属于一项发布决定，不构成一次编辑。
- **许可证清单应当维护。** 应当记录每个组件的名称、版本、SPDX 标识符、来源、用途（运行时、构建、开发、
  可选）、修改状态、义务与负责人。每次发布均须重新生成；仅用于开发的依赖也应当记录，因其可能变为随产品
  分发的依赖。该清单为声明文件与 SBOM 的来源，不得作为另一份手写列表存在。
- **每次发布均须生成 SBOM。** 应当基于构建制品所用的已解析依赖图生成 SPDX 或 CycloneDX JSON，包含传递
  组件、版本、包标识符、许可证与哈希。SBOM 应当附至发布，保留至支持周期加上团队所采用的保留期限，并与
  上一发布版本做差异对比，使新组件可见。SBOM 应当包含容器基础镜像与操作系统包；仅含源码的 SBOM 将低估
  实际部署的内容。
- **声明与署名应当随制品提供。** 应当自清单生成 `THIRD-PARTY-NOTICES.md`，在许可证要求时包含完整许可证文本，为 Apache-2.0 组件保留上游 `NOTICE` 内容，并记录许可证要求的版权行。声明文件应当随制品分发；其位置与打包要求由 `repository-governance-conventions` 管辖。仅挂在网站上的署名无法满足随二进制分发的义务。
- **贡献协议应当确定。** 默认要求每个提交均具有 Developer Certificate of Origin 签署；仅在组织要求时使用
  贡献者许可协议，并在 `CONTRIBUTING` 中说明所采用者。除法务另有批准外，入站许可证即为出站许可证；不得
  合并来源不明的代码、自互不兼容来源复制的代码，或缺少所需签署的贡献。
- **出口与监管问题应当标记。** 产品使用密码学、分发至受监管或受制裁市场，或属于受监管行业的，应当将分类
  问题交由法务，并记录决定或“不适用”的判定。不得将法律结论写入仓库；应当保留有记录的决定及其负责人，并在
  分发或功能变化时重新审视。

| 好 | 坏 | 原因 |
|---|---|---|
| 按策略检查 SPDX 标识符 | “其在仓库托管平台上公开，因此可以复用” | 无许可证意味着保留所有权利。 |
| 扫描传递依赖的许可证 | 仅检查直接依赖 | copyleft 义务隐藏于顶层之下。 |
| 使用 Apache-2.0 并保留上游 `NOTICE` | 复制源码时未附 `NOTICE` 文件 | 分发时违反了署名义务。 |
| 自清单生成声明文件 | 手工复制的署名列表 | 第一次依赖变更即失准。 |
| 每个贡献均有签署 | 合并未签署的代码 | 权利与来源均不明确。 |
| 经法务批准、带负责人与到期日的例外 | 法务的口头批准 | 无记录，且例外将超出当时语境继续有效。 |

按分发类型划分的出站默认许可证如下，须经法务并根据组织策略确定：

| 项目类型 | 默认出站许可证 | 原因 |
|---|---|---|
| 可复用库或 SDK | Apache-2.0 | 宽松使用外加明确的专利授权。 |
| 公开发布的小型内部工具 | MIT | 简短、宽松且广为人知。 |
| 托管应用 | 专有或不授予许可证 | 服务不分发，因此源码许可证属于另一项决定。 |
| 文档与规范 | CC BY 4.0 | 允许带署名复用内容；不适用于代码。 |
| 文档内的示例代码 | 与项目许可证一致 | 代码片段将被复制，因此条款必须清晰。 |

## 4. 隐私

隐私工作自字段被收集之前开始，至数据被删除时结束。本维度覆盖分级、清单、用途、最小化、保留、数据主体
请求、处理者、传输与泄露通知；规则取决于司法管辖区的，由法务决定并记录决定。

- **个人数据应当分级。** 应当按敏感度与访问权限对每个元素分级，使用公开、内部、保密与受限四级。姓名、
  电子邮箱地址、电话号码、账户标识符与客服消息属于保密级；政府标识符、金融账户、健康信息、精确位置与
  认证机密属于受限级。清单应当将 IP 地址、设备标识符与假名标识符视为个人数据；司法管辖区特有的分级交由
  法务确定。
- **清单与流转应当绘制。** 应当为每个元素记录：数据主体、来源、用途、系统、存储位置、接收方与处理者、
  区域、保留期限与访问角色。应当以表格或图绘出服务、数据仓库、日志、备份与供应商之间的流转；该图使删除
  请求或泄露评估成为可能。新字段、系统、供应商或导出应当于生产流量到达之前先行增加清单行。
- **用途应当说明，要求时应当记录同意。** 数据应当为明确用途收集；未经审查，不得将数据复用于新用途；
  合法性依据以及何处需要同意，由法务确定。营销同意必须为选择加入，不得预先勾选；cookie 与 SDK 类别应当
  按对应的同意情况放行；同意记录应当包含版本、时间戳与范围。“数据可用于任何用途”等同于未说明用途。
- **存在的数据应当最小化。** 应当删除任何无书面用途的字段；优先使用内部标识符，而非直接标识符；不需要
  身份时，应当哈希、截断或聚合；不得使个人数据进入日志、URL、查询字符串、错误消息、事件名称与测试夹具。
  每个分析事件均应当作为一次数据收集处理：明确其用途与负责人；审查其属性 schema；截断 IP 地址；不得捕获
  页面文本或表单输入；并以与发送它的 SDK 相同的同意决定加以控制。
- **保留期限应当限定，执行机制应当交接。** 清单应当为每个元素设定保留期限，并定义删除路径，包括备份、
  缓存、日志与处理者副本。数据与平台角色负责删除任务与迁移；本规范制定策略，并要求提供任务已经运行的
  证据。法律保留由法务决定；法务解除之前，该元素的删除应当暂停并记录原因。
- **数据主体请求应当处理。** 应当公布受理渠道，核实请求者身份，并在团队所采用的 30 天期限或法务确定的
  法定期限内答复，以较短者为准。应当检索清单中的每个系统，包括日志与处理者；按请求的格式交付结果；记录
  日期、已检索的系统与结果。删除请求应当按有记录的安排传递给处理者与备份。
- **处理者与传输应当审查。** 处理者满足数据处理协议、安全审查、有记录的数据存放位置与删除承诺之前，不得
  向其提供个人数据；次处理者列表应当保持最新，并每年重新评估。跨境传输需要法务批准的机制、存储区域以及
  远程支持访问规则；将生产数据复制至笔记本电脑或本地开发数据库，属于绕过全部控制措施的传输。
- **泄露通知应当在泄露发生之前准备。** 发现后应当于 24 小时内完成分级与遏制，保留证据，并向事件负责人
  与法务通报。法务确定法定的通知期限与通知对象；团队应当准备事实与时间线，通知合同要求的各方，并阻止
  任何未经批准的公开声明。应当完成事后审查，记录缺口以及防止再次发生的控制措施。

| 级别 | 示例 | 处理方式 |
|---|---|---|
| 公开 | 已发布的文档、营销页面 | 除发布批准外无其他限制 |
| 内部 | 内部指标、非敏感配置 | 已认证员工可访问 |
| 保密 | 姓名、电子邮箱地址、电话号码、账户标识符、客服消息 | 基于角色的访问、传输与静态加密、不写日志 |
| 受限 | 政府标识符、金融账户、健康数据、精确位置、凭据 | 明确批准、字段级加密、访问经审计、最小保留 |

| 好 | 坏 | 原因 |
|---|---|---|
| 含用途、保留期限与区域的清单行 | “这只是一个电子邮箱地址” | 每个标识符均附带义务与删除路径。 |
| 部署前审查事件 schema | 分析团队自行添加字段 | 收集绕过了用途限制与审查。 |
| 分析中使用假名标识符 | 事件属性中使用原始邮箱 | 数据仓库将变为第二个身份存储。 |
| SDK 加载前设置同意门禁 | 仅设置告知横幅 | 收集之后记录的同意无法授权该收集。 |
| 对照备份与处理者验证删除 | 仅自主表删除 | 副本仍留存于日志、备份与供应商处。 |
| 数据流转之前审查处理者 | 先添加 SDK、事后再披露 | 数据已在未约定的条款下离开。 |
| 由法务确定通知期限 | 团队猜测期限并公开通知 | 错误的披露本身将带来责任。 |

## 5. 漏洞披露

披露属于附带承诺的流程：报告者必须能够找到人员；团队必须遵守自身公布的时间线；用户必须能够在细节公开
之前完成打补丁。本维度覆盖渠道、评级、修复、公告、署名、CVE 处理、赏金边界与禁发期。

- **渠道与范围应当公布。** `SECURITY.md` 内容应当包括受监控的报告地址、可用的加密渠道、支持的版本、
  范围内的组件、范围外的类别（如社会工程与物理访问）、善意研究的安全港条款，以及下文列出的响应承诺。
  `SECURITY.md` 的归属划分见 `SKILL.md` 的边界说明；本规范管辖内容及其公布的承诺。至少每季度应当确认该地址可送达、渠道有人监控。
- **确认与分诊应当按时间要求实施。** 应当自报告到达起 2 个工作日内确认收到，并在 5 个工作日内完成初步分诊，
  向报告者给出严重程度、负责人与下一里程碑。报告处理期间应当至少每 10 个工作日发送一次状态更新，并在报告
  日志中记录时间戳。未获确认的报告，将使报告者选择公开或放弃。
- **严重程度应当依公开评分标准评定。** 应当采用 CVSS v3.1 或 v4.0 评分并记录指标向量，随后在公告备注中
  依据暴露程度、利用可得性、数据敏感度与补偿性控制措施进行调整。严重程度决定修复期限：严重自分诊完成起
  7 个自然日；高危 30 个自然日、中危 90 个自然日、低危取 180 个自然日与下一个计划的小版本发布中的先到者，
  均自同一时点起算。依赖漏洞的修复期限沿用同一分级，见第 1 节。分歧应当上报至安全负责人并记录评级，不得在
  报告线程中协商。
- **修复与发布应当协调。** 应当复现问题，在私有分支或 fork 上修复，在同一变更中加入回归测试，对严重与
  高危发现项发布计划外补丁，不得等待计划发布。应当向每个支持的版本回移植，与存在漏洞的依赖的维护者或
  下游分发者协调，并在合同要求时于禁发期内提前通知重要客户。
- **公告与细节公开应当分两步。** 修复版本发布后 2 个工作日内，应当发布包含受影响版本、修复版本、严重程度与
  向量、影响、临时缓解措施、报告者署名以及 CVE 编号（无 CNA 时记录申请状态）的公告，并将该条目加入变更日志
  与发布说明；公告不得等待禁发期结束。利用细节与概念验证属于细节公开，仅在禁发期结束或经报告者同意后公开；
  公告包含临时缓解措施不构成细节公开。用户获得打补丁窗口之前，不得公开利用细节。
- **署名规则应当可预期。** 应当按姓名或昵称加链接提供署名，默认给予每位遵循流程的报告者署名，并尊重匿名
  请求。署名独立于赏金支付与严重程度；有助于确认问题的重复报告仍可获得署名。不得将署名或撤销署名作为
  争议中的筹码。
- **CVE 编号应当申请，无 CNA 时按分支处理。** 发布公告之前，应当通过项目的 CNA 或授权的 CNA 申请 CVE，包含
  受影响版本、弱点类型与影响描述；该编号应当记录于公告、变更日志与发布说明。编号分配延迟的，应当先发布公告
  并说明申请状态，待编号分配后更新。项目无 CNA 且无授权 CNA 的，公告可以不包含 CVE 编号，但应当记录所联系
  的 CNA、申请状态与时间，不得虚构编号。
- **赏金与禁发期边界应当明确设定。** 仅在具备预算、规则与分诊流程时，方可运行赏金计划；应当说明范围内的
  资产、禁止的测试、奖励标准，并说明访问他人数据永远不被授权。禁发期默认自报告之日起 90 个自然日；对
  正在被利用或已公开的问题应当缩短，仅在经报告者同意并记录原因时延长；其他方先行公开的，应当立即发布
  缓解措施与公告，不得独自继续遵守禁发期。

| 好 | 坏 | 原因 |
|---|---|---|
| 受监控的渠道与已公布的承诺 | 无人查看的安全邮箱 | 报告将丢失，研究者转而公开。 |
| 当天完成修复与公告 | 静默打补丁、不发公告 | 用户无法评估暴露面或验证修复。 |
| 公告中记录 CVSS 向量 | 凭直觉选择严重程度 | 无可比较的依据，亦无审计轨迹。 |
| 发布前申请 CVE | 公告无编号 | 下游扫描器与客户无法跟踪。 |
| 提供署名并尊重退出 | 未经同意公开报告者姓名 | 将失去下一位研究者的信任。 |
| 公布禁发期并记录结束日期 | 无日期的无限期禁发 | 报告者将升级为公开披露。 |
