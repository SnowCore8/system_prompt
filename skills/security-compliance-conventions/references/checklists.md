# 安全与合规检查清单

应当将上述工作表与运行手册同 `SKILL.md`、`dimensions.md` 配合使用。每一节均可操作：在设计或审查时填写，
将填好的记录附至变更或发布，并与项目一并保存。应当以项目值替换示例值；不得在填好的检查清单中记录真实机密
或个人数据，使用 `security@example.test.invalid` 与 `example.test.invalid` 之类的假值。

正文“审查清单”为设计期权威；本文件仅载安全审查、许可证与披露响应时点的工作表与正文未展开的条件。

## 1. 轻量威胁模型工作表

每个资产与信任边界填写一行。结果为一项一页说明，不构成一份目录；应当将练习限制于 30-60 分钟内，并记录
残余风险，不得推定其为零。

| 字段 | 提示 | 示例 |
|---|---|---|
| 功能与负责人 | 正在构建的内容，以及该模型的负责人？ | 订单导出，计费团队 |
| 资产 | 该功能保护或暴露的内容，以及每项的价值？ | 客户地址、导出文件、API 令牌 |
| 入口点 | 不可信输入如何到达该功能？ | `POST /v1/exports`、webhook 回调、文件上传 |
| 信任边界 | 数据或控制权在何处于不同信任级别的组件之间传递？ | 浏览器至 API、API 至对象存储、worker 至邮件服务商 |
| 滥用场景 | 攻击者将如何滥用该功能，造成何种效果？ | 读取另一租户的导出、造成成本激增、向 CSV 注入公式 |
| 现有控制措施 | 已有哪些措施在阻止每个滥用场景？ | 查询中的租户过滤、按租户的速率限制、CSV 公式转义 |
| 数据类别 | 该功能存储或传输哪些数据类别，其中最高者为何级？ | 保密级地址、内部指标 |
| 依赖与处理者 | 涉及哪些第三方服务、包或处理者？ | 对象存储、CSV 库、邮件服务商 |
| 缺口与残余风险 | 仍存在哪些缺口，由谁接受？ | 无按对象的审计日志；由计费负责人接受，直至第三季度 |
| 决定 | 发布、有条件发布或阻塞；适用何种条件？ | 在公开发布前补上审计日志，随后发布 |
| 审查日期 | 何时重新审视该模型？ | 下次信任边界变更时，或 6 个月后 |

每个资产与滥用场景均对应至控制措施、每个缺口均具有负责人与日期、决定与功能设计一并记录时，模型方为完整。
仅列出通用风险而不点名本功能的数据与入口点的模型，仅为模板，不构成审查。

## 2. 安全审查触发条件清单

任一条为真的，应当将变更分派给安全审查人。全部条目均不成立的，应当在变更描述中记录已核对本清单。

- [ ] 认证、会话处理、密码重置或令牌签发发生变更。
- [ ] 授权模型、角色、范围或租户隔离发生变更。
- [ ] 密码学、密钥管理、哈希或随机数使用发生变更。
- [ ] 出现新的外部接口、webhook、公共端点或回调。
- [ ] 新的处理者、SDK 或托管服务接收项目数据。
- [ ] 支付、定价、计费或财务计算逻辑发生变更。
- [ ] 新增文件上传、文件解析、归档解压或用户可控的 URL 抓取。
- [ ] 个人数据字段、分析事件或同意行为发生变更。
- [ ] 新增或变更管理工具、身份冒充或紧急访问。
- [ ] 基础设施身份、网络规则、IAM 策略或机密管理发生变更。
- [ ] 反序列化、模板渲染、动态代码执行或 shell 调用发生变更。
- [ ] 新的原生依赖、安装脚本或构建时可执行文件进入供应链。
- [ ] 分发、许可证、声明或出口分类发生变更。
- [ ] 未关闭的安全发现项或已披露漏洞影响本次变更。
- [ ] 变更触及生产数据、备份恢复路径或删除任务。
- [ ] 新的数据导出、批量下载或报告使记录超出当前受众范围。
- [ ] 升级改变了原生代码、安装行为或依赖的实际许可证。

## 3. 机密生命周期登记册

全部机密应当记录于同一登记册，并每季度审查。负责人应当为人员或团队，不得为工单；无下次轮换日期的机密
默认已逾期。

| 类型 | 存储 | 轮换 | 负责人 |
|---|---|---|---|
| CI 部署令牌 | CI 机密存储，按环境限定范围 | 90 天，暴露后立即轮换 | 发布负责人 |
| 服务 API 密钥 | 机密管理器，运行时注入 | 180 天，双密钥重叠 | 服务负责人 |
| 数据库凭据 | 机密管理器或动态数据库凭据 | 90 天 | 数据负责人 |
| 签名密钥 | 带密钥版本管理的 KMS 或 HSM | 365 天，带轮换重叠期 | 发布负责人 |
| 加密密钥 | 启用轮换的 KMS | 每年，并针对旧数据制定重新加密计划 | 安全负责人 |
| OAuth 客户端机密 | 机密管理器 | 180 天 | 身份负责人 |
| 开发者访问令牌 | 身份提供方，短期有效 | 最长 30 天，角色变更时吊销 | 身份团队 |
| 第三方集成密钥 | 机密管理器 | 180 天 | 集成负责人 |
| webhook 签名机密 | 机密管理器，轮换期间两个有效值 | 180 天 | 端点负责人 |
| 本地开发机密 | 被 Git 忽略的本地文件或开发者 vault | 90 天，不得共享 | 每位开发者 |

- 仅在验证新值上的流量、且审计日志不再显示旧值仍在使用之后，方可停用凭据。
- 不在登记册中的机密没有轮换日期；应当登记或移除。
- 任何在日志、制品、截图或工单中暴露的凭据均须轮换，即使暴露看似无害。
- 开发与测试凭据不得带有生产范围或生产数据。

## 4. 依赖与供应链控制清单

每个新依赖以及每个改变受维护版本的升级，均应当适用本清单；答案应当附至依赖审查。

- [ ] 包名与来源已对照预期项目核实，确认非相似的仿冒包。
- [ ] 维护者与发布历史显示项目处于活跃且可信的维护之下。
- [ ] 包自配置的包仓库获取，并以哈希固定于锁文件中。
- [ ] 直接与传递依赖数量相对其提供的价值可以接受。
- [ ] 除经审查批准外，不运行安装脚本、post-install hook 或构建时下载。
- [ ] 许可证通过门禁，包括传递组件。
- [ ] 无已知的严重或高危漏洞缺少书面缓解措施。
- [ ] 该版本仍受上游支持，且未停止维护。
- [ ] 原生代码、二进制文件与预构建制品已识别并扫描。
- [ ] 生态支持时，构建产出来源证明或签名制品。
- [ ] 自动更新拉取请求已启用，并在测试后合并。
- [ ] 容器基础镜像已最小化、按摘要固定并扫描。
- [ ] 未使用的依赖已删除，而非保留安装状态。
- [ ] 私有包仓库允许列表阻止已批准集合之外的包。
- [ ] 变更后重新生成 SBOM，并与上一发布版本做差异对比。

## 5. 许可证策略类别

类别与动作应当记录于许可证清单。类别不构成法律意见；例外由法务批准，由负责人记录。

| 类别 | 示例 | 动作 |
|---|---|---|
| 允许 | MIT、BSD-2-Clause、BSD-3-Clause、ISC、0BSD、Apache-2.0 | 可以使用；保留许可证文本、版权行与任何上游 `NOTICE`。 |
| 审查 | MPL-2.0、LGPL-2.1、LGPL-3.0、EPL-2.0、CDDL-1.0、专利条款不清晰的公有领域声明 | 分派给许可证负责人与法务；批准前记录链接方式、修改情况与声明事实。 |
| 禁止 | 分发代码中的 GPL-2.0 与 GPL-3.0、网络服务代码中的 AGPL-3.0、SSPL、BUSL-1.1、Commons Clause、仅限非商业使用的条款、无许可证 | 不得添加；替换该依赖，或取得经法务批准的书面例外，注明负责人与到期日。 |
| 未知 | 自定义条款、无许可证头的复制源码、固定版本的 fork | 在人工识别条款并记录决定之前，按禁止处理。 |

- 双许可证包应当记录实际选择的许可证，不得两者均记。
- 内置代码应当保留上游许可证文件，并记录每个本地补丁。
- 文档与素材的许可证应当与代码许可证分开检查。
- 现有依赖的许可证变更应当作为新依赖审查处理。
- CC BY-SA 等相同方式共享内容未经审查不得并入代码；该义务可能覆盖组合作品。
- 自第三方规范生成的客户端与 schema 应当保留上游许可证与声明。

## 6. SBOM 与声明清单

两种制品应当自同一份已解析依赖图生成；手工维护的列表在发布说明写好之前即已过时。

- [ ] SBOM 在 CI 中自构建制品所用的依赖图生成。
- [ ] 直接与传递组件包含版本、包标识符、许可证与哈希。
- [ ] 包含容器基础镜像与操作系统包。
- [ ] 记录 SBOM 格式与规范版本（SPDX 或 CycloneDX）。
- [ ] SBOM 附至发布并与制品一并存储，并非仅置于 CI 日志中。
- [ ] SBOM 与上一发布版本做差异对比，并审查新组件。
- [ ] 声明文件列出许可证要求署名的每个组件。
- [ ] 在需要处包含完整许可证文本，并保留上游 `NOTICE` 内容。
- [ ] 声明文件随制品置于分发根目录与打包制品内部。
- [ ] 已记录保留期限，每个受支持的发布版本均能够取回其 SBOM。
- [ ] SBOM 与制品一致：抽查三个组件，与已安装版本比对。
- [ ] SBOM 生成器名称与版本随发布记录。
- [ ] 组件哈希与构建该制品的锁文件条目抽查比对。
- [ ] 例外与审查类许可证链接至其有记录的批准。

## 7. PII 清单与隐私审查工作表

每个数据元素填写一行，每条数据流转填写一遍。某字段无法填完整行的，该字段不具备上生产的条件。

| 字段 | 提示 | 示例 |
|---|---|---|
| 数据元素 | 收集何种数据，以何种形式，粒度如何？ | 客户电子邮箱地址，精确字符串 |
| 数据主体 | 数据归属何人，是否可能包括未成年人或员工？ | 企业账户的终端客户 |
| 来源 | 数据来自何处，来源是否获授权？ | 结算表单、客服导入 |
| 用途 | 哪项明确用途需要该数据，该用途由谁负责？ | 订单收据与客服查询，商务团队 |
| 系统与流转 | 数据存放于何处，经过哪些系统？ | 订单数据库、邮件处理者、客服工具 |
| 处理者与区域 | 哪些供应商接收数据，依据哪份协议，位于哪个区域？ | 经批准区域内的邮件服务商 |
| 保留与删除 | 保留时长，以及删除机制？ | 24 个月，每夜删除任务加处理者删除 |
| 访问 | 哪些角色可以读取，访问是否记录日志？ | 客服只读，经审计 |
| 分级 | 公开、内部、保密或受限？ | 保密 |
| 同意或合法性依据 | 记录了哪项依据，由谁确认？ | 合同履行，由法务确认 |
| 保留负责人 | 谁执行删除，任务已运行的证据位于何处？ | 数据平台角色，月度任务报告 |

变更合并前，应当以下列清单审查填写好的数据清单：

- [ ] 用途具体明确，且数据未被复用于未记录的用途。
- [ ] 收集已最小化：无字段缺少用途，且无直接标识符可以替换。
- [ ] 要求同意时，同意为选择加入、有版本记录，并在收集开始前设置门禁。
- [ ] 清单行、流转图与保留期限在生产流量到达之前已经存在。
- [ ] 处理者与传输具有协议、区域与删除承诺。
- [ ] 日志、分析属性、URL、测试夹具或截图中不出现个人数据。
- [ ] 仅凭清单即可满足数据主体请求，包括处理者副本。

## 8. 数据主体请求运行手册

应当将清单作为检索图谱。所采用的答复目标为 30 天或法务确认的法定期限，以较短者为准；即使请求被拒绝，也
应当记录日期。

1. 登记请求：收到日期、渠道、请求者、所请求的权利与期限。
2. 以与数据相称的方法核实身份；不得为核实而收集额外数据。
3. 对请求分类：访问、更正、删除、可携带、反对或限制。
4. 检索清单中的每个系统：主存储、数据仓库、日志、备份与处理者。应当记录每个已检索与每个被排除的系统及
   原因。
5. 应用法律保留与第三方权利；记录何时必须保留或拒绝提供，由法务决定。
6. 履行请求：按请求的格式导出、更正记录，或按有记录的安排删除。拒绝删除的，应当给出法律或法律保留所要求
   的理由。
7. 通知处理者并确认完成；记录发送内容与发送时间。
8. 在期限内答复请求者并记录结果，包括任何拒绝及其理由。

## 9. 漏洞披露运行手册与时间线

上述各项为 `SECURITY.md` 内容中公布的承诺。缓冲时间应当置于日历，不得置于表格。

| 阶段 | 期限 | 动作 | 负责人 |
|---|---|---|---|
| 接收 | T+0 | 登记报告，并回复渠道与时间线。 | 安全联系人 |
| 确认收到 | 2 个工作日 | 确认收到，并说明处理人。 | 安全联系人 |
| 初步分诊 | 5 个工作日 | 复现、确定影响版本、指定严重程度与负责人，并商定下一里程碑。 | 安全审查人 |
| 更新 | 每 10 个工作日 | 发送状态、阻塞项与任何修订后的日期。 | 报告负责人 |
| 严重漏洞修复 | 7 个自然日 | 发布计划外补丁，并回移植至支持的版本。 | 工程负责人 |
| 高危漏洞修复 | 30 个自然日 | 在下一个补丁版本中发布。 | 工程负责人 |
| 中危漏洞修复 | 90 个自然日 | 纳入发布计划。 | 工程负责人 |
| 低危漏洞修复 | 180 个自然日 | 与其他工作合并处理。 | 工程负责人 |
| 公告 | 修复版本发布后 2 个工作日 | 发布公告、CVE 编号、受影响版本与修复版本、临时缓解措施与署名。 | 安全负责人 |
| 禁发期结束 | 报告日期加 90 个自然日 | 发布，或仅在报告者同意并记录原因后延长。 | 安全负责人 |

- 重复或已修复的报告也应当答复，并附公告引用；在确有帮助之处给予署名。
- 范围外的报告也应当答复，说明原因，并附适用的范围条目。
- 依赖漏洞应当遵循维护者的公告；用户受影响时，项目应当发布自身声明。
- 正在被利用的问题将把禁发期缩短至发布修复并通报事件负责人所需的时间。
- 针对不受支持版本的报告仍应当答复；团队应当决定修复、记录临时缓解措施或提示升级。
- 公告应当自 `SECURITY.md` 内容与修复版本的发布说明链接。
