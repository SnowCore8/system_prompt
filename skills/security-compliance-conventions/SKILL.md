# 安全与合规规范

安全与合规的失效具有不对称性。遗漏一条命名规则，代价只是审查意见与事后改名；而凭据进入提交历史、copyleft
库随二进制产物分发、个人数据被发送至未经批准的处理者，都无法通过后续工作修复，因为披露已经发生。本 skill
规定项目侧的安全开发、凭据与机密、许可证、隐私与漏洞披露规则，以及每条规则所需的证据。其服务对象为设计
功能的工程师、评判变更的审查人，以及准备发布或答复报告的维护者。本 skill 仅规定项目策略：代理行为由宿主
与用户指令层管辖，此处不再重述。问题取决于法律条文或合同的，由法务决定；本 skill 的任何内容均不构成法律
意见。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充；同一范围内不得混用多套标准。

1. 强制的平台、法律、宿主与用户全局约束。法律、法规、有约束力的合同、许可证条款，以及宿主或用户指令
   层，均非可选事项；法定截止期限、数据处理协议、许可证义务或代理层面的行为规则，不得被项目的本地安排
   覆盖。
2. 本 skill 的规则。安全控制、严重程度与修复期限、披露承诺，以本文件与 `references/` 为准。
3. 现有项目策略与事实：`SECURITY.md`、`LICENSE`、数据清单、已批准的架构决策与项目配置。自创规则之前应当
   先阅读这些内容；它们属于事实输入，依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充，不得
   覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- 代理行为与项目策略。代理可以在输出中包含何种内容、何时必须为不可逆操作取得同意，由宿主与用户指令层
  规定；这些规则属于第 1 层，此处不再重述。本 skill 规定项目策略：哪些数据可以存储、分发、收集或披露，
  以及每一项由谁批准。
- 注释与文档规则禁止在注释、示例与文档中出现机密值。本 skill 管辖真实值的存放位置，以及其扫描、轮换与
  披露方式；两者均须执行，并应当将已暴露的值追溯至其存储条目，不得仅删除可见副本。
- 发布与事件响应角色负责流水线执行与事件指挥。本 skill 管辖这些流水线运行的安全门禁、每个门禁背后的
  严重程度与修复策略，以及事件公开之前的披露流程。
- API 与数据角色负责保留机制、删除任务与迁移。本 skill 管辖 PII 分级、隐私审查以及团队所采纳的法律义务；
  保留策略在此制定，在该角色处实现。
- `repository-governance-conventions` 仅管辖 `SECURITY.md` 是否存在、位置与基本元数据（负责人、审查日期）；
  `documentation-conventions` 管辖其页面结构与行文。本 skill 管辖必需内容、报告与响应承诺，以及在该文件
  中发布的公告流程。
- 测试与质量角色负责确定扫描在何处作为质量门禁运行。本 skill 管辖严重程度策略、修复期限，以及针对发现项
  决定修复、接受或阻塞。
- 第三方代码仅应报告，不得改动：内置、生成与外部维护的代码仅作清点与扫描，不得手工编辑。应当将问题报告
  至上游，或者在独立的 fork 中维护有记录的补丁，并记录该补丁。
- 报告优先于便利。扫描失败、依赖缺少许可证、隐私缺陷或疑似泄露，即使将阻塞发布，也应当报告；便利不得
  成为沉默的理由，报告亦不等同于修复。
- 同一效力层级的强制规则冲突的，应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与
  所选约定，连同负责人一并记录该决定，使后续变更遵循该决定。
- **单人维护与无 CNA。** 单人维护时，应当将时限标注为“尽力而为，不构成 SLA”；无 CNA 或无授权 CNA 时，
  公告可以不包含 CVE 编号，但应当以发布说明与平台安全公告记录申请状态与所联系的 CNA，不得虚构编号。

## 流程

1. 对变更及其触及的数据分类：资产、入口点、信任边界、凭据路径、依赖、个人数据、第三方代码与分发目标。
   应当依 diff 或设计开展工作，不得照搬通用清单。
2. 阅读已经生效的义务：项目的 `SECURITY.md` 内容、`LICENSE`、数据清单与已接受风险登记册。应当记录本次
   变更新增、改变或移除的义务。
3. 应当为每个新增或变更的信任边界构建或更新轻量威胁模型：资产、滥用场景、现有控制措施、残余风险与
   负责人。该模型应当与设计一并记录，或存放于 `docs/security/` 中。
4. 应当按顺序应用控制措施：安全默认值；服务端校验，配合与上下文相符的编码；认证与授权分离；限定范围的
   运行时凭据；依赖与许可证门禁。任何被推迟的事项均应当记为安全债务，附负责人与审查日期。
5. 合并前应当分派必需的审查：触发安全审查条件的，实施安全审查；涉及个人数据或新处理者的，实施隐私
   审查；涉及依赖或分发变更的，实施许可证审查；涉及法律问题的，交由法务处理。必需的审查尚未完成的，
   不得合并。
6. 应当产出发布证据：重新生成的 SBOM、声明文件、许可证清单、扫描结果与残余风险。证据应当附至发布，不得
   置于聊天线程或口头评论中。
7. 验证并交接：重跑门禁；确认修复期限与已接受风险的到期日期；更新 `SECURITY.md` 内容与公告；并说明仍未
   完成的事项及其负责人。

## 核心规则

- **按比例对每个信任边界建模。** 接受不可信输入、跨服务或授予访问权限的功能，均须具备一份轻量模型，涵盖
  资产、入口点、滥用场景、控制措施与残余风险；不跨越任何边界的功能，应当记录一行“未跨越边界”的说明。
  投入程度应当跟随风险，不得流于形式。
- **默认拒绝并失效关闭。** 新权限默认不存在；新字段默认私有；新开关默认关闭；新端点默认要求认证，直至
  有意开放。依赖不可用时反而失效开放的控制措施属于缺陷，即使全部扫描均无发现。
- **在服务端校验，并按上下文编码。** 每个边界均应以允许列表校验类型、长度、范围与格式；先规范化，再
  校验；使用参数化查询；分别对 HTML、属性、JavaScript、URL 与 shell 参数编码。客户端校验仅为用户体验，
  不构成控制措施。
- **在边缘认证，在资源处授权。** 每个请求均须针对具体对象与租户在服务端作出权限决定，不受界面隐藏内容
  影响。特权操作应当记录拒绝日志；管理操作与销毁性操作应当要求更强的认证因素。
- **不得使机密值进入仓库。** 仅应提交对机密的引用：环境变量注入、机密管理器或平台机密存储。
  `.env.example` 仅应包含变量名与不可用的假值；机密扫描应当覆盖提交、拉取请求、历史与构建日志。
- **凭据应当限定至单一任务并指定负责人。** 每个服务、任务与环境各签发一个凭据，并限制至其所需的资源与
  操作。应当记录负责人、可触达范围与轮换时点；共享的管理员凭据属于永久性发现项，不构成便利。
- **依赖应当视为待分发的代码。** 新依赖应当审查维护情况、已知漏洞、许可证、传递依赖规模与安装脚本。
  依赖应当固定至锁文件，自经验证的包仓库获取，并随制品分发列出其 SBOM；未使用的依赖应当删除，不得
  禁用。
- **依赖进入代码库之前须通过许可证门禁。** 应当对照允许、审查与禁止三类检查 SPDX 标识符与传递依赖的
  许可证；未识别的许可证在人工识别之前一律禁止。每个例外均须具备书面记录、负责人与日期。
- **依赖漏洞扫描应当设为合并门禁。** 门禁的阻塞条件（包括 Go、Rust、Java、C# 等语言生态的阈值）与扫描
  命令、位置只在 `testing-and-quality-conventions` 的 `references/gates.md` 定义，本规范不重复，以免两处
  阈值分叉；本规范管辖严重程度、修复期限与例外批准：没有修复方案或在本产品上下文中不可利用的发现，应当
  记录 VEX 评估、豁免与到期日。两处规则冲突的，以测试与质量角色的门禁定义为准，记录冲突并报告本规范
  维护者；修复本规范须另行授权，不得自行修改共享规范。
- **每次发布均须生成 SBOM 与声明文件。** 两者均应当基于构建制品所用的依赖图生成，包含传递组件与必需的
  署名，附至发布，并保留至支持周期加上团队所采用的保留期限。
- **收集个人数据之前须先行分级。** 生产流量到达之前，每个数据元素均须在数据清单中具有类别、用途、系统、
  保留期限、接收方列表与区域；隐藏于日志或分析中的收集仍属收集。
- **个人数据应当最小化并限定生命周期。** 无书面用途的字段一律不得存在；日志、URL 或事件名称中不得出现
  PII；开发或测试环境不得使用生产数据。不需要身份时应当使用假名化，并为每个保留期限配置强制执行该期限
  的删除路径。
- **发现项应当依策略评定，不得依扫描器评定。** 严重程度应当依据可利用性、暴露程度与数据敏感度确定；每个
  发现项均须具备负责人与修复期限；风险接受应当记录到期日与补偿性控制措施。无负责人的扫描器报告不构成
  决定。
- **披露应当依承诺的时间线实施。** 公布报告渠道与范围；自报告到达起 2 个工作日内确认收到，5 个工作日内
  完成初步分诊；严重问题自分诊完成起 7 个自然日内修复，并在修复发布时发布公告。公告应当包含 CVE 编号；
  无 CNA 或无授权 CNA 的，可以不包含编号，但须说明申请状态与所联系的 CNA，不得虚构编号。静默修复将使用户
  无法评估自身暴露面。
- **报告，不得绕过门禁实施改动。** 疑似泄露、未知许可证或隐私缺陷应当中止受影响的步骤，并连同证据一并
  报告；不得重写历史、删除日志或禁用以绕过门禁。第三方代码应当报告至上游，不得就地打补丁。

## 风险控制矩阵

每一行将一项资产或义务与其面临的失效、最低控制措施以及审查核对的证据对应。

| 资产或义务 | 威胁或失效 | 最低控制措施 | 证据 |
|---|---|---|---|
| 源代码仓库 | 凭据或个人数据进入提交历史且无法撤回 | 推送时与 CI 中运行机密扫描；`.gitignore` 覆盖本地配置与数据库转储；每个 diff 均审查新增文件 | 拉取请求上的扫描结果；命中确认后的轮换记录 |
| 运行时凭据 | 泄露的长期密钥可广泛访问生产环境 | 自机密管理器注入、按服务限定范围的凭据、有负责人的计划轮换 | 包含范围、负责人与下次轮换日期的凭据清单行 |
| 身份与权限 | 缺少对象级检查将使一个租户读取另一租户的数据 | 在资源处实施服务端授权、默认拒绝、逐个端点测试租户过滤 | 端点的授权测试；变更中的审查批准 |
| 依赖与构建 | 恶意、仿冒或已被攻陷的包在构建中运行 | 经过审查的依赖、固定的锁文件、经验证的包仓库、禁用的安装脚本、来源证明检查 | 依赖审查条目、锁文件 diff、构建证明 |
| 入站许可证 | copyleft 或无许可证代码随产品分发 | 对直接与传递组件执行许可证门禁，仅允许书面例外 | 每次发布的许可证报告；经签署的例外，注明负责人与到期日 |
| 出站许可证与署名 | 产品发布时缺少必需的声明，或条款不兼容 | 分发根目录的 `LICENSE`、生成的声明文件、入站与出站兼容性检查 | 含许可证与声明文件的发布归档；SBOM |
| 个人数据与遥测 | 无限制收集将带来监管与信任风险 | 收集前的用途审查、事件 schema 允许列表、最小化、同意门禁 | 数据清单行与已批准的事件 schema |
| 数据主体请求 | 数据位于日志、备份或处理者处，导致请求被遗漏 | 已发布的运行手册、完整的检索图谱、处理者删除条款 | 含日期、已检索系统与完成情况的请求日志 |
| 漏洞报告 | 报告丢失，或在用户能够打补丁之前即披露 | 受监控的渠道、确认与分诊期限、禁发期、带 CVE 编号的公告 | 报告时间戳、公告、CVE 编号、已署名报告者 |
| 发布流水线 | 未经审查或未签名的制品到达用户 | 必需的审查门禁、签名制品与来源证明、最小权限部署身份 | 显示门禁与签名验证的流水线运行记录 |
| 第三方代码 | 本地补丁在下次供应商更新时丢失，或上游缺陷随产品发布 | 记录许可证与版本的供应商边界；上游报告；有记录的 fork 补丁 | 供应商清单条目；上游问题单引用；fork 补丁文件 |

## 反模式

| 反模式 | 为何失败 | 修复 |
|---|---|---|
| 扫描无发现却无人负责 | 扫描器仅能够证明其规则未匹配；无负责人与日期的发现项永远不会关闭 | 指定严重程度、负责人与期限；登记已接受风险 |
| “稍后再轮换密钥” | 泄露的长期凭据在任务被推迟期间仍然有效 | 保留证据并报告；取得 AU-1/AU-2 同意后 24 小时内吊销或轮换，调查结束并经同意后再清理 |
| 一个共享的管理员凭据 | 一次泄露即授予所有操作，且无法归因 | 每个服务、任务与环境一个限定范围的凭据 |
| 提交 `.env` 文件并称为“临时” | 文件删除后历史仍保留该值 | 以 `.gitignore` 忽略真实文件，只提交名称，扫描历史 |
| 仅在界面中执行授权 | 直接调用 API 将绕过被隐藏的按钮 | 每个请求均实施服务端对象级检查 |
| 自研密码学或会话处理 | 细微缺陷对审查与测试均不可见 | 使用框架与经批准的库；要求密码学审查 |
| “其在仓库托管平台上公开，因此可以免费使用” | 无许可证的仓库保留所有权利 | 许可证门禁：识别 SPDX 条款，否则拒绝该包 |
| 手工维护的 SBOM | 第一次依赖变更即失准，并掩盖新组件 | 在 CI 中自锁文件生成，并附至发布 |
| “先添加一个分析字段，以后再审查” | 字段级收集将绕过用途限制与审查 | 部署前完成事件 schema 审查并登记清单行 |
| “内部工具，因此无需威胁模型” | 内部工具将变得可访问，而管理工具持有最高权限 | 同样的触发条件与默认值；按网络已被攻陷的假设建模 |
| 严重修复留至下一个计划发布 | 利用窗口将开放整个发布周期 | 7 个自然日内发布计划外补丁 |
| 静默安全修复 | 用户无法评估暴露面，研究人员将重复报告 | 公告、CVE 编号、变更日志条目、署名 |
| 修复发布之前即公开 | 报告公开期间用户将被利用 | 遵守禁发期，协调发布日期，随修复一并发布 |
| 就地修改内置的第三方代码 | 下次供应商更新时补丁将消失 | 报告上游，或维护有记录的 fork 补丁 |
| 在聊天线程中接受风险 | 无负责人、无到期日，下一位审查人亦无法找到记录 | 风险登记册条目包含负责人、到期日与补偿性控制措施 |

## 审查清单

- [ ] 每个新增或变更的信任边界均有威胁模型，或有一行“未跨越边界”的说明。
- [ ] 资产、入口点与滥用场景均有明确名称，并给出控制措施与残余风险。
- [ ] 服务端校验覆盖每个新输入的类型、长度、范围与格式。
- [ ] 输出按上下文编码；查询已参数化；shell 调用避免插值。
- [ ] 授权按资源与租户执行，并非仅在界面中执行。
- [ ] 安全默认值已开启：拒绝、私有字段、关闭的开关、生产环境不输出调试信息。
- [ ] diff 中无机密值、密钥、令牌、`.env` 文件或携带凭据的连接字符串。
- [ ] 每个变更过的凭据均有范围、负责人、轮换间隔与下次轮换日期。
- [ ] CI 机密已打码、按环境限定范围，并且不提供给不受信任的 fork 构建。
- [ ] 机密扫描覆盖提交、拉取请求、历史与构建日志。
- [ ] 每个新依赖均经过审查、被固定，并带有允许的许可证或有记录的例外。
- [ ] 依赖漏洞扫描已按 `testing-and-quality-conventions` 的 gates 运行；需要例外时，均有书面缓解措施或到期豁免。
- [ ] SBOM 与声明文件已重新生成并附至发布。
- [ ] 个人数据字段均有清单条目，包含用途、保留期限、接收方与区域。
- [ ] 日志、URL、分析事件、测试夹具或截图中均不出现 PII。
- [ ] 处理者、跨境或同意相关变更已实施隐私审查，需要时已经过法务审查。
- [ ] 发现项均有严重程度、负责人与期限；已接受风险均有到期日。
- [ ] 漏洞报告在承诺的时间线内确认收到并完成初步分诊。
- [ ] 第三方代码报告至上游，而非手工修改。
- [ ] `SECURITY.md` 内容、公告与发布说明与实际发布状态一致。

## 示例

<example>
新增文件上传端点：资产为用户文件与存储凭据；信任边界为浏览器至 API。滥用场景为超大文件、可执行内容、
解压缩炸弹与路径遍历。控制措施为内容类型允许列表、大小上限、图片重新编码、存储于 web 根目录之外，以及
提供前扫描。残余风险及其负责人写入威胁模型说明。
</example>

<example>
某一依赖使用 LGPL-3.0，许可证门禁将其转入审查。审查记录动态链接、未修改源码、声明义务与负责人，并由
法务在合并前批准使用。现有 MIT 替代方案能够满足需求的，优先采用该方案并取消审查。
</example>

<example>
分析团队要求在结算事件中加入 `user_email` 属性。隐私审查予以拒绝：该事件仅需内部账户标识符与订单金额。
事件 schema 已更新，用途已记录，该属性从未进入生产环境。
</example>

<example>
一名研究者在周五报告远程代码执行漏洞。在 2 个工作日内确认收到，5 个工作日内完成初步分诊，并评为严重。
修复在 7 个自然日内发布，CVE 编号已分配，公告随发布一并发布，包含受影响版本与修复版本，以及报告者
署名。
</example>

<example>
构建日志打印出了部署令牌。应当先停止操作、保留证据并报告；取得 AU-1/AU-2 同意后于 24 小时内吊销并轮换
该令牌。随后审计其使用情况；调查结束并按 AU-1 取得明确同意后，方可清理日志、从全部制品或缓存中移除该
值，并记录该事件。不得将重写历史作为第一步；无论是否重写，令牌均仍然有效。
</example>
