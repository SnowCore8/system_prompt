# 代码风格规范

风格、布局、依赖、配置与错误处理方面的失效会相互叠加：diff 中的机械噪声将掩盖审查者本应察觉的行为变更；
模块之间隐含的边界将转化为后续每次变更均须改动的隐藏耦合；环境差异配置将使服务在本地环境与生产环境的表
现不一致；被吞掉的错误将使可见故障转化为数日后才显现的静默故障。每一问题以一条规则预防，成本很低；发布后
再诊断，代价高昂。本 skill 规定一套决策流程与完整规则集，覆盖代码的机械层面与结构层面：格式化、源码树与
模块边界、依赖、配置、错误与日志策略，以及生成代码与第三方代码。其服务对象为搭建仓库的作者与评判 diff 的
审查者，因为同一套规则既决定事实的放置位置，亦决定变更的安全性。上述规则与语言无关；各语言参考文档规定工
具默认值，项目配置作为事实输入，依“适用范围与优先级”使用。本 skill 适用于三种模式：项目启动时定义规则、依
规则审查变更，以及以一次范围明确的迁移修复既有仓库。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充：

1. 强制性的平台、法律、宿主与用户全局约束。语言语法、编译器与平台的硬性要求，均非可选事项。
2. 本 skill 的规则。格式化、目录布局、依赖、配置、错误与日志的规则，以本文件与 `references/` 为准；已配置
   的 formatter、linter 与 `.editorconfig` 属于项目事实，应当依上述规则使用。
3. 既有项目约定与事实。制定规则前，代理应当先阅读代码、配置、构建脚本与有文档的项目风格指南；上述内容属
   于事实输入，依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- 命名由 `naming-conventions` skill 管辖。标识符、文件与目录名、大小写以及命名表不属于本 skill 的范围；本
  skill 使用上述名称，并将其应用于布局、格式与策略。重命名与重新格式化同时实施的，应当分别实施，因重命名
  属于 `naming-conventions` skill 的管辖范围。
- 注释与文档注释由 `comment-conventions` skill 管辖。formatter 决定注释块的缩进方式；注释是否应当存在，由
  该 skill 决定。
- 独立文档及其模板由 `documentation-conventions` skill 管辖。配置参考页与运行手册属于文档；其描述的配置键，
  遵循本 skill。
- API 契约设计，以及数据库 schema 与数据保留流程，由 `api-and-data-conventions` skill 管辖。本 skill 管辖服
  务内部的通用代码技艺，不管辖对外契约的形态。
- 测试、质量门禁与开发环境由 `testing-and-quality-conventions` skill 管辖。formatter 或 linter 门禁位于 CI；
  各项门禁是否具有强制性，由该 skill 决定。
- CI/CD 流水线、发布、可观测性字段 schema、事故响应与备份由 `release-operations-conventions` skill 管辖。
  日志级别与日志内容策略属于本 skill；日志的存储位置、索引方式与告警规则，由该 skill 负责。
- 常驻指令文件（`AGENTS.md`、`CLAUDE.md`、`QWEN.md`）由 `system-prompt-authoring` skill 管辖；运行时与产品
  提示词由 `prompt-authoring` skill 管辖。上述文件不构成应用代码，不遵循本 skill 的 formatter 或 lint 规则；
  依风格审查上述文件时，应当依其所属 skill 的规则实施。
- 依赖准入的通用标准由本 skill 裁定：维护状况、移除路径与传递依赖规模是否记录；漏洞、许可证、原生代码、安装
  脚本与供应链证据由 `security-compliance-conventions` 裁定。传递依赖规模是风险信号，不得单独作为拒绝理由。
- 生成代码与第三方引入代码不受编辑要求约束，但仍受下列规则约束：应当保留生成标记，保持第三方引入文件不被
  改动，将两者排除于 formatter 与 linter 之外，并以重新生成或重新引入替代编辑。
- 强制手段应当留在仓库内。缺乏 formatter、linter、测试或审查检查点的规则，将在一个季度内失效；应当将校验
  置于变更发生处，使其在 CI 中可见，并在指南中写明命令。
- 风格变更即代码变更。代理应当以一次范围明确的变更实施，不得将其混入行为变更的 diff；应当更新强制该风格
  的 formatter 或 linter 配置，于同一次交付中更新受影响的文档，并在干净检出的代码上验证。代理不得重新格式
  化因其他原因修改的文件，因审查者无法将两处变更分开。
- 强制规则冲突的，代理应当先说明冲突，遵循优先级更高的层级；无法判定的，报告用户裁决，不得自行选定。
  非强制的项目约定冲突，可以说明冲突并记录所选约定。对两项规则各执行一部分的，视为缺陷。

## 流程

1. 确定已配置的权威来源。代理应当定位 formatter 与 linter 配置、`.editorconfig`、包 manifest、锁文件、配
   置加载器与 CI 命令；项目有风格指南的，应当阅读该指南。
2. 对关注点进行分类。代理应当判断关注点属于格式化，布局或模块边界，依赖，配置，错误或日志策略，抑或生成
   代码与第三方代码。跨类别的变更构成一份计划，而非一次编辑；同时符合两个类别的关注点，应当实施两次变更，
   各自验证。
3. 判断 linter 是否已强制该关注点。已有规则的，应当修正违规，不得另行记录一条约定；无规则的，应当于独
   立的配置变更中新增一条规则，或者将约定记录于项目风格指南。
4. 实施最小的配置或代码变更。应当优先采用一行配置或一次范围明确的代码变更；不得重新格式化无关文件，亦不
   得于风格修复中升级工具版本。
5. 在干净检出的代码上验证。代理应当依项目文档中的命令运行 formatter 校验、linter、构建与相关测试，随后粘
   贴真实输出与退出码。本地通过而 CI 失败的校验，说明工具版本或检出状态不一致；应当先对齐二者，再修改规则。
6. 于同一次变更中更新文档与配置。一条规则需要其强制配置与项目风格指南中的一行说明；一个依赖需要 manifest、
   锁文件与许可证声明；一个配置键需要参考页。
7. 审查 diff。代理应当确认仅预期文件被改动，无生成文件或第三方引入文件被编辑，无机密出现，无行为变更隐藏
   于格式化之中，且该变更可以单独回滚。交付中应当说明验证命令及其退出码，不得仅声称其通过。

## 核心规则

- **空白由 formatter 负责。** 代理应当运行已配置的 formatter，不得手工折行、对齐或重新缩进；手工编辑将被
  下一次运行撤销，其间仅产生审查噪声。例外仅限 formatter 不覆盖的宏体等区段，且应当按该工具文档手工处理。
- **行宽仅有一个取值，且应当在配置或审查规则中设定。** 代理应当自 formatter 配置或项目审查规则读取行宽，
  并依其折行；字符串字面量、URL、哈希与数据表不得拆分，因拆分将改变含义。
- **机械变更应当依工具输出审查，不得依肉眼审查。** 纯格式化变更在其描述中仅应包含 formatter 命令，不得包
  含其他内容；行为变更不得夹带重排。
- **导入顺序表达依赖结构。** 代理应当按标准库、第三方、项目分组排列 import，组内排序，并禁止通配符导入；
  该顺序使边界违规于测试失败之前即可见。
- **依赖仅指向一个方向。** 领域与应用代码不得导入基础设施；适配器实现领域拥有的接口，因此替换数据库或队
  列永远不会影响业务规则。判据由 `architecture-and-design-conventions` 裁定，本 skill 仅负责以 lint 与 CI 强制。
- **每个模块应当声明自身的公开接口面。** 应当暴露命名导出，其余内容不可导入，并且仅应通过模块接口面导入其
  他模块；导入内部路径属于边界违规，不构成捷径。接口面与边界的判据，同样由
  `architecture-and-design-conventions` 裁定。
- **仅应使用已声明的依赖。** 导入某一包，系因 manifest 已声明该包，不得因另一依赖安装了该包；应当导入已声
  明者，声明已导入者。
- **复用优先于手写，新增依赖仍属设计决策。** 标准库、现有依赖或维护良好的第三方库能够胜任的，不得编写替代
  实现；准入仍须检查维护状况与移除路径，但费用、安装占用与传递依赖数量不构成拒绝优质库的理由，证据记录于
  拉取请求中；漏洞、许可证与供应链证据由 `security-compliance-conventions` 裁定。
- **配置仅应有一套有文档的优先级顺序。** 应当依命令行标志优先于环境变量、环境变量优先于配置文件、配置文件
  优先于编译期默认值的顺序应用，于启动时加载并合并一次，并禁止模块自行读取环境。
- **应当于启动时校验配置一次。** 应当按 schema 检查必填键、类型、范围与组合，指出失败的键，并拒绝启动，不
  不得待负载到达后才失败。
- **机密不得进入代码、配置、日志或错误。** 应当按名称引用机密，并于运行时自安全团队拥有的存储中解析；在所
  有可能被写入的位置掩码或省略。
- **仅应捕获能够处理的错误。** 处理失败的，应当补充上下文并保留原因，或者使其继续传播；空 catch 与记录日
  志后再抛出，均将破坏下一位响应者所需的证据。
- **仅应记录一次结构化日志，并使用能够说明何人应当行动的级别。** 应当于决定结果的边界输出稳定字段；ERROR
  意味着必须有人行动，任何日志行均不得包含机密或未脱敏的个人数据。
- **生成代码不得手工编辑。** 修改生成器、schema 或模板后，应当重新生成；本地补丁应当置于生成树之外，附负
  责人与上游引用，并于上游修复后移除。

## 风格决策矩阵

| 关注点 | 默认规则 | 规则所在位置 | 示例 |
|---|---|---|---|
| 格式化 | 已配置的 formatter 重写文件；审查者无需争论空白 | formatter 配置与 pre-commit hook | `ruff format`, `prettier --write`, `gofmt -w` |
| 行宽 | 依 formatter 配置或审查规则确定一个值；无行宽规则的语言依审查规则 | formatter 配置或审查规则 | `line-length = 100`, `"printWidth": 100` |
| 导入顺序 | 标准库、第三方、项目；组内排序 | linter 规则或 formatter | Ruff `I001`, `import/order`, goimports |
| 块结构 | 可选花括号处均写花括号；嵌套超过三层即行提取 | linter 规则与审查 | `curly`, `max-depth`, 提前返回 |
| 模块接口面 | 命名公开导出；跨边界时内部内容不可导入 | 包配置与 lint 规则 | `__all__`, `internal/`, `pub(crate)` |
| 依赖方向 | 基础设施依赖领域；领域不导入基础设施 | 导入规则与审查 | `dependency-cruiser`, `import-linter` |
| 新依赖 | 复用优先；标准库或现有依赖无法胜任时，选择维护良好的库，准入时核查健康度、许可证与漏洞 | 拉取请求检查清单 | `cargo deny`, `pip-audit`, 许可证扫描 |
| 版本锁定 | 应用锁定精确版本；库声明范围；提交锁文件 | manifest 与锁文件 | `package-lock.json`, `uv.lock`, `go.sum` |
| 依赖版本单一来源 | 多包仓库将同一依赖的版本集中声明一次；子包仅作引用 | version catalog 或 dependencyManagement | `libs.versions.toml`, `<dependencyManagement>` |
| 配置策略 | 标志优先于环境变量、环境变量优先于文件、文件优先于默认值；启动时校验 | 配置加载器与 schema | `APP_PORT` 覆盖 `config.yaml`；`APP_PORT=0` 以非零退出 |
| 错误包装 | 增加操作上下文，保留类型化原因，于边界记录一次日志 | 代码约定与 lint 规则 | `raise InvoiceSyncError(...) from exc`, `%w` |
| 错误分类 | 领域错误与系统错误分开；分类决定 catch 与日志级别 | 代码约定与审查 | 领域失败返回结果；系统失败于重试耗尽后记 ERROR |
| 日志内容 | 带稳定字段的事件；不包含机密、令牌或完整个人数据 | 日志器配置与审查 | `logger.error("invoice.sync_failed", error_code="E_SYNC")` |
| 生成代码 | 重新生成，不得编辑；提交的输出存在差异时 CI 失败 | 生成器配置与 CI 任务 | `git diff --exit-code -- gen/` |

## 维度索引

每个维度的详细规则、示例与边界情况见 `references/` 中对应的维度文件；维度列中的编号就是该文件中的节号。

| 维度 | 首条规则 | 详情 |
|---|---|---|
| 1. 代码风格与格式化 | 一个已配置的 formatter 负责空白；行宽、引号与导入顺序属于配置值或审查规则。 | `references/dimensions.md` 第 1 节 |
| 2. 布局、模块与边界 | 仅选定一个组织轴；模块接口面与依赖方向的判据由 `architecture-and-design-conventions` 裁定，本 skill 仅以 lint 与 CI 强制。 | `references/dimensions.md` 第 2 节 |
| 3. 依赖管理 | 仅声明直接依赖，提交一个锁文件，并依书面标准准入依赖。 | `references/dimensions.md` 第 3 节 |
| 4. 配置管理 | 固定优先级顺序，于启动时校验合并后的结果，并使机密远离一切来源。 | `references/dimensions.md` 第 4 节 |
| 5. 错误处理与日志 | 带上下文包装并保留原因；仅记录一次结构化日志，字段稳定且不含个人数据。 | `references/dimensions-errors.md` 第 5 节 |
| 6. 生成代码与第三方代码 | 标记生成输出，不得编辑，于 CI 中重新生成，并隔离带来源记录的第三方引入代码。 | `references/dimensions-errors.md` 第 6 节 |

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 手工将行折至 formatter 忽略的宽度 | 下一次运行将重新合并，diff 成为双重噪声 | 于配置中设置宽度，由 formatter 折行 |
| 于行为变更中重新格式化整个文件 | 真正的变更淹没于噪声，回滚仅能全有全无 | 先行以独立的范围变更落地格式化 |
| 通配符导入，如 `from x import *` 或 `import java.util.*` | 隐藏名称来源，依赖变化时即遭破坏 | 显式导入名称并强制该规则 |
| 将 `utils/`、`helpers/` 或 `common/` 作为无主目录 | 吸引无关辅助代码，随后出现循环依赖与不清晰的归属 | 命名职责，并为模块指定负责人 |
| 以抑制注释修复导入循环 | 耦合仍在，下一个循环亦将被隐藏 | 以接口反转，或将共享类型下移 |
| 直接导入传递依赖 | 中间依赖变化时即行消失，且未被声明 | 声明该依赖，或使用拥有该依赖的 API |
| 删除锁文件以清除冲突 | 安装未经审查的版本并破坏可复现性 | 解决冲突、重新生成并审查锁文件 diff |
| 于生产构建中使用 `latest` 或未锁定的工具 | 构建将在未提交、未审查的情况下变化 | 锁定版本或镜像摘要，并有意识地升级 |
| 于业务逻辑中按环境分支 | 测试覆盖一个分支，生产却运行另一分支 | 于边缘加载类型化配置并注入 |
| 将必填配置键默认成空值或看似合理的值 | 服务将启动，并于第一个请求时失败，而非于启动时失败 | 于启动时校验并指出缺失的键 |
| “临时”提交 `.env` 或机密值 | 临时需求结束后，该值仍留在历史中 | 引用机密存储并忽略本地文件 |
| 空 catch，或每一层均 catch、记录日志后再重抛 | 失败消失或重复，同时原因丢失 | 处理它、以上下文包装它，或传播它 |
| 记录完整请求、响应或插值后的个人数据 | 将个人数据复制进日志存储与告警 | 仅记录稳定字段、ID 与脱敏值 |
| 直接编辑生成文件 | 下一次重新生成将无痕删除该编辑 | 修改生成器输入并重新生成 |
| 对生成树或第三方引入树运行 formatter | 重新生成产生噪声，上游补丁冲突 | 排除上述树，并使排除项可见 |
| 提交流水线可以重建的构建输出 | 每个分支均在无来源的二进制制品上冲突 | 忽略该目录，并于流水线中重建 |

## 审查清单

- [ ] formatter 校验通过，且未重写任何文件。
- [ ] 已配置的 linter 依项目规则集通过。
- [ ] 无代码行超过配置宽度，亦无手工折行的行将被重新合并；规则允许的长字面量、URL、哈希、数据表，以及无行宽规则的语言，不在此限。
- [ ] import 已分组并排序；无通配符导入，亦无未使用的 import。
- [ ] 模块接口面与依赖方向符合 `architecture-and-design-conventions` 的判据，并已由 lint/CI 强制。
- [ ] 不存在导入循环；依赖自基础设施指向领域。
- [ ] 每个被导入的包均在 manifest 中直接声明。
- [ ] 新增或删除依赖带有准入证据与锁文件变更。
- [ ] 多包仓库中同一依赖的版本仅声明一次。
- [ ] 锁文件已提交，CI 以冻结模式安装。
- [ ] 配置优先级有文档，合并后的配置于启动时校验。
- [ ] 必填配置于调用点无静默回退。
- [ ] 代码、配置、fixture、日志与示例中均不出现机密值。
- [ ] 捕获的错误增加上下文并保留原因；无空 catch，亦无记录后再抛出。
- [ ] 错误按领域/系统分类，领域错误不记 ERROR 级别。
- [ ] 内部失败于边界映射为公开契约的错误码，不存在并行的目录。
- [ ] 日志为结构化，携带约定字段，并使用与“何人必须行动”相匹配的级别。
- [ ] 日志行中不出现机密、令牌、完整请求体或未脱敏的个人数据。
- [ ] 生成文件带有标记，且系重新生成而非编辑所得；第三方引入文件未被改动。
- [ ] 描述该行为的配置与文档于同一次交付中变更。
- [ ] 该变更系一次范围明确的提交，可以在不影响其他关注点的情况下回滚。
- [ ] diff 中不出现构建输出、缓存或第三方引入文件，除非其为经过审查的输入。

## 示例

<example>
一个拉取请求修改了一个函数，还重排了另一个文件的 400 行。应当将其拆分：将对第二个文件的 formatter 运行作为
仅含 formatter 命令的机械变更提交，随后针对干净的文件落地行为变更，使 diff 显示逻辑。
</example>

<example>
一个服务自环境读取 `APP_DATABASE_URL`，缺失时回退为空字符串。应当将回退替换为启动时校验：指出该键并以非零
状态退出；以一个使用 `db.example.test.invalid` 且不含真实地址的测试 fixture 证明该失败。
</example>

<example>
一个功能模块导入了另一个功能的仓储，以复用查询。应当将该查询移至领域包拥有的接口之后，或者将共享类型提升
至其自身的模块；不得导入另一个功能的内部路径。
</example>

<example>
一个生成的 API 客户端需要超时字段。应当修改生成器模板或 schema 输入，重新生成，并将输入与输出一并提交；生
成文件不得被手工修改。
</example>

<example>
一个依赖承诺替代 30 行解析代码。应当先检查标准库与现有依赖，再检查维护状态、许可证与安装占用；于拉取请求中
将理由记录于 manifest 与锁文件变更之旁。
</example>

## 参考资料

阅读 [references/dimensions.md](references/dimensions.md)，了解维度 1-4 的完整规则集；阅读
[references/dimensions-errors.md](references/dimensions-errors.md)，了解维度 5-6。每个维度各有一节编号章节，
包含默认值、正例与反例以及边界情况。搭建仓库、选择边界，或决定 formatter 与 linter 未覆盖的策略时，应当阅读
对应文件；更改某一维度的规则前，应当先阅读对应章节。

阅读 [references/languages.md](references/languages.md)，了解各语言的 formatter、linter、行宽与导入顺序默认
值。向项目添加工具前，应当阅读对应语言行；仓库跨多种语言时，应当阅读整个矩阵，并将项目配置的值作为该行的
实际取值。项目无已配置工具链时，应当自其主要语言对应的矩阵行开始，且在添加任何第二条规则之前，先添加
一个 formatter。
