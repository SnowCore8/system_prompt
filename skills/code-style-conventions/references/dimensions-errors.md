# 代码风格：错误、日志与生成代码

本文件承载 `code-style-conventions` 的维度 5 与 6；维度 1-4 见 `dimensions.md`。每一编号章节规定一个维度的默认值、决策规则与边界情况；代理仅应阅读与关注点匹配的章节。

## 5. 错误处理与日志

错误与日志是生产故障的唯一见证。丢失原因的错误、吞掉错误的 catch，或无字段的日志行，将把事故变为猜测、
把修复变为搜索。应当于能够作出决定之处处理错误，于结果已知之处记录日志，因既无法决定亦无法报告的层仅会
增加噪声。

- 每层应当仅选择一种错误风格：异常用于意外且不可恢复的情况，结果值或错误值用于预期的领域结果，例如校验失
  败、未找到或支付被拒。不得于一个 API 中混用两种风格，并应当于模块的公开接口面上说明所选风格，使调用方
  知道应当 catch 还是检查返回值。
- 按来源对错误分类：领域错误是预期的业务失败（校验失败、未找到、支付被拒），由调用方处理；系统错误是意外
  的运行失败（连接失败、依赖超时、违反不变量），由响应者处理。分类决定日志级别：领域错误不记 ERROR；系统
  错误于放弃重试时记 ERROR。调用方取消或截止属于预期情况，不记 ERROR。分类应当写在模块公开接口面上，与所
  选错误风格一并声明。
- 不得吞掉错误。仅应于为了处理、补充上下文或转换为结果时 catch。空 catch、每层均记录并重抛的 catch，以及
  把所有失败都映射为一个通用错误的 catch-all，将破坏堆栈、错误类型，以及响应者区分超时与校验缺陷所需的证
  据。应当捕获可用的最窄类型，因捕获基类将把编程错误变为已处理情况，并掩盖修复。
- 以上下文包装并保留原因：Python 用 `raise InvoiceSyncError(invoice_id=...) from exc`，Go 用
  `fmt.Errorf("sync invoice %s: %w", id, err)`，Java 用
  `throw new InvoiceSyncException("...", cause)`。应当加上操作与安全标识符，不得以丢弃堆栈的格式化字符串
  替换原因。
- 为边界错误提供稳定错误码：每个原因一个错误码，机器可读，仅在展示时本地化。应当于 API 边缘把内部错误映射
  为公开错误码，不得向客户端泄露堆栈跟踪、SQL、内部主机名或异常类名，因上述内容将暴露拓扑与实现细节。公开
  错误码目录、其信封以及错误码值，属于 `api-and-data-conventions` 定义的外部契约的一部分；应当于边界把内部
  失败映射到上述错误码，不得于此处维护平行目录。
- 于决定结果的边界仅记录一次事件，并带上稳定字段，例如 `timestamp`、`level`、`event`、`service`、
  `trace_id` 与 `error_code`。较低层返回错误，不得记录上层将再次记录的内容；重复日志行将放大日志量并使首
  次出现变得含糊。事件名应当稳定且基数低，可变数据应当置于字段中，不得置于事件字符串里。
- 使用能够说明何人必须行动的级别：ERROR 用于需要人处理的用户可见操作失败，WARN 用于值得一看的降级但已处
  理情况，INFO 用于生命周期与业务事件，DEBUG 用于在生产中保持关闭的诊断信息，TRACE 仅用于短期调查。级别
  不是装饰，任何日志级别均不得替代指标或告警。级别属于结果而非异常类型：同一超时于被重试时为 WARN，于结
  束请求时为 ERROR。
- 不得记录机密、令牌、密码、cookie、Authorization 头、会话标识符、加密密钥、完整请求或响应体，或完整个
  人数据。应当记录标识符或脱敏值：用 `user_id` 而非邮箱，用 `a***@example.test.invalid` 而非真实地址，
  并且仅在业务规则要求时记录最后四位数字。
- 返回可操作的错误消息：说明什么失败了、调用方或用户可以做什么，包含关联 ID，并把堆栈跟踪与内部拓扑留在
  日志中。启动时，应当以阻塞启动的配置键或依赖名失败，不得以一条使响应者于无线索的情况下去翻日志的通用
  消息失败。应当于日志中写出组件、操作与关联 ID；于响应中仅写失败的步骤与下一步操作。

| 正例 | 反例 | 原因 |
|---|---|---|
| 增加了上下文，并保留原始原因 | 裸重抛，或仅带消息的新错误 | 错误链指向真正的失败 |
| 带恢复路径的已处理 catch | 空 catch 块 | 失败或得到修复，或得到暴露 |
| API 边缘的稳定公开错误码 | 把原始异常作为 HTTP 500 返回 | 客户端可以行动，内部细节保持私有 |
| 带命名字段的结构化事件 | 含五个值的插值句子 | 查询与告警可以匹配字段 |
| 仅在必须有人行动时用 ERROR | 每个失败都以 ERROR 记录 | 严重级别保持其含义 |
| 日志行中用 `user_id` | 日志中出现邮箱、电话或地址 | 个人数据不进入日志存储 |
| 于结果边界记录一行日志 | 同一错误于四层分别记录 | 日志量保持低，原因保持清晰 |
| 启动时指出阻塞的键 | 通用的“无法启动”消息 | 响应者无需搜索即有线索 |

调用方取消、调用方截止与关闭信号属于预期情况而非错误；依赖超时属于系统错误（见上）。重试不得于每次尝试
时发出新的错误行而无最终结果。库代码返回
错误，由调用方决定记录什么。日志与跟踪的字段 schema、仪表盘与告警规则属于发布与运维；本节负责级别选择与
内容策略。应当把失败分为可重试与致命，仅于一个边界重试，并带退避与上限，因重试风暴将成倍放大错误量，可能
把部分中断变为全面中断。记录每次探测的健康检查属于噪声，而隐藏不健康原因的健康检查属于盲点。

## 6. 生成代码与第三方代码

生成代码与第三方引入代码归生成器或上游项目所有，不归本项目的风格规则所有。应当将两者均视为带来源的构建
输入，否则下一次重新生成将静默抹掉所有手工编辑。规则很简单：生成代码通过修改其来源而变化，第三方引入代码通
过修改其版本而变化。

- 应当将生成输出置于已声明的目录或文件名模式中，例如 `gen/`、`generated/`、`*.pb.go`、
  `*_generated.py` 或 `*.g.dart`，并加上机器可检测的头部，写明生成器、其版本与命令。应当使用生态标记，例如
  `// Code generated by protoc-gen-go. DO NOT EDIT.` 或 `@generated`，使工具自动排除文件，不得依赖手工维
  护的列表。
- 不得手工编辑生成代码。修改 schema、模板或生成器调用，重新生成，并把输入与输出一并提交。手工编辑仅在下一次生成
  之前有效，随后不留审查轨迹地消失，因此他人一旦重新生成，修复即丢失。应当于头部记录生成器版本，使审查
  者能够看出文件由哪次重新生成产生。
- 本地改动无法避免的，应当将其置于生成树之外：`patches/` 下的补丁文件、适配器，或带锁定上游版本、负责人、
  issue 链接与移除条件的包装层。构建应当应用该补丁，补丁无法应用的，CI 应当失败，不得发布静默的分歧。
- 审查输入，不得审查生成的行。应当审查 schema 或模板 diff、生成器版本升级，以及重新生成的摘要。输入变化时
  生成 diff 很大属于预期，输入未变时则可疑，此即逐行审查生成代码无法提供的信号。
- 应当于 CI 中重新生成，并对漂移失败。于任务中运行生成器，以 `git diff --exit-code` 或工具自身的校验模式比
  较工作树与已提交输出，并报告能够重现该输出的命令。过期的生成代码应当成为构建失败，不得成为一条后来被静默
  否定的审查发现。生成器自带校验模式的，应当使用该模式；`git diff --exit-code` 属于无该模式的生成器的回退
  方案。
- 应当把第三方引入代码置于隔离目录，并附来源：上游来源、版本或提交、许可证文本，以及引入的理由，置于
  manifest 或 README 中。应当通过一个边界导入，使后续替换或升级仅涉及一个文件；复制的代码片段同样按第三方
  引入代码处理，需要相同的来源与许可证记录。应当记录该依赖为何被引入而非直接声明，并于每次升级时重新审视该
  理由。
- 应当把生成代码与第三方引入代码排除于 formatter、linter、覆盖率阈值与风格审查之外，并将排除项保留于可审
  查的工具配置中。是否排除测试、搜索或安全分析属于另一项决定，因风格豁免不意味着未阅读的代码即未检查的代
  码。每个排除项均应当带注释，写明生成器或上游项目，使后来的读者能够看出该文件为何被排除在外。
- 区分生成源码与构建输出。锁文件或生成的客户端应当提交，因其属于可复现与审查的输入；构建目录、缓存、编译
  后的二进制与包管理器目录应当忽略并重建。提交的构建制品将于每个分支上变成合并冲突，且其来源不明。忽略规则
  应当置于仓库根，并确认干净克隆能够重建每一被忽略的制品。

| 正例 | 反例 | 原因 |
|---|---|---|
| 头部写明生成器、版本与命令 | 看起来像手写、无标记的文件 | 工具与读者能够识别并排除它 |
| CI 重新生成并 diff 已提交输出 | 手工提交过期的生成代码 | 漂移使构建失败，而非变成审查发现 |
| 带负责人与 issue 链接的补丁目录 | 手工编辑的第三方引入文件 | 补丁可见且可移除 |
| 带版本与许可证的第三方引入清单 | 无来源的第三方引入代码 | 升级与许可证问题均能够回答 |
| 生成树排除于 formatter 之外 | 格式化生成的客户端 | 重新生成不产生噪声 |
| 忽略并重建 `dist/` | 提交构建输出 | 二进制制品不产生合并冲突 |
| 审查生成器输入与版本 | 逐行审查生成的行 | 审查注意力放在决策所在处 |
| 带来源与许可证的复制片段 | 无许可证的上游代码副本 | 归属与许可证义务得到满足 |

生成的文档与迁移文件，属于 `documentation-conventions` 与 `api-and-data-conventions` 拥有的文档和 schema
变更；其仍然带有标记与来源。IDE 生成与脚手架输出属于生成代码，即使项目保留它们。重新生成必须具有确定性：锁定
生成器版本、排序其输入，并从输出中排除时间戳、绝对路径与机器名，使无变化运行不产生 diff。生成客户端的公开
API 属于 API 契约，因此接口与数据审查覆盖 schema，代码审查覆盖其周围的适配器与错误映射。生成器无法锁定
的，应当于 CI 中记录输出哈希，使无法解释的重新生成导致构建失败。
