# 代码风格维度

本文件与 `SKILL.md` 配合使用。每一编号章节规定一个维度的默认值、决策规则与边界情况；已配置的工具与有文档
的项目约定属于事实输入，本 skill 未规定时由其补充规则，已规定时以本 skill 的规则为准。代理仅应阅读与关注点
匹配的章节，并应当先阅读 `SKILL.md`，了解优先级顺序以及与其他 skill 的边界。每一章节均说明一项默认值、在
具备条件时强制执行该默认值的工具，以及决定该默认值何时不适用的边界情况。

## 1. 代码风格与格式化

格式化是机器可以完全裁决的唯一风格类别。每种语言与文件类型应当配置一个 formatter，在所有位置运行该
formatter，并将审查注意力集中于工具无法作出的决定：行宽、结构与例外。判断一条格式化规则的标准，为机器
能否裁决该规则；需要人争论的，该规则实际上属于结构规则或命名规则。

- 每种文件类型应当仅指定一个 formatter，将其配置保存在仓库中，并于构建镜像或 pre-commit hook 中锁定工具
  版本。两个重写同一文件的 formatter 将产生无休止的变更循环，未锁定的 formatter 版本将于升级当日重新格式
  化无关文件。应当于 CI 中运行校验模式、于本地运行写入模式，二者使用同一已锁定的命令，使格式化失败于审
  查之前即被捕获。
- 应当将 formatter 输出视为构造上正确。审查者不认可某一折行参数的，应当修改行宽或代码本身；手工编辑格式
  将被下一次运行撤销，浪费两次审查，并掩盖作者是否理解规则。配置变化时应当审查配置 diff，因该 diff 决定
  后续上百个格式化 diff。
- 行宽应当于 formatter 配置中仅设置一次：Black 与 Ruff format 为 88，Prettier 为 80，rustfmt 为 100，
  google-java-format 为 100，LLVM 与 Google clang-format 为 80，Microsoft clang-format 为 120，ktlint
  为 140，RuboCop 为 120。项目配置为上述每一数字提供实际取值；行宽不得按文件或按作者设置。
- 引号、分号、缩进与尾随逗号应当于配置中决定，不得于代码中决定。Black 与 Ruff format 将字符串统一为双引
  号，Prettier 默认使用双引号与分号，Go 要求制表符。对选择有异议的，应当作为项目级配置变更处理，不得于单
  个文件中内联覆盖。
- 应当按三个组排列 import：标准库、第三方、项目。组内排序，组间空一行，并禁止通配符导入。goimports、Ruff
  `I`、eslint-plugin-import 与 clang-format `IncludeBlocks` 强制分组；跨两个组的 import 往往说明模块边界
  有误。清理属于另一条规则：goimports 增删 import，Ruff `F401` 标记未使用的导入而 `I` 仅负责排序，isort
  于启用 `remove-redundant-aliases` 时删除冗余别名，ESLint `no-unused-vars` 标记未使用的绑定，clang-format
  从不删除 include。
- 应当保持块结构扁平：每行一条语句，花括号可选的语言中亦写花括号，以提前返回代替 return 之后的 `else`，
  嵌套超过三层即行提取。需要注释解释形状的代码块，属于待提取的函数。代码块无法容纳于一屏，或其头部注释
  描述的操作与周围代码不同的，应当提取。
- 应当以一条命令在整个代码树上运行 formatter，并于该配置中排除生成目录、第三方引入目录与构建输出目录。重
  新格式化生成代码将掩盖真正的重新生成 diff，格式化第三方引入代码将使每一上游补丁成为后续维护者无法解决
  的冲突。
- 应当于已提交的 `.editorconfig` 中设置编辑器默认值：UTF-8、LF 换行、文件末尾换行、除 Markdown 必要处之
  外无行尾空白，以及按语言的缩进。应当提交最小的共享 IDE 设置文件，或忽略 IDE 目录，因 formatter 无法修复
  某一编辑器以错误编码保存的文件。按自身设置保存时重新格式化的编辑器插件，是混合 diff 最常见的来源；应当
  提交其设置，或于该仓库中关闭该插件。

| 正例 | 反例 | 原因 |
|---|---|---|
| `ruff format` 置于 pre-commit hook 中 | 审查者于审查时要求使用 Black | 机器裁决空白；人审查逻辑 |
| 带 `end_of_line = lf` 的 `.editorconfig` | 一台机器使用 CRLF，另一台使用 LF | 换行不再出现于每一 diff 中 |
| Prettier 排除 `gen/` | 重新格式化生成的客户端 | 重新生成保持小且可审查的 diff |
| import 按标准库、第三方、项目分组 | 一个按字母排序的整块 | 依赖方向于测试失败之前即可见 |
| `pyproject.toml` 中 `line-length = 100` | 按 120 手工折行 | formatter 将重新合并手工折行的行 |
| 以提前返回代替 `else` 链 | 深层缩进的 `else` 分支 | 自上而下阅读并降低嵌套 |
| formatter 版本锁定于构建镜像中 | 使用 `latest` formatter 版本 | 格式化不会于未提交的情况下变化 |
| 每行一条语句 | 一行写 `x = 1; y = 2` | 调试器、覆盖率与 diff 分别处理语句 |

formatter 无法拆分长字符串、URL、哈希或 base64 数据块；应当使该行保持长，并记录该例外，不得为整个项目放
宽行宽。formatter 版本升级将重新格式化无关文件，因此应当将升级作为独立变更落地。Markdown 表格、生成数据
与压缩后的资源不属于本规则集的范围。无 formatter 的语言，下一条权威为 lint 规则；两者均无的，应当将规则
写入项目风格指南，并给出一个好的与一个坏的示例，使下一次变更遵循同一形态。格式化分歧应当通过一次带自身
审查的配置变更解决，不得要求审查者记住某一例外。formatter 与 linter 对同一文件意见不一致的，属于需要解决
的配置冲突，不得作为文件豁免处理。

## 2. 文件布局与导入格式

项目级目录、包/工作区与物理门禁由 `project-structure-conventions` 裁定；模块公开面、依赖方向与循环的架构判定由 `architecture-and-design-conventions` 裁定；本节只规定模块内部的文件与资源放置、单文件职责与 import 呈现。

- 模块内部文件与资源按一种布局放置；项目级目录、包与模块边界由 `project-structure-conventions` 裁定，
  冲突时以该 skill 为准。
- 每个文件应当只有一个内聚的变更理由。设置团队阈值，例如应用代码至 300 行警告、至 500 行拆分；即使未达
  行数，文件长出第二项职责时亦应拆分；生成文件与数据表不受该阈值约束，因其长度取决于生成器而非设计。阈值
  属于触发拆分讨论的审查信号，不构成阻止无关变更的硬性门禁。
- import 语句按标准库、第三方、项目分组排列；该顺序用于可读性与审查，不用于裁定谁依赖谁。
- 依赖方向、模块公开接口与循环的架构判定由 `architecture-and-design-conventions` 裁定，其物理落点与门禁由 `project-structure-conventions` 裁定；共享代码的物理归属由 `project-structure-conventions` 裁定；本 skill 只按已配置的 lint 与 CI 执行，不重新裁定边界。
- 移动文件或目录属于结构变更，应当与逻辑编辑分开；移动的目标与引用更新由 `project-structure-conventions`
  与 `refactoring-conventions` 裁定。
- 生成与第三方引入目录应当排除于 formatter 与 linter 之外；格式化它们会掩盖生成差异并使上游补丁难以维护。

| 正例 | 反例 | 原因 |
|---|---|---|
| 一个 220 行的 `billing/invoice.py` | 一个 1800 行、承担五种角色的 `billing/helpers.py` | 一个文件，一个变更理由 |
| import 按标准库、第三方、项目分组 | 一个按字母排序的整块 | 依赖在审查中可见，但不裁定方向 |
| formatter 排除 `gen/` | 重新格式化生成的客户端 | 重新生成保持小且可审查的 diff |
| 移动与编辑分为两次变更 | 将重命名隐藏于重构之中 | 每一变更均可单独审查与回滚 |

## 3. 依赖管理

依赖是项目随制品发布但不维护的代码。每一依赖均增加版本约束、许可证、攻击面与发布节奏，因此 manifest 属
于设计文档，而非便利清单。manifest 应当与锁文件一并审查；锁文件 diff 是实际发布内容的证据。

- 仅应依赖直接依赖。导入某一包，系因 manifest 已声明该包，不得因另一依赖安装了该包。传递导入将于下一次
  锁更新时消失，对 manifest 审查不可见，亦无法由依赖它的应用独立锁定。仅被测试或脚本导入的依赖，仍属于项
  目声明的依赖。
- 每个项目应当仅提交一个锁文件，并将其作为构建输入：`package-lock.json` 或 `pnpm-lock.yaml`、`uv.lock`
  或 `poetry.lock`、`go.sum`、`Cargo.lock`、`Gemfile.lock`、`composer.lock`。应当于 CI 中以 `npm ci`、
  `pnpm install --frozen-lockfile`、`uv sync --locked`、`cargo build --locked` 或
  `bundle install --frozen` 冻结模式安装；不得为使冲突消失而删除锁文件。应当于目标分支上重新生成并审查结
  果以解决锁文件冲突，因手工编辑的锁条目是任何工具均无法重现的状态。
- 按角色锁定。应用锁定精确版本与镜像摘要，使构建仅在提交变化时变化；库声明兼容范围，并测试最低支持版本与
  最新版本。应当以相同方式锁定 CI 工具与基础镜像，并有意识地升级，因浮动工具版本即未审查的依赖。每次锁定
  变更均应当于变更中说明理由，因无法解释的升级与错误无法区分。
- 多包仓库应当将版本集中声明于一处：Gradle 用 `libs.versions.toml`，Maven 用 `<dependencyManagement>`，
  npm workspace 用根 manifest 的集中声明，Rust 用 `[workspace.dependencies]`。同一依赖的版本仅应出现一次，
  子包 manifest 仅应引用该键，使版本升级仅改一处；多个 manifest 各自固定版本，将使同一依赖于两个包中漂移
  成两个版本。
- 按计划更新，不得机会主义地更新。固定节奏的自动化拉取请求处理补丁版本，而主版本应当专门审查发布说明、废
  弃项与破坏性变更。应当为升级运行完整构建与测试，并使其不混入功能变更。应当为自动更新设置最短发布时长，
  因被攻陷的维护者账号可以于数分钟内发布恶意版本，而短暂延迟能够把立即安装变为经过审查的安装。
- 依书面标准准入依赖：标准库、现有依赖与维护良好的第三方库能够胜任的，不得编写替代实现；该包应当有维护，
  近期有发布、issue 响应及时且维护者不止一人；无已知未修补漏洞；许可证兼容并已记录；有负责人能够移除
  它；安装大小与传递依赖数量应当如实记录，但不构成拒绝优质库的理由。应当将证据记录于拉取请求中，核查包名
  与包仓库来源不会被同名的公共包遮蔽，内部包优先使用带作用域的名称。
- 彻底移除。删除使用点与 import，移除 manifest 条目，重新生成锁文件，随后移除与其相关的配置、环境变量、
  CI 引用与凭据。代码中已移除但仍留于 manifest 中的依赖仍会发布、仍会被扫描，并仍会产生更新噪声。依赖离
  开时，应当于同一次变更中更新许可证声明与 SBOM，使清单永不描述已不存在的代码。
- 通过仓库配置接入私有包仓库：于 `.npmrc` 中设置作用域与包仓库，于 `pip.conf` 或项目的包管理器配置中设置
  索引 URL，于 `settings.xml` 中设置镜像，于 `composer.json` 中设置仓库。凭据应当自环境或 CI 机密存储注
  入，不得提交令牌，并应当于包仓库不可达时失败关闭，不得回退到公共镜像。
- 许可证策略、漏洞严重程度分级与豁免由 `security-compliance-conventions` skill 裁定；本 skill 仅要求在 CI
  中执行上述扫描并记录证据。许可证与漏洞决定应当交由安全团队。应当于 CI 中以 `pip-audit`、`npm audit`、
  `cargo audit`、`govulncheck`、`bundle audit`，或者 SBOM 与许可证扫描器运行扫描；记录允许的许可证集合；
  对被拒绝或未知的许可证上报审批，不得于代码审查中批准。每次发布应当附一份 SBOM，为该交接提供稳定清单，并
  使已撤回的依赖于发布后仍可见。

| 正例 | 反例 | 原因 |
|---|---|---|
| 每个被导入的包均有一条直接的 manifest 条目 | 导入某一依赖所安装的包 | manifest 说明项目依赖什么 |
| 一个已提交的锁文件以冻结模式安装 | 删除锁文件以清除冲突 | 安装可复现且经过审查 |
| 应用锁定 `1.4.2` | 应用声明 `^1.4.2` | 构建仅在提交变化时变化 |
| 按计划生成的补丁更新拉取请求 | 生产中的静默自动更新 | 变更经过测试且可归因 |
| 拉取请求中的准入证据 | “它很流行，所以安全” | 健康度、许可证与占用均经过检查 |
| 包仓库与机密自 CI 注入 | 于 `.npmrc` 中提交令牌 | 凭据不得进入仓库 |
| 许可证扫描器门禁构建 | 审查者批准 copyleft 许可证 | 许可证风险成为有记录的决策 |
| 最后一个 import 移除时 manifest 条目一并移除 | manifest 中留下未使用的依赖 | 未使用代码不再发布与扫描 |

仅开发用依赖属于开发作用域，不随制品发布。peer 依赖与可选依赖遵循定义它们的生态规则。工作区内包仅决定构
建顺序，不按外部依赖扫描。气隙（air-gapped）构建会引入依赖，该第三方引入树遵循生成代码与第三方代码规则。
应当按数量与传递依赖总大小记录依赖预算并跟踪膨胀；预算不构成拒绝能够替代手写实现的优质库的理由。预发布版
本或提交哈希不属于发布版本：仅应于无任何版本可用时使用，并记录该锁定为何无法移到某一版本。

## 4. 配置管理

配置决定同一份构建于每一环境中的行为。优先级无文档，或校验被推迟时，同一提交将于两个地方表现不同，而差
异仅于生产负载下出现。配置是在每一环境中运行的代码，因此其接受与读取它的代码相同的审查、版本管理与回滚
路径。

- 固定并记录一套优先级顺序：命令行标志、环境变量、本地配置文件、共享配置文件、编译期默认值。应当于启动时
  按该顺序加载并合并一次，并使一个模块负责读取所有来源，使任何功能均不得另造第二套阶梯。应当于 README 中
  记录该阶梯，并为每一层以一个测试验证合并。
- 使用与该设置的变化频率和保密性相匹配的来源。安全的编译期默认值置于代码中，签入的环境文件保存共享的非机
  密设置，环境变量或配置服务保存部署特定的值，标志承载一次性的运维意图。机密应当按名称引用，并于运行时自
  机密存储解析。某个值必须在所有地方相同的，其属于共享文件或编译期常量，不得于每一环境文件中重复。
- 按数据而非分支分离环境：以同一环境变量选择 `config/dev.yaml`、`config/staging.yaml` 与
  `config/prod.yaml`。生产配置应当像代码一样审查，通过流水线部署，不得于运行中的主机上就地编辑，否则下一
  次部署将静默还原它。应当以显式环境变量选择文件，并使缺失文件成为错误，不得静默回退到默认值。
- 不得于业务逻辑中按环境分支。应当于边缘加载类型化配置并注入；请求处理器中的 `if env == "prod"` 之类条
  件意味着测试走一个分支而生产走另一个，而事故恰好发生于未测试的分支。
- 应当于启动时按 schema 校验合并后的配置一次：必填键存在、类型与范围正确、URL 可解析、引用的路径存在、互
  斥选项被拒绝。应当指出失败的键，说明预期形式，并于进程接收流量之前以非零状态退出。仅应校验一次并将结果
  向下传递；校验请求参数中的值属于另一个边界，不得替代启动时校验。
- 应当为每个可选键提供有文档的默认值，并带单位与范围；必填键则完全不提供回退。应当移除调用点中诸如
  `timeout or 30` 的隐藏回退，因其与有文档的默认值矛盾，并使行为取决于该值是缺失、空还是零。
- 应当向模块传入类型化配置对象，不得传入字典或直接访问环境。读取 `os.environ` 或 `process.env` 的模块将
  绕过优先级阶梯、跳过校验，并使其测试依赖开发者的 shell。依赖注入或一个小型配置模块均能够满足该要求；关键
  属性是整个应用仅有一个读取点。
- 应当退役不再控制任何行为的配置：无代码读取它、两个键控制同一行为，或某个布尔值变成了永久路径。一个行为仅
  应有一个键，重命名键属于一次带兼容窗口的迁移，不得作为一次性应用到所有部署的重命名。被移除的键应当于参
  考页和停止读取它的那次变更中留下迁移说明，不得仅留于配置文件中。

| 正例 | 反例 | 原因 |
|---|---|---|
| 有文档的标志优先于环境变量、环境变量优先于文件、文件优先于默认值 | 每个模块读取自己的来源 | 行为在每一环境中都可预测 |
| 缺失的必填键以其名称退出 | 缺失的 URL 默认为空字符串 | 失败于启动时出现，而非于负载下 |
| 类型化配置对象注入模块 | 字典穿过五层传递 | 访问被检查且仅校验一次 |
| 用一个变量选择 `config/prod.yaml` | 处理器内部的 `if env == "prod"` | 同一代码路径在所有环境运行 |
| 按名称引用机密 | 于 `config.yaml` 中提交值 | 存储与轮换留在安全团队 |
| 每个行为一个键 | `TIMEOUT` 与 `TIMEOUT_MS` 都被读取 | 重复键之间无优先级难题 |
| 生产配置通过流水线部署 | 于生产主机上手工编辑 | 变更经过审查且可回滚 |
| `APP_PORT=0` 于启动时被拒绝 | 第一个请求因坏端口失败 | 范围检查于流量到达之前运行 |

机密存储、轮换与访问策略属于安全团队；本节负责优先级、校验与快速失败边界。测试套件应当构建显式配置
fixture，不得读取开发者的环境，使通过的测试不依赖未导出的变量。长期存在且仍选择代码路径的布尔值属于配置，
依本节退役；改变部署行为的标志属于发布与运维。无法单独回滚的配置变更属于一项部署风险：应当于新值表现出
预期行为之前保留旧值，随后于后续变更中移除它。
