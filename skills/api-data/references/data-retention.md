# 数据保留

## 1. 数据保留

数据集的生命周期长于创建它的请求，每个副本的生命周期又长于其来源记录的删除。`security-compliance` 在
数据清单中设定类别与保留期；本节管 schema 与 API 如何执行并证明上述设定。

- 在字段级应用数据清单：把每个清单类别映射至承载它的表、集合与字段，记录于 schema 元数据或数据字典；
  派生字段继承输入中最严格的类别。
- 执行清单设定的保留期：每个数据集记录继承的期限、计时触发条件、处置方式与负责人；不得默认永久保留。
- 把删除作为穿越每个副本的路径，而非一条 DELETE：自主存储传播至搜索索引、缓存、分析表、事件流、日志与
  导出；删除任务幂等、带重试与审查记录，按存储计数或查询验证。
- 显式选择软删除或硬删除并履行义务：软删除属于保留而非删除，每次读取过滤它，存在带日期的清理任务；不得
  把软删除描述为已擦除。
- 把备份作为具有自身保留与恢复行为的副本：擦除流程说明备份到期日期，不得声称立即移除；备份保留长于
  清单期限须有记录的理由与补偿控制。
- 日志、分析与导出作为数据副本管理：日志写入时脱敏；导出带到期时间、访问日志与删除路径。
- 不得把生产数据放入测试或开发环境：使用合成数据或不可逆脱敏的数据；测试 fixture 不得包含真实人员或
  机密。

## 2. 判定与边界

- 判定：清空一张表而三个副本仍存在的删除端点属于合规缺陷；仅设标志的删除使数据以另一名称永久存活。
- 冷存储与归档只改变成本，不改变义务：访问控制、加密、保留、删除与审查仍然适用。
- 无人拥有的副本即无人删除的副本；每个副本都有负责人与删除机制。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| `deleted_at` 加清理任务与过滤读取 | 仅设删除标志且无清理 | 行及其个人数据永久存活 |
| 每个存储一个删除任务并逐存储验证 | 只执行 `DELETE FROM users WHERE id = 42` | 搜索、缓存、日志仍暴露该人员 |
| 有界备份保留并声明擦除窗口 | 备份永久保留 | 数据仍可恢复，删除承诺即为虚假 |
| 合成 fixture 或不可逆脱敏 | 每晚把生产转储恢复到测试环境 | 个人数据扩散到每台机器与备份 |
