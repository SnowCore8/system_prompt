# schema 迁移

## 1. schema 迁移

schema 变更比代码变更更难：发布期间新旧数据共存，每一步都触碰在线数据库。默认假设零停机，假设至读取
切换为止的每一步都有可由代码回滚的路径；最后的删除作为带备份与审批的销毁性变更处理。

- 保持有序、不可变的迁移历史：迁移存放于仓库，由同一工具按顺序应用；任何环境应用过即不得编辑，更正为
  新迁移。
- 对旧代码可见的每个变更使用扩展-收缩：新增结构、双写、回填、校验、切换读取、废弃窗口后删除旧结构；
  至读取切换为止每步独立部署且可回滚。
- 以可重启、可观测的批次回填：keyset 区间而非 OFFSET 窗口，按批提交，更新幂等（如
  `WHERE new_column IS NULL`），按每秒行数限流，记录最后处理的键。
- 执行 DDL 之前估算锁：说明引擎将取什么锁及其阻塞什么，设置 `lock_timeout` 与 `statement_timeout`，
  把迁移作为独立部署步骤运行。
- 数据干净之后再安排约束：新增 NOT NULL 先回填并校验非空；新增唯一约束先并发创建唯一索引再以其添加
  约束；CHECK 与外键以 `NOT VALID` 新增后独立 `VALIDATE CONSTRAINT`。
- 销毁性变更按生产变更对待：明确批准、消费方清单、备份或时间点恢复检查、带计数的试运行与变更后验证
  查询。

## 2. 判定与边界

- 迁移不得在应用启动时运行：滚动部署会使锁尝试次数乘以副本数。
- 唯一索引是并发写入者下唯一可靠的重复检查；应用层的先查后插会竞争并失败。
- 在回填之前新增约束，会使旧数据在旧代码写入时立即成为生产故障；向脏数据新增唯一约束会留下半途应用的
  迁移。
- 反向迁移属于最后手段，不属于计划；优先前向修复。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| 新增可空列、双写、回填、再 NOT NULL | 一次迁移中新增 `tenant_id NOT NULL` | 既有行失败，且锁定或重写表 |
| `CREATE INDEX CONCURRENTLY` | 热表事务中普通 `CREATE INDEX` | 构建期间阻塞写入 |
| 分批回填带游标与休眠 | 对整表执行一条 `UPDATE` | 长事务、表膨胀、副本延迟 |
| 新列双写，稍后删除旧列 | `ALTER TABLE ... RENAME COLUMN` | 发布期间破坏停留于旧版本的读取方 |
