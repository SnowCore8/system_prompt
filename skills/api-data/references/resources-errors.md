# 资源与错误设计

## 1. 资源与错误设计

资源形状决定调用方的耦合面，错误形状决定故障的可诊断性。两者都按“机器可读、人可读”拆分责任。

- 建模操作，不建模存储：不得直接暴露 ORM 实体、内部连接表或存储层可空性怪癖；成员端点与集合端点返回
  相同形状。
- PUT 替换整个表示且幂等；PATCH 说明其合并语义（JSON Merge Patch 或 JSON Patch）；批量端点定义逐项的
  部分失败结果。
- 每个错误携带机器可读的 `code`、可安全展示的 `message`、结构化 `details` 列表与请求标识符。
- 错误码唯一且永久：新增错误码属于兼容变更，客户端必须容忍未知 code；变更含义或删除不属于兼容变更。
- 消息面向运维者与最终用户，可以变更，且不得被客户端解析；HTTP 状态码承载大类；校验 details 逐项指出
  字段路径与违反的规则。
- 不得把堆栈跟踪、SQL 片段、机密或个人数据置于错误中；网关与校验失败返回同一信封。

## 2. 判定与边界

- 以 200 返回错误体不可接受：网关、缓存与客户端库将其视为成功。
- 429 必须带 `Retry-After` 与限制头；401 表示未认证，403 表示被拒绝，存在性敏感时用 404。
- 错误码目录属于发布制品，按新增方式增长。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| 稳定错误码加结构化 details | 错误消息作为唯一信号 | 客户端解析字符串，消息一变即破坏 |
| 正确的 4xx/5xx 状态码 | 以 200 返回错误体 | 网关与客户端把失败当成功 |
| 401/403/404 各司其职 | 每个失败都返回 403 | 客户端无法区分重新认证与停止 |
