# API 契约

## 1. API 契约

契约是仓库之外的代码能看到的部分，生命周期最长、变更周期最慢。契约应当为仍停留在前一版本的调用方设计，
不得仅为当前正在编写的客户端设计。

- 先定义契约再实现：机器可读定义（OpenAPI、protobuf、GraphQL SDL、JSON Schema 或等价 IDL）与服务一并
  提交，其 diff 作为 API 变更审查。
- 实现与客户端 stub 由该定义生成或校验；绕过 IDL 的手工编辑属于漂移，在同一次变更中修复。
- 契约 diff 在合并前对比已发布基线：protobuf 用 `buf breaking --against`，OpenAPI 用 `oasdiff breaking`；
  基线取最近发布标签。
- 契约 lint 与 diff 检查同为必需校验，规则文件与工具版本入库；不得以忽略规则静默通过破坏性发现。
- 某行为无法在 IDL 中表达的（语义约束、条件存在），以文字记录于契约文档并显式测试。
- 仓库内的客户端、生成 SDK、契约测试、示例与文档在同一次交付中更新；仓库外的消费方只提供契约与迁移
  指南并协调切换。

## 2. 判定与边界

- 增量变更（可选字段、新操作、新错误码）属于兼容变更；删除或重命名字段、可选改必填、收窄类型或扩展
  封闭枚举，除经证明并非破坏性的外，均属破坏性变更。
- 破坏性的判定证据是消费方清单加针对真实客户端的契约测试；缺字段被使用的证据不等于字段未被使用。
- 版本化在发生变化的边界处实施：公共 API 用主版本路径段，协调发布的内部 IDL 用增量演进；不对单个字段
  版本化。
- 生成接口面与第三方接口面保持其形态，隔离在适配器之后，在边界映射到规范契约并重新生成。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| 契约变更先入 IDL 并过 diff 检查 | 先改实现，事后补 schema 描述 | 描述不属于契约，漂移无门禁 |
| 在旧字段旁新增字段再废弃 | 就地替换字段 | 停留于前一发布的调用方当场破坏 |
| 契约测试覆盖前一客户端版本 | 假定客户端兼容 | 兼容性未经验证 |
