# 缺陷报告与复现

## 1. 缺陷报告与复现

缺陷报告是把模糊陈述转化为可判定事实的过程。未复现的缺陷无法验证修复，也无法阻止回退。

- 报告包含四项要素：最小复现步骤、环境（语言与运行时版本、平台、依赖与版本、配置）、期望结果与实际
  结果。
- 缺少“期望与实际”或复现步骤的报告，先按现有信息做不修改代码与数据的调查与复现尝试，同时索取缺失
  信息；修改代码前必须有可判定复现。
- 无法复现的，报“无法复现”并附已尝试的环境与步骤，不得猜测；猜测所得改动无法对应缺陷，也无法证明
  修复。
- 最小复现达到“最小”标准：删至删除任何一步即无法触发为止；超过十步或需要完整环境方能执行的，先行
  拆分。
- 环境完整到可以重跑，包括操作系统、运行时版本、依赖锁定版本、配置差异与数据规模；仅说“本机没有问题”
  不构成环境描述。

## 2. 判定与边界

- 判据：修复提交的说明能引用一条稳定触发缺陷的步骤或测试；引用不了的，视为未复现。
- 最小复现的裁剪：自完整场景出发逐步删除无关输入、依赖与数据，每删一步重新运行确认缺陷仍触发。
- 附最小复现代码或命令，不得粘贴整个服务日志；附关键数据样本时须脱敏。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| 报告含四要素与最小复现 | 报告仅称“有时失败” | 无法判定也无法复现 |
| 无法复现时列已尝试的环境与步骤 | 无法复现仍提交“可能有用”的改动 | 改动属于猜测，无法证明修复 |
| 复现步骤删无可删 | 附上完整服务日志与全量数据 | 后续人员无法复核 |
