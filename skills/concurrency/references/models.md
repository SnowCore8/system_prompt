# 异步与并发模型

## 1. 异步与并发模型

模型决定“何者在何时被调度、阻塞发生于何处”。模型选择错误，将使阻塞扩散到不应阻塞之处，或使共享状态
失去清晰边界。

- 线程是抢占式调度的执行流，共享同一进程内存；适用于 CPU 密集任务与独立的阻塞任务；线程数量以可并行资源数量为上限，不得无界创建。
- 协程与 async/await 是协作式调度，在显式等待点让出；适用于大量 I/O 密集、低时延任务。
- 事件循环是单线程调度器，把回调与异步任务排队执行；规则是“不得阻塞”：同步阻塞 I/O、长时间计算与持锁
  的慢操作均不得进入事件循环。
- 线程池隔离阻塞任务与 CPU 任务：阻塞 I/O 与长计算交给工作线程，事件循环只做调度与快速路径；池大小与
  任务类型匹配，并设定队列上限与拒绝策略。
- 模型之间应有明确边界：跨线程共享用锁或消息传递；同一线程内以 await 交替的协程仍需处理共享状态的数据
  竞争（单线程且无交错的除外）。
- 记录每个执行流可以访问的状态：“该回调在哪个线程运行、可以访问什么”必须可回答。

## 2. 判定与边界

- 并发属于结构（任务拆成可独立推进的执行流，单核可通过交错实现），并行属于执行（多任务真正同时运行，
  需要多核）；单核可以实现并发，无法实现并行。
- 引入并发的理由必须可判定：响应性、吞吐或资源利用至少一项；无此三者的，不得引入。
- 收益依据目标硬件上的测量，不依据直觉；加锁、切换与内存同步均有成本。
- 并发不解决单线程算法低效：先优化算法与数据结构，再考虑并发化。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| I/O 密集采用 async/协程 | 在事件循环内同步阻塞 I/O | 一个调用使全部任务停滞 |
| 阻塞工作交由线程池 | 以协程执行长时间 CPU 计算 | 协作式让出点之间无法抢占 |
| CPU 密集按核数确定线程池 | 无界创建线程 | 上下文切换与内存耗尽 |
| 记录执行流的可见状态 | 未写明回调所在线程 | 共享状态无从审查 |
