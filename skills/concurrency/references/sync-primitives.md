# 同步原语选择

## 1. 同步原语选择

原语选择错误，将使正确的代码变慢，或使简单问题复杂化。选择依据为：保护对象、读写比例、等待方式，
以及是否需要公平或可重入。先回答“是否可以不共享”，再回答“采用哪一种”。

- 互斥锁为默认选项：保护一段临界区，任何时刻仅一个执行流进入；适用于写多读多、临界区较短且无等待的
  场景。
- 读写锁仅在读远多于写时适用：读并发、写互斥；写入频繁时开销反超互斥锁，应先测量读写比例。
- 信号量用于限量：限制同时访问某项资源的执行流数量，或有界缓冲区的容量信号；它不保护状态。
- 条件变量用于等待状态变化：在互斥锁上等待直至谓词为真，避免忙等；等待必须循环重查谓词并设定超时。
- 原子操作用于单个标量的读改写：计数、标志、无锁比较并交换；不保护多个字段，不保证复合判断的原子性。
- 可重入锁掩盖锁设计问题：优先采用不可重入锁并修正结构。
- 不得以忙等自旋替代条件变量或信号量；短时自旋可采用，无界自旋消耗 CPU 并可能形成活锁。

## 2. 判定与边界

- 单个标量的读改写选原子操作；涉及两个以上内存位置的选锁。
- 等待状态变化选条件变量或信号量；限量与容量选信号量；读写比例悬殊且读可并发才选读写锁。
- 原语并非语言无关：同一概念在不同语言中能力不同（如 Go 的 channel 优先于显式锁，Rust 以类型系统禁止
  竞争）。
- 原语不支持超时的，改用可取消等待、看门狗或带超时的 select/channel，并把替代方案记入并发文档。

## 3. 正反例

| 正例 | 反例 | 原因 |
|---|---|---|
| 写多读多采用互斥锁 | 写入频繁仍采用读写锁 | 写者互斥的开销超过互斥锁 |
| 读多写少采用读写锁 | 以单一大锁串行化全部读取 | 读并发被消除 |
| 限量与容量采用信号量 | 以互斥锁模拟计数上限 | 混入互斥语义，难以推理 |
| 等待状态变化采用条件变量 | 以忙等自旋轮询标志 | 空转消耗 CPU，可能形成活锁 |
