# 接口与数据维度

本文件应当与 `SKILL.md` 配合使用。每一节规定一个接口与数据维度的规则、边界情况与失败模式。项目已有契约、
schema 或兼容性策略的，代理应当先阅读，并将其作为事实输入；本 skill 的规则优先，项目约定仅在本 skill 未规定
时补充。本文件提供默认值与理由。章节编号与 `SKILL.md` 中的维度索引对应。资源、字段、表、列、索引与枚举成员
的名称由 `naming-conventions` 管辖；本文件决定必须存在的内容、其行为方式及其变更方式。

## 1. API 设计

契约是服务中仓库之外的代码能够看到的部分，因此生命周期最长、变更周期最慢。契约应当为仍停留于前一版本的调用
方设计，不得仅为当前正在编写的客户端设计。

- **先定义契约，再实施。** 代理应当将机器可读定义（OpenAPI、protobuf、GraphQL SDL、JSON Schema 或等价
  IDL）与服务一并提交，并将其 diff 作为 API 变更审查。代理应当在 CI 中由该定义生成或校验服务端实现与客户端
  stub；事后自注解生成的 schema 属于描述，不属于契约。绕过 IDL 的手工编辑属于漂移，应当于同一次变更中修
  复，不得留待以后清理。某行为无法在 IDL 中表达（语义约束、条件存在）的，应当将其以文字记录于契约文档，并
  显式测试。
- **建模操作，不建模存储。** 路径形状、资源名、HTTP 方法选择与路径参数大小写，遵循 `naming-conventions`；本
  维度决定请求与响应语义。PUT 替换整个表示且幂等；PATCH 说明其合并语义（JSON Merge Patch 或 JSON
  Patch）；批量端点定义逐项的部分失败结果。不得直接暴露 ORM 实体、内部连接表或存储层可空性怪癖。成员端点
  与集合端点应当保持对称：同一操作在单独获取条目与在列表中获取时，返回相同形状。
- **错误响应应当成为稳定的公开类型。** 每个错误均携带机器可读的 `code`、可安全展示的面向人的 `message`、结
  构化 `details` 列表以及请求标识符。错误码唯一且永久：新增错误码属于兼容变更，客户端必须容忍未知 code；变更其含义或删除则不属于。
  消息面向运维者与最终用户，可以变更，且不得被客户端解析；HTTP 状态码承载大类。校验 details 为结构化对象
  的列表，逐项指出字段路径与违反的规则。不得将堆栈跟踪、SQL 片段、机密或个人数据置于错误中。网关与校验失
  败亦返回同一信封，并将请求标识符暴露为响应头，使支持工单无需客户端响应体即可追踪。
- **集合行为应当仅定义一次，并在各处应用。** 同一 API 默认一种分页风格：大型或变化的集合用游标分页；仅小
  型稳定集合需 offset 的，方可在契约中记录为例外，且同一操作不得混用两种风格；代理应当在服务端强制最大页
  大小。默认排序应当记录，使其确定，并以唯一键打破
  平局，使页既不跳过也不重复。返回下一个游标或链接；总数设为可选，因其代价高昂；完整导出作为独立任务处理，
  不得作为一页。过滤字段、操作符与值格式应当加入允许列表，对未知过滤条件应用一套有文档的策略；热过滤与排
  序字段的索引需求由 `performance-conventions` 裁定，并在契约中记录索引或接受的成本。在同一版本内，默认页
  大小与默认排序应当保持固定；即使 schema 未变，变更任一项亦属于行为破坏。
- **重试安全与负载控制应当构建于契约之中。** 客户端可能重试的 POST 或动作端点应当接受作用于主体的
  `Idempotency-Key`，服务按有文档的 TTL 保存请求指纹与存储的响应：相同键与相同请求体重放存储的响应，相同
  键配不同请求体则属于冲突。PUT 与 DELETE 按定义幂等。应当以响应头公布速率限制，返回带 `Retry-After` 的
  429，将突发限制与持续配额分开，按租户与按主体设定预算，并公布重试指引：客户端以指数退避加全抖动，以
  `Retry-After` 为下限，设定最大重试次数与总超时，且仅重试安全操作或幂等操作：429 按 `Retry-After` 重试；
  500 仅在带幂等键时可重试；502 与 503 亦须限安全或幂等操作；4xx（除 408 与 429）不重试。配额不得作为正确
  性机制；应当改用幂等、预留或队列。键的作用域应当限定至
  端点与主体，在处理程序运行之前拒绝被复用的键，并在契约而非代码中记录 TTL。
- **为每个操作明确认证与授权边界。** 在边缘认证、在资源处授权：每个操作均应当说明其检查的主体、租户与对
  象，租户与所有者来自已验证的令牌，不得来自请求体或查询参数。令牌作用域应当狭窄，使内部操作不经过公共网
  关；凭据缺失或无效返回 401，已认证但被拒绝的调用方返回 403，资源存在性本身敏感时返回 404。授权变更即契
  约变更，应当遵循相同的版本化与废弃路径。内部端点与管理端点应当通过与公共端点相同的策略检查；调试绕过即
  更换名称的公共端点。
- **同步或异步投递应当显式决定。** 同步调用返回最终状态，仅当工作能够装入调用方超时时间时方为正确。长操作
  返回 202 与状态资源，该资源记录待处理、成功与失败状态，并带有取消或重试路径。事件与 webhook 携带稳定类
  型、schema 版本、事件 ID、时间戳与因果关系 ID；投递为至少一次，因此消费方应当按事件 ID 去重、容忍乱序投
  递并验证签名。应当公布重试计划、死信路径与重放流程。webhook 接收方本身即一个 API：其快速确认、幂等处
  理，并暴露其失败与重试行为；事件 schema 仅承诺增量字段，并在字段消失时版本化。
- **兼容性、废弃与版本化应当一并规划。** 增量变更（可选字段、新操作、新错误码）属于兼容变更；删除或重命名
  字段、将可选字段变为必填、收窄类型或扩展封闭枚举，除经证明并非破坏性的外，均属于破坏性变更。废弃时应当提供
  替代方案、`Deprecation` 头、`Sunset` 日期、迁移指南与已测量的使用量，然后仅在用量为零或公告日期已过时移
  除。版本化应当在发生变化的边界处实施：公共 API 用主版本路径段（`/v1`），协调发布的内部 IDL 用增量演进，
  仅当每一跳均保留时方使用媒体类型或头。不得对单个字段版本化，亦不得为一个概念长期保留两个存活名称。应当
  于契约中记录支持窗口（当前主版本加前一主版本，或固定月数），并按调用方测量字段用量，因一个小消费方即可
  能无限期阻止移除。

| 正例 | 反例 | 原因 |
|---|---|---|
| `GET /v1/orders?status=paid&page_size=50` | 带过滤体的 `POST /v1/orders/search` | 读取应当保持为安全、可重试的 GET；将其包入 POST 隐藏了语义。 |
| `{"code":"validation.invalid_field","details":[{"field":"email","issue":"invalid_format"}]}` | `{"error":"Order 42 does not exist"}` | 错误码稳定且机器可读；details 为结构化对象的列表。 |
| `202 Accepted` 带 `Location: /v1/jobs/{jobId}` | 一个 90 秒的请求，客户端将超时并重试 | 长时间工作需要状态资源，而非更长的超时。 |
| 带存储响应的 `Idempotency-Key` | README 中的“客户端不应重试” | 即使客户端代码不重试，网关与用户亦会重试。 |
| 排序中的游标加唯一决胜键 | 在活跃表上用 `OFFSET 20000 LIMIT 20` | 插入或删除行时 OFFSET 页将漂移。 |
| 缺少令牌返回 401，被拒绝的调用方返回 403 | 每个失败均返回 403 | 客户端无法判断应当重新认证还是停止。 |
| 在 `email` 旁新增 `email_hash`，废弃旧字段 | 就地以 `email_hash` 替换 `email` | 停留于前一发布的调用方将在部署时破坏。 |
| 指数退避加抖动，尊重 `Retry-After`，仅重试幂等写入 | 对每个失败立即重试且不限次数 | 立即重试将放大中断，并在服务恢复后将其击垮。 |

| 版本化策略 | 适用情形 | 避免情形 |
|---|---|---|
| 主版本路径段（`/v1`） | 公共或合作伙伴 API 需要清晰的破坏边界且路由简单 | 每个客户端均按同一 IDL 同步重新生成的内部调用 |
| 媒体类型或 `Accept` 头 | 一个 URL 提供不同表示，且每一跳均保留该头 | 会剥离或规范化该头的共享缓存、网关或移动端技术栈 |
| 仅增量演进 | GraphQL、protobuf 或带容忍式读取方且发布协调的内部服务 | 移除、重命名或必填输入，任何增量规则均无法使其安全 |
| 功能开关或影子端点 | 新旧行为并行的迁移窗口 | 窗口关闭后作为稳定公共版本的替代品 |

## 2. 数据库与 schema 变更

schema 变更较代码变更更为困难，因发布期间新旧数据共存，且每一步均触碰在线数据库。代理应当假设零停机，并假
设至读取切换为止的每一步均有可由代码回滚的路径；最后的删除应当作为带自身备份与审批门禁的销毁性变更处理，
缺少任一者的，视为设计缺陷，而非排期上的不便。

- **保持有序、不可变的迁移历史。** 迁移应当存放于仓库中，在每个环境中由同一工具按顺序应用，一旦在任何地
  方应用过便不得编辑；更正应当为新迁移。工具应当加锁，使两次部署不竞争；测试数据库应当通过运行完整历史构
  建；手工生产 DDL 属于紧急破例操作，之后应当补一条记录它的迁移。不得使 ORM 针对在线数据库自动生成 schema
  并将其作为真源。默认仅向前；工具提供向下迁移时，仍应优先前向修复，因 down 脚本很少针对真实数据演练。
- **对旧代码能够看到的每个变更使用 expand-contract。** 阶段为：新增结构而不移除任何内容；部署同时写入两种
  形式并读取旧形式的代码；回填既有行；验证两种形式一致；将读取切换至新形式；在废弃窗口之后删除旧结构。至
  读取切换为止的每个阶段均为独立部署，并可通过重新部署前一代码回滚；最后的删除不可逆，应当等待经过验证的
  备份或时间点恢复点以及审批门禁。反向迁移属于最后手段，不属于计划。双写期间应当保持两种形式一致，并在切
  换前对账；不匹配行数属于扩展阶段退出标准的一部分。
- **以可重启、可观测的批次回填。** 应当选择 keyset 区间，而非 OFFSET 窗口；按批提交；使更新幂等
  （`WHERE new_column IS NULL`），使重跑安全；按每秒行数限流；记录最后处理的键；监控复制延迟、锁等待、
  CPU 与磁盘。代理应当在生产规模数据上估算时长，并在开始前定义停止条件与试运行计数。对大型表执行一条
  UPDATE 将在其运行期间持续持锁、使表膨胀并拖慢副本。回填属于生产数据写入，需要自身批准、限流与急停开关，
  于低峰时段由负责人观察运行。
- **执行 DDL 之前估算锁。** 应当说明引擎将取什么锁以及其阻塞什么：在 PostgreSQL 上，新增带易变默认值的列
  将重写表；不是二进制兼容的列类型变更将重写表并阻塞写入；普通索引构建阻塞写入，并发构建不阻塞；
  `VALIDATE CONSTRAINT` 取 SHARE UPDATE EXCLUSIVE，阻塞其他 DDL 与 VACUUM，但不阻塞读或写。应当设置
  `lock_timeout` 与 `statement_timeout`，重试，将迁移作为独立部署步骤运行，并在运行期间观察数据库。排在长
  事务后面、随后阻塞每个写入者的迁移属于中断，而非部署细节。迁移应当作为显式部署步骤运行，不得在应用启动
  时运行：滚动部署将使锁尝试次数乘以副本数。
- **依不变量选择与 schema 绑定的索引和约束。** 应当为每个外键、唯一约束与软删除谓词建立索引；索引的查询收益、
  复合列顺序与写放大取舍由 `performance-conventions` 裁定；本 skill 只规定 schema 形态与 DDL 影响，包括部分
  索引、并发构建与锁。CHECK 与外键约束应当以 `NOT VALID` 形式新增，再于独立步骤中 `VALIDATE CONSTRAINT`；
  新增 NOT NULL
  应当先回填并校验非空，再强制该约束；新增唯一约束应当先并发创建唯一索引，再以该索引添加约束，且仅在数据
  满足之后。应用层无法保证的不变量应当在数据库层强制，包括并发下的唯一性；唯一索引属于并发写入者下唯一可
  靠的重复检查，应用层的先查后插将竞争并失败。
- **数据干净之后再安排约束。** 在新增 NOT NULL、UNIQUE、FOREIGN KEY 或 CHECK 之前，应当检查违规行与孤儿
  行；部署写入有效行的代码，并按类型新增与校验：CHECK 与外键以 `NOT VALID` 新增后在独立步骤中
  `VALIDATE CONSTRAINT`；NOT NULL 先回填并校验非空，再设置；UNIQUE 先并发创建唯一索引，再以该索引添加约
  束。在回填之前新增约束，将使旧数据在旧代码写入时立即成为生产故障；向脏数据新增唯一约束将留下半途应用
  的迁移。可延迟约束服务于多语句事务，而非无序写入。在选择修复方案之前应当先统计违规行；答案有时为数据清
  理，而非 schema 变更。
- **将销毁性变更作为带审批门禁的生产变更。** 删除或重命名列或表、截断、收窄类型与批量删除，均可能丢失任
  何代码回滚均无法恢复的数据。每个操作均要求明确批准（在用户全局约束下，迁移属于数据库写入）、消费方清
  单、备份或时间点恢复检查、低峰时段、带受影响行数的试运行，以及变更后验证查询。应当优先选择废弃与稍后删
  除，而非就地重命名。在获批请求中应当写下被删除对象的定义与受影响行数，使未来的恢复尝试知悉须重建的内
  容。
- **如审查代码一般审查与测试迁移，包括升级路径。** 迁移审查覆盖文件、前向修复、回填、估算时长与锁、验证
  查询，以及将会消失的数据。CI 应当在空数据库上运行完整历史，并将前一发布的快照升级至新 head；测试不得从
  ORM 生成的 schema 开始。销毁性或重锁迁移应当在生产规模、已脱敏的副本上演练，不得在其他团队正在使用的共
  享 staging 数据上演练。迁移历史与已部署 schema 快照分歧时，CI 应当失败，使漂移在到达环境之前被捕获。

| 正例 | 反例 | 原因 |
|---|---|---|
| 新增可空 `tenant_id`，双写，回填，然后 NOT NULL | 在一次迁移中新增 `tenant_id NOT NULL` | 单步将在既有行上失败，并锁定或重写表。 |
| `CREATE INDEX CONCURRENTLY idx_orders_tenant_id ...` | 在热表的事务中执行普通 `CREATE INDEX` | 普通构建在整个构建期间阻塞写入。 |
| `ADD CONSTRAINT ... CHECK/FOREIGN KEY ... NOT VALID`，然后 `VALIDATE CONSTRAINT` | 一条 `ADD CONSTRAINT` 在持有 ACCESS EXCLUSIVE 时验证每一行 | `VALIDATE CONSTRAINT` 在 PostgreSQL 上取 SHARE UPDATE EXCLUSIVE：其他 DDL 与 VACUUM 等待，读写不等待。 |
| 带回填游标与批次间休眠的分批回填 | 对整个表执行一条 `UPDATE` | 单条更新持锁、使表膨胀，并使副本延迟数分钟。 |
| 新列加双写，稍后删除旧列 | `ALTER TABLE ... RENAME COLUMN` | 重命名将在发布期间破坏停留于旧版本的每个读取方。 |
| 合并错误后的后续迁移 | 编辑已应用的迁移 | 已应用文件不可变；编辑将使环境拥有不同 schema。 |
| 恢复或前向修复加验证查询 | 删除后“回滚部署” | 代码回滚无法恢复已删除的数据。 |

| 操作 | 锁与成本 | 风险 | 缓解 |
|---|---|---|---|
| 新增无默认值的可空列 | 短暂元数据锁 | 低，但会排在长事务后面等待 | 设置 `lock_timeout`，作为独立步骤运行 |
| 新增带易变默认值的列或更改类型 | 重写表，写入被阻塞 | 在大型或繁忙表上风险高 | 先加可空列、回填，再换入新列 |
| 普通 `CREATE INDEX` | 在整个构建期间阻塞写入 | 在热表上风险高 | 并发构建，且在事务之外 |
| `ADD CONSTRAINT ... CHECK/FOREIGN KEY ... NOT VALID` | 短暂锁，不扫描行 | 低 | 随后进行独立的验证步骤 |
| 回填后 `SET NOT NULL` | ACCESS EXCLUSIVE 扫描表 | 中 | 先回填并校验非空；以 `CHECK ... NOT VALID` 与 `VALIDATE CONSTRAINT` 证明无空值 |
| `CREATE UNIQUE INDEX CONCURRENTLY` 后 `ADD CONSTRAINT ... UNIQUE USING INDEX` | 并发构建不阻塞写入，添加约束短暂锁 | 低到中 | 先捕获重复值；应用层先查后插会竞争 |
| `VALIDATE CONSTRAINT`（PostgreSQL） | SHARE UPDATE EXCLUSIVE；阻塞 DDL 与 VACUUM，不阻塞读或写 | 低到中，与大型表扫描时间成正比 | 低峰时段、`lock_timeout`、监控等待 |
| 分批 `UPDATE` 回填 | 行锁加复制负载 | 中，随批次大小增长 | 小批次、休眠、观察延迟 |
| `DROP COLUMN` 或 `DROP TABLE` | 短暂元数据锁 | 不可逆数据丢失 | 先停止读取，备份，取得批准 |
| `TRUNCATE` | ACCESS EXCLUSIVE 锁 | 销毁性且快速 | 批准、先计数、不得在共享迁移中实施 |

## 3. 数据保留与生命周期

数据集的生命周期将长于创建它的请求，而每个副本的生命周期又长于其来源记录的删除。
`security-compliance-conventions` 在其数据清单中设定类别与保留期；本节管辖 schema 与 API 如何执行并证明上
述设定，不管辖策略如何决定。

- **在字段级应用数据清单。** 代理应当将每个清单类别（公开、内部、机密或受限）映射至承载它的表、集合与字
  段，并将该映射记录于 schema 元数据或数据字典，因列名无法对其内容分类。派生字段继承其输入中最严格的类
  别；未分类字段在清单覆盖它之前按受限处理。该映射驱动访问控制、加密、日志时的脱敏以及清单保留期的执行。
- **执行清单设定的保留期。** 代理应当为每个数据集记录其继承的期限、启动计时的触发条件（created_at、账户
  关闭、合同结束、最后活动）、处置方式（删除、匿名化、归档）与负责人。不得默认永久保留，亦不得凭空发明期
  限：法律下限、上限、例外与保全属于安全与法务角色，本 skill 记录该计划如何实施、每年审查与测试。
- **将删除作为穿越每个副本的路径，而非一条 DELETE。** 删除或擦除请求自主存储开始，并传播至搜索索引、缓
  存、分析或数据仓库表、事件流、日志与导出；每个目的地均具有机制与已测量的延迟。删除任务应当以幂等方式运
  行，带重试与审查记录，按存储计数或查询验证，并将备份到期日期报告为流程的终点。清空一张表而三个副本仍存
  在的删除端点，属于合规缺陷，而非部分成功。删除应当建模为异步流水线：API 接受请求，任务执行它，回执报告
  每个存储的完成情况与任何残留副本。
- **显式选择软删除或硬删除，并履行其义务。** 软删除（`deleted_at`）适合恢复窗口与审查需求，但属于保留而
  非删除：每次读取均应当过滤它或通过视图读取，唯一约束使用部分索引，并且存在带日期的清理任务。硬删除适合
  擦除请求以及没有审查要求的短生命周期数据。跨副本扇出的擦除返回 202 与状态资源以及按存储的回执；仅单存
  储、无恢复路径的同步硬删除方返回 204。不得将软删除描述为已擦除。软删除的行仍计入存储、导出、备份成本与
  访问请求，因此将其留在原地的擦除并不完整。
- **将备份作为具有自身保留与恢复行为的副本。** 备份、快照与时间点恢复在到期之前仍包含已删除的行，因此其
  保留期界定真正的删除窗口，并且应当有文档。擦除流程应当说明备份到期日期，不得声称立即移除；恢复不得复活
  保留计划已经清除的数据，因此恢复运行手册包含恢复后清理。静态加密与恢复演练由
  `release-operations-conventions` 管辖。备份保留长于清单期限属于安全决策，应当具有记录的理由与补偿控制，
  不得成为未经审视的默认值。
- **将日志、分析与导出作为数据副本管理。** 日志属于高频写入的副本：应当在写入时脱敏个人数据与机密，执行
  清单的日志保留期，默认不得记录完整请求或响应体。分析与数据仓库表携带主体标识符，需要相同的删除传播；事
  件流具有自身保留期；导出属于带到期时间、签名 URL、访问日志与删除路径的副本。无人拥有的副本即无人删除的
  副本。应当优先使用带脱敏规则的结构化字段，而非自由文本消息，因模板可以测试，而消息无法测试。
- **不得将生产数据放入测试或开发环境。** 代理应当生成合成数据，或在离开生产之前不可逆地脱敏；能够通过查
  找表逆转的匿名化不属于脱敏。测试 fixture 不得包含真实人员、机密或内部地址，示例值应当使用保留名称，例如
  `example.test.invalid`。非生产存储获得较短保留期与定期重置，使陈旧副本不会累积。用于调试的生产导出遵循
  与产品导出相同的规则：到期、访问日志与删除。
- **归档与冷存储应当遵循同一套规则。** 将数据移至冷存储、归档桶或离线导出，仅改变成本，不改变义务：访问
  控制、加密、保留、删除与审查仍然适用。代理应当记录归档格式与 schema，使数据在无应用时仍可读；包含校验
  和；测试恢复；将归档保留期绑定至同一计划。安全或法务角色设定的法律保全暂停该计划；针对数据集应当记录其
  范围、授权与到期时间，并仅在该角色的指示下解除。冷数据或归档数据仅在清单期限允许时，方可比热数据存活更
  久。

| 正例 | 反例 | 原因 |
|---|---|---|
| `deleted_at` 加清理任务与过滤读取 | 将 `deleted_at` 当作删除且没有清理 | 该行及其个人数据以另一名称永久存活。 |
| 每个存储一个删除任务并逐存储验证 | 仅执行 `DELETE FROM users WHERE id = 42` | 搜索、缓存、数据仓库与日志仍然暴露该人员。 |
| 由生成器产生的合成 fixture | 每晚将生产转储恢复到 staging | 个人数据扩散到每台开发者机器与备份。 |
| 仅携带主体 ID 的脱敏日志 | 日志消息中出现邮箱与电话号码 | 日志副本比账户存活更久，且无法可靠删除。 |
| 有界备份保留并声明擦除窗口 | “备份永久保留” | 数据仍可恢复，删除承诺即为虚假。 |
| 会过期的导出 URL 加访问日志 | 永久的公共导出链接 | 目的结束后任何持有者均可重取完整数据集。 |

| 存储 | 副本类型 | 删除机制 | 验证 |
|---|---|---|---|
| 主数据库 | 真源 | 在事务中删除或匿名化行 | 行数与读取查询 |
| 搜索索引 | 派生 | 按 ID 删除或重建受影响范围 | 按主体 ID 查询 |
| 缓存 | 派生、短生命周期 | 删除键并让 TTL 到期 | 键存在性检查 |
| 数据仓库或分析 | 派生、只追加 | 删除分区或按主体运行清理任务 | 主体查询与任务日志 |
| 日志与跟踪 | 事件副本 | 保留到期加写入时脱敏 | 保留配置与样本查询 |
| 备份与时间点恢复 | 快照副本 | 只有到期，没有选择性删除 | 备份到期日期与恢复测试 |
| 导出与文件 | 显式提取 | 删除对象并使 URL 失效 | 访问日志与对象列表 |
