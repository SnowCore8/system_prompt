# 接口与数据规范

API 契约与数据库 schema 是系统中生命周期最长的接口：外部调用方据其构建，背后的数据会累积多年。
改字段会让作者看不见的客户端失效；删列、未分批的迁移，或让每个写入者排队的锁，都会导致数据丢失或服务中断；这些后果都不是回滚代码能修复的。
本 skill 规定 API 契约的设计、审查与变更方式，数据库在不中断服务前提下的演进方式，以及数据在生命周期结束后的退役方式。
读者是新端点或新迁移的作者、评判 schema diff 的审查者，以及规划废弃或擦除路径的工程师。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。
   HTTP 语义、所用 IDL（OpenAPI、protobuf、GraphQL）、数据库引擎的行为以及数据保护义务，都不是可选项。
2. 本 skill 的规则。
   契约设计、演进、迁移与数据保留的规则，以本文件与 `references/` 为准。
3. 既有项目约定与事实。
   智能体应当先阅读当前 API 版本、迁移工具、错误码目录、已发布的兼容性策略与支持窗口；这些是事实输入，按本 skill 的规则处理。
   项目约定只在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好不得覆盖上述三层。

分工边界如下：

- **名称由 `naming-conventions` 管辖。** 该 skill 管辖资源、字段、表、列、索引与枚举的名称；本 skill 管辖围绕这些名称的契约与流程，不得重命名该 skill 管辖的名称。契约变更需要新名称的，智能体应当向该 skill 索取，不得另造第二套词汇。
- **独立文档由 `documentation-conventions` 管辖。** 该 skill 管辖 API 参考页与其他页面；本 skill 管辖这些页面所描述的设计规则，页面应当随契约一并更新。设计在此处审查，页面在该处审查。
- **发布运维由 `release-operations-conventions` 管辖。** 该 skill 管辖产品版本化、发布流程与 CI/CD；本 skill 管辖契约内部的 API 版本化策略。该 skill 同时管辖事故与备份；本 skill 管辖销毁性 schema 变更的安全性。
- **测试策略由 `testing-and-quality-conventions` 管辖。** 该 skill 管辖测试策略与门禁；本 skill 管辖作为要求的契约测试，不管辖运行这些测试的工具。发布期间无人运行的契约测试只是注释。
- **隐私策略由 `security-compliance-conventions` 管辖。** 该 skill 管辖隐私策略、带 PII 分类与保留期的数据清单以及许可证；本 skill 使用该清单，并管辖执行事项，包括 schema 元数据、删除传播、备份到期与测试数据处理。
- **生成接口面与第三方接口面属于例外。** 生成的客户端与服务端、第三方引入的 schema 以及外部 API 应当保持其形态；智能体应当把它们隔离在适配器之后，在边界映射到规范契约，并重新生成，不得手工编辑。
- **影响评估默认按破坏性处理；经证明并非破坏性的，不在此限。** 证明是消费方清单加上针对真实客户端的契约测试；缺少字段被使用的证据，不等于该字段未被使用。这是影响评估的默认；实施方案默认两步增量，无法两步完成的破坏性变更才需要版本边界。
- **强制规则冲突的，智能体应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与所选约定。** 所选约定应当记录于契约或 ADR，使下一次变更遵循该决定，避免重复争论同一问题。
- 生命周期：契约与数据设计主责 S2 计划（G2），数据迁移与破坏性变更在 S5 发布（G5）复核；阶段门禁与证据见 `project-lifecycle-governance`。

## 流程

1. 识别契约接口面与受影响的数据。
   智能体应当识别操作、请求与响应字段、事件、表、列、索引以及派生存储，并映射每个消费方，包括依赖当前形态的移动客户端、合作伙伴、仪表盘、导出与分析任务。
   清单不完整的，应当在提出变更前补全；未列出的消费方会成为未来的中断。
2. 检查当前版本与兼容性策略。
   智能体应当检查已发布的版本、记录的支持窗口、相邻字段的废弃状态，以及产生当前 schema 的迁移历史。
3. 选择增量式或破坏性。
   契约允许的，智能体应当以两个可部署步骤完成变更；无法两步完成的，才引入版本边界。
   优先选择扩展加废弃窗口，避免同时切换。无法描述两步路径的，视为该变更尚未准备就绪。
4. 编写带回滚的迁移与发布计划。
   计划应当载明 schema 阶段、回填批次、部署顺序、功能开关状态、验证查询，以及每一步的前向修复或恢复路径，并写明执行者、观察者与有权叫停者。
5. 针对真实客户端与数据验证。
   智能体应当以前一客户端版本运行契约测试，在生产规模数据上规划语句，重放真实请求样本，并确认旧客户端在双跑期间仍可工作。
   某个客户端无法测试的，应当记录为未验证的兼容性风险，不得假设其能够容忍变更。
6. 更新文档与示例。
   智能体应当更新 IDL、错误码目录、API 参考交接、迁移指南、变更日志与代码示例；无示例的契约变更不构成完整变更。
   迁移指南面向调用方的改动，而非实现者的改动。
7. 审查。
   智能体应当运行正文“审查清单”，并按 `references/checklists.md` 中的工作表执行；取得所需审查者，为销毁性变更与破坏性变更记录批准，并确认回滚路径经过测试，而非假定。
   批准没有使用证据的破坏性变更的审查，不构成完整审查。

## 核心规则

- **已发布的契约是唯一真源。** IDL、schema 与错误码目录应当如代码一般审查；与上述内容不一致的实现属于缺陷，应当于同一次变更中修复，不得记录为例外。过期的生成制品应当重新生成，不得手工修补。
- **GitHub 托管仓库的破坏性变更由契约 diff 在合并前检出。** 仓库中的 IDL 是唯一真源，生成的客户端、服务端桩与参考页由它产生，
  生成物差异以 `git diff --exit-code` 在 CI 失败；OpenAPI 以 `oasdiff breaking`、protobuf 以 `buf breaking` 对比
  已发布基线，检查名称与运行方式归 `testing-and-quality-conventions`，不得以人工比对替代。
- **实施方案默认增量；破坏性变更须经决策。** 影响评估按破坏性处理，实施时优先采用两步增量：可以自由新增可选字段、操作与错误码；删除、重命名、变更类型或新增必填项，需具备两步增量路径（无法两步完成时则为版本边界）、废弃窗口与已测量的使用量。
  被废弃的字段在移除日期之前应当保持受支持、有文档且有测试。
- **契约变更包含其消费方。** 本仓库内的客户端、生成的 SDK、契约测试、示例与文档应当于同一次交付中更新；本仓库之外的消费方，智能体应当只提供契约与迁移说明并协调切换，不得假定可更新，也不得要求智能体修改其他仓库。
  仍能工作的旧客户端应当经测试确认，不得假定。
- **机器读取错误码，人读取消息。** 错误码应当保持稳定、唯一且永久；消息应当保持安全且可变更；字段级细节应当置于结构化对象的 details 列表中，不得置于客户端会解析的字符串中。
  错误码目录属于发布制品，按新增方式增长；该目录是开放枚举，客户端必须容忍未知 code。
- **每个可能被重试的写入均具有幂等契约。** 键的作用域、存储的响应、TTL 与重放行为均应当明确规定并测试；不得假定客户端不实施重试。
- **重试仅适用于安全操作或幂等操作，并应当采用指数退避。** 客户端仅应自动重试幂等写入与安全读取，采用指数退避加抖动，并设定最大次数与总超时；429 按 `Retry-After` 重试；500 仅在带幂等键时可重试；502 与 503 亦须限安全或幂等操作；4xx（除 408 与 429）不重试。
  服务端应当以幂等键与 429 使重试安全且有界。
- **集合应当有界、有序且可重复。** 应当强制最大页大小、确定性排序与允许列表过滤条件，并确保请求路径上不存在无界导出。
  同一 API 默认一种分页风格；小型稳定集合需 offset 的，必须在契约中记录为例外，且同一操作不得混用两种风格。
- **授权按对象检查，不按路由检查。** 租户与所有者应当来自已验证的令牌；401、403 与 404 应当遵循一套有文档的存在性策略。在检查对象之前即返回数据的端点，属于带有测试套件的数据泄露。
- **长时间工作与事件投递属于设计内容，不得临时拼凑。** 长操作应当返回 202 与状态资源；事件属于至少一次投递，携带 ID 与 schema 版本，并具有去重、签名、重试、死信与重放路径。
- **版本化与废弃应当有意识地进行。** 版本化应当在发生变化的边界处实施：公共 API 用主版本路径段，协调发布的内部 IDL 用增量演进，仅当每一跳均保留媒体类型时，方使用媒体类型。
  废弃时应当提供替代方案、`Deprecation` 与 `Sunset` 头、迁移指南，以及按调用方统计的使用量。
- **schema 变更先扩展，再收缩。** 应当新增结构、双写、回填、校验、切换读取，然后移除旧结构。至读取切换为止的阶段均可由代码回滚；最后的删除不可逆，需要经过验证的备份或时间点恢复点以及审批门禁。无法在支持窗口内完成的变更应当拆分，直至能够完成。
- **执行 DDL 之前应当估算锁。** 智能体应当说明锁的名称，设置超时，在生产规模数据上测量，于低峰时段将迁移作为显式步骤运行，并在运行期间观察复制延迟与锁等待。
- **销毁性数据变更需要批准、备份与验证。** 迁移或回填属于生产写入：应当取得明确同意，具备消费方清单、恢复点、带计数的试运行，以及变更后查询。
- **每个数据集均具有类别、保留规则与负责人。** 删除应当传播至每个副本；软删除属于保留，不属于删除；备份、日志与导出属于各具到期时间与删除路径的副本。
- **测试应当自迁移构建，并使用合成数据。** 测试数据库应当由迁移历史构建，并自上一个发布版本升级；生产数据不得以未脱敏方式进入非生产存储。

## 变更风险矩阵

| 变更 | 兼容性 | 必需路径 | 验证 |
|---|---|---|---|
| 新增可选响应字段 | 兼容 | 加入 IDL，先发布服务端，再发布客户端 | 前一版本客户端通过契约测试 |
| 新增带默认值的可选请求字段 | 兼容 | 记录默认值，接受字段缺失 | 不带该字段的旧客户端 payload 测试 |
| 新增必填请求字段 | 破坏性 | 新版本，或带默认值的可选窗口直至调用方迁移 | 消费方清单与双跑测试 |
| 重命名字段或端点 | 破坏性 | 在别名旁新增名称，双写与双读，废弃旧名 | 移除前旧名的使用量降至零 |
| 移除字段或端点 | 破坏性 | 废弃窗口、停用日期、替代方案与使用量证明 | 客户端测试与按调用方的遥测 |
| 更改字段类型或格式 | 破坏性 | 在旧字段旁新增字段，或新主版本 | 往返测试与消费方测试 |
| 新增非错误码枚举值 | 对封闭客户端是破坏性 | 新版本，或记录容忍未知值的客户端要求 | 以早于该值的客户端构建测试 |
| 更改默认页大小或排序 | 行为破坏 | 公告并版本化，或把旧行为保留在参数之后 | 客户端对顺序与页内容的断言 |
| 新增可空列 | 兼容 | 仅扩展阶段：新增、双写、稍后回填 | 生产规模数据上的迁移；旧代码检查 |
| 新增 CHECK 或外键 | 数据不干净时会阻塞 | 清理数据；PostgreSQL 以 `NOT VALID` 新增，再于独立步骤 `VALIDATE CONSTRAINT`；其他引擎按引擎事实选择等价在线 DDL | 违规行查询与锁估算 |
| 新增 NOT NULL | 既有行不满足时会失败 | 回填并校验非空，再设置 `NOT NULL` | 非空校验与锁估算 |
| 新增 UNIQUE | 重复值会使迁移失败 | 并发创建唯一索引，再以该索引添加约束 | 重复值查询与索引构建时长 |
| 删除列或表 | 破坏性且销毁性 | 停止读取，等待废弃期结束，备份，取得批准 | 无引用残留；计数；恢复测试 |
| 在热表上回填或建索引 | 运行风险 | 限流分批或并发构建，避开高峰时段 | 复制延迟、锁等待、总耗时 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 把存储模型暴露为 API | 调用方耦合于表，每次迁移均成为 API 破坏。 | 设计线上契约，并在边界映射。 |
| 将错误消息作为唯一信号 | 客户端对文本实施字符串匹配，消息一经变更即破坏。 | 稳定错误码加结构化 details。 |
| 在变化的集合上使用 OFFSET 分页 | 数据在底层移动时，页将跳过并重复行。 | 带确定性排序的游标分页。 |
| 仅称“客户端应当重试”而无键 | 被重试的 POST 将重复订单或扣款。 | 带存储响应的幂等键。 |
| 以 200 返回错误体 | 网关、缓存与客户端库将其视为成功。 | 正确的 4xx 或 5xx 状态码。 |
| 429 不带 `Retry-After` | 客户端猛烈请求服务，使限流更为严重。 | 带限制头与 `Retry-After` 的 429。 |
| 每个失败均返回 403 | 客户端无法区分重新认证与停止，调试亦变慢。 | 401 表示未认证，403 表示被拒绝，存在性隐藏时用 404。 |
| “以后再版本化” | 客户端增加时兼容性债务将累积。 | 在第一个外部消费方之前设定版本化策略。 |
| 静默扩展枚举 | 穷举式客户端将崩溃或错误处理新值。 | 版本化，或记录容忍未知值的客户端要求。 |
| 在部署流水线中执行大型 ALTER | 锁等待将使每个写入者在它后面排队。 | 显式迁移步骤、`lock_timeout`、并发索引构建。 |
| 编辑已应用的迁移 | 环境产生分歧，历史无法解释 schema。 | 新增后续迁移。 |
| 以一条 UPDATE 完成回填 | 长事务、表膨胀、复制延迟与写入阻塞。 | 带限流的 keyset 分批回填。 |
| 把生产转储恢复到 staging | 个人数据扩散到每台机器与备份。 | 合成数据或不可逆脱敏的数据。 |
| 仅设置标志的删除 | 数据与个人记录以另一名称永久存活。 | 清理任务、过滤读取与保留规则。 |
| “以后可能使用”的保留 | 数据被无限期保存，没有负责人或法律依据。 | 类别、期限、触发条件、负责人与年度审查。 |
| 把速率限制当作并发控制 | 合法重试将失败，正确性依靠运气。 | 幂等、预留或队列。 |

## 审查清单

- [ ] 契约变更位于 IDL 中，且实现在 CI 校验中与其一致。
- [ ] 生成客户端、服务端桩与参考页由 IDL 重新生成，无手工副本。
- [ ] 破坏性变更由契约 diff 对比已发布基线检出，未以人工比对替代。
- [ ] 列出每个受影响的消费方，包括本仓库之外的客户端。
- [ ] 声明为增量式或破坏性，并附兼容性策略；破坏性变更具有两步增量路径或版本边界、废弃窗口、迁移指南与记录的支持窗口。
- [ ] 新错误使用稳定错误码、正确的状态码族与结构化对象的 details 列表。
- [ ] 集合有界、确定性有序；同一 API 默认一种分页风格，offset 例外已记录于契约，且同一操作未混用两种风格。
- [ ] 过滤与排序位于允许列表中；热过滤与排序字段的索引需求已按 `performance-conventions` 评估，并在契约中记录索引或接受的成本。
- [ ] 可重试写入具有幂等契约与重放测试。
- [ ] 速率限制与配额有文档，并带响应头、429 与 `Retry-After`。
- [ ] 授权为对象级，租户 ID 来自令牌，404/403 策略一致。
- [ ] 长操作与事件定义了状态、投递保证、去重与重放行为。
- [ ] 迁移遵循 expand-contract，每个阶段均可独立部署。
- [ ] 回填分批、幂等、可重启且限流。
- [ ] 锁影响与持续时间已经在生产规模数据上测量。
- [ ] 约束仅在数据满足之后验证。
- [ ] 销毁性变更具有批准、消费方清单、备份与验证查询。
- [ ] 每个新字段、新表与新集合均具有类别、保留期、删除路径与负责人。
- [ ] 删除传播至搜索、缓存、分析、日志与备份；软删除具有清理任务。
- [ ] 测试数据为合成数据，测试 schema 由迁移历史构建。
- [ ] 文档、示例、变更日志与错误码目录在同一次变更中更新。
- [ ] 变更具有回滚或前向修复路径，或对不可逆删除具有经过验证的恢复路径。

## 示例

<example>
为订单响应新增可选 `tracking_number`：应当将其加入 IDL，先发布服务端，再发布客户端，并以前一客户端版本针对新 schema 运行。
不需要版本边界，因字段缺失仍属有效状态。应当双向验证：不带该字段的旧客户端，以及带该字段的新客户端。
</example>

<example>
将 `customer_email` 重命名为 `email`：应当在旧字段旁新增 `email`，同时填充两者，切换读取方，发布带停用日期的废弃通知，并按调用方统计使用量。
仅在使用量降至零后删除旧字段，并提前一个版本公告移除。
</example>

<example>
为大型订单表新增必填 `tenant_id`：应当先以可空形式新增，部署双写代码，在设置 `lock_timeout` 的情况下按 keyset 分批回填，验证 `NOT VALID` 约束，然后强制 NOT NULL。
每一步均为独立部署并各自具有回滚，回填时长应当先在生产规模数据上测量。
</example>

<example>
处理擦除请求：应当于主存储中删除或匿名化行，自搜索索引移除文档，使缓存键失效，排队数据仓库与日志清理任务，并记录结束该流程的备份到期日期。
应当按存储分别验证，不得仅在数据库中验证。
</example>

<example>
在 v2 中将 `status` 查询参数改为必填过滤条件：应当发布 `/v2/orders`，在记录的支持窗口内继续提供 `/v1`，发布迁移指南，并在 v1 上返回 `Deprecation` 与 `Sunset` 头。
仅当每个调用方均已迁移，或停用日期已经到来时，方可移除 v1。两个版本写入相同记录；仅契约不同。
</example>
