# 注释规范

注释以三种方式失效：重述代码已经说明的内容；随代码演进变得过时；用机械的概括掩盖意图。
只有当注释记录读者无法从代码恢复的信息——契约、理由、隐患或计划——时才值得付出维护成本。
本 skill 规定一套决策流程，以及项目所写每一种注释所需的完整规则集：从生成 API 参考的文档注释，到标记、指令、法律声明头与被注释掉的代码。
它既服务于添加注释的作者，也服务于评判注释的审查者，因为同一套规则既决定注释是否应当存在，也决定它是否可信。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。
   Javadoc doclint、rustdoc、TSDoc 与 godoc 等语言或文档工具的注释位置要求，都不是可选项。
2. 本 skill 的规则。
   注释内容、位置、标记、弃用与工具指令的规则，以本文件与 `references/` 为准。
3. 既有项目约定与事实。
   智能体应当先阅读代码、文档工具配置、已配置的注释 linter 与仓库声明的自然语言；这些是事实输入，按本 skill 的规则处理。
   项目约定只在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- 注释与文档之分。本 skill 管辖嵌入源码的注释、由文档注释生成的 API 文档、标记、指令与法律声明头。独立文档（README、文档站点、ADR、变更日志、发布说明、API 参考页面）不在范围内，由 `documentation-conventions` skill 管辖。注释长成文档时，应当移动它并链接，不得复制。
- 弃用时机、移除窗口与公告位置由 `release-operations-conventions` 裁定。
- 生成代码、第三方引入代码与第三方代码不受风格修改约束。应当保留生成标记与上游注释；重新生成或重新引入，不得手工编辑，并应当将本地补丁记录于文件之外。
- 每个仓库仅应使用一种自然语言。应当明确声明该语言（库与开源项目默认英语，内部代码用团队语言），应用于每一种注释类型，并使标识符、API 术语与引用的上游文本保持原样。
- 注释变更亦为代码变更。应当于同一次提交中更新它，像审查代码一样审查它，更新生成的文档与 doctest，并重新运行文档构建；公开符号上的文档注释属于 API 契约的一部分。
- 强制规则冲突时，应当报告用户裁决，不得自行选定；非强制约定冲突时，可以说明冲突与选定的规则并记录该决定，使后续变更遵循它。
- 注释不得替代测试、类型或清晰的名称。正确性重要时，应当把它写进代码或测试；只承诺代码并不强制执行的行为的注释属于愿望，不属于契约。
- 审查注释时，应当遵循符号的可见性。公开符号的文档注释与其签名接受同样的审查；内部辅助函数的注释则看其是否能够防止将来的错误。
- 格式化工具、行宽与 linter 配置由 `code-style-conventions` 管辖；本 skill 负责注释内容、位置与指令语法。
- 门禁阈值以及跳过、隔离与豁免策略由 `testing-and-quality-conventions` 管辖。
- 机密扫描、轮换与披露由 `security-compliance-conventions` 管辖。
- 整体变更审查深度与合并门禁由 `vcs-collaboration-conventions` 管辖。

## 流程

1. 判断是否确实需要注释。
   代码已经说明事实的，应当删除注释或改进代码；代码清晰时，缺少注释不构成缺陷。
2. 为注释分类：文档注释、模块或文件头、行内理由、块说明、标记、弃用、法律声明头、工具指令或被注释掉的代码。
   分类决定必填字段以及将评判它的清单项。
3. 阅读周边代码、项目约定与文档工具配置；配置了 linter 的，找出将评判结果的 lint 规则。
   文档构建与已配置的 linter 属于验收测试，不属于装饰。
4. 写出读者无法自代码获得的内容：契约、理由、隐患、外部约束或计划。
   宁可一句精确的话，不得以三句含糊的话替代。
5. 套用形式：正确的语法与位置、必需的标签或小节、一种自然语言、项目的行宽与标点。
6. 于同一次变更中更新所有相关注释：调用方、生成的文档、示例、弃用声明，以及被本次变更解决的标记。
7. 对照当前代码验证：最终编辑之后重读注释，运行文档构建、doctest 与注释 linter，并删除任何不再成立的内容。
   验证是注释与猜测的分界线。

## 核心规则

- **解释原因，不得复述行为。** 重述代码的注释使维护成本翻倍，并且最先过时。应当说明理由、契约或隐患；代码本身能够表达的，应当重写代码。
- **文档注释是契约。** 应当在每个公开边界上记录参数、返回值、错误、副作用与不变量。调用方先读契约再读函数体，改变契约即改变 API。
- **代码是事实来源。** 与当前代码矛盾的注释属于缺陷；应当于同一次变更中修复或删除它。不得因“代码很明显”而留下错误注释。
- **无注释胜于错误注释。** 缺少解释仅需看一眼实现；错误的解释将带来缺陷。应当删除不确定的注释，自代码或作者处恢复事实。
- **删除代码，不得将其注释掉。** 版本控制保留历史；被注释掉的代码块会腐化、掩盖废弃 API，并干扰搜索。禁用仅为临时措施的，应当标明负责人、工单与到期时间。
- **标记应当带上其类型要求的内容。** `TODO`、`FIXME` 与 `HACK` 应当包含负责人与移除触发条件；`NOTE` 与 `WARNING` 应当说明条件、后果与必需动作。所有标记均应当遵循项目的拼写。
- **工单引用与生成标记使用平台可解析的语法。** issue 引用写作 `#123`，跨仓库写作 `owner/repo#123`，外部跟踪器使用
  完整链接；生成文件除工具原生标记外包含 `@generated`，使 GitHub 折叠其 diff。裸的“以后修复”不属于工单引用。
- **弃用标记应当写明替代项与移除版本。** 应当使用语言的弃用机制，并于标记里写明替代项与移除版本；仅有 `@deprecated` 将使调用方缺乏迁移路径。
- **工具指令应当最少且有理由。** 应当自最窄范围开始，先一行再一个函数；每条指令均需要理由，文件级抑制还需要清理工单，任何情况下都不得为一个位置在仓库范围禁用规则。
- **法律声明头与生成标记应当保持字节级一致。** 工具与许可证会读取它们；不得重排格式、翻译或手工编辑，亦不得删除第三方声明。
- **记录不显而易见的内容，不得记录熟悉的内容。** 应当记录外部约束、变通做法、unsafe 不变量、令人意外的边界情况与实测性能界限；跳过语言教程。解释超出一段的，属于设计说明，注释仅负责链接。
- **应当写明单位、范围、可空性与所有权。** 类型无法承载时，文档注释必须说明：毫秒还是秒、包含还是不包含、缺失还是为空、借用还是拥有。
- **应当将注释附着于其对象上。** 文档注释放在声明上，行内注释放在它所解释的行或块上，文件头置于文件开头。脱离对象的注释将被对照错误的代码阅读，重复的注释将与其孪生条目产生漂移。
- **依照格式的语气写作。** 句首大写、完整句子、正确标点、项目的行宽；文档注释中的描述用现在时陈述行为，指令用祈使式。
- **密度取决于意外程度，而非行数。** 应当注释不显而易见的内容，不注释显而易见的内容；每行都有注释的文件与完全无注释的文件一样难读，而且每条注释都是额外的维护负担。

## 注释类型矩阵

注释类型决定语法、位置与必填字段。动笔之前应当先选定类型，因文档注释与行内注释遵循不同的规则：

| 类型 | 用途 | 必需形式 | 示例 |
|---|---|---|---|
| 文档注释（docstring） | 声明的公开契约 | 紧跟声明上方的工具语法；摘要、契约、标签 | `"""Return the invoice total in cents."""` |
| 文件或模块头 | 文件的用途、范围与不变量 | 法律声明头之后的第一个注释；不记载变更历史 | `// Package billing reconciles invoices.` |
| 行内理由 | 解释下一行中不显而易见的选择 | 行上方的 `//` 或 `#`，同缩进，一个想法 | `# Retry once: the gateway resets idle connections.` |
| 块说明 | 多行理由、算法、外部约束 | 项目的块注释语法，折行，无装饰边框 | `/* The vendor caps a batch at 500 items. */` |
| API 文档标签 | 供生成的参考文档使用的机器可读字段 | 工具要求的语言标签语法与顺序 | `@throws InvoiceNotFoundError when the id is unknown` |
| TODO | 有负责人的计划内工作 | 标记加负责人、动作、issue 或移除触发条件 | `// TODO(maria): drop the shim after v2 ships (#512).` |
| FIXME/HACK/NOTE/WARNING | 缺陷、捷径、上下文或隐患 | FIXME/HACK：错误行为、负责人、移除触发条件；NOTE/WARNING：条件、后果、动作 | `// WARNING: without the caller's lock, the balance read races writers; acquire the lock first (#318).` |
| 弃用标记 | 迁移路径与移除版本 | 语言机制加替代项与版本 | `@deprecated Use create_invoice; removed in v3.0.` |
| 法律声明头 | 许可证与版权义务 | 位于要求位置的精确 SPDX 与版权行 | `// SPDX-License-Identifier: Apache-2.0` |
| 工具指令 | 给 linter、格式化工具或生成器的指令 | 最窄范围内的精确工具语法，并给出理由 | `// eslint-disable-next-line no-console -- CLI output.` |
| 生成标记 | 阻止手工编辑并指向生成器 | 位于顶部的工具原生标记，字节级一致 | `// Code generated by sqlc. DO NOT EDIT.` |
| 被注释掉的代码 | 无：旧代码由版本控制负责 | 删除它；使用构建系统，或带到期时间的标记指令 | `n/a` |

遗留项目强制要求的变更头按 `references/dimensions-inline.md` 第 10 节处理；该例外仅限既有文件，新文件不得引入。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 逐行重述的注释（`// increment i`） | 重复代码，而且最先失效 | 删除它；意图不明时重命名标识符。 |
| 与代码矛盾的过时注释 | 使读者形成错误理解 | 于同一次变更中修复或删除；每次行为变更后审查。 |
| 裸的 `// TODO: fix later` | 无负责人、无触发条件、无审查路径 | `TODO(owner): action and reason` 加一个 issue。 |
| 被注释掉的代码块 | 掩盖废弃 API，干扰搜索与覆盖率 | 删除它；依赖版本控制。 |
| `@param user the user` | 重复签名，未增加任何契约 | 写明格式、范围、可空性或所有权。 |
| 文件头里的变更历史 | 重复版本控制，而且立刻过时 | 删除它；遗留项目强制格式按 `references/dimensions-inline.md` 第 10 节处理；提交消息承载历史。 |
| 无理由的整文件 lint 抑制 | 掩盖未来所有违规，且存续时间超过其理由 | 仅在行级或函数级范围不可行时使用文件级；补上理由与清理工单。 |
| 无替代项的弃用 | 使调用方无迁移路径 | 补上替代项、版本与移除工单。 |
| 被注释掉的调试输出 | 造成污染，且会于提交中再次出现 | 使用可配置级别的 logger。 |
| 未指明动作的警告 | 读者无法针对隐患采取行动 | 写明条件、后果与必需动作。 |
| 示例中的机密或个人数据 | 注释随源码一起发布并泄露 | 使用 `example.test.invalid` 与占位标识符。 |
| 外语注释 | 破坏单一语言规则，拖慢审查 | 使用仓库声明的语言。 |
| 以注释代替具名常量 | 将含义置于代码之外 | 提取 `DEFAULT_TIMEOUT_MS` 并删除该说明。 |
| 于多个函数间复制的文档注释 | 副本之间互相漂移 | 链接到唯一的归属处，或只写一次契约。 |
| 作者或日期横幅 | 工具与读者都不需要的噪声 | 删除它；提交元数据承载该信息。 |
| 注释里的变更记录（`// 2026-02-11: changed order`） | 重复提交历史，并于下次变更时腐化 | 删除它；提交消息承载变更。 |

## 审查清单

- [ ] 注释补充了代码未说明的信息。
- [ ] 每条文档注释都与当前签名、行为与错误一致。
- [ ] 公开的参数、返回值、错误、副作用与不变量都有记录。
- [ ] 类型无法承载时，单位、范围、可空性与所有权都是显式的。
- [ ] 摘要只有一句：描述用现在时，指令用祈使式，并带句末标点。
- [ ] 行内注释位于所解释行的上方或旁边，缩进相同。
- [ ] 每个 TODO、FIXME 与 HACK 都有负责人，以及被跟踪的 issue 或移除触发条件；到期条目由 CI 报错。
- [ ] issue 引用使用 `#123` 或 `owner/repo#123`；外部跟踪器使用完整链接。
- [ ] 生成文件包含工具原生标记与 `@generated`。
- [ ] 每个 NOTE 与 WARNING 说明条件、后果与必需动作。
- [ ] 变更中未留下被注释掉的代码或调试输出；迁移期临时禁用的代码注明了负责人、工单与到期时间。
- [ ] 弃用声明写明替代项与移除版本或日期。
- [ ] 法律声明头与生成标记完整且未被修改。
- [ ] 工具指令最少且包含理由；文件级抑制还有清理工单。
- [ ] 任何注释中均无机密、令牌、个人数据或内部地址。
- [ ] 注释语言是仓库声明的语言，标识符保持不变。
- [ ] 行宽、标点、大小写与间距都符合项目约定。
- [ ] 支持 doctest 的文档工具中的代码示例已执行并产生所述输出；其余示例按非执行处理，标为 `text` 或 `console` 围栏。
- [ ] 生成文件与引入文件是重新生成的，而非手工编辑的。
- [ ] 被重构移动或删除的注释未留下孤立或过时的引用。
- [ ] 已配置的文档构建、doctest 与注释 linter 通过。
- [ ] 与独立文档重复的注释改为链接，而非复制。
- [ ] diff 中的每个行为变更都包含对应的注释更新。

## 示例

<example>
为公开函数写文档注释：

```python
"""Charge the invoice and return the payment id; raise PaymentDeclinedError when the gateway declines."""
```

项目使用 Google 风格时补上 `Args:` 与 `Raises:` 小节，不得在正文里重复类型提示。
该注释同时说明成功结果与调用方必须处理的失败；函数体不再重复。

</example>

<example>
在不显而易见的语句上方写行内理由：
`# Sort by created_at, not id: imports can insert older rows after the initial load.`
把它直接写在排序调用上方；比较器名称已经说明这一点的，应当删除该注释。
每条注释一个想法；第二个理由单独一行、单独审查。
</example>

<example>
对无锁读取写并发警告：

```text
// WARNING: the snapshot may be stale if a writer commits; take the write lock before comparing versions (#412).
```

按条件、后果、必需动作的顺序说明，并把完整历史链接到 issue。不得把隐患埋于一段描述之中。

</example>

<example>
带负责人与移除触发条件的标记：
`// TODO(maria): drop the retry shim when gateway v2 is the only client (#512, target v2.4).`
裸的 `// TODO: fix this` 无法通过审查；未被跟踪的工作不会留在代码里。
issue 编号与版本让不是作者的人也能够移除该标记。
</example>

<example>
修复过时的文档注释：
注释写着 `Return the cached user or None`，但函数现在会抛出 `UserNotFoundError`。
在同一次变更中重写契约，更新仍然承诺 null 的调用方注释，并修正断言 `is None` 的 doctest。
在仓库中搜索旧的承诺；一次行为变更通常留下不止一条过时注释。
</example>
