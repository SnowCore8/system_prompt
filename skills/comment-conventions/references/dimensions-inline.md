# 注释维度：行内说明与语言场景

本文件是 `SKILL.md` 维度索引中“行内说明与语言场景”部分的细则；节号与索引一致，其他维度见同目录的
`dimensions-*.md`。

## 2. 模块、文件与取值头

- 文件或模块头说明该单元的用途、范围与不变量；其并非记载“改了什么”历史或最近修复清单之处。
- Go 中，包注释紧贴 `package` 上方，以 `Package <name>` 开头，描述整个包；中间有空行将使其分离。
- Python 中，模块 docstring 是文件的第一条语句，说明模块的角色与公开入口。
- Rust 与 C/C++ 中，文件级文档使用 `//!` 或许可证头之后的 `@file` 块；不得在该处重复类型文档。
- 取值或常量头解释该数字的策略或来源（例如“与合作伙伴 API 的上限一致”），而非字面量本身。
- 头块中不含作者名、日期、被当作变更历史的工单号，也不含装饰性横幅。
- 应当链接独立的设计文档，不得复制它；重复文档的头会在两个地方同时过时。

| 好 | 差 | 原因 |
|---|---|---|
| `// Package billing reconciles invoices against the ledger.` | `// Billing package.` | 说明职责，而非文件夹。 |
| `# Time zone used for every cut-off date in this module.` | `# tz` | 说明该值为什么存在。 |
| `//! Parser for the v2 wire format; see docs/wire-format.md.` | `//! TODO: document module.` | 指向权威来源而不复制它。 |

## 8. TODO 与计划说明

- TODO、FIXME 或 HACK 是带负责人的承诺。格式为 `MARKER(owner): action and reason`，并附 issue 或移
  除条件。
- 应当按含义使用标记：TODO 表示计划内工作，FIXME 表示已知的错误行为，HACK 表示有意为之的捷径，NOTE 表
  示上下文，WARNING 表示隐患。
- 不得留下裸的 `TODO`、`FIXME`、`XXX` 或 `???`；匿名标记是任何审查都无法解决的未跟踪债务。
- 应当把标记绑定到触发条件：版本、日期或依赖升级，而非含糊的“以后”。
- 应当使用平台可解析的 issue 引用：同仓库写作 `#123`，跨仓库写作 `owner/repo#123`，外部跟踪器使用完整 URL；
  仅写数字或“以后修复”无法从代码跳转到工单，读者仍需再次搜索。
- 触发条件到期后应当由 CI 强制：把带日期或版本的标记接入扫描器，使到期条目于构建中报为错误，而非
  无人查看的警告；到期意味着移除该标记或重新排期，二者择一。
- 应当将标记置于其约束的代码旁；文件顶部的计划说明对阅读该行的人不可见。
- 不再成立的标记是错误注释：工作落地时应当删除它，不得仅作勾选标记。
- 扫描工具（todo-tree、issue linter）依赖精确的标记拼写；应当使用项目配置的风格。

| 好 | 差 | 原因 |
|---|---|---|
| `// TODO(maria): remove the retry shim after gateway v2 ships (#512).` | `// TODO: fix this later.` | 负责人与触发条件使债务可审查。 |
| `// FIXME(maria): negative totals round toward zero; fix before v2.2.` | `// HACK.` | 负责人与期限使修复可审查。 |
| `// HACK(devon): the vendor header requires a trailing space; do not trim.` | `// Weird.` | 负责人与理由说明捷径为何必须保留。 |

## 9. 被注释掉的代码

- 应当删除代码，不得将其注释掉；版本控制保留历史，删除亦保持可逆。
- 为某个构建变体禁用的代码属于构建系统：功能开关、预处理器条件编译或配置，而非注释。
- 迁移期间确实需要临时禁用的，应当标明负责人、工单与到期时间，并设置一项到期后会失败的校验。
- 被注释掉的代码会干扰搜索结果与覆盖率报告，并掩盖未使用的导入与废弃 API。
- 不得以“以防万一”为由把调试输出注释掉；应当改用可配置级别的 logger。
- 审查时，应当把被注释掉的代码块当作删除请求，而非风格问题。
- 有意的代码示例应当仅保留在带围栏且有测试的文档示例中（见 `dimensions-api.md` 第 11 节）。
- 自动校验具有助益：在 diff 中标记被注释掉代码的扫描，较逐个代码块争论更为可行。

## 10. 变更历史与日志式注释

- 版本控制历史即变更日志；不得于注释中重述它（“2026-03-01：新增重试”、“Sam 修改”）。
- 不得把作者标签、日期或逐行版本标记当作项目历史保留；提交元数据承载这些信息。
- 未来读者需要的理由是现在时的上下文（“供应商拒绝空请求体”），而非日志条目。
- 强制要求变更头的遗留项目：应当于既有文件中遵循既有格式，并记录迁移期限；新文件不得引入。
- 除发布工具会生成并校验外，不得于文件头中添加版本号。
- 新决定取代旧决定时，应当以当前规则替换旧注释；不得于顶部再叠加第二行历史。

## 12. 生成代码与第三方引入代码的标记

- 不得手工编辑生成文件；应当修改生成器或事实来源，重新生成，并连同其标记一起提交输出。
- 应当将工具生成的标记按原样保留在顶部（“Code generated by ... DO NOT EDIT.”）；工具与审查者依赖它。
- 生成文件应当在工具原生标记之外包含 `@generated`，使 GitHub 在 diff 中折叠生成内容；折叠只影响审查视图，
  不改变只读规则，标记行仍须字节级保留。
- 生成的文档注释属于生成器的模板；应当修改模板，不得修改实例。
- 引入的第三方代码应当逐字保留其上游注释、头与许可证；应当于文件之外记录版本与本地补丁集。
- 本地补丁无法避免时，应当保持最小、带补丁说明，并由引入流程重新应用。
- 应当从注释密度与风格校验中排除生成路径与引入路径；它们不是审查对象。
- 生成文件中与生成器矛盾的注释是生成器的缺陷；应当修改来源。

| 好 | 差 | 原因 |
|---|---|---|
| `// Code generated by sqlc. DO NOT EDIT.` | `// Generated, but tweak the types here if needed.` | 任何手工编辑都会在下次运行时丢失。 |
| `// Patch: upstream v2.3.0; our fix tracked in issue #644.` | `// Modified.` | 写明基线与被跟踪的差异。 |
| `// Source: schema.sql; regenerate with make gen-db.` | `// Auto.` | 给出生成器与命令。 |

## 15. 测试与 fixture

- 测试注释说明场景以及该用例为什么存在（回归、边界、契约），而非调用了哪些方法。
- 应当在测试名称中写明行为；注释用于说明行为为何重要，以及指向缺陷或决定的链接。
- 应当解释不显而易见的安排：fixture 为什么大、时钟为什么冻结、为什么预期会重试。
- 仅当期望值需要说明出处时，方注释断言（“与账本的舍入规则一致”）。
- 跳过与预期失败的理由应当写在框架的理由字段或旁边的注释内；未作解释的跳过属于静默删除。
- fixture 数据注释说明场景，不得含真实个人数据；应当使用假值，存在生成器时注明生成器。
- 不得把失败的测试注释掉；应当修复它，并针对任何跳过、隔离或豁免处置遵循
  `testing-and-quality-conventions`。

## 16. 配置与基础设施

- 每种格式有自己的注释语法与持久化规则；应当使用语言矩阵，而非源语言的语法。
- YAML 与 TOML 使用 `#`；应当将注释置于其所解释的键上方，不得置于带引号的标量内部。
- Dockerfile 注释以 `#` 置于指令上方；续行指令内部的整行注释会被解析器删除，而命令文本后同一行的行尾
  `#` 属于 shell 命令。
- SQL 迁移带有注释头，写明工单、意图与回滚说明；已应用的迁移不可变，因此修正以新文件到来。
- Terraform 与 HCL 使用 `#`；应当将持久的解释置于 `description` 属性，使 `terraform-docs` 一并输出。
- 基础设施注释说明某项设置存在的原因，以及缺少它时何种行为将失效；不得重述取值。
- 不得于配置注释中放置凭据、令牌、账号标识符或内部主机名；应当改为引用机密存储。

| 好 | 差 | 原因 |
|---|---|---|
| `# Keep 1 replica during the backfill; the writer serializes.` | `# replicas = 1` | 解释临时约束。 |
| `-- 20261114_add_status: add status for audit; rollback drops it.` | `-- migration` | 意图与回滚可见。 |
| `variable "ttl_days" { description = "Retention; 0 disables expiry." }` | `description = "TTL"` | 文档工具承载契约。 |

## 17. Shell 脚本

- 应当以 shebang 开头，并撰写一个简短的目的块：脚本的用途、接受的参数与所需环境。
- 注释以 `#` 开头且必须开启一个词；`echo value#suffix` 不是注释。
- Shell 无块注释；`: <<'END' ... END` 这种 here-document 技巧属于变通做法，不是约定，且不得用它包住
  会执行的命令。
- 应当在对应行旁边解释不常见的标志、引号要求与错误处理选择，不得另建一份图例。
- 应当在设置旁边记录 `set -euo pipefail` 的效果以及任何有意的例外。
- 使用 `# shellcheck disable=SC2086` 这类 linter 指令时，应当给出理由与最窄范围。
- 不得把被注释掉的命令当作用法文档；应当将预期用法置于 `usage()` 函数或 `--help` 中。

## 18. 标记语言、CSS 与模板注释

- HTML 注释（`<!-- ... -->`）会发送到浏览器；不得在其中放置机密、个人数据或内部 URL，并应当在构建工
  具支持时于生产环境剥离它们。
- HTML 注释不得包含 `--`，亦不得嵌套；应当拆分注释或改用其他分隔符。
- CSS 注释仅使用 `/* ... */`；`//` 在纯 CSS 中无效，在 Sass/SCSS 中是不会输出的静默注释。
- 应当于 Sass 中有意选择输出型或静默型：`/* */` 会保留到浏览器，`//` 仅供维护者阅读。
- 模板引擎有自己的语法：Jinja 用 `{# #}`，ERB 用 `<%# %>`，Handlebars 用 `{{! }}`；不得于模板中以输
  出语言的语法包裹注释。
- JSX 与 TSX 注释为 `{/* ... */}`；JSX 文本中的裸 `//` 会被渲染成文本。
- 注释用于结构、可访问性意图与条件包含；营销文案与法律声明应当保留在内容或构建工具中。

## 19. i18n 与本地化注释

- 每个仓库应当为注释声明一种自然语言，并应用到每个文件；多语言混用的注释属于审查缺陷。
- 标识符、API 字段名、协议术语与引用的上游文本应当保持原语言；不得于正文中翻译符号名。
- 本地化代码库中，对本地团队需要的领域、监管或法律背景，应当使用声明的语言。
- 不得把注释当作面向用户文本的翻译来源；用户文本属于资源文件与 i18n 键。
- 工具链、编码或终端会破坏非 ASCII 字符时，应当避免使用它们；在重要之处记录编码策略。
- 标点应当与声明的自然语言保持一致；代码的标识符大小写规则仍然适用。
- 注释引用本地化文档时，应当引用其路径与节号，而非可能变化的译文标题。
