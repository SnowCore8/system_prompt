# 注释维度：策略、卫生与审查

本文件是 `SKILL.md` 维度索引中“策略、卫生与审查”部分的细则；节号与索引一致，其他维度按同目录的
`dimensions-*.md` 查阅。

## 13. 法律与许可证头

- 应当把许可证头精确放在许可证工具或项目策略要求的位置：通常为文件开头几行，在导入与文档注释之前。
- 应当使用项目标准形式的 SPDX 标识符，例如 `SPDX-License-Identifier: Apache-2.0`；不得改写许可证
  文本。
- 应当保留原始权利人的版权行；添加贡献者行应当遵循项目策略，而非个人偏好。
- 不得删除或重排引入代码中的第三方头；应当保留声明并添加项目的 NOTICE 条目。
- 应当让许可证工具（reuse、licensee、addlicense、某个格式化插件）写入并更新头；不得手工拼装变体。
- 法律声明头不得替代许可证文件；应当链接完整文本，不得将其粘贴进每一文件。
- 删除头属于法律与构建层面的变更；应当由项目所有者决定，不得作为一次清理实施。
- 生成文件从生成器模板获得头；应当修模板，不得逐个修输出文件。

## 14. 工具指令

- 指令属于供机器读取的代码：应当精确匹配工具的语法与范围，并放在工具读取它的位置。
- 应当使用能够起作用的最窄范围：先一行，再一个函数，再一个文件；不得为修复一个位置而在仓库范围禁用规则。
- 应当始终按工具支持的形式给出理由（ESLint 用 `-- reason`，其他工具使用邻近注释）；未作解释的抑制无法
  审查。
- 抑制不构成修复：文件级抑制还应当留下清理工单，说明何时可以移除。
- 指令类别：禁用 lint（`eslint-disable-next-line`、`# noqa`、`//nolint`、`@SuppressWarnings`）、关闭
  格式化（`prettier-ignore`、`# fmt: off`、`clang-format off`）、忽略覆盖率（`pragma: no cover`）、
  忽略类型（`@ts-expect-error`、`# type: ignore`）。
- 语言支持时，应当优先用注解或属性而非注释；配置属于配置文件，而非某次调用之旁。
- 不抑制任何对象的过时指令属于冗余内容；应当在它掩盖下一条真实违规之前删除它。

| 好 | 差 | 原因 |
|---|---|---|
| `// eslint-disable-next-line no-console -- CLI output is the product.` | `/* eslint-disable */` | 范围与理由都是显式的。 |
| `x = stub.field  # type: ignore[attr-defined]  # vendor stub lacks it` | `x = stub.field  # type: ignore` | 代码与理由都写明了。 |
| `//nolint:errcheck // close error is reported by the caller` | `//nolint` | 只禁用被理解的那条规则。 |

## 20. 注释中的机密与隐私

- 应当把注释当作公开内容：它们会随源码、生成的文档、调试符号与包一起发布；不得在其中放置凭据、令牌、密
  钥或连接字符串。
- 被注释掉的代码是常见的泄露渠道；发现其中嵌有凭据的，应当立即停止操作、保留证据并报告，不得先删除。
- 不得在示例中添加真实姓名、邮箱、电话、地址、客户 ID 或生产 URL；应当使用 `example.test.invalid` 与
  占位标识符。
- 不得在公开或引入的注释中描述内部网络、服务拓扑或主机名。
- 应当对注释中的安全事件细节脱敏；指向私有跟踪系统，而非粘贴报告。
- 在注释中发现机密属于一起安全事件：应当立即停止操作、保留证据并报告，随后按 `security-compliance-conventions` 的泄露响应轮换与披露；调查结束前不得清理，一旦提交，仅删除该行不足以补救。
- 应当在 pre-commit hook 与 CI 中扫描机密模式，并把注释纳入检测范围。
- 脱敏时，应当用 `REDACTED` 这类明显的占位符替换该值；空值将被理解为确实不存在。

## 21. 注释密度、行宽、标点与大小写

- 应当以完整句子书写注释，句首大写并带句末标点；每条注释一个想法。
- 行宽由 `code-style-conventions` 从项目配置读取；续行应当折到该宽度，不得重排不相关的注释。
- 块注释与它所描述的代码之间应当空一行；行尾注释仅用于简短的、行内的说明。
- 首词大写，并遵循注释语言的标点；全大写仅留给 `NOTE:` 与 `WARNING:` 这类既有标记。
- 应当避免 ASCII 艺术、横幅分隔线与对齐填充；它们会被格式化工具破坏，并产生 diff 噪音。
- 注释密度取决于意外程度，而非行数：应当注释不显而易见的内容；逐行叙述式的过密注释与完全无注释
  都是审查发现项。
- 工具链要求时，应当保持注释为 ASCII，并删除行尾空白；缩进由格式化工具负责。

| 好 | 差 | 原因 |
|---|---|---|
| `// Reuse the pooled client: TLS handshakes dominate this path.` | `// get client` | 解释选择，而非调用。 |
| `# Start inclusive, end exclusive; empty when start equals end.` | `# range` | 说明读者容易猜错的约定。 |
| `/* The partner API treats 429 as retryable after 30 s. */` | `/* 30 s */` | 把外部约束与取值放在一起。 |

## 22. 过时与说谎的注释

- 错误注释比无注释更糟；其以确定的表述将读者引向错误的方向，属于有修复期限的缺陷。
- 每次行为变更都应当包含注释审查：搜索旧的函数名、参数、默认值、返回类型与错误文本。
- 引用已删除代码、已删除文件、旧版本或失效工单的注释必须删除，不得为提供上下文而保留。
- 为真但已不再必要的注释（琐碎的重述）也是过时的；代码清晰时应当删除它。
- 自动化检测：doctest 于 CI 中运行，链接检查器捕获失效引用，文档工具警告仅在 CI 将其升级时，方使构
  建失败（`RUSTDOCFLAGS=-D warnings`、Sphinx `-W`、把 doclint 当作错误）。
- 审查时应当先读注释再读代码；两者不一致时，这次变更是不完整的。
- 存续时间超过触发条件的 TODO 或弃用属于错误注释；应当用定期校验标出逾期标记。
- 注释中应当引用符号与节号，而非行号或文件路径；行引用将于下次编辑时失效。

## 23. 重构与移动注释

- 注释随它所解释的代码一起移动；文档注释属于声明，而不属于调用点或旧文件。
- 抽取函数时，应当把契约移到新声明，只在调用方保留调用点的理由。
- 内联函数时，仅当承诺仍然成立，方可将它的契约并入周围的文档注释；否则应当删除它。
- 拆分函数时，应当按职责拆分它记录的契约；不得把整条注释复制到两半。
- 符号、参数或节移动时，应当更新所有引用：生成的文档链接、锚点与跨文件指针。
- 不得为“保留历史”而保留关于已移动代码的注释；版本控制跟踪移动，过时的副本属于不实记载。
- 重命名之后，应当在注释、文档与示例中搜索旧名称；仍在使用旧名称的注释是缺陷。
- 代码移动进生成代码或第三方代码时，应当删除旧注释，并把理由记录到跟踪系统或设计说明中。

## 24. 注释审查流程

- 应当在 diff 中阅读每一条新增或修改的注释，并查明其所保护的是哪一行代码。
- 应当检查契约：签名、参数、返回值、错误、副作用与边界情况是否仍然一致。
- 应当检查形式：语法、标签、行宽、自然语言与标记拼写。
- 应当检查隐患：机密、个人数据、内部地址与被复制的第三方文本。
- 应当验证文档构建、doctest 与注释 linter；仅修改注释的变更亦应当运行它们。
- 应当移除触发条件已过的标记；把未跟踪的 TODO 转为有链接的 issue，或删除它们。
- 注释与独立文档重复时，应当链接该文档，只保留读者需要的差异部分。
- 应当把注释缺陷与行为缺陷分开报告，使作者能够看出必须修改的内容。
