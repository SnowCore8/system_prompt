# 注释维度：策略、卫生与审查

本文件是 `SKILL.md` 维度索引中「策略、卫生与审查」部分的细则；节号与索引一致，其他维度见同目录的 `dimensions-*.md`。

## 13. 法律与许可证头

- 把许可证头精确放在许可证工具或项目策略要求的位置：通常是文件开头几行，在导入与文档注释之前。
- 使用项目标准形式的 SPDX 标识符，例如 `SPDX-License-Identifier: Apache-2.0`；不要改写许可证文本。
- 保留原始权利人的版权行；添加贡献者行遵循项目策略，而不是个人偏好。
- 绝不删除或重排引入代码中的第三方头；保留声明并添加项目的 NOTICE 条目。
- 让许可证工具（reuse、licensee、addlicense、某个格式化插件）写入并更新头；绝不手工拼装变体。
- 法律声明头不能替代许可证文件；链接完整文本，而不是把它粘贴进每个文件。
- 删除头是法律与构建层面的变更；它需要项目所有者决定，而不是一次清理。
- 生成文件从生成器模板获得头；修模板，而不是逐个修输出文件。

## 14. 工具指令

- 指令是给机器读的代码：精确匹配工具的语法与范围，并放在工具读取它的位置。
- 使用能起作用的最窄范围：先一行，再一个函数，再一个文件；绝不要为修一个位置而在仓库范围禁用规则。
- 始终按工具支持的形式给出理由（ESLint 用 `-- reason`，其他工具用邻近注释）；没有解释的抑制无法审查。
- 抑制不是修复：文件级抑制还要留下清理工单，说明何时可以移除。
- 指令家族：禁用 lint（`eslint-disable-next-line`、`# noqa`、`//nolint`、`@SuppressWarnings`）、
  关闭格式化（`prettier-ignore`、`# fmt: off`、`clang-format off`）、忽略覆盖率
  （`pragma: no cover`）、忽略类型（`@ts-expect-error`、`# type: ignore`）。
- 语言支持时，优先用注解或属性而不是注释；配置属于配置文件，而不是某次调用旁边。
- 什么都不抑制的过时指令是死重；在它掩盖下一条真实违规之前删除它。

| 好 | 差 | 原因 |
|---|---|---|
| `// eslint-disable-next-line no-console -- CLI output is the product.` | `/* eslint-disable */` | 范围与理由都是显式的。 |
| `x = stub.field  # type: ignore[attr-defined]  # vendor stub lacks it` | `x = stub.field  # type: ignore` | 代码与理由都写明了。 |
| `//nolint:errcheck // close error is reported by the caller` | `//nolint` | 只禁用被理解的那条规则。 |

## 20. 注释中的机密与隐私

- 把注释当作公开内容：它们会随源码、生成的文档、调试符号与包一起发布；绝不在其中放凭据、令牌、密钥
  或连接字符串。
- 被注释掉的代码是常见的泄露渠道；删除前先检查其中是否嵌有凭据。
- 绝不在示例中添加真实姓名、邮箱、电话、地址、客户 ID 或生产 URL；使用 `example.test.invalid` 与
  占位标识符。
- 不要在公开或引入的注释中描述内部网络、服务拓扑或主机名。
- 对注释中的安全事件细节脱敏；指向私有跟踪系统，而不是粘贴报告。
- 在注释中发现机密是一起安全事件：删除它、轮换它，并遵循披露流程；一旦提交，只删那一行是不够的。
- 在 pre-commit hook 与 CI 中扫描机密模式，并把注释纳入检测范围。
- 脱敏时，用 `REDACTED` 这类明显的占位符替换该值；空值会被读成真的不存在。

## 21. 注释密度、行宽、标点与大小写

- 用完整句子写注释，句首大写并带句末标点；每条注释一个想法。
- 行宽由 `code-style-conventions` 从项目配置读取；续行折到该宽度，绝不重排不相关的注释。
- 块注释与它所描述的代码之间空一行；行尾注释只用于简短的、行内的说明。
- 首词大写，并遵循注释语言的标点；全大写只留给 `NOTE:` 与 `WARNING:` 这类既有标记。
- 避免 ASCII 艺术、横幅分隔线与对齐填充；它们会被格式化工具破坏，并制造 diff 噪音。
- 注释密度取决于意外程度，而不是行数：注释不显而易见的内容；逐行叙述式的过密注释与完全没有注释
  都是审查发现项。
- 工具链要求时保持注释为 ASCII，并删除行尾空白；缩进交给格式化工具。

| 好 | 差 | 原因 |
|---|---|---|
| `// Reuse the pooled client: TLS handshakes dominate this path.` | `// get client` | 解释选择，而不是调用。 |
| `# Start inclusive, end exclusive; empty when start equals end.` | `# range` | 说明读者容易猜错的约定。 |
| `/* The partner API treats 429 as retryable after 30 s. */` | `/* 30 s */` | 把外部约束与取值放在一起。 |

## 22. 过时与说谎的注释

- 错误注释比没有注释更糟；它自信地把读者带向错误方向，是有修复期限的缺陷。
- 每次行为变更都包含注释审查：搜索旧的函数名、参数、默认值、返回类型与错误文本。
- 引用已删除代码、已删除文件、旧版本或失效工单的注释必须删除，不能为了提供上下文而保留。
- 为真但已不再必要的注释（琐碎的重述）也是过时的；代码清晰时删除它。
- 自动化检测：doctest 在 CI 中运行，链接检查器捕获失效引用，文档工具警告只有在 CI 将其升级时才会
  让构建失败（`RUSTDOCFLAGS=-D warnings`、Sphinx `-W`、把 doclint 当作错误）。
- 审查时先读注释再读代码；两者不一致时，这次变更是不完整的。
- 活得比触发条件更久的 TODO 或弃用是错误注释；用定期校验标出逾期标记。
- 注释中引用符号与节号，而不是行号或文件路径；行引用会在下次编辑时腐化。

## 23. 重构与移动注释

- 注释随它所解释的代码一起移动；文档注释属于声明，而不属于调用点或旧文件。
- 抽取函数时，把契约移到新声明，只在调用方保留调用点的理由。
- 内联函数时，只有承诺仍然成立才把它的契约并入周围的文档注释；否则删除它。
- 拆分函数时，按职责拆分它记录的契约；不要把整条注释复制到两半。
- 符号、参数或节移动时更新所有引用：生成的文档链接、锚点与跨文件指针。
- 不要为“保留历史”而保留关于已移动代码的注释；版本控制跟踪移动，过时的副本是谎言。
- 重命名之后，在注释、文档与示例中搜索旧名称；仍在使用旧名称的注释是缺陷。
- 代码移动进生成代码或第三方代码时，删除旧注释，并把理由记录到跟踪系统或设计说明中。

## 24. 注释审查流程

- 在 diff 中阅读每一条新增或修改的注释，并问它保护的是哪一行代码。
- 检查契约：签名、参数、返回值、错误、副作用与边界情况是否仍然一致。
- 检查形式：语法、标签、行宽、自然语言与标记拼写。
- 检查隐患：机密、个人数据、内部地址与被复制的第三方文本。
- 验证文档构建、doctest 与注释 linter；只改注释的变更也要运行它们。
- 移除触发条件已过的标记；把未跟踪的 TODO 变成有链接的 issue，或删除它们。
- 注释与独立文档重复时，链接该文档，只保留读者需要的差异部分。
- 把注释缺陷与行为缺陷分开报告，让作者能看出必须改什么。
