# 依赖版本管理

## 1. 依赖版本管理

manifest 是设计文档，不是便利清单；锁文件 diff 是实际发布内容的证据。

- 仅声明直接依赖：导入某一包系因 manifest 已声明它，不因另一依赖安装了它；仅被测试或脚本导入的依赖同样声明。
- 每个项目只提交一个锁文件并作为构建输入：`package-lock.json`、`uv.lock`、`go.sum`、`Cargo.lock`；CI 以冻结模式安装，不以删除锁文件解决冲突。
- 按角色锁定：应用锁定精确版本与镜像摘要，库声明兼容范围并测试最低支持版本；CI 工具与基础镜像同样锁定并有意识地升级。
- 多包仓库把同一依赖的版本集中声明一处：`libs.versions.toml`、`<dependencyManagement>`、`[workspace.dependencies]`；子包只引用该键。
- 按计划更新而非机会主义更新：补丁版本走固定节奏的自动化拉取请求，主版本专门审查发布说明与破坏性变更；自动更新设最短发布时长。
- 彻底移除：删除使用点与 import、移除 manifest 条目、重新生成锁文件，再清理相关配置、环境变量与凭据；许可证声明与 SBOM 在同一次变更中更新。
- 预发布版本或提交哈希只在没有任何发布版本可用时使用，并记录该锁定为何无法移到某个版本。

### 依赖准入

- 准入顺序：先看标准库与现有依赖，再看维护良好的第三方库；现有实现能胜任的不手写。
- 准入证据：有维护且近期有发布、issue 响应及时、无已知未修补漏洞、许可证兼容、有负责人能移除；费用、安装占用与传递依赖数量如实记录，但不单独构成拒绝理由。
- 漏洞、许可证与供应链判据由 `security-compliance` 裁定；本文件只要求准入证据随拉取请求提交。
- 私有包仓库经仓库配置接入，凭据自 CI 机密存储注入；包仓库不可达时失败关闭，不回退公共镜像。
- 移除依赖即缩小攻击面：代码不再引用而 manifest 仍声明，该依赖仍会发布与被扫描。
