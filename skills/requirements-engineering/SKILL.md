# 需求工程

受理与需求是生命周期中修正成本最低、影响最大的位置。请求分类错误会把整个项目引向错误对象；验收标准不可判定，构建与验证只能靠猜测；收益没有基线，收尾时无法判断是否值得。本 skill 管辖 S0 受理与 S1 需求：把请求固定为可复核的受理记录，把想法提炼为带验收标准、收益基线与优先级的需求，使后续设计、构建与收尾都有可对照的基准。
智能体任务、软件交付与组织级立项共用本 skill 的判据，差异只在工件厚度。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制约束。宿主、法律、平台与 `rules/global-user-constraints.md` 的授权（AUT）、意图（INT）、诚实（HON）与不确定（UNC）条款优先；请求分类与歧义处理不得与本层冲突。
2. 本 skill 的规则。受理记录、需求收集、验收标准、DoR、收益基线与优先级排序，以本文件与 `references/` 为准。
3. 项目约定与事实。既有需求文档、术语表与待办属于事实输入，依本 skill 的规则处理，仅在本 skill 未规定时补充。

本 skill 管辖：请求复述与分类、授权与风险分级的记录、需求收集与澄清、验收标准、Definition of Ready、收益基线与结果指标、选项比较与优先级。
本 skill 不管辖：方案与架构裁定（`architecture-design`）、任务拆分与估算（`planning-estimation`）、实现与提交（`implementation-practices`），以及测试策略与发布操作（对应专业 skill）。

## 生命周期定位

上游：用户请求、问题反馈、组合提案或变更请求。下游：S2 设计的范围与验收输入，S3 构建的待办条目。停止条件：对象缺失或歧义无法澄清、授权或风险级别无法确定、收益无法衡量且无人确认价值时，停止收集并报告，不得按推测推进。

| 阶段 | 职责 | 产出与证据 |
|---|---|---|
| S0 受理 | 复述请求并分类，确认授权、风险级别、停止条件与负责人 | 受理记录、分类结论、G0 证据 |
| S1 需求 | 收集并澄清问题与用户，定义验收标准、收益基线与选项比较，排序并给出建议 | 需求说明、验收标准、收益基线、选项比较、DoR 结论、G1 证据 |
| S2 设计 | 移交可实施的需求与验收标准，参与固定范围与非范围 | 需求移交清单、DoR 复核结论 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G0 受理 | 请求复述、分类依据、授权依据、风险级别、停止条件、负责人 | 澄清或 Hold；不得进入需求收集 |
| G1 需求 | 问题与用户、可判定验收标准、收益基线与结果指标、至少两个选项的比较（含不做事）、建议与主要风险 | Hold：证据缺失；Recycle 到 S1：需求不可判定；No-Go：价值不成立 |
| G2 设计 | DoR 检查结论、验收标准与验收人、未决需求及负责人 | Hold：条目未满足 DoR 不得进入 S3；Recycle 到 S1：验收标准不可判定 |

## 核心规则

- 先复述，后行动。S0 先复述对象、动作与预期结果，再确认授权与风险；缺少关键对象或存在歧义时按 INT 条款列出不同理解，不得按最可能的解释实施。
- 区分“想要”与“需要”。记录用户说出的要求，同时追问其要完成的任务；两者不一致时以要完成的任务为分析对象，并把不一致记为待确认项。
- 验收标准必须可判定。每条标准写明对象、条件与判据，可由非作者执行并得出通过或失败；“好用”“更快”等词语不得充当验收标准。
- 收益必须可衡量。每个结果指标写明测量方式、当前基线与目标值；没有基线的先测量，不得以“改善”替代数字。
- 选项至少两个。任一提案都列出至少两个选项（含不做事），比较成本、风险与收益后给出建议；只列一个方案视为未完成探索。
