# 文档维度：项目与内容

本文件与 `SKILL.md` 配合使用。每一节规定一个文档维度的规则、示例与边缘情况。项目约定与事实作为输入；本 skill
的规则优先，项目约定仅在本 skill 未规定时补充。本文件提供默认值与理由。智能体应当阅读与待编写或待审查文档相匹配
的节。

## 1. README

- 应当以一句话开头，说明项目是什么、面向哪类读者以及做什么；仅有项目名称，不构成描述。
- 应当包含安装、能够产生可见结果的快速开始、载明默认值的配置，以及指向更深入文档的链接；完整的功能巡览应当
  省略，其过时最快。
- 应当在安装命令旁说明前提（运行时版本、操作系统、数据库）；未说明前提，为首次运行失败最常见的原因。
- README 应当简短且稳定；详细工作流置于 `docs/guides/`，并由 README 建立链接。
- 应当包含许可证与支持路径（issue 跟踪器、讨论论坛）；二者均无的项目，外观上等同于已废弃项目。
- 仅在徽章有效且具有实际意义时使用；失效的构建徽章将损害展示该徽章的页面。
- 每次发布前，应当于干净环境中测试快速开始；README 为阅读量最大的页面，亦为最先失效的页面。

| 好 | 坏 | 为什么 |
|---|---|---|
| “开具发票并对账付款。” | “一个强大的计费平台。” | 指明工作内容；口号不构成描述。 |
| 安装一节写明运行时版本与命令。 | 安装一节省略 Python 版本。 | 将导致首次运行失败。 |
| 快速开始以可见结果结束。 | 以“配置很简单”结束。 | 结果可以确认环境搭建成功。 |
| 链接至指南，以了解真实工作流。 | 将完整工作流复制至 README。 | 副本将漂移；仅单一页面可以保持正确。 |

## 2. 上手与 CONTRIBUTING

- 应当将环境搭建、运行、测试、lint 与构建的命令入口置于同一列表，自全新克隆即可工作；命令值以项目配置为准，
  文档只保留入口与链接（命令规则见 `testing-and-quality-conventions` 的 CH-8）；仅在命令需要某一选项时，链接
  至工具文档。
- 应当说明分支、提交与审查约定，以及预期的审查时间；不了解规则的贡献者，将在审查中为该缺口付出代价。
- 应当包含首次变更路径：一项小任务、该任务涉及的文件，以及证明可行的命令。
- 应当写明代码所有者、支持渠道，以及跨团队或跨仓库变更的决策路径。
- 应当记录环境搭建的失败模式（缺少系统包、运行时错误、端口被占用）及其各自的精确修复方法。
- 贡献者上手与用户上手应当分开；二者的受众、工具链与成功标准不同。
- 工具链变更时，应当于干净机器或容器上验证环境搭建；上手文档的失效速度快于其他页面。
- 首次发布前，应当要求新贡献者依指南走一遍；作者无法察觉被跳过的步骤。

GitHub 贡献入口：

- `CONTRIBUTING.md` 从 README、issue 表单配置与 PR 模板三处链接；贡献者不应在提问后才能找到环境搭建与审查预期。
- `.github/ISSUE_TEMPLATE/` 放置 bug 与功能表单，必填字段为复现步骤、期望行为、版本与环境；`config.yml` 关闭
  空白 issue，并把使用问题、漏洞报告与支持请求分别指向 Discussions、私有漏洞报告与 `SUPPORT.md`。
- PR 模板写明关联 issue、变更类型、验证证据、风险与回滚、自审清单；多个模板以文件名区分，并在贡献指南中说明
  选择方式。模板字段与仓库 PR 规范一致，不得要求作者提供未使用的信息。
- `CODE_OF_CONDUCT.md`、`SUPPORT.md` 与 `SECURITY.md` 从贡献指南与 README 可达；行为准则写明执行联系人与
  处理流程，支持页写明范围与响应目标，安全页链接私有报告入口。
- issue 标签分类由 `naming-conventions` 管辖；本 skill 要求表单与模板使用同一套分类，避免作者在提交时猜测。

## 3. 架构与设计文档

- 应当以新维护者所需粒度描述组件、边界、数据流与部署形态；接口应当链接至代码，不得复述。
- 应当记录塑造设计的约束（规模、延迟、合规、团队规模），并链接拥有各项决策的 ADR。
- 应当写明架构依赖的外部系统与契约，以及每份契约的负责人。
- 仅保留一份当前架构页；被取代的图表应当删除或移至历史文件，不得留存于当前页旁。
- 图表应当保持最新；格式、源文件与标注规则见 `dimensions-usage.md` 第 13 节“图表与截图”。
- 应当包含简短的“已知限制”一节：设计无法实现的事项，以及需要变更的事项。
- 组件边界移动或新增外部依赖时，应当审查该页面。

## 4. ADR 与决策记录

- 每条记录仅载一项决策，编号且不可变；决策变更时，应当编写新的 ADR 取代旧记录。
- 应当在顶部以一句话陈述决策，其后为状态、背景与后果；仅作扫读的读者阅读第一行即可停止。
- 备选方案为必需内容，以其显示被否决的方案及理由；未载备选方案的记录将引发重复争论。
- 应当如实记录后果，包括成本与已接受的风险；仅列好处的 ADR 属于辩护词。
- 每条记录应当标注日期，并自架构页与实现该决策的变更建立链接。
- ADR 应当置于仓库中，使其随代码一同版本化；仅存于聊天中的决策将丢失。
- 不得重写已接受的 ADR；应当追加一条取代链接，并保持原文完整。
- ADR 仅用于约束后续工作的决策；成本较低且可逆的选择，以代码注释或笔记记录即可。

| 好 | 坏 | 为什么 |
|---|---|---|
| “状态：由 ADR-0012 取代”，并附链接。 | 悄然编辑已接受的文本。 | 读者亦需要历史。 |
| 后果一节列出成本与风险。 | 记录仅列好处。 | 隐藏成本日后将受到评判。 |
| 载明日期并自实现链接至该记录的条目。 | 文件夹中未载日期的文件。 | 日期与链接决定顺序。 |
| 记录中保留被否决的备选方案。 | 记录未载备选方案。 | 否决记录可以防止重新争论。 |

## 7. 解释与概念文档

- 应当以页面所传达的唯一想法开头；读者仅记住一句话的，该句应当即为该想法。
- 应当在任何步骤之前解释模型及其词汇；概念页回答原因，并链接到相应操作指南。
- 应当使用一个贯穿示例，并在整页保持一致；第二个示例将重置读者的上下文。
- 应当明确陈述权衡，包括该模型属于错误选择的情形；推销式的概念页属于营销材料。
- 每个术语首次使用时应当定义，并链接至术语表；不得假定读者具备团队背景。
- 模型与当前实现应当分开；应当链接实现页面，不得描述内部细节。
- 页面应当保持稳定；仅在模型变化时修改，不得因每增加一个选项而修改。
- 应当以链接结束：应用该模型的教程，以及列出选项的参考。

## 16. 术语与术语表

- 每个项目仅保留一份术语表，只写散文定义；规范名称、大小写与被禁用的同义词由 `naming-conventions` 的项目命
  名表裁定，术语表应当链接该表。
- 术语表应当置于单一文件；每个团队各设一份的，将漂移并互相矛盾。
- 每个术语应当定义一次并链接至该定义；不得在每个页面上重新定义。
- 定义应当说明该术语在项目中的含义与边界；规范拼写、大小写与缩写形式由项目命名表规定，不在术语表内重复。
- 应当包含有歧义、经翻译或领域特有的术语；仅有一个明显含义的词可以省略。
- 被禁用的同义词由项目命名表记录，术语表不复制该列；混用术语将使读者认为概念不同。
- 应当在重命名概念的同一变更中更新术语表；过时的术语表将传播旧名称。
- 条目应当保持一句话，并按字母顺序排列；需要段落的术语表属于解释页。

| 好 | 坏 | 为什么 |
|---|---|---|
| “Charge：一次收款尝试。” | 同一术语在三个页面上分别定义。 | 单一权威定义可以终止比较。 |
| 按字母顺序排列的单行条目。 | 读起来如同一章正文的术语表。 | 供查阅之用，而非通读。 |
| UI 标签与术语表术语一致。 | UI 使用“transaction”，文档使用“charge”。 | 分歧暗示存在两个概念。 |
| 被禁用的同义词只记录于命名表。 | 术语表与命名表各记一份禁用同义词。 | 两份副本将分叉。 |

## 19. 归属、维护与新鲜度

- 应当在 front matter 或文档索引中为每个页面指定负责人，写成可以解析的团队句柄或角色（例如 `@docs-team`），
  不得写成人名；无负责人或负责人不可解析的页面，将无人维护。
- 应当在页面元数据或文档索引中记录每种文档类型的审查触发条件，写成一等条件（“每次发布”“每次 API 变更”“每
  季度”），不得使用形容词；变更日志、发布说明、运行手册与事故复盘的节奏，由 `release-operations-conventions`
  设定。
- 应当跟踪最后审查日期，并标记超过审查间隔的页面；新鲜度为维护信号，而非正确性承诺。
- 应当在改变行为的变更中更新页面，并将文档步骤置于与代码相同的 issue。
- 功能被移除的页面，应当优先归档并留下重定向或墓碑；仅在无法归档且完成引用核查后删除；描述不存在产品的页面，
  较无页面更为不利。
- 应当先审查阅读量最大的页面；依据搜索分析构建的仪表盘，优于通读整棵文档树。
- 已知缺口应当记录为 issue，载明负责人与目标发布，不得留下无声的空洞。
- 文档审查应当在团队成员之间轮换，避免归属演变为某一人的私人记忆。

## 20. 模板与脚手架

- 仓库中应当为每种文档类型保留一个模板，每个新页面均自该模板开始；模板消除了本应统一的决定。
- 模板应当包含必需章节，不得包含可选章节；作者应当添加页面所需内容，必需章节不得删除。
- 每个模板应当能在十分钟内填写完毕；需要编辑器的模板，本身就是一份文档。
- 模板应当版本化，并在现有页面下次实质性编辑时更新，不得实施大规模重写。
- 项目支持的，应当以脚本或文档生成器自模板生成文件。
- 一轮审查两次发现同一缺失章节的，应当修订模板。
- 模板应当与维度规则同步；规则变化时，骨架应当于同一次审查中变更。

| 好 | 坏 | 为什么 |
|---|---|---|
| 团队填写的五节 ADR 模板。 | “按合适的格式编写。” | 自由将阻碍比较。 |
| 模板中标记必需章节。 | 二十个可选标题。 | 可选标题将被跳过。 |
| 审查规则变化时更新模板。 | 多年无人阅读的模板。 | 将传授过时的结构。 |
| 由脚本生成模板。 | 每位作者重新输入标题。 | 重新输入的结构将漂移。 |

## 23. 公开与内部边界

- 每个页面应当分类为公开（客户、集成者）或内部（员工、运维），并在仓库或站点配置中记录受众。
- 公开页面应当面向外部读者编写：不得出现内部主机名、工单 ID、员工姓名或未发布计划。
- 内部文档应当置于有权限控制的空间；依赖未列出的 URL，不构成访问控制。
- 仅在审查机密、准确性与支持承诺之后，方可将内部内容提升为公开。
- 边界变更应当指定审查者；改变受众的页面，应当取得负责人批准。
- 边界两侧应当保持共享词汇，使公开页面与其内部对应页使用相同术语。
- 仓库或站点变更可见性时，应当重新检查边界；镜像可能意外发布内部页面。

| 好 | 坏 | 为什么 |
|---|---|---|
| 公开页面链接至公开渠道。 | 公开页面写出值班轮值。 | 内部路由与姓名将泄露。 |
| 内部运行手册置于有权限控制的仓库。 | 以未列出的 URL 隐藏运行手册。 | 未列出的 URL 最终将被发现。 |
| 两个空间共享同一术语表。 | 两侧使用不同术语。 | 读者无法将二者对应。 |
| 受众记录于站点配置中。 | 仅作者知晓。 | 新作者将发布至错误的一侧。 |
