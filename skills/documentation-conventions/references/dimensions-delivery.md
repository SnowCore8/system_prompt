# 文档维度：发布与维护

本文件规定 `SKILL.md` 维度索引中发布与维护部分的细则；节号与索引一致，读者与使用及项目与内容部分见同目录其余
`dimensions-*.md` 文件。

## 8. 变更日志与发布说明

- 应当按版本与日期分组；版本内依影响（新增、变更、修复、移除、安全）分组，并将升级动作置于靠前位置。
- 应当面向用户编写：说明行为发生何种变化、读者必须实施何种动作，不得说明哪些文件发生移动。
- 每个条目应当链接至解释该条目的 issue 或 PR；条目为摘要，并非唯一记录。
- 应当明确标出弃用与破坏性变更及其移除版本；不得将其置于“变更”之下。
- 每个用户可见变化应当占一行；若每个条目写成一段，就会掩盖读者所查找的清单。
- 未归属版本的条目应当保留于“未发布”一节；条目移入已发布一节的时点，依 `release-operations-conventions` 设定
  的触发条件确定。
- 不得重写已发布章节以隐瞒回归；应当添加一条引用原始条目的更正条目。
- 发布流程自变更日志生成发布说明的，应当验证二者一致。

| 好 | 坏 | 为什么 |
|---|---|---|
| “`GET /v1/orders` 在 3.0 中移除；改用 `/v2/orders`。” | “订单 API 清理完毕。” | 读者需要动作与发布版本。 |
| 按版本分组并载明日期的条目。 | 自发布以来未载日期的一份清单。 | 版本与日期决定相关性。 |
| 修复条目链接至 issue 与发布。 | “各种缺陷修复。” | 含糊条目无法据以行动。 |
| 破坏性变更列于最前。 | 破坏性变更置于“变更”之下。 | 读者将错过必需的升级。 |

## 9. 运行手册、运维与事故复盘

- 每本运行手册对应一项告警或操作，并以触发条件、影响与首个动作开头；读者正处于压力之下，仅有数分钟，而非
  一个下午。
- 应当给出精确命令，附环境、权限与预期输出；不得仅写“检查日志”而不给出检查日志的命令。
- 应当包含验证操作已生效的步骤，以及恢复先前状态的回滚。
- 应当写明升级路径，以及回滚较故障更为不利时的决策权归属。
- 仪表盘、告警与流水线应当以稳定名称或 ID 链接；仅作者可以找到的链接，于凌晨三点无任何用处。
- 运行手册步骤应当与其最近处理的事故复盘一致；审查触发条件与节奏由 `release-operations-conventions` 设定。
- 应当自运行手册链接至事故复盘：运行手册承载步骤，事故复盘承载叙述；事故复盘的编写时点，由
  `release-operations-conventions` 设定。

| 好 | 坏 | 为什么 |
|---|---|---|
| 带命名空间与数量的精确扩缩容命令。 | “扩缩容 worker。” | 值班人员不应当自行设计命令。 |
| 回滚步骤包含对回滚自身的验证。 | “需要时回滚。” | 撤销需要已知路径。 |
| 写明升级渠道与负责人。 | “向团队升级。” | 可达目标与权限。 |
| 每条命令后的预期输出。 | “检查日志。” | 读者必须知道成功时的输出。 |

## 10. 安全、法律与支持文档

- 安全策略内容应当置于 `SECURITY.md`，以可扫读的章节呈现，并链接至其负责人；必需内容与响应承诺，由
  `security-compliance-conventions` 规定。
- 不得发布内部地址、机密、员工数据或客户数据；应当使用示例值，例如 `example@test.invalid`。
- 法律页面（许可证、条款、隐私）由法务所有，不归工程；应当链接至上述页面，不得转述为第二份文档。
- 支持页面应当说明支持范围、响应目标与范围外内容；含糊的承诺将转化为义务。
- 安全策略、支持路径与许可证应当可自 README 与文档首页到达。
- 每个承担风险的页面应当记录负责人与最后审查日期；安全与法律文本将无声失效。
- 每次演练后，应当对照实际事故流程审查安全页面；未经任何人完整走查的策略，仅为假设。

## 12. 迁移与弃用指南

- 应当说明旧行为与新行为、时间线、移除版本，以及旧路径的支持窗口。
- 应当提供一张映射表，载明被移除名称、字段或端点及其替代方案。
- 应当给出分步迁移，在触碰数据前实施备份，并为每个不可逆步骤提供回滚。
- 应当包含一个验证步骤，以读者运行的命令或校验证明迁移成功。
- 发布指南前，应当确认迁移负责人已在生产形态的数据上实施测试。
- 弃用通知应当写明替代方案与移除发布；公告位置与时机，由 `release-operations-conventions` 裁定。
- 运行时或生成客户端的告警写法，由 `comment-conventions` 的弃用标记规则裁定；仅载于文档的弃用，将被发现过晚。
- 不得在宣布的发布之前移除旧路径；静默移除违反已发布的契约。

| 好 | 坏 | 为什么 |
|---|---|---|
| 自 `amount` 到 `amount_cents` 的映射表。 | “更新集成。” | 映射方为工作内容。 |
| 在 3.0 移除，附日期与指南链接。 | “很快会移除。” | 无法针对“很快”作出计划。 |
| 重写数据前先备份，并准备回滚。 | 单向迁移脚本。 | 迁移失败将丢失数据。 |
| 迁移后运行验证命令。 | “验证它能工作。” | 读者需要通过条件。 |

## 18. 版本管理与适用性

- 每个页面应当写明适用版本（front matter 的 version 字段或首段“适用于 2.x”），或者显式标注“适用于所有版本”；
  二者均缺的，按缺陷处理，因为读者会将其误认为当前版本。
- 行为不同的，应当按主版本发布文档，使默认路由保持当前版本，并自版本选择器链接旧版本。
- 变更与移除的选项应当以其发生变更时的版本标记，并保留于参考中直至移除。
- 同一页面描述同一产物的，应当使用该产物的版本；文档跟随产品主版本，API 版本可以独立，但页面应当写明产品
  版本与 API 版本的映射。
- 不受支持的版本应当从主导航中移除，但应当为仍在使用该版本的用户保留可访问路径。
- 任何时间敏感内容均应当标注日期：支持窗口、证书到期、迁移截止日期与停止支持日期。
- 支持窗口结束后，应当自搜索索引中移除已停止支持的页面，同时保持 URL 可访问，使旧链接仍可解析。

| 好 | 坏 | 为什么 |
|---|---|---|
| “适用于 2.x；1.9 见 1.x 文档。” | 页面未载版本。 | 读者无法判断适用性。 |
| 在参考中标记“3.0 移除”。 | 静默删除被移除的选项。 | 2.x 读者仍需要该条目。 |
| 文档跟随产品主版本，并写明“产品 v2 使用 API /v1”的映射。 | 同一页面混用产品版本与 API 版本，却不说明映射。 | 读者无法将页面版本对应至实际 API。 |
| 自选择器链接旧版本。 | 仅发布当前版本。 | 使用旧版本的用户将失去文档。 |

## 22. 文档站与工具

- 应当选择一种生成器并锁定其版本；MkDocs、Docusaurus、Sphinx、VitePress 与纯 Markdown 均可，前提为项目能够
  可靠地构建并发布文档站。
- 内容应当保留为可移植的 Markdown，并使用相对链接，使站点迁移时无需重写页面。
- MkDocs 适用于中小型文档集，导航文件简单，作者以 Markdown 为主。
- Docusaurus 适用于需要在单一构建中包含 React 站点、博客与翻译的版本化产品文档。
- Sphinx 适用于需要生成参考页与交叉引用的 API 与 Python 项目文档。
- VitePress 适用于带 Vue 组件的快速 Markdown 站点；纯 Markdown 适用于未设站点的项目。
- 应当在 CI 中构建并自产物发布；不得自开发者机器发布。
- 配置、主题与导航应当置于内容旁，纳入版本控制。

| 好 | 坏 | 为什么 |
|---|---|---|
| 锁定生成器版本并设 CI 构建。 | 仅在某台笔记本上可用的构建。 | 发布不得依赖单台机器。 |
| 采用相对链接的纯 Markdown 内容。 | 满是短代码的页面。 | 可移植内容可在迁移后存续。 |
| 导航保存于单一经过审查的文件中。 | 仅在 Web 管理后台编辑导航。 | 文件可以回滚。 |
| 在 CI 中构建并发布制品。 | 自开发者机器发布。 | 可复现构建需要单一通道。 |

## 24. 生成文档

- 不得编辑生成产物；应当修改生成器配置，或者由注释负责人更新源文件，然后重新生成。
- 应当保留可见的生成标记与命令，使下一位读者知晓该文件并非手工编辑。
- 仅在审查或托管流程要求时提交生成页面；否则应当于发布时构建。
- 应当记录本地重新生成的方法，使贡献者可以在审查前重建。
- 应当锁定生成器版本，并阅读生成差异中的噪声；重新格式化的改动将掩盖审查中的真实变化。
- 应当审查生成器无法提供的人工部分：概览、认证、错误、示例与版本说明。
- 错误的生成页面应当在源头修复；修补输出的内容将在下次构建时被还原。
- 生成产物应当排除于会与生成器冲突的格式化与 lint 规则之外。

## 25. 文档审查

- 应当对照读者的任务实施审查：指定读者能否依该页面完成任务。
- 应当先检查结构（类型、必需章节、范围），再检查事实（命令、版本、链接），最后检查语言。
- 审查前应当运行构建、链接校验与示例；审查者不应当为第一个发现坏链的人。
- 审查中应当要求证据：命令输出、渲染后的页面、链接校验结果。
- diff 应当局限于被审查的页面；重写不相关章节的文档变更，将消耗审查时间并掩盖真实变化。
- 应当检查代码 diff 中的每个行为变化均有对应的文档变更；缺少文档 diff 的，构成一项发现。
- 事故或破坏性发布之后，应当重新审查页面，并记录审查日期。
- 应当拒绝将未发布计划文档化为当前行为的页面；该情形属于事实错误，而非风格问题。

## 26. 归档与删除

- 功能或决策不存在的，应当优先归档并留下墓碑页；仅在无法归档且完成入站引用核查后，方可删除；批量删除依
  IR-1 与 AU-1 取得明确同意。历史具有长期审查或考古价值的，应当归档。
- 归档时应当留下墓碑页，写明日期、原因与替代位置，并使其离开主导航。
- 被移除的 URL 应当重定向至替代页面或索引；旧文档 URL 上的 404 将失去读者与搜索排名。
- 删除前应当于仓库内与分析数据中检索入站链接，确认每条引用均有替代目标。
- 归档文档应当保持只读，并标记为不再维护；仍在接收编辑的归档页面，不构成归档。
- 仅在验证权威页面且无法归档之后，方可删除重复副本；于别处保留备份副本，将重新制造问题。
- 外部读者可能收藏过页面的，应当在变更日志中记录删除。

| 好 | 坏 | 为什么 |
|---|---|---|
| 自旧 URL 重定向。 | 无替代页面的 404。 | 读者仍能获得答案。 |
| “已归档：由计费指南取代。” | 页面被悄然留在导航中。 | 读者无法判断该页面已过时。 |
| 删除前更新入站链接。 | 先删除，稍后修复链接。 | “稍后”始终不会到来；链接持续为死链。 |
| 墓碑页写明日期与替代位置。 | 未作解释的归档文件夹。 | 读者将重新打开已消失的页面。 |
