# 安全与合规：依赖供应链与 SBOM

供应链风险来自依赖本身的缺陷、被攻陷的发布渠道与构建过程的篡改。控制分三段：
引入前审查、构建时锁定与验证、分发时以 SBOM 提供可核查清单。

## 1. 引入前审查

- 新依赖审查五项：维护活跃度、已知漏洞、许可证、传递依赖规模与安装脚本；安装脚本默认禁止，确需时先阅读再批准。
- 依赖固定至锁文件，自经验证的包仓库获取；未使用的依赖删除，不得只注释禁用。
- 包名与上游仓库都要核对，防止仿冒包；直接依赖与传递依赖同等对待。

## 2. 构建与制品溯源

- 构建在受控流水线中进行，输入为锁文件与经审查的源码；制品签名或来源证明在生态支持时启用。
- 补丁与依赖更新经与人工变更相同的门禁；自动更新 PR 的测试通过后才合并。
- 第三方引入代码只作清点与扫描，不得手工编辑；问题报告上游，或在独立 fork 维护有记录的补丁。

## 3. SBOM 与漏洞处置

- 每次发布依构建制品实际使用的依赖图生成 SBOM，覆盖直接与传递组件，附至发布并保留至支持周期之后。
- 漏洞发现依可利用性与暴露面评定严重程度，按期限修复；不可利用的传递依赖记录 VEX 评估与豁免到期日。
- 扫描门禁的位置与阈值归 `testing-quality`；本 skill 管辖严重程度、修复期限与例外批准。
