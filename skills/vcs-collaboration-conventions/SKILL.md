# 版本控制与协作规范

多数团队丢失代码，原因并非算法质量，而是协作失效：PR 持续膨胀，致使任何审查者均无法一次审阅完毕；历史中留下
无人能够解释的合并；某一目录在作者离职后失去归属；受保护分支被绕过一次之后即成为常态。上述失效在规则阶段均
易于预防，待某一发布依赖其后方行修复，则代价高昂。本 skill 规定自工作副本至主分支乃至更远环节的决策流程与完
整规则，涵盖分支模型与合并方式、PR 与 MR 规范、审查深度、分支保护与代码所有权。本 skill 假定使用 Git 与基
于审查的托管平台，并对项目语言与平台界面保持中立。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充；同一分支类别内不得混用模型。

1. 强制性的平台、法律、宿主与用户全局约束。托管平台或组织的强制策略，包括必需校验、审查要求与签名提交规
   则，以及监管机构的变更控制规则，均非可选事项。
2. 本 skill 的规则。分支模型、合并方式、审查深度与所有权，以本文件与 `references/` 为准。
3. 既有项目约定与事实。代理提出规则之前，应当先阅读分支模型、合并设置、CODEOWNERS 文件与贡献者指南；上
   述内容属于事实输入，依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- `naming-conventions` skill 管辖分支名、提交消息的类型与范围以及标签名；本 skill 管辖使用上述名称的工作流、
  合并策略与审查流程。
- 本 skill 管辖 PR 与 issue 模板的要求，以及模板必须记录的决定；模板属于文档，其行文遵循仓库的文档风格。
- `release-operations-conventions` skill 管辖发布版本号、发布时机与 CI/CD；本 skill 管辖变更到达主分支的方式
  及其合并路径。
- `security-compliance-conventions` skill 管辖访问控制策略的细节；本 skill 管辖分支保护与代码所有权机制，包
  括必需校验与绕过记录。签名提交要求来自第 1 层的托管平台或组织策略。
- `testing-and-quality-conventions` skill 管辖门禁本身；本 skill 管辖受保护分支上必需的门禁，以及可以合并的
  时点。
- 生成路径、第三方引入路径与机器产出路径免于逐行审查，但不豁免合并规则。代理应当审查生成器输入、重新生成
  命令与生成标记；手工修改生成产物，在任何情形下均不视为经过审查的变更。
- 历史属于公开记录：仅在策略允许时方可重写。在取得 AU-1 明确同意后，代理可以 amend 未发布的提交，且仅可
  以对个人主题分支带租约强制推送；即使内容完全相同，重写受保护分支亦应当按事故处理。远程推送、强制推送与
  删除分支，均须先取得 AU-1 明确同意；本条不另设例外。
- 仅存在于审查者记忆中的规则，不构成规则。分支模型、合并方式、审查深度与所有权，应当记录于贡献者指南或所
  链接的策略文件中，并在变更做法的同一次变更中更新。
- 两项规则冲突的，代理应当说明冲突与所选规则，将决定记录于分支模型旁，并使下一次变更遵循该决定。
- **单人仓库、trunk-based 与无 PR。** 直接提交主干属于合法模型，此时审查由自查与必需 CI 替代；CODEOWNERS
  仅有一条通配条目的，仍可以合并，但必须在治理文件中记录该单点。

## 流程

1. 确认当前状态。代理应当阅读平台的分支设置、合并方式、CODEOWNERS 文件、CI 配置、贡献者指南，以及最近二
   十次合并提交。任何规则写出之前，团队规模与发布节奏已经决定模型。
2. 自下表中选择或确认一个分支模型并予以记录：分支类别、生命周期上限、每个类别的合并方式、发布路径、热修复
   路径与标签策略。
3. 开启分支之前，代理应当先估算变更体量。每个分支仅保留一个逻辑变更；超出体量预算的，拆成堆叠分支或以功能
   开关隐藏，并按合入顺序链接各部分。
4. 准备 PR 或 MR，写明标题、描述、关联 issue、风险级别、验证证据与自审结果。仅在必需校验与模板均已完成
   时，方可标记为就绪。
5. 按所有权与风险分派审查：请求归属团队与风险级别所要求的领域审查者，并在请求中写明审查深度。
6. 依规定路径合入：仓库配置了合并队列或自动合并的，应当使用上述机制；否则，在合并结果上全部必需校验通过
   后，依该分支类别的方式合并，然后删除主题分支。
7. 定期审查：确认已合入，核实部署或发布路径，审查绕过记录，并在下一次变更之前修复 CODEOWNERS 覆盖、过期
   批准与保护漂移。

## 核心规则

- **每个分支类别仅使用一个模型。** 分支模型应当在贡献者指南中写明，并在平台上强制执行；仓库未设书面边界而
  混用主干合并、发布分支合并与热修复 cherry-pick 的，其产出的历史无审查者能够还原。
- **分支生命周期应当短，体量应当小。** 分支应当在三个工作日内集成，可审查的 diff 保持在约 400 行改动以
  内；存续更久的分支应当每日变基；无法拆分至开关之后的变更属于设计信号，不构成例外。
- **主分支始终可发布。** main 上的每个提交均应当能够构建、通过必需门禁并可部署；main 变为失败状态将阻塞全
  部合并，其优先级高于新功能工作。
- **每个分支类别仅使用一种合并方式。** 功能分支压缩合并进主干，发布晋级使用合并提交，仅对未共享的分支变
  基；同一类别中混用方式将使 blame、bisect 与 revert 不可靠。
- **公开历史仅可追加。** 代理不得重写他人已在其上开展工作的提交；已发布的错误应当以 revert 或后续提交修
  复，带租约的强制推送仅用于个人主题分支。
- **审查深度取决于风险，而非审查者是否有空。** 代理应当按影响范围将每项变更分为轻量、标准或高风险；认证、
  支付、权限、数据迁移与公共接口适用高风险路径，并配置第二名审查者。
- **每项变更均应当经过审查与必需校验方可合入。** 受保护分支要求存在批准审查，且合并结果上的必需校验全部通
  过；实质性推送之前取得的批准已过期，必须重新取得。单人仓库或无第二人的，必需批准设为 0，并以自审记录与
  必需 CI 替代批准审查；自审记录应当写明检查项与结论，并作为已知缺口上报。
- **默认保护，绕过即事故。** 受保护分支应当要求审查、校验与合并方式所需的线性历史，并禁止强制推送；每次管
  理性绕过均应当记录操作者、原因与合并后审查。
- **CODEOWNERS 应当为每条可合并路径指定真实所有者。** 没有所有者的路径属于带期限的缺陷；回退所有者应当为
  平台或仓库维护者团队，不得为下一个编辑该路径的人。
- **门禁应当在合并结果上运行，而非仅在作者的副本上运行。** 合并队列或预合并任务针对基线测试变更；本地通过
  不足以替代必需校验。
- **机器人执行门禁，人实施判断。** 构建、测试、lint、类型校验、机密扫描与文档构建由 CI 强制执行；人工审查
  负责正确性、设计取舍、安全语义、测试充分性与文档影响。可判定的项必须自动化，判断性的项必须由人实施。
- **每条审查评论均应当带有严重级别与明确要求。** 每条评论应当标记为阻塞、非阻塞、Nit 或需要回答的疑问，并
  要求作者以回复或关联修复解决每个阻塞线程；沉默不构成同意。
- **草稿视为未就绪。** 为尽早获得反馈而开启草稿的，仅在描述、证据与自审均已完成后方可标记就绪；草稿不进入
  合并审查，亦不被合并。
- **删除已合并分支，冻结发布标签。** 合并后应当删除主题分支，使分支列表反映未完成工作；代理不得移动、删除
  或重建已发布的发布标签，因为已发布的制品指向该标签。
- **所有权变更应当与代码同等接受审查。** 授予或移除所有权的 CODEOWNERS 修改需要维护者审查，并在独立请求
  中合入；依仓库治理规则，此类修改需要两名批准者。单人仓库或无第二人的，依“每项变更均应当经过审查与必需校
  验方可合入”的例外，改为自审记录与必需 CI，并由维护者自批记录；存在第二人的，所有者不得批准扩大自身权限
  的变更。

## 分支模型矩阵

代理应当选择满足发布流程的最轻模型；模型决定合并方式与热修复路径。

| 模型 | 团队与仓库规模 | 合并方式 | 发布路径 | 适用场景 |
|---|---|---|---|---|
| 主干开发，无发布分支 | 2 至 15 名工程师，一个可部署服务 | 压缩合并到主干；变基主题分支 | 主干持续部署；发布即主干上的一个标签 | 持续交付、功能开关、强 CI |
| 主干开发，带发布分支 | 15 至 100 名工程师，多个部署目标 | 压缩合并到主干；到发布分支用合并提交；热修复 cherry-pick 到两边 | 冻结时切出，给发布提交打标签，在分支上热修复并向前移植 | 版本化发布，或客户固定使用某一版本 |
| GitHub flow | 2 至 30 名工程师，一个生产环境 | 压缩合并或合并提交，全仓统一一种 | 合并到 main，从 main 部署 | 刚建立审查实践的小团队；无需运行发布列车 |
| 发布列车分支 | 30 至 200 名工程师，按计划发布 | 晋级用合并提交；小修复用压缩合并 | 候选发布分支、资格验证，然后打标签；修复用 cherry-pick | 受监管的发布节奏、长时间 QA 与多个受支持版本 |
| GitFlow | 10 至 100 名工程师，交付或安装型软件 | 带 `--no-ff` 的合并提交；热修复分支 | `develop` 集成，`release/*` 稳定化，`main` 保存带标签的发布，`hotfix/*` 从标签切出 | 有支持窗口的桌面或本地部署软件 |
| Fork-and-pull | 公开仓库，贡献者数量不限 | 维护者快进或压缩合并已审查分支 | main 承载发布；标签与说明予以公告 | 开源项目，或无写权限的不可信贡献者 |
| 按版本维护分支 | 5 至 50 名工程师，支持多个发布 | 压缩合并到维护分支；晋级用合并提交 | 每个受支持版本一个分支；修复用 cherry-pick 并向前移植到主干 | 小团队运营的长期支持窗口 |

两种模型均适用的，应当选择较轻者，并在一个发布周期后重新评估；较轻指需要维护的分支类别更少、每类仅一种合并
方式、发布与热修复路径更短，按分支类别数量、合并方式与发布路径逐项比较；较重的模型将增加需要维护的分支与
需要记住的热修复路径。选择、日期与下次审查的触发条件，应当记录于贡献者指南中。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 长期功能分支 | 与主干漂移，冲突增长，集成风险延迟至最后方暴露 | 拆成堆叠请求或置于开关之后；每日集成 |
| 同一分支类别混用合并方式 | blame、bisect 与 revert 不再与审查历史对应 | 每类选择一种方式，并在设置中强制执行 |
| 对共享分支强制推送 | 抹除同事的提交与审查评论锚点 | 仅在个人分支上带租约强制推送；已发布的错误使用 revert |
| 不阅读 diff 即批准 | 将合并门禁变为仪式，掩盖缺陷 | 要求与风险相称的证据，并审查自审清单 |
| 将重命名、格式化与行为变更混于一个请求 | 无法作为同一单位审查，亦无法单独回退 | 隔离机械性改动，行为变更单独合入 |
| 必需校验仅作建议 | 校验失败仍可合并，信号仅具装饰作用 | 将校验标为必需，并采用失败即拒绝 |
| 将可判定的校验留予人工重复实施 | 审查者为 lint、格式与拼写所淹没，遗漏正确性问题 | 可判定的项全部自动化，人工仅实施判断 |
| 提交夹带调试输出或本地配置 | 历史受污染，本地状态进入共享历史 | 推送前以 diff 与 status 自检，敏感内容立即删除 |
| 以“就这一次”为由直接推送 main | 绕过审查与门禁，其后成为先例 | 默认拒绝；仅授予有记录、有时限且经事后审查的例外 |
| 校验或描述未完成即将草稿标为就绪 | 审查者将时间用于无法合并的请求 | 就绪意味着校验全部通过、描述完整且自审完成 |
| CODEOWNERS 仅有通配回退 | 仅通知回退团队，路径所有者始终未被通知，孤儿路径长期隐藏 | 为每条路径指定真实团队；审查覆盖情况与孤儿路径 |
| 审查评论无严重级别或要求 | 作者无法区分阻塞项与可选项 | 添加 `must:`、`should:`、`nit:` 或 `q:` 前缀，并写明应当采取的行动 |
| 绕过合并队列实施合并 | 最终合入的非经测试的合并组合 | 由队列决定合并顺序；修复后重新入队 |
| 移动发布标签以纳入新增修复 | 已发布制品与标签不再匹配 | 自修复提交切出新的补丁版本 |
| 实质性推送后批准仍被视为有效 | 审查者批准的代码已不在请求中 | 推送时使过期批准失效，并重新审查增量 |
| 所有权文件由新所有者自行编辑 | 未经维护者审查即自我授权 | 在独立的、经维护者审查的请求中审查所有权变更 |
| 重组后无人负责的服务 | 无人收到审查请求，缺陷持续等待 | 重组当日指定回退团队，并每季度审查 |
| 将 CI 凭据暴露给来自 fork 的 PR | 外部贡献者能够读取生产凭据 | 不得使凭据进入不可信 fork 构建；不得在流水线中打印凭据 |

## 审查清单

- [ ] 分支模型、每个类别的合并方式与热修复路径已写入文档，并与平台设置一致。
- [ ] 变更为体量预算内的一个逻辑单元，或其堆叠顺序已有文档。
- [ ] 标题说明结果，描述说明问题、做法与风险。
- [ ] 请求链接了其应当关闭的 issue，并列出推迟的后续工作。
- [ ] 验证证据已粘贴，且与所描述行为一致。
- [ ] 校验通过、自审完成之前，请求保持草稿状态。
- [ ] 必需校验在合并结果上通过，而非仅在作者最后一次推送的提交上通过。
- [ ] 审查者的选择与归属路径及风险级别匹配，并包含归属团队的批准。
- [ ] 每条阻塞评论均通过回复或关联修复得到解决。
- [ ] 批准仍然有效；批准后的实质性推送已触发重新审查。
- [ ] 合并方式与分支类别匹配，合入后的历史保持清晰可读。
- [ ] 未对受保护分支强制推送；任何强制推送均为个人分支上的带租约推送。
- [ ] 保护设置依策略要求审查、校验与线性历史。
- [ ] 任何绕过或管理性合并均具有操作者、原因与已安排的合并后审查。
- [ ] CODEOWNERS 覆盖每条变更路径，且回退所有者能够解析。
- [ ] 生成文件与第三方引入文件已重新生成，标记与生成器输入均已审查。
- [ ] 热修复已依热修复路径实施，并已向前移植至主线。
- [ ] 已合并分支已删除，已发布的发布标签未变更。
- [ ] diff、描述、评论或 CI 日志中未出现机密、令牌或个人信息。
- [ ] 合并后验证（部署、健康检查、发布说明）已计划或已完成。

## 示例

<example>
主干合并：
一个存续三天的分支改动 180 行，必需校验在合并结果上全部通过，归属团队已批准，描述链接了 issue 并粘贴了测试
输出。代理应当压缩合并该分支，删除该分支，并确认自 main 部署成功。同一仓库中，一个 900 行的分支在审查开始
前已拆成堆叠，而非等待审查受阻后再拆；堆叠中的每个请求均写明其父请求与所依赖的分支。
</example>

<example>
高风险审查：
一项令牌刷新变更被归为高风险：两名审查者，一名来自负责认证的团队，一名安全审查者，另附一项证明过期刷新令牌
将被拒绝的负向测试。作者将威胁场景与回滚开关粘贴至描述中，在请求离开草稿前将一条未标记评论改写为 `must:`；
其后一次实质性推送使两项批准均失效。
</example>

<example>
历史修复：
未推送提交的消息有误的，应当 amend 该提交。已经推送至作者主题分支的提交，应当以 revert 或后续提交处理；仅在
策略允许重写该分支时，方使用带租约的强制推送。main 不接受强制推送：应当先 revert，再使修正后的变更经审查合
入。revert 保留原始消息，修复提交写明其恢复的提交，使阅读历史者能够看到前后两部分。
</example>

<example>
CODEOWNERS 审查：
审查发现 `services/billing/**` 归属于一个已不存在的团队，`vendor/**` 无人负责。为 billing 指定回退维护者团队
并设定期限，使平台团队成为第三方引入代码的所有者，并增加一项 CI 校验，确认每条变更路径均能够解析至所有者。审
查结果写明修复项、临时所有者与下次审查日期；生成路径仍归属生成器的所有者。
</example>

<example>
热修复路径：
某一受支持版本存在缺陷，遂自标签 `v2.3.0` 切出 `hotfix/2.3.1`，使最小修复经发布所有者批准后经审查合入，打
上 `v2.3.1` 标签，并将修复 cherry-pick 至 main。热修复分支不再复用，旧标签不移动。发布说明写明所修复的缺
陷，新补丁标签与其他所有发布标签同等受保护。
</example>
