# 协作操作手册

这些操作手册与 `SKILL.md` 和 `dimensions.md` 配合使用。每个操作手册将一个反复出现的协作决策自问题引至结
果；代理应当依序执行步骤，并将答案记录于下一个人会阅读之处。本地已有策略作为输入，依 `SKILL.md` 的规则审查
与处理；项目约定仅在 skill 未规定时补充，不得覆盖本 skill。

正文“审查清单”为设计期权威；本文件仅放置合并与发布冻结时点的工作表，以及正文未展开的条件。

## 分支模型选择工作表

针对仓库依次回答下列问题。模型按由轻至重的固定顺序排列：主干开发（无发布分支）、主干开发（带发布分支）、
GitHub flow、发布列车分支、按版本维护分支、GitFlow、Fork-and-pull；应当按该顺序选择第一个同时满足全部答案
的模型，并记录顺序比较中每一步的取舍。

1. 集成分支上的每个提交是否均能够不经单独稳定化步骤直接部署至生产？属肯定情形的，应当优先采用主干开发。
2. 发布是否需要代码冻结、资格验证或受支持版本窗口？属肯定情形的，应当在主干开发之上增加发布分支，或选择发
   布列车分支。
3. 多个已交付版本是否需要支持数月，且每个版本均需修复？属肯定情形的，应当选择 GitFlow 或按版本维护分支，并
   为向前移植工作编制预算。
4. 贡献者是否对仓库没有写权限？属肯定情形的，应当采用 fork-and-pull，保护目标分支，并要求维护者合并。
5. 问题 1 为否时，团队是否少于十名工程师且只有一个可部署服务？属肯定情形的，GitHub flow 即已足够；不得为
   仪式感采用 GitFlow。
6. 监管机构或客户是否要求独立于提交历史的发布记录？属肯定情形的，应当选择发布列车分支或按版本维护分支，使
   发布标签不可变，并将记录附于标签；不得以环境分支模拟该审查。

结果应当记录为分支类别、每个类别的合并方式、生命周期上限、热修复路径与下次审查日期。答案组合决定模型：

| 答案组合 | 模型 |
|---|---|
| 每个提交都可部署、一个环境、小团队 | 主干开发，无发布分支 |
| 每个提交都可部署、版本化或固定版本发布 | 主干开发，带发布分支 |
| 一个生产环境、基于审查的流程 | GitHub flow |
| 代码冻结、资格验证、多个受支持版本 | 发布列车分支 |
| 多个已交付版本需支持数月，且每个版本均需修复 | 按版本维护分支 |
| 监管或客户要求独立于提交历史的发布记录 | 发布列车分支；受支持版本不止一个且周期较长时用按版本维护分支 |
| 有支持窗口的交付或安装型软件 | GitFlow |
| 没有写权限的不可信贡献者 | Fork-and-pull |
| 以上均不匹配（默认） | GitHub flow |

默认行仅在答案组合未被上述行覆盖时使用；选择后记录理由、下次审查日期，并在一个发布周期后重新评估。

## PR 描述与体量检查清单

审查者不打开 diff 即能够作出决定时，描述方为完整；审查者能够一次审阅完毕时，请求方为足够小。请求审查之前，应
当先检查上述两点。

必须包含的决定内容：

- 问题与影响：当前何处发生故障或缺少何种内容，谁将注意到。
- 做法：以两三句话说明变更；选择不明显的，补充被否决的备选方案。
- 验证：已运行的命令及其结果、新增的测试名称，以及 UI 变更的手工步骤或截图。
- 风险与回滚：有风险的 hunk、影响范围、开关或 revert 路径，以及迁移或回填计划。
- 关联 issue 与后续事项：本次关闭何种内容、推迟何种内容，以及依赖哪个堆叠请求。

体量阈值：

- 改动少于 200 行：常规审查；风险级别另有要求的除外，由一名审查者审查。
- 改动 200 至 400 行：说明其作为单一单位的理由；任何部分能够独立合入的，应当拆分。
- 改动 400 至 800 行：审查前应当拆分或堆叠；无法拆分的，补充一份设计说明与第二名审查者。
- 改动超过 800 行：应当作为一个请求予以拒绝，但其属于机械性变更（生成产物、锁文件、重命名），且机械部分已
  隔离并有可复现该部分的命令的除外。

请求审查之前：

- [ ] 标题说明结果并遵循提交格式。
- [ ] 描述回答了必须包含的内容要点。
- [ ] 仅在验收标准满足时关闭关联 issue。
- [ ] diff 中无调试输出、被注释掉的代码或无关改动。
- [ ] 作者已阅读 diff 的每个 hunk，包括生成内容。
- [ ] 必需校验全部通过，否则请求保持草稿。

请求审查之前的自审流程：

1. 逐 hunk 阅读 diff，标出描述未解释的每个 hunk。
2. 运行审查将要运行的校验，包括 linter 与文档构建。
3. 自 diff 中删除调试输出、被注释掉的代码与无关改动。
4. 对照最终 diff 重读描述，在标记就绪之前更正过期表述。

## 提交卫生检查清单

每个提交均应当在推送前自查；合并前应当压缩 fixup，使最终历史仅保留可审查单位。

- [ ] 一个提交仅实施一个逻辑变更，重命名、格式化、依赖升级与行为变更分开。
- [ ] 每个提交均能够独立构建并通过其所在领域的校验。
- [ ] 无调试输出、被注释掉的代码、临时日志或 WIP 标记。
- [ ] 无机密、令牌、个人数据或本地配置。
- [ ] 提交信息说明变更的原因与结果，而非仅说明修补顺序；格式语法由 `naming-conventions` 管辖。
- [ ] 合并前以 `git diff` 与 `git status` 核对，不残留未跟踪的临时产物。

## 审查级别表

| 变更级别 | 示例 | 审查者 | 所需测试 | 所需文档 |
|---|---|---|---|---|
| 轻量 | 注释、文档、格式化、仅测试的重构、补丁级依赖更新 | 1 | 现有测试套件；仅在行为变更时新增测试 | 用户可见表述变更时更新 |
| 标准 | 功能、缺陷修复、内部重构、配置默认值、次版本依赖更新 | 1 名所有者 | 一个证明该行为的新增或更新测试，加上受影响的测试套件 | 更新记录该行为的页面 |
| 高风险 | 认证、支付、权限、加密、数据迁移、公共 API、依赖主版本升级、CI 或发布工具 | 2 名，包含领域或安全负责人 | 单元、集成、负向和失败路径测试，以及 staging 验证 | 在同一请求中更新运行手册、迁移说明或 API 参考 |

规则：审查者存在分歧的，应当上调级别，不得下调；触及高风险路径的轻量变更成为高风险；级别应当记录于请求中；
缺少第二名审查者的高风险变更应当等待，不得以“之后再审查”的承诺合并。领域审查者可以加入不熟悉的区域，但所有
者批准仍为要求；仅高风险代码变更需要两名批准者（治理与所有权变更的批准要求由 `repository-governance-conventions` 裁定）。

## 审查评论严重级别分类

| 严重级别 | 前缀 | 含义 | 作者行动 | 合并影响 |
|---|---|---|---|---|
| 阻塞 | `must:` | 缺陷、缺少证据、安全或数据风险 | 修复并回复修复链接 | 阻塞，直到问题解决并重新批准 |
| 非阻塞 | `should:` | 值得现在做或值得解释的改进 | 修复，或回复不做的理由 | 不阻塞；线程保持打开直到得到回答 |
| Nit | `nit:` | 局部偏好或润色 | 采纳或忽略 | 从不阻塞；由作者决定 |
| 疑问 | `q:` | 需要回答、但不要求改动的问题 | 用证据回复 | 不阻塞 |

规则：

- 每条评论仅使用一个严重级别，并写出要求，而非仅作观察：“将校验移入 handler，使 CLI 路径亦能够覆盖”优于“感觉
  不对”。
- 未标记的评论按 `should:` 处理并回答；仅有 nit 的审查仍属审查，因此应当标记。
- 无新证据的，不得重开已解决的线程；应当开启新线程并引用已解决者。
- 有争议的阻塞评论应当交由决策负责人裁决，不得交由合并决定。
- 审查者无法继续辩护的评论应当撤回；撤回的评论代价低于未解决的评论。

## 分支保护规则表

| 设置 | 受保护默认值 | 例外与取舍 |
|---|---|---|
| 必需批准 | 标准 1 名，高风险路径 2 名；推送时使过期批准失效 | 单人维护者仓库设为 0 并记录自审，作为已知缺口上报 |
| 必需状态校验 | 构建、测试、lint、类型校验、机密扫描，以及发布处的文档构建 | 跳过校验需要修改策略，不得以按请求的标签替代 |
| 线性历史 | 合并方式为压缩合并或变基时在主干启用 | 发布分支保留合并提交；按分支类别配置 |
| 强制推送与删除 | 在每个受保护分支和发布标签上禁用 | 向前 revert；重写受保护历史属于事故 |
| 管理员绕过 | 常规路径关闭；仅保留给紧急通道组 | 每次绕过均需要操作者、原因、请求链接和合并后审查 |
| 对话解决 | 阻塞线程必须解决 | 作者回复后 nit 可以保持未解决 |
| 合并队列 | 合并量导致反复集成失败时启用 | 低合并量仓库在最新提交上运行同样的校验 |
| 凭据 | 凭据不得暴露给不可信的 fork 构建；存储策略由安全流程管辖 | 可信分支仅获得其任务所需的凭据 |

例外路径：

- 使用例外之前，应当先开启该例外，写明被跳过的校验、原因与到期时间。
- 该例外应当记录于请求线程中，便于合并后审查查阅。
- 应当在一个工作日内审查该例外，并决定修改校验还是修改策略。
- 同一校验反复出现例外的，说明应当修改校验，而非放宽策略。

每月审查：

1. 导出受保护分支设置与必需校验，与已写入文档的策略对照。
2. 列出上次审查以来的管理性合并、绕过与强制推送，确认每一项均有记录与合并后审查。
3. 确认上次审查以来创建的标签指向发布提交，且无标签被移动或删除。
4. 在仓库的运维记录中报告数量与修复项；未经审查的绕过将变为常态。

## CODEOWNERS 设置与审查

设置：

1. 确认平台读取哪些位置（`CODEOWNERS`、`.github/` 或 `docs/`），以及本仓库使用其中哪一个；放错位置的文件将
   被静默忽略。
2. 应当自目录树出发，而非自团队架构图出发：列出服务、共享库、工具、生成代码、第三方引入代码与文档，然后为
   每一项指定一个团队。
3. 宽泛回退应当置于前面，具体模式置于后面，因为最后匹配的模式生效；写在最后的通配符将覆盖其上方的所有具体
   所有者。
4. 应当优先使用团队句柄，仅在风险路径上要求所有者审查，并将风险策略记录于模式旁或仓库的协作文档中。
5. 应当增加一项 CI 校验，确认每条变更路径均能够解析至所有者，且每个被引用的团队均存在。

一份最小文件，按让具体模式生效的顺序排列：

```text
# Broad fallback first; the last matching pattern wins.
* @example-org/maintainers
/services/billing/** @example-org/billing-team
/infra/** @example-org/platform-team
/vendor/** @example-org/platform-team
```

审查清单：

- [ ] 每个源码目录均解析至一个团队，而非仅解析至回退团队。
- [ ] 每个被引用的团队均存在，且至少有两名成员。
- [ ] 每个必需审查模式均至少匹配一条现存路径。
- [ ] 生成目录与第三方引入目录指向工具所有者，而非服务团队。
- [ ] 无路径仅由已离开组织的人拥有。
- [ ] 审查产生的所有权变更在经维护者审查的请求中合入。
- [ ] 审查结果、临时所有者与下次审查日期均已记录。

修复所有权漂移：

- 重组的团队应当在归档旧团队的同一变更中将其模式移至新句柄。
- 被移除的服务应当随服务移除其模式，所有者先确认归档。
- 成员少于两人的团队应当增加共同所有者，或将其路径指向父团队。
- 被加上具名所有者的生成目录应当改回工具所有者，并删除误加的条目。

## 历史修复决策表

| 情形 | 操作 | 批准 | 风险 |
|---|---|---|---|
| 最近一个未推送提交的消息错误或漏了文件 | 用 `git commit --amend` 修改 | 无；该提交从未离开本机 | 低；提交在本地，可从 reflog 恢复 |
| 最近一个未推送提交需要拆分 | `git reset --soft HEAD~1` 后重新提交 | 无；本地历史 | 低；工作区保留 |
| 已推送主题分支在审查开始前需要重写 | 变基，然后用 `--force-with-lease` 推送 | 分支是私人的、策略允许，且已取得 AU-1 第 3 级明确同意 | 中；评论锚点会移动，须提前通知 |
| 已推送主题分支已经审查并批准 | 追加后续提交；不得重写 | 对增量做标准审查 | 中；历史保持只追加 |
| 已发布的 main 提交有误 | `git revert` 或新的修复提交 | 常规审查；不得对 main 强制推送 | 中；修正过程向前可见 |
| 提交了凭据 | 停止操作、保留证据并报告；按 `security-compliance-conventions` 的泄露响应执行 | 用户明确同意；安全所有者协助；任何历史重写由 admin 执行 | 高；重写无法让已复制的机密重新保密 |
| 发布标签指向错误的提交 | 从修复提交打新补丁标签；保留旧标签 | 发布所有者 | 高；已安装制品必须与其标签匹配 |
| 必须重写受保护历史 | 冻结合并、做备份、记录事故 | 仓库维护者和书面记录，且已取得 AU-1 第 3 级明确同意；按事故流程 | 高；每个克隆都必须对齐 |
| 已审查的堆叠必须更换基线提交 | 重写堆叠并通知新的头部 | 分支所有者、堆叠中的每位审查者，且已取得 AU-1 第 3 级明确同意 | 中；每个批准都需重新获取 |
| 分支包含多位作者的提交 | 每位作者修改自己的提交 | 每位作者 | 中；重写他人的提交需经其同意 |

对于未推送提交的整理，本表仅放行 IR-8 允许的两种操作：修改最近一个未推送提交（`git commit --amend`），或用 `git reset --soft HEAD~1` 拆分该提交；不得对多个未推送提交执行 `reset`、交互式变基或其他历史重写。

规则：

- 仅撤销能够解决问题的最小单位，优先实施前向修复，而非重写。
- 每次强制推送均必须带租约；裸 `--force` 永不获得批准。
- 重写他人已在其上开展工作的分支属于事故，即使内容正确。
- 重写应当在请求线程中通知，并说明哪些提交发生变更。

## 合并队列与自动合并规则

队列规则：

- 仅在批准后且最新提交针对当前基线全部通过时，方可入队；队列将变基并重跑必需校验，因此落后于基线的分支将
  等待，不得带着陈旧状态合并。
- 不得绕过队列合并；队列启用期间直接实施管理性合并即绕过路径。
- 队列失败时，应当修复请求并推送；修复属于实质性的，应当重新请求审查，然后重新入队，不得重试同一条目并期
  望结果不同。
- 请求在队列中等待超过一日的，说明校验缓慢或不稳定；应当修改校验或拆分请求，不得增加重试。

自动合并规则：

- 仅在必需的批准审查均存在后，方可允许启用自动合并；自动合并属于排期便利，不得构成提前批准。
- 自动合并继承分支的必需校验、队列与线性历史设置；不得绕过校验或过期批准。
- 高风险路径仅在满足高风险审查人数且有具名回滚负责人时，方可使用自动合并。
- 基线分支失败或发布冻结生效时，应当禁用自动合并；冻结由发布所有者控制。
- 作者无法在审查周转期内响应的，应当关闭自动合并，以免变更带着过期描述合入。

冻结规则：

- 发布冻结将暂停队列中的每个请求，发布所有者指定的修复除外。
- 安全事件仅在安全所有者批准并记录例外后，方可绕过冻结。
- 冻结结束后应当重开队列，并将每个请求变基至冻结时的顶端后重新入队。
