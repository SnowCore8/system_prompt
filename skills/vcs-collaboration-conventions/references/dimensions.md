# 版本控制各维度

本文件与 `SKILL.md` 配合使用。每一节规定一个协作维度的规则、决策表与边界情况，编号与维度索引一致。仓库已有策
略或平台设置的，代理应当先阅读上述内容并将其作为输入，依 `SKILL.md` 的规则审查与处理；项目约定仅在本 skill
未规定时补充，不得覆盖本 skill。本文件提供默认值与理由。

## 1. Git 工作流与分支

分支模型是关于变更如何到达生产的承诺。每一仓库或每一分支类别应当选定一次并记录，使其他所有规则继承该模型。分
支类别是一组共享合并方式与生命周期上限的分支，例如主干、发布、热修复或维护。

- 依发布路径选择，不得依潮流选择：每次合并均能够部署的，使用主干开发；某一版本需要稳定化或持续支持的，使用发
  布分支；多个维护中的版本需要交付给客户的，使用 GitFlow。照搬其他团队仓库的模型，通常败于发布节奏而非纪
  律；因此应当以发布流程论证选择。
- 限制分支寿命：主题分支应当在三个工作日内集成；五日视为临界点，此时应当变基并重新审查，仍无法集成的，应
  当拆分；分支每多存续一日，冲突与集成风险即增长，等待期间审查上下文亦会丢失。
- 限制分支体量：每个可审查变更约为 400 行改动或十个文件；机械性重命名、格式扫描、锁文件更新或生成文件，应
  当自行为变更中拆出，使每一部分均能够单独审查、回退与 bisect。
- 每个分支类别选择一种合并方式：压缩合并至主干，发布晋级使用合并提交，仅在平台强制线性历史之处使用变基合
  并；同一类别中混用方式将使 blame、bisect 与 revert 指向错误的提交，审查者亦不再信任眼前的历史。
- 堆叠应当自底部开始合入：父变更合并后，应当将每个依赖分支变基至更新后的基线，重跑其校验，并在描述中保留
  其位置与父分支，使审查者依序阅读堆叠，且不基于过期基线审查依赖变更。
- 冲突应当在作者分支上解决：变基至当前基线并重跑受影响的校验；仅在分支被共享时，方将基线合并进主题分支；
  代理不得在发布分支的合并提交中解决冲突，因为此种解决方式将隐藏于无人逐行审查的合并之中。
- 仅在私有历史中重写：代理可以 amend 未推送的提交，在个人分支上使用 `--force-with-lease` 强制推送，不得使
  用裸 `--force`；重写 main 或发布分支应当按事故处理并留下记录。本条规则保护的是他人的工作，而非作者的便
  利。
- 以可审查的单位提交：每个提交包含一个逻辑变更，每个提交均能够构建并通过其所在领域的校验，合并前应当压缩
  fixup，使合入的提交说明变更原因而非修补顺序；将重命名、依赖升级与行为变更混于同一提交的，无法单独回退。
- 提交卫生属于硬性要求：提交中不得出现调试输出、被注释掉的代码、WIP 标记、机密或本地配置；合并前应当以
  `git status` 与 `git diff` 自检，临时产物随用随删。重命名、格式化与依赖升级应当与行为变更分开提交。

| 好 | 坏 | 原因 |
|---|---|---|
| 每天集成一个三天的分支 | 三周的分支到最后才合并 | 冲突与集成风险随分支年龄增长。 |
| 把功能压缩合并进主干 | main 上合并提交与压缩合并交替出现 | 仅使用一种方式，方能使 blame 与 revert 保持可预测。 |
| 用 `--force-with-lease` 变基个人分支 | 对共享分支执行 `git push --force` | 租约会拒绝覆盖上次 fetch 之后推送的工作。 |
| 从发布标签切出热修复并 cherry-pick 到主干 | 直接编辑发布分支并重新打标签 | 修复必须同时存在于两条线上，且不得移动历史。 |
| 把重命名与行为变更拆开 | 一个 900 行、既重命名又改逻辑的 diff | 每一部分均能够单独审查与回退。 |
| amend 未推送的提交 | amend 已经推送且审查过的提交 | 重写已发布的提交将迫使每个依赖分支对齐。 |
| 给发布提交打一次标签 | 再补一个修复后重建标签 | 已发布制品指向标签对应的确切提交。 |
| 父变更合入后变基堆叠中的子分支 | 保留旧基线稍后再合并 | 审查与测试将作用于一个已不存在的状态。 |
| 用 `-x` cherry-pick 热修复以记录来源 | 在分支之间手工复制 diff | 来源信息在再次应用后仍保留。 |

按分支类别的合并路径：

| 分支类别 | 合并方式 | 热修复路径 |
|---|---|---|
| 主题分支到主干 | 必需校验通过后压缩合并 | 不适用；主干持续部署 |
| 发布分支到 main | 发布校验通过后用合并提交 | 在发布分支上修复，再向前移植到主干 |
| 功能分支进入 `develop`（GitFlow） | 带 `--no-ff` 的合并提交 | 从发布标签切热修复，合并到 main 和 develop |
| fork 贡献 | 审查后由维护者压缩合并 | 维护者在常规分支上应用修复 |
| 已发布版本 | 在发布提交上打标签 | 自热修复分支打新补丁标签；不得移动旧标签 |
| 受支持版本的热修复 | 以合并提交进入发布分支，不得使用压缩合并 | 修复无需功能版本即可到达用户 |
| 私下准备的安全修复 | 安全所有者审查后用合并提交 | 披露时机保持可控 |

主干与发布分支需要不同规则的，应当按分支类别拆分策略，不得要求审查者记住例外；拆分应当记录一次，并在下一个
发布中验证。

## 2. PR 与 MR 规范

PR 或 MR 属于审查单位与回退单位，亦为变更存在原因的记录。其标题、描述与状态应当视为变更的组成部分，而非变
更之外的文书。请求亦为审查记录：变更内容、批准主体、已运行的校验，以及风险被接受的理由。

- 标题应当依仓库的提交格式说明结果；`naming-conventions` skill 管辖类型与范围的语法，本 skill 要求标题说明
  变更内容与理由。标题仅有工单号、“修复”或 WIP 的，审查者仅可打开 diff 方能得知目的。
- 描述应当按顺序回答四个问题：解决何种问题、如何解决、验证了何种内容、可能出现何种错误；选择不明显的，应
  当补充被否决的备选方案。代理不得仅描述代码机制，因为审查者需要 diff 无法表达的目的。
- 请求应当链接变更所关闭的 issue，以及其依赖与后续事项：部分修复仅链接、不写关闭关键字，使 issue 在验收标
  准满足前保持打开；关闭关键字是“合并即完成工作”的承诺。
- 应当要求使用仓库模板，因为空描述属于请求被拒绝的情形，而非轻微的风格问题；本 skill 管辖模板的要求以及模
  板必须记录的决定，包括验证证据与回滚；模板行文遵循仓库的文档风格。
- 尽早反馈具有价值的，可以开启草稿；仅在描述完整、自审完成且必需校验全部通过后，方可标记就绪；草稿不进入
  审查队列，不被批准合并；工作停止的，应当关闭而非搁置。
- 保持请求可审查：改动应当少于 400 行且仅包含一个逻辑变更；必须扩大的，应当拆分并堆叠各部分，因为 diff 超
  过数百行后，审查质量的下降速度快于审查时间的上升速度。
- 审查状态应当有意识地处理：仅在存在证据时批准，请求修改时给出编号的必改项列表，以评论提出待决问题；审查
  期间以提交形式推送修复，不得重写分支；阻塞线程未解决的，不得合并。
- 合并前应当要求校验与队列，并且仅在全部条件均成立时合并：所有者批准、合并结果上的必需校验全部通过、无未
  解决的阻塞线程、无使测试结果失效的更新基线提交，以及合并方式与分支类别匹配。

| 好 | 坏 | 原因 |
|---|---|---|
| 标题说明结果：`fix(invoice): reject expired cards` | `Fixed stuff (#412)` | 在查看 diff 之前即可看到目的。 |
| 描述列出问题、做法、验证和风险 | `See the ticket` | 审查者能够核对声明，而非仅查看代码。 |
| 只在验收完成时写 `Closes #412` | 部分修复也写 `Closes #412` | 关闭关键字会在合并时关闭 issue。 |
| 请求改动少于 400 行 | 一个 1,400 行的“小重构” | 超过数百行后，审查注意力将崩塌。 |
| 在校验全绿且有描述之前保持草稿 | 空描述却标为就绪 | 审查者将排入无法合并的工作。 |
| 审查期间推送 fixup，合并时压缩 | 审查中途不通知就强制推送 | 审查评论失去锚点。 |
| 必需校验在合并结果上运行 | 只在作者最新提交上全绿 | 最终交付的是合并组合。 |
| 每个描述都写明堆叠顺序 | 三个请求没有说明顺序 | 审查者不知道哪个先合入。 |
| 验证粘贴失败与通过的运行结果 | “本地测过了” | 证据可核查。 |

请求状态与允许的操作：

| 状态 | 允许的操作 | 条件 |
|---|---|---|
| 草稿 | 仅为早期反馈而审查 | 不符合批准或合并条件 |
| 就绪，校验进行中 | 阅读 diff；校验结束前暂不批准 | 此时即可以提出阻塞评论 |
| 已批准，发生实质性推送 | 重新审查增量，然后重新批准 | 依策略，推送后批准即过期 |
| 在合并队列中 | 等待；失败时修复并重新入队 | 不得绕过队列合并 |
| 已批准，基线已移动 | 变基、重跑校验；若冲突解决未改代码则保留批准 | 经测试的结果必须与实际合入的结果一致 |
| 已启用自动合并 | 等待队列；不得手工合并 | 该设置属于承诺，不构成覆盖手段 |
| 已合并 | 删除分支并核实部署 | 修正通过新请求进行 |

无法以描述的四个问题说清的请求，尚未达到可审查的程度；模板不鼓励提供证据的，缺陷在模板，不在作者。

## 3. 代码审查

审查是第二个人判断变更是否正确、安全与可维护的环节。投入的注意力应当与出错代价成正比，并使每条评论均可执
行。审查记录亦保护作者：带证据的批准表明，具备该领域知识的人接受了风险。

- 选择审查者之前，应当先划分风险级别：文档、注释、仅测试变更与格式化属于轻量；普通功能或缺陷修复属于标
  准；认证、支付、权限、加密、数据迁移、公共接口、依赖升级以及 CI 或发布工具属于高风险，因为上述失败代价高
  且在 diff 中不易察觉。
- 可判定的门禁应当由机器人负责，判断事项应当由人工审查负责。构建、单元与集成测试、lint、类型校验、机密扫
  描、覆盖率阈值与文档构建由 CI 强制执行，人工审查不重复实施；正确性、设计取舍、安全语义、测试充分性、性能
  与文档影响由审查者判断，机器人无法替代。可判定的项必须自动化，否则将反复漏检；判断性的项必须由人实施，否
  则合并将变为仪式。
- 选择审查者时，应当先按所有权、再按专长确定：CODEOWNERS 要求归属团队审查的，必须有该团队审查；未读过变
  更区域的审查者仅为评论者，不构成批准者，因为批准所依据的判断只有熟悉该区域方能支撑。
- 审查人数应当按风险设定：轻量一名，标准一名所有者，高风险两名且包含领域或安全审查者；仓库每项变更均需同
  两人审查的，属于人员配置问题而非审查策略，解法是增加所有者而非减少审查。
- 应当设定周转预期：一个工作日内首次响应，较小的增量当日重新审查，停滞的审查一日后改派，不得使作者持续阻
  塞。周转属于策略的组成部分，因为未审查的变更将在等待中失效。
- 应当区分阻塞与非阻塞：每条评论添加前缀，`must:` 阻塞合并，`should:` 请求修复或解释，`nit:` 表示局部偏
  好，`q:` 表示需要回答但不要求改动的问题；未标记的评论按 `should:` 计算，仍须回复，使作者始终知晓变更与合
  并之间的阻塞事项。
- 审查对象为变更本身，而非仅 diff：应当对照 issue 检查正确性，检查无该变更即会失败的测试、错误与失败路
  径、安全与隐私、预期规模下的性能、兼容性以及文档影响；diff 展示变更内容，不展示变更是否正确。
- 作者职责如下：保持描述最新，回答每条评论，审查期间推送小 fixup，仅在修复完成或决定达成后将线程标为已解
  决，并在实质性变更后请求重新审查，不得假定旧批准仍然适用。
- 出现分歧的，应当升级至归属团队的决策负责人，并将决定记录于请求或 ADR 中；阻塞线程未解决的，不得合并；代
  理不得为结束分歧而解决线程。

| 好 | 坏 | 原因 |
|---|---|---|
| `must: reject a token without an audience claim` | “不太确定” | 严重级别与要求采取的行动均明确。 |
| 归属团队批准认证路径 | 由归属区域之外的人批准 | 所有权承载 diff 看不到的知识。 |
| 测试在修复前失败、修复后通过 | 行为变更没有新测试就合并 | 测试证明行为确实按声明发生了变化。 |
| 一天后改派停滞的审查 | 等同一个审查者两周 | 作者被阻塞，而更换审查者即可解开。 |
| 修复并回复后解决线程 | 点“解决”来清空队列 | 静默解决会掩盖未获回答的反对意见。 |
| 升级到决策负责人并记录 | 阻塞线程未解决就合并 | 记录下来的决定比审查更长久。 |
| 审查迁移的回滚步骤 | 因为 CI 全绿就批准 | CI 无法证明恢复能力。 |
| 对 nit 回复理由 | 静默忽略 nit | 已获回答的线程无需强制执行。 |

审查状态及其对合并的影响：

| 状态 | 含义 | 作者行动 | 合并影响 |
|---|---|---|---|
| 批准 | 审查者对该变更满意 | 解决剩余的 nit | 必需校验通过后允许合并 |
| 带评论批准 | 仅有非阻塞建议 | 逐条处理或回复 | 允许合并 |
| 请求修改 | 存在阻塞缺陷或缺少证据 | 修复并重新请求审查 | 阻塞，直到重新批准 |
| 评论 | 提出问题或信息，不是结论 | 用证据回复 | 不算批准 |
| 过期批准 | 批准后发生了实质性推送 | 请求重新审查增量 | 阻塞，直到重新批准 |
| 审查被驳回 | 一次推送或策略事件清掉了它 | 重新请求并重新处理提出的问题 | 阻塞，直到获得新批准 |
| 审查者不可达 | 被请求的所有者不回应 | 改派给归属团队的回退审查者 | 等待不构成审查状态 |

审查不属于校对：关于拼写的评论应当置于最后；在同一轮审查中，正确性问题优先于任何风格偏好。

## 4. 分支保护与权限

分支保护将共享约定转化为强制约定。代理应当配置能够保持受保护分支可发布的最小规则集，并将每次例外作为有记
录、经审查的事件处理。受保护分支的强度取决于其最薄弱的例外，因此例外路径属于设计的组成部分，而非对设计的规
避。

- 保护集成分支与每个受支持的发布分支：禁止直接推送、禁止删除、禁止强制推送、禁止例行绕过；受保护集合应当
  作为一份简短、具名的清单保存于仓库设置中，便于审查时对照策略核查。
- 应当要求真正守护发布的校验；校验集合取自 `testing-and-quality-conventions` 的门禁表，本 skill 仅决定按分
  支类别启用哪些项。无人强制执行的校验仅具装饰作用，因此应当将其提升为必需，或予以删除，不得保留看似通过而
  无意义的信号。
- 校验应当按分支类别分级要求：主干要求全集，发布分支额外要求打包与发布校验，维护分支可以仅要求构建、测试与
  发布所有者批准；全局清单要么以无关工作阻塞发布，要么对真正交付的分支校验不足。
- 合并方式依赖线性历史之处，应当强制线性历史，即压缩合并或变基进入主干时；发布分支允许合并提交，且应当显
  式设定该选择，不得接受平台默认值，因为历史规则与合并方式必须一致。
- 标签应当与分支同等保护：已发布的发布标签不可变，仅发布自动化或发布所有者可以创建标签；门禁失败的标签应
  当在发布前删除且不恢复；被删除或移动的已发布标签应当依记录恢复，不得凭猜测重建，因为已安装制品指向确切的
  标签提交。
- 以五种平台角色及下文列出的服务角色实施最小权限，并显式设定合并权限：外部人员为 read，issue 与审查协调为
  triage，贡献者为 write，所有者为 maintain，小型紧急通道组为 admin；作者在批准后合并，但该分支类别要求维
  护者合并的除外。
- 凭据应当视为由安全流程拥有、由流水线消费：此处仅保留一条 CI 本地规则，即凭据不得进入不可信的 fork 构建，
  因为工作流能够打印的机密，fork 请求即能够窃取。
- 记录例外路径：绕过需要操作者、原因、请求链接，以及一个工作日内的合并后审查；管理操作应当每月审查，并在
  仓库的运维记录中报告数量，因为未经审查的绕过将变为常规路径。

| 好 | 坏 | 原因 |
|---|---|---|
| main 上要求审查和校验 | “管理员可合并任何内容” | 例外会变成常规路径。 |
| 保护发布标签 | 让发布脚本创建并移动标签 | 已发布制品必须与标签匹配。 |
| 凭据不进入不可信 fork 构建 | 每个工作流都用仓库级机密 | fork 请求能够读取仓库机密。 |
| 每次绕过都记录原因 | 静默的管理性合并 | 下一次事故无法解释这个缺口。 |
| 所有者 maintain，紧急通道组 admin | 所有人都是 admin | 最小权限限制影响范围。 |
| 主干上的线性历史 | main 上混用合并提交与压缩合并 | 历史与审查模型一致。 |
| 文档发布处要求文档构建 | 合并从未渲染过的文档 | 发布的页面就是产品。 |
| 把发布令牌与部署令牌分开 | 一个令牌既能够打标签又能够部署 | 两种权限将一次失陷的影响限制在较小范围。 |

角色及其可执行的操作：

| 角色 | 分支操作 | 设置与权限操作 |
|---|---|---|
| read | 查看代码、issue 和校验结果 | 无 |
| triage | 管理 issue 与审查请求；不得推送代码 | 无 |
| write | 推送主题分支、发起请求 | 无 |
| maintain | 合并到受保护分支；管理非受保护设置 | 向 admin 请求变更 |
| admin | 绕过保护；编辑设置、规则和标签 | 有时限、有记录、事后审查 |
| 发布自动化 | 打标签并发布制品 | 不修改设置；仅使用限定范围的令牌 |
| 安全团队 | 读取所有操作和审查日志 | 设定机密与密码策略 |

平台无法强制某一规则的，应当以定期人工检查替代该规则，并指定负责人；人人以为正在强制执行、实际无人执行的规
则，比没有规则更为有害。

## 5. 代码所有权

所有权确定谁必须审查某条路径、失败时由谁负责。所有权应当编码于平台能够强制执行之处，保持最新，并不得存在没
有具名所有者的路径。所有权不等同于专长：所有者对审查覆盖负责，不对了解每一行代码负责。

- CODEOWNERS 应当作为可执行策略：所有者将被自动请求，必需审查规则使所有者批准成为合并条件；代理应当核实
  平台自受支持位置读取该文件，且最后匹配的模式生效，因为放错位置的文件将被静默忽略。
- 覆盖每条可合并路径：仓库的根级回退、每个服务或领域一个团队，以及共享库、配置、CI、发布脚本、生成目录与
  第三方引入代码的显式模式；无任何模式匹配的路径属于孤儿路径，下一次改动时无人审查。
- 应当写团队，不写个人：团队句柄能够在人员离开后存续，分摊审查负载，并避免休假阻塞合并；仅当路径确实只有
  一名维护者时，方写个人，且该条目应当设定到期审查，不得成为永久条目。
- 归属应当按领域划分，不按文件类型划分：服务团队拥有其代码、测试、配置与迁移，平台团队拥有共享 CI、构建工
  具、生成代码与第三方引入依赖；对生成目录或第三方引入目录的变更，应当按“带生成器输入的重新生成”审查，不
  得按手工编辑的 diff 审查。
- 仅在风险足以证明必要时，方强制要求所有权审查：认证、财务、隐私、基础设施与公共接口路径要求所有者审查，
  其他位置的所有权仅作建议，使两人团队无需等待外部人员即可合并。
- 保留回退所有者：归属团队不可用或已解散的，由平台或仓库维护者团队接收请求；回退方案应当写入文档并实际演
  练，不得待事故中时钟已经开始走时方被发现。
- 每次重组后以及每季度，应当审查覆盖情况：找出孤儿路径、失效句柄、没有成员的团队，以及不匹配任何路径的必
  需审查规则，然后在专门的请求中修复覆盖，指定具名负责人与期限。
- 转移或退役所有权应当有意识实施：转移应当在一次经审查的变更中同时移动模式与团队成员；退役服务应当移除其
  路径，并由所有者确认归档，使审查请求不指向失效句柄，已删除的代码亦不保留所有者。

| 好 | 坏 | 原因 |
|---|---|---|
| 服务路径用团队句柄 | 服务用个人句柄 | 团队能够在人员离开后存续。 |
| 认证路径强制所有者审查 | 密码重置只作建议性所有权 | 风险决定哪里适用强制审查。 |
| 孤儿路径有回退维护者团队 | 没人抱怨之前都没有所有者 | 下一次变更有着落。 |
| 审查生成器输入并重新生成 | 手工编辑 `vendor/` 下的文件 | 生成目录归工具链所有，不归 diff 所有。 |
| 每季度审查，修复项具名且有期限 | 只有一条通配规则 | 通配符会掩盖孤儿路径。 |
| 所有权转移在维护者审查的请求中进行 | 新所有者批准自己的授权 | 权限变更应当经过审查。 |
| 具体模式放在宽泛回退之后 | 宽泛模式放在最后，覆盖所有具体所有者 | 最后匹配的模式生效。 |
| 移除路径前由所有者确认归档 | 先移除路径，之后再退役 | 所有者应当为损失签字确认。 |

路径类型及其所有权约定：

| 路径类型 | 所有者 | 审查要求 |
|---|---|---|
| 按领域划分的源码 | 归属服务团队 | 风险策略要求之处需要所有者批准 |
| 共享库或 SDK | 归属平台或库团队 | 公共变更需一名所有者加一名消费方 |
| CI、构建与发布脚本 | 平台团队 | 每次变更均强制 |
| 生成代码 | 生成器所有者 | 提供重新生成证明；不逐行审查 |
| 第三方引入依赖 | 平台或依赖所有者 | 固定版本、许可证与安全公告检查 |
| 文档与模板 | 文档所有者 | 除非页面已发布，否则只作建议 |
| 基础设施即代码 | 平台团队 | plan 输出随变更一起审查 |
| 已退役服务 | 归档所有者，直到删除 | 移除由原所有者审查 |

未指定回退的所有权规则属于单点故障；代理应当以“所有者明日消失时，由谁审查该路径”检验该规则，并在下一次变
更到来之前修正答案。
