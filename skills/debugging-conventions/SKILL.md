# 调试规范

调试有四类可预见的失效：未复现就改代码，把猜测当诊断；只修症状，同一缺陷换个触发条件又出现；修复不附回归
测试，既无法证明缺陷曾经存在，也无法确定回退时点；工具越界，日志淹没信号、调试器代替推理、profiler 被用来
回答正确性问题。本 skill 给出从缺陷报告到修复验证的单一决策流程，并规定复现、二分定位、根因分析、最小修复与
工具纪律。它适用于任何语言与运行环境，把“先复现、再定位、后修复、必验证”作为不可跳过的顺序；在生命周期中，
它把一次缺陷转化为 G3 的增量、G4 的验证证据与 G5 的发布复核输入。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。调试器、日志系统、CI 能力、语言运行时与合规要求都不是可选项。
2. 本 skill 的规则。复现、二分定位、根因分析、最小修复与回归验证以本文件与 `references/` 为准。
3. 既有项目约定与事实。运行手册、日志规范与缺陷跟踪系统的格式属于事实输入，依本 skill 的规则处理。
4. 个人偏好，不得覆盖上述三层。

边界：

- 测试策略（层级、门禁阈值与豁免程序）归 `testing-and-quality-conventions`；本 skill 只管辖一条纪律：修复必须
  附一条能证明缺陷的回归测试或可复现步骤。
- 性能剖析（延迟、内存、CPU 与吞吐瓶颈）归 `performance-conventions`；本 skill 负责确认“确实慢”并交出复现与
  二分结果，再由该 skill 定位热点。
- 并发竞态（数据竞争、死锁、时序与原子性）归 `concurrency-conventions`；本 skill 提供复现与二分的通用方法。
- 修复提交的拆分与历史改写归 `vcs-collaboration-conventions`；本 skill 只要求修复与无关改动分开提交。
- 阶段划分、门禁判定与风险分级归 `project-lifecycle-governance`；本 skill 在 S3–S6 提供可核验的缺陷证据。
- 强制规则冲突时按 `rules/global-user-constraints.md` 的效力顺序处理；无法判定时报告用户裁决，不得自行选定。

## 生命周期定位

上游输入：可判定的缺陷报告、失败测试、事故单或监控告警，以及 G0 已记录的授权、风险级别与停止条件。缺陷可能
在 S3 构建或 S4 验证期间发现，也可能来自 S5 发布后的运营反馈。

下游交接：修复增量与回归证据交给 G4 验证；未关闭缺陷、仅修症状与临时缓解交给 G5 发布复核；根因、逃逸原因与
补充测试交给 S6 复盘，并由复盘推动测试与威胁模型更新。

升级与停止：无法复现时停止改码并向报告人索取信息；同一问题第二个补丁仍失败时停止打补丁、回到根因定位，根因
属结构性时升级到 `architecture-and-design-conventions` 与用户决策；根因修复超出授权、成本或兼容性时按 HO-7
说明并报告，不得自行降级为症状修补。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S0 受理 | 判定报告是否可判定，确认对象与授权，区分正确性缺陷、性能问题与并发竞态 | 受理结论、缺失信息清单、分流结论 |
| S2 计划 | 为已确认缺陷固定复现环境、回归测试位置、修复范围与回滚点 | 复现方案、回归测试清单、修复范围说明 |
| S3 构建 | 复现、二分定位、根因假设与验证、失败测试、最小修复 | 最小复现、已排除事项记录、根因说明、修复提交 |
| S4 验证 | 取得修复前失败与修复后通过的对照，运行受影响范围的回归 | 两次执行输出、回归结论、未覆盖部分与残留风险 |
| S5 发布 | 复核未关闭缺陷、症状修补与临时缓解的接受记录 | 缺陷状态清单、风险接受记录、发布阻塞项 |
| S6 收尾 | 把根因、逃逸原因与补充测试写入复盘 | 根因报告、行动项与负责人、新增回归测试 |

## 门禁与证据

阶段表中的门禁是该阶段的出口门；下表只列本 skill 直接提供证据的门禁，其余证据由
`project-lifecycle-governance` 与其他 skill 汇总。

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G3 构建 | 最小复现步骤、修复前失败的回归测试、根因假设与已排除事项 | Hold：复现或失败测试缺失，不得申报增量；范围不清时 Recycle 到 S3 |
| G4 验证 | 修复前后两次执行输出、受影响范围回归结论、未自动化时的双次步骤记录 | Recycle 到 S3：修复未针对根因或回归未捕获缺陷；输出缺失时 Hold |
| G5 发布 | 未关闭缺陷清单、仅修症状的接受记录、临时缓解的负责人与到期日 | Hold：阻塞级缺陷未关闭且无接受记录；是否 No-Go 由发布负责人决定 |
| G6 收尾 | 根因报告、逃逸原因、补充回归测试与行动项 | Hold：证据不全时不得关闭复盘；Recycle 到 S4：根因未落成可复用测试 |

证据必须来自本次修复的同一提交范围；跨版本复用的旧输出、仅凭口头说明的验证均不构成证据。R0 任务可以合并
G3 与 G4 的记录，但“失败在前、通过在后”的对照不得省略。

## 工作流

1. 受理与分流（S0）。复述缺陷，检查报告四要素；判定属于正确性缺陷、性能问题还是并发竞态，后两类移交对应
   skill；写明授权、风险级别与停止条件。
2. 复现（S3）。把报告转成能稳定触发缺陷的最小步骤，环境记录到可重跑；无法复现的，报告“无法复现”并列出已
   尝试的环境与步骤，不得改代码。
3. 缩小范围（S3）。以 git bisect、日志、断点或插桩把范围减半，每一步记录“现已排除的事项”，收敛到单个函数
   或语句后再修改。
4. 定位根因（S3）。区分根因与触发条件，形成可验证的假设，再用调试器或日志验证假设；第二个补丁仍失败的，
   停止打补丁并回到本步。
5. 编写回归测试并取得失败（S3）。先写一条修复前失败、修复后通过的测试并留存失败输出；无法自动化的，用能
   稳定复现缺陷的步骤，修复前执行一次并记录结果。
6. 实施最小修复（S3）。仅修改根因所需的最小代码；重构、格式化、重命名与升级依赖分开提交。
7. 取得通过并回归（S4）。重跑该测试或步骤，确认由失败转为通过；运行受影响范围的回归，记录未覆盖部分与残留
   风险。
8. 发布前复核（S5）。列出未关闭缺陷与临时缓解，确认接受记录、负责人与到期日，提交发布负责人判断。
9. 复盘（S6）。把根因、逃逸原因与补充测试写入复盘，行动项带负责人与到期日；同一根因再次出现时，回到第 4
   步而不是叠加新补丁。

## 核心规则

- **先复现，后修改。** 未取得复现步骤就改代码，属于猜测。判定标准：修复提交的说明必须引用一条能稳定触发
  缺陷的步骤或测试；引用不了的，视为未复现。无法复现的，报告“无法复现”并附已尝试的环境与步骤，不得提交
  “可能有用”的改动。
- **缺陷报告应当可判定。** 报告必须写明最小复现步骤、环境（版本、平台、依赖）、期望结果与实际结果。缺少
  “期望与实际”或复现步骤的，先做不修改代码与数据的调查与复现尝试，同时索取缺失信息；修改代码前必须有可判定
  复现。
- **修复必须附一条能够证明缺陷曾经存在、修复后通过的测试或可复现步骤。** 先写回归测试并确认修复前失败，
  修复后通过；无法自动化的，用能稳定复现缺陷的步骤在修复前后各执行一次，并在交付说明中记录。判定标准：
  修复前该测试失败、修复后通过，或同一复现步骤在修复前后得到不同结果。
- **定位至根因，不得仅修复症状。** 根因不可修复或暂不具备修复条件的，方可仅修改症状。仅修改症状，包括捕获
  异常后吞掉、增加特判绕过、屏蔽日志，必须说明根因未能修复的理由并记录为遗留跟踪项，且须取得用户明确同意。
  超出授权、成本、兼容性属于申请授权或排期的理由，不构成自动放行。针对同一问题的第二个补丁仍然失败的，
  停止打补丁，回到根因定位。
- **二分缩小范围，每一步保留证据。** 用 git bisect、日志、断点或插桩将范围减半；每一步记录“现已排除的事项”。
  二分至单个函数或语句后方可修改；修改完成后，将该证据写入修复说明。
- **最小修复，不得顺带修改。** 修复仅修改根因所需的最小代码；顺带重构、格式化、重命名、升级依赖与缺陷修复
  分开提交。审查者发现修复 diff 混有无关改动的，应当驳回并要求拆分。
- **工具纪律。** 临时日志结构化、分级、可关闭，提交前移除；调试器用于验证假设，不得替代推理，不得遗留断点；
  profiler 只回答“慢在何处”，不回答正确性。日志级别与格式归 `code-style-conventions`，竞态推理归
  `concurrency-conventions`。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 未复现即修改代码 | 改动属于猜测，可能未修复该缺陷，并引入新问题 | 先复现；无法复现的，报告“无法复现” |
| 仅修复症状，不修复根因 | 同一缺陷在另一触发条件下重现，补丁持续叠加 | 定位根因；仅修复症状的，须用户同意并记录理由 |
| 修复未附回归测试 | 无法证明缺陷曾经存在，亦无法阻止回退 | 先取得失败测试，修复后取得通过结果 |
| 修复缺陷时顺带重构或格式化 | 无法分辨哪项改动修复了缺陷，亦无法单独回滚 | 实施最小修复，其他改动分开提交 |
| 凭猜测二分，不留证据 | 定位过程不可复现，审查者无法复核 | 每一步记录已排除事项 |
| 以调试器替代推理 | 单步跟踪仅观察现象，未形成根因假设 | 先提出假设，再验证；调试器仅用于验证假设 |
| 日志淹没信号 | 噪声日志使关键线索不可见，并拖慢系统 | 使用结构化、分级、可关闭的临时日志，用后移除 |
| 以重试或忽略掩盖缺陷 | 失败被隐藏，根因未处理，缺陷在别处复现 | 记录失败，按本流程定位；重试仅用于已证实的基础设施错误 |

## 审查清单

- [ ] 缺陷报告包含最小复现步骤、环境、期望结果与实际结果，或被标记为“无法复现”并附已尝试项。
- [ ] 分流结论明确：正确性缺陷留在本 skill，性能与竞态已移交对应 skill。
- [ ] 修复提交的说明引用了一条能稳定触发缺陷的步骤或测试。
- [ ] 二分每一步记录已排除事项，范围收敛至单个函数或语句。
- [ ] 写明根因与触发条件的区别，修复针对根因而非症状。
- [ ] 仅修复症状时，记录根因不可修复的理由、接受人，并建立跟踪项。
- [ ] 修复只改根因所需的最小代码，无无关重构、格式化或重命名。
- [ ] 回归测试，或无法自动化时的可复现步骤，在修复前失败、修复后通过。
- [ ] 受影响范围的回归已运行，未运行部分已在交付中标注“未运行”。
- [ ] 临时日志、断点与插桩在提交前移除，提交中无调试残留。
- [ ] 发布前复核列出未关闭缺陷与临时缓解，接受记录有负责人与到期日。
- [ ] 根因已落成可复用的回归测试，并进入复盘行动项。

## 示例

<example>
场景：支付接口偶发返回 500，报告仅称“有时失败”。
做法：在索取环境与最小复现的同时，先用日志与二分把范围收敛到币种换算函数，查明根因为除零，触发条件为特定
币种缺失汇率。修复只补除零保护，并补一条“缺失汇率时返回可判定错误”的回归测试，修复前失败、修复后通过。
</example>

<example>
场景：崩溃无法在本地复现。
做法：报告“无法复现”，附已尝试的版本、平台、输入与日志摘录，不得猜测并修改代码；等待补充期间继续不修改代码
与数据的排查（日志、配置、历史）；补充到位后按正常流程定位。
</example>
