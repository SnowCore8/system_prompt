# 调试规范

调试工作存在四类可预见的失效情形：在复现之前修改代码，将猜测作为诊断；仅修复症状，使同一缺陷在另一触发
条件下重现；修复未附回归测试，无法证明缺陷曾经存在，亦无法确定回退时点；工具使用超出边界，日志淹没信号、
调试器替代推理、profiler 被用于回答正确性问题。上述失效情形均易引入而难以逆转，因为团队将围绕失效的调试
习惯重组其对缺陷的处理方式。本 skill 规定自缺陷报告至修复验证的单一决策流程，并规定复现、二分定位、根因分
析、最小修复与工具纪律的规则集。本 skill 适用于任何语言与运行环境，并将“先复现、再定位、后修复、必验证”
作为不可跳过的顺序。其服务对象为排查缺陷的工程师、复核缺陷报告的审查者，以及判断修复是否真正消除根因的维
护者。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充：

1. 强制性的平台、法律、宿主与用户全局约束。调试器、日志系统、CI 能力、语言运行时提供的约束，以及适用的
   合规要求，均非可选事项。
2. 本 skill 的规则。复现、二分定位、根因分析、最小修复与回归验证的规则，以本文件与 `references/` 为准。
3. 既有项目约定与事实。代理应当先阅读运行手册、日志规范与缺陷跟踪系统的既有格式；上述内容属于事实输入，
   依本 skill 的规则处理。项目约定仅在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

- 测试策略，包括测试类型、分层方式与门禁阈值，由 `testing-and-quality-conventions` skill 管辖。本 skill 仅
  管辖“修复必须附一条能够证明缺陷的回归测试或可复现步骤”这一纪律，不重复规定测试层级与门禁。
- 性能剖析，包括定位延迟、内存、CPU 与吞吐瓶颈，由 `performance-conventions` skill 管辖。本 skill 管辖正确
  性缺陷；性能缺陷应当先依本 skill 复现，再交由性能规范处理瓶颈。
- 并发竞态，包括数据竞争、死锁、时序与原子性，由 `concurrency-conventions` skill 管辖。本 skill 提供复现与
  二分的通用方法；竞态特有的推理与工具由该 skill 规定。
- 修复后的提交拆分，由 `vcs-collaboration-conventions` skill 管辖。本 skill 仅管辖修复与无关改动分开提交这
  一纪律。
- 两项规则冲突的，代理应当依 `rules/global-user-constraints.md` §3.3 的效力顺序实施，说明冲突与所选规则，并将决定记录于缺陷工单或运行手册；无法判定时报告用户裁决。

## 流程

1. 复现。代理应当将报告转化为能够稳定触发缺陷的最小步骤；无法复现的，应当报告“无法复现”，列明已尝试的
   环境与步骤，不得凭猜测修改代码。
2. 缩小范围。代理应当以 git bisect、日志、断点或插桩，将缺陷范围收敛至最小可复现单元；每一步记录“现已排
   除的事项”。
3. 定位根因。代理应当区分根因，即导致缺陷的代码缺陷，与触发条件，即使缺陷显现的输入；记录根因与证据，
   不得仅修复症状。
4. 编写回归测试并取得失败结果。代理应当编写一条在修复前失败、修复后通过的测试；无法自动化的，以能够稳定
   复现缺陷的步骤替代。
5. 实施最小修复。代理仅应修改修复根因所需的最小代码；顺带重构、格式化与重命名应当分开提交。
6. 取得通过结果并回归验证。修复后应当重跑该测试或步骤，确认其由失败转为通过；修复前失败、修复后通过，
   方构成证明。

## 核心规则

- **先复现，后修改。** 未取得复现步骤即修改代码，属于猜测。判定标准：修复提交的说明必须引用一条能够稳定
  触发缺陷的步骤或测试；无法引用的，视为未复现。无法复现的，应当报告“无法复现”并附已尝试的环境与步骤，
  不得提交“可能有用”的改动。
- **缺陷报告应当可判定。** 报告必须写明最小复现步骤、环境（版本、平台、依赖）、期望结果与实际结果。缺少
  “期望与实际”或复现步骤的报告无法判定是否修复，应当退回补齐后再开始。
- **修复必须附一条能够证明缺陷曾经存在、修复后通过的测试或可复现步骤。** 代理应当先编写回归测试并确认其
  在修复前失败，修复后通过；无法自动化的，使用能够稳定复现缺陷的步骤，在修复前后各执行一次，并在交付说明
  中记录。判定标准：修复前该测试失败、修复后通过，或者同一复现步骤在修复前后得到不同结果。
- **定位至根因，不得仅修复症状。** 根因确不可修复的，方可仅修改症状；仅修改症状，包括捕获异常后吞掉、增加
  特判绕过、屏蔽日志，必须说明根因为何不可修复，并记录为遗留跟踪项。针对同一问题的第二个补丁仍然失败的，
  应当停止打补丁，回到第 3 步重新定位根因。
- **二分缩小范围，每一步保留证据。** 代理应当以 git bisect、日志、断点或插桩将范围减半；每一步记录“现已
  排除的事项”。二分至单个函数或语句后方可修改；修改完成后，应当将该证据写入修复说明。
- **最小修复，不得顺带修改。** 修复仅应修改根因所需的最小代码；顺带重构、格式化、重命名、升级依赖与缺陷
  修复应当分开提交。审查者发现修复 diff 混有无关改动的，应当驳回并要求拆分。

## 维度索引

每个维度的详细规则、示例与边界情况见 `references/dimensions.md`；维度列中的编号就是该文件中的节号。

| 维度 | 首条规则 | 详情 |
|---|---|---|
| 1. 复现与缺陷报告 | 无法复现的，报告“无法复现”，不得猜测；报告必须包含最小复现、环境、期望与实际。 | `references/dimensions.md` 第 1 节 |
| 2. 二分定位 | 每一步减半范围并记录已排除事项，定位至单个函数或语句。 | `references/dimensions.md` 第 2 节 |
| 3. 根因分析 | 区分根因与触发条件，仅修复根因；仅修复症状的，记录根因不可修复的理由。 | `references/dimensions.md` 第 3 节 |
| 4. 修复与回归验证 | 实施最小修复；回归测试在修复前失败、修复后通过，方构成证明。 | `references/dimensions.md` 第 4 节 |
| 5. 调试工具纪律 | 日志、调试器与 profiler 各有适用边界；超出边界将淹没信号。 | `references/dimensions.md` 第 5 节 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 未复现即修改代码 | 改动属于猜测，可能未修复该缺陷，并引入新问题 | 先复现；无法复现的，报告“无法复现” |
| 仅修复症状，不修复根因 | 同一缺陷在另一触发条件下重现，补丁持续叠加 | 定位根因；仅修复症状的，记录理由 |
| 修复未附回归测试 | 无法证明缺陷曾经存在，亦无法阻止回退 | 先取得失败测试，修复后取得通过结果 |
| 修复缺陷时顺带重构或格式化 | 无法分辨哪项改动修复了缺陷，亦无法单独回滚 | 实施最小修复，其他改动分开提交 |
| 凭猜测二分，不留证据 | 定位过程不可复现，审查者无法复核 | 每一步记录已排除事项 |
| 以调试器替代推理 | 单步跟踪仅观察现象，未形成根因假设 | 先提出假设，再验证；调试器仅用于验证假设 |
| 日志淹没信号 | 噪声日志使关键线索不可见，并拖慢系统 | 使用结构化、分级、可关闭的临时日志，用后移除 |

## 审查清单

- [ ] 缺陷报告包含最小复现步骤、环境、期望结果与实际结果。
- [ ] 修复提交的说明引用了一条能够稳定触发缺陷的步骤或测试。
- [ ] 无法复现时报告“无法复现”，附已尝试的环境与步骤，且无猜测性改动。
- [ ] 二分每一步记录已排除事项，范围收敛至单个函数或语句。
- [ ] 写明根因与触发条件的区别，修复针对根因而非症状。
- [ ] 仅修复症状时，记录根因不可修复的理由，并建立跟踪项。
- [ ] 修复仅修改根因所需的最小代码，无无关重构、格式化或重命名。
- [ ] 回归测试，或无法自动化时的可复现步骤，在修复前失败、修复后通过。
- [ ] 临时日志、断点与插桩在提交前移除。
- [ ] 性能问题与并发竞态已转交对应 skill，未以调试方法强行处理。

## 示例

<example>
场景：支付接口偶发返回 500，报告仅称“有时失败”。
做法：先索取环境与最小复现；以日志与二分将范围收敛至币种换算函数，查明根因为除零，触发条件为特定币种缺
失汇率。修复仅补充除零保护，并补一条“缺失汇率时返回可判定错误”的回归测试，修复前失败、修复后通过。
</example>

<example>
场景：崩溃无法在本地复现。
做法：报告“无法复现”，附已尝试的版本、平台、输入与日志摘录，不得猜测并修改代码；要求补充能够稳定触发的
最小步骤后，再行定位。
</example>
