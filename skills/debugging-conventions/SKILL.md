# 调试规范

调试会以四种可预见的方式失效：在复现之前就改代码，把猜测当成诊断；只修症状，让同一缺陷换个触发条件再回来；
修复不带回归测试，无法证明缺陷曾存在、也不知道何时回退；以及工具被用错边界，日志淹没信号、调试器当成替代
推理、profiler 拿来回答正确性问题。每种失效都容易引入、难以逆转，因为团队会围绕失效的调试习惯重组自己对缺陷
的处理方式。本 skill 给出从缺陷报告到修复验证的单一决策流程，以及复现、二分定位、根因分析、最小修复与工具
纪律的规则集。它适用于任何语言与运行环境，把「先复现、再定位、后修复、必验证」作为一条不可跳过的顺序。它
服务于排查缺陷的工程师、复核缺陷报告的审查者，以及判断一条修复是否真的修好了根的维护者。

## 适用范围与优先级

采用第一条适用的规则，同一范围内不要混用标准：

1. 平台、工具链与合规的强制要求。调试器、日志系统、CI 能力与语言运行时不是可选项。
2. 既有项目约定。发明规则之前先读运行手册、日志规范与缺陷跟踪系统的既有格式。
3. 本规范的默认值，在前两层未作规定时适用。
4. 个人偏好，永远不能覆盖上述三层。

- 测试策略（写什么测试、如何分层、门禁阈值）归 testing-and-quality-conventions skill 管。本 skill 只管「修复
  必须带一条能证明缺陷的回归测试或可复现步骤」这条纪律，不重述测试层级与门禁。
- 性能剖析（定位慢、内存、CPU 与吞吐）归 performance-conventions skill 管。本 skill 覆盖正确性缺陷；性能缺陷
  先按本 skill 复现，再交性能规范处理瓶颈。
- 并发竞态（数据竞争、死锁、时序与原子性）归 concurrency-conventions skill 管。本 skill 提供复现与二分的通用
  方法，竞态特有的推理与工具在该 skill。
- 修复后的提交如何拆分归 vcs-collaboration-conventions skill 管。本 skill 只管修复与无关改动分开提交这条纪律。
- 两条规则冲突时，说明冲突与所选规则，并把决定记录在缺陷工单或运行手册中。

## 流程

1. 先复现。把报告转化为一条能稳定触发缺陷的最小步骤；复现不了就报告「无法复现」，给出已尝试的环境与步骤，
   禁止凭猜测改代码。
2. 缩小范围。用 git bisect、日志、断点或插桩把缺陷范围收敛到最小可复现单元；每一步记录「现在排除了什么」。
3. 定位根因。区分根因（导致缺陷的代码缺陷）与触发条件（让它显现的输入），写下根因与证据，不修症状。
4. 写回归测试并跑红。写一条在修复前失败、修复后通过的测试；无法自动化时，用能稳定复现缺陷的步骤代替。
5. 做最小修复。只改修复根因所需的最小代码；顺手重构、格式化、重命名分开提交。
6. 跑绿并回归验证。修复后重跑该测试或步骤，确认由红转绿；修复前红、修复后绿才算证明。

## 核心规则

- **先复现，后修改。** 没有复现步骤就改代码是猜。判定：修复提交的说明必须引用一条能稳定触发缺陷的步骤或测试；
  引用不出来就是没复现。复现不了就报告「无法复现」并附已尝试的环境与步骤，禁止提交「可能有用」的改动。
- **缺陷报告要可判定。** 报告必须写清最小复现步骤、环境（版本、平台、依赖）、期望结果与实际结果。缺「期望与
  实际」或复现步骤的报告无法判定是否修好，退回补齐再开始。
- **修复必须带一条能证明缺陷曾存在、修复后通过的测试或可复现步骤。** 先写回归测试并确认它在修复前失败（红），
  修复后通过（绿）；无法自动化时，用能稳定复现缺陷的步骤在修复前后各跑一次，并在交付说明中记录。判定：修复前
  该测试红、修复后绿，或同一复现步骤在修复前后得到不同结果。
- **定位到根因，不修症状。** 只改症状（捕获异常后吞掉、加特判绕过、屏蔽日志）必须说明根因为何不可修，并记录为
  遗留跟踪项。第二个针对同一问题的补丁仍失败时停止打补丁，先回到第 3 步重定位根因。
- **二分缩小范围，每步留证据。** 用 git bisect、日志、断点或插桩把范围减半；每一步记录「排除了什么」。二分到
  单个函数或语句才动手改，改完把该证据写进修复说明。
- **最小修复，不顺手改。** 修复只改根因所需的最小代码；顺手重构、格式化、重命名、升级依赖与缺陷修复分开提交。
  审查者看到修复 diff 里混着无关改动，应驳回要求拆分。

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 没复现就改代码 | 改动是猜，可能修的不是这个缺陷，还引入新问题 | 先复现；复现不了报告「无法复现」 |
| 只修症状不修根因 | 同一缺陷换个触发条件就回来，补丁越叠越多 | 定位根因；只修症状要记录理由 |
| 修复不带回归测试 | 无法证明缺陷曾存在，也无法阻止回退 | 先写红测试，修复后转绿 |
| 修缺陷顺带重构或格式化 | 无法分辨哪处改动修好了缺陷，也无法单独回滚 | 最小修复，其他改动分开提交 |
| 靠猜二分，不留证据 | 定位过程不可复现，审查者无法复核 | 每步记录排除了什么 |
| 用调试器替代推理 | 单步跟踪看现象，不形成根因假设 | 先假设、再验证，调试器只验证假设 |
| 日志淹没信号 | 噪音日志让关键线索不可见，还拖慢系统 | 结构化、分级、可关闭的临时日志，用完移除 |

## 审查清单

- [ ] 缺陷报告含最小复现步骤、环境、期望结果与实际结果。
- [ ] 修复提交的说明引用了一条能稳定触发缺陷的步骤或测试。
- [ ] 复现不了时报告「无法复现」，附已尝试的环境与步骤，没有猜测性改动。
- [ ] 二分每一步记录排除了什么，范围收敛到单个函数或语句。
- [ ] 写明根因与触发条件的区别，修复针对根因而非症状。
- [ ] 只修症状时记录了根因为何不可修，并开跟踪项。
- [ ] 修复只改根因所需的最小代码，无无关重构、格式化或重命名。
- [ ] 回归测试（或无法自动化时的可复现步骤）在修复前失败、修复后通过。
- [ ] 临时日志、断点与插桩在提交前移除。
- [ ] 性能问题与并发竞态已转交对应 skill，没有用调试方法硬套。

## 示例

<example>
场景：支付接口偶发返回 500，报告只有「有时失败」。
做法：先要环境与最小复现；用日志与二分把范围收敛到币种换算函数，发现根因是除零，触发条件是特定币种缺失
汇率。修复只补除零保护，并补一条「缺失汇率时返回可判定错误」的回归测试，修复前红、修复后绿。
</example>

<example>
场景：崩溃无法在本地复现。
做法：报告「无法复现」，附已尝试的版本、平台、输入与日志摘录，不猜测改代码；要求补充能稳定触发的最小步骤
后再定位。
</example>
