# 调试维度

本文件与 `SKILL.md` 配合使用。每一节规定一个调试维度的决策、示例与边界情况。项目已有运行手册或日志规范的，
智能体应当先阅读，并将其作为事实输入；本 skill 的规则优先，项目约定仅在本 skill 未规定时补充。本文件提供默认值
与理由。智能体仅应阅读与待处理缺陷相匹配的节。

## 1. 复现与缺陷报告

缺陷报告是将模糊陈述转化为可判定事实的过程。未复现的缺陷无法验证修复，亦无法阻止回退。

- 报告应当包含四项要素：最小复现步骤、环境（语言版本、平台、依赖与版本、配置）、期望结果与实际结果。缺少
  “期望与实际”或复现步骤的报告，先按现有信息做不修改代码与数据的调查与复现尝试，同时索取缺失信息；修改代码前
  必须有可判定复现。应当附最小复现代码或命令，不得粘贴整个服务日志。
- 无法复现的，应当报告“无法复现”，附已尝试的环境与步骤，不得猜测。猜测所得改动无法对应缺陷，亦无法证
  明修复。
- 最小复现应当达到“最小”标准：删至删除任何一步均无法触发为止。复现步骤超过 10 步，或需要完整环境方能执
  行的，应当先行拆分，否则后续人员无法复核。
- 环境应当完整到可以重跑，包括操作系统、语言与运行时版本、依赖锁定版本、配置差异与数据规模。仅说明“本机
  没有问题”，不构成环境描述。

## 2. 二分定位

二分将缺陷范围逐步减半，每一步均留下可复核的证据。

- 优先以 git bisect 定位引入缺陷的提交：确定一个已知正常的历史点与一个异常点，在两者之间自动二分。应当写
  明“好”与“坏”两个参照点的可判定条件。
- 无可运行历史的，以日志、断点或插桩二分：将疑点范围减半，插入断言或日志，确认缺陷位于左半部分还是右半部
  分。
- 每一步记录“已排除的事项”。二分至单个函数或语句后方可修改；记录应当写入修复说明，供审查者复核。
- 使用调试器单步前应当先有假设：调试器用于验证“此处状态与假设不符”，不得替代推理。无假设的单步跟踪仅消
  耗时间。

## 3. 根因分析

根因指导致缺陷的代码缺陷；触发条件指使缺陷显现的输入。仅修复症状将使缺陷在另一条件下重现。

- 以“五个为什么”自现象追问至根因：每次回答后继续追问为什么，直至落到代码缺陷或数据缺陷。停留于某一输入
  特例的，属于触发条件，不属于根因。
- 区分根因与触发条件。除零的根因是缺少保护，触发条件是缺失汇率；修复应当补充保护，不得仅对缺失汇率作特
  判。
- 针对同一问题的第二个补丁仍然失败的，应当停止打补丁，回到定位步骤；根因属于结构性的，重构的成本低于叠
  加补丁。
- 仅修复症状的，须取得用户明确同意，说明根因不可修复或暂不具备修复条件的理由（超出授权、成本、兼容性），
  并记录为遗留跟踪项；上述理由属于申请授权或排期的依据，不构成自动放行；未记录的，视为未完成。

## 4. 修复与回归验证

修复必须最小，并且能够由一条回归测试或可复现步骤证明。

- 最小修复：仅修改根因所需的最小代码。顺带重构、格式化、重命名、升级依赖与缺陷修复，应当分开提交。
- 回归测试先失败后通过：先编写一条在修复前失败、修复后通过的测试并取得失败结果，再实施最小修复，最后取
  得通过结果。仅有通过结果而无失败结果的，说明测试未捕获缺陷。
- 无法自动化时，以能够稳定复现缺陷的步骤替代测试，在修复前后各执行一次并记录；跳过失败结果这一步，等同
  于未证明。
- 回归测试层级由 `testing-and-quality-conventions` skill 管辖；本 skill 不另设默认层级或优先级。

## 5. 调试工具纪律

日志、调试器与 profiler 各有适用范围；超出适用范围将淹没信号或答非所问。

- 日志：结构化、分级、可关闭；临时诊断日志用后移除，不得带入提交。日志内容与级别策略由
  `code-style-conventions` skill 管辖。
- 调试器：用于验证假设与检查状态，不得替代推理；不得在代码中遗留断点。
- profiler：仅回答“慢在何处、内存去向何处”，不回答正确性问题。性能剖析由 `performance-conventions`
  skill 管辖。
- 并发竞态的复现与推理由 `concurrency-conventions` skill 管辖；本 skill 仅提供通用的复现与二分方法。
