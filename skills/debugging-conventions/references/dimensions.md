# 调试维度

本文件与 SKILL.md 配合使用。每一节给出一个调试维度的决策、示例与边界情况。项目已有运行手册或日志规范时，先读
并执行效力更高的规则；本文件提供默认值与理由。只读与你要处理的缺陷相匹配的那一节。

## 1. 复现与缺陷报告

缺陷报告是把模糊抱怨转化为可判定事实的过程。没有复现的缺陷无法验证修复，也无法阻止回退。

- 报告四要素：最小复现步骤、环境（语言版本、平台、依赖与版本、配置）、期望结果、实际结果。缺「期望与实际」
  或复现步骤的报告退回补齐。附最小复现代码或命令，而不是粘贴整个服务日志。
- 复现不了就报告「无法复现」，附已尝试的环境与步骤，禁止猜。猜出来的改动无法对应到缺陷，也无法证明修好。
- 最小复现要「最小」：删到删掉任何一步都无法触发为止。复现步骤超过 10 步或需要完整环境才能跑时，先把它
  拆小，否则下一个人无法复核。
- 环境要完整到能重跑：操作系统、语言与运行时版本、依赖锁定版本、配置差异、数据规模。只说「我机器上没问题」
  不是环境描述。

## 2. 二分定位

二分把缺陷范围逐步减半，每一步都留下可复核的证据。

- 优先用 git bisect 定位到引入缺陷的提交：找一个已知正常的历史点，再找一个异常点，中间自动二分。写清「好」
  与「坏」两个参照点的可判定判定条件。
- 没有可跑的历史时用日志、断点、插桩二分：把怀疑范围减半，插入断言或日志，确认缺陷在左半还是右半。
- 每一步记录「排除了什么」。二分到单个函数或语句才动手改；记录写入修复说明，让审查者能复核。
- 用调试器单步前先有假设：调试器验证「这里的状态与假设不符」，而不是替代推理。没有假设的单步跟踪只会消耗
  时间。

## 3. 根因分析

根因是导致缺陷的代码缺陷，触发条件是让它显现的输入。只修症状会让缺陷换个条件回来。

- 用「五个为什么」从现象问到根因：每次回答再问为什么，直到问到一个代码缺陷或数据缺陷。停在一个输入特例上
  是触发条件，不是根因。
- 区分根因与触发条件。除零的根因是缺保护，触发条件是缺失汇率；修复缺保护，而不是只对缺失汇率特判。
- 第二个针对同一问题的补丁仍失败时停止打补丁，回到定位步骤；如果根因是结构性的，重构比叠加补丁便宜。
- 只修症状必须说明根因为何不可修（超出授权、成本、兼容性），并记录为遗留跟踪项，否则视为未完成。

## 4. 修复与回归验证

修复必须最小，且能被一条回归测试或可复现步骤证明。

- 最小修复：只改根因所需的最小代码。顺手重构、格式化、重命名、升级依赖与缺陷修复分开提交。
- 回归测试先红后绿：先写一条在修复前失败、修复后通过的测试并跑红，再做最小修复，最后跑绿。只绿不红说明测试
  没捕获缺陷。
- 无法自动化时，用能稳定复现缺陷的步骤代替测试，在修复前后各跑一次并记录；跳过红的那一步等于没证明。
- 回归测试放在能失败的最廉价层级（单元优先）；层级选择归 testing-and-quality-conventions skill 管。

## 5. 调试工具纪律

日志、调试器、profiler 各管一段，用错边界会淹没信号或答非所问。

- 日志：结构化、分级、可关闭；临时诊断日志用完移除，禁止带入提交。日志内容与级别策略归 code-style-conventions
  skill 管。
- 调试器：用来验证假设与检查状态，不替代推理；不留断点在代码里。
- profiler：只回答「慢在哪、内存去哪」，不回答正确性问题。性能剖析归 performance-conventions skill 管。
- 并发竞态的复现与推理归 concurrency-conventions skill 管；本 skill 只提供通用复现与二分方法。
