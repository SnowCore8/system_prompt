# 版本控制与协作规范

多数团队丢失代码，原因并非算法质量，而是协作失效：PR 持续膨胀，任何审查者都无法一次审阅完毕；历史中留下
无人能够解释的合并；某一目录在作者离职后失去归属；受保护分支被绕过一次之后即成为常态。这些失效在规则
阶段都容易预防，等到某一发布依赖它们之后才修复，代价就十分高昂。本 skill 规定自工作副本至主分支乃至更远
环节的决策流程与规则，涵盖分支模型与合并方式、PR 与 MR、审查深度、分支保护与代码所有权，并把合并与审查
证据接入 G2、G3、G4 与 G5 门禁。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充；同一分支类别内不得混用模型。

1. 强制性的平台、法律、宿主与全局用户约束。托管平台或组织的强制策略，包括必需校验、审查要求与签名提交
   规则，以及监管机构的变更控制规则，均非可选事项。
2. 本 skill 的规则。分支模型、合并方式、审查深度与所有权，以本文件与 `references/` 为准。
3. 既有项目约定与事实。提出规则前先阅读分支模型、合并设置、CODEOWNERS 文件与贡献者指南；这些内容属于
   事实输入，依本 skill 的规则处理，项目约定仅在本 skill 未规定时补充。
4. 个人偏好不得覆盖上述三层。

- `naming-conventions` 管辖分支名、提交消息的类型与范围以及标签名；本 skill 管辖使用上述名称的工作流、
  合并策略与审查流程。
- 本 skill 管辖 PR 与 issue 模板的要求，以及模板必须记录的决定；模板属于文档，其行文遵循仓库的文档风格。
- `release-operations-conventions` 管辖发布版本号、发布时机与 CI/CD；本 skill 管辖变更到达主分支的方式及
  其合并路径，以及标签的不可变与保护。
- `security-compliance-conventions` 管辖访问控制策略的细节；本 skill 管辖分支保护与代码所有权机制，包括
  必需校验与绕过记录。签名提交要求来自第 1 层的托管平台或组织策略。
- `testing-and-quality-conventions` 管辖门禁本身；本 skill 管辖受保护分支上必需的门禁，以及可以合并的时点。
- 生成路径、第三方引入路径与机器产出路径免于逐行审查，但不豁免合并规则。应当审查生成器输入、重新生成
  命令与生成标记；手工修改生成产物，在任何情形下均不视为经过审查的变更。
- 历史属于公开记录：仅在策略允许时方可重写。可以 amend 未发布的提交；仅可对个人主题分支带租约强制推送，
  强制推送须取得明确同意；即使内容完全相同，重写受保护分支亦按事故处理。不触发发布、部署或 Release 的
  非保护分支推送属计划级；触发上述动作的推送、推送至受保护或共享分支、删除远端分支均须逐次明确同意。
- 仅存在于审查者记忆中的规则，不构成规则。分支模型、合并方式、审查深度与所有权，应当记录于贡献者指南或
  所链接的策略文件中，并在变更做法的同一次变更中更新。
- 同一效力层级的强制规则冲突时报告用户裁决，不得自行选定；非强制的项目约定冲突，说明冲突与所选约定，
  记录于分支模型旁，使下一次变更遵循该决定。
- 单人仓库、trunk-based 与无 PR：直接提交主干属于合法模型，此时审查由自查与必需 CI 替代；CODEOWNERS
  仅有一条通配条目的，仍可以合并，但必须在治理文件中记录该单点。

## 生命周期定位

上游输入是 S1 的分支模型取舍与 G2 的范围、审查者与合并方式；本 skill 在 S3 执行分支、PR、审查与合并，
在 S4 提供独立审查与批准证据，在 S5 核对发布分支与发布标签的保护。合并与标签证据交给发布门禁与仓库治理
角色；缺少审查、必需校验或所有权证据时停在 G3/G4；分支模型与发布路径不符时回到 G2 重新选择；需要重写
受保护分支、移动发布标签或绕过保护时升级用户裁决。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S2 计划 | 选择分支模型、合并方式、审查级别、保护集合与所有权边界 | 分支策略、规则集配置、CODEOWNERS 草案 |
| S3 构建 | 控制分支寿命与体量，准备 PR，按风险分派审查，按依赖顺序合并 | PR 记录、审查结论、合并提交 |
| S4 验证 | 保证批准有效、校验在合并结果上通过、阻塞线程已解决 | 批准记录、必需校验输出、过期批准处理 |
| S5 发布 | 保护发布分支与发布标签，确认热修复经审查并向前移植 | 标签规则、热修复 PR、合并证据 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 计划 | 分支模型与每类合并方式、审查级别表、保护清单、所有权映射 | Recycle 至设计，补齐模型 |
| G3 构建 | 体量合规的 PR、描述与自审、必需校验在合并结果上通过 | 退回修改，不得合入 |
| G4 验证 | 归属团队批准、阻塞评论已解决、批准未因推送过期 | Hold，重新审查增量 |
| G5 发布 | 发布分支保护、标签规则、热修复已向前移植 | 停止打标签与发布 |

G2 的模型或保护与发布路径冲突时 Recycle；G3/G4 证据缺失时 Hold；保护无法启用且无补偿检查时 No-Go。绕过
记录须写明操作者、原因、被绕过的规则与合并后审查；无记录的绕过按事故处理。决定语义与批准角色见
`project-lifecycle-governance`。

## 工作流

1. 确认当前状态：阅读平台的分支设置、合并方式、CODEOWNERS、CI 配置、贡献者指南与最近二十次合并提交。
   无法读取平台设置或 API 的，记录缺口，以仓库内策略文件为准并请求有权限者核对，不得猜测设置值。
2. 从分支模型矩阵中选择或确认模型并记录：分支类别、生命周期上限、每类合并方式、发布路径、热修复路径与
   标签策略。
3. 开启分支前估算变更体量。每个分支仅保留一个逻辑变更；超出体量预算的拆成堆叠分支或以功能开关隐藏，并
   按合入顺序链接各部分。
4. 准备 PR 或 MR，写明标题、描述、关联 issue、风险级别、验证证据与自审结果；仅在必需校验与模板均已完成
   时标记为就绪。
5. 按所有权与风险分派审查：请求归属团队与风险级别所要求的领域审查者，并在请求中写明审查深度。
6. 依规定路径合入：配置了合并队列或自动合并的应当使用；否则在合并结果上全部必需校验通过后，依该分支
   类别的方式合并，然后删除主题分支。
7. 定期审查：确认已合入，核实部署或发布路径，审查绕过记录，并在下一次变更之前修复 CODEOWNERS 覆盖、
   过期批准与保护漂移。

## 核心规则

- **每个分支类别仅使用一个模型。** 分支模型在贡献者指南中写明并在平台强制执行；混用主干合并、发布分支
  合并与热修复 cherry-pick 的历史，没有审查者能够还原。
- **分支生命周期应当短，体量应当小。** 分支在三个工作日内集成，可审查 diff 保持约 400 行改动以内；
  400 至 800 行的按 `references/playbooks.md` 的体量例外记录设计说明与第二名审查者；存续更久的分支每日
  变基；无法拆分至开关之后的变更属于设计信号，不构成例外。
- **主分支始终可发布。** main 上的每个提交均应能够构建、通过必需门禁并可部署；main 失败会阻塞全部合并，
  其优先级高于新功能工作。
- **每个分支类别仅使用一种合并方式。** 功能分支压缩合并进主干，发布晋级使用合并提交，仅对未共享的分支
  变基；同一类别混用方式会使 blame、bisect 与 revert 不可靠。
- **公开历史仅可追加。** 不得重写他人已在其上开展工作的提交；已发布的错误以 revert 或后续提交修复，
  带租约的强制推送仅用于个人主题分支。
- **审查深度取决于风险，而非审查者是否有空。** 按影响范围分为轻量、标准或高风险；认证、支付、权限、
  数据迁移与公共接口适用高风险路径并配置第二名审查者。
- **每项变更均须经过审查与必需校验方可合入。** 受保护分支要求批准审查，且合并结果上的必需校验全部通过；
  实质性推送之前的批准已过期，必须重新取得。单人仓库或无第二人的，必需批准设为 0，以自审记录与必需 CI
  替代，自审记录写明检查项与结论并作为已知缺口上报。
- **默认保护，绕过即事故。** 受保护分支要求审查、校验与合并方式所需的线性历史，并禁止强制推送；每次
  管理性绕过记录操作者、原因与合并后审查。
- **CODEOWNERS 为每条可合并路径指定真实所有者。** 没有所有者的路径属于带期限的缺陷；回退所有者应为平台
  或仓库维护者团队，不得为下一个编辑该路径的人。
- **门禁在合并结果上运行，而非仅在作者副本上运行。** 合并队列或预合并任务针对基线测试变更；本地通过不足
  以替代必需校验。
- **GitHub 规则集是默认保护机制。** 分支与标签保护使用规则集：阻止强制推送与删除、要求 PR 与批准、使过期
  批准失效、要求最近一次推送的批准、要求代码所有者审查与对话解决，并把必需校验设为合并条件。规则集与
  旧式保护叠加时最严格者生效；绕过列表仅保留紧急通道，按次记录操作者、原因、被绕过规则与合并后审查。
- **合并队列在合并结果上验证。** 主干合并量大时启用合并队列；必需工作流必须同时响应 `pull_request` 与
  `merge_group`，队列失败修复后重新入队，不得重试同一结果。自动合并仅在必需批准与校验齐备时启用，冻结
  或事故期间禁用。
- **签名提交是策略，不是身份证明。** 平台或组织要求签名时使用 GPG、SSH 或 S/MIME 并启用 vigilant 模式，
  由规则集强制；网页与 API 提交由 GitHub 签名，不证明作者身份；本地钩子仅作早期提示。
- **fork 与工作流变更适用最小信任。** fork 的 `pull_request` 构建只获得只读令牌且无仓库机密；不得在
  `pull_request_target` 或 `workflow_run` 中检出并执行不可信代码。工作流、复合 action 与 CODEOWNERS 的
  变更由平台团队审查；发布与部署机密仅在受保护环境批准后可用。
- **机器人执行门禁，人实施判断。** 构建、测试、lint、类型校验、机密扫描与文档构建由 CI 强制执行；人工
  审查负责正确性、设计取舍、安全语义、测试充分性与文档影响。可判定的项必须自动化，判断性的项必须由人实施。
- **每条审查评论带严重级别与明确要求。** 评论标记为阻塞、非阻塞、Nit 或需要回答的疑问，作者以回复或关联
  修复解决每个阻塞线程；沉默不构成同意。前缀与响应时限见 `references/lifecycle.md`。
- **草稿视为未就绪。** 为尽早反馈而开启草稿的，仅在描述、证据与自审均完成后标记就绪；草稿不进入合并审查，
  亦不被合并。
- **删除已合并分支，冻结发布标签。** 合并后删除主题分支，使分支列表反映未完成工作；不得移动、删除或重建
  已发布的发布标签，因为已发布制品指向该标签。
- **所有权变更与代码同等接受审查。** 授予或移除所有权的 CODEOWNERS 修改需要维护者审查，并在独立请求中
  合入；批准要求由 `repository-governance-conventions` 的治理规则裁定。单人仓库改为自审记录与必需 CI；
  存在第二人的，所有者不得批准扩大自身权限的变更。

## 分支模型矩阵

选择满足发布流程的最轻模型；模型决定合并方式与热修复路径。

| 模型 | 团队与仓库规模 | 合并方式 | 发布路径 | 适用场景 |
|---|---|---|---|---|
| 主干开发，无发布分支 | 2 至 15 名工程师，一个可部署服务 | 压缩合并到主干；变基主题分支 | 持续部署；发布即主干上的一个标签 | 持续交付、功能开关、强 CI |
| 主干开发，带发布分支 | 15 至 100 名工程师，多个部署目标 | 压缩合并到主干；到发布分支用合并提交；热修复 cherry-pick 到两边 | 冻结时切出，给发布提交打标签，在分支上热修复并向前移植 | 版本化发布，或客户固定使用某一版本 |
| GitHub flow | 2 至 30 名工程师，一个生产环境 | 压缩合并或合并提交，全仓统一一种 | 合并到 main，从 main 部署 | 刚建立审查实践的小团队；无需运行发布列车 |
| 发布列车分支 | 30 至 200 名工程师，按计划发布 | 晋级用合并提交；小修复用压缩合并 | 候选发布分支、资格验证，然后打标签；修复 cherry-pick | 受监管的发布节奏、长时间 QA 与多个受支持版本 |
| GitFlow | 10 至 100 名工程师，交付或安装型软件 | 带 `--no-ff` 的合并提交；热修复分支 | `develop` 集成，`release/*` 稳定化，`main` 保存带标签的发布 | 有支持窗口的桌面或本地部署软件 |
| Fork-and-pull | 公开仓库，贡献者数量不限 | 维护者快进或压缩合并已审查分支 | main 承载发布；标签与说明予以公告 | 开源项目，或无写权限的不可信贡献者 |
| 按版本维护分支 | 5 至 50 名工程师，支持多个发布 | 压缩合并到维护分支；晋级用合并提交 | 每个受支持版本一个分支；修复 cherry-pick 并向前移植到主干 | 小团队运营的长期支持窗口 |

两种模型均适用的，选择较轻者，并在一个发布周期后重新评估；较轻指需要维护的分支类别更少、每类仅一种合并
方式、发布与热修复路径更短。选择、日期与下次审查的触发条件记录于贡献者指南。

## 反模式

| 反模式 | 为什么失败 | 修复 |
|---|---|---|
| 长期功能分支 | 与主干漂移，冲突增长，集成风险延迟暴露 | 拆成堆叠请求或置于开关之后，每日集成 |
| 同一分支类别混用合并方式 | blame、bisect 与 revert 不再对应审查历史 | 每类选择一种方式并在设置中强制执行 |
| 对共享分支强制推送 | 抹除同事的提交与审查评论锚点 | 仅在个人分支带租约推送；已发布错误用 revert |
| 不阅读 diff 即批准 | 将合并门禁变为仪式，掩盖缺陷 | 要求与风险相称的证据并审查自审清单 |
| 将重命名、格式化与行为变更混于一个请求 | 无法作为同一单位审查，也无法单独回退 | 隔离机械性改动，行为变更单独合入 |
| 必需校验仅作建议 | 校验失败仍可合并，信号仅具装饰作用 | 将校验标为必需，失败即拒绝 |
| 将可判定校验留予人工重复 | 审查者被 lint 与格式淹没，遗漏正确性问题 | 可判定项自动化，人工只做判断 |
| 提交夹带调试输出或本地配置 | 历史受污染，本地状态进入共享历史 | 推送前以 diff 与 status 自检，敏感内容立即删除 |
| 以“就这一次”直接推送 main | 绕过审查与门禁，其后成为先例 | 默认拒绝；仅授予有记录、有时限且经事后审查的例外 |
| 校验或描述未完成即标为就绪 | 审查者把时间用于无法合并的请求 | 就绪意味着校验通过、描述完整且自审完成 |
| CODEOWNERS 仅有通配回退 | 路径所有者始终未被通知，孤儿路径长期隐藏 | 为每条路径指定真实团队并审查覆盖 |
| 审查评论无严重级别或要求 | 作者无法区分阻塞项与可选项 | 添加 `must:`、`should:`、`nit:` 或 `q:` 前缀 |
| 绕过合并队列实施合并 | 最终合入的是未经测试的合并组合 | 由队列决定顺序，修复后重新入队 |
| 移动发布标签以纳入新增修复 | 已发布制品与标签不再匹配 | 自修复提交切出新的补丁版本 |
| 实质性推送后批准仍被视为有效 | 审查者批准的代码已不在请求中 | 推送时使过期批准失效并重新审查增量 |
| 所有权文件由新所有者自行编辑 | 未经维护者审查即自我授权 | 在独立的、经维护者审查的请求中审查 |
| 将 CI 凭据暴露给来自 fork 的 PR | 外部贡献者能够读取生产凭据 | 凭据不进入不可信 fork 构建，不打印到日志 |

## 审查清单

- [ ] 分支模型、每类合并方式与热修复路径已写入文档，并与平台设置一致。
- [ ] 变更为体量预算内的一个逻辑单元，或其堆叠顺序已有文档。
- [ ] 标题说明结果，描述说明问题、做法、风险与验证证据。
- [ ] 请求链接其应关闭的 issue，并列出推迟的后续工作。
- [ ] 校验通过、自审完成之前，请求保持草稿状态。
- [ ] 必需校验在合并结果上通过，而非仅在作者最后一次推送的提交上通过。
- [ ] 审查者的选择与归属路径及风险级别匹配，并包含归属团队的批准。
- [ ] 每条阻塞评论均通过回复或关联修复得到解决。
- [ ] 批准仍然有效；批准后的实质性推送已触发重新审查。
- [ ] 合并方式与分支类别匹配，合入后的历史保持清晰可读。
- [ ] 未对受保护分支强制推送；任何强制推送均为个人分支上的带租约推送。
- [ ] 保护设置依策略要求审查、校验与线性历史，规则集覆盖默认分支与发布标签。
- [ ] 绕过列表仅有紧急通道，且每次绕过均已记录与复审。
- [ ] fork 工作流使用只读令牌且不执行不可信代码；工作流与 CODEOWNERS 变更经平台团队审查。
- [ ] CODEOWNERS 覆盖每条变更路径，回退所有者能够解析，生成路径归生成器所有者。
- [ ] 生成文件与第三方引入文件已重新生成，标记与生成器输入均已审查。
- [ ] 热修复已依热修复路径实施，并已向前移植至主线。
- [ ] 已合并分支已删除，已发布的发布标签未变更。
- [ ] diff、描述、评论或 CI 日志中未出现机密、令牌或个人信息。
- [ ] 合并后验证（部署、健康检查、发布说明）已计划或已完成。
