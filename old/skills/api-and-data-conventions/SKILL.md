# 接口与数据规范

API 契约与数据库 schema 是系统中生命周期最长的接口：外部调用方据其构建，背后的数据会累积多年。
改字段会让作者看不见的客户端失效；删列、未分批的迁移，或让每个写入者排队的锁，都会导致数据丢失或服务中断。
这些后果都不是回滚代码能修复的。
本 skill 规定 API 契约的设计、审查与变更方式，数据库在不中断服务前提下的演进方式，以及数据在生命周期结束后的退役方式。
读者是新端点或新迁移的作者、评判 schema diff 的审查者，以及规划废弃或擦除路径的工程师。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。
   HTTP 语义、所用 IDL（OpenAPI、protobuf、GraphQL）、数据库引擎的行为以及数据保护义务，都不是可选项。
2. 本 skill 的规则。
   契约设计、演进、迁移与数据保留的规则，以本文件与 `references/` 为准。
3. 既有项目约定与事实。
   智能体应当先阅读当前 API 版本、迁移工具、错误码目录、已发布的兼容性策略与支持窗口；这些是事实输入，按本 skill 的规则处理。
   项目约定只在本 skill 未规定时补充，不得覆盖本 skill。
4. 个人偏好不得覆盖上述三层。

分工边界如下：

- **名称由 `naming-conventions` 管辖。** 该 skill 管辖资源、字段、表、列、索引与枚举的名称；本 skill 管辖围绕这些名称的契约与流程，不得重命名该 skill 管辖的名称。契约变更需要新名称的，应当向该 skill 索取，不得另造第二套词汇。
- **独立文档由 `documentation-conventions` 管辖。** 该 skill 管辖 API 参考页与其他页面；本 skill 管辖这些页面所描述的设计规则，页面应当随契约一并更新。
- **发布运维由 `release-operations-conventions` 管辖。** 该 skill 管辖产品版本化、发布流程与 CI/CD；本 skill 管辖契约内部的 API 版本化策略与 schema 变更的安全性。
- **测试策略由 `testing-and-quality-conventions` 管辖。** 该 skill 管辖测试策略与门禁；本 skill 管辖作为要求的契约测试，不管辖运行这些测试的工具。发布期间无人运行的契约测试只是注释。
- **隐私策略由 `security-compliance-conventions` 管辖。** 该 skill 管辖数据清单、PII 分类与保留期；本 skill 使用该清单，并管辖执行事项，包括 schema 元数据、删除传播、备份到期与测试数据处理。
- **生成接口面与第三方接口面属于例外。** 生成的客户端与服务端、第三方引入的 schema 以及外部 API 应当保持其形态；应当把它们隔离在适配器之后，在边界映射到规范契约，并重新生成，不得手工编辑。
- **影响评估默认按破坏性处理；经证明并非破坏性的不在此限。** 证明是消费方清单加上针对真实客户端的契约测试；缺少字段被使用的证据，不等于该字段未被使用。
- **强制规则冲突的，应当报告用户裁决，不得自行选定；非强制的项目约定冲突，可以说明冲突与所选约定。** 所选约定应当记录于契约或 ADR，使下一次变更遵循该决定。
- 生命周期：契约与数据设计主责 S2 计划（G2），随增量在 S3 构建（G3）与 S4 验证（G4）出证据；销毁性迁移在 S5 发布阶段执行，其证据并入 G5。阶段与门禁由 `project-lifecycle-governance` 裁定。

## 生命周期定位

上游输入：G1 确认的范围与结果指标、`security-compliance-conventions` 的数据清单与威胁模型、`performance-conventions` 的查询与索引目标、`testing-and-quality-conventions` 的测试策略。数据清单或性能目标缺失时，保留期与索引取舍只能记为未决风险。

下游交接：契约文件与生成物交 `code-style-conventions` 排除于格式化、交 `documentation-conventions` 同步参考页；迁移与回填步骤交 `release-operations-conventions` 执行；契约 diff 校验与契约测试交 `testing-and-quality-conventions` 纳入 CI。

升级与停止：消费方清单不完整、销毁性变更缺少经过验证的恢复点、版本边界与项目承诺冲突时停止实施，报 Hold 或 Recycle 到 S1/S2；两项强制规则冲突时报告用户裁决。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S2 计划 | 定义 IDL、错误模型、分页与幂等契约、授权边界与 schema 形态；确定两步增量或版本边界 | 契约 diff、消费方清单、迁移与回滚方案、锁估算、保留与删除路径 |
| S3 构建 | 按 expand-contract 阶段实现，生成物由 IDL 重生成，契约测试随增量编写 | 可运行增量、生成 diff 为空、契约测试、分批回填脚本 |
| S4 验证 | 以前一客户端版本验证兼容性，在生产规模数据上验证锁与延迟，逐存储验证删除传播 | 契约测试输出、锁与复制延迟数据、约束验证查询、删除回执 |
| S5 发布 | 复核销毁性迁移的批准、备份与试运行计数；迁移作为独立步骤执行 | 批准记录、恢复点、试运行计数、变更后验证查询 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 计划 | 契约 diff、消费方清单、两步增量或版本边界的声明、迁移与回滚方案、生产规模锁估算、每个新字段的保留与删除路径 | Hold：消费方清单或恢复点缺失；Recycle 到 S1：版本策略与支持窗口冲突 |
| G3 构建 | IDL 与实现一致的 CI 输出、生成物重生成后 diff 为空、增量测试与契约测试、回填脚本的幂等与游标 | Recycle 到 S2/S3：手工编辑生成物，或破坏性变更未走两步增量 |
| G4 验证 | 前一客户端版本的契约测试、双跑结果、锁与复制延迟数据、约束验证查询、删除传播的逐存储回执 | Hold：兼容性未测或删除传播未验证；No-Go：销毁性变更无经过测试的恢复路径 |
| G5 发布 | 迁移独立执行的记录、已验证的备份或时间点恢复点、试运行计数、变更后查询、销毁性变更的逐次明确同意 | Hold 或取消发布：批准缺失或恢复点未演练；不得以部署代替迁移步骤 |

## 工作流

1. 识别契约接口面与受影响的数据（G2 入口）。
   识别操作、请求与响应字段、事件、表、列、索引与派生存储，并映射每个消费方，包括移动客户端、合作伙伴、仪表盘、导出与分析任务。
   清单不完整时先补全；未列出的消费方会成为未来的中断。
2. 检查当前版本与兼容性策略（S2）。
   检查已发布的版本、记录的支持窗口、相邻字段的废弃状态，以及产生当前 schema 的迁移历史。
3. 选择增量式或破坏性（S2）。
   契约允许的，以两个可部署步骤完成；无法两步完成的，才引入版本边界。优先扩展加废弃窗口，避免同时切换；无法描述两步路径的视为尚未准备就绪。
4. 编写带回滚的迁移与发布计划（G2 证据）。
   计划载明 schema 阶段、回填批次、部署顺序、功能开关状态、验证查询，以及每一步的前向修复或恢复路径，并写明执行者、观察者与有权叫停者。
5. 以契约先行实现（S3）。
   实现与生成物由 IDL 产生；每个阶段独立部署，至读取切换为止均可回滚，数据库写入属于生产变更，按授权级别取得同意。
6. 针对真实客户端与数据验证（S4）。
   以前一客户端版本运行契约测试，在生产规模数据上规划语句，重放真实请求样本，确认旧客户端在双跑期间仍可工作；无法测试的客户端记录为未验证的兼容性风险。
7. 更新文档与示例（G3/G4）。
   更新 IDL、错误码目录、API 参考交接、迁移指南、变更日志与代码示例；迁移指南面向调用方，无示例的契约变更不构成完整变更。
8. 审查并提交门禁证据（G3–G5）。
   运行“审查清单”与 `references/checklists.md` 的工作表，取得所需审查者，为销毁性变更与破坏性变更记录批准，并确认回滚路径经过测试而非假定。

## 核心规则

- **已发布的契约是唯一真源（S2）。** IDL、schema 与错误码目录应当如代码一般审查；与上述内容不一致的实现属于缺陷，应当于同一次变更中修复，不得记录为例外。过期的生成制品应当重新生成，不得手工修补。
- **GitHub 托管仓库的破坏性变更由契约 diff 在合并前检出（G2）。** 仓库中的 IDL 是唯一真源，生成的客户端、服务端桩与参考页由它产生，
  生成物差异以 `git diff --exit-code` 在 CI 失败；OpenAPI 以 `oasdiff breaking`、protobuf 以 `buf breaking` 对比
  已发布基线，检查名称与运行方式归 `testing-and-quality-conventions`，不得以人工比对替代。
- **实施方案默认增量，破坏性变更须经决策（S2）。** 影响评估按破坏性处理；可以自由新增可选字段、操作与错误码；删除、重命名、变更类型或新增必填项，需具备两步增量路径（无法两步完成时则为版本边界）、废弃窗口与已测量的使用量。被废弃的字段在移除日期之前应当保持受支持、有文档且有测试。
- **契约变更包含其消费方（S3）。** 本仓库内的客户端、生成的 SDK、契约测试、示例与文档应当于同一次交付中更新；本仓库之外的消费方，只提供契约与迁移说明并协调切换，不得假定可更新，也不得要求修改其他仓库。仍能工作的旧客户端应当经测试确认。
- **机器读取错误码，人读取消息（S2）。** 错误码保持稳定、唯一且永久；消息保持安全且可变更；字段级细节置于结构化对象的 details 列表，不得置于客户端会解析的字符串。错误码目录属于发布制品，按新增方式增长；该目录是开放枚举，客户端必须容忍未知 code。
- **每个可能被重试的写入均具有幂等契约（S2/G4）。** 键的作用域、存储的响应、TTL 与重放行为均应当明确规定并测试；不得假定客户端不实施重试。
- **重试仅适用于安全操作或幂等操作，并应当采用指数退避（S2）。** 客户端仅应自动重试幂等写入与安全读取，采用指数退避加抖动，并设定最大次数与总超时；429 按 `Retry-After` 重试；500 仅在带幂等键时可重试；502 与 503 亦须限安全或幂等操作；4xx（除 408 与 429）不重试。服务端以幂等键与 429 使重试安全且有界。
- **集合应当有界、有序且可重复（S2）。** 强制最大页大小、确定性排序与允许列表过滤条件，并确保请求路径上不存在无界导出。同一 API 默认一种分页风格；小型稳定集合需 offset 的，必须在契约中记录为例外，且同一操作不得混用两种风格。
- **授权按对象检查，不按路由检查（S2/G4）。** 租户与所有者应当来自已验证的令牌；401、403 与 404 应当遵循一套有文档的存在性策略。在检查对象之前即返回数据的端点，属于带有测试套件的数据泄露。
- **长时间工作与事件投递属于设计内容，不得临时拼凑（S2）。** 长操作返回 202 与状态资源；事件属于至少一次投递，携带 ID 与 schema 版本，并具有去重、签名、重试、死信与重放路径。
- **版本化与废弃应当有意识地进行（S2）。** 版本化在发生变化的边界处实施：公共 API 用主版本路径段，协调发布的内部 IDL 用增量演进，仅当每一跳均保留媒体类型时方使用媒体类型。废弃时提供替代方案、`Deprecation` 与 `Sunset` 头、迁移指南，以及按调用方统计的使用量。
- **schema 变更先扩展，再收缩（S3）。** 新增结构、双写、回填、校验、切换读取，然后移除旧结构。至读取切换为止均可由代码回滚；最后的删除不可逆，需要经过验证的备份或时间点恢复点以及审批门禁。无法在支持窗口内完成的变更应当拆分。
- **执行 DDL 之前应当估算锁（S3）。** 说明锁的名称，设置超时，在生产规模数据上测量，于低峰时段将迁移作为显式步骤运行，并在运行期间观察复制延迟与锁等待。
- **销毁性数据变更需要批准、备份与验证（S5）。** 迁移或回填属于生产写入：取得明确同意，具备消费方清单、恢复点、带计数的试运行，以及变更后查询。
- **每个数据集均有类别、保留规则与负责人（S4）。** 删除应当传播至每个副本；软删除属于保留，不属于删除；备份、日志与导出属于各具到期时间与删除路径的副本。
- **测试应当自迁移构建，并使用合成数据（S4）。** 测试数据库由迁移历史构建，并自上一个发布版本升级；生产数据不得以未脱敏方式进入非生产存储。

## 变更风险矩阵

| 变更 | 兼容性 | 必需路径 | 验证 |
|---|---|---|---|
| 新增可选响应字段 | 兼容 | 加入 IDL，先发布服务端，再发布客户端 | 前一版本客户端通过契约测试 |
| 新增带默认值的可选请求字段 | 兼容 | 记录默认值，接受字段缺失 | 不带该字段的旧客户端 payload 测试 |
| 新增必填请求字段 | 破坏性 | 新版本，或带默认值的可选窗口直至调用方迁移 | 消费方清单与双跑测试 |
| 重命名字段或端点 | 破坏性 | 在别名旁新增名称，双写与双读，废弃旧名 | 移除前旧名的使用量降至零 |
| 移除字段或端点 | 破坏性 | 废弃窗口、停用日期、替代方案与使用量证明 | 客户端测试与按调用方的遥测 |
| 更改字段类型或格式 | 破坏性 | 在旧字段旁新增字段，或新主版本 | 往返测试与消费方测试 |
| 新增非错误码枚举值 | 对封闭客户端是破坏性 | 新版本，或记录容忍未知值的客户端要求 | 以早于该值的客户端构建测试 |
| 更改默认页大小或排序 | 行为破坏 | 公告并版本化，或把旧行为保留在参数之后 | 客户端对顺序与页内容的断言 |
| 新增可空列 | 兼容 | 仅扩展阶段：新增、双写、稍后回填 | 生产规模数据上的迁移；旧代码检查 |
| 新增 CHECK 或外键 | 数据不干净时会阻塞 | 清理数据；PostgreSQL 以 `NOT VALID` 新增，再于独立步骤 `VALIDATE CONSTRAINT`；其他引擎选等价在线 DDL | 违规行查询与锁估算 |
| 新增 NOT NULL | 既有行不满足时会失败 | 回填并校验非空，再设置 `NOT NULL` | 非空校验与锁估算 |
| 新增 UNIQUE | 重复值会使迁移失败 | 并发创建唯一索引，再以该索引添加约束 | 重复值查询与索引构建时长 |
| 删除列或表 | 破坏性且销毁性 | 停止读取，等待废弃期结束，备份，取得批准 | 无引用残留；计数；恢复测试 |
| 在热表上回填或建索引 | 运行风险 | 限流分批或并发构建，避开高峰时段 | 复制延迟、锁等待、总耗时 |

## 反模式

| 反模式 | 失败原因 | 修复 |
|---|---|---|
| 把存储模型暴露为 API | 调用方耦合于表，每次迁移均成为 API 破坏。 | 设计线上契约，并在边界映射。 |
| 将错误消息作为唯一信号 | 客户端对文本实施字符串匹配，消息一经变更即破坏。 | 稳定错误码加结构化 details。 |
| 在变化的集合上使用 OFFSET 分页 | 数据在底层移动时，页将跳过并重复行。 | 带确定性排序的游标分页。 |
| 仅称“客户端应当重试”而无键 | 被重试的 POST 将重复订单或扣款。 | 带存储响应的幂等键。 |
| 以 200 返回错误体 | 网关、缓存与客户端库将其视为成功。 | 正确的 4xx 或 5xx 状态码。 |
| 429 不带 `Retry-After` | 客户端猛烈请求服务，使限流更为严重。 | 带限制头与 `Retry-After` 的 429。 |
| 每个失败均返回 403 | 客户端无法区分重新认证与停止，调试亦变慢。 | 401 表示未认证，403 表示被拒绝，存在性隐藏时用 404。 |
| “以后再版本化” | 客户端增加时兼容性债务将累积。 | 在第一个外部消费方之前设定版本化策略。 |
| 静默扩展枚举 | 穷举式客户端将崩溃或错误处理新值。 | 版本化，或记录容忍未知值的客户端要求。 |
| 在部署流水线中执行大型 ALTER | 锁等待将使每个写入者在它后面排队。 | 显式迁移步骤、`lock_timeout`、并发索引构建。 |
| 编辑已应用的迁移 | 环境产生分歧，历史无法解释 schema。 | 新增后续迁移。 |
| 以一条 UPDATE 完成回填 | 长事务、表膨胀、复制延迟与写入阻塞。 | 带限流的 keyset 分批回填。 |
| 把生产转储恢复到 staging | 个人数据扩散到每台机器与备份。 | 合成数据或不可逆脱敏的数据。 |
| 仅设置标志的删除 | 数据与个人记录以另一名称永久存活。 | 清理任务、过滤读取与保留规则。 |
| “以后可能使用”的保留 | 数据被无限期保存，没有负责人或法律依据。 | 类别、期限、触发条件、负责人与年度审查。 |
| 把速率限制当作并发控制 | 合法重试将失败，正确性依靠运气。 | 幂等、预留或队列。 |

## 审查清单

条目按 G2 → G3 → G4 → G5 排列；未勾选的条目属于未决风险，不得以打勾代替。

- [ ] 契约变更位于 IDL 中，且实现与生成物由该 IDL 产生、在 CI 校验中一致。
- [ ] 破坏性变更由契约 diff 对比已发布基线检出，未以人工比对替代；契约 lint 与 diff 检查同为必需校验。
- [ ] 列出每个受影响的消费方，包括本仓库之外的客户端、仪表盘、导出与分析任务。
- [ ] 声明为增量式或破坏性，并附兼容性策略；破坏性变更具有两步增量路径或版本边界、废弃窗口、迁移指南与支持窗口。
- [ ] 新错误使用稳定错误码、正确的状态码族与结构化对象的 details 列表。
- [ ] 集合有界、确定性有序；同一 API 默认一种分页风格，offset 例外已记录于契约，且同一操作未混用两种风格。
- [ ] 过滤与排序位于允许列表中；热过滤与排序字段的索引需求已按 `performance-conventions` 评估，并在契约中记录索引或接受的成本。
- [ ] 可重试写入具有幂等契约与重放测试；速率限制有文档，并带响应头、429 与 `Retry-After`。
- [ ] 授权为对象级，租户 ID 来自令牌，401/403/404 策略一致。
- [ ] 长操作与事件定义了状态、投递保证、去重与重放行为。
- [ ] 迁移遵循 expand-contract，每个阶段均可独立部署；回填分批、幂等、可重启且限流。
- [ ] 锁影响与持续时间已经在生产规模数据上测量；约束仅在数据满足之后验证。
- [ ] 测试数据为合成数据，测试 schema 由迁移历史构建，并覆盖自上一发布升级。
- [ ] 文档、示例、变更日志与错误码目录在同一次变更中更新。
- [ ] 销毁性变更具有批准、消费方清单、备份与验证查询，且变更具有回滚或前向修复路径。
- [ ] 每个新字段、新表与新集合均具有类别、保留期、删除路径与负责人。
- [ ] 删除传播至搜索、缓存、分析、日志与备份；软删除具有清理任务。

## 示例

<example>
为订单响应新增可选 `tracking_number`：将其加入 IDL，先发布服务端，再发布客户端，并以前一客户端版本针对新 schema 运行。
字段缺失仍属有效状态，因此不需要版本边界；双向验证旧客户端与新客户端。
</example>

<example>
将 `customer_email` 重命名为 `email`：在旧字段旁新增 `email`，同时填充两者，切换读取方，发布带停用日期的废弃通知，并按调用方统计使用量。
仅在使用量降至零后删除旧字段，并提前一个版本公告移除。
</example>

<example>
为大型订单表新增必填 `tenant_id`：先以可空形式新增，部署双写代码，在设置 `lock_timeout` 的情况下按 keyset 分批回填，验证 `NOT VALID` 约束，然后强制 NOT NULL。
每一步均为独立部署并各自具有回滚，回填时长先在生产规模数据上测量。
</example>

<example>
处理擦除请求：于主存储中删除或匿名化行，自搜索索引移除文档，使缓存键失效，排队数据仓库与日志清理任务，并记录结束该流程的备份到期日期。
按存储分别验证，不得仅在数据库中验证。
</example>
