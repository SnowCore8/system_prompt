# 并发与并行规范

并发程序有四类可预见的失效：共享可变状态未经同步就被并发读写，产生时有时无的数据竞争；锁的申请顺序不一致，
两个执行流互相等待形成死锁；用无界复制代替共享，把锁竞争掩盖成性能问题；测试只证明“本次未崩溃”，而竞态具有
概率性。本 skill 规定以“是否可以不共享”为起点的决策流程、同步原语的选择、死锁与活锁的排查，以及让并发缺陷
在测试阶段暴露的手段。

## 适用范围与优先级

效力依下列层级判断：高层覆盖低层，低层仅在高层未规定时补充。

1. 强制性的平台、法律、宿主与全局用户约束。内存模型、语言提供的同步原语、运行时调度器与 CPU 的缓存一致性
   都不是可选项。
2. 本 skill 的规则：共享状态、同步原语、死锁与并发模型、并发测试。
3. 既有项目约定与事实。先读项目的并发文档、既有锁、通道与线程池，以及同步工具类；项目约定仅在本 skill
   未规定时补充，不得覆盖本 skill。
4. 个人偏好，不得覆盖上述三层。

管辖与边界：

- 本 skill 管辖并发正确性：数据竞争、可见性、死锁与活锁；锁竞争的性能诊断与优化归 performance-conventions。
- 通用测试策略、CI 与门禁阈值归 testing-and-quality-conventions；本 skill 管辖并发特有的检测器、压力测试与
  交错覆盖。
- 跨服务重试、幂等键与退避归 api-and-data-conventions；本 skill 只处理进程内共享与同步。
- 锁、通道、协程与任务的标识符命名归 naming-conventions；锁与不变式的注释写法归 comment-conventions，本 skill
  只规定应记录哪些内容。
- 共享可变状态是唯一审查对象：不共享的数据、单执行流数据与不可变数据不适用同步规则，但仍应写明为何可以不共享。
- 同一效力层级的强制规则冲突时报告用户裁决；跨层冲突按全局用户约束处理，并把所选约定记录于并发策略或 ADR。

## 生命周期定位

上游输入来自 S2 的并发模型、共享状态清单与锁顺序设计：哪些数据共享、用何种原语、等待如何超时、如何测试；
下游交接给 S3 的实现与审查、S4 的检测器与压测证据、S6 的事故复盘与回归。

- 升级与停止：新增跨进程共享、修改全局锁顺序或引入新并发模型时退回 G2；无法取得竞态证据时不得声称正确，
  报告覆盖缺口；事故期间按 AU-5 先止损，再补记录。

| 阶段 | 本 skill 的职责 | 产出 / 证据 |
|---|---|---|
| S2 计划 | 确定并发模型、共享状态清单、原语、锁的全序与超时，设计并发测试 | 并发设计说明、锁顺序表、测试与检测方案 |
| S3 构建 | 按原语决策表实现同步，临界区不含回调与 I/O，记录锁与不变式 | 代码与注释、锁顺序记录、检测器运行结果 |
| S4 验证 | 运行竞态检测器与压力测试，排查死锁并说明未覆盖的交错 | 检测器与压测输出、死锁分析、覆盖缺口说明 |
| S6 收尾 | 复盘竞态事故，更新检测器接入、并发文档与回归测试 | 事故根因结论、行动项、回归用例 |

## 门禁与证据

| 门禁 | 必须提供的证据 | 不满足时 |
|---|---|---|
| G2 计划 | 共享状态清单、并发模型、原语选择理由、锁全序与超时、并发测试方案 | 模型或锁顺序未定时 Hold，退回 S1/S2 |
| G3 构建 | 每项共享状态的同步覆盖读写两侧、临界区清单、检测器运行命令与结果 | Recycle 到 S3；无同步的共享写入阻断合并 |
| G4 验证 | 检测器与压力测试输出、死锁排查记录、未覆盖交错与替代验证说明 | 修复或 Recycle；以单次通过冒充证明时按 No-Go 处理 |
| G6 收尾 | 事故根因、复现用例、并发文档与检测器接入的更新记录 | 补齐复盘行动后再关闭 |

证据必须可复核：检测器命令与退出码、压测参数与种子、资源等待图；一次通过不等于正确。

## 工作流

1. 区分并发与并行，列出所有被多个执行流读写的变量、字段与容器；只读共享与单执行流状态注明无需同步。
2. 尽量消除共享：可变状态改为不可变值，或以通道/队列把所有权交给单一所有者，最后才加锁共享。
3. 必须共享时按“保护对象、读写比例、等待还是轮询”选择互斥锁、读写锁、信号量、条件变量或原子操作；加锁覆盖
   读写两侧，锁住整个不变量。
4. 控制锁的粒度与顺序：临界区尽量小，持锁期间不回调、不做 I/O、不申请顺序未知的锁；多把锁按全局偏序申请，
   自第二把起用 try-lock 加超时，并记录锁数与超时。
5. 验证：有运行期竞态检测器的语言运行检测器与压力测试；没有的以压力测试、静态工具与审查替代并记录缺口；
   发现死锁先绘制资源等待图。
6. 记录不变式：把每把锁保护的数据、不变式与申请顺序写入代码与并发文档。

## 核心规则

- **可变状态默认不共享；确需共享的必须具有显式同步。** 可改为不可变值的改为不可变值；否则以消息传递或加锁。
  同步覆盖读写两侧；原子性只保护单个操作，多字段不变量由同一把锁整体保护。
- **锁定的对象是不变量，而非字段。** 一把锁保护一组必须同时成立的字段；任何读写其中一部分的路径都持有同一
  把锁。
- **锁的持有区间应当较小。** 持锁期间不得回调、不得实施 I/O、不得申请顺序未知的锁；外部代码会把锁的顺序与
  生命周期交给它自己决定。
- **多把锁按全局偏序申请。** 自第二把起采用 try-lock 加超时，并记录锁数与超时；无法取得的释放并重试，或者
  超时上报，不得无限等待。
- **可以采用原子操作的，不使用锁；原子操作不保护多个字段。** 单标量读改写用原子类型；涉及两个以上字段或复合
  判断的改用锁。
- **不可变优先，以消息传递减少共享。** 返回不可变值或冻结可变对象；数据只由一个所有者拥有并经通道/队列传递，
  不得由多个所有者共享同一份内存。
- **提供运行期竞态检测器的语言，运行并发测试时必须启用检测器。** Go 用 `-race`，C/C++ 用 ThreadSanitizer，
  Rust 用 Miri 或 Loom；无法覆盖全部测试的，记录覆盖缺口。Java、Python 等无检测器的语言以压力测试、静态工具
  与审查替代并记录缺口。检测器只覆盖已执行的路径。
- **死锁排查先绘制资源等待图。** 把执行流、持有的锁与等待的锁画成图并找环；破环方法为统一顺序、引入超时或
  减少锁的数量。
- **不得以测试通过作为并发正确的证明。** 竞态具有概率性；以压力测试提高交错覆盖率，并说明未能覆盖的交错。
- **并发并非并行的同义词；不得为使用并发而引入并发。** 引入前确定可判定的收益（响应性、吞吐或资源利用），
  先优化算法与数据结构。

## 反模式

| 阶段 | 反模式 | 为什么失败 | 修复 |
|---|---|---|---|
| S2 | 未经同步即读写共享字段 | 构成数据竞争；结果为内存模型允许的任意值，且仅在特定交错下复现。 | 加锁或采用原子类型；或者改为不可变/单一所有者。 |
| S2 | 以单一大锁覆盖整个请求 | 串行化消除并发，锁竞争成为新的瓶颈。 | 缩小临界区，仅锁定不变量。 |
| S3 | 仅锁定写侧，未锁定读侧 | 读取到写入一半的中间状态。 | 读与写持有同一把锁。 |
| S3 | 持锁调用回调或实施 I/O | 锁的顺序交由外部代码决定，可能因反向申请形成死锁。 | 将回调与 I/O 移出临界区。 |
| S3 | 两处代码以相反顺序加锁 | 两个执行流互相等待，形成死锁。 | 按全局偏序申请；自第二把锁起用 try-lock 加超时。 |
| S3 | 无超时地等待锁或条件变量 | 一次等待阻塞整个执行流，死锁或活锁无从恢复。 | 设定超时；原语不支持时采用可取消等待、看门狗或带超时的 select/channel，并记录替代方案。 |
| S3 | 以忙等自旋替代条件变量 | 空转消耗 CPU，且可能形成活锁。 | 采用条件变量/信号量等待，或者退避。 |
| S3 | 在事件循环内实施阻塞 I/O | 阻塞整个事件循环，其他任务全部停滞。 | 交由线程池或异步 API 处理。 |
| S4 | 并发测试仅运行一次，且未启用检测器 | 概率性竞态未被检出；通过结果不构成正确性证明。 | 启用检测器并施加压力测试。 |
| S4 | 以 `-race` 通过作为充分证明 | 检测器仅覆盖已执行的交错。 | 说明未覆盖的交错，并采用压力测试与模型检查。 |

## 审查清单

计划与模型（G2）：

- [ ] 已列出全部共享可变状态；只读共享与单执行流状态已注明无需同步。
- [ ] 并发模型、原语与锁顺序有选择理由；等待均有超时或可取消方案。
- [ ] 并发测试方案写明检测器、压力测试与覆盖缺口。

构建（G3）：

- [ ] 每项共享可变状态均具有同步，读与写两侧均被覆盖；每把锁保护一项已写明的不变量。
- [ ] 临界区仅包含必要操作；持锁期间无回调、无 I/O、无无序锁嵌套。
- [ ] 多把锁按全局偏序申请，自第二把起用 try-lock 加超时，并记录锁数与超时。
- [ ] 单个标量采用原子操作；多字段复合判断采用锁；可以实现不可变或消息传递的未退化为多所有者共享。
- [ ] 事件循环内无阻塞调用；每把锁的数据、不变式与申请顺序已写入代码与并发文档。

验证与收尾（G4/G6）：

- [ ] 提供检测器的语言已运行检测器，并记录命令、测试路径、执行范围与未覆盖缺口；其余语言已记录替代验证。
- [ ] 死锁已通过资源等待图排查；所有等待均有超时或可取消方案。
- [ ] 并发变更具有可判定收益：响应性、吞吐或资源利用存在目标。
- [ ] 事故后的复现用例、检测器接入与并发文档已更新，行动项有负责人与到期日。

## 示例

<example>
多个 goroutine 并发递增同一计数器：`count++` 属于读改写，未经同步即构成数据竞争。
单标量改用 `atomic.AddInt64`；计数器还需与另一字段共同构成不变量的，改用同一把互斥锁保护两个字段。
</example>

<example>
服务中一段代码持有锁 A 后申请锁 B，另一段持有锁 B 后申请锁 A，形成循环等待。
统一为“始终先 A 后 B”的全局偏序；自第二把锁起用 try-lock 加超时，并在并发文档记录锁数与超时。
</example>

<example>
并发测试仅运行 `go test`，未启用 `-race`，且仅运行一次。
改为在 CI 中运行 `go test -race` 并施加压力测试；同时说明检测器只证明已执行的交错不存在竞争。
</example>
