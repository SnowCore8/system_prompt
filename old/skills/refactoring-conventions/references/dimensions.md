# 重构维度

本文件与 `SKILL.md` 配合使用。每一节规定一个重构维度的决策、示例与边界情况。项目约定与事实属于输入；本 skill
的规则优先，项目约定仅在本 skill 未规定时补充。本文件提供默认值与理由。智能体仅应阅读与拟实施重构相匹配的节。

## 1. 重构与修复的判定

判断重构的唯一标准为外部行为是否变更，而非改动规模。

- 可观察行为包括：API 与返回结构、错误语义、输出、副作用与性能特征。任何一项发生变更的，均不构成重构。
- 判定流程：运行既有测试；测试通过仅为必要条件，智能体还应当逐项核对 API、返回结构、错误语义、副作用与性能特
  征是否变更。全部不变的，方构成重构；测试失败或任何一项变更的，属于行为变更，应当使用 fix/feat 并新增或修
  改测试。测试未覆盖当前行为的，应当先补充特征测试；补齐后仍无法判定的，按行为变更处理。
- 既无测试、亦无可对照行为的，应当先补充特征测试锁定现状，再决定属于重构还是修复。
- 提交类型是判定结果，不是判定原因：智能体应当先判定行为，再选择 refactor 或 fix/feat，禁止为使用 refactor 而
  变更行为。

## 2. 安全重构手法

安全手法是每一步均保持等价的变换；手法目录见 `catalog.md`。

- 一次仅实施一项手法。提取方法或类、内联、移动、重命名、替换魔法数，每一项变换单独一步、单独提交。
- 每一项手法均有明确的反向手法（提取对偶内联、重命名对偶重命名），出现问题的，可以逆回。
- 应当优先使用语言或 IDE 提供的自动重构，因为其保证引用同步更新；手工重命名的，应当核对全部引用，包括测试、
  文档、配置与序列化字段。
- 禁止以手工大段重写冒充重构：没有等价步骤即无法验证，出错亦无法定位至单步。

## 3. 小步提交

重构的价值在于每一步可验证、可回滚。

- 单条提交仅含一项手法，diff 中不得出现行为变更。审查者逐条复核等价性，任何一步失败均可单独回滚。
- 每一步之后运行测试，套件保持通过。智能体应当先实施机械安全的步骤，再实施引入风险的结构调整。
- 重构与行为变更、风格迁移、重命名应当分开提交；混在一起的，分提交。
- 提交消息使用 `refactor(scope):` 说明所做手法与理由，不得夹带行为变更；提交拆分的完整规则由
  `vcs-collaboration-conventions` skill 管辖。

## 4. 何时重构与何时不重构

重构由代码异味触发，不由压力触发。

- 触发重构的情形：重复、长函数、长参数列表、数据泥团、开关语句；完整清单与阈值见 `catalog.md`。
- 不实施重构的情形：没有测试覆盖且无法补充特征测试的危险区域；发布冻结窗口；范围蔓延，即顺带改动本次任务
  之外的内容。
- 遗留项目应当分阶段改造：为现有违规建立基线，对每个变更文件执行新结构，并随基线缩小而删除基线；一次性大重
  构必然半途而废。
- 重构与缺陷修复同时出现的，应当先修复缺陷再重构，或先补充测试再重构；两者应当分开提交。
