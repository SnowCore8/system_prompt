# 文档维度：读者与使用

本文件细化 `SKILL.md` 维度索引中的读者与使用部分；节号与索引一致，其余维度见同目录的 `dimensions-*.md`。

## 5. 教程与操作指南

- 教程以动手实践施教：固定前提、编号步骤、一个可工作的结果，不设选择；操作指南面向已掌握基础的读者，回答一项
  任务。
- 二者均应当以结果及时间或难度估计开头，使读者决定是否继续。
- 应当使用读者的词汇与产品真实的 UI 标签；自行创制名称的教程将使读者困惑。
- 到达结果不需要的步骤，应当全部删除；每个多余步骤均为一个额外的失败点。
- 每次发布前，均应当自干净环境测试教程；失效的教程即为失效的第一印象。
- 每个步骤应当原子化，并展示预期结果；无法判断成功或失败的读者将停止操作并提出询问。
- 操作指南应当增加验证步骤与常见失败；读者无法确认之前，任务不构成完成。
- 不得将教学与参考的完整性混同；某一选项位于路径之外的，应当链接至参考。

## 6. 参考与 API 参考页

- 参考应当穷尽且中立：精确名称、类型、默认值、约束、允许值与版本说明，按稳定顺序排列。
- 每个单元（函数、标志、端点、字段）应当各设一条记录；不得将不相关的单元合并至同一表格行。
- 应当对每个端点说明认证、参数、响应 schema、错误码、速率限制与版本。
- API 参考页应当自 IDL/schema 生成，并链接至契约；契约是请求与响应形态的唯一真源，参考页仅是其生成投影。
- 生成的参考页，结构依本 skill，文笔依注释 skill；不得手工复制生成的细节。
- 示例应当最小且可以运行；参考示例展示最小的正确调用，而非整套功能。
- 每个单元应当链接至使用该单元的指南或教程；脱离任务的参考难以应用。
- 参考应当随 API 版本化；未载版本说明的参考页，仅对单一发布正确。

| 好 | 坏 | 为什么 |
|---|---|---|
| `timeout_ms`，整数，默认 `30000`，范围 `1..600000`。 | `timeout`：等待时间。 | 已说明类型、默认值与范围。 |
| 每参数一行，载明类型与默认值。 | 以整段文字描述所有参数。 | 表格便于扫读；段落必须通读。 |
| 最小请求与预期响应。 | 以完整应用遮蔽端点调用。 | 隔离被记录的单元。 |
| 每个变更条目均载版本说明。 | 单份参考覆盖所有版本。 | 读者将套用错误版本。 |

## 11. 故障排查与常见问题

- 应当依读者可以观察到的症状组织，不得依读者尚不知道的原因组织。
- 每个条目应当给出症状、可能原因、修复与预防；已知未修复的缺陷，应当链接至 issue 跟踪器。
- 精确错误文本与版本应当置于标题，以便搜索与浏览器检索。
- 不再适用的条目应当更新或标注过时；仅在无法更新且完成引用核查后删除；载有过时修复的页面，将使读者不信任该页面。
- 常见问题条目应当仅保留用户实际会提出的问题，并按频率排序；常见问题页并非第二套文档。
- 仅出现于旧版本中的错误消息与版本，应当标注日期，或者删除。
- 修复无效的，应当在每个条目结尾给出接下来应当阅读的页面。
- 代码可以实现的，应当自错误消息或 CLI 输出链接至每个条目；读者检索的对象为症状，而非文档树。

## 13. 图表与截图

- 图表应当以可 diff 的文本格式（Mermaid、PlantUML、Graphviz）保存，源文件置于渲染图旁。
- 每张图应当标注范围、版本与日期；未标注的图将被视为当前版本，变更后将误导读者。
- 应当选择读者所需的层次（上下文、容器、组件、时序）后停止；为每个受众各设一张图，将导致无法阅读。
- UI 变化时，应当重新生成截图并裁剪至相关区域；过时截图将与正文矛盾，并让读者仍按旧界面操作。
- 说明应当保留为文本，不得仅置于图片中；图片无法被检索、翻译，亦无法被屏幕阅读器读取。
- 每张图片应当提供说明其内容的替代文本；装饰性图片使用空 alt 属性。
- 大型二进制源文件应当置于主仓库之外，并自页面建立链接。

| 好 | 坏 | 为什么 |
|---|---|---|
| 带版本标签的 Mermaid 代码块。 | 未载日期的白板照片。 | 文本图表可 diff、可修复。 |
| 当前对话框的截图，已裁剪。 | 旧 UI 的截图。 | 截图将被视为当前版本。 |
| 描述图片内容的替代文本。 | 替代文本：“screenshot.png”。 | 服务于检索与屏幕阅读器。 |
| 图表源文件保存于图片旁。 | 仅保存导出的 PNG。 | 图表日后无法编辑。 |

## 14. 链接与交叉引用

- 应当链接至权威页面，不得链接至副本，并以页面标题或动作描述作为链接文字；“点击这里”无法向读者传达任何
  信息。
- 仓库内应当使用相对链接，使其在每个分支与本地预览中均可工作；绝对站点 URL 将在 fork 与预览中失效。
- 应当于文档构建中校验链接，将坏链视为失败，不得视为警告。
- 应当链接至稳定的锚点；标题必须变更时，应当于同一次变更中更新每个入站链接，并在站点支持时添加重定向。
- 同一目标在各页面应当使用相同的链接文字，以便检索与扫读识别。
- 应当采用一条有力的交叉引用，不得使用“另见”列表；十个链接将把决定推回给读者。
- 外部引用应当标注日期，并在来源变更时重新核对；外部页面可能移动或改变含义。
- 不得自页面链接至该页面自身，亦不得在同一屏重复同一链接。

## 15. 导航与文档索引

- 路径应当保持浅层：读者自文档首页经两到三次点击即可到达任何核心页面。
- 应当依读者任务或文档类型（教程、指南、参考、解释）分组，不得依团队或仓库布局分组。
- 应当保留一个索引页，列出每个已发布章节；未列入索引的页面，事实上等同于未发布。
- 导航条目应当依读者可以获得的收益命名，不得采用内部项目名或工单名。
- 侧边栏顺序应当跨发布保持稳定；移动条目将破坏书签与操作习惯。
- 草稿与空页面应当自导航中移除；指向未完成页面的链接，为未兑现的承诺。
- 文档首页应当简短并承担分流：产品是什么、做什么，文档服务对象，以及接下来的三个步骤。
- 添加、移动或删除页面后，应当审查索引；过时导航为文档集过时的首个症状。

## 17. 本地化与翻译

- 源文档应当以短句编写，一句表达一个想法，并将代码、命令、标识符与产品名排除于可翻译散文之外。
- 翻译文件应当置于源文件旁或本地化系统中，并确定一侧为真源；不得手工同时编辑两侧。
- 译文应当随源文版本化；旧页面的译文，即为另一种语言中的错误页面。
- 应当避免特定文化的示例、日期、货币与习语；采用 ISO 日期、明确单位与平实语言。
- 截图应当尽可能保持语言中立；含嵌入文本的图片应当加以标记，以便重新翻译。
- 未翻译页面应当明确标记，不得提供过时译文；错误译文较缺失译文更易被信任。
- 应当为文本膨胀预留空间；德语与日语标签通常长于英语。
- 译文应当由能够运行示例的母语者审查；可用的机器翻译极为罕见。

## 21. 文档测试与示例校验

- 应当于 CI 中运行代码示例：将其置于测试文件，或自页面提取；示例失效时，使构建失败。
- 示例通过的硬标准为：示例命令退出码为 0，且输出与页面粘贴的内容一致。无法于 CI 自动运行的交互式示例或需外
  部凭据的示例，必须标注“未在 CI 校验”并写明手动验证步骤；否则按未验证处理。
- 应当于构建中校验链接、锚点与图片路径；死链校验成本较低，并可以发现最常见的文档失效。
- 应当于干净容器中针对最低支持版本运行命令；需要最新版本的示例，将传授错误的搭建方式。
- 应当以项目词典实施拼写与风格校验；将每个产品术语均标红的校验器，将被停用。
- 每次变更均应当构建文档站，不得仅在发布时构建；运行过晚的构建，将使错误隐藏至最不利的时刻。
- 应当审查表格、代码块与导航的渲染输出；仅审查源文件将遗漏渲染失败。
- 失败的文档校验应当报告为变更中的缺陷；是否阻塞，由门禁负责人 `testing-and-quality-conventions` 决定。
- 校验配置应当置于仓库中，使本地运行与 CI 完全一致。

GitHub Actions 文档校验：

- 文档工作流在 `pull_request`、`merge_group` 与主干 `push` 上运行，顶层权限只读；构建预览制品上传后供审查者
  查看渲染结果，产物保留期覆盖审查周期。
- 构建以警告为错误，链接校验区分内部链接与外部链接：内部死链阻塞合并，外部链接失败先重试一次以排除网络波动，
  仍失败时记录为待修复项，不以忽略规则静默通过。
- 代码示例从页面提取后在最低支持版本上运行；示例需要凭据或交互时标注“未在 CI 校验”并写明手动步骤。
- 拼写与术语校验使用项目词典；每个产品术语均被标红的规则会训练作者忽略输出，应当先修词典。
- 工作流变更由平台团队按 `vcs-collaboration-conventions` 审查，门禁名称与 `testing-and-quality-conventions`
  的必需校验一致。
