# 注释维度

配合 `SKILL.md` 使用本文件。每一节给出一种注释类型或隐患的规则、边界情况与失败模式。项目已有约定或
linter 时，先读它并应用优先级更高的规则；本文件提供默认值与理由。节号与 `SKILL.md` 中的维度索引对应。

## 1. 文档注释与公开 API 契约

- 文档注释是调用方能看到的一切的公开契约：导出函数、类型、方法、协议实现与有文档的配置。
- 契约覆盖签名无法表达的内容：含义、前置条件、后置条件、错误行为、副作用、所有权与稳定性承诺。
- 以一句祈使式或第三人称摘要开头（“Return the invoice total in cents”），只有当调用方需要摘要无法
  承载的上下文时，才加一段正文。
- 不要重述签名。`@param user the user` 什么也没增加；`@param email lower-cased and trimmed` 说明了
  前置条件。
- 把文档注释当作代码：审查它的 diff，与行为变更在同一次变更中更新，公开含义变化时对它做版本化。
- 注明某行为是有意不规定的（“iteration order is not guaranteed”），而不是让读者去推断契约。
- 把实现说明留在私有注释或函数体里；不要向公开契约泄露内部缓存、加锁或字段布局。

| 好 | 差 | 原因 |
|---|---|---|
| `@param email Lower-cased and trimmed; rejects input without a local part.` | `@param email The email.` | 说明了签名无法承载的前置条件。 |
| `@returns 0 when no tax applies; never negative.` | `@returns the tax.` | 写出调用方必须处理的边界情况。 |
| `@throws InvoiceNotFoundError when the id is unknown.` | `@throws Exception on errors.` | 调用方能处理具体类型，而不是兜底异常。 |

## 2. 模块、文件与取值头

- 文件或模块头说明该单元的用途、范围与不变量；它不是写“改了什么”历史或最近修复清单的地方。
- Go 中，包注释紧贴 `package` 上方，以 `Package <name>` 开头，描述整个包；中间有空行会把它分离。
- Python 中，模块 docstring 是文件的第一条语句，说明模块的角色与公开入口。
- Rust 与 C/C++ 中，文件级文档使用 `//!` 或许可证头之后的 `@file` 块；不要在那里重复类型文档。
- 取值或常量头解释该数字的策略或来源（例如“与合作伙伴 API 的上限一致”），而不是字面量本身。
- 头块中不含作者名、日期、被当作变更历史的工单号，也不含装饰性横幅。
- 链接独立的设计文档，而不是复制它；重复文档的头会在两个地方同时过时。

| 好 | 差 | 原因 |
|---|---|---|
| `// Package billing reconciles invoices against the ledger.` | `// Billing package.` | 说明职责，而不是文件夹。 |
| `# Time zone used for every cut-off date in this module.` | `# tz` | 说明该值为什么存在。 |
| `//! Parser for the v2 wire format; see docs/wire-format.md.` | `//! TODO: document module.` | 指向权威来源而不复制它。 |

## 3. 函数与方法

- 每个公开函数、方法与协议实现都要有文档注释；私有辅助函数只有在名称与函数体确实留下空白时才需要。
- 类型无法承载含义时记录参数：格式、编码、范围、可空性、所有权与默认行为。
- 记录返回值的含义与边界情况：为空与缺失、哨兵值、部分结果与顺序保证。
- 记录调用方需要处理的每一种错误，按类型与触发条件说明；不要列出内部且不会外泄的错误。
- 记录副作用（I/O、变更、事件、缓存写入），以及调用是否幂等、可重试或事务性。
- 调用顺序不显而易见时，在正文中放一个示例；示例要保持可运行（见第 11 节）。
- 以“This function...”开头的描述是噪音；直接从动作及其对象开始。

| 好 | 差 | 原因 |
|---|---|---|
| `Read the current balance; the call may block up to timeout_ms.` | `Gets the balance.` | 说明 I/O 与上界。 |
| `Return matched orders sorted by created_at; empty when none match.` | `Returns orders.` | 排序与空状态是契约的一部分。 |
| `Idempotent: a repeat with the same idempotency key returns the first result.` | `Safe to call.` | 说明了真实的重试契约。 |

## 4. 类型、字段、枚举与常量

- 类型的文档注释说明实例代表什么，以及它保证或要求的不变量；字段注释记录类型名称未能说明清楚的部分。
- 枚举成员含义不能从名称看出时，为它写文档；只有线上值与代码名称不同时才写明线上值。
- 字段注释包含单位、范围、null 的含义，以及值是可变的、派生的、缓存的，还是归接收者所有。
- 不要在描述中重复字段名；说明缺失的契约。
- 常量记录其来源与策略：数字从哪来、由谁负责、什么时候可以改变。
- 别名到另一种表示形式的类型要说明边界（“仅用于线上格式”）以及映射发生在哪里。
- 不要在公开类型上记录私有表示（字段顺序、内部缓存、哈希种子）。

| 好 | 差 | 原因 |
|---|---|---|
| `OrderId` 是不透明的：不要解析、排序或显示它。 | `The order id.` | 说明了该表示形式的契约。 |
| `RetryCount` 每次尝试递增，并受 `MaxAttempts` 限制。 | `How many retries.` | 把字段与它们之间的不变量关联起来。 |
| `StatusRefunded` 是终态；不允许再发生状态转换。 | `Refunded status.` | 写出调用方依赖的规则。 |

## 5. 单位、范围、可空性与所有权

- 类型无法强制单位时，在文档注释中按名称里的拼写写明单位：`timeout_ms`、`amount_cents`、`size_bytes`。
- 明确写范围与包含关系：“0 到 100，包含两端”、“起点包含、终点不包含”；绝不依赖读者的假设。
- 把 null、None、nil、undefined 与空定义为不同状态；说明每一种的含义，以及是否可能被返回。
- 在跟踪所有权的语言中记录所有权、生命周期与修改权：谁释放该值、谁可以修改它、允许怎样的别名共享。
- 对于借用或引用的值，说明借用期限，以及调用返回后接收者是否仍持有引用。
- 对于集合，只在顺序有保证时说明迭代顺序；否则声明顺序未指定。
- 数值的舍入、截断与溢出行为属于契约。

| 好 | 差 | 原因 |
|---|---|---|
| `Timeout in milliseconds; 0 means wait forever.` | `Timeout value.` | 单位与哨兵值是契约的一部分。 |
| `Return the slice borrowed from self; valid until the next mutation.` | `Returns a slice.` | 生命周期与别名规则决定安全用法。 |
| `Amount is an integer number of cents; never a float.` | `The amount.` | 表示形式与单位都是显式的。 |

## 6. 副作用、变更、并发与性能警告

- 说明每一个外部可观察的效果：网络、磁盘、数据库写入、事件发送、日志输出、全局状态，以及时钟或随机数
  的使用。
- 说明并发契约：线程安全、需要外部锁、必须在主线程运行，或不可重入。
- 在隐患之前而不是之后警告：在同一条注释中说明条件、后果与必需动作。
- 记录对参数与接收者状态的修改，包括输入集合是被消费还是被保留。
- 性能说明必须可操作且有实测依据：“规则数量达到 n 时为 O(n^2)；规则只编译一次”胜于“慢”。
- 不要记录调用方无法依赖的临时实现细节（特定锁类型、缓冲区大小、线程数）。
- “WARNING”或“NOTE”前缀是真正的标记：留给隐患与令人意外的行为，以免它失去分量。

| 好 | 差 | 原因 |
|---|---|---|
| `// Caller must hold the account lock; this method does not acquire it.` | `// Thread safe.` | 说明了实际的加锁契约。 |
| `// Emits one order.paid event after commit; consumers may see it twice.` | `// Sends event.` | 重复投递会改变消费者设计。 |
| `// WARNING: O(n^2) above 100 rules; precompile in the hot path.` | `// Slow.` | 界限与补救措施让说明可用。 |

## 7. 弃用声明

- 使用工具的标签进行弃用（`@deprecated`、`@Deprecated`、`#[deprecated]`），并用一句话写明替代项与
  迁移方式。
- 写明移除版本或日期，以及跟踪 issue；“很快会移除”不是计划。
- 保持被弃用的符号可用且文档真实；绝不留下已经与事实不符的弃用文档注释。
- 使用可搜索的稳定替代名称；API 形态变化时给出迁移片段。
- 弃用是公开 API 变更：本 skill 负责标签、迁移说明与源码注释；发布说明文档属于
  documentation-conventions，声明的时间与位置属于 release-operations-conventions。
- 不要把内部辅助函数标记为弃用来代替删除它；删除未使用的内部实现。
- 弃用窗口结束时，在同一次变更中移除符号、它的文档注释与它的引用。

| 好 | 差 | 原因 |
|---|---|---|
| `@deprecated Use create_invoice; removed in v3.0 (issue #812).` | `@deprecated` | 写明路径、版本与跟踪项。 |
| `# Deprecated: use Store.put; the old key format is read-only.` | `# Old API.` | 说明替代项与仍保留的行为。 |
| `/** @deprecated Use totalCents; this getter rounds. */` | `/** Do not use. */` | 说明差异，而不只是禁令。 |

## 8. TODO 与计划说明

- TODO、FIXME 或 HACK 是带负责人的承诺。格式为 `MARKER(owner): action and reason`，并附 issue 或
  移除条件。
- 按含义使用标记：TODO 表示计划内工作，FIXME 表示已知的错误行为，HACK 表示有意为之的捷径，NOTE 表示
  上下文，WARNING 表示隐患。
- 绝不留下裸的 `TODO`、`FIXME`、`XXX` 或 `???`；匿名标记是任何审查都无法解决的未跟踪债务。
- 把标记绑定到触发条件：版本、日期或依赖升级，而不是含糊的“以后”。
- 把标记放在它约束的代码旁边；文件顶部的计划说明对阅读该行的人不可见。
- 不再成立的标记是错误注释：工作落地时删除它，绝不打勾了事。
- 扫描工具（todo-tree、issue linter）依赖精确的标记拼写；使用项目配置的风格。

| 好 | 差 | 原因 |
|---|---|---|
| `// TODO(maria): remove the retry shim after gateway v2 ships (#512).` | `// TODO: fix this later.` | 负责人与触发条件让债务可审查。 |
| `// FIXME(maria): negative totals round toward zero; fix before v2.2.` | `// HACK.` | 负责人与期限让修复可审查。 |
| `// HACK(devon): the vendor header requires a trailing space; do not trim.` | `// Weird.` | 负责人加理由说明捷径为何必须保留。 |

## 9. 被注释掉的代码

- 删除代码，而不是把它注释掉；版本控制保留历史，删除也保持可逆。
- 为某个构建变体禁用的代码属于构建系统：功能开关、预处理器条件编译或配置，而不是注释。
- 迁移期间确实需要临时禁用时，标明负责人、工单与到期时间，并加一个到期后会失败的校验。
- 被注释掉的代码会干扰搜索结果与覆盖率报告，并掩盖未使用的导入与废弃 API。
- 不要“以防万一”把调试输出注释掉；改用可配置级别的 logger。
- 审查时，把被注释掉的代码块当作删除请求，而不是风格问题。
- 有意的代码示例只保留在带围栏且有测试的文档示例中（见第 11 节）。
- 自动校验有帮助：在 diff 中标记被注释掉代码的扫描比逐个代码块争论更省事。

## 10. 变更历史与日志式注释

- 版本控制历史就是变更日志；不要在注释中重述它（“2026-03-01：新增重试”、“Sam 修改”）。
- 不要把作者标签、日期或逐行版本标记当作项目历史保留；提交元数据承载这些信息。
- 未来读者需要的理由是现在时的上下文（“供应商拒绝空请求体”），而不是日志条目。
- 强制要求变更头的遗留项目：在既有文件中遵循既有格式，未经项目决定不要在新文件中引入它。
- 除非发布工具会生成并校验，不要在文件头中添加版本号。
- 新决定取代旧决定时，用当前规则替换旧注释；不要在顶上再堆第二行历史。

## 11. 文档注释中的代码示例

- 文档注释中带围栏的示例是可执行的文档：文档工具会编译或运行它，所以它必须在每次构建时通过。
- 使用文档工具识别的语言标记（`python`、`rust`、`ts`）；有意不运行的片段标记为 `text` 或 `console`。
- 展示最小完整设置：导入、必需的 fixture 与贴近实际的值；绝不要调用未写文档的辅助函数。
- 示例是被执行的 doctest 时，精确写明期望输出，包括空白。
- 示例中不要使用机密、个人数据或生产 URL；使用 `example.test.invalid` 这类假值。
- API 大到无法完整演示时，只展示一次调用，并链接独立指南，而不是给出不完整的片段。
- 保持输出跨平台稳定：工具允许时，避免时间戳、随机 ID 与绝对路径。

## 12. 生成代码与第三方引入代码的标记

- 绝不要手工编辑生成文件；修改生成器或事实来源，重新生成，并连同其标记一起提交输出。
- 将工具生成的标记按原样保留在顶部（“Code generated by ... DO NOT EDIT.”）；工具与审查者依赖它。
- 生成的文档注释属于生成器的模板；修模板，而不是修实例。
- 引入的第三方代码逐字保留其上游注释、头与许可证；在文件之外记录版本与本地补丁集。
- 本地补丁无法避免时，保持最小、带补丁说明，并由引入流程重新应用。
- 从注释密度与风格校验中排除生成路径与引入路径；它们不是审查对象。
- 生成文件中与生成器矛盾的注释是生成器的缺陷；修来源。

| 好 | 差 | 原因 |
|---|---|---|
| `// Code generated by sqlc. DO NOT EDIT.` | `// Generated, but tweak the types here if needed.` | 任何手工编辑都会在下次运行时丢失。 |
| `// Patch: upstream v2.3.0; our fix tracked in issue #644.` | `// Modified.` | 写明基线与被跟踪的差异。 |
| `// Source: schema.sql; regenerate with make gen-db.` | `// Auto.` | 给出生成器与命令。 |

## 13. 法律与许可证头

- 把许可证头精确放在许可证工具或项目策略要求的位置：通常是文件开头几行，在导入与文档注释之前。
- 使用项目标准形式的 SPDX 标识符，例如 `SPDX-License-Identifier: Apache-2.0`；不要改写许可证文本。
- 保留原始权利人的版权行；添加贡献者行遵循项目策略，而不是个人偏好。
- 绝不删除或重排引入代码中的第三方头；保留声明并添加项目的 NOTICE 条目。
- 让许可证工具（reuse、licensee、addlicense、某个格式化插件）写入并更新头；绝不手工拼装变体。
- 法律声明头不能替代许可证文件；链接完整文本，而不是把它粘贴进每个文件。
- 删除头是法律与构建层面的变更；它需要项目所有者决定，而不是一次清理。
- 生成文件从生成器模板获得头；修模板，而不是逐个修输出文件。

## 14. 工具指令

- 指令是给机器读的代码：精确匹配工具的语法与范围，并放在工具读取它的位置。
- 使用能起作用的最窄范围：先一行，再一个函数，再一个文件；绝不要为修一个位置而在仓库范围禁用规则。
- 始终按工具支持的形式给出理由（ESLint 用 `-- reason`，其他工具用邻近注释）；没有解释的抑制无法审查。
- 抑制不是修复：文件级抑制还要留下清理工单，说明何时可以移除。
- 指令家族：禁用 lint（`eslint-disable-next-line`、`# noqa`、`//nolint`、`@SuppressWarnings`）、
  关闭格式化（`prettier-ignore`、`# fmt: off`、`clang-format off`）、忽略覆盖率
  （`pragma: no cover`）、忽略类型（`@ts-expect-error`、`# type: ignore`）。
- 语言支持时，优先用注解或属性而不是注释；配置属于配置文件，而不是某次调用旁边。
- 什么都不抑制的过时指令是死重；在它掩盖下一条真实违规之前删除它。

| 好 | 差 | 原因 |
|---|---|---|
| `// eslint-disable-next-line no-console -- CLI output is the product.` | `/* eslint-disable */` | 范围与理由都是显式的。 |
| `x = stub.field  # type: ignore[attr-defined]  # vendor stub lacks it` | `x = stub.field  # type: ignore` | 代码与理由都写明了。 |
| `//nolint:errcheck // close error is reported by the caller` | `//nolint` | 只禁用被理解的那条规则。 |

## 15. 测试与 fixture

- 测试注释说明场景以及该用例为什么存在（回归、边界、契约），而不是调用了哪些方法。
- 在测试名称中写明行为；注释用于说明行为为何重要，以及指向缺陷或决定的链接。
- 解释不显而易见的安排：fixture 为什么大、时钟为什么冻结、为什么预期会重试。
- 只有当期望值需要说明出处时才注释断言（“与账本的舍入规则一致”）。
- 跳过与预期失败的理由写在框架的理由字段或旁边的注释里；没有解释的跳过是静默删除。
- fixture 数据注释说明场景，绝不含真实个人数据；使用假值，存在生成器时注明生成器。
- 不要把失败的测试注释掉；修复它，并针对任何跳过、隔离或豁免处置遵循
  testing-and-quality-conventions。

## 16. 配置与基础设施

- 每种格式有自己的注释语法与持久化规则；使用语言矩阵，而不是源语言的语法。
- YAML 与 TOML 使用 `#`；把注释放在它所解释的键上方，绝不放进带引号的标量内部。
- Dockerfile 注释用 `#` 放在指令上方；续行指令内部的整行注释会被解析器删除，而命令文本后同一行的
  行尾 `#` 属于 shell 命令。
- SQL 迁移带有注释头，写明工单、意图与回滚说明；已应用的迁移不可变，所以修正以新文件到来。
- Terraform 与 HCL 使用 `#`；把持久的解释放进 `description` 属性，让 `terraform-docs` 带走它。
- 基础设施注释说明某个设置为什么存在、缺少它时什么会坏；不要重述取值。
- 绝不在配置注释中放凭据、令牌、账号标识符或内部主机名；改为引用机密存储。

| 好 | 差 | 原因 |
|---|---|---|
| `# Keep 1 replica during the backfill; the writer serializes.` | `# replicas = 1` | 解释临时约束。 |
| `-- 20261114_add_status: add status for audit; rollback drops it.` | `-- migration` | 意图与回滚可见。 |
| `variable "ttl_days" { description = "Retention; 0 disables expiry." }` | `description = "TTL"` | 文档工具承载契约。 |

## 17. Shell 脚本

- 以 shebang 开头，并写一个简短的目的块：脚本做什么、接受什么参数、需要什么环境。
- 注释以 `#` 开头且必须开启一个词；`echo value#suffix` 不是注释。
- Shell 没有块注释；`: <<'END' ... END` 这种 here-document 技巧是变通做法，不是约定，且绝不能用它
  包住会执行的命令。
- 在对应行旁边解释不常见的标志、引号要求与错误处理选择，而不是另建一份图例。
- 在设置旁边记录 `set -euo pipefail` 的效果以及任何有意的例外。
- 使用 `# shellcheck disable=SC2086` 这类 linter 指令时给出理由与最窄范围。
- 不要把被注释掉的命令当作用法文档；把预期用法放进 `usage()` 函数或 `--help`。

## 18. 标记语言、CSS 与模板注释

- HTML 注释（`<!-- ... -->`）会发送到浏览器；绝不在其中放机密、个人数据或内部 URL，并在构建工具支持
  时于生产环境剥离它们。
- HTML 注释不能包含 `--`，也不能嵌套；拆分注释或改用其他分隔符。
- CSS 注释只使用 `/* ... */`；`//` 在纯 CSS 中无效，在 Sass/SCSS 中是不会输出的静默注释。
- 在 Sass 中有意选择输出型或静默型：`/* */` 会保留到浏览器，`//` 只给维护者看。
- 模板引擎有自己的语法：Jinja 用 `{# #}`，ERB 用 `<%# %>`，Handlebars 用 `{{! }}`；绝不要在模板中
  用输出语言的语法包裹注释。
- JSX 与 TSX 注释为 `{/* ... */}`；JSX 文本中的裸 `//` 会被渲染成文本。
- 注释用于结构、可访问性意图与条件包含；营销文案与法律声明保留在内容或构建工具中。

## 19. i18n 与本地化注释

- 每个仓库为注释声明一种自然语言，并应用到每个文件；多语言混用的注释是审查缺陷。
- 标识符、API 字段名、协议术语与引用的上游文本保持原语言；绝不在正文中翻译符号名。
- 本地化代码库中，对本地团队需要的领域、监管或法律背景使用声明的语言。
- 不要把注释当作面向用户文本的翻译来源；用户文本属于资源文件与 i18n 键。
- 工具链、编码或终端会破坏非 ASCII 字符时避免使用它们；在重要之处记录编码策略。
- 标点与声明的自然语言保持一致；代码的标识符大小写规则仍然适用。
- 注释引用本地化文档时，引用其路径与节号，而不是可能变化的译文标题。

## 20. 注释中的机密与隐私

- 把注释当作公开内容：它们会随源码、生成的文档、调试符号与包一起发布；绝不在其中放凭据、令牌、密钥
  或连接字符串。
- 被注释掉的代码是常见的泄露渠道；删除前先检查其中是否嵌有凭据。
- 绝不在示例中添加真实姓名、邮箱、电话、地址、客户 ID 或生产 URL；使用 `example.test.invalid` 与
  占位标识符。
- 不要在公开或引入的注释中描述内部网络、服务拓扑或主机名。
- 对注释中的安全事件细节脱敏；指向私有跟踪系统，而不是粘贴报告。
- 在注释中发现机密是一起安全事件：删除它、轮换它，并遵循披露流程；一旦提交，只删那一行是不够的。
- 在 pre-commit hook 与 CI 中扫描机密模式，并把注释纳入检测范围。
- 脱敏时，用 `REDACTED` 这类明显的占位符替换该值；空值会被读成真的不存在。

## 21. 注释密度、行宽、标点与大小写

- 用完整句子写注释，句首大写并带句末标点；每条注释一个想法。
- 遵循项目的行宽限制（常见为 100 或 120 列），续行折到该宽度；绝不重排不相关的注释。
- 块注释与它所描述的代码之间空一行；行尾注释只用于简短的、行内的说明。
- 首词大写，并遵循注释语言的标点；全大写只留给 `NOTE:` 与 `WARNING:` 这类既有标记。
- 避免 ASCII 艺术、横幅分隔线与对齐填充；它们会被格式化工具破坏，并制造 diff 噪音。
- 注释密度取决于意外程度，而不是行数：注释不显而易见的内容；逐行叙述式的过密注释与完全没有注释
  都是审查发现项。
- 工具链要求时保持注释为 ASCII，并删除行尾空白；缩进交给格式化工具。

| 好 | 差 | 原因 |
|---|---|---|
| `// Reuse the pooled client: TLS handshakes dominate this path.` | `// get client` | 解释选择，而不是调用。 |
| `# Start inclusive, end exclusive; empty when start equals end.` | `# range` | 说明读者容易猜错的约定。 |
| `/* The partner API treats 429 as retryable after 30 s. */` | `/* 30 s */` | 把外部约束与取值放在一起。 |

## 22. 过时与说谎的注释

- 错误注释比没有注释更糟；它自信地把读者带向错误方向，是有修复期限的缺陷。
- 每次行为变更都包含注释审查：搜索旧的函数名、参数、默认值、返回类型与错误文本。
- 引用已删除代码、已删除文件、旧版本或失效工单的注释必须删除，不能为了提供上下文而保留。
- 为真但已不再必要的注释（琐碎的重述）也是过时的；代码清晰时删除它。
- 自动化检测：doctest 在 CI 中运行，链接检查器捕获失效引用，文档工具警告只有在 CI 将其升级时才会
  让构建失败（`RUSTDOCFLAGS=-D warnings`、Sphinx `-W`、把 doclint 当作错误）。
- 审查时先读注释再读代码；两者不一致时，这次变更是不完整的。
- 活得比触发条件更久的 TODO 或弃用是错误注释；用定期校验标出逾期标记。
- 注释中引用符号与节号，而不是行号或文件路径；行引用会在下次编辑时腐化。

## 23. 重构与移动注释

- 注释随它所解释的代码一起移动；文档注释属于声明，而不属于调用点或旧文件。
- 抽取函数时，把契约移到新声明，只在调用方保留调用点的理由。
- 内联函数时，只有承诺仍然成立才把它的契约并入周围的文档注释；否则删除它。
- 拆分函数时，按职责拆分它记录的契约；不要把整条注释复制到两半。
- 符号、参数或节移动时更新所有引用：生成的文档链接、锚点与跨文件指针。
- 不要为“保留历史”而保留关于已移动代码的注释；版本控制跟踪移动，过时的副本是谎言。
- 重命名之后，在注释、文档与示例中搜索旧名称；仍在使用旧名称的注释是缺陷。
- 代码移动进生成代码或第三方代码时，删除旧注释，并把理由记录到跟踪系统或设计说明中。

## 24. 注释审查流程

- 在 diff 中阅读每一条新增或修改的注释，并问它保护的是哪一行代码。
- 检查契约：签名、参数、返回值、错误、副作用与边界情况是否仍然一致。
- 检查形式：语法、标签、行宽、自然语言与标记拼写。
- 检查隐患：机密、个人数据、内部地址与被复制的第三方文本。
- 验证文档构建、doctest 与注释 linter；只改注释的变更也要运行它们。
- 移除触发条件已过的标记；把未跟踪的 TODO 变成有链接的 issue，或删除它们。
- 注释与独立文档重复时，链接该文档，只保留读者需要的差异部分。
- 把注释缺陷与行为缺陷分开报告，让作者能看出必须改什么。
